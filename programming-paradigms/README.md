## 프로그래밍 패러다임 · Programming paradigms

문제를 코드로 표현하는 서로 다른 사고방식이에요. 실무에선 여러 패러다임을 섞어 써요.  
*Different ways of expressing problems in code; real projects mix them.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **명령형 vs 선언형**<br><sub>Imperative vs declarative</sub> | 명령형은 "어떻게" 할지 단계별로 지시하고, 선언형은 "무엇을" 원하는지 설명해요.<br><sub>Imperative code says how, step by step; declarative code says what you want.</sub> | SQL, HTML, CSS, React JSX, map/filter가 선언형이에요. 읽기 쉽고 실수가 적지만 내부 동작(성능)은 알고 써야 해요.<br><sub>SQL, HTML, CSS, JSX and map/filter are declarative: easier to read, but know what they do under the hood.</sub> |
| **객체지향 4대 특성**<br><sub>Four pillars of OOP</sub> | 캡슐화, 상속, 다형성, 추상화로 데이터와 동작을 객체 단위로 묶어 복잡도를 다뤄요.<br><sub>Encapsulation, inheritance, polymorphism and abstraction bundle data and behaviour into objects to manage complexity.</sub> | Java·C#·Kotlin·Swift 생태계의 기본이에요. 클래스 계층을 깊게 만들기보다 작은 객체를 조합하는 쪽이 유지보수가 쉬워요.<br><sub>The backbone of Java, C#, Kotlin and Swift codebases; composing small objects usually beats deep class hierarchies.</sub> |
| **캡슐화**<br><sub>Encapsulation</sub> | 객체의 데이터를 숨기고 정해진 메서드로만 바꾸게 해서, 규칙(불변식)을 한곳에서 지켜요.<br><sub>Hide an object’s data and change it only through methods, so its rules (invariants) are enforced in one place.</sub> | getter/setter를 기계적으로 다 만드는 건 캡슐화가 아니에요. "잔액은 음수가 될 수 없다" 같은 규칙을 객체 안에 두세요.<br><sub>Auto-generating getters and setters for everything isn’t encapsulation; keep rules like “balance can’t go negative” inside.</sub> |
| **다형성**<br><sub>Polymorphism</sub> | 같은 메서드 호출이 객체의 실제 타입에 따라 다르게 동작해요.<br><sub>The same method call behaves differently depending on the object’s actual type.</sub> | 타입별 if/switch를 다형성으로 바꾸면 새 타입을 추가해도 기존 코드를 안 고쳐도 돼요(OCP).<br><sub>Replacing type-based if/switch with polymorphism lets you add types without editing existing code (open–closed).</sub> |
| **상속보다 합성**<br><sub>Composition over inheritance</sub> | 상속은 부모의 모든 것을 물려받아 강하게 묶이고, 합성은 필요한 기능을 가진 객체를 조립해요.<br><sub>Inheritance binds a child tightly to everything in its parent; composition assembles objects that provide the needed abilities.</sub> | 상속은 진짜 "is-a" 관계이고 깊이가 얕을 때만 쓰세요. 대부분은 인터페이스 + 합성이 변경에 강해요.<br><sub>Inherit only for genuine, shallow is-a relationships; interfaces plus composition handle change better.</sub> |
| **순수 함수**<br><sub>Pure functions</sub> | 같은 입력엔 항상 같은 출력을 내고, 바깥 상태를 읽거나 바꾸지 않는(부수 효과 없는) 함수예요.<br><sub>A function that always returns the same output for the same input and has no side effects.</sub> | 테스트·캐싱·병렬 처리가 쉬워요. DB·네트워크 같은 부수 효과는 프로그램의 가장자리로 몰고 핵심 로직은 순수하게 두세요.<br><sub>Easy to test, cache and parallelize. Push side effects like DB and network calls to the edges and keep core logic pure.</sub> |
| **불변성**<br><sub>Immutability</sub> | 값을 직접 고치지 않고, 바뀐 새 값을 만들어요. 원본은 그대로 남아요.<br><sub>Instead of changing a value in place, create a new one with the change; the original stays intact.</sub> | React·Redux는 참조 비교로 변경을 감지해서 불변 업데이트가 필수예요. 멀티스레드에서도 공유 데이터 버그를 없애 줘요.<br><sub>React and Redux detect changes by reference, so immutable updates are required; it also removes shared-data bugs in threads.</sub> |
| **고차 함수 · map/filter/reduce**<br><sub>Higher-order functions</sub> | 함수를 인자로 받거나 함수를 돌려주는 함수예요. map·filter·reduce로 데이터 변환을 파이프라인처럼 이어요.<br><sub>Functions that take or return functions; map, filter and reduce chain data transformations like a pipeline.</sub> | 반복문보다 의도가 잘 드러나요. 다만 큰 데이터에서 단계마다 배열을 새로 만드니 성능이 중요하면 측정하세요.<br><sub>Intent reads more clearly than loops, but each step allocates a new array, so measure on large data.</sub> |
| **함수 합성**<br><sub>Function composition</sub> | 작은 함수들을 이어서 새로운 함수를 만들어요. 앞 함수의 출력이 다음 함수의 입력이 돼요.<br><sub>Join small functions into a new one, where each output feeds the next input.</sub> | 유닉스 파이프(cat \| grep \| sort)와 같은 생각이에요. 미들웨어 체인, 데이터 정제 파이프라인에 써요.<br><sub>Same idea as Unix pipes (cat \| grep \| sort); used for middleware chains and data-cleaning pipelines.</sub> |
| **반응형 프로그래밍**<br><sub>Reactive programming</sub> | 이벤트·데이터를 시간에 따라 흐르는 스트림으로 보고, 연산자로 거르고 합치고 변환해요.<br><sub>Treat events and data as streams over time and filter, merge and transform them with operators.</sub> | 자동 완성, 실시간 대시보드, 드래그 처리처럼 비동기 이벤트가 얽힌 곳에 강해요(RxJS, Kotlin Flow). 과하게 쓰면 디버깅이 어려워요.<br><sub>Shines with tangled async events like autocomplete, live dashboards and drag handling (RxJS, Kotlin Flow); overuse hurts debugging.</sub> |
| **논리 프로그래밍**<br><sub>Logic programming</sub> | 사실과 규칙만 선언하면, 질의에 답하는 방법(탐색)은 엔진이 알아서 찾는 패러다임이에요. Prolog가 대표적이에요.<br><sub>Declare facts and rules, and the engine works out how to answer queries by search. Prolog is the classic example.</sub> | parent(tom, bob) 같은 사실과 grand(X, Z) :- parent(X, Y), parent(Y, Z) 같은 규칙을 적고 ?- grand(tom, Who)라고 물으면, 엔진이 변수에 값을 맞춰 보는 단일화(unification)로 증명을 찾고, 백트래킹으로 다른 답(ann, liz)도 찾아 줘요. Datalog는 데이터베이스 질의와 정적 분석에, 비슷한 규칙 엔진은 타입 검사와 권한 정책(OPA)에 쓰여요.<br><sub>Write facts like parent(tom, bob) and rules like grand(X, Z) :- parent(X, Y), parent(Y, Z), then ask ?- grand(tom, Who): the engine builds a proof by unification, binding variables, and backtracks to find every answer (ann, liz). Datalog powers database queries and static analysis, and similar rule engines drive type checkers and policy engines such as OPA.</sub> |
| **커링과 부분 적용**<br><sub>Currying and partial application</sub> | 커링은 인자 여러 개를 받는 함수를 인자 하나씩 받는 함수의 사슬로 바꾸는 것, 부분 적용은 일부 인자를 미리 고정해 새 함수를 만드는 거예요.<br><sub>Currying turns a multi-argument function into a chain of one-argument functions; partial application fixes some arguments up front to make a new function.</sub> | add = a => b => c => a + b + c에서 add(1)은 값이 아니라 b => c => 1 + b + c라는 함수를 돌려주고, 인자가 다 모이면 계산해요. log(level, msg)에 level만 'WARN'으로 고정하면 warn(msg)라는 새 함수가 생겨서, 설정은 한 번 하고 호출은 여러 번 할 수 있어요. map(add(1)), 이벤트 핸들러 팩토리에 흔하고, Haskell은 모든 함수가 자동으로 커링돼요.<br><sub>With add = a => b => c => a + b + c, add(1) returns the function b => c => 1 + b + c, and the sum is computed once every argument arrives. Fixing log(level, msg) at level 'WARN' yields a new warn(msg): configure once, call many times. It shows up in map(add(1)) and handler factories, and in Haskell every function is curried automatically.</sub> |
| **펑터와 모나드**<br><sub>Functors and monads</sub> | map을 가진 “상자”가 펑터, 상자를 돌려주는 단계를 flatMap으로 이어 붙일 수 있는 상자가 모나드예요. Option, List, Promise가 모두 그래요.<br><sub>A functor is a box you can map over; a monad is a box whose steps, each returning a box, chain with flatMap. Option, List and Promise all qualify.</sub> | Some(3).map(x => x \* 2)은 Some(6)이고 None은 건너뛰어요. 리스트도 같은 상자예요. 그런데 상자를 돌려주는 함수(parse: 문자열 → Option)에 map을 쓰면 Some(Some(42))처럼 겹치니, map 후 한 겹 펴는 flatMap을 써요. findUser(id).flatMap(u => u.team).map(t => t.name)처럼 이어 붙이면 중간에 None이 나와도 null 검사 없이 안전하게 흘러가요. Promise의 then, async/await도 같은 모양이에요.<br><sub>Some(3).map(x => x \* 2) is Some(6), while None is skipped; a list is the same kind of box. Mapping a function that itself returns a box (parse: string → Option) nests them, Some(Some(42)), so flatMap maps and flattens one layer. Chains like findUser(id).flatMap(u => u.team).map(t => t.name) then flow safely past a None without null checks. Promise.then and async/await have the same shape.</sub> |
| **클래스 기반 vs 프로토타입 기반**<br><sub>Classes vs prototypes</sub> | 클래스 기반은 설계도(클래스)로 인스턴스를 찍어내고, 프로토타입 기반은 객체가 다른 객체에 직접 연결되어 없는 속성을 위임해요.<br><sub>Class-based languages stamp instances from a blueprint; prototype-based languages link objects directly to other objects and delegate missing properties.</sub> | Java, C++에서는 class Animal로 a1, a2를 만들고 메서드는 클래스에 있어요. JavaScript에서는 dog 객체가 \_\_proto\_\_로 animal 객체에 연결되어, dog.speak()를 부르면 dog에 없으니 animal에서 찾고, 끝내 null까지 없으면 undefined가 돼요. JS의 class 문법은 이 프로토타입 체인 위의 문법 설탕이고, 프로토타입을 바꾸면 위임하는 모든 객체가 바로 영향을 받아요(Lua, Self도 같은 방식).<br><sub>In Java or C++, class Animal produces a1 and a2, and methods live in the class. In JavaScript, dog links via \_\_proto\_\_ to an animal object: dog.speak() isn’t on dog, so the lookup walks up to animal, and if nothing is found by null the result is undefined. JS class syntax is sugar over this prototype chain, and changing a prototype instantly affects every object delegating to it (as in Lua and Self).</sub> |
| **관점 지향 프로그래밍**<br><sub>Aspect-oriented programming</sub> | 로깅, 인증, 트랜잭션처럼 여러 메서드에 흩어지는 횡단 관심사를 “관점(aspect)”으로 떼어내 한 곳에서 관리해요.<br><sub>Pull cross-cutting concerns such as logging, auth and transactions out of the methods they’re scattered across, into “aspects” managed in one place.</sub> | order(), pay(), refund()마다 로그, 권한 검사, 트랜잭션 시작·커밋 코드가 반복되면, 그 부분을 관점으로 빼내고 핵심 로직만 남겨요. 실행 시 프레임워크가 프록시 등으로 호출 앞뒤에 관점 코드를 끼워 넣는데(위빙), Spring의 @Transactional, Python 데코레이터, 웹 미들웨어가 같은 아이디어예요. 대신 메서드만 읽어서는 실제로 무엇이 실행되는지 보이지 않는다는 단점이 있어요.<br><sub>When order(), pay() and refund() each repeat logging, permission checks and transaction begin/commit, move that code into aspects and leave only the business logic. At run time the framework weaves the aspect code around each call, often via a proxy; Spring’s @Transactional, Python decorators and web middleware share the idea. The downside is that reading a method no longer shows everything that runs.</sub> |
| **데이터 지향 설계**<br><sub>Data-oriented design</sub> | 객체 단위가 아니라 “함께 처리되는 데이터”가 메모리에 붙어 있도록 배치해 캐시를 잘 쓰는 설계 방식이에요. AoS 대신 SoA가 대표적이에요.<br><sub>Lay out memory by what gets processed together rather than by object, so the cache is used well. Struct-of-arrays instead of array-of-structs is the classic move.</sub> | 엔티티마다 x, y, hp, name을 모은 구조체 배열(AoS)에서 hp만 줄이는 루프는 캐시 라인을 전부 읽고 그중 1/4만 써요. 필드별로 연속 배열을 두는 SoA로 바꾸면 hp 8개가 캐시 라인 하나에 들어가 읽은 바이트를 모두 쓰고, SIMD로 한 번에 처리하기도 쉬워요. 게임 엔진의 ECS(Unity DOTS, Bevy), 열 지향 DB, Arrow 데이터프레임이 같은 원리예요.<br><sub>In an array of structs (AoS) holding x, y, hp and name per entity, a loop that only decrements hp loads every cache line and uses a quarter of each. Switching to a struct of arrays (SoA), one contiguous array per field, packs 8 hps into one cache line so every loaded byte is used, and SIMD can process them together. Game-engine ECS (Unity DOTS, Bevy), columnar databases and Arrow dataframes apply the same idea.</sub> |
| **제어의 역전 (IoC)**<br><sub>Inversion of control</sub> | 내 코드가 라이브러리를 부르는 대신, 프레임워크가 정해진 흐름 속에서 내 코드를 불러요. “우리가 부를게요”(할리우드 원칙).<br><sub>Instead of your code calling a library, a framework owns the flow and calls your code at the right moments: “don’t call us, we’ll call you.”</sub> | 라이브러리를 쓸 때는 main()이 parse(), sort()를 직접 불러 흐름의 주도권이 내게 있어요. 프레임워크는 시작 → 라우팅 → 렌더링 → 응답이라는 흐름을 쥐고, 내가 등록한 핸들러와 컴포넌트를 알맞은 때에 불러요(app.get('/users', handler)). 콜백, 템플릿 메서드, 이벤트, 의존성 주입이 이를 구현하는 수단이고, 테스트 러너의 @Test, React 렌더링, 서블릿 컨테이너가 모두 제어의 역전이에요.<br><sub>With a library, main() calls parse() and sort() itself, so you own the control flow. A framework runs the flow (start → route → render → respond) and invokes the handlers and components you registered when it decides, as in app.get('/users', handler). Callbacks, template methods, events and dependency injection implement it; test runners (@Test), React rendering and servlet containers are all inversion of control.</sub> |
| **함수형 코어, 명령형 셸**<br><sub>Functional core, imperative shell</sub> | 결정을 내리는 순수한 로직(코어)과 DB·네트워크·시계 같은 I/O(셸)를 분리해, 로직은 값만 주고받게 만드는 구조예요.<br><sub>Separate the pure logic that makes decisions (the core) from I/O such as the database, network and clock (the shell), so the logic only exchanges values.</sub> | DB를 읽고, 현재 시각을 확인하고, 계산하고, 저장하는 코드가 한 함수에 섞여 있으면 테스트에 목이 잔뜩 필요해요. 셸이 db.get과 Date.now()로 입력을 모아 price(cart, now) 같은 순수 함수에 넘기고, 결과대로 db.save를 실행하게 나누면, 코어는 값만 넣고 값만 확인하는 빠른 단위 테스트로 검증할 수 있어요. 헥사고날 아키텍처, Elm·Redux의 리듀서도 같은 분리를 해요.<br><sub>A function that reads the database, checks the clock, computes and saves all at once needs piles of mocks to test. Let the shell gather inputs with db.get and Date.now(), pass them to a pure function like price(cart, now), and act on the result with db.save; the core is then verified by fast unit tests with values in and values out. Hexagonal architecture and Elm/Redux reducers make the same split.</sub> |

## 클린 코드와 리팩터링 · Clean code and refactoring

*Habits for code that others, including future you, can read and change.*

| **의미 있는 이름**<br><sub>Meaningful names</sub> | 변수·함수 이름에 의도와 단위를 담아 주석 없이도 읽히게 해요.<br><sub>Put intent and units into names so code reads without comments.</sub> | 축약어·한 글자 이름은 반복문 인덱스 정도만 허용하세요. boolean은 is·has·can으로, 함수는 동사로 시작해요.<br><sub>Allow one-letter names only for loop indexes. Start booleans with is/has/can and functions with verbs.</sub> |
| **작은 함수**<br><sub>Small functions</sub> | 함수는 한 가지 일만, 한 수준의 추상화로 짧게 써요. 긴 함수는 의미 있는 이름의 작은 함수들로 나눠요.<br><sub>Functions should do one thing at one level of abstraction; split long ones into well-named smaller ones.</sub> | 함수 이름이 "그리고"로 길어지면 나눌 때예요. 작게 나누면 테스트와 재사용이 쉬워져요.<br><sub>If a function name needs “and”, split it; small pieces are easier to test and reuse.</sub> |
| **DRY · KISS · YAGNI**<br><sub>DRY · KISS · YAGNI</sub> | 같은 지식은 한 곳에(DRY), 최대한 단순하게(KISS), 지금 필요 없는 건 만들지 않기(YAGNI).<br><sub>Keep each piece of knowledge in one place (DRY), keep things simple (KISS) and don’t build what you don’t need yet (YAGNI).</sub> | 세 번째 중복이 보일 때 추출하세요(Rule of Three). 우연히 비슷한 코드를 억지로 합치면 오히려 결합이 생겨요.<br><sub>Extract on the third repetition (rule of three); merging merely similar code creates coupling.</sub> |
| **조기 반환 (가드 절)**<br><sub>Guard clauses</sub> | 예외 상황을 함수 앞쪽에서 먼저 처리하고 반환해서, 핵심 로직의 들여쓰기를 얕게 만들어요.<br><sub>Handle edge cases at the top and return early so the main logic stays shallow.</sub> | "화살표 모양" 코드가 보이면 조건을 뒤집어 일찍 반환하세요. 에러 처리 경로도 한눈에 보여요.<br><sub>When you see arrow-shaped code, invert the conditions and return early; error paths become obvious.</sub> |
| **리팩터링**<br><sub>Refactoring</sub> | 외부 동작은 바꾸지 않고 내부 구조를 개선하는 작업이에요. 작은 단계로 나눠 매번 테스트로 확인해요.<br><sub>Improving internal structure without changing external behaviour, in small steps verified by tests.</sub> | 기능 추가와 리팩터링을 같은 커밋에 섞지 마세요. IDE의 자동 리팩터링(이름 변경, 추출)을 쓰면 실수가 줄어요.<br><sub>Keep refactors and features in separate commits, and use IDE automated refactorings to avoid mistakes.</sub> |
| **코드 스멜**<br><sub>Code smells</sub> | 긴 함수, 거대한 클래스, 중복, 긴 매개변수 목록처럼 당장 버그는 아니지만 문제가 생길 징후예요.<br><sub>Long methods, god classes, duplication and long parameter lists: not bugs yet, but signs of trouble.</sub> | 스멜마다 대응하는 리팩터링이 정리되어 있어요(마틴 파울러, 『리팩터링』). 리뷰에서 공통 어휘로 쓰세요.<br><sub>Each smell has a matching refactoring (Martin Fowler’s Refactoring); use them as shared review vocabulary.</sub> |
| **결합도와 응집도**<br><sub>Coupling · Cohesion</sub> | 모듈 사이의 의존(결합)은 약하게, 모듈 안의 관련성(응집)은 강하게 만들어야 변경이 퍼지지 않아요.<br><sub>Keep dependencies between modules loose and relatedness within modules strong, so changes don’t spread.</sub> | "이걸 고치려면 파일 몇 개를 건드려야 하나?"가 결합도의 체감 지표예요. 기능 단위로 폴더를 나누면 응집이 높아져요.<br><sub>“How many files must I touch for this change?” is coupling you can feel; feature-based folders raise cohesion.</sub> |
| **좋은 주석, 나쁜 주석**<br><sub>Good and bad comments</sub> | 코드는 “무엇을·어떻게”, 주석은 “왜”를 말해요. 코드를 반복하는 주석은 소음이고, 설명이 필요하면 먼저 코드를 고쳐요.<br><sub>Code says what and how; comments say why. A comment that repeats the code is noise, and when explanation is needed, improve the code first.</sub> | i++ // i를 1 증가 같은 주석은 지워요. “30일 지나면 만료”를 설명하는 주석은 TRIAL\_DAYS 같은 이름 있는 상수로, 복잡한 조건을 설명하는 주석은 canPay(user) 같은 함수 추출로 대신해요. 반면 “결제사 API가 초당 1회를 넘으면 거절해서 1초 쉰다” 같은 결정의 이유, 경고, 공개 API 문서, 이슈 번호가 달린 TODO는 남길 가치가 있어요. 코드와 함께 고쳐지지 않는 주석은 거짓말이 돼요.<br><sub>Delete comments like i++ // increment i. Replace a comment explaining “expire after 30 days” with a named constant such as TRIAL\_DAYS, and a comment explaining a complex condition with an extracted function like canPay(user). Reasons behind decisions (“the payment API rejects more than one call per second, so wait”), warnings, public API docs and TODOs tied to an issue are worth keeping. Comments that aren’t updated with the code turn into lies.</sub> |
| **플래그 인자와 매개변수 객체**<br><sub>Flag arguments and parameter objects</sub> | render(doc, true, false, 3)처럼 의미 없는 boolean·숫자 인자는 호출부를 읽을 수 없게 만들어요. 함수를 나누거나 이름 있는 매개변수 객체로 바꿔요.<br><sub>Bare boolean and number arguments, as in render(doc, true, false, 3), make call sites unreadable; split the function or pass a named parameter object.</sub> | boolean 플래그 하나는 “이 함수는 두 가지 일을 한다”는 신호라서 renderDraft, renderFinal처럼 나누는 게 좋아요. 인자가 많으면 render(doc, { draft: true, watermark: false, copies: 3 })처럼 매개변수 객체로 묶으면 이름이 붙고 순서를 외울 필요가 없고 항목 추가도 쉬워요. 정의 쪽은 구조 분해와 기본값으로 선택 인자를 표현하고, 이름 있는 인자를 지원하는 언어(Kotlin, Python, Swift)라면 그걸 써도 돼요.<br><sub>A boolean flag signals that the function does two things, so split it into renderDraft and renderFinal. With many arguments, group them into a parameter object: render(doc, { draft: true, watermark: false, copies: 3 }) is named, order-free and easy to extend. On the definition side, destructuring with defaults expresses optional arguments, and languages with named arguments (Kotlin, Python, Swift) solve it directly.</sub> |
| **디미터 법칙**<br><sub>The Law of Demeter</sub> | 메서드는 바로 옆 “친구”에게만 말하고, 낯선 객체의 내부를 줄줄이 따라가지 않아야 한다는 원칙이에요(최소 지식 원칙).<br><sub>A method should talk only to its immediate friends and not reach through the insides of strangers: the principle of least knowledge.</sub> | order.getCustomer().getWallet().pay(total) 같은 “기차 충돌” 코드는 호출자가 Customer와 Wallet의 구조까지 알아야 해서, 어느 하나만 바뀌어도 깨져요. order.pay(total)처럼 시키면 각 객체가 바로 이웃에게만 위임해요(묻지 말고 시켜라). 메서드 안에서는 자기 자신, 매개변수, 직접 만든 객체, 자기 필드의 메서드만 부르는 게 원칙이고, 스트림·빌더처럼 같은 종류를 돌려주는 체이닝은 괜찮아요. 대신 위임 메서드가 늘어나니 균형이 필요해요.<br><sub>Train wrecks like order.getCustomer().getWallet().pay(total) make the caller depend on the structure of Customer and Wallet, so any change breaks it. Telling instead, order.pay(total), lets each object delegate only to its neighbor (tell, don’t ask). Inside a method, call only methods of this, parameters, objects you create and your own fields; fluent chains that return the same kind, such as streams or builders, are fine. The trade-off is more small delegating methods.</sub> |
| **명령-조회 분리 (CQS)**<br><sub>Command–query separation</sub> | 메서드는 값을 돌려주는 조회이거나 상태를 바꾸는 명령이거나, 둘 중 하나만 해야 한다는 원칙이에요(버트런드 마이어).<br><sub>A method should either return a value (a query) or change state (a command), never both, as Bertrand Meyer put it.</sub> | nextId()처럼 값을 돌려주면서 카운터도 올리는 메서드는 log(nextId()) 한 줄만 추가해도 저장되는 ID가 바뀌는 버그를 만들어요. ids.current()(조회)와 ids.advance()(명령)로 나누면 조회는 몇 번 불러도 안전해서 디버깅·캐시·테스트가 쉬워져요. 다만 stack.pop()이나 compareAndSet()처럼 동시성 때문에 읽기와 바꾸기가 한 번에 일어나야 하는 경우는 예외예요. 이 원칙을 아키텍처 수준으로 키운 것이 CQRS예요.<br><sub>A method like nextId() that returns a value and bumps a counter means adding log(nextId()) silently changes which ID gets saved. Splitting it into ids.current() (query) and ids.advance() (command) makes queries safe to repeat, which helps debugging, caching and testing. Exceptions are operations like stack.pop() or compareAndSet(), where concurrency requires reading and changing in one step. Scaled up to architecture, the idea becomes CQRS.</sub> |
| **순환 복잡도**<br><sub>Cyclomatic complexity</sub> | 코드를 지나는 서로 독립인 경로의 수로, 분기가 얼마나 복잡한지 재는 지표예요. 결정 지점 수 + 1로 쉽게 구해요.<br><sub>The number of independent paths through code, a measure of branching complexity, computed simply as decision points + 1.</sub> | if 세 개, for 하나, 삼항 연산자 하나가 있는 grade 함수는 결정 지점이 5개라 M = 6이고, 흐름 그래프의 간선·노드 수로 M = E − N + 2를 계산해도 같아요. 이는 분기를 모두 덮는 데 필요한 테스트 수의 기준이 돼요. 대략 1–10은 단순, 11–20은 복잡, 21 이상은 쪼개야 할 위험 신호예요. 가드 절, 표 조회, 다형성, 함수 추출로 줄이고, ESLint의 complexity 규칙이나 SonarQube가 자동으로 측정해 줘요.<br><sub>A grade function with three ifs, a for loop and a ternary has 5 decision points, so M = 6; computing M = E − N + 2 from the flow graph’s edges and nodes gives the same result, a baseline for how many tests cover every branch. Roughly, 1–10 is simple, 11–20 complex and 21+ a sign to split. Guard clauses, lookup tables, polymorphism and extraction reduce it, and ESLint’s complexity rule or SonarQube measure it automatically.</sub> |
| **계약에 의한 설계**<br><sub>Design by contract</sub> | 함수마다 사전 조건(호출자의 의무), 사후 조건(구현의 약속), 불변식(언제나 참)을 명시하고 어기면 바로 실패하게 하는 설계 방법이에요.<br><sub>State each function’s preconditions (the caller’s duty), postconditions (the implementer’s promise) and invariants (always true), and fail immediately when one is broken.</sub> | withdraw(amount)는 amount > 0, amount ≤ balance를 사전 조건으로 요구하고, 끝나면 balance가 정확히 amount만큼 줄었음을 사후 조건으로 보장하며, balance ≥ 0은 모든 공개 메서드 앞뒤로 지켜지는 불변식이에요. withdraw(-5)처럼 사전 조건을 어기면 호출자 버그, 사후 조건이 깨지면 구현 버그라 책임이 분명해져요. Eiffel에서 시작했고 assert, Kotlin의 require/check로 실천하며, 하위 클래스는 사전 조건을 약하게·사후 조건을 강하게만 바꿀 수 있어요(리스코프).<br><sub>withdraw(amount) requires amount > 0 and amount ≤ balance, guarantees afterwards that balance dropped by exactly amount, and keeps balance ≥ 0 as an invariant around every public call. A call like withdraw(-5) breaks a precondition, so it’s the caller’s bug; a broken postcondition is the implementer’s bug. It began in Eiffel and lives on in assert and Kotlin’s require/check; subclasses may only weaken preconditions and strengthen postconditions (Liskov).</sub> |
