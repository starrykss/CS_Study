## 값과 기본 문법 · Values and core syntax

변수에 무엇이 담기고, 문법이 값을 어떻게 다루는지예요. 자바스크립트에서 가장 자주 헷갈리는 규칙들을 모았어요.  
*What variables hold and how the syntax treats values, collecting the rules that trip people up most often.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **원시 값과 참조**<br><sub>Values and references</sub> | 숫자·문자열 같은 원시 값은 대입할 때 값이 복사되고, 객체·배열·함수는 “가리키는 참조”가 복사돼요.<br><sub>Primitives such as numbers and strings are copied by value on assignment, while objects, arrays and functions copy a reference to the same object.</sub> | let b = a로 숫자를 복사한 뒤 b를 바꿔도 a는 그대로예요. 반면 const p = o로 객체를 대입하면 o와 p가 같은 객체 하나를 가리켜서, p.n을 바꾸면 o.n도 바뀌어요. 함수에 객체를 넘겨 안에서 고치면 호출한 쪽의 원본이 바뀌는 것도 같은 이유예요. ===로 객체를 비교하면 내용이 아니라 같은 객체인지만 따져요. 원시 타입은 string, number, bigint, boolean, undefined, null, symbol 7가지예요.<br><sub>After let b = a copies a number, changing b leaves a alone. Assigning an object with const p = o makes o and p point at one object, so changing p.n changes o.n too. The same reason explains why a function that mutates an object argument changes the caller’s original. === on objects asks whether they are the same object, not whether their contents match. The seven primitives are string, number, bigint, boolean, undefined, null and symbol.</sub> |
| **var·let·const**<br><sub>var, let and const</sub> | var는 함수 단위, let·const는 블록 단위 스코프예요. const는 재할당만 막고 내용 변경은 막지 않아요.<br><sub>var is scoped to the function, let and const to the block; const blocks reassignment but not changes to contents.</sub> | var i로 반복문을 돌며 setTimeout을 걸면, 반복문 전체가 i 하나를 공유해 콜백 셋이 모두 3을 출력해요. let j는 반복마다 새 변수가 생겨서 0, 1, 2가 나와요. const arr = [1]에 push는 되지만 arr = []처럼 다시 넣으면 TypeError예요. 요즘은 기본은 const, 값이 바뀌어야 할 때만 let을 쓰고 var는 쓰지 않아요. 객체 자체를 얼리고 싶다면 Object.freeze를 써요(얕게만 얼어요).<br><sub>Looping with var i and scheduling setTimeout makes the whole loop share one i, so all three callbacks print 3. let j creates a fresh variable per iteration, printing 0, 1 and 2. const arr = [1] still allows push, but arr = [] throws a TypeError. Modern style uses const by default, let only when a value must change, and no var. To freeze the object itself, use Object.freeze, which is shallow.</sub> |
| **호이스팅과 TDZ**<br><sub>Hoisting and the TDZ</sub> | 엔진은 실행 전에 선언을 먼저 등록해요. var는 undefined로 시작하고, let·const는 선언 줄 전까지 TDZ라 접근하면 오류예요.<br><sub>Before running, the engine registers declarations first: var starts as undefined, while let and const sit in the temporal dead zone until their line.</sub> | 선언보다 위에서 var x를 읽으면 오류 없이 undefined가 나와 버그를 숨겨요. let·const도 미리 등록되지만 선언 줄에 닿기 전까지는 일시적 사각지대(TDZ)라 ReferenceError를 내요. function 선언은 본문까지 통째로 올라가 파일 위쪽에서 호출해도 돼요. 반면 const f = () => {} 같은 함수 표현식은 변수 규칙을 따라서 선언 전에 부르면 실패해요. 선언은 쓰는 곳보다 위에 두는 습관이 가장 안전해요.<br><sub>Reading var x above its declaration silently yields undefined, which hides bugs. let and const are registered too, but touching them before their line throws a ReferenceError because they are in the temporal dead zone. Function declarations are hoisted with their bodies, so they can be called from the top of the file. Function expressions such as const f = () => {} follow variable rules and fail if called early. Declaring things before using them is the safest habit.</sub> |
| **== 와 ===**<br><sub>== versus ===</sub> | ==는 타입이 다르면 변환한 뒤 비교하고, ===는 변환 없이 타입과 값이 모두 같아야 true예요.<br><sub>== converts mismatched types before comparing; === requires the same type and value without conversion.</sub> | "" == 0과 "0" == 0은 true지만 "" == "0"은 false라서, ==는 전이 법칙조차 성립하지 않아요. 그래서 거의 항상 ===를 써요. 예외로 x == null은 null과 undefined만 함께 거르는 관용구로 쓰여요. NaN은 자기 자신과도 같지 않아서 NaN === NaN이 false예요. Number.isNaN이나 Object.is(NaN, NaN)로 검사하고, Object.is는 +0과 −0도 구분해요.<br><sub>"" == 0 and "0" == 0 are true but "" == "0" is false, so == is not even transitive. That is why === is the default almost everywhere. The exception is x == null, an idiom that catches both null and undefined. NaN is not equal even to itself, so NaN === NaN is false. Use Number.isNaN or Object.is(NaN, NaN), and note that Object.is also tells +0 from −0.</sub> |
| **truthy와 falsy**<br><sub>Truthy and falsy</sub> | 조건문은 값을 불리언으로 바꿔 판단해요. false가 되는 값은 false, 0, −0, 0n, "", null, undefined, NaN 8개뿐이에요.<br><sub>Conditions convert values to booleans, and only eight values become false: false, 0, −0, 0n, "", null, undefined and NaN.</sub> | “0”, “false”, 빈 배열 [], 빈 객체 {}는 모두 truthy라서 다른 언어에 익숙하면 자주 헷갈려요. count \|\| 10처럼 \|\|로 기본값을 주면 0이나 빈 문자열 같은 정상 값도 기본값으로 덮어써요. ??는 null과 undefined일 때만 기본값을 줘서 0과 “”를 지켜요. if (list.length)처럼 truthy를 짧게 쓰는 건 좋지만, 0이 의미 있는 값이면 명시적으로 비교하세요.<br><sub>"0", "false", an empty array and an empty object are all truthy, which surprises people coming from other languages. A default written as count \|\| 10 overwrites legitimate values such as 0 or an empty string. ?? supplies the default only for null and undefined, so 0 and "" survive. Short truthy checks such as if (list.length) are fine, but compare explicitly when 0 is a meaningful value.</sub> |
| **구조 분해 할당**<br><sub>Destructuring</sub> | 객체나 배열에서 필요한 값만 골라 변수로 꺼내는 문법이에요. 이름 바꾸기, 기본값, 중첩까지 한 줄로 해요.<br><sub>Syntax that pulls just the values you need out of objects and arrays into variables, with renaming, defaults and nesting in one line.</sub> | const { name, age: years = 0 } = user는 name을 꺼내고 age를 years라는 이름으로, 없으면 0으로 받아요. 중첩된 객체도 모양 그대로 써서 깊은 값을 한 번에 꺼내요. 배열은 위치로 꺼내며 쉼표로 건너뛸 수 있어요. 함수 매개변수에 쓰면 옵션 객체를 받기 편하고, [a, b] = [b, a]로 임시 변수 없이 두 값을 바꿔요. 없는 중첩 객체를 분해하면 TypeError이니 기본값 = {}을 함께 줘요.<br><sub>const { name, age: years = 0 } = user takes name, renames age to years, and falls back to 0. Nested objects can be unpacked by writing the same shape. Arrays unpack by position, and commas skip items. In parameters it makes option objects easy to accept, and [a, b] = [b, a] swaps two values without a temporary. Destructuring a missing nested object throws a TypeError, so pair it with a default of {}.</sub> |
| **전개와 나머지**<br><sub>Spread and rest</sub> | ...은 놓인 자리에 따라 반대 역할을 해요. 값 쪽에서는 펼치고(전개), 받는 쪽에서는 남은 것을 모아요(나머지).<br><sub>The same ... does opposite jobs depending on position: it expands values where they are used and gathers the rest where they are received.</sub> | Math.max(...nums)는 배열을 인자 여러 개로 펼쳐요. [...a, 4]는 원본을 바꾸지 않은 새 배열이고, { ...base, theme: "dark" }는 객체를 합치되 같은 키는 뒤의 것이 이겨요. 이 복사는 얕아서 안쪽 객체는 여전히 공유돼요. 매개변수의 (...args)나 const [first, ...rest] = arr에서는 나머지를 배열로 모아요. 나머지는 항상 마지막 자리에만 올 수 있어요.<br><sub>Math.max(...nums) expands an array into separate arguments. [...a, 4] builds a new array without touching the original, and { ...base, theme: "dark" } merges objects with later keys winning. The copy is shallow, so nested objects are still shared. In parameters such as (...args) or in const [first, ...rest] = arr, it gathers the remaining items into an array. A rest element must always come last.</sub> |
| **옵셔널 체이닝과 ??**<br><sub>Optional chaining and ??</sub> | ?.는 앞의 값이 null·undefined면 멈추고 undefined를 돌려주고, ??는 null·undefined일 때만 기본값을 써요.<br><sub>?. stops and returns undefined when the value before it is null or undefined, and ?? applies a default only for null or undefined.</sub> | user.address.city는 address가 없으면 TypeError로 멈춰요. user?.address?.city는 중간이 비어도 undefined로 끝나고, obj.method?.()나 arr?.[0]처럼 호출과 인덱스에도 써요. 여기에 ?? "미정"을 붙이면 깊은 경로 읽기와 기본값이 한 줄이에요. \|\|와 달리 ??는 0과 빈 문자열을 지켜요. 다만 반드시 있어야 할 값에 ?.를 쓰면 버그가 조용히 숨으니, 정말 없을 수 있는 값에만 쓰세요.<br><sub>user.address.city throws a TypeError when address is missing. user?.address?.city ends quietly with undefined, and the same works for calls and indexes, as in obj.method?.() and arr?.[0]. Adding ?? "unknown" reads a deep path and supplies a default in one line. Unlike \|\|, ?? keeps 0 and empty strings. Using ?. on values that must exist hides bugs, so keep it for values that can genuinely be absent.</sub> |

## 함수와 스코프 · Functions and scope

변수가 어디서 보이는지, 함수가 무엇을 기억하는지, this가 어떻게 정해지는지예요.  
*Where variables are visible, what functions remember, and how this gets decided.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **렉시컬 스코프와 스코프 체인**<br><sub>Lexical scope and the scope chain</sub> | 변수가 보이는 범위는 코드를 “어디에 썼는지”로 정해져요. 찾을 때는 안쪽 스코프에서 바깥쪽으로 차례로 올라가요.<br><sub>Where a variable is visible is decided by where the code is written, and lookups climb from the inner scope outward.</sub> | inner 함수 안에서 i를 쓰면 먼저 자기 스코프를 보고, 없으면 감싸는 outer에서 o를, 그래도 없으면 전역에서 g를 찾아요. 이렇게 이어진 사슬이 스코프 체인이에요. 방향은 안에서 밖으로만이라 바깥 코드는 안쪽 변수를 볼 수 없어요. 함수를 어디서 호출했는지가 아니라 어디서 정의했는지가 기준이라서 렉시컬(어휘적) 스코프라고 불러요. 안쪽에서 같은 이름을 다시 선언하면 바깥 변수를 가려요(섀도잉).<br><sub>Using i inside inner checks inner’s own scope first, then finds o in the enclosing outer, then g in the global scope. That chain of scopes is the scope chain. Lookups go only from inside to outside, so outer code cannot see inner variables. Because the rule depends on where a function is defined, not where it is called, it is called lexical scope. Redeclaring the same name inside hides the outer variable, which is called shadowing.</sub> |
| **클로저**<br><sub>Closures</sub> | 함수가 자신이 만들어진 환경(바깥 변수)을 기억해, 바깥 함수가 끝난 뒤에도 그 변수를 쓰는 것이에요.<br><sub>A function remembers the environment it was created in, so it can keep using outer variables after the outer function has returned.</sub> | makeCounter()를 실행하면 count = 0을 담은 환경이 생기고, 돌려준 화살표 함수가 그 환경을 계속 참조해요. 그래서 c1()을 부를 때마다 같은 count가 1, 2, 3으로 올라가지만 밖에서는 count에 직접 손댈 수 없어요. makeCounter를 다시 부르면 새 환경이 생겨 c2는 c1과 따로 세요. 클로저는 비공개 상태, 이벤트 핸들러, 메모이제이션, React 훅의 바탕이에요. 큰 객체를 붙잡은 클로저가 오래 살아 있으면 메모리가 풀리지 않는 점은 주의해요.<br><sub>Calling makeCounter() creates an environment holding count = 0, and the returned arrow function keeps a reference to it. Each call to c1() raises the same count to 1, 2, 3, yet nothing outside can touch count directly. Calling makeCounter again creates a new environment, so c2 counts independently of c1. Closures underpin private state, event handlers, memoization and React hooks. A long-lived closure that holds a large object also keeps that memory from being freed.</sub> |
| **this가 정해지는 규칙**<br><sub>How this is decided</sub> | this는 함수를 정의한 곳이 아니라 “어떻게 호출했는지”로 정해져요. 화살표 함수만 예외로 바깥의 this를 써요.<br><sub>this is set by how a function is called, not where it is defined; arrow functions are the exception and use the outer this.</sub> | obj.hi()처럼 점을 찍어 부르면 this는 점 앞의 obj예요. 같은 함수를 const f = obj.hi로 꺼내 f()로 부르면 점이 없어 this가 undefined(엄격 모드)가 되어 오류가 나요. call·apply·bind로 this를 직접 정할 수 있고, new로 부르면 새로 만든 객체가 this예요. 화살표 함수는 자기 this가 없어 정의된 곳 바깥의 this를 그대로 써요. 우선순위는 new > bind·call > 메서드 호출 > 일반 호출 순이에요.<br><sub>Calling obj.hi() with a dot makes this the object before the dot. Pulling the same function out with const f = obj.hi and calling f() has no dot, so this is undefined in strict mode and the call fails. call, apply and bind set this explicitly, and calling with new makes the newly created object this. Arrow functions have no this of their own and use the one from where they were defined. The precedence is new, then bind or call, then a method call, then a plain call.</sub> |
| **화살표 함수**<br><sub>Arrow functions</sub> | (x) => x \* 2처럼 짧게 쓰는 함수예요. 자기 this·arguments가 없고 바깥 것을 그대로 써서 콜백에 잘 맞아요.<br><sub>A short function syntax such as (x) => x \* 2 that has no this or arguments of its own and borrows the outer ones, which suits callbacks.</sub> | setTimeout에 일반 함수를 넘기면 타이머가 호출하므로 this가 우리 객체가 아니에요. 화살표 함수는 바깥 메서드의 this를 그대로 써서 this.count가 제대로 올라가요. 식 하나면 중괄호와 return을 생략하고, 객체 리터럴을 돌려줄 때는 () => ({ id: 1 })처럼 괄호로 감싸요. new로 생성자를 만들 수 없고 arguments도 없으며, 객체의 메서드로 쓰면 this가 객체가 아니게 돼요. 그런 곳엔 일반 함수나 메서드 문법을 써요.<br><sub>Passing a regular function to setTimeout means the timer calls it, so this is not our object. An arrow function uses the enclosing method’s this, so this.count increments correctly. A single expression drops the braces and return, and an object literal needs parentheses, as in () => ({ id: 1 }). Arrows cannot be constructors, have no arguments, and as object methods their this is not the object. Use regular functions or method syntax there.</sub> |
| **call·apply·bind**<br><sub>call, apply and bind</sub> | 함수의 this를 직접 정해 주는 세 메서드예요. call·apply는 바로 실행하고, bind는 this를 고정한 새 함수를 만들어요.<br><sub>Three methods that set a function’s this explicitly: call and apply run it immediately, while bind returns a new function with this fixed.</sub> | greet.call(kim, "안녕")은 this를 kim으로 정해 즉시 실행하고, apply는 같은 일을 인자 배열로 받아요(지금은 call과 전개 연산자를 더 많이 써요). bind는 실행하지 않고 this와 앞쪽 인자 일부를 고정한 새 함수를 돌려줘서 부분 적용에도 써요. 클래스 메서드를 이벤트 핸들러로 넘길 때 this.onClick.bind(this)로 this를 지켜요. 한 번 bind한 함수는 다시 bind해도 this가 바뀌지 않아요.<br><sub>greet.call(kim, "hi") runs the function at once with this set to kim, and apply does the same with an array of arguments (call plus spread is more common today). bind runs nothing; it returns a new function with this and some leading arguments fixed, which also gives partial application. When handing a class method to an event handler, this.onClick.bind(this) keeps this intact. A bound function ignores later attempts to rebind this.</sub> |

## 이벤트 루프와 비동기 · The event loop and async code

스레드 하나로 기다림을 처리하는 방법이에요. 이벤트 루프, Promise, async/await, 그리고 취소까지 다뤄요.  
*How a single thread handles waiting: the event loop, promises, async/await and cancellation.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **이벤트 루프**<br><sub>The event loop</sub> | 자바스크립트는 콜 스택 하나로 한 번에 한 가지만 실행해요. 기다리는 일은 브라우저에 맡기고, 끝난 콜백은 큐에서 차례를 기다려요.<br><sub>JavaScript runs one thing at a time on a single call stack; waiting is handed to the browser, and finished callbacks wait in a queue.</sub> | log("A"), setTimeout(() => log("B"), 0), log("C")를 실행하면 A, C, B 순서로 찍혀요. setTimeout은 타이머를 브라우저(Web API)에 맡기고 바로 끝나서 C가 먼저 실행돼요. 타이머가 끝난 콜백은 태스크 큐에서 기다리다가, 콜 스택이 완전히 비었을 때 이벤트 루프가 스택에 올려요. 그래서 0ms 타이머도 “최소 0ms 뒤”일 뿐이에요. 스택을 오래 붙잡는 계산이 있으면 클릭과 렌더링도 모두 멈춰요.<br><sub>Running log("A"), setTimeout(() => log("B"), 0) and log("C") prints A, C, B. setTimeout hands the timer to the browser’s Web APIs and returns immediately, so C runs first. When the timer fires, the callback waits in the task queue until the call stack is empty, and then the event loop pushes it onto the stack. A 0 ms timer therefore means “no sooner than 0 ms”. Any computation that holds the stack for long freezes clicks and rendering too.</sub> |
| **마이크로태스크와 태스크**<br><sub>Microtasks and tasks</sub> | 큐는 두 개예요. Promise 콜백은 마이크로태스크 큐로, 타이머·이벤트 콜백은 태스크 큐로 가고, 마이크로태스크가 항상 먼저 다 비워져요.<br><sub>There are two queues: promise callbacks go to the microtask queue and timer or event callbacks to the task queue, and microtasks always drain first.</sub> | 1을 찍고, setTimeout으로 2, Promise.then으로 3, queueMicrotask로 4를 예약하고, 5를 찍으면 출력은 1, 5, 3, 4, 2예요. 동기 코드가 끝나 스택이 비면 이벤트 루프는 마이크로태스크 큐를 끝까지 비운 뒤에야 태스크 하나를 꺼내요. 그래서 0ms 타이머보다 Promise가 먼저예요. 마이크로태스크 안에서 계속 새 마이크로태스크를 만들면 태스크와 렌더링이 영영 밀릴 수 있어요. 렌더링은 보통 태스크 사이에 일어나요.<br><sub>Logging 1, scheduling 2 with setTimeout, 3 with Promise.then and 4 with queueMicrotask, then logging 5 prints 1, 5, 3, 4, 2. Once synchronous code ends and the stack is empty, the event loop drains the entire microtask queue before taking a single task. That is why a promise beats a 0 ms timer. | **Promise의 세 상태**<br><sub>The three states of a promise</sub> | Promise는 아직 끝나지 않은 작업의 결과를 대신하는 객체예요. pending에서 fulfilled나 rejected 중 하나로 단 한 번 바뀌어요.<br><sub>A promise stands in for the result of unfinished work and settles exactly once, from pending to either fulfilled or rejected.</sub> | 처음엔 pending이고, resolve되면 fulfilled가 되어 then 콜백이 값을 받아요. then은 새 Promise를 돌려주므로 .then().then()으로 이어 쓰고, 콜백이 돌려준 값이 다음 단계로 넘어가요. reject되거나 중간 then에서 예외가 나면 rejected가 되어 아래쪽 then들은 건너뛰고 catch가 받아요. finally는 성공·실패와 상관없이 로딩 해제 같은 정리 작업을 해요. 한 번 정해진 상태는 다시 바뀌지 않아요.<br><sub>It starts pending; once resolved it is fulfilled and then callbacks receive the value. then returns a new promise, so calls chain as .then().then(), with each callback’s return value passed to the next step. Once settled, the state never changes.</sub> |
| **async/await**<br><sub>async/await</sub> | async 함수는 항상 Promise를 돌려주고, 그 안의 await는 Promise가 끝날 때까지 그 함수만 잠시 멈춰요. 비동기 코드를 동기 코드처럼 읽게 해 줘요.<br><sub>An async function always returns a promise, and await inside it pauses just that function until a promise settles, so asynchronous code reads like synchronous code.</sub> | async function load() { return 1 }은 1이 아니라 Promise<1>을 돌려줘요. await fetch(url)는 응답이 올 때까지 load 함수만 멈추고, 그동안 이벤트 루프는 다른 일을 계속해요. await한 Promise가 reject되면 그 줄에서 예외가 던져져 try/catch로 잡아요. 서로 기다릴 필요 없는 요청 두 개를 차례로 await하면 시간이 두 배라서, Promise.all로 동시에 시작해요. 반복문 안의 await도 같은 이유로 느려질 수 있어요.<br><sub>async function load() { return 1 } returns Promise<1>, not 1. await fetch(url) pauses only load until the response arrives while the event loop keeps doing other work. Awaiting inside a loop can be slow for the same reason.</sub> |
| **Promise 조합기**<br><sub>Promise combinators</sub> | 여러 Promise를 하나로 묶는 네 가지 방법이에요. all은 모두 성공, allSettled는 모두 끝, race는 먼저 끝난 것, any는 먼저 성공한 것을 기다려요.<br><sub>Four ways to combine promises: all waits for every success, allSettled for everything to finish, race for the first to settle, and any for the first success.</sub> | Promise.all은 모두 성공하면 결과 배열을 주지만 하나라도 실패하면 그 즉시 실패해요(나머지 작업은 계속 돌지만 결과는 버려요). allSettled는 실패와 상관없이 모두 끝날 때까지 기다려 { status, value 또는 reason } 배열을 줘서 일괄 처리 보고에 좋아요. race는 성공이든 실패든 가장 먼저 끝난 것을 따라가 타임아웃 구현에 쓰여요. any는 가장 먼저 성공한 결과를 주고, 모두 실패해야 AggregateError로 실패해요.<br><sub>Promise.all yields an array of results when all succeed but fails the moment any one fails (the others keep running, but their results are discarded). allSettled waits for everything regardless of failures and returns { status, value or reason } entries, which suits batch reports. race follows whichever settles first, success or failure, and is used for timeouts. any yields the first success and fails with an AggregateError only if all fail.</sub> |
| **AbortController로 취소**<br><sub>Cancelling with AbortController</sub> | AbortController의 signal을 fetch나 리스너에 넘겨 두면, abort() 한 번으로 진행 중인 작업을 취소해요.<br><sub>Pass an AbortController’s signal to fetch or listeners, and one abort() call cancels the work in progress.</sub> | 검색창에 빠르게 입력하면 요청이 여러 개 나가고, 늦게 도착한 옛 응답이 최신 결과를 덮어쓰는 경쟁 상태가 생겨요. 새 입력마다 이전 컨트롤러를 abort하면 옛 요청은 AbortError로 끝나 화면을 덮지 않아요. AbortSignal.timeout(5000)은 5초 뒤 저절로 취소되는 signal을 만들어요. addEventListener에 { signal }을 주면 abort 한 번으로 여러 리스너를 함께 해제해요. React의 useEffect 정리 함수에서 abort하는 패턴이 흔해요.<br><sub>Typing quickly into a search box sends several requests, and a stale response that arrives late can overwrite the newest result, a race condition. Aborting the previous controller on each new input ends old requests with an AbortError so they never touch the screen. AbortSignal.timeout(5000) creates a signal that cancels itself after five seconds. Passing { signal } to addEventListener lets one abort remove many listeners at once. Aborting in a React useEffect cleanup function is a common pattern.</sub> |

## 모듈, 브라우저, 런타임 · Modules, the browser and the runtime

코드를 파일로 나누는 법, 브라우저 이벤트와 네트워크, 오류 처리, 숫자와 메모리, 그리고 스레드까지예요.  
*Splitting code into files, browser events and the network, error handling, numbers and memory, and threads.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **ES 모듈과 CommonJS**<br><sub>ES modules and CommonJS</sub> | ES 모듈은 import·export로 파일 사이의 의존을 선언하는 표준이에요. Node.js의 옛 방식인 CommonJS는 require로 실행 중에 불러와요.<br><sub>ES modules are the standard way to declare dependencies between files with import and export; CommonJS, Node.js’s older system, loads with require at run time.</sub> | export로 내보낸 것만 다른 파일에서 import할 수 있고, 파일 하나가 자기만의 스코프를 가져요. import는 파일 맨 위에서 정적으로 선언되어, 번들러가 실행 전에 의존 관계를 읽고 안 쓰는 코드를 빼는 트리 셰이킹이 가능해요. require는 실행 중에 동기로 불러오는 CommonJS 방식이고, package.json에 "type": "module"을 주면 Node.js도 ESM으로 동작해요. import()는 필요한 순간에 모듈을 불러와 Promise로 돌려줘 코드 스플리팅에 써요. 모듈은 한 번만 실행되고 캐시돼요.<br><sub>Only what a file exports can be imported elsewhere, and each file has its own scope. import is declared statically at the top, so bundlers read the dependency graph before running and drop unused code, which is tree shaking. require is CommonJS’s synchronous run-time loader, and "type": "module" in package.json switches Node.js to ESM. import() loads a module when needed and returns a promise, enabling code splitting. A module runs once and is cached.</sub> |
| **이벤트 위임**<br><sub>Event delegation</sub> | 자식마다 리스너를 다는 대신 공통 부모에 하나만 달아, 버블링으로 올라온 이벤트를 처리하는 방법이에요.<br><sub>Instead of a listener on every child, one listener on a common parent handles the events that bubble up to it.</sub> | 목록의 ✕ 버튼을 누르면 클릭 이벤트가 버튼 → li → ul → document로 차례로 올라가요(버블링). 그래서 ul에 리스너 하나만 달고, e.target.closest("li")로 어느 항목인지 찾아 data-id로 대상을 지워요. 리스너 수가 줄어 메모리를 아끼고, 나중에 추가된 항목도 따로 연결할 필요가 없어요. stopPropagation은 위로 올라가는 것을, preventDefault는 링크 이동 같은 기본 동작을 막는데 꼭 필요할 때만 써요. focus처럼 버블링하지 않는 이벤트는 focusin을 써요.<br><sub>Clicking a ✕ button in a list sends the click up through button, li, ul and document, which is bubbling. So one listener on ul suffices: e.target.closest("li") finds the item and its data-id identifies what to remove. Fewer listeners save memory, and items added later need no extra wiring. stopPropagation halts bubbling and preventDefault blocks defaults such as following a link; use them only when needed. For non-bubbling events such as focus, use focusin.</sub> |
| **fetch로 HTTP 요청**<br><sub>HTTP requests with fetch</sub> | fetch는 Promise 기반의 표준 HTTP API예요. 404·500 응답에도 reject하지 않으니 res.ok를 직접 확인해야 해요.<br><sub>fetch is the standard promise-based HTTP API; it does not reject on 404 or 500 responses, so you must check res.ok yourself.</sub> | POST 요청은 method, headers, body 옵션을 주고, 본문은 JSON.stringify로 문자열로 만들어요. 서버가 404나 500을 돌려줘도 fetch는 성공으로 끝나고, 네트워크가 끊겼을 때만 reject해요. 그래서 if (!res.ok) throw로 직접 실패를 처리해요. 본문은 await res.json()으로 한 번 더 기다려 읽고, 같은 본문은 두 번 읽을 수 없어요. 다른 출처로 보내면 CORS 규칙이 적용되고 쿠키를 보내려면 credentials: "include"가 필요해요. 기본 타임아웃이 없으니 AbortSignal.timeout을 함께 써요.<br><sub>A POST passes method, headers and body options, with the body turned into a string by JSON.stringify. Even if the server returns 404 or 500, fetch resolves; it rejects only when the network fails. So handle failures explicitly with if (!res.ok) throw. The body is read with another await, res.json(), and can be read only once. Cross-origin requests follow CORS, and sending cookies needs credentials: "include". There is no default timeout, so pair it with AbortSignal.timeout.</sub> |
| **에러 처리**<br><sub>Error handling</sub> | try·catch·finally로 실패를 잡고, Error를 상속해 종류를 구분하며, 처리되지 않은 Promise 실패는 전역 이벤트로 모아요.<br><sub>Catch failures with try, catch and finally, classify them by extending Error, and collect unhandled promise rejections through a global event.</sub> | try 안에서 예외가 나면 catch로 넘어가고, 처리할 수 없는 종류는 throw e로 다시 던져요. finally는 성공·실패·return과 상관없이 항상 실행돼 로딩 해제 같은 정리에 좋아요. class InputError extends Error로 오류 종류를 나누고 { cause: e }로 원래 오류를 연결하면 디버깅이 쉬워요. await 없이 버려진 Promise의 실패는 try/catch에 잡히지 않고 unhandledrejection 이벤트로만 나타나요. 빈 catch로 오류를 삼키지 말고, API 호출부나 화면 단위 같은 경계에서 모아 처리해요.<br><sub>An exception inside try jumps to catch, and kinds you cannot handle are rethrown with throw e. finally always runs, after success, failure or a return, which suits cleanup such as clearing a loading flag. class InputError extends Error classifies failures, and { cause: e } links the original error for easier debugging. A failing promise that nobody awaits escapes try/catch and surfaces only as an unhandledrejection event. Do not swallow errors with empty catches; handle them at boundaries such as API calls or screens.</sub> |
| **숫자의 함정**<br><sub>Number pitfalls</sub> | 자바스크립트의 number는 모두 64비트 부동소수점이에요. 그래서 0.1 + 0.2가 0.3이 아니고, 2^53보다 큰 정수는 정확하지 않아요.<br><sub>Every JavaScript number is a 64-bit float, so 0.1 + 0.2 is not 0.3 and integers beyond 2^53 lose precision.</sub> | 0.1은 2진수로 딱 떨어지지 않아 0.1 + 0.2는 0.30000000000000004가 되고, 같음 비교는 Number.EPSILON 같은 오차 범위로 해요. Number.MAX\_SAFE\_INTEGER(2^53 − 1)를 넘으면 2 \*\* 53 + 1이 2 \*\* 53과 같아질 만큼 정수도 부정확해서, DB의 64비트 ID는 문자열로 받아요. 큰 정수는 끝에 n을 붙인 BigInt로 다루지만 number와 섞어 계산할 수는 없어요. 금액은 원·센트 단위 정수로 계산하고 Intl.NumberFormat으로 표시해요. NaN은 Number.isNaN으로 검사해요.<br><sub>0.1 has no exact binary form, so 0.1 + 0.2 gives 0.30000000000000004, and equality checks need a tolerance such as Number.EPSILON. Beyond Number.MAX\_SAFE\_INTEGER (2^53 − 1), even integers blur, so 2 \*\* 53 + 1 equals 2 \*\* 53; receive 64-bit database IDs as strings. Large integers use BigInt with a trailing n, which cannot mix with numbers in arithmetic. Compute money in integer units such as won or cents and display it with Intl.NumberFormat. Test for NaN with Number.isNaN.</sub> |
| **가비지 컬렉션과 메모리 누수**<br><sub>Garbage collection and memory leaks</sub> | 가비지 컬렉터는 루트(전역·실행 중인 변수)에서 닿지 않는 객체를 자동으로 치워요. 누수는 안 쓰는데도 여전히 닿는 객체예요.<br><sub>The garbage collector automatically removes objects unreachable from the roots (globals and live variables); a leak is an object that is unused yet still reachable.</sub> | 마크 앤 스윕은 루트에서 출발해 닿는 객체에 표시하고, 표시되지 않은 객체를 치워요. 서로를 가리키는 두 객체라도 루트에서 닿지 않으면 함께 정리돼요. 멈추지 않은 setInterval, 떼지 않은 이벤트 리스너, 끝없이 커지는 캐시는 안 쓰는 객체를 계속 붙잡아 누수가 돼요. clearInterval, abort, removeEventListener로 해제하고, 객체에 덧붙일 정보는 WeakMap에 둬요. DevTools의 Memory 탭에서 힙 스냅숏을 비교하면 늘어나기만 하는 객체를 찾을 수 있어요.<br><sub>Mark-and-sweep starts at the roots, marks every reachable object and sweeps the rest. Two objects that reference each other are still collected if no root reaches them. An uncleared setInterval, a listener never removed or a cache that only grows keeps unused objects alive, which is a leak. Release them with clearInterval, abort or removeEventListener, and keep side data about objects in a WeakMap. Comparing heap snapshots in the DevTools Memory panel reveals objects that only grow.</sub> |
| **웹 워커**<br><sub>Web workers</sub> | 웹 워커는 무거운 계산을 메인 스레드와 별도의 스레드에서 돌려 화면이 멈추지 않게 해요. 둘은 postMessage로만 대화해요.<br><sub>A web worker runs heavy computation on a thread separate from the main thread so the page stays responsive; the two talk only through postMessage.</sub> | 메인 스레드에서 2초짜리 해시 계산을 돌리면 그동안 클릭, 스크롤, 렌더링이 모두 멈춰요. new Worker("hash.js")로 워커를 만들어 데이터를 postMessage로 보내면, 워커가 계산하고 결과를 다시 postMessage로 돌려줘요. 데이터는 복사되어 전달되고, 큰 ArrayBuffer는 transfer로 소유권을 넘겨 복사 비용을 없애요. 워커는 DOM에 접근할 수 없어 계산·파싱·압축·이미지 처리를 맡아요. Node.js에는 worker\_threads가 있어요.<br><sub>Running a two-second hash on the main thread freezes clicks, scrolling and rendering for those two seconds. Creating new Worker("hash.js") and sending it data with postMessage lets the worker compute and post the result back. Data is copied across, while a large ArrayBuffer can be transferred to avoid the copy. Workers cannot touch the DOM, so they take on computing, parsing, compression and image processing. Node.js offers worker\_threads.</sub> |
