## 데이터 모델과 설계 · Data models and design

데이터를 어떤 모양의 표로 나눠 담을지 정하는 단계예요.  
*Deciding how data is split into tables.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **테이블 · 키**<br><sub>Tables · Keys</sub> | 관계형 DB는 데이터를 테이블(행과 열)에 담고, 기본 키로 행을 구분하고, 외래 키로 다른 테이블의 행을 가리켜요.<br><sub>A relational database stores data in tables of rows and columns, identifies rows by primary keys and links tables through foreign keys.</sub> | 기본 키는 의미 없는 값(자동 증가, UUID)을 쓰는 게 안전해요. 외래 키 제약은 잘못된 참조를 DB 차원에서 막아 줘요.<br><sub>Prefer meaningless primary keys (auto-increment, UUID). Foreign key constraints stop bad references at the database level.</sub> |
| **외래 키와 참조 무결성**<br><sub>Foreign keys and referential integrity</sub> | 외래 키는 한 테이블의 열이 다른 테이블의 실제 행을 가리키도록 DB가 보장하는 제약이에요. 부모를 지울 때의 동작과 인덱스가 중요해요.<br><sub>A constraint by which the database guarantees that a column points at a real row in another table. Delete behaviour and indexing are what matter in practice.</sub> | orders.user\_id REFERENCES users(id)를 걸면 존재하지 않는 사용자(예: 99)를 가리키는 주문을 넣는 순간 DB가 외래 키 위반으로 거부해요. 반대로 주문이 있는 사용자를 지우려 할 때는 정책을 골라요. RESTRICT(기본, NO ACTION)는 삭제를 거부하고, CASCADE는 그 사용자의 주문까지 함께 지우고, SET NULL은 주문의 user\_id를 NULL로 바꿔요. CASCADE는 편하지만 삭제 하나가 연쇄적으로 많은 행을 지울 수 있어 신중해야 해요. 부모 행을 지우거나 키를 바꿀 때 DB는 자식 행을 찾아야 하므로 외래 키 열에 인덱스가 없으면 삭제마다 orders 전체를 훑고 잠금도 오래 잡아요. PostgreSQL은 외래 키 열에 인덱스를 자동으로 만들지 않으니(MySQL InnoDB는 만듦) CREATE INDEX ON orders(user\_id)를 직접 추가해요. 대량 적재 때는 부모를 먼저 넣거나 DEFERRABLE 제약으로 커밋 시점까지 검사를 미뤄요. users와 orders가 서로 다른 샤드나 다른 서비스의 DB에 있으면 DB가 참조를 지켜 줄 수 없으므로, 앱에서 존재를 확인하고 고아 행은 배치 작업으로 정리해요.<br><sub>With orders.user\_id REFERENCES users(id), inserting an order for a non-existent user (say 99) is rejected as a foreign-key violation. Deleting a user who still has orders requires a policy: RESTRICT (the default, NO ACTION) refuses, CASCADE deletes the user’s orders too, and SET NULL clears their user\_id. CASCADE is convenient but one delete can ripple through many rows, so use it deliberately. Deleting a parent or changing its key forces the database to find the children, so without an index on the foreign-key column every delete scans the whole orders table and holds locks longer. PostgreSQL does not create that index automatically (MySQL InnoDB does), so add CREATE INDEX ON orders(user\_id) yourself. For bulk loads, insert parents first or make the constraint DEFERRABLE so it is checked at commit. When users and orders live on different shards or in different services’ databases, the database cannot enforce the reference, so the application checks existence and batch jobs clean up orphans.</sub> |
| **정규화**<br><sub>Normalization</sub> | 같은 정보가 여러 곳에 반복되지 않도록 테이블을 쪼개는 과정이에요. 반복이 있으면 일부만 고쳐서 데이터가 어긋나요.<br><sub>Splitting tables so the same fact is not repeated; repetition lets copies drift apart when only some are updated.</sub> | 기본은 3정규형까지 맞추고, 조회가 너무 느린 곳만 일부러 합쳐요(역정규화). 이때는 동기화 책임이 생겨요.<br><sub>Aim for third normal form, then denormalize deliberately only where reads are too slow, accepting the job of keeping copies in sync.</sub> |
| **ER 모델 · 관계**<br><sub>ER model · Relationships</sub> | 엔티티(학생, 과목)와 관계(1:1, 1:N, N:M)를 그림으로 설계해요. N:M 관계는 연결 테이블로 풀어요.<br><sub>Model entities (students, courses) and relationships (1:1, 1:N, N:M) as a diagram; N:M becomes a join table.</sub> | 설계 리뷰 때 ERD를 그려 보면 빠진 관계나 중복을 일찍 찾아요. 연결 테이블에는 관계 자체의 속성(수강일, 성적)을 담아요.<br><sub>Drawing an ERD in design reviews catches missing or duplicate relations early. Join tables can hold attributes of the relationship itself.</sub> |
| **관계 대수**<br><sub>Relational algebra</sub> | 테이블을 받아 테이블을 돌려주는 연산(σ 선택, π 투영, ⋈ 조인 등)의 체계예요. SQL은 이 연산의 식으로 바뀌어 실행·최적화돼요.<br><sub>A set of operators that take tables and return tables (σ select, π project, ⋈ join, …). SQL is compiled into expressions of these operators and optimized.</sub> | σ dept = dev(emp)는 조건에 맞는 행만, π name은 원하는 열만 남기고, emp ⋈ dept는 dept 값이 같은 행끼리 이어 붙여요. 결과도 테이블이라 연산을 자유롭게 조합할 수 있고, SELECT name FROM emp WHERE dept = 'dev'는 π name(σ dept='dev'(emp))와 같아요. 옵티마이저는 이 식을 결과가 같은 더 싼 식으로 바꿔요(예: 선택을 조인 아래로 밀어 내리기).<br><sub>σ dept = dev(emp) keeps matching rows, π name keeps chosen columns, and emp ⋈ dept glues rows with equal dept values. Results are tables too, so operators compose freely: SELECT name FROM emp WHERE dept = 'dev' equals π name(σ dept='dev'(emp)). The optimizer rewrites such expressions into cheaper equivalents, for example pushing selections below joins.</sub> |
| **NULL과 3값 논리**<br><sub>NULL and three-valued logic</sub> | NULL은 값이 아니라 “모름”이라 비교 결과가 TRUE도 FALSE도 아닌 UNKNOWN이 돼요. WHERE는 TRUE인 행만 남겨요.<br><sub>NULL means “unknown”, not a value, so comparisons yield UNKNOWN rather than TRUE or FALSE, and WHERE keeps only TRUE rows.</sub> | age가 NULL인 Lee는 age > 30에도 age <= 30에도 안 나와요. NULL = NULL도 UNKNOWN이라 IS NULL로 검사하고, COALESCE(age, 0)로 기본값을 줘요. x NOT IN (1, NULL)은 항상 빈 결과, COUNT(age)는 NULL을 건너뛰어 COUNT(\*)와 달라요. 가능하면 NOT NULL 제약과 기본값으로 NULL 자체를 줄여요.<br><sub>Lee, whose age is NULL, matches neither age > 30 nor age <= 30. Even NULL = NULL is UNKNOWN, so test with IS NULL and supply defaults with COALESCE(age, 0). x NOT IN (1, NULL) is always empty, and COUNT(age) skips NULLs unlike COUNT(\*). Where possible, avoid NULLs with NOT NULL constraints and defaults.</sub> |

## SQL 기본기 · SQL essentials

데이터를 꺼내고 합치고 요약하는 질의 언어예요.  
*The query language for fetching, combining and summarizing data.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **SELECT 실행 순서**<br><sub>SELECT execution order</sub> | SQL은 SELECT부터 쓰지만 실제로는 FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT 순서로 실행돼요.<br><sub>SQL is written starting with SELECT, but it runs FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT.</sub> | WHERE에서 SELECT의 별칭을 못 쓰는 이유, HAVING과 WHERE의 차이가 모두 이 순서로 설명돼요. 행을 일찍 줄일수록 빨라요.<br><sub>This order explains why WHERE cannot use SELECT aliases and how HAVING differs from WHERE. Filtering rows early is faster.</sub> |
| **조인**<br><sub>JOIN</sub> | 두 테이블에서 키가 같은 행끼리 짝지어 하나의 결과로 합쳐요. INNER는 짝이 있는 것만, LEFT는 왼쪽을 모두 남겨요.<br><sub>Combines two tables by pairing rows with matching keys. INNER keeps only matches; LEFT keeps every left row.</sub> | LEFT JOIN 뒤에 WHERE로 오른쪽 열을 거르면 INNER JOIN처럼 돼 버려요. 조인 키에는 인덱스를 꼭 거세요.<br><sub>Filtering right-side columns in WHERE after a LEFT JOIN silently turns it into an INNER JOIN. Always index join keys.</sub> |
| **GROUP BY · 집계**<br><sub>GROUP BY · Aggregates</sub> | 같은 값을 가진 행을 묶어 COUNT, SUM, AVG 같은 집계로 한 줄씩 요약해요. 묶은 뒤의 조건은 HAVING으로 걸러요.<br><sub>Groups rows with the same value and summarizes each group with aggregates like COUNT, SUM and AVG; HAVING filters groups.</sub> | 대시보드·리포트 쿼리의 대부분이 이것이에요. 큰 테이블에선 미리 집계한 테이블이나 머티리얼라이즈드 뷰를 써요.<br><sub>Most dashboard and report queries are this. On big tables, use pre-aggregated tables or materialized views.</sub> |
| **서브쿼리와 EXISTS**<br><sub>Subqueries and EXISTS</sub> | 쿼리 안의 쿼리예요. 바깥 행의 값을 참조하는 상관 서브쿼리와 EXISTS로 “관련 행이 있는지”를 물을 수 있어요.<br><sub>A query inside a query. Correlated subqueries reference the outer row, and EXISTS asks whether any related row exists.</sub> | WHERE EXISTS (SELECT 1 FROM orders o WHERE o.cust\_id = c.id)는 고객마다 주문이 있는지 확인하고 첫 일치에서 멈춰요(세미 조인). 같은 걸 JOIN으로 쓰면 주문이 여러 건인 고객이 중복돼 DISTINCT가 필요해요. NOT EXISTS는 NULL에도 안전하지만 NOT IN은 NULL이 하나만 있어도 결과가 비어요. 서브쿼리는 스칼라 값, IN/EXISTS, FROM 절의 파생 테이블로 쓸 수 있고, 옵티마이저가 조인으로 바꿔 실행하기도 해요.<br><sub>WHERE EXISTS (SELECT 1 FROM orders o WHERE o.cust\_id = c.id) checks each customer for an order and stops at the first match (a semi-join). Written as a JOIN, customers with several orders repeat and need DISTINCT. NOT EXISTS is NULL-safe, whereas NOT IN returns nothing if any NULL appears. Subqueries work as scalars, with IN/EXISTS or as derived tables in FROM, and optimizers often turn them into joins.</sub> |
| **윈도 함수**<br><sub>Window functions</sub> | 행을 줄이지 않고, 각 행 “주변의 행들”을 보고 순위·누적 합·이전 값 등을 계산하는 함수예요.<br><sub>Functions that compute ranks, running totals, previous values and more over the rows surrounding each row, without collapsing them.</sub> | RANK() OVER (PARTITION BY dept ORDER BY amt DESC)는 부서별로 나눠 매출 순위를 매기고, SUM(amt) OVER 같은 창에서는 누적 합계를 구해요. GROUP BY는 부서마다 한 행으로 접지만, 윈도 함수는 5행을 그대로 두고 열만 더해요. ROW\_NUMBER, LAG/LEAD(이전·다음 행), ROWS BETWEEN으로 이동 평균을 구할 수 있어 부서별 1등, 전월 대비 증감 같은 분석 쿼리의 기본기예요.<br><sub>RANK() OVER (PARTITION BY dept ORDER BY amt DESC) ranks sales within each department, and SUM(amt) over the same window gives a running total. GROUP BY would collapse each department into one row, while window functions keep all rows and add columns. With ROW\_NUMBER, LAG/LEAD and ROWS BETWEEN for moving averages, they underpin queries like top-per-group and month-over-month change.</sub> |
| **CTE와 재귀 쿼리**<br><sub>CTEs and recursive queries</sub> | WITH로 이름 붙은 임시 결과를 만들어 긴 쿼리를 단계별로 나눠요. WITH RECURSIVE는 트리·그래프를 따라가요.<br><sub>WITH names an intermediate result so long queries split into readable steps; WITH RECURSIVE walks trees and graphs.</sub> | 재귀 CTE는 시작 행(앵커)을 고른 뒤, 직전 결과와 테이블을 조인해 다음 단계 행을 만드는 일을 새 행이 없을 때까지 반복해요. boss\_id로 이어진 직원 테이블에서 CEO부터 Kim·Lee, Park, Choi까지 단계(lvl)와 함께 뽑을 수 있어요. 조직도, 카테고리 트리, 그래프 도달 가능성에 쓰이며, 사이클이 있으면 무한 반복할 수 있어 방문 기록이나 깊이 제한을 둬요.<br><sub>A recursive CTE picks starting rows (the anchor), then repeatedly joins the previous result with the table to produce the next level, until no new rows appear. On an employee table linked by boss\_id, it lists the CEO, then Kim and Lee, then Park and Choi, each with a level. It serves org charts, category trees and graph reachability; since cycles can loop forever, track visited rows or cap the depth.</sub> |
| **재귀 쿼리**<br><sub>Recursive queries</sub> | 앵커 행에서 출발해 직전 결과와 테이블을 조인하는 단계를 새 행이 없을 때까지 반복해요. 그래프에 순환이 있으면 경로 기록이나 깊이 제한으로 멈춰요.<br><sub>Starting from an anchor row, the step that joins the previous result with a table repeats until no new rows appear; cycles are stopped with a path record or a depth limit.</sub> | WITH RECURSIVE r AS (앵커 UNION ALL 반복 단계)는 먼저 앵커를 실행해 첫 행을 만들고, 반복 단계가 바로 직전에 생긴 행만 가지고 다음 행을 만드는 일을 새 행이 하나도 나오지 않을 때까지 되풀이해요. 항공편 테이블에서 서울을 앵커(hops 0)로 두면 1단계에 도쿄·베이징, 2단계에 LA와 베이징 경유 도쿄, 3단계에 뉴욕과 LA가 나와요. 그래프에는 도쿄 → 서울 같은 순환이 있어서 그대로 두면 서울 ↔ 도쿄를 끝없이 돌아요. 그래서 지나온 도시를 배열(path)에 쌓고 f.dst <> ALL(r.path)로 이미 방문한 도시를 건너뛰거나, r.hops < 3 같은 깊이 제한을 둬요. PostgreSQL 14부터는 CYCLE city SET is\_cycle USING path 절이 이 일을 대신하고, SEARCH BREADTH FIRST BY로 결과 순서를 너비 우선이나 깊이 우선으로 정할 수 있어요. UNION ALL 대신 UNION을 쓰면 완전히 같은 행은 버려서 반복이 줄어요. 조직도·카테고리 트리, 그래프 도달 가능성, 부품 전개(BOM), 날짜 시퀀스 생성에 쓰고, 큰 그래프에서는 조인 열(f.src)의 인덱스와 깊이 제한이 성능을 좌우해요.<br><sub>WITH RECURSIVE r AS (anchor UNION ALL step) first runs the anchor, then repeatedly runs the step using only the rows produced in the previous round, until a round yields nothing new. With Seoul as the anchor (hops 0) over a flights table, round one finds Tokyo and Beijing, round two LA and Tokyo via Beijing, and round three New York and LA. The graph contains a cycle (Tokyo → Seoul), so left alone the query would bounce between Seoul and Tokyo forever; accumulating visited cities in a path array and filtering with f.dst <> ALL(r.path), or adding a depth limit such as r.hops < 3, stops it. Since PostgreSQL 14 the CYCLE city SET is\_cycle USING path clause does this for you, and SEARCH BREADTH FIRST BY orders results breadth- or depth-first. Using UNION instead of UNION ALL discards identical rows and cuts repetition. Recursive queries serve org charts and category trees, graph reachability, bills of materials and date-series generation, and on large graphs an index on the join column (f.src) plus a depth limit decide performance.</sub> |

## 빠르게 찾는 법 · Finding things fast

느린 쿼리의 대부분은 인덱스와 쿼리 패턴 문제예요.  
*Most slow queries come down to indexes and query patterns.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **인덱스 (B+트리)**<br><sub>Index · B+ tree</sub> | 인덱스는 컬럼 값을 정렬해 둔 트리라서, 전체를 읽지 않고 몇 단계 만에 원하는 행을 찾아요.<br><sub>An index is a sorted tree of column values, so the right row is found in a few steps instead of reading everything.</sub> | EXPLAIN으로 인덱스를 타는지 확인하세요. 인덱스는 쓰기를 느리게 하고 공간을 차지하니 자주 쓰는 조건에만 만들어요.<br><sub>Check with EXPLAIN that queries use it. Indexes slow writes and take space, so add them only for frequent conditions.</sub> |
| **복합 인덱스**<br><sub>Composite index</sub> | 여러 컬럼을 묶은 인덱스는 앞 컬럼 순서대로 정렬돼요. 그래서 앞 컬럼 없이 뒤 컬럼만으로는 인덱스를 쓰기 어려워요.<br><sub>A multi-column index is sorted by its first column, then the next, so it rarely helps a query on a later column alone.</sub> | (last, first) 인덱스는 last 조건, last+first 조건에 쓰이지만 first만으로는 못 써요. 컬럼 순서가 성능을 좌우해요.<br><sub>An index on (last, first) serves “last” and “last + first” queries, but not “first” alone. Column order decides performance.</sub> |
| **N+1 쿼리**<br><sub>N+1 queries</sub> | 목록을 1번 가져온 뒤, 항목마다 관련 데이터를 따로 조회해서 쿼리가 1+N번 나가는 문제예요.<br><sub>Fetching a list once and then querying related data separately for every item: 1 + N queries.</sub> | ORM의 지연 로딩에서 흔해요. 개발 땐 데이터가 적어 모르다가 운영에서 터져요. JOIN, IN 절, fetch join, DataLoader로 묶으세요.<br><sub>Common with ORM lazy loading; invisible with little dev data, painful in production. Batch with JOINs, IN clauses, fetch joins or DataLoader.</sub> |
| **실행 계획 (EXPLAIN)**<br><sub>Execution plans (EXPLAIN)</sub> | 옵티마이저가 쿼리를 어떤 방법(스캔 방식, 조인 순서·알고리즘)으로 실행할지와 그 비용 추정을 보여 줘요.<br><sub>Shows how the optimizer will run a query (scan methods, join order and algorithms) along with its cost estimates.</sub> | 인덱스가 없으면 Seq Scan으로 100만 행을 다 읽고 12행만 남기지만, 인덱스를 만들면 Index Scan으로 바로 찾아가요. 그렇다고 인덱스가 늘 이기진 않아서, 90%의 행이 해당하는 조건이면 무작위 읽기가 많아 순차 스캔을 골라요. 비용 기반 옵티마이저는 통계로 선택도를 추정하니, EXPLAIN ANALYZE로 추정과 실제 행 수를 비교하고 차이가 크면 ANALYZE로 통계를 갱신해요.<br><sub>Without an index, a Seq Scan reads all 1M rows to keep 12; after creating one, an Index Scan jumps straight to them. Indexes don’t always win: if a condition matches 90% of rows, random reads cost more, so the planner picks a sequential scan. A cost-based optimizer estimates selectivity from statistics, so compare estimated and actual rows with EXPLAIN ANALYZE and refresh stale statistics with ANALYZE.</sub> |
| **커버링 인덱스**<br><sub>Covering indexes</sub> | 쿼리에 필요한 열이 모두 인덱스 안에 있어서, 테이블(힙)을 다시 읽지 않고 인덱스만으로 답하는 거예요.<br><sub>Every column a query needs lives in the index, so it is answered from the index alone without revisiting the table (heap).</sub> | (email) 인덱스는 email과 행의 위치만 갖고 있어서 name을 얻으려면 행마다 테이블을 한 번 더 읽어야 해요(무작위 I/O). (email) INCLUDE (name)이나 복합 인덱스 (email, name)로 만들면 인덱스만 읽고 끝나는 Index Only Scan이 돼요. 대신 인덱스가 커지고 쓰기가 느려지니 자주 쓰는 조회에만 쓰고, SELECT \* 대신 필요한 열만 고르는 습관이 이 최적화를 가능하게 해요.<br><sub>An index on (email) stores only email and a row location, so fetching name means one extra table read per row (random I/O). Building (email) INCLUDE (name), or a composite (email, name), turns it into an Index Only Scan. The index grows and writes slow down, so reserve it for hot queries; selecting only needed columns instead of SELECT \* is what makes it possible.</sub> |
| **조인 알고리즘**<br><sub>Join algorithms</sub> | DB는 같은 조인을 중첩 루프, 해시 조인, 정렬 병합 조인 중 하나로 실행해요. 데이터 크기와 인덱스에 따라 비용이 크게 달라요.<br><sub>A database runs a join as a nested loop, a hash join or a sort-merge join, and the cost varies hugely with data size and indexes.</sub> | 중첩 루프는 바깥 행마다 안쪽을 훑어 O(N·M)이지만, 바깥이 작고 안쪽에 인덱스가 있으면 가장 빨라요. 해시 조인은 작은 쪽으로 해시 테이블을 만들고 큰 쪽을 한 번씩 조회해 O(N + M)이지만 메모리가 필요해요. 정렬 병합 조인은 양쪽을 정렬한 뒤 두 포인터로 맞춰 가며, 이미 정렬된 입력이나 범위 조인에 유리해요. 옵티마이저가 통계로 고르고 EXPLAIN에 이름이 나와요.<br><sub>A nested loop scans the inner side for every outer row, O(N·M), yet is fastest with a small outer side and an index on the inner. A hash join builds a hash table from the smaller input and probes it once per row of the larger, O(N + M), but needs memory. A sort-merge join sorts both sides and advances two pointers, ideal for pre-sorted inputs and range joins. The optimizer chooses using statistics, and EXPLAIN names the choice.</sub> |
| **오프셋 vs 커서 페이지네이션**<br><sub>Offset vs cursor pagination</sub> | OFFSET은 건너뛸 행도 모두 읽어서 뒤 페이지일수록 느려요. 마지막으로 본 키에서 이어 읽는 키셋(커서) 방식이 대안이에요.<br><sub>OFFSET reads every skipped row, so later pages get slower; keyset (cursor) paging continues from the last key seen instead.</sub> | LIMIT 20 OFFSET 100000은 10만 행을 읽고 버린 뒤 20행을 돌려줘요. 게다가 읽는 사이 새 글이 끼면 같은 글이 두 번 나오거나 빠져요. WHERE id < :last\_id ORDER BY id DESC LIMIT 20처럼 쓰면 인덱스로 바로 점프해 항상 20행만 읽고 중복도 없어요. 대신 특정 페이지 번호로 바로 갈 수는 없어서, 피드·무한 스크롤·API엔 키셋, 페이지 번호가 필요한 관리 화면엔 OFFSET을 써요.<br><sub>LIMIT 20 OFFSET 100000 reads and discards 100,000 rows to return 20, and posts arriving mid-browse cause duplicates or gaps. WHERE id < :last\_id ORDER BY id DESC LIMIT 20 jumps straight there via the index, always reads 20 rows and never repeats. It can’t jump to an arbitrary page number, so use keysets for feeds, infinite scroll and APIs, and OFFSET for admin screens with page numbers.</sub> |
| **LSM 트리**<br><sub>LSM trees</sub> | 쓰기를 메모리(memtable)에 모았다가 정렬된 파일(SSTable)로 한꺼번에 내리고, 나중에 백그라운드에서 병합(컴팩션)하는 저장 구조예요.<br><sub>A storage structure that buffers writes in memory (the memtable), flushes them as sorted files (SSTables) in bulk, and merges them later in the background (compaction).</sub> | put은 WAL에 덧붙이고 memtable에 넣기만 해서 빨라요. memtable이 차면 순차 쓰기로 SST 파일을 만들고, 쌓인 파일은 컴팩션으로 병합하며 덮어쓴 값과 삭제 표시를 정리해요. 읽기는 memtable → L0 → L1 순으로 확인하고 블룸 필터로 없는 파일을 건너뛰어요. 제자리 수정하는 B+트리보다 쓰기에 강하지만 읽기·쓰기 증폭이 있어요. RocksDB, LevelDB, Cassandra가 써요.<br><sub>A put just appends to the WAL and inserts into the memtable, so it’s fast. A full memtable is written sequentially as an SST file, and compaction merges accumulated files, dropping overwritten values and tombstones. Reads check the memtable, then L0, then L1, skipping files via Bloom filters. It beats in-place B+ trees at writes but pays in read and write amplification. RocksDB, LevelDB and Cassandra use it.</sub> |

## 트랜잭션과 동시성 · Transactions and concurrency

여러 작업을 하나로 묶고, 동시에 일어나는 요청을 안전하게 처리해요.  
*Grouping work into one unit and handling concurrent requests safely.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **ACID**<br><sub>ACID</sub> | 트랜잭션은 원자성, 일관성, 격리성, 지속성을 보장해요. 돈·재고처럼 틀리면 안 되는 데이터의 기본이에요.<br><sub>Transactions guarantee atomicity, consistency, isolation and durability: the baseline for money, stock and anything that must be right.</sub> | 분산 시스템이나 NoSQL은 성능과 확장을 위해 일부를 완화하기도 해요(BASE). 무엇을 포기했는지 알고 써야 해요.<br><sub>Distributed stores and NoSQL may relax some of these (BASE) for scale. Know what was traded away.</sub> |
| **커밋과 롤백**<br><sub>Commit · Rollback</sub> | BEGIN으로 시작한 변경은 COMMIT해야 확정되고, 중간에 실패하면 ROLLBACK으로 모두 되돌려요.<br><sub>Changes after BEGIN become permanent only on COMMIT; if anything fails, ROLLBACK undoes them all.</sub> | 트랜잭션 안에서 외부 API 호출처럼 오래 걸리는 일을 하면 잠금이 길어져요. 트랜잭션은 짧게 유지하세요.<br><sub>Slow work inside a transaction, like external API calls, holds locks for long. Keep transactions short.</sub> |
| **격리 수준**<br><sub>Isolation levels</sub> | 동시에 실행되는 트랜잭션이 서로의 변경을 얼마나 볼 수 있는지 정하는 단계예요. 높을수록 안전하지만 느려요.<br><sub>How much concurrent transactions can see of each other’s changes; higher levels are safer but slower.</sub> | 재고 차감처럼 경합이 있는 곳은 SELECT … FOR UPDATE나 낙관적 락(버전 컬럼)을 함께 써요.<br><sub>For contended updates like stock counts, add SELECT … FOR UPDATE or optimistic locking with a version column.</sub> |
| **MVCC**<br><sub>MVCC · Multiversion concurrency</sub> | 값을 덮어쓰지 않고 새 버전을 만들어, 읽는 트랜잭션은 시작 시점의 스냅숏을 보게 해요. 읽기와 쓰기가 서로를 막지 않아요.<br><sub>Instead of overwriting, writes create new versions and readers see the snapshot from when they started, so reads and writes don’t block each other.</sub> | PostgreSQL, MySQL InnoDB, Oracle이 모두 써요. 오래 열린 트랜잭션은 옛 버전 정리를 막아 테이블이 부풀어요.<br><sub>PostgreSQL, InnoDB and Oracle all use it. A long-open transaction blocks cleanup of old versions and bloats tables.</sub> |
| **WAL · 로그 선행 기록**<br><sub>Write-ahead logging</sub> | 데이터 파일을 고치기 전에 변경 내용을 로그에 먼저 순서대로 기록해요. 서버가 죽어도 로그를 다시 실행해 복구해요.<br><sub>Every change is appended to a log before data files are touched; after a crash the log is replayed to recover.</sub> | 순차 쓰기라 빠르고, 복제·특정 시점 복구(PITR)·CDC도 이 로그를 써요. 디스크 fsync 설정이 지속성을 좌우해요.<br><sub>Sequential writes are fast, and replication, point-in-time recovery and CDC all reuse the log. fsync settings decide real durability.</sub> |
| **잠금과 교착 상태**<br><sub>Locks and deadlocks</sub> | 공유(S)·배타(X) 잠금으로 동시 수정을 막고, 2단계 잠금(2PL)으로 직렬화 가능성을 보장해요. 서로의 잠금을 기다리면 교착 상태가 돼요.<br><sub>Shared (S) and exclusive (X) locks prevent conflicting changes, and two-phase locking (2PL) guarantees serializability. Waiting on each other’s locks causes a deadlock.</sub> | 읽기(S) 잠금끼리는 함께 걸 수 있지만 쓰기(X)는 혼자만 가능해요. 2PL은 잠금을 얻기만 하는 단계와 놓기만 하는 단계를 나누고, 보통 커밋 때 한꺼번에 해제해요. T1이 A를, T2가 B를 잠근 채 서로의 것을 기다리면 대기 그래프에 사이클이 생기고, DB는 이를 감지해 한쪽을 롤백해요. 항상 같은 순서로 잠그고 트랜잭션을 짧게 유지하며, 실패하면 재시도하는 게 예방책이에요.<br><sub>Several readers can hold S locks together, but an X lock is exclusive. 2PL separates a phase that only acquires locks from one that only releases them, usually all at commit. If T1 holds A and T2 holds B while each waits for the other, the wait-for graph has a cycle; the database detects it and rolls one back. Locking in a consistent order, keeping transactions short and retrying on failure prevent it.</sub> |
| **낙관적 vs 비관적 잠금**<br><sub>Optimistic vs pessimistic locking</sub> | 두 사용자가 같은 값을 읽고 고치면 한쪽 변경이 사라져요(갱신 분실). 미리 잠그거나(비관적) 쓸 때 버전으로 확인해(낙관적) 막아요.<br><sub>When two users read and update the same value, one change can vanish (a lost update). Prevent it by locking first (pessimistic) or checking a version at write time (optimistic).</sub> | 재고 10을 A와 B가 동시에 읽고 각각 9로 쓰면 결과는 8이 아니라 9예요. 비관적 잠금은 SELECT … FOR UPDATE로 먼저 잠가 B가 기다리게 하고, 낙관적 잠금은 UPDATE … WHERE version = 5로 쓰고 0행이 바뀌면 다시 읽어 재시도해요. 경합이 잦으면 비관적, 드물거나 사용자가 오래 머무는 웹 폼이면 낙관적이 좋아요. 단순 차감은 SET stock = stock - 1처럼 한 문장으로 처리해요.<br><sub>If A and B both read stock 10 and each write 9, the result is 9 instead of 8. Pessimistic locking takes the lock first with SELECT … FOR UPDATE so B waits; optimistic locking writes with UPDATE … WHERE version = 5 and, if zero rows change, re-reads and retries. Prefer pessimistic under frequent contention and optimistic when conflicts are rare or users linger in web forms. A plain decrement is best done atomically as SET stock = stock - 1.</sub> |

## 더 많은 데이터와 요청 · More data, more requests

한 대로 감당이 안 될 때 쓰는 방법들이에요.  
*What to do when one machine is not enough.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **복제**<br><sub>Replication</sub> | 주 서버의 변경 로그를 복제본에 보내 같은 데이터를 유지해요. 읽기를 나누고, 장애 때 복제본을 승격해요.<br><sub>The primary streams its change log to replicas so they hold the same data; reads are spread out and a replica takes over on failure.</sub> | 비동기 복제는 지연이 있어서 방금 쓴 데이터를 복제본에서 못 읽을 수 있어요. 중요한 읽기는 주 서버로 보내세요.<br><sub>Asynchronous replication lags, so a replica may miss what you just wrote. Send critical reads to the primary.</sub> |
| **샤딩**<br><sub>Sharding</sub> | 데이터를 키 기준으로 나눠 여러 DB 서버에 나눠 담아요. 한 대의 용량과 쓰기 한계를 넘어설 수 있어요.<br><sub>Data is split by key across several database servers to go beyond one machine’s capacity and write limits.</sub> | 샤드 키를 잘못 고르면 한쪽에 몰려요(핫스팟). 샤드 간 조인이 어려워서 최후의 수단으로 쓰고, 먼저 복제·캐시·파티셔닝을 검토하세요.<br><sub>A bad shard key creates hotspots, and cross-shard joins are hard, so treat it as a last resort after replicas, caching and partitioning.</sub> |
| **NoSQL 종류**<br><sub>NoSQL families</sub> | 키-값, 문서, 와이드 컬럼, 그래프처럼 표가 아닌 모양으로 데이터를 저장하는 DB들이에요.<br><sub>Databases that store data in shapes other than tables: key-value, document, wide-column and graph.</sub> | 접근 패턴이 단순하고 규모가 크면 NoSQL이 유리하고, 관계와 트랜잭션이 중요하면 관계형이 유리해요. 둘을 함께 쓰는 경우가 많아요.<br><sub>NoSQL suits simple access patterns at large scale; relational suits rich relations and transactions. Many systems use both.</sub> |
| **캐시 (캐시 어사이드)**<br><sub>Caching · Cache-aside</sub> | 자주 읽는 데이터를 메모리 캐시(Redis 등)에 두고, 없을 때만 DB에서 읽어 채워요.<br><sub>Keep frequently read data in an in-memory cache such as Redis, and read from the database only on a miss.</sub> | 캐시 무효화가 가장 어려워요. TTL을 두고, 데이터가 바뀌면 캐시를 지우세요. 인기 키가 동시에 만료되면 DB가 몰려 죽는 캐시 스탬피드도 조심해요.<br><sub>Invalidation is the hard part: set TTLs and delete on change. Beware stampedes when a hot key expires and everyone hits the database.</sub> |
| **전문 검색과 역색인**<br><sub>Full-text search and inverted indexes</sub> | 단어마다 그 단어가 나오는 문서 목록을 저장한 역색인으로, 문장 속 단어를 빠르게 찾고 관련도 순으로 정렬해요.<br><sub>An inverted index stores, for each term, the documents containing it, so words inside text are found fast and ranked by relevance.</sub> | 문서를 토큰으로 쪼개 db → [d1, d2], lock → [d2, d3]처럼 기록하면, “fast AND lock”은 두 목록의 교집합 [d3]으로 바로 답이 나와요. 분석기가 소문자화, 어간 추출, 불용어 제거를 하고, TF-IDF나 BM25로 순위를 매겨요. LIKE '%lock%'은 B+트리 인덱스를 못 써서 전체를 훑어요. Lucene·Elasticsearch, PostgreSQL tsvector + GIN, MySQL FULLTEXT가 이 구조이고, 한국어는 형태소 분석기나 n-gram으로 토큰을 나눠요.<br><sub>Tokenize documents and record postings such as db → [d1, d2] and lock → [d2, d3]; then “fast AND lock” is just the intersection of two lists, [d3]. Analyzers lowercase, stem and drop stop words, and TF-IDF or BM25 ranks the results. LIKE '%lock%' can’t use a B+ tree index and scans everything. Lucene/Elasticsearch, PostgreSQL tsvector + GIN and MySQL FULLTEXT use this structure; Korean needs a morphological analyzer or n-grams.</sub> |
