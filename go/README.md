| **제로 값과 선언**<br><sub>Zero values and declarations</sub> | Go의 모든 변수는 선언되는 순간 제로 값으로 채워져요. :=로 타입을 추론해 선언하고, nil 슬라이스는 바로 쓰지만 nil 맵에 쓰면 panic이 나요.<br><sub>Every Go variable is filled with its zero value when declared. := declares with an inferred type, and while a nil slice works right away, writing to a nil map panics.</sub> | Go에서는 변수를 선언하면 값을 주지 않아도 그 타입의 제로 값으로 채워져요. 숫자는 0, bool은 false, 문자열은 빈 문자열 "", 포인터·슬라이스·맵·채널·함수·인터페이스는 nil이에요. C에서 초기화하지 않은 지역 변수를 읽으면 쓰레기 값이나 정의되지 않은 동작이 나오지만, Go에는 초기화되지 않은 메모리를 읽는 일이 아예 없어요. 구조체의 제로 값은 모든 필드가 각자의 제로 값인 상태예요. Go 표준 라이브러리는 이 성질을 적극 활용해서, sync.Mutex는 제로 값이 곧 잠기지 않은 뮤텍스이고 bytes.Buffer는 제로 값이 곧 빈 버퍼라서 생성자 없이 바로 쓸 수 있어요. 제로 값이 쓸모 있도록 타입을 설계하라는 것이 Go의 관용구예요. 변수 선언은 var n int처럼 하거나, 함수 안에서는 x := 42처럼 짧은 선언으로 오른쪽 값에서 타입을 추론해요. :=는 왼쪽에 새 변수가 하나 이상 있어야 하고, 같은 범위의 기존 변수는 재사용해요. Go는 선언하고 쓰지 않은 지역 변수와 import를 경고가 아니라 컴파일 오류로 처리해서 코드를 깔끔하게 유지해요. nil에도 차이가 있어요. nil 슬라이스는 길이 0인 빈 슬라이스처럼 동작해서 len이 0이고 append도 바로 돼요. nil 맵은 읽으면 제로 값이 나오고 len도 0이지만, 쓰려고 하면 panic: assignment to entry in nil map이 나요. 그래서 맵은 make(map[string]int)나 리터럴로 만들어서 써요. 상수는 const로 선언하고, iota로 열거형처럼 연속된 값을 만들 수 있어요.<br><sub>In Go, a declared variable is filled with its type’s zero value even without an initializer: 0 for numbers, false for bool, the empty string "" for strings, and nil for pointers, slices, maps, channels, functions and interfaces. Reading an uninitialized local in C yields a garbage value or undefined behavior, but in Go uninitialized memory is never read at all. A struct’s zero value has every field at its own zero value. The standard library leans on this: the zero value of sync.Mutex is an unlocked mutex and the zero value of bytes.Buffer is an empty buffer, so both work immediately without a constructor. Designing types so their zero value is useful is a Go idiom. Variables are declared as in var n int, or inside functions with the short declaration x := 42, which infers the type from the right-hand side. := requires at least one new variable on the left and reuses existing ones in the same scope. Go treats a local variable or import that is declared but unused as a compile error, not a warning, which keeps code clean. nil comes in different flavors. A nil slice behaves like an empty slice of length 0, so len is 0 and append works immediately. A nil map returns zero values on reads and also has len 0, but writing to it panics with assignment to entry in nil map. So maps are created with make(map[string]int) or a literal before use. Constants are declared with const, and iota produces consecutive values much like an enum.</sub> |
| **슬라이스와 append**<br><sub>Slices and append</sub> | 슬라이스는 배열을 가리키는 ptr·len·cap 헤더예요. 잘라 낸 슬라이스는 배열을 공유하고, append는 용량이 남으면 같은 배열에, 꽉 차면 새 배열에 써요.<br><sub>A slice is a ptr, len and cap header over an array. Subslices share the array, and append writes into the same array while capacity remains, or into a new one when full.</sub> | Go의 배열 [5]int는 길이가 타입의 일부인 값이라 대입하거나 함수에 넘기면 통째로 복사돼요. 그래서 실제로는 거의 항상 슬라이스를 써요. 슬라이스 []int는 아래에 있는 배열을 가리키는 포인터, 현재 길이 len, 배열 끝까지의 용량 cap으로 된 24바이트 헤더예요. t := a[1:3]은 새 배열을 만들지 않고 a의 배열 1번 칸을 가리키는 헤더를 만들어서, len은 2이고 cap은 배열 끝까지인 4예요. 문제는 공유에서 생겨요. t = append(t, 99)는 cap이 남아 있으므로 새 배열 없이 t 바로 뒤의 칸에 99를 쓰는데, 그 칸이 바로 a[3]이에요. 그래서 a를 출력하면 [1 2 3 99 5]가 되어, t만 바꿨는데 a도 바뀌어요. 용량이 꽉 찬 상태에서 append하면 더 큰 배열을 새로 할당해 원소를 복사하고 새 헤더를 돌려줘요. 이 환경(Go 1.24)에서 []int에 하나씩 append하면 cap이 1, 2, 4, 8, …, 256, 512, 848, 1280, 1792로 늘었어요. 256까지는 두 배로 늘고, 그 뒤로는 증가율이 점점 1.25배 쪽으로 줄어들며, 할당자의 메모리 크기 등급에 맞춰 반올림되어 848 같은 값이 나와요. append는 원래 배열을 공유하는 슬라이스를 돌려줄 수도, 새 배열의 슬라이스를 돌려줄 수도 있으므로 반드시 s = append(s, x)처럼 결과를 다시 대입해야 해요. 함수가 인자로 받은 슬라이스에 append하면 호출자의 배열을 덮어쓸 수 있으니, 독립된 복사본이 필요하면 slices.Clone이나 copy를 쓰고, 크기를 알면 make([]int, 0, n)으로 용량을 미리 잡아요. a[1:3:3]처럼 세 번째 인덱스로 cap을 제한하면 append가 반드시 새 배열을 쓰게 할 수 있어요.<br><sub>A Go array such as [5]int is a value whose length is part of its type, so assigning it or passing it to a function copies the whole thing, which is why slices are used almost everywhere instead. A slice []int is a 24-byte header holding a pointer to an underlying array, the current length len and the capacity cap up to the array’s end. t := a[1:3] makes no new array; it builds a header pointing at element 1 of a’s array, with len 2 and cap 4, up to the end of the array. Trouble comes from that sharing. t = append(t, 99) has spare capacity, so it writes 99 into the slot right after t without a new array, and that slot is a[3]. Printing a then shows [1 2 3 99 5]: only t was changed, yet a changed too. Appending at full capacity allocates a larger array, copies the elements and returns a new header. In this environment (Go 1.24), appending to a []int one element at a time grew cap through 1, 2, 4, 8 and so on to 256, 512, 848, 1280, 1792. It doubles up to 256, after which the growth rate tapers toward 1.25×, rounded up to the allocator’s size classes, which yields values like 848. Since append may return a slice sharing the original array or one over a new array, its result must always be reassigned, as in s = append(s, x). Appending to a slice received as an argument can overwrite the caller’s array, so use slices.Clone or copy when an independent copy is needed, and when the size is known, reserve capacity up front with make([]int, 0, n). Limiting cap with a third index, as in a[1:3:3], forces append to use a new array.</sub> |
| **맵**<br><sub>Maps</sub> | Go 1.24의 맵은 스위스 테이블이라 8칸 그룹을 한 번에 비교해요. 없는 키는 제로 값을 주고, 순회 순서는 무작위이며, 동시 쓰기는 프로그램을 멈춰요.<br><sub>Go 1.24 maps are Swiss tables that compare an 8-slot group at once. Missing keys yield zero values, iteration order is random, and concurrent writes stop the program.</sub> | Go의 맵은 해시 테이블이고, Go 1.24부터는 구글 Abseil의 스위스 테이블(Swiss Table) 설계로 다시 구현됐어요. 슬롯 8개와 8바이트 제어 워드가 한 그룹을 이루고, 제어 바이트 하나는 해당 슬롯이 비었는지, 지워졌는지, 쓰이는지를 나타내며 쓰이는 슬롯이면 키 해시의 하위 7비트(H2)를 담아요. 조회할 때는 해시의 상위 비트(H1)로 시작 그룹을 고른 뒤, 비트 연산 한 번으로 그룹의 7비트 해시 8개를 동시에 비교하고, 일치한 칸만 실제 키를 비교해요. 그룹에 없으면 이차 탐사로 다음 그룹을 봐요. 테이블은 슬롯 1024개까지는 두 배 크기로 다시 만들고, 그보다 커지면 해시 상위 비트로 테이블을 고르는 확장 해싱으로 둘로 쪼개서, 한 번의 성장이 너무 오래 걸리지 않게 해요. 맵 변수 자체는 이 구조를 가리키는 8바이트 포인터라서, 함수에 넘겨도 같은 맵을 가리켜요. 없는 키를 읽으면 panic 없이 값 타입의 제로 값이 나와요. 그래서 v, ok := m["rust"]처럼 두 번째 결과 ok로 키가 정말 없는지, 값이 0인지 구분하는 comma ok 관용구를 써요. range로 맵을 돌면 순서가 실행할 때마다 달라요. 이 환경에서 같은 맵이 한 번은 abcd, 한 번은 bcda 순으로 나왔어요. 런타임이 일부러 시작 위치를 무작위로 골라서 순서에 기대는 코드가 생기지 않게 하는 것이에요. 순서가 필요하면 키를 slices.Sorted(maps.Keys(m))처럼 정렬해서 써요. 맵은 동시 접근에 안전하지 않아서, 여러 고루틴이 동시에 쓰면 런타임이 감지해 fatal error: concurrent map writes로 프로그램 전체를 멈춰요. 이것은 recover로도 잡을 수 없으므로 sync.Mutex나 sync.RWMutex로 감싸거나, 키가 겹치지 않는 캐시처럼 특수한 경우에는 sync.Map을 써요.<br><sub>Go’s map is a hash table, and since Go 1.24 it has been reimplemented on the Swiss Table design from Google’s Abseil. Eight slots plus an 8-byte control word form a group, and each control byte tells whether its slot is empty, deleted or in use, holding the low 7 bits of the key’s hash (H2) when in use. A lookup uses the hash’s upper bits (H1) to pick a starting group, compares all eight 7-bit hashes in the group at once with a single bitwise operation, and compares actual keys only for matching slots. If the key is not in the group, quadratic probing moves to the next group. A table is rebuilt at double size up to 1,024 slots, beyond which it splits in two using extendible hashing, which picks the table by the hash’s upper bits, so no single growth step takes too long. A map variable itself is an 8-byte pointer to this structure, so passing it to a function shares the same map. Reading a missing key returns the value type’s zero value without panicking, which is why the comma-ok idiom v, ok := m["rust"] uses the second result ok to tell a truly absent key from a value of 0. Ranging over a map gives a different order on each run; here the same map came out once as abcd and once as bcda. The runtime deliberately picks a random starting point so that no code comes to depend on the order. When order matters, sort the keys, as in slices.Sorted(maps.Keys(m)). Maps are not safe for concurrent use: when several goroutines write at once, the runtime detects it and stops the whole program with fatal error: concurrent map writes. Since even recover cannot catch this, wrap maps in a sync.Mutex or sync.RWMutex, or, for special cases such as caches with disjoint keys, use sync.Map.</sub> |
| **문자열과 룬**<br><sub>Strings and runes</sub> | Go 문자열은 읽기 전용 UTF-8 바이트예요. len과 인덱스는 바이트 단위이고, range는 UTF-8을 풀어 룬(코드 포인트) 단위로 돌아요.<br><sub>Go strings are read-only UTF-8 bytes. len and indexing work in bytes, while range decodes UTF-8 and walks rune by rune (code points).</sub> | Go의 문자열은 읽기 전용 바이트 배열을 가리키는 포인터와 길이로 된 16바이트 헤더예요. 문자열을 대입하거나 넘겨도 헤더만 복사되고 바이트는 공유되며, 문자열은 불변이라 공유해도 안전해요. Go 소스 코드는 UTF-8이므로 문자열 리터럴도 UTF-8 바이트로 저장돼요. "Go한글"에서 G와 o는 ASCII라 1바이트씩, 한과 글은 3바이트씩이라 len(s)는 글자 수 4가 아니라 바이트 수 8이에요. s[i]도 i번째 글자가 아니라 i번째 바이트예요. s[2]는 한의 첫 바이트인 0xed이고, s[:3]처럼 바이트 위치로 자르면 글자 중간이 잘려 깨진 문자열이 될 수 있어요. 글자 단위로 다루려면 룬(rune)을 써요. rune은 int32의 별칭으로 유니코드 코드 포인트 하나를 나타내요. for i, r := range s는 UTF-8을 해독하면서 각 룬과 그 룬이 시작하는 바이트 위치를 주므로, 인덱스가 0, 1, 2, 5로 건너뛰어요. []rune(s)로 바꾸면 글자마다 하나씩 4개의 룬 슬라이스가 되고, 글자 수만 필요하면 utf8.RuneCountInString(s)가 할당 없이 세 줘요. 다만 룬도 화면에 보이는 글자 하나와 항상 같지는 않아서, 이모지 조합이나 결합 문자는 여러 룬으로 이루어져요. 문자열은 불변이라 반복문에서 s += x로 이어 붙이면 매번 새 문자열을 할당하고 복사해 O(n²)이 될 수 있어요. 많이 이어 붙일 때는 strings.Builder를 써요. []byte(s)와 string(b) 변환은 보통 복사가 일어나지만, 컴파일러가 복사를 생략할 수 있는 경우도 있어요.<br><sub>A Go string is a 16-byte header holding a pointer to a read-only byte array and a length. Assigning or passing a string copies only the header and shares the bytes, which is safe because strings are immutable. Go source code is UTF-8, so string literals are stored as UTF-8 bytes too. In "Go한글", G and o are ASCII and take one byte each, while each of the two Hangul syllables takes three, so len(s) is 8 bytes, not 4 characters. s[i] is likewise the i-th byte, not the i-th character: s[2] is 0xed, the first byte of the first Hangul syllable, and slicing at byte positions, as in s[:3], can cut a character in half and produce a broken string. To work in characters, use runes. A rune is an alias of int32 representing one Unicode code point. for i, r := range s decodes UTF-8 as it goes, yielding each rune with the byte index where it starts, which is why the indices jump 0, 1, 2, 5. Converting with []rune(s) produces a slice of 4 runes, one per character, and when only the count is needed, utf8.RuneCountInString(s) counts without allocating. Even a rune is not always one visible character, though: emoji sequences and combining marks are made of several runes. Because strings are immutable, appending with s += x in a loop allocates and copies a new string every time and can become O(n²); for heavy concatenation, use strings.Builder. Converting with []byte(s) and string(b) usually copies, though the compiler can elide the copy in some cases.</sub> |
| **구조체와 메서드**<br><sub>Structs and methods</sub> | Go에는 클래스가 없고 리시버가 있는 함수로 메서드를 붙여요. 값 리시버는 복사본, 포인터 리시버는 원본을 다루고, 상속 대신 임베딩으로 조합해요.<br><sub>Go has no classes; methods are functions with receivers. | **탈출 분석**<br><sub>Escape analysis</sub> | Go에서는 컴파일러가 탈출 분석으로 값을 스택에 둘지 힙에 둘지 정해요. 함수 밖으로 새는 포인터가 힙 할당을 부르고, -gcflags=-m으로 판단을 볼 수 있어요.<br><sub>In Go the compiler decides by escape analysis whether values live on the stack or the heap. Pointers that leak out of a function cause heap allocation, and -gcflags=-m shows the decisions.</sub> | Go에는 C의 malloc이나 C++의 new처럼 힙과 스택을 고르는 문법이 없어요. 대신 컴파일러가 탈출 분석(escape analysis)으로 각 값이 함수가 끝난 뒤에도 쓰일 수 있는지를 따져 위치를 정해요. func newUser() \*User가 지역 변수 u의 주소 &u를 반환하면, u는 함수가 끝난 뒤에도 호출자가 쓰므로 스택에 둘 수 없어요. 그래서 컴파일러는 u를 힙으로 옮기고(moved to heap: u), 이 덕분에 Go에서는 C처럼 사라진 스택 프레임을 가리키는 댕글링 포인터가 생기지 않아요. 반대로 xs := make([]int, 8)처럼 함수 밖으로 나가지 않고 크기도 컴파일 때 정해진 값은 스택에 놓여요. 스택 할당은 스택 포인터를 옮기는 것으로 끝나고, 함수가 끝나면 아무 비용 없이 사라지며, GC가 신경 쓸 필요도 없어요. 이 환경에서 newUser는 호출마다 할당 1번, 같은 크기의 슬라이스를 쓰는 sum은 0번이었어요. 크기가 변수인 make([]int, n)이나 너무 큰 값은 힙으로 가요. 24바이트 구조체 하나를 힙에 할당하는 데 약 18ns가 걸렸고 스택에서는 거의 0이었는데, 힙 객체는 나중에 GC가 추적해야 하므로 실제 비용은 더 커요. 값이 힙으로 가는 흔한 원인은 지역 변수의 포인터 반환, 인터페이스로의 변환(fmt.Println의 인자 등), 클로저의 변수 캡처, 크기를 알 수 없는 슬라이스예요. go build -gcflags=-m을 쓰면 컴파일러가 줄마다 무엇을 왜 힙으로 보냈는지 출력해요. 다만 모든 할당을 없애려 할 필요는 없고, 프로파일링으로 찾은 뜨거운 경로에서 벤치마크의 -benchmem이 보여 주는 allocs/op를 줄이는 데 집중해요.<br><sub>Go has no syntax for choosing heap or stack like C’s malloc or C++’s new. Objects still white at the end are unreachable from anywhere and are reclaimed in the sweep phase. The key point is that marking proceeds concurrently with the program. So that no object is missed while the program changes pointers, a write barrier reports changed pointers to the GC. | **늘어나는 스택**<br><sub>Growable stacks</sub> | 고루틴 스택은 2KB로 시작해, 모자라면 2배 크기로 통째로 복사하며 자라요. 그래서 고루틴을 수십만 개 만들 수 있고, 한도는 1GB예요.<br><sub>Goroutine stacks start at 2 KB and grow by copying into a stack twice the size. The compiler inserts a few instructions at the entry of almost every function to check whether the current stack has room for that function’s frame. If there is enough room, execution continues; otherwise the runtime’s morestack is called. | **메모리 할당기**<br><sub>The memory allocator</sub> | Go 할당기는 요청을 68개 크기 등급으로 나누고 P마다 캐시를 둬서 대부분 락 없이 할당해요. 16B 미만은 모아 담고, 32KB 초과는 페이지를 바로 받아요.<br><sub>Go’s allocator splits requests into 68 size classes and keeps a cache per P, so most allocations take no lock. Tiny objects are packed together, and anything over 32 KB gets pages directly.</sub> | Go의 메모리 할당기는 구글의 TCMalloc을 바탕으로 고루틴이 많은 환경에 맞게 다듬은 설계예요. 먼저 크기 등급(size class)이 있어요. 할당 요청은 8바이트부터 32KB까지 미리 정한 68개 등급 중 요청보다 크거나 같은 가장 작은 등급으로 올림돼요. 24바이트 구조체는 24 등급에, make([]byte, 1000)은 1024 등급에 들어가요. 같은 등급의 객체는 8KB 페이지 여러 장으로 된 span을 나눠 쓰므로, 서로 다른 크기가 섞여 생기는 조각화가 줄고, 객체 위치를 계산하기도 쉬워요. 다음은 계층 구조예요. 각 P에는 mcache가 있어서 등급마다 비어 있는 칸이 있는 span을 하나씩 들고 있어요. 고루틴이 할당하면 자기 P의 mcache에서 다음 빈칸을 주므로 대부분의 할당은 락 없이 끝나요. mcache의 span이 꽉 차면 등급별 공유 저장소인 mcentral에서 새 span을 받고, mcentral도 모자라면 페이지를 관리하는 mheap에서, mheap도 모자라면 운영체제에서 메모리를 받아요. 16바이트보다 작고 포인터가 없는 객체는 tiny 할당기가 16바이트 블록 하나에 여러 개를 이어서 담아요. 작은 문자열이나 정수를 인터페이스에 담을 때 생기는 작은 객체가 많아서 효과가 커요. 32KB를 넘는 큰 객체는 등급을 거치지 않고 mheap에서 필요한 페이지를 바로 받아요. 이 환경의 벤치마크에서 24바이트 객체 할당은 약 18ns, 1KB 바이트 슬라이스는 0으로 채우는 시간까지 포함해 약 360ns였어요. 할당 자체는 빠르지만, 할당이 많을수록 GC가 더 자주 돌고 더 많이 추적해야 하므로, 성능 최적화의 첫 단계는 대개 할당 수를 줄이는 거예요.<br><sub>Go’s memory allocator is based on Google’s TCMalloc, refined for environments with many goroutines. First come size classes. An allocation request is rounded up to the smallest of 68 predefined classes, from 8 bytes to 32 KB, that fits it. A 24-byte struct goes into class 24, and make([]byte, 1000) into class 1024. Objects of the same class share spans made of 8 KB pages, which reduces the fragmentation caused by mixing sizes and makes object positions easy to compute. Next comes a hierarchy. Each P has an mcache holding, for every class, one span with free slots. When a goroutine allocates, its P’s mcache hands out the next free slot, so most allocations finish without a lock. When an mcache span fills up, it takes a new span from mcentral, the shared store for that class; when mcentral runs short, it asks mheap, which manages pages; and when mheap runs short, it gets memory from the operating system. Large objects over 32 KB skip the classes and take the pages they need straight from mheap. The go.mod file at the module’s root records the module path, the Go version it needs, and, under require, the modules it depends on and their versions. Versions follow semantic versioning (SemVer), as in v1.4.0. Go’s version selection differs from other languages’ package managers. npm or pip usually pick the newest version satisfying the constraints and pin the result in a lock file, but Go uses Minimal Version Selection (MVS). | **워커 풀과 파이프라인**<br><sub>Worker pools and pipelines</sub> | 워커 풀은 고정된 수의 고루틴이 작업 채널을 나눠 처리해 동시성의 상한을 정해요. 종료는 보내는 쪽이 채널을 닫아 range를 따라 전해요.<br><sub>In a worker pool, a fixed number of goroutines share a job channel, capping concurrency. Termination travels as senders close channels and ranges end in turn.</sub> | 고루틴은 싸지만, 작업마다 고루틴을 하나씩 만들면 작업이 수만 개일 때 동시에 열리는 DB 연결, 파일, 메모리, 외부 API 호출이 감당할 수 없을 만큼 늘어나요. 워커 풀은 정해진 수의 고루틴만 띄우고, 각 워커가 jobs 채널에서 작업을 꺼내 처리한 뒤 results 채널로 결과를 보내게 해서 동시에 도는 일의 수에 상한을 둬요. 이 환경에서 10ms씩 걸리는 작업 100개를 워커 4개로 처리하자 258ms가 걸렸어요. 하나씩 순서대로 했다면 약 1초가 걸렸을 것이므로 거의 4배 빨라진 거예요. 워커 수는 병목이 되는 자원에 맞춰요. CPU를 많이 쓰는 일이면 코어 수 정도, I/O를 기다리는 일이면 외부 시스템이 견딜 수 있는 동시 요청 수에 맞춰요. 워커 풀에서 가장 헷갈리는 부분은 언제 무엇을 닫느냐예요. 규칙은 채널은 보내는 쪽이 닫는다는 거예요. 작업을 다 보낸 생산자가 close(jobs)를 하면 워커들의 for j := range jobs가 끝나고 각자 wg.Done()을 불러요. 결과 채널은 여러 워커가 함께 보내므로 어느 워커도 혼자 닫을 수 없어서, 별도 고루틴이 wg.Wait()로 모든 워커가 끝나기를 기다린 뒤 close(results)를 해요. 그러면 결과를 받는 쪽의 range도 자연스럽게 끝나요. 이 구조를 단계별로 이으면 각 단계가 채널로 연결된 파이프라인이 되고, 한 채널을 여러 워커가 나눠 읽는 팬아웃과 여러 결과를 하나로 모으는 팬인을 조합할 수 있어요. 실무에서는 golang.org/x/sync/errgroup을 많이 써요. g.SetLimit(4)로 동시 실행 수를 제한하고, 한 작업이 오류를 내면 context를 취소해 나머지를 멈추며, g.Wait()가 첫 오류를 돌려줘요.<br><sub>Goroutines are cheap, but creating one per task can, with tens of thousands of tasks, open more database connections, files, memory and external API calls than can be handled at once. A worker pool starts only a fixed number of goroutines, each taking tasks from the jobs channel, processing them and sending results to the results channel, which caps how much work runs at once. In this environment, 100 tasks of 10 ms each took 258 ms with 4 workers. Doing them one at a time would have taken about 1 s, so this is nearly 4× faster. The worker count is matched to the bottleneck resource: about the core count for CPU-heavy work, or the number of concurrent requests an external system can bear for work that waits on I/O. The most confusing part of a worker pool is what to close and when. The rule is that channels are closed by their senders. When the producer has sent all tasks it calls close(jobs), which ends each worker’s for j := range jobs, and each calls wg.Done(). Since several workers send on the results channel, no single worker can close it, so a separate goroutine waits with wg.Wait() for all workers to finish and then calls close(results). The consumer’s range over results then ends naturally. Chaining this structure in stages produces a pipeline whose stages are connected by channels, combining fan-out, where several workers share one channel, with fan-in, where several results merge into one. In practice golang.org/x/sync/errgroup is popular: g.SetLimit(4) limits concurrency, an error in one task cancels a context to stop the rest, and g.Wait() returns the first error.</sub> |
| **encoding/json**<br><sub>encoding/json</sub> | encoding/json은 리플렉션으로 구조체 태그를 읽어 JSON 키를 정해요. 소문자 필드는 무시되고, nil 슬라이스는 null이 되며, 모르는 필드는 조용히 버려져요.<br><sub>encoding/json reads struct tags by reflection to name the JSON keys. Lowercase fields are ignored, nil slices become null, and unknown fields are dropped silently.</sub> | encoding/json은 Go 값과 JSON 사이를 변환하는 표준 패키지예요. json.Marshal은 리플렉션으로 구조체의 필드를 살펴보고, 각 필드에 붙은 `json:"..."` 구조체 태그로 JSON 키 이름을 정해요. 태그가 없으면 필드 이름이 그대로 키가 돼요. 이 환경에서 User{ID: 1, Name: "Kim"}을 Marshal하자 {"id":1,"name":"Kim","tags":null}이 나왔어요. 소문자로 시작하는 pass 필드는 내보내지지 않은 필드라서 json 패키지가 볼 수 없으므로 출력에서 아예 빠졌어요. 비밀번호 같은 값이 실수로 나가지 않는 장점이 있지만, 반대로 소문자 필드에 태그를 붙여도 동작하지 않는다는 점을 기억해야 해요. 태그의 omitempty 옵션은 필드가 제로 값이면 키를 출력하지 않아서, 빈 Email은 결과에 없어요. 함정은 슬라이스예요. nil 슬라이스인 Tags는 빈 배열 []가 아니라 null로 출력되어, 배열을 기대하는 프런트엔드 코드에서 오류를 내기 쉬워요. 빈 배열이 필요하면 []string{}로 초기화해요. json.Unmarshal은 반대 방향이에요. JSON의 타입이 필드와 맞지 않으면 이 환경에서처럼 cannot unmarshal string into Go struct field User.id of type int 오류를 내요. 하지만 구조체에 없는 age 같은 필드는 오류 없이 조용히 무시돼서, 오타 난 키가 그냥 사라질 수 있어요. 엄격하게 검사하려면 json.NewDecoder(r).DisallowUnknownFields()를 써요. HTTP 요청 본문이나 큰 파일은 전체를 메모리에 읽지 않고 json.NewDecoder로 스트림에서 바로 해석하고, 응답은 json.NewEncoder(w)로 바로 써요. 시간 형식이나 열거형처럼 표현을 직접 정하고 싶은 타입에는 MarshalJSON과 UnmarshalJSON 메서드를 구현해요. 리플렉션 기반이라 아주 빠르지는 않아서, 처리량이 중요하면 코드 생성 방식의 라이브러리를 고려하기도 해요.<br><sub>encoding/json is the standard package for converting between Go values and JSON. json.Marshal inspects a struct’s fields by reflection and names each JSON key from the `json:"..."` struct tag on the field, falling back to the field name when there is no tag. Here, marshaling User{ID: 1, Name: "Kim"} produced {"id":1,"name":"Kim","tags":null}. The pass field, starting with a lowercase letter, is unexported, so the json package cannot see it and it was left out of the output entirely. That keeps values such as passwords from leaking by accident, but it also means that tagging a lowercase field does nothing. The omitempty tag option omits a key when the field holds its zero value, so the empty Email is absent from the result. The trap is slices: Tags, a nil slice, is output as null rather than an empty array [], which easily breaks front-end code expecting an array. When an empty array is wanted, initialize it with []string{}. json.Unmarshal goes the other way. When a JSON type does not match the field, it fails with an error such as cannot unmarshal string into Go struct field User.id of type int, as it did here. But fields missing from the struct, such as age, are silently ignored without error, so a mistyped key can simply vanish. For strict checking, use json.NewDecoder(r).DisallowUnknownFields(). HTTP request bodies and large files are parsed straight from the stream with json.NewDecoder instead of being read fully into memory, and responses are written directly with json.NewEncoder(w). Types whose representation you want to control, such as time formats or enums, implement MarshalJSON and UnmarshalJSON methods. Being reflection-based, the package is not especially fast, so code-generating libraries are sometimes considered when throughput matters.</sub> |
| **반복자**<br><sub>Iterators</sub> | Go 1.23의 반복자는 yield를 부르는 함수예요. for range에 함수를 넘길 수 있고, break하면 yield가 false를 돌려줘 반복자가 멈춰요.<br><sub>Go 1.23 iterators are functions that call yield. Functions can be passed to for range, and on break yield returns false so the iterator stops.</sub> | Go 1.23은 사용자 정의 반복자를 언어에 넣었어요. 특별한 인터페이스가 아니라 함수예요. iter.Seq[V]는 func(yield func(V) bool) 타입이고, 원소를 두 개씩 주는 iter.Seq2[K, V]도 있어요. 반복자는 원소마다 yield(v)를 불러 값을 하나씩 밀어 넣는 방식이에요(push iterator). Count(n)은 0부터 n-1까지 yield(i)를 부르는 함수를 돌려줘요. 이런 함수를 for i := range Count(10)처럼 for range에 바로 쓸 수 있어요. 컴파일러는 루프 몸체를 yield 함수로 바꿔 반복자에 넘기므로, 반복자를 만드는 쪽도 쓰는 쪽도 평범한 반복문처럼 코드를 읽을 수 있어요. 예전에는 트리나 사용자 정의 컬렉션을 순회하려면 슬라이스로 모두 복사해서 돌려주거나, 콜백을 받거나, 채널과 고루틴을 써야 했는데, 각각 메모리 낭비, 조기 종료의 어려움, 고루틴 비용이라는 단점이 있었어요. 반복자의 핵심 규칙은 yield의 반환값이에요. 루프에서 break나 return으로 빠져나가면 다음 yield 호출이 false를 돌려줘요. 반복자는 이를 확인해 즉시 return해야 하고, 계속 yield를 부르면 런타임이 panic을 내요. 이 환경에서도 i가 3일 때 break하자 반복자가 3에서 멈췄다는 메시지를 찍었어요. 파일이나 DB 커서를 쓰는 반복자라면 이 시점에 자원을 정리해요. 표준 라이브러리에는 maps.Keys, maps.Values, maps.All, slices.All, slices.Values, slices.Backward 같은 반복자와, 반복자를 받는 slices.Collect, slices.Sorted, maps.Collect가 추가됐어요. slices.Sorted(maps.Keys(m))는 맵의 키를 정렬된 슬라이스로 만들어 이 환경에서 [a b c]를 돌려줬어요. 두 반복자를 번갈아 읽는 것처럼 당기기 방식이 필요하면 iter.Pull이 next() 함수로 바꿔 줘요.<br><sub>Go 1.23 brought user-defined iterators into the language, and they are functions rather than a special interface. iter.Seq[V] is the type func(yield func(V) bool), and iter.Seq2[K, V] yields pairs. An iterator pushes values one at a time by calling yield(v) for each element (a push iterator). Count(n) returns a function that calls yield(i) for 0 through n-1. Such a function can be used directly with for range, as in for i := range Count(10). The compiler turns the loop body into a yield function and passes it to the iterator, so both the code that makes the iterator and the code that uses it read like ordinary loops. Previously, traversing a tree or custom collection meant copying everything into a slice, taking a callback, or using a channel and goroutine, with the respective drawbacks of wasted memory, awkward early exit and goroutine cost. The key rule of iterators is yield’s return value. Leaving the loop with break or return makes the next yield call return false. The iterator must check this and return immediately; calling yield again makes the runtime panic. Here too, breaking when i was 3 made the iterator print a message that it stopped at 3. Iterators holding files or database cursors release them at this point. The standard library added iterators such as maps.Keys, maps.Values, maps.All, slices.All, slices.Values and slices.Backward, along with consumers such as slices.Collect, slices.Sorted and maps.Collect. slices.Sorted(maps.Keys(m)) turned the map’s keys into a sorted slice, returning [a b c] here. When a pull style is needed, such as reading two iterators alternately, iter.Pull converts one into a next() function.</sub> |
| **우아한 종료**<br><sub>Graceful shutdown</sub> | 종료 신호를 context 취소로 받고 Server.Shutdown을 부르면, 새 연결은 막고 진행 중인 요청은 끝까지 처리한 뒤 멈춰요.<br><sub>Receive the termination signal as context cancellation and call Server.Shutdown: new connections are refused while in-flight requests run to completion before the server stops.</sub> | 서버는 배포나 확장 때문에 수시로 재시작돼요. 쿠버네티스 같은 환경은 파드를 멈출 때 먼저 SIGTERM 신호를 보내고, 일정 시간(기본 30초)이 지나도 끝나지 않으면 SIGKILL로 강제 종료해요. 신호를 받자마자 프로세스가 죽으면 처리 중이던 요청이 끊겨 사용자에게 오류가 가므로, 진행 중인 일을 마무리하고 멈추는 우아한 종료가 필요해요. Go에서는 signal.NotifyContext(ctx, syscall.SIGTERM, os.Interrupt)로 신호를 context 취소로 바꿔 받아요. 서버는 고루틴에서 ListenAndServe로 돌리고, 메인 고루틴은 <-ctx.Done()에서 신호를 기다려요. 신호가 오면 srv.Shutdown(sctx)를 불러요. Shutdown은 먼저 모든 리스너를 닫아 새 연결을 받지 않고, 쉬고 있는 연결을 닫은 뒤, 처리 중인 요청이 끝나 연결이 쉬게 될 때까지 기다려요. 이때 ListenAndServe는 즉시 http.ErrServerClosed를 돌려주므로 이를 오류로 취급하지 않아요. 이 환경에서 300ms 걸리는 요청을 처리하던 중 50ms에 Shutdown을 부르자, Shutdown은 요청이 끝난 317ms에 돌아왔고 클라이언트는 응답 done을 정상적으로 받았어요. 그 뒤에 보낸 새 요청은 연결이 거부됐어요. 끝나지 않는 요청도 있을 수 있으니 Shutdown에 넘기는 context에는 context.WithTimeout으로 시한을 두고, 시한이 지나면 Shutdown이 context 오류를 돌려줘요. 서버가 멈춘 뒤에는 DB 연결 풀을 닫고, 버퍼에 남은 로그와 메트릭을 내보내고, 백그라운드 워커에 취소를 전해요. 쿠버네티스에서는 로드밸런서가 파드를 엔드포인트에서 빼는 데 시간이 걸리므로, 신호를 받은 뒤 잠깐 기다렸다가 Shutdown을 부르는 경우도 많아요.<br><sub>Servers restart frequently for deployments and scaling. Environments such as Kubernetes first send SIGTERM when stopping a pod and force-kill it with SIGKILL if it has not exited after a grace period (30 s by default). If the process dies the moment the signal arrives, requests in progress are cut off and users see errors, so a graceful shutdown that finishes work in progress before stopping is needed. In Go, signal.NotifyContext(ctx, syscall.SIGTERM, os.Interrupt) turns the signal into context cancellation. The server runs ListenAndServe in a goroutine, and the main goroutine waits for the signal on <-ctx.Done(). When it arrives, call srv.Shutdown(sctx). Shutdown first closes all listeners so no new connections are accepted, closes idle connections, and then waits until in-flight requests finish and their connections go idle. ListenAndServe meanwhile returns http.ErrServerClosed at once, which should not be treated as an error. Here, calling Shutdown at 50 ms while serving a request that takes 300 ms made Shutdown return at 317 ms, after the request finished, and the client received its response, done, normally. A new request sent afterward was refused. Since some requests may never finish, give the context passed to Shutdown a deadline with context.WithTimeout; when the deadline passes, Shutdown returns the context’s error. After the server stops, close the database connection pool, flush buffered logs and metrics, and pass cancellation to background workers. In Kubernetes, load balancers take a moment to remove a pod from their endpoints, so servers often wait briefly after the signal before calling Shutdown.</sub> |
