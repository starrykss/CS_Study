## 줄지어 담는 자료구조 · Structures that line data up

데이터를 한 줄로 늘어놓는 구조예요. 어디서 넣고 빼느냐가 성능을 결정해요.  
*Structures that lay data out in a line. Where you add and remove decides the performance.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **배열**<br><sub>Array</sub> | 같은 크기의 칸을 메모리에 붙여 놓은 구조예요. 번호만 알면 바로 꺼낼 수 있지만, 중간에 넣거나 빼면 뒤를 전부 밀어야 해요.<br><sub>Equal-size slots placed side by side in memory. Any index is reachable instantly, but inserting or deleting in the middle shifts everything after it.</sub> | 읽기가 대부분이고 크기가 거의 안 바뀌는 데이터에 써요. 캐시 친화적이라 실제 성능은 이론보다 더 좋은 경우가 많아요.<br><sub>Use it for read-heavy data whose size rarely changes. It is cache-friendly, so real performance is often better than the theory suggests.</sub> |
| **동적 배열**<br><sub>Dynamic array · Amortized O(1)</sub> | 공간이 차면 두 배 크기의 새 배열을 만들고 옮겨 담아요. 가끔 느린 복사가 있어도 평균으로 보면 추가는 O(1)이에요.<br><sub>When full, it allocates an array twice as large and copies everything over. Despite the occasional slow copy, appends are O(1) on average.</sub> | 파이썬 list, 자바 ArrayList, 자바스크립트 Array가 이 구조예요. 넣을 개수를 미리 안다면 처음부터 크기를 잡아 복사를 줄이세요.<br><sub>Python lists, Java ArrayList and JavaScript arrays work this way. If you know the final size, reserve capacity up front to avoid copies.</sub> |
| **연결 리스트**<br><sub>Linked list</sub> | 각 노드가 값과 다음 노드의 주소를 들고 있어요. 위치만 알면 화살표만 바꿔 O(1)에 넣고 빼지만, 찾으려면 처음부터 따라가야 해요.<br><sub>Each node holds a value and the address of the next node. Insertion and deletion are O(1) once you are there, but finding a position means walking from the head.</sub> | 앞뒤로 자주 넣고 빼는 큐, LRU 캐시, 운영체제의 작업 목록에 쓰여요. 노드가 흩어져 있어 순회는 배열보다 느려요.<br><sub>Used for queues, LRU caches and OS task lists with frequent insertions and removals. Nodes are scattered in memory, so traversal is slower than an array.</sub> |
| **스택**<br><sub>Stack · LIFO</sub> | 마지막에 넣은 것이 가장 먼저 나오는 구조예요. 넣기(push)와 빼기(pop)가 모두 맨 위에서만 일어나요.<br><sub>The last item in is the first out. Push and pop both happen at the top.</sub> | 함수 호출(콜 스택), 실행 취소, 괄호 짝 맞추기, 브라우저 뒤로 가기, DFS가 모두 스택이에요.<br><sub>Function calls (the call stack), undo, bracket matching, the browser back button and DFS are all stacks.</sub> |
| **큐**<br><sub>Queue · FIFO</sub> | 먼저 들어온 것이 먼저 나가는 줄 서기 구조예요. 뒤로 넣고(enqueue) 앞에서 빼요(dequeue).<br><sub>First in, first out, like a line of people. Enqueue at the back, dequeue at the front.</sub> | 작업 대기열, 메시지 큐, 프린터 출력, BFS에 써요. 배열로 만들면 앞에서 뺄 때 밀기가 생기니 원형 버퍼나 덱을 쓰세요.<br><sub>Used for job queues, message queues, print spooling and BFS. A plain array shifts on dequeue, so use a ring buffer or deque instead.</sub> |
| **원형 버퍼**<br><sub>Ring buffer</sub> | 고정된 칸을 원처럼 이어서, 쓰는 위치와 읽는 위치가 계속 돌아가게 해요. 메모리를 새로 잡지 않고 끝없이 재사용해요.<br><sub>Fixed slots joined into a circle so the read and write positions keep wrapping around, reusing memory forever without new allocations.</sub> | 오디오·네트워크 스트림 버퍼, 최근 N개 로그, 생산자-소비자 큐처럼 크기가 정해진 흐름에 딱 맞아요.<br><sub>Perfect for fixed-size streams: audio and network buffers, the last N log lines and producer-consumer queues.</sub> |
| **자료구조 고르는 법**<br><sub>Choosing a structure</sub> | 같은 데이터라도 무엇을 자주 하느냐에 따라 맞는 구조가 달라요. 접근, 찾기, 넣기·빼기 비용을 비교해 고르세요.<br><sub>The right structure depends on which operations you do most. Compare the cost of access, search and insert or delete.</sub> | 면접 단골 질문이자 실무 성능 문제의 대부분이에요. 가장 자주 하는 연산이 O(1)이나 O(log n)이 되는 구조를 고르세요.<br><sub>A classic interview topic and the root of most real performance issues. Pick the structure that makes your most frequent operation O(1) or O(log n).</sub> |
| **덱 (Deque)**<br><sub>Deques</sub> | 앞과 뒤 양쪽에서 O(1)로 넣고 뺄 수 있는 큐예요. 스택과 큐를 하나로 합친 셈이에요.<br><sub>A queue with O(1) pushes and pops at both the front and the back: a stack and a queue in one.</sub> | push\_front, push\_back, pop\_front, pop\_back이 모두 O(1)이고, 보통 front/back 인덱스를 모듈러로 돌리는 원형 버퍼로 구현해요. 슬라이딩 윈도 최댓값은 덱에 감소하는 후보만 남겨 O(n)에 풀고, 0-1 BFS, 작업 훔치기 스케줄러(주인은 뒤에서, 도둑은 앞에서), 길이 제한이 있는 실행 취소 기록에도 써요. Python collections.deque, Java ArrayDeque가 대표 구현이에요.<br><sub>push\_front, push\_back, pop\_front and pop\_back are all O(1), usually on a ring buffer whose front/back indices wrap around. Sliding-window maximum keeps only decreasing candidates in a deque for O(n), and deques also power 0-1 BFS, work-stealing schedulers (owners pop the back, thieves steal the front) and capped undo histories. Python’s collections.deque and Java’s ArrayDeque are typical implementations.</sub> |
| **단조 스택**<br><sub>Monotonic stacks</sub> | 원소가 한 방향으로 정렬된 상태를 유지하는 스택이에요. “가장 가까운 더 큰(작은) 값” 문제를 O(n)에 풀어요.<br><sub>A stack kept sorted in one direction, solving “nearest greater (or smaller) element” problems in O(n).</sub> | [2, 7, 3, 5, 4, 6, 8]에서 각 원소의 오른쪽 첫 큰 수를 찾을 때, 새 원소보다 작은 스택 원소를 모두 꺼내며 답을 확정하고 새 원소를 쌓아요. 7이 2를 꺼내 2의 답은 7, 6이 4와 5를 꺼내는 식이에요. 각 원소가 한 번 쌓이고 한 번 꺼내지므로 이중 루프 O(n²)가 O(n)이 돼요. 일일 온도, 주가 스팬, 히스토그램에서 가장 큰 직사각형 문제의 기본 도구예요.<br><sub>To find the next greater element in [2, 7, 3, 5, 4, 6, 8], pop every stack entry smaller than the new element, fixing its answer, then push the new one: 7 pops 2 (answer 7), 6 pops 4 and 5, and so on. Each element is pushed and popped once, so the O(n²) nested loop becomes O(n). It is the core tool for daily temperatures, stock span and the largest rectangle in a histogram.</sub> |
| **스킵 리스트**<br><sub>Skip lists</sub> | 정렬된 연결 리스트 위에 “급행 차선” 층을 확률적으로 쌓아, 균형 트리처럼 O(log n)에 찾는 자료구조예요.<br><sub>Layers of randomly promoted “express lanes” over a sorted linked list give balanced-tree O(log n) search.</sub> | 맨 아래는 모든 원소의 정렬된 연결 리스트이고, 각 노드는 동전을 던져 1/2 확률로 위층에도 올라가요. 17을 찾을 땐 맨 위층에서 12까지 가고, 다음이 17보다 크면 한 층씩 내려가며 범위를 좁혀요. 회전 없이 확률로 균형을 맞춰 구현이 간단하고 동시성 버전을 만들기 쉬워서, Redis 정렬 집합, LevelDB·RocksDB의 memtable, Java ConcurrentSkipListMap이 써요.<br><sub>The bottom level is a sorted linked list of every element, and each node flips coins to rise to higher levels with probability 1/2. Searching for 17 runs along the top level to 12, dropping a level whenever the next node is too large. Balance comes from randomness instead of rotations, so it is simple and easy to make concurrent; Redis sorted sets, LevelDB/RocksDB memtables and Java’s ConcurrentSkipListMap use it.</sub> |

## 키로 바로 찾는 해시 · Finding by key with hashing

키를 숫자로 바꿔 칸 번호로 쓰는 방법이에요. 충돌을 어떻게 처리하느냐가 핵심이에요.  
*Turning keys into numbers used as slot indexes. Handling collisions is the core problem.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **해시 테이블**<br><sub>Hash table</sub> | 해시 함수가 키를 칸 번호로 바꿔 줘서, 찾기·넣기·빼기가 평균 O(1)이에요.<br><sub>A hash function turns a key into a slot index, so lookup, insert and delete are O(1) on average.</sub> | 딕셔너리, 맵, 집합, 캐시, 중복 제거 등 실무에서 가장 많이 쓰는 자료구조예요. 순서가 필요하면 정렬된 구조를 따로 쓰세요.<br><sub>Dictionaries, maps, sets, caches and deduplication: the most used structure in practice. If you need order, use a sorted structure alongside.</sub> |
| **충돌과 체이닝**<br><sub>Collision · Chaining</sub> | 서로 다른 키가 같은 칸에 들어가는 걸 충돌이라고 해요. 체이닝은 그 칸에 리스트로 이어 붙여 해결해요.<br><sub>A collision is when different keys map to the same slot. Chaining solves it by linking entries into a list in that slot.</sub> | 자바 HashMap은 한 칸에 너무 많이 쌓이면 리스트를 트리로 바꿔요. 칸 대비 원소 비율(적재율)이 높아지면 칸을 늘려 다시 배치해요.<br><sub>Java’s HashMap even turns a long chain into a tree. When the load factor gets high, the table grows and rehashes.</sub> |
| **개방 주소법**<br><sub>Open addressing · Linear probing</sub> | 충돌이 나면 정해진 규칙(다음 칸, 제곱 간격 등)으로 빈칸을 찾아 넣어요. 모든 데이터가 배열 안에 있어 캐시에 유리해요.<br><sub>On a collision, it searches for an empty slot by a fixed rule such as the next slot. Everything stays inside the array, which is cache-friendly.</sub> | 파이썬 dict, 고성능 해시맵이 이 방식이에요. 삭제할 때는 빈칸 대신 "삭제됨" 표시를 남겨야 탐색이 끊기지 않아요.<br><sub>Python dicts and high-performance hash maps use it. Deletions leave a tombstone instead of an empty slot so lookups don’t stop early.</sub> |
| **블룸 필터**<br><sub>Bloom filter</sub> | 비트 배열과 해시 여러 개로 "확실히 없다" 또는 "있을 수도 있다"를 아주 적은 메모리로 답해요.<br><sub>A bit array plus several hashes answers “definitely not” or “maybe” using very little memory.</sub> | DB가 디스크를 읽기 전에 없는 키를 걸러내거나, 이미 본 URL·스팸을 빠르게 거를 때 써요. 거짓 양성은 있어도 거짓 음성은 없어요.<br><sub>Databases use it to skip disk reads for missing keys, and crawlers to skip seen URLs. It can give false positives but never false negatives.</sub> |
| **쿠쿠 해싱**<br><sub>Cuckoo hashing</sub> | 해시 함수 두 개로 키마다 들어갈 자리를 딱 두 곳 정하고, 자리가 차 있으면 기존 키를 쫓아내 다른 자리로 보내는 해싱이에요.<br><sub>Two hash functions give each key exactly two possible homes; inserting into an occupied one evicts the resident to its other home.</sub> | C를 넣을 자리에 A가 있으면 A를 쫓아내고, A는 자기의 다른 자리로 가며 거기 있던 B를 다시 밀어내는 식으로 연쇄 이동해요. 덕분에 조회는 최악에도 두 곳만 확인하면 돼서 O(1)이 보장돼요. 쫓아내기가 순환하면 해시 함수를 바꿔 전체를 다시 넣고, 두 테이블 기준 적재율은 약 50%예요. 지연이 일정해야 하는 네트워크 장비와 쿠쿠 필터에 쓰여요.<br><sub>If A occupies C’s slot, A is evicted to its alternate slot, which may bump B in turn, and the chain continues until everyone settles. Lookups therefore check at most two places: O(1) even in the worst case. If evictions cycle, everything is rehashed with new functions; with two tables the load factor tops out around 50%. It suits network hardware that needs predictable latency, and underlies cuckoo filters.</sub> |
| **카운트-민 스케치**<br><sub>Count-min sketch</sub> | 해시 함수 여러 개로 작은 카운터 행렬에 개수를 더하고, 행들의 최솟값으로 빈도를 추정하는 확률적 자료구조예요.<br><sub>A probabilistic structure that adds counts into a small hashed matrix and estimates frequency by the minimum across rows.</sub> | cat이 들어오면 행마다 해시된 칸 하나씩 +1, dog가 두 번 오면 +2를 해요. 충돌하면 값이 커지기만 하므로 cat의 추정은 min(1, 3, 1) = 1처럼 최솟값을 써요. 메모리는 d × w칸으로 고정이고, 오차는 대략 (e / w) × 전체 개수, 확률 1 − e^(−d)로 보장돼요. 스트림의 인기 검색어, 네트워크 트래픽 분석, 실시간 트렌드 Top-K에 쓰고, 고유 개수는 HyperLogLog, 존재 여부는 블룸 필터와 짝을 이뤄요.<br><sub>Each arrival of cat adds 1 to one hashed cell per row, and two dogs add 2. Collisions only inflate counts, so the estimate takes the minimum, e.g. min(1, 3, 1) = 1 for cat. Memory is fixed at d × w cells, and error is about (e / w) × total with probability 1 − e^(−d). It finds heavy hitters in streams, analyzes network traffic and drives real-time trending top-K, alongside HyperLogLog for distinct counts and Bloom filters for membership.</sub> |

## 나뭇가지처럼 뻗는 트리 · Trees that branch out

부모와 자식으로 이어진 계층 구조예요. 높이를 낮게 유지하는 게 성능의 핵심이에요.  
*Hierarchies of parents and children. Keeping the height low is the key to performance.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **이진 탐색 트리**<br><sub>Binary search tree</sub> | 왼쪽 자식은 작게, 오른쪽 자식은 크게 둬서 비교할 때마다 절반을 버리며 찾아요.<br><sub>Smaller keys go left and larger keys go right, so each comparison discards half the tree.</sub> | 정렬된 데이터를 자주 넣고 빼면서 찾아야 할 때 써요. 정렬된 순서로 넣으면 한쪽으로 치우쳐 O(n)이 되니 균형 트리를 쓰세요.<br><sub>Use it when you insert, delete and search sorted data often. Inserting already sorted data skews it to O(n), so use a balanced tree.</sub> |
| **트리 순회**<br><sub>Tree traversal</sub> | 트리의 모든 노드를 정해진 순서로 방문해요. 전위(자신 먼저), 중위(가운데), 후위(자식 먼저), 레벨 순서(층별)가 있어요.<br><sub>Visiting every node in a set order: pre-order (self first), in-order (middle), post-order (children first) and level order.</sub> | 중위는 정렬 출력, 전위는 트리 복사·직렬화, 후위는 폴더 크기 계산이나 삭제, 레벨 순서는 최단 거리에 써요.<br><sub>In-order prints sorted data, pre-order copies or serializes a tree, post-order computes folder sizes or deletes, and level order finds shortest paths.</sub> |
| **균형 트리와 회전**<br><sub>Balanced trees · Rotation</sub> | 한쪽으로 기운 트리를 회전으로 다시 세워 높이를 log n으로 유지해요. AVL 트리와 레드블랙 트리가 대표적이에요.<br><sub>Rotations straighten a lopsided tree so its height stays log n. AVL and red-black trees are the best-known.</sub> | 자바 TreeMap, C++ map, 리눅스 스케줄러가 레드블랙 트리를 써요. 직접 구현할 일은 드물지만 정렬된 맵이 왜 O(log n)인지 알려줘요.<br><sub>Java’s TreeMap, C++ std::map and the Linux scheduler use red-black trees. You rarely implement one, but it explains why sorted maps are O(log n).</sub> |
| **힙 · 우선순위 큐**<br><sub>Heap · Priority queue</sub> | 부모가 항상 자식보다 작은(또는 큰) 완전 이진 트리예요. 맨 위에서 최솟값을 바로 꺼낼 수 있고, 배열 하나로 표현돼요.<br><sub>A complete binary tree where every parent is smaller (or larger) than its children. The minimum sits at the top, and the whole tree fits in one array.</sub> | 작업 스케줄러, 다익스트라, 상위 K개 고르기, 타이머 관리에 써요. 전체 정렬이 아니라 "가장 급한 것"만 필요할 때 좋아요.<br><sub>Used for schedulers, Dijkstra, top-K selection and timers, whenever you need the most urgent item rather than full order.</sub> |
| **트라이**<br><sub>Trie · Prefix tree</sub> | 문자 하나가 한 단계가 되는 트리예요. 같은 접두사를 공유해서 접두사로 찾기가 아주 빨라요.<br><sub>A tree where each level is one character. Shared prefixes share nodes, so prefix lookups are very fast.</sub> | 검색어 자동 완성, 사전, IP 라우팅 테이블, 맞춤법 검사에 써요. 메모리를 많이 쓰니 압축 트라이(래딕스 트리)도 고려하세요.<br><sub>Used for autocomplete, dictionaries, IP routing tables and spell checking. It is memory-hungry, so consider a compressed radix tree.</sub> |
| **B-트리 · B+트리**<br><sub>B-tree · B+ tree</sub> | 한 노드에 키를 여러 개 담아 자식이 많고 높이가 아주 낮은 트리예요. B+트리는 데이터를 리프에만 두고 리프끼리 연결해요.<br><sub>A tree whose nodes hold many keys, so it has many children and very little height. A B+ tree keeps data only in leaves and links the leaves together.</sub> | MySQL·PostgreSQL 인덱스, 파일 시스템의 기본 구조예요. 디스크를 몇 번만 읽고도 수억 건에서 찾을 수 있고, 범위 검색도 빨라요.<br><sub>The core of MySQL and PostgreSQL indexes and file systems. A few disk reads find one row among hundreds of millions, and range scans are fast.</sub> |
| **레드-블랙 트리**<br><sub>Red-black trees</sub> | 노드에 빨강·검정 색을 칠하고 네 가지 규칙을 지켜 높이를 2 log n 이하로 유지하는 균형 이진 탐색 트리예요.<br><sub>A balanced binary search tree that colors nodes red or black and follows four rules to keep its height under 2 log n.</sub> | 규칙은 루트는 검정, 빨강이 연달아 올 수 없음, 모든 경로의 검정 노드 수가 같음이에요. 새 노드는 빨강으로 넣고, 빨강–빨강이 생기면 삼촌이 검정일 땐 회전 + 색 바꾸기, 빨강일 땐 색만 바꿔 위로 문제를 넘겨요. AVL보다 덜 엄격해 회전이 적어 쓰기가 많은 곳에 유리하고, Java TreeMap, C++ std::map, 리눅스 CFS 스케줄러가 써요.<br><sub>The rules: the root is black, no red node has a red child, and every root-to-leaf path has the same number of black nodes. New nodes go in red; a red–red clash is fixed by a rotation plus recoloring when the uncle is black, or by recoloring alone (pushing the problem upward) when the uncle is red. Looser than AVL, it rotates less and suits write-heavy use; Java’s TreeMap, C++ std::map and Linux’s CFS scheduler rely on it.</sub> |
| **세그먼트 트리**<br><sub>Segment trees</sub> | 배열의 구간마다 합(또는 최소·최대)을 트리로 저장해, 구간 질의와 값 갱신을 모두 O(log n)에 처리해요.<br><sub>A tree storing the sum (or min/max) of each range of an array, so range queries and updates both take O(log n).</sub> | [5, 8, 6, 3, 2, 7, 2, 6]의 두 칸씩 합을 위로 쌓아 루트에 전체 합 39를 둬요. sum(a2..a6)은 [2–3], [4–5], a6 세 노드만으로 9 + 9 + 2 = 20이 되고, a4를 10으로 바꾸면 루트까지 4개 노드만 갱신해요. 배열 2n칸으로 구현하며, 지연 전파(lazy propagation)를 쓰면 구간 갱신도 O(log n)이에요. 누적 합 배열은 갱신이 O(n)이라 갱신이 잦을 때 이 구조를 써요.<br><sub>Pairs of [5, 8, 6, 3, 2, 7, 2, 6] are summed upward until the root holds the total, 39. sum(a2..a6) uses just three nodes, [2–3], [4–5] and a6, for 9 + 9 + 2 = 20, and setting a4 to 10 updates only four nodes up to the root. It fits in a 2n array, and lazy propagation brings range updates to O(log n) too. Prefix-sum arrays need O(n) per update, so this is the choice when values change often.</sub> |
| **펜윅 트리 (BIT)**<br><sub>Fenwick trees (BIT)</sub> | 배열 하나와 비트 연산 i & −i만으로 누적 합 질의와 값 갱신을 O(log n)에 하는 자료구조예요.<br><sub>Prefix-sum queries and updates in O(log n) using a single array and the bit trick i & −i.</sub> | t[i]는 i의 가장 낮은 1비트 길이만큼의 구간 (i − i&−i, i]의 합을 저장해요. prefix(7)은 i에서 최하위 비트를 지우며 t[7] + t[6] + t[4] = 33, a3 갱신은 비트를 더하며 t[3], t[4], t[8]만 고쳐요. 구간 합은 prefix(r) − prefix(l − 1)이에요. 세그먼트 트리보다 코드가 짧고 빠르지만 최솟값 같은 일반 구간 연산엔 덜 유연하며, 순위 통계와 역순 쌍 세기에 자주 써요.<br><sub>t[i] stores the sum of the range (i − i&−i, i], whose length is i’s lowest set bit. prefix(7) clears low bits as it goes: t[7] + t[6] + t[4] = 33, and updating a3 adds low bits to touch only t[3], t[4] and t[8]. A range sum is prefix(r) − prefix(l − 1). Shorter and faster than a segment tree but less flexible for operations like range minimum, it is a staple of rank statistics and inversion counting.</sub> |

## 관계를 담는 구조와 실무 자료구조 · Relationships and practical structures

서로 연결된 관계를 표현하는 법과, 실무에서 자주 만나는 조합형 자료구조예요.  
*How to represent connections, and composite structures you meet in real systems.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **그래프 표현**<br><sub>Graph representation</sub> | 정점과 간선을 저장하는 두 방법이에요. 인접 행렬은 연결 여부를 O(1)로 확인하고, 인접 리스트는 공간을 적게 써요.<br><sub>Two ways to store vertices and edges. An adjacency matrix checks a connection in O(1); an adjacency list uses far less space.</sub> | SNS 친구 관계, 지도, 의존성처럼 대부분의 실제 그래프는 간선이 적어서 인접 리스트가 기본이에요.<br><sub>Most real graphs, such as social networks, maps and dependencies, are sparse, so adjacency lists are the default.</sub> |
| **유니온 파인드**<br><sub>Union-find · Disjoint set</sub> | 원소들이 어느 그룹에 속하는지 대표 원소로 관리해요. 경로 압축과 랭크 합치기를 쓰면 거의 O(1)이에요.<br><sub>Tracks which group each element belongs to via a representative. With path compression and union by rank it is almost O(1).</sub> | 크루스칼 최소 신장 트리, 네트워크 연결 여부, 이미지의 영역 묶기, 친구 그룹 합치기에 써요.<br><sub>Used in Kruskal’s MST, network connectivity, image region labelling and merging friend groups.</sub> |
| **LRU 캐시**<br><sub>LRU cache</sub> | 가장 오래 쓰지 않은 항목부터 내보내는 캐시예요. 해시맵으로 바로 찾고, 이중 연결 리스트로 사용 순서를 관리해요.<br><sub>A cache that evicts the least recently used item first. A hash map finds entries instantly; a doubly linked list keeps the usage order.</sub> | 면접 단골 구현 문제이자 브라우저 캐시, DB 버퍼, CDN의 기본 정책이에요. 자바 LinkedHashMap으로 쉽게 만들 수 있어요.<br><sub>A classic interview problem and the basic policy behind browser caches, database buffers and CDNs. Java’s LinkedHashMap builds one easily.</sub> |
| **쿼드트리와 공간 인덱스**<br><sub>Quadtrees and spatial indexes</sub> | 2차원 공간을 4등분하며 점을 담아, 볼 필요 없는 영역을 통째로 건너뛰게 해 주는 트리예요.<br><sub>A tree that recursively splits 2D space into quadrants so whole regions can be skipped during searches.</sub> | 점이 2개 이상인 칸만 다시 4등분하는 식으로 재귀적으로 나누면, 범위 질의나 가장 가까운 점 찾기에서 질의와 겹치는 칸만 내려가고 나머지는 통째로 건너뛰어요. k-d 트리는 x와 y를 번갈아 2등분하고, R-트리는 겹치는 사각형으로 묶어 PostGIS 같은 공간 DB 인덱스로 쓰여요. 게임 충돌 감지, 지도 타일, 근처 가게 검색, 이미지 압축에 쓰여요.<br><sub>Any cell with two or more points is split into four again; a range or nearest-neighbor query then descends only into cells overlapping the query and skips the rest wholesale. k-d trees alternate x and y halvings, and R-trees group overlapping rectangles, serving as spatial indexes in databases such as PostGIS. They power game collision detection, map tiles, “near me” search and image compression.</sub> |
| **영속 자료구조**<br><sub>Persistent data structures</sub> | 값을 바꿀 때 원본을 고치지 않고 새 버전을 만들되, 바뀌지 않은 부분은 공유해 효율적인 불변 자료구조예요.<br><sub>Immutable structures that create a new version on every change while sharing all unchanged parts with the old one.</sub> | 불변 리스트 v1 = [1, 2, 3] 앞에 0을 붙인 v2는 새 노드 하나만 만들고 나머지를 공유해요. 트리에서 G를 바꾸면 루트까지 경로(A′, C′, G′)만 복사하고 나머지 서브트리는 그대로 가리켜 O(log n)에 새 버전이 생겨요. 옛 버전도 그대로 읽을 수 있어 실행 취소·시간 여행과 동시성에 안전하고, Redux/Immer, Clojure·Scala의 32갈래 벡터, Git 커밋이 같은 원리예요.<br><sub>Prepending 0 to the immutable list v1 = [1, 2, 3] builds a single node and shares the rest as v2. Changing G in a tree copies only its path to the root (A′, C′, G′) and points at every untouched subtree, producing a new version in O(log n). Old versions remain readable, which enables undo, time travel and safe concurrency; Redux/Immer, Clojure and Scala’s 32-way vectors and Git commits all work this way.</sub> |
