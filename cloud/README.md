| **리전과 가용 영역**<br><sub>Regions and availability zones</sub> | 리전은 지리적으로 떨어진 데이터센터 묶음이고, 가용 영역(AZ)은 리전 안에서 전원·네트워크가 독립된 구역이에요. 여러 AZ에 나눠 두는 것이 고가용성의 출발점이에요.<br><sub>Regions are geographically separate groups of data centers, and availability zones (AZs) are independently powered and networked areas within a region; spreading across AZs is where high availability begins.</sub> | 리전은 서울(ap-northeast-2, koreacentral, asia-northeast3)처럼 지리적으로 떨어진 데이터센터 묶음이에요. 리전을 고를 때는 사용자와의 거리(지연), 데이터가 특정 국가 안에 있어야 하는지 같은 법규, 그 리전에서 쓸 수 있는 서비스와 가격을 함께 따져요. 가용 영역은 한 리전 안에서 전원, 냉각, 네트워크가 독립된 하나 이상의 데이터센터이고, AZ끼리는 지연이 아주 짧은 전용망으로 연결돼요. 그래서 앱 서버와 DB 복제본을 여러 AZ에 나눠 두면 한 AZ가 통째로 멈춰도 로드밸런서가 나머지 AZ로 트래픽을 보내고 대기 DB가 승격돼 서비스가 이어져요. AZ 사이 데이터 전송에도 요금이 붙고, 리전 전체 장애까지 대비하려면 다중 리전 설계가 필요해요. 이 밖에 도시 가까이 두는 로컬 존이나 엣지 위치처럼 더 작은 단위도 있어요.<br><sub>A region such as Seoul (ap-northeast-2, koreacentral, asia-northeast3) is a geographically separate group of data centers. Choosing one means weighing distance to users (latency), laws such as data residency, and which services and prices that region offers. An availability zone is one or more data centers in a region with independent power, cooling and networking, linked to other AZs by very low-latency private fiber. Spreading app servers and database replicas across AZs means that when one AZ stops entirely, the load balancer shifts traffic to the others and a standby database is promoted, keeping the service up. Data moving between AZs is billed, and surviving a whole-region outage requires a multi-region design. Smaller units also exist, such as local zones near cities and edge locations.</sub> |
| **공동 책임 모델**<br><sub>Shared responsibility model</sub> | 데이터센터·하드웨어·가상화처럼 “클라우드 자체”의 보안은 제공자가, 그 위에 올린 데이터·권한·설정의 보안은 고객이 책임져요. 관리형일수록 고객 몫이 줄어요.<br><sub>Providers secure the cloud itself (data centers, hardware, virtualization) while customers secure what they put in it (data, permissions, configuration), and managed services shrink the customer’s share.</sub> | 클라우드 제공자는 건물 출입 통제, 서버와 네트워크 장비, 가상화 계층처럼 클라우드 “의” 보안을 책임져요. 고객은 그 위에 올린 데이터, 계정과 권한, 네트워크 설정, OS 패치, 애플리케이션 코드처럼 클라우드 “안”의 보안을 책임져요. 경계는 서비스 종류에 따라 움직여요. 가상 머신(IaaS)이라면 OS 패치와 방화벽까지 고객 몫이지만, 관리형 DB나 서버리스 함수로 갈수록 제공자가 맡는 범위가 넓어져요. 그래도 데이터 분류, 접근 권한, 암호화 설정, 공개 범위는 어떤 서비스에서도 늘 고객의 책임으로 남아요. 실제 클라우드 사고의 대부분은 제공자의 결함이 아니라 공개된 버킷, 너무 넓은 권한, 유출된 키처럼 고객 쪽 설정 실수에서 나와요.<br><sub>Cloud providers handle security of the cloud: physical access to buildings, servers and network gear, and the virtualization layer. Customers handle security in the cloud: their data, accounts and permissions, network settings, OS patches and application code. The boundary moves with the service type. On virtual machines (IaaS) the customer patches the OS and manages firewalls, while managed databases and serverless functions shift more onto the provider. Even so, data classification, access permissions, encryption settings and exposure always remain the customer’s responsibility. Most real cloud incidents come not from provider flaws but from customer misconfigurations such as public buckets, overly broad permissions and leaked keys.</sub> |
| **AWS·Azure·GCP 서비스 대응**<br><sub>AWS, Azure and GCP service map</sub> | 가상 머신, 객체 스토리지, 관리형 DB, 서버리스처럼 세 클라우드의 핵심 서비스는 이름만 다르고 개념이 같아요. 개념으로 익히면 클라우드를 옮겨 다니기 쉬워요.<br><sub>The three clouds offer the same core concepts (VMs, object storage, managed databases, serverless) under different names, so learning concepts first makes moving between clouds easy.</sub> | 세 클라우드는 같은 개념을 다른 이름으로 제공해요. 가상 머신은 EC2·Azure Virtual Machines·Compute Engine, 객체 스토리지는 S3·Blob Storage·Cloud Storage, 관리형 SQL은 RDS·Azure SQL Database·Cloud SQL이에요. 컨테이너는 EKS·AKS·GKE, 서버리스 함수는 Lambda·Azure Functions·Cloud Run functions, 메시징은 SQS/SNS·Service Bus·Pub/Sub, 권한은 IAM·Microsoft Entra ID와 Azure RBAC·Cloud IAM으로 대응돼요. 이름보다 “무엇을 맡기고 무엇을 직접 하는가”라는 개념을 먼저 익히면 한 클라우드에서 배운 것을 다른 클라우드로 그대로 옮길 수 있어요. 다만 세부 동작은 달라서, GCP의 VPC는 전역이고 AWS·Azure는 리전 단위이며, 권한 모델과 계정 구조도 서로 달라요. 각 제공자의 공식 서비스 비교표를 옆에 두고 보면 편해요.<br><sub>The three clouds sell the same concepts under different names. Virtual machines are EC2, Azure Virtual Machines and Compute Engine; object storage is S3, Blob Storage and Cloud Storage; managed SQL is RDS, Azure SQL Database and Cloud SQL. Containers map to EKS, AKS and GKE, serverless functions to Lambda, Azure Functions and Cloud Run functions, messaging to SQS/SNS, Service Bus and Pub/Sub, and permissions to IAM, Microsoft Entra ID with Azure RBAC, and Cloud IAM. Learning the concept of what you hand off versus run yourself, rather than the names, lets knowledge from one cloud carry over to another. Details still differ: GCP VPCs are global while AWS and Azure networks are regional, and permission models and account structures vary. Keeping each provider’s official comparison chart nearby helps.</sub> |
| **클라우드 요금 모델**<br><sub>Cloud pricing models</sub> | 온디맨드는 쓴 만큼, 약정 할인은 1·3년 약속으로 크게 싸게, 스팟은 남는 용량을 아주 싸게 쓰되 회수될 수 있어요. 부하의 성격에 맞게 섞어 써요.<br><sub>On-demand bills for what you use, commitments trade one- or three-year promises for big discounts, and spot rents spare capacity cheaply but can be reclaimed; mix them by workload.</sub> | 온디맨드는 약정 없이 쓴 시간(초·분 단위)만큼 내는 방식이라 가장 유연하지만 단가가 가장 비싸요. 실험이나 예측하기 어려운 부하에 맞아요. 약정 할인은 1년이나 3년 동안 일정 사용량을 약속하고 크게 할인받는 방식으로 AWS Savings Plans·예약 인스턴스, Azure Reservations·Savings Plan, GCP 약정 사용 할인(CUD)이 있어요. 늘 켜져 있는 기본 부하에 걸면 효과가 커요. 스팟(Spot VM)은 클라우드의 남는 용량을 최대 90%까지 싸게 쓰지만, 용량이 필요해지면 짧은 예고 후 회수돼요. 그래서 배치, CI, 다시 시작해도 되는 작업에 써요. 그 밖에 GCP는 오래 켜 둔 VM에 자동 할인을 주고, 저장 용량·요청 수·데이터 전송처럼 컴퓨팅 외의 요금도 따로 붙으니 전체 구성을 계산기로 미리 따져 봐요.<br><sub>On-demand bills by the second or minute with no commitment, the most flexible and most expensive option, suited to experiments and unpredictable load. Commitment discounts promise a level of usage for one or three years in exchange for large discounts: AWS Savings Plans and Reserved Instances, Azure Reservations and Savings Plan, and GCP committed use discounts (CUDs). They pay off most on always-on baseline load. Spot VMs rent spare capacity at up to 90% off but are reclaimed after a short notice when capacity is needed, so they suit batch jobs, CI and restartable work. GCP also applies automatic sustained-use discounts to long-running VMs, and storage, requests and data transfer are billed separately from compute, so estimate whole architectures with the pricing calculators.</sub> |
| **계정·구독·프로젝트 구조**<br><sub>Accounts, subscriptions and projects</sub> | 조직 아래에 환경과 팀별로 계정(구독·프로젝트)을 나누면 권한, 비용, 사고 범위가 깔끔하게 분리돼요. 상위에서 정책으로 가드레일을 걸어요.<br><sub>Splitting accounts, subscriptions or projects by environment and team under an organization separates permissions, cost and blast radius, with guardrail policies applied from the top.</sub> | AWS는 Organization 아래 OU(조직 단위)와 계정, Azure는 관리 그룹 아래 구독과 리소스 그룹, GCP는 조직 아래 폴더와 프로젝트로 클라우드 공간을 계층으로 나눠요. 운영(prod), 스테이징, 개발을 서로 다른 계정이나 프로젝트로 분리하면 개발자의 실수가 운영에 번지지 않고, 권한과 비용도 경계가 분명해져요. 상위 계층에는 AWS SCP(서비스 제어 정책), Azure Policy, GCP 조직 정책 같은 가드레일을 걸어 “서울 외 리전 사용 금지”, “공개 버킷 금지”처럼 하위 계정 누구도 어길 수 없는 규칙을 정해요. 사람의 로그인은 IAM Identity Center, Microsoft Entra ID, Cloud Identity로 한곳에서 관리하고, 각 계정에는 역할로 들어가요. 감사 로그와 보안 도구는 별도의 보안 계정에 모아 두면 계정 하나가 탈취돼도 기록이 지워지지 않아요.<br><sub>AWS organizes the cloud as an Organization with organizational units (OUs) and accounts, Azure as management groups with subscriptions and resource groups, and GCP as an organization with folders and projects. Putting production, staging and development in separate accounts or projects keeps developer mistakes away from production and draws clear permission and cost boundaries. Guardrails at upper levels, such as AWS service control policies (SCPs), Azure Policy and GCP organization policies, set rules no child account can break, like “no regions outside Seoul” or “no public buckets.” Human sign-in is managed centrally with IAM Identity Center, Microsoft Entra ID or Cloud Identity, and people enter each account through roles. Collecting audit logs and security tools in a separate security account keeps records intact even if one account is compromised.</sub> |
| **잘 설계된 아키텍처 기준**<br><sub>Well-architected frameworks</sub> | AWS Well-Architected의 6개 기둥(운영 우수성·보안·안정성·성능 효율성·비용 최적화·지속 가능성)은 클라우드 설계를 점검하는 질문 목록이에요. Azure와 Google도 비슷한 프레임워크가 있어요.<br><sub>The six pillars of AWS Well-Architected (operational excellence, security, reliability, performance efficiency, cost optimization, sustainability) are a checklist for reviewing cloud designs, with similar frameworks from Azure and Google.</sub> | AWS Well-Architected 프레임워크는 시스템을 여섯 기둥으로 점검해요. 운영 우수성은 배포와 장애 대응을 자동화하고 개선하는지, 보안은 최소 권한과 암호화, 추적성을 갖췄는지, 안정성은 장애를 견디고 스스로 복구하는지를 물어요. 성능 효율성은 알맞은 자원을 고르고 확장하는지, 비용 최적화는 필요 없는 지출을 없애는지, 지속 가능성은 자원을 효율적으로 써서 환경 영향을 줄이는지를 봐요. Azure Well-Architected Framework와 Google Cloud Architecture Framework도 비슷한 기둥을 가지고 있어요. 기둥끼리는 서로 부딪히기도 해서, 다중 리전은 안정성을 높이지만 비용이 커지는 식으로 균형을 정해야 해요. 각 제공자가 제공하는 리뷰 도구로 질문에 답해 보면 위험 항목과 개선 순서가 정리돼요.<br><sub>The AWS Well-Architected Framework reviews systems through six pillars. Operational excellence asks whether deployment and incident response are automated and improving, security whether least privilege, encryption and traceability are in place, and reliability whether the system withstands failures and recovers on its own. Performance efficiency checks that resources are well chosen and scale, cost optimization that unneeded spending is removed, and sustainability that resources are used efficiently to reduce environmental impact. The Azure Well-Architected Framework and Google Cloud Architecture Framework have similar pillars. Pillars can conflict, as multi-region designs raise reliability but also cost, so trade-offs must be chosen. Answering the questions in each provider’s review tool organizes risks and an order of improvements.</sub> |

## 권한과 비밀 관리 · Identity, keys and secrets

IAM 정책의 구조와 평가 방식, 영구 키 대신 역할과 임시 자격 증명, KMS 봉투 암호화, 비밀 관리 서비스까지 클라우드 보안의 핵심인 “누가 무엇을 할 수 있는가”를 다뤄요.  
*How IAM policies are structured and evaluated, roles and temporary credentials instead of long-lived keys, KMS envelope encryption, and secrets management: the core of cloud security, deciding who can do what.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **IAM 정책**<br><sub>IAM policies</sub> | 누가(주체) 무엇을(행동) 어디에(리소스) 어떤 조건에서 할 수 있는지를 적은 문서예요. 기본은 모두 거부, 명시적 거부가 모든 허용을 이겨요.<br><sub>An IAM policy is a document stating who (principal) can do what (action) on which resource under which conditions; everything is denied by default and an explicit deny beats any allow.</sub> | IAM 정책은 Effect(허용·거부), Action(s3:GetObject 같은 행동), Resource(대상의 ARN), Condition(IP, 시간, 태그 같은 조건)으로 이루어진 JSON 문서예요. 아무 정책이 없으면 기본은 모두 거부이고, 허용 문장이 있어야 비로소 할 수 있어요. 여러 정책이 겹치면 명시적 Deny가 어떤 Allow보다도 우선해서, 조직 차원의 금지 규칙을 확실하게 걸 수 있어요. 최소 권한 원칙에 따라 s3:\*나 Resource "\*" 같은 와일드카드를 피하고, 필요한 행동과 리소스만 좁게 적어요. Azure는 역할 정의를 범위(관리 그룹·구독·리소스 그룹)에 할당하는 RBAC, GCP는 역할을 리소스 계층에 바인딩하는 방식이라 모양은 달라도 생각은 같아요. IAM Access Analyzer나 정책 시뮬레이터로 실제로 쓰인 권한을 확인해 점점 좁혀 가요.<br><sub>An IAM policy is a JSON document of Effect (allow or deny), Action (such as s3:GetObject), Resource (the target’s ARN) and Condition (IP, time, tags and so on). With no policy, everything is denied by default, and an Allow statement is required to act. When policies overlap, an explicit Deny overrides any Allow, which makes organization-wide bans reliable. Least privilege means avoiding wildcards such as s3:\* or Resource "\*" and listing only the needed actions and resources. Azure assigns role definitions at scopes (management group, subscription, resource group) through RBAC, and GCP binds roles on the resource hierarchy; the shapes differ but the thinking is the same. Tools such as IAM Access Analyzer and policy simulators show which permissions are actually used so they can be narrowed over time.</sub> |
| **역할과 임시 자격 증명**<br><sub>Roles and temporary credentials</sub> | 코드에 영구 액세스 키를 넣는 대신, 서버나 함수에 역할을 붙여 몇 시간짜리 임시 자격 증명을 자동으로 받게 해요. 새도 금방 만료돼요.<br><sub>Instead of long-lived access keys in code, attach roles to servers and functions so they receive short-lived credentials automatically, which expire quickly even if leaked.</sub> | 영구 액세스 키를 코드, 환경 변수, 설정 파일에 넣으면 깃 저장소, 로그, 컨테이너 이미지로 새기 쉽고, 새면 누군가 키를 바꿀 때까지 계속 위험해요. 역할(role)은 권한 묶음에 “누가 맡을 수 있는가”를 정해 둔 것이고, EC2 인스턴스 프로필, Lambda 실행 역할, EKS의 서비스 계정 연동처럼 실행 환경에 붙이면 SDK가 알아서 임시 자격 증명을 받아 와요. 임시 자격 증명은 보통 1시간 안팎으로 만료되고 자동으로 갱신되므로, 새더라도 피해 시간이 짧아요. Azure는 관리 ID(Managed Identity), GCP는 서비스 계정을 같은 방식으로 써요. GitHub Actions 같은 외부 CI도 OIDC 연동으로 저장된 키 없이 역할을 맡을 수 있어요. 사람도 IAM 사용자 대신 SSO로 로그인해 역할을 맡는 것이 기본이에요.<br><sub>Long-lived access keys in code, environment variables or config files leak easily through Git repositories, logs and container images, and stay dangerous until someone rotates them. A role is a set of permissions plus a rule about who may assume it, and attaching it to the runtime, such as an EC2 instance profile, a Lambda execution role or EKS service account integration, lets the SDK fetch temporary credentials automatically. Temporary credentials typically expire within about an hour and renew automatically, so a leak has a short window. Azure uses managed identities and GCP service accounts the same way. External CI such as GitHub Actions can assume roles through OIDC federation without stored keys. People, too, should sign in through SSO and assume roles rather than using IAM users.</sub> |
| **KMS와 봉투 암호화**<br><sub>KMS and envelope encryption</sub> | 데이터는 데이터 키로 암호화하고, 데이터 키는 KMS 안의 마스터 키로 다시 암호화해 함께 저장해요. 마스터 키는 KMS 밖으로 나오지 않아요.<br><sub>Data is encrypted with a data key, which is itself encrypted by a master key inside KMS and stored alongside, so the master key never leaves KMS.</sub> | AWS KMS, Azure Key Vault, Cloud KMS는 암호화 키를 하드웨어 보안 모듈(HSM) 기반으로 보관하고, 키를 쓴 기록을 감사 로그로 남겨요. 큰 데이터를 KMS로 직접 암호화하지 않고 봉투 암호화를 써요. 먼저 KMS에 데이터 키를 요청하면 평문 키와 마스터 키로 암호화된 키 두 벌을 받아요. 평문 키로 데이터를 암호화한 뒤 메모리에서 지우고, 암호화된 키는 데이터 옆에 저장해요. 읽을 때는 암호화된 키를 KMS에 보내 복호화받는데, 이때 IAM 권한 검사가 일어나므로 키 권한이 곧 데이터 접근 권한이 돼요. S3, EBS, RDS의 저장 시 암호화도 내부적으로 이 방식이에요. 마스터 키는 KMS 밖으로 나오지 않고, 자동 교체를 켜 두면 이전 데이터도 그대로 읽혀요. 키를 지우면 데이터도 영영 못 읽으니 삭제에는 대기 기간이 있어요.<br><sub>AWS KMS, Azure Key Vault and Cloud KMS keep encryption keys backed by hardware security modules (HSMs) and log every key use for auditing. Large data is not sent to KMS directly; envelope encryption is used instead. You first ask KMS for a data key and receive two copies: a plaintext key and one encrypted under the master key. The plaintext key encrypts the data and is then wiped from memory, while the encrypted key is stored next to the data. To read, you send the encrypted key to KMS for decryption, which triggers an IAM check, so key permissions effectively become data access permissions. Encryption at rest in S3, EBS and RDS works this way internally. Master keys never leave KMS, and enabling automatic rotation keeps older data readable. Deleting a key makes its data unreadable forever, so deletion has a waiting period.</sub> |
| **비밀 관리 서비스**<br><sub>Secrets management</sub> | DB 비밀번호와 API 키는 .env나 이미지에 넣지 말고 Secrets Manager·Key Vault·Secret Manager에 두고 실행 시 역할 권한으로 읽어요. 자동 교체도 걸 수 있어요.<br><sub>Keep database passwords and API keys out of .env files and images; store them in Secrets Manager, Key Vault or Secret Manager and read them at run time with role permissions, optionally with automatic rotation.</sub> | .env 파일이나 설정에 비밀번호를 넣어 이미지나 저장소에 포함하면, 그 이미지를 받은 누구나 비밀을 읽을 수 있고 한 번 퍼지면 회수하기 어려워요. AWS Secrets Manager(또는 Parameter Store), Azure Key Vault, Google Secret Manager에 비밀을 저장하고, 앱은 실행할 때 역할 권한으로 읽어 와요. 누가 언제 어떤 비밀을 읽었는지 감사 로그가 남고, 비밀마다 접근할 수 있는 역할을 따로 정할 수 있어요. Secrets Manager는 RDS 비밀번호를 정해진 주기로 자동 교체(rotation)하고 DB에도 반영해 줘요. 앱은 비밀을 캐시하되 교체 후에도 새 값을 다시 읽을 수 있게 만들어요. 쿠버네티스에서는 External Secrets Operator나 CSI 드라이버로 같은 저장소를 연결하고, 깃 저장소에는 비밀 스캐너를 걸어 실수를 막아요.<br><sub>Putting passwords in .env files or config baked into images or repositories lets anyone with the image read them, and once spread they are hard to recall. Store secrets in AWS Secrets Manager (or Parameter Store), Azure Key Vault or Google Secret Manager, and have apps read them at run time using role permissions. Audit logs record who read which secret when, and each secret can grant access to specific roles. Secrets Manager can rotate RDS passwords on a schedule and update the database automatically. Apps should cache secrets while still being able to reload new values after rotation. In Kubernetes, the External Secrets Operator or CSI drivers connect the same stores, and secret scanners on Git repositories catch mistakes.</sub> |

| **VPC와 서브넷**<br><sub>VPCs and subnets</sub> | VPC(VNet)는 클라우드 안의 격리된 나만의 네트워크예요. 공개·비공개·데이터 서브넷으로 나누고 라우팅 테이블로 인터넷 경로를 정해요.<br><sub>A VPC (VNet) is your isolated network in the cloud, split into public, private and data subnets, with routing tables deciding the internet paths.</sub> | VPC(Azure는 VNet)는 10.0.0.0/16처럼 IP 범위를 정해 만드는 격리된 가상 네트워크이고, 그 안을 서브넷으로 나눠요. 서브넷이 public인지 private인지는 라우팅 테이블이 정해요. 기본 경로(0.0.0.0/0)가 인터넷 게이트웨이(IGW)로 향하면 public 서브넷이고, 로드밸런서처럼 외부에 열려야 하는 것만 둬요. 앱 서버는 private 서브넷에 두고, 패키지 설치나 외부 API 호출처럼 밖으로 나가는 트래픽은 public 서브넷의 NAT 게이트웨이를 거쳐요. 이렇게 하면 밖으로는 나갈 수 있어도 인터넷에서 직접 들어올 수는 없어요. DB는 인터넷 경로가 아예 없는 서브넷에 두고 앱 서버에서만 접근해요. 서브넷은 AZ마다 하나씩 만들어 고가용성을 챙기고, NAT 게이트웨이는 처리한 데이터 양에 요금이 붙으니 트래픽이 많은 S3 접근은 엔드포인트로 돌려요. GCP의 VPC는 전역이고 서브넷이 리전 단위예요.<br><sub>A VPC (VNet in Azure) is an isolated virtual network created with an IP range such as 10.0.0.0/16 and divided into subnets. Routing tables decide whether a subnet is public or private. If the default route (0.0.0.0/0) points to an internet gateway (IGW) the subnet is public, and it should hold only what must face the internet, such as load balancers. App servers sit in private subnets, and their outbound traffic for package installs or external APIs passes through a NAT gateway in a public subnet, so they can reach out but cannot be reached directly. Databases sit in subnets with no internet route at all, reachable only from app servers. Subnets are created per AZ for high availability, and since NAT gateways bill per data processed, heavy S3 traffic should go through endpoints. GCP VPCs are global with regional subnets.</sub> |
| **보안 그룹과 NACL**<br><sub>Security groups and NACLs</sub> | 보안 그룹은 인스턴스에 붙는 상태 저장 방화벽(허용만), NACL은 서브넷 경계의 무상태 필터(허용·거부, 번호 순)예요. 계층마다 필요한 포트만 열어요.<br><sub>Security groups are stateful, allow-only firewalls on instances, while NACLs are stateless allow/deny filters at subnet boundaries evaluated in order; open only the ports each tier needs.</sub> | 보안 그룹은 인스턴스의 네트워크 인터페이스에 붙는 방화벽이에요. 허용 규칙만 있어서 적지 않은 것은 모두 막히고, 상태 저장(stateful)이라 허용된 요청의 응답은 자동으로 나가요. 출처를 IP 대신 다른 보안 그룹으로 지정할 수 있어서 “DB는 앱 서버 그룹에서 오는 5432만 허용”처럼 계층 사이 규칙을 간단히 쓸 수 있고, 서버가 늘거나 IP가 바뀌어도 규칙은 그대로예요. NACL은 서브넷 경계에서 동작하는 무상태(stateless) 필터로, 번호가 작은 규칙부터 평가하고 허용과 거부를 모두 쓸 수 있어요. 무상태라 응답이 나가는 임시 포트(1024–65535)도 직접 열어야 해서 실수가 잦아요. 그래서 보통은 보안 그룹으로 세밀하게 막고, NACL은 특정 IP 대역 차단처럼 넓은 규칙에만 써요. Azure NSG와 GCP 방화벽 규칙은 상태 저장 방식에 우선순위로 허용·거부를 함께 써요. SSH 포트를 열기보다 Session Manager나 IAP 같은 접속 도구를 쓰는 편이 안전해요.<br><sub>Security groups are firewalls attached to an instance’s network interface. They hold allow rules only, so anything unlisted is blocked, and being stateful they let replies to allowed requests flow out automatically. Sources can reference other security groups instead of IPs, which makes tier rules such as “the database accepts 5432 only from the app servers’ group” simple and stable as servers scale or change IPs. NACLs are stateless filters at subnet boundaries that evaluate numbered rules from lowest to highest and support both allow and deny. Because they are stateless, return ephemeral ports (1024–65535) must be opened explicitly, a frequent source of mistakes. So security groups usually do the fine-grained work, and NACLs handle broad rules such as blocking IP ranges. Azure NSGs and GCP firewall rules are stateful and combine allow and deny by priority. Access tools such as Session Manager or IAP are safer than opening SSH.</sub> |
| **클라우드 로드밸런서**<br><sub>Cloud load balancers</sub> | L7 로드밸런서는 경로·호스트로 HTTP를 나누고 TLS를 끝내며, L4는 TCP·UDP를 빠르게 넘겨요. 전역 로드밸런서는 사용자와 가까운 리전으로 보내요.<br><sub>L7 load balancers split HTTP by path or host and terminate TLS, L4 load balancers forward TCP and UDP quickly, and global load balancers send users to the nearest region.</sub> | L7(애플리케이션) 로드밸런서는 HTTP를 이해해서 /api는 API 서버로, /img는 이미지 서버로, shop.\* 호스트는 쇼핑 서비스로 보내고, TLS 인증서도 여기서 처리해요. AWS ALB, Azure Application Gateway, GCP 외부 애플리케이션 LB가 여기에 속해요. L4(네트워크) 로드밸런서는 TCP·UDP 연결만 보고 넘겨서 지연이 아주 짧고, 고정 IP가 필요하거나 DB·게임·MQTT 같은 비HTTP 트래픽에 써요(AWS NLB, Azure Load Balancer, GCP 네트워크 LB). Azure Front Door나 GCP 전역 외부 LB처럼 전역 L7은 하나의 주소(애니캐스트 IP)로 받아 사용자와 가까운 리전으로 보내고, 리전 장애 때는 다른 리전으로 넘겨요. 모든 로드밸런서는 헬스 체크로 응답하지 않는 대상을 빼고 회복하면 다시 넣으므로, 헬스 체크 경로는 가볍지만 실제 준비 상태를 반영해야 해요. 앞단에 WAF를 붙이면 SQL 인젝션 같은 공격도 걸러요.<br><sub>L7 (application) load balancers understand HTTP, sending /api to API servers, /img to image servers and shop.\* hosts to the shop service, and they terminate TLS. AWS ALB, Azure Application Gateway and GCP’s external Application Load Balancer belong here. L4 (network) load balancers forward TCP and UDP connections with minimal latency, suiting static IP needs and non-HTTP traffic such as databases, games or MQTT (AWS NLB, Azure Load Balancer, GCP Network Load Balancer). Global L7 options such as Azure Front Door and GCP’s global external load balancer accept traffic on one anycast address, send users to the nearest region and fail over when a region goes down. Every load balancer uses health checks to drop unresponsive targets and re-add them on recovery, so health endpoints should be light yet reflect real readiness. A WAF in front filters attacks such as SQL injection.</sub> |
| **DNS 라우팅과 CDN**<br><sub>DNS routing and CDNs</sub> | 관리형 DNS는 지연·가중치·장애 조치 정책으로 사용자를 알맞은 곳에 보내고, CDN은 전 세계 엣지에서 캐시해 가까이에서 응답해요.<br><sub>Managed DNS routes users with latency, weighted and failover policies, and CDNs cache content at edges worldwide to answer close to users.</sub> | Route 53, Azure DNS(전역 라우팅은 Traffic Manager), Cloud DNS 같은 관리형 DNS는 이름을 IP로 바꾸는 것을 넘어 라우팅 정책을 지원해요. 지연 기반 정책은 사용자에게 가장 빠른 리전의 주소를 알려 주고, 가중치 정책은 새 버전에 트래픽 10%만 보내는 식으로 점진 배포에 쓰고, 장애 조치 정책은 헬스 체크가 실패하면 대기 리전으로 바꿔요. 지역 기반 정책은 나라별로 다른 엔드포인트를 줘요. DNS 응답은 TTL 동안 캐시되므로 TTL이 길면 전환이 늦게 퍼져요. CDN(CloudFront, Azure Front Door, Cloud CDN)은 전 세계 엣지 서버에 콘텐츠를 캐시해서 사용자와 가까운 곳에서 응답하고 오리진 부하를 줄여요. 어떤 요청을 같은 캐시로 볼지(캐시 키), 얼마나 둘지(TTL), 언제 지울지(무효화)를 설계하고, 정적 파일은 app.3f9a.js처럼 해시 이름을 붙여 1년씩 캐시해요. CDN은 DDoS 완화와 WAF가 붙는 첫 관문이기도 해요.<br><sub>Managed DNS such as Route 53, Azure DNS (with Traffic Manager for global routing) and Cloud DNS supports routing policies beyond turning names into IPs. Latency-based policies answer with the fastest region’s address, weighted policies send, say, 10% of traffic to a new version for gradual rollouts, and failover policies switch to a standby region when health checks fail. Geolocation policies return different endpoints per country. DNS answers are cached for their TTL, so long TTLs slow down switchovers. CDNs (CloudFront, Azure Front Door, Cloud CDN) cache content on edge servers worldwide, answering near users and offloading the origin. Design what counts as the same cached request (cache keys), how long to keep it (TTL) and when to purge it (invalidation), and give static files hashed names such as app.3f9a.js so they can be cached for a year. CDNs are also the first line for DDoS mitigation and WAF.</sub> |
| **VPC 사이 프라이빗 연결**<br><sub>Private connectivity</sub> | VPC 피어링은 1:1이고 전이되지 않아서, VPC가 많아지면 Transit Gateway 같은 허브로 모아요. 관리형 서비스는 프라이빗 엔드포인트로 인터넷 없이 불러요.<br><sub>VPC peering is one-to-one and not transitive, so many VPCs are gathered on a hub such as Transit Gateway, and private endpoints reach managed services without the internet.</sub> | VPC 피어링은 두 VPC를 1:1로 이어서 사설 IP로 통신하게 해요. 하지만 전이되지 않아서 A-B, B-C를 이어도 A와 C는 통하지 않고, VPC가 n개면 연결이 n(n-1)/2개까지 늘어나요. 그래서 VPC가 많아지면 AWS Transit Gateway, Azure Virtual WAN(또는 허브-스포크 VNet), GCP Network Connectivity Center 같은 허브에 모두 연결하고, 라우팅과 방화벽 검사를 허브에 모아요. 프라이빗 엔드포인트(AWS PrivateLink·인터페이스 엔드포인트, Azure Private Endpoint, GCP Private Service Connect)는 S3, DB, 다른 회사의 SaaS 같은 서비스를 내 VPC 안의 사설 IP로 불러 와서 트래픽이 인터넷에 나가지 않게 해요. S3와 DynamoDB용 게이트웨이 엔드포인트는 무료라 NAT 게이트웨이 비용도 줄여요. 나중에 네트워크를 이으려면 IP 범위가 겹치지 않아야 하므로 조직 전체의 IP 주소 계획을 처음부터 세워요.<br><sub>VPC peering joins two VPCs one-to-one so they talk over private IPs. It is not transitive, though: peering A-B and B-C does not connect A and C, and n VPCs can need up to n(n-1)/2 links. As VPCs multiply, they connect to a hub such as AWS Transit Gateway, Azure Virtual WAN (or hub-and-spoke VNets) or GCP Network Connectivity Center, which centralizes routing and firewall inspection. Private endpoints (AWS PrivateLink interface endpoints, Azure Private Endpoint, GCP Private Service Connect) bring services such as S3, databases or other companies’ SaaS onto private IPs inside your VPC, keeping traffic off the internet. Gateway endpoints for S3 and DynamoDB are free and also cut NAT gateway costs. Future connections need non-overlapping IP ranges, so plan addressing for the whole organization from the start.</sub> |
| **하이브리드 연결**<br><sub>Hybrid connectivity</sub> | 사이트 간 VPN은 인터넷 위 암호화 터널로 빠르게 시작하고, Direct Connect·ExpressRoute·Interconnect 전용선은 안정적인 대역폭을 줘요. 둘을 함께 두면 이중화돼요.<br><sub>Site-to-site VPNs start fast with encrypted tunnels over the internet, dedicated lines such as Direct Connect, ExpressRoute and Interconnect give steady bandwidth, and pairing them adds redundancy.</sub> | 사내 데이터센터와 클라우드를 잇는 가장 빠른 방법은 사이트 간 VPN이에요. 인터넷 위에 IPsec 암호화 터널을 만들어서 몇 시간 만에 시작할 수 있지만, 대역폭과 지연이 인터넷 상태에 따라 흔들려요. AWS Direct Connect, Azure ExpressRoute, Google Cloud Interconnect는 통신사나 코로케이션 시설을 통한 전용 회선이라 대역폭과 지연이 일정하고, 대량 데이터 전송 요금이 더 싸기도 해요. 대신 회선 개통에 수주에서 수개월이 걸리고 고정 비용이 커서, 대량 데이터나 지연에 민감한 업무에 써요. 보통 전용선을 주 경로로, VPN을 백업 경로로 함께 두고 BGP로 경로를 주고받아 한쪽이 끊기면 자동으로 우회하게 해요. DNS도 사내와 클라우드 양쪽에서 서로의 이름이 풀리도록 조건부 전달을 설정하고, 사내 IP 대역과 겹치지 않게 VPC 주소를 정해요.<br><sub>The quickest way to link an on-premises data center with the cloud is a site-to-site VPN. It builds IPsec tunnels over the internet and can be running within hours, but bandwidth and latency vary with internet conditions. AWS Direct Connect, Azure ExpressRoute and Google Cloud Interconnect are dedicated lines through carriers or colocation facilities, offering steady bandwidth and latency and often cheaper bulk data transfer. They take weeks to months to provision and carry higher fixed costs, so they serve heavy data or latency-sensitive workloads. A common setup uses the dedicated line as the primary path and a VPN as backup, exchanging routes over BGP so traffic fails over automatically. DNS needs conditional forwarding so names resolve in both directions, and VPC ranges must not overlap with on-premises addresses.</sub> |

| **가상 머신과 인스턴스 유형**<br><sub>Virtual machines and instance types</sub> | EC2·Azure VM·Compute Engine은 vCPU·메모리를 골라 빌리는 서버예요. 워크로드에 맞는 계열을 고르고 온디맨드·약정·스팟을 섞어 비용을 맞춰요.<br><sub>EC2, Azure VMs and Compute Engine are servers rented by vCPU and memory; pick the family that fits the workload and mix on-demand, committed and spot capacity to fit the budget.</sub> | 가상 머신은 클라우드의 가장 기본적인 컴퓨팅으로, vCPU, 메모리, 디스크, 네트워크 성능을 골라 빌리는 서버예요. Target tracking policies set goals such as “average CPU at 50%” or “1,000 requests per server,” adding servers above the target and removing them when there is slack. New servers take minutes to boot and become ready, so predictable peaks such as morning traffic are handled ahead of time with scheduled or predictive scaling. Scale-in should be slow with cooldowns to avoid flapping. Servers failing health checks are terminated and replaced automatically, which presumes stateless design with sessions in Redis and files in object storage. Spanning groups across AZs refills capacity in other AZs during an outage. Pre-baked golden images shorten boot time and speed up reactions.</sub> |
| **클라우드 컨테이너 서비스**<br><sub>Cloud container services</sub> | 관리형 쿠버네티스(EKS·AKS·GKE)는 컨트롤 플레인을, Fargate·Autopilot은 노드까지, Cloud Run·Container Apps는 확장까지 클라우드가 맡아요. 통제권과 운영 부담을 맞바꿔요.<br><sub>Managed Kubernetes (EKS, AKS, GKE) hands off the control plane, Fargate and Autopilot hand off nodes too, and Cloud Run and Container Apps hand off scaling as well, trading control for less operations.</sub> | EKS, AKS, GKE 같은 관리형 쿠버네티스는 API 서버와 etcd 같은 컨트롤 플레인을 클라우드가 운영하고 업그레이드해요. 대신 노드 VM의 크기, 패치, 오토스케일링은 보통 내가 챙겨요. ECS는 쿠버네티스보다 단순한 AWS 고유의 오케스트레이터예요. 쿠버네티스는 이식성과 생태계, 세밀한 제어가 장점이지만 배울 것과 운영할 것이 많고, 서버리스 컨테이너는 편하지만 실행 시간, 네트워크, 상태 유지에 제약이 있어요. 팀 규모와 필요한 제어 수준으로 골라요. 이미지는 ECR, ACR, Artifact Registry에 두고 취약점 스캔을 켜요.<br><sub>Managed Kubernetes such as EKS, AKS and GKE has the cloud running and upgrading the control plane, including the API server and etcd, while you usually handle node VM sizing, patching and autoscaling. ECS is AWS’s own orchestrator, simpler than Kubernetes. Kubernetes offers portability, an ecosystem and fine control but much to learn and operate, while serverless containers are easy but limit run time, networking and state. Choose by team size and the control you need. Images live in ECR, ACR or Artifact Registry with vulnerability scanning turned on.</sub> |
| **서버리스 함수**<br><sub>Serverless functions</sub> | Lambda·Azure Functions·Cloud Run functions는 이벤트가 오면 핸들러를 실행하고 요청만큼 자동 확장되며 쓴 만큼만 과금돼요. 콜드 스타트와 실행 시간 제한을 감안해요.<br><sub>Lambda, Azure Functions and Cloud Run functions run handlers on events, scale automatically with requests and bill only for use, with cold starts and time limits to keep in mind.</sub> | 서버리스 함수는 HTTP 요청, 파일 업로드, 큐 메시지, 일정 같은 이벤트가 오면 내가 쓴 핸들러 함수를 실행해요. 서버 프로비저닝, OS 패치, 확장은 클라우드가 맡고, 동시 요청 수만큼 인스턴스가 자동으로 늘어나며, 실행 횟수와 실행 시간(메모리 크기와 곱한 값)만큼만 요금을 내요. 트래픽이 없으면 비용도 거의 없어서 들쭉날쭉한 부하나 작은 자동화에 잘 맞아요. 한동안 호출이 없다가 처음 실행되면 런타임을 띄우는 콜드 스타트 지연이 생겨요. 의존성을 줄이고, DB 연결이나 SDK 클라이언트는 핸들러 밖에서 만들어 재사용하고, 지연이 중요한 API는 미리 데워 두는 프로비저닝 동시성을 써요. Lambda는 최대 15분까지 실행되고 로컬 상태가 유지되지 않으므로 짧고 상태 없는 일에 맞아요. 동시 실행이 폭증하면 DB 연결이 넘치니 RDS Proxy 같은 연결 풀을 두고, 꾸준한 고부하라면 컨테이너가 더 쌀 수 있어요.<br><sub>Serverless functions run a handler you write when an event arrives, such as an HTTP request, a file upload, a queue message or a schedule. Idle time costs almost nothing, so they fit spiky load and small automations. The first call after idling pays a cold start while the runtime boots. Trim dependencies, create database connections and SDK clients outside the handler for reuse, and use provisioned concurrency to pre-warm latency-sensitive APIs. Lambda runs at most 15 minutes and keeps no lasting local state, making it best for short, stateless work. Bursts of concurrency can exhaust database connections, so add a pool such as RDS Proxy, and for steady heavy load containers may be cheaper.</sub> |
| **이벤트 기반 아키텍처**<br><sub>Event-driven architecture</sub> | 생산자는 “무슨 일이 있었다”만 이벤트로 발행하고, EventBridge·Event Grid·Eventarc가 규칙으로 골라 여러 대상에 전달해요. 서비스가 느슨하게 연결돼요.<br><sub>Producers publish only what happened, and EventBridge, Event Grid or Eventarc match events with rules and deliver them to many targets, loosely coupling services.</sub> | 이벤트 기반 아키텍처에서 주문 서비스는 “주문이 들어왔다(OrderPlaced)”는 사실만 이벤트로 발행하고, 누가 그 이벤트로 무엇을 하는지는 몰라요. AWS EventBridge, Azure Event Grid, GCP Eventarc 같은 이벤트 버스는 이벤트의 source, type, 내용을 보는 규칙으로 메일 발송, 재고 차감, 분석 적재 같은 여러 대상에 전달해요. 새 기능이 필요하면 규칙과 소비자를 하나 더 붙이면 되므로 생산자 코드를 건드리지 않고, 한 소비자가 느려지거나 죽어도 다른 흐름은 영향을 덜 받아요. 클라우드 서비스 자체의 이벤트(S3 업로드, 인스턴스 상태 변화)도 같은 버스로 받아 자동화를 만들 수 있어요. 전달은 보통 “최소 한 번”이라 같은 이벤트가 두 번 올 수 있으니 소비자를 멱등하게 만들고, 계속 실패한 이벤트는 재시도 후 DLQ로 보내요. 흐름이 눈에 보이지 않게 되기 쉬우니 이벤트 스키마를 버전 관리하고 상관 ID로 추적해요.<br><sub>In event-driven architecture an order service publishes only the fact “an order was placed” (OrderPlaced) without knowing who does what with it. Event buses such as AWS EventBridge, Azure Event Grid and GCP Eventarc use rules on an event’s source, type and content to deliver it to targets such as sending mail, reducing stock and loading analytics. A new feature is just another rule and consumer, leaving producer code untouched, and one slow or failing consumer affects other flows less. Events from cloud services themselves, such as S3 uploads or instance state changes, arrive on the same bus for automation. Delivery is usually at least once, so the same event may come twice; make consumers idempotent and send repeatedly failing events to a DLQ after retries. Flows easily become invisible, so version event schemas and trace them with correlation IDs.</sub> |
| **API 게이트웨이**<br><sub>API gateways</sub> | API Gateway·API Management·Apigee는 모든 API 요청의 정문이에요. 경로별 라우팅, 인증, 사용량 제한, 캐시, 로그를 한곳에서 처리해요.<br><sub>API Gateway, API Management and Apigee are the front door for API calls, handling routing, authentication, throttling, caching and logging in one place.</sub> | API 게이트웨이는 클라이언트가 만나는 하나의 입구로, GET /orders/{id}는 Lambda 함수로, POST /orders는 주문 서비스로 보내는 식으로 경로와 메서드별로 백엔드를 연결해요. AWS API Gateway, Azure API Management(APIM), Google Apigee와 API Gateway가 대표적이에요. JWT 검증, API 키, IAM 서명 같은 인증을 입구에서 처리하므로 백엔드는 업무 로직에만 집중할 수 있어요. 키나 클라이언트별로 초당 요청 수 제한(throttling)과 월 할당량을 걸어 트래픽 폭주와 남용을 막고, 넘으면 429 Too Many Requests를 돌려줘요. 응답 캐시, 요청·응답 형식 변환, 접근 로그와 지표, v1·v2 같은 API 버전과 dev·prod 스테이지 관리도 게이트웨이에서 해요. APIM과 Apigee는 개발자 포털과 API 상품화 기능까지 갖춰 외부에 API를 공개할 때 유용해요. 게이트웨이에 업무 로직을 넣기 시작하면 또 하나의 모놀리스가 되니 경계를 지켜요.<br><sub>An API gateway is the single entrance clients meet, connecting each path and method to a backend: GET /orders/{id} to a Lambda function, POST /orders to the order service. AWS API Gateway, Azure API Management (APIM), and Google’s Apigee and API Gateway are the main options. Authentication such as JWT validation, API keys or IAM signatures happens at the door, so backends can focus on business logic. Per-key or per-client rate limits (throttling) and monthly quotas stop floods and abuse, answering 429 Too Many Requests when exceeded. Response caching, request and response transformation, access logs and metrics, and API versions such as v1 and v2 with dev and prod stages are handled there too. APIM and Apigee add developer portals and API productization, useful when publishing APIs externally. Putting business logic in the gateway turns it into another monolith, so keep the boundary.</sub> |

| **오브젝트 스토리지**<br><sub>Object storage</sub> | S3·Blob Storage·Cloud Storage는 버킷에 키로 객체를 저장하는 사실상 무한한 저장소예요. 저장 등급과 수명 주기로 비용을, 퍼블릭 차단과 서명 URL로 보안을 챙겨요.<br><sub>S3, Blob Storage and Cloud Storage store objects by key in buckets with practically unlimited capacity; storage classes and lifecycle rules manage cost, while blocked public access and signed URLs manage security.</sub> | 오브젝트 스토리지는 버킷 안에 키(이름)로 객체(파일과 메타데이터)를 저장해요. s3://acme-media/2026/11/cat.jpg에서 폴더처럼 보이는 경로도 사실은 키 이름의 일부예요. | **클라우드 메시징**<br><sub>Cloud messaging</sub> | 큐(SQS·Service Bus)는 작업을 한 소비자에게, 토픽(SNS·Pub/Sub)은 구독자 모두에게, 스트림(Kinesis·Event Hubs)은 순서대로 쌓아 다시 읽게 해요.<br><sub>Queues (SQS, Service Bus) hand each job to one consumer, topics (SNS, Pub/Sub) copy to every subscriber, and streams (Kinesis, Event Hubs) keep ordered logs that can be replayed.</sub> | 큐는 생산자와 소비자 사이의 완충지대예요. SQS 표준 큐는 순서와 단 한 번 전달을 보장하지 않고, FIFO 큐는 보장하는 대신 처리량에 한계가 있어요. 어떤 경우든 소비자는 멱등하게 만들어요.<br><sub>Queues buffer between producers and consumers. Jobs placed on Amazon SQS or Azure Service Bus queues are pulled one by one by workers at their own pace even during spikes, and adding workers raises throughput. SQS standard queues guarantee neither order nor exactly-once delivery, while FIFO queues do at limited throughput. Either way, make consumers idempotent.</sub> |

| **클라우드 모니터링**<br><sub>Cloud monitoring</sub> | CloudWatch·Azure Monitor·Cloud Monitoring으로 지표·로그·트레이스를 모으고, CPU 같은 원인보다 지연·오류율처럼 사용자가 느끼는 증상에 알람을 걸어요.<br><sub>CloudWatch, Azure Monitor and Cloud Monitoring gather metrics, logs and traces, and alarms should fire on user-facing symptoms such as latency and error rate rather than causes such as CPU.</sub> | CloudWatch, Azure Monitor, Google Cloud Monitoring은 클라우드 서비스의 지표를 자동으로 모아요. 요청 수, CPU, 지연, 오류율 같은 숫자 시계열은 대시보드와 알람의 재료예요. 로그(CloudWatch Logs, Log Analytics, Cloud Logging)는 요청과 오류의 자세한 기록으로, 구조화된 JSON으로 남기면 쿼리 언어로 검색하고 지표로 바꾸기도 쉬워요. 분산 트레이스(AWS X-Ray, Application Insights, Cloud Trace)는 요청 하나가 게이트웨이, 서비스, DB를 지나며 어디서 느려졌는지 구간별로 보여줘요. 요즘은 OpenTelemetry로 세 신호를 함께 수집해 어느 백엔드로든 보내요. 알람은 CPU 80%처럼 원인보다 p99 지연이나 오류율처럼 사용자가 실제로 느끼는 증상에 걸고, 알람마다 확인할 것과 조치를 적은 런북을 연결해요. 로그는 양이 많아 비용이 빨리 늘므로 보존 기간과 샘플링을 정하고, CloudTrail 같은 감사 로그는 별도 계정에 오래 보관해요.<br><sub>CloudWatch, Azure Monitor and Google Cloud Monitoring collect metrics from cloud services automatically, and numeric time series such as requests, CPU, latency and error rate fuel dashboards and alarms. | **고가용성 설계**<br><sub>High availability design</sub> | 가용성 목표를 허용 중단 시간으로 바꿔 정하고, 모든 계층을 여러 AZ에 중복해 단일 장애점을 없애요. 직렬 의존성은 가용성을 곱해서 깎아요.<br><sub>Set availability targets as allowed downtime, remove single points of failure by duplicating every tier across AZs, and remember that serial dependencies multiply availability down.</sub> | 가용성 99.9%는 한 달에 약 43분, 99.99%는 약 4분, 99.999%는 약 26초의 중단을 허용한다는 뜻이에요. 숫자를 허용 중단 시간으로 바꿔 보면 목표가 얼마나 어려운지, 배포나 점검 시간이 들어갈 여지가 있는지 현실적으로 보여요. 고가용성의 기본은 단일 장애점을 없애는 거예요. 로드밸런서, 앱 서버, 캐시, DB까지 모든 계층을 여러 AZ에 두 개 이상 두고, 하나가 죽어도 나머지가 부하를 감당할 여유를 남겨요. 직렬로 엮인 의존성은 가용성을 곱하므로 99.9%짜리 세 서비스를 차례로 거치면 약 99.7%가 돼요. 그래서 외부 의존성에는 타임아웃, 재시도, 서킷 브레이커, 캐시된 값으로 대체하는 동작을 둬요. 다중 리전은 리전 전체 장애까지 버티지만 데이터 복제, 비용, 운영 복잡도가 크게 늘어요. 각 클라우드 서비스의 SLA를 확인하고, 일부러 장애를 내 보는 게임 데이로 설계가 실제로 버티는지 검증해요.<br><sub>Availability of 99.9% allows about 43 minutes of downtime a month, 99.99% about 4 minutes and 99.999% about 26 seconds. Serial dependencies multiply availability, so passing through three 99.9% services in sequence yields about 99.7%. Multi-region designs survive whole-region outages but add replication, cost and operational complexity. Check each cloud service’s SLA, and verify designs with game days that inject failures on purpose.</sub> |
| **백업과 재해 복구**<br><sub>Backup and disaster recovery</sub> | RPO(잃어도 되는 데이터)와 RTO(복구 시간) 목표에 맞춰 백업·복원, 파일럿 라이트, 웜 스탠바이, 멀티 사이트 중 전략을 고르고 복원 훈련으로 검증해요.<br><sub>Choose backup-restore, pilot light, warm standby or multi-site according to RPO (data you may lose) and RTO (time to recover) targets, and prove it with restore drills.</sub> | RPO(복구 시점 목표)는 장애가 났을 때 얼마 전까지의 데이터를 잃어도 되는지, RTO(복구 시간 목표)는 서비스가 다시 돌기까지 얼마나 걸려도 되는지예요. 재해 복구 전략은 네 단계로 나뉘어요. 백업·복원은 백업만 다른 리전에 두고 장애 때 전부 새로 만들어서 가장 싸지만 RTO가 몇 시간이에요. 파일럿 라이트는 DB 같은 핵심 데이터만 다른 리전에 계속 복제하고 서버는 장애가 나면 그때 띄워요. 웜 스탠바이는 작은 규모의 전체 환경을 늘 켜 두었다가 키우고, 멀티 사이트(액티브-액티브)는 두 리전이 함께 트래픽을 받아 RPO·RTO가 거의 0이지만 가장 비싸요. AWS Backup, Azure Backup, Google Backup and DR 같은 서비스로 백업 정책을 한곳에서 관리하고, 백업은 다른 계정과 리전에 지울 수 없게(불변, Object Lock·볼트 잠금) 보관해야 랜섬웨어나 계정 탈취에도 살아남아요. 복원해 본 적 없는 백업은 믿을 수 없으니 정기적으로 실제 복원 훈련을 하고 걸린 시간을 RTO와 비교해요.<br><sub>The recovery point objective (RPO) is how much recent data you can lose in an incident, and the recovery time objective (RTO) is how long the service may stay down. Disaster recovery strategies come in four steps. Backup and restore keeps only backups in another region and rebuilds everything on failure, the cheapest option but with an RTO of hours. Pilot light continuously replicates only core data such as databases to another region and starts servers on failure. Warm standby keeps a scaled-down full environment running to scale up, and multi-site (active-active) has two regions serving traffic together, with near-zero RPO and RTO at the highest cost. Services such as AWS Backup, Azure Backup and Google Backup and DR manage backup policies centrally, and backups must sit in another account and region, made immutable (Object Lock, vault lock), to survive ransomware or account takeover. A backup never restored cannot be trusted, so drill real restores regularly and compare the time taken against the RTO.</sub> |
| **FinOps와 비용 최적화**<br><sub>FinOps and cost optimization</sub> | 태그로 비용을 보이게 하고, 크기 조정·미사용 정리·약정으로 줄이고, 예산 알람과 이상 탐지로 지켜요. 데이터 전송료 같은 숨은 비용도 설계 때 따져요.<br><sub>Make cost visible with tags, cut it by rightsizing, cleanup and commitments, and guard it with budget alerts and anomaly detection, weighing hidden costs such as data transfer at design time.</sub> | FinOps는 엔지니어링, 재무, 비즈니스가 함께 클라우드 비용을 관리하는 문화이자 방법이에요. 첫 단계는 보이게 하기로, 모든 리소스에 team, service, env 같은 태그를 붙여 누가 무엇에 얼마를 쓰는지 배분해요. 태그가 없는 리소스는 정책으로 막거나 찾아내요. 다음은 줄이기예요. 사용률이 낮은 인스턴스와 DB를 작은 크기로 바꾸고(rightsizing), 지운 인스턴스에 남은 디스크·탄력적 IP·오래된 스냅샷을 정리하고, 꾸준한 사용량에는 약정 할인을, 개발 환경은 밤과 주말에 꺼요. 마지막은 지키기로, 예산 알람과 비용 이상 탐지(AWS Budgets·Cost Anomaly Detection, Azure Cost Management, GCP 예산 알림)로 갑작스러운 비용 사고를 일찍 잡아요. 인터넷이나 다른 리전으로 나가는 데이터 전송료(egress), NAT 게이트웨이 처리 요금, 로그 저장 비용은 잘 보이지 않는 복병이라 아키텍처를 그릴 때 데이터 흐름의 비용도 함께 계산해요. 요청당·고객당 같은 단위 비용을 추적하면 성장과 낭비를 구분할 수 있어요.<br><sub>FinOps is a culture and practice of engineering, finance and business managing cloud cost together. The first step is visibility: tag every resource with keys such as team, service and env to allocate who spends what, and block or hunt down untagged resources with policies. Next comes cutting: rightsize underused instances and databases, clean up disks, elastic IPs and old snapshots left behind by deleted instances, cover steady usage with commitments, and shut down dev environments at night and on weekends. Last is guarding: budget alerts and cost anomaly detection (AWS Budgets and Cost Anomaly Detection, Azure Cost Management, GCP budget alerts) catch sudden cost incidents early. Outbound data transfer (egress) to the internet or other regions, NAT gateway processing and log storage are hidden traps, so weigh data-flow cost when drawing architecture. Tracking unit cost, such as per request or per customer, separates growth from waste.</sub> |
| **마이그레이션 7R**<br><sub>The 7 Rs of migration</sub> | 앱마다 retire·retain·rehost·relocate·replatform·repurchase·refactor 중 전략을 골라요. 빠른 이전과 클라우드 이점 사이에서 균형을 잡고 웨이브로 옮겨요.<br><sub>Pick retire, retain, rehost, relocate, replatform, repurchase or refactor for each app, balancing speed against cloud benefits, and migrate in waves.</sub> | 클라우드 마이그레이션은 앱과 서버 목록, 그리고 서로의 의존성을 파악하는 것에서 시작해요. 그다음 앱마다 7R 중 전략을 골라요. 더 쓰지 않는 앱은 없애고(retire), 규제나 기술 문제로 아직 못 옮기는 앱은 남겨둬요(retain). rehost(lift & shift)는 VM을 그대로 옮겨서 가장 빠르지만 클라우드다운 이점은 적고, relocate는 VMware 같은 가상화 플랫폼째 옮겨요. replatform은 DB를 관리형 RDS로 바꾸거나 컨테이너로 감싸는 정도로 조금 손봐서 노력 대비 이득이 좋아요. repurchase는 자체 CRM을 SaaS로 갈아타는 식이고, refactor는 서버리스나 마이크로서비스로 다시 설계해서 이득이 가장 크지만 시간과 위험도 커요. 의존성이 묶인 앱끼리 그룹으로 만들어 작은 파일럿부터 웨이브 단위로 옮기고, 웨이브마다 데이터 동기화, 전환 시점, 롤백 계획을 정해요. 데이터는 AWS DMS나 Database Migration Service로 복제하며 옮기고, 옮긴 뒤에는 실제 사용량을 보고 크기와 비용을 다시 최적화해요.<br><sub>Cloud migration starts with an inventory of apps, servers and their dependencies. Each app then gets one of the 7 Rs. Apps no longer used are retired, and those that regulations or technology keep in place are retained for now. Rehosting (lift and shift) moves VMs as-is, fastest but with few cloud benefits, and relocating moves whole virtualization platforms such as VMware. Replatforming makes modest changes, such as moving a database to managed RDS or wrapping an app in containers, offering good returns for the effort. Repurchasing swaps, say, an in-house CRM for SaaS, and refactoring redesigns around serverless or microservices for the largest gains at the highest time and risk. Dependent apps are grouped and moved in waves starting with a small pilot, each wave with data synchronization, a cutover time and a rollback plan. Data is replicated across with AWS DMS or Database Migration Service, and after moving, sizes and costs are re-optimized based on real usage.</sub> |
