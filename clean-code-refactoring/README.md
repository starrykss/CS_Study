| **순환 복잡도와 인지 복잡도**<br><sub>Cyclomatic and cognitive complexity</sub> | 같은 배송비 규칙을 중첩 if, 가드 절, 한 줄 &&로 쓰자 순환 복잡도는 모두 5였지만 인지 복잡도는 10, 4, 2로 갈렸어요.<br><sub>Same shipping rule as nested ifs, guard clauses and a one-line &&: cyclomatic 5 for all, cognitive 10, 4 and 2.</sub> | 코드가 얼마나 복잡한지 숫자로 재는 가장 오래된 방법은 순환 복잡도예요. 함수 안의 결정 지점, 곧 if, 반복문, case, &&와 \|\| 같은 갈림길을 세고 1을 더해요. 서로 다른 실행 경로의 최소 개수라서, 모든 분기를 한 번씩 지나려면 테스트가 몇 개 필요한지 알려 줘요. 그런데 이 숫자는 사람이 읽을 때 느끼는 어려움과 자주 어긋나요. 그래서 SonarSource가 제안한 인지 복잡도는 흐름이 끊길 때마다 1을 더하고, 중첩된 구조에는 깊이만큼 더 많이 더해요. 같은 배송비 규칙, 곧 주문이 있고 상품이 있고 국내이고 5만 원 미만이면 3,000원이라는 규칙을 세 가지 모양으로 써서 ESLint의 complexity 규칙과 eslint-plugin-sonarjs로 쟀어요. if를 네 겹으로 중첩한 모양은 순환 5, 인지 10, 깊이 4였어요. 조건이 안 맞으면 바로 0을 돌려주는 가드 절 모양은 순환 5, 인지 4, 깊이 1이었어요. 네 조건을 &&로 한 줄에 이은 모양은 순환 5, 인지 2였어요. 순환 복잡도는 세 모양을 구별하지 못했어요. 길의 수는 똑같기 때문이에요. 반대로 요일 일곱 개를 고르는 switch는 순환 8로 더 높았지만 인지 1이었어요. 갈래가 많아도 한 줄로 늘어서 있어 한눈에 읽히기 때문이에요. 실제 코드에서도 두 지표는 갈렸어요. Fastify의 Context 생성자는 a \|\| b 꼴의 기본값을 여러 번 이어 붙여 순환 11, 인지 0이었어요. 스키마를 정리하는 normalizeSchema는 반복문 안의 if 안에 다시 반복문이 있어 순환 17, 인지 39였어요. 두 지표는 쓰임이 달라요. 순환 복잡도는 테스트를 몇 개 짜야 하는지 가늠할 때 쓰고, 인지 복잡도는 읽기 어려운 함수를 골라 리팩터링할 때 써요. sonarjs의 기본 한도는 함수당 15예요. 인지 복잡도를 낮추는 방법은 대개 중첩을 줄이는 거예요. 가드 절로 일찍 돌려주고, 깊은 블록을 이름 있는 함수로 꺼내고, 조건을 이름 있는 변수로 바꿔요.<br><sub>The oldest way to put a number on how complex code is, cyclomatic complexity, counts the decision points in a function, its ifs, loops, cases and && or \|\| forks, and adds one. As the minimum number of distinct execution paths, it tells how many tests it takes to pass every branch once. Yet this number often disagrees with how hard code feels to read, so cognitive complexity, proposed by SonarSource, adds one for each break in the linear flow and adds more for structures nested deeper. The same shipping rule, charging 3,000 KRW when there is an order, it has items, it is domestic and it is under 50,000 KRW, was written in three shapes and measured with ESLint’s complexity rule and eslint-plugin-sonarjs. Four nested ifs scored 5 cyclomatic, 10 cognitive and a depth of 4. Guard clauses that return 0 as soon as a condition fails scored 5, 4 and a depth of 1. One line joining the four conditions with && scored 5 and 2. Cyclomatic complexity could not tell the three apart, because the number of paths is the same. Conversely, a switch choosing among seven days scored a higher 8 cyclomatic but only 1 cognitive, since its many branches sit side by side and read at a glance. The two metrics diverged in real code too. Fastify’s Context constructor chains many a \|\| b defaults and scored 11 cyclomatic but 0 cognitive, while normalizeSchema, which tidies route schemas with loops inside ifs inside loops, scored 17 and 39. The two serve different purposes: cyclomatic complexity estimates how many tests to write, and cognitive complexity picks the hard-to-read functions worth refactoring, with sonarjs defaulting to a limit of 15 per function. Lowering cognitive complexity usually means reducing nesting, returning early with guard clauses, pulling deep blocks out into named functions and turning conditions into named variables.</sub> |
| **지표를 흐리는 생성된 코드**<br><sub>Generated code that skews metrics</sub> | Fastify에서 파일별 복잡도 1위는 자동 생성된 1,189줄짜리 검증 파일이었어요. 함수 하나가 순환 441, 인지 4,602였어요.<br><sub>Fastify’s most complex file was a generated 1,189-line validator; one function scored 441 cyclomatic and 4,602 cognitive.</sub> | 코드 품질 지표를 처음 켜면 대개 저장소 전체를 한 번에 재요. 그런데 저장소에는 사람이 쓰지 않은 코드도 섞여 있어요. Fastify의 lib 폴더에는 자동으로 만들어진 파일이 두 개 있어요. config-validator.js는 서버 설정의 JSON 스키마를 Ajv로 미리 컴파일해 만든 1,189줄짜리 파일이고, error-serializer.js는 오류 응답을 JSON으로 바꾸는 135줄짜리 파일이에요. 둘 다 첫 줄에 자동 생성된 파일이니 고치지 말라는 주석이 있어요. ESLint로 함수마다 순환 복잡도를 재서 파일별로 더하자 config-validator.js가 441로 1위였어요. 사람이 쓴 파일 가운데 가장 복잡한 reply.js가 263, fastify.js가 205, route.js가 188이었으니 넉넉한 차이예요. 441은 거의 전부 validate10이라는 함수 하나에서 나왔고, 이 함수의 인지 복잡도는 4,602였어요. 사람이 쓴 함수 489개의 순환 복잡도를 모두 더하면 1,702인데, 생성된 함수 3개가 470을 더해 전체 2,172 가운데 21.6%를 차지해요. 이대로 대시보드를 만들면 가장 복잡한 코드는 아무도 열어 보지 않는 파일이 되고, 평균과 한도를 넘는 함수 개수, 파일 순위가 모두 이 파일 하나에 끌려가요. 생성된 코드는 읽거나 직접 고치는 대상이 아니에요. 바꾸려면 생성기나 그 입력, 여기서는 설정 스키마를 고쳐야 하고, 검증은 생성기를 테스트해서 해요. 그래서 지표를 재기 전에 생성물, 외부에서 그대로 가져온 코드, 압축된 번들, 테스트 스냅숏, 잠금 파일을 제외 목록에 넣어요. Fastify도 이 파일 맨 위에 c8 ignore 주석을 달아 테스트 커버리지 계산에서는 이미 빼고 있었어요. 지표는 무엇을 셀지 정한 뒤에야 의미가 생겨요. 같은 이유로 복잡도 한도를 CI에 걸 때도 생성된 파일 때문에 빌드가 깨지지 않게 경로를 먼저 정리해요.<br><sub>When quality metrics are first switched on, they usually measure the whole repository at once, yet repositories mix in code no person wrote. Fastify’s lib folder holds two generated files: config-validator.js, 1,189 lines produced by precompiling the JSON schema of the server options with Ajv, and error-serializer.js, 135 lines that turn error responses into JSON, both opening with a comment saying they are autogenerated and must not be edited. Measuring the cyclomatic complexity of every function with ESLint and summing per file put config-validator.js first at 441, comfortably ahead of the most complex hand-written files, reply.js at 263, fastify.js at 205 and route.js at 188. Nearly all of the 441 came from a single function called validate10, whose cognitive complexity was 4,602. The 489 hand-written functions sum to 1,702 cyclomatic, and the three generated functions add 470, making up 21.6% of the 2,172 total. A dashboard built this way would name a file no one ever opens as the most complex code, and averages, counts of functions over the limit and file rankings would all be dragged toward that one file. Generated code is not something to read or edit directly: changing it means changing the generator or its input, here the options schema, and verifying it means testing the generator. So before measuring, generated output, vendored code copied in as is, minified bundles, test snapshots and lock files go on an exclusion list. Fastify already left this file out of test coverage with a c8 ignore comment at its top. Metrics only mean something once what they count has been settled, and for the same reason, when complexity limits are enforced in CI, paths are cleaned up first so generated files do not break the build.</sub> |
| **소수의 파일에 몰리는 변경**<br><sub>Change piles up in a few files</sub> | Fastify의 10년 치 커밋에서 소스 파일 35개 가운데 상위 4개가 변경의 62.7%를, 상위 7개가 75.6%를 차지했어요.<br><sub>In Fastify’s ten years of commits, 4 of 35 source files took 62.7% of all changes, and 7 took 75.6%.</sub> | 리팩터링할 곳을 고를 때 흔히 가장 지저분해 보이는 코드부터 손대요. 하지만 코드는 고르게 바뀌지 않아요. Fastify 저장소의 main 브랜치에서 머지가 아닌 커밋 4,492개를 모아, 2016년 9월부터 2026년 11월까지 지금 있는 소스 파일 35개가 각각 몇 번 바뀌었는지 셌어요. 테스트, 문서, 예제, 빌드 스크립트는 뺐어요. fastify.js가 598번으로 가장 많았고, lib/reply.js 287번, 타입 정의 파일 fastify.d.ts 215번, lib/route.js 147번, lib/validation.js 99번이 뒤를 이었어요. 35개 파일의 변경을 모두 더하면 1,990건이에요. 상위 10%인 4개 파일이 그 가운데 1,247건, 62.7%를 차지했어요. 상위 20%인 7개 파일로 넓히면 75.6%예요. 나머지 31개 파일은 10년 동안 다 합쳐 743번 바뀌었어요. 경로는 지금 이름으로 셌기 때문에 이름이 바뀐 파일의 옛 기록은 빠져 있지만, 몰림의 정도는 분명해요. 이 분포가 뜻하는 바는 단순해요. 대부분의 코드는 한번 쓰이고 나면 거의 다시 열리지 않아요. 그런 코드를 깔끔하게 다듬어도 그 덕을 볼 일이 드물어요. 반대로 자주 고치는 파일은 고칠 때마다 이해하는 시간과 실수할 위험을 다시 치러요. 그래서 다듬는 노력은 변경이 몰리는 곳에 쓸 때 가장 많이 돌아와요. 새 기능이 들어갈 자리를 고치기 전에 먼저 정리하라는 조언도 같은 이야기예요. 변경 횟수는 git log 한 줄로 얻을 수 있어 비용이 거의 들지 않아요. 다만 변경이 많다고 다 나쁜 것은 아니에요. 진입점이나 설정처럼 원래 자주 바뀌는 파일도 있어요. 변경 횟수는 혼자 쓰기보다 복잡도와 함께 볼 때 힘이 커요. 그것이 다음 항목인 핫스팟 분석이에요.<br><sub>When choosing what to refactor, people often start with the code that looks messiest, but code does not change evenly. From the main branch of the Fastify repository, 4,492 non-merge commits were collected, and for the 35 source files that exist today, the number of commits touching each between September 2016 and November 2026 was counted, leaving out tests, docs, examples and build scripts. fastify.js changed most, 598 times, followed by lib/reply.js at 287, the type definition file fastify.d.ts at 215, lib/route.js at 147 and lib/validation.js at 99. The 35 files add up to 1,990 changes, of which the top 10%, four files, took 1,247, or 62.7%. Widening to the top 20%, seven files, gives 75.6%, while the other 31 files changed 743 times in total over ten years. Paths were counted by their current names, so older history of renamed files is missing, but the concentration is clear. What this distribution means is simple. Most code, once written, is rarely opened again, and polishing such code seldom pays back, while files that are edited often charge the time to understand them and the risk of mistakes again on every edit. Tidying effort therefore returns the most when spent where change concentrates, which is also the point of the advice to tidy the place where a new feature will go before changing it. Change counts come from a single git log command and cost almost nothing to get. A high count is not bad in itself, though, since entry points and configuration files naturally change often. Change counts are strongest when read together with complexity, which is the next item, hotspot analysis.</sub> |
| **변경과 복잡도를 곱한 핫스팟**<br><sub>Hotspots: change times complexity</sub> | 변경 횟수와 복잡도를 곱하자 Fastify의 상위 3개 파일이 드러났어요. 코드의 35.1%인데 변경의 59.6%가 몰렸어요.<br><sub>Multiplying change counts by complexity singled out Fastify’s top three files: 35.1% of the code, 59.6% of changes.</sub> | 복잡도만 보면 아무도 손대지 않는 복잡한 코드에 시간을 쓰게 되고, 변경 횟수만 보면 단순하지만 자주 바뀌는 설정 파일이 위로 올라와요. 핫스팟 분석은 두 신호를 곱해요. 버전 관리 기록에서 얻은 변경 횟수와 코드에서 잰 복잡도가 둘 다 높은 곳, 곧 복잡한데 자주 고치는 곳을 찾는 거예요. | **의존이 몰리는 모듈**<br><sub>Modules everything depends on</sub> | Fastify의 symbols.js에는 32개 모듈 가운데 20개가 직접, 21개가 건너서 기대요. 그래서 내부 import가 하나도 없는 단순한 목록이에요.<br><sub>Fastify’s symbols.js has 20 direct and 21 transitive dependents among 32 modules, and it is a simple list with no internal imports.</sub> | 코드를 바꿀 때 가장 먼저 궁금한 것은 이 변경이 어디까지 번지느냐예요. 모듈 사이의 의존을 그래프로 그리면 답의 윤곽이 보여요. madge는 코드를 실행하지 않고 require와 import 문만 읽어 이 그래프를 그려요. ## 타입 검사기를 리팩터링 도구로 · The type checker as a refactoring tool

| **유니언에 값을 더할 때**<br><sub>Adding a value to a union</sub> | 결제 수단에 crypto를 더하자, 수수료 함수 여섯 모양 가운데 strict에서는 3개만 오류를 냈어요. default에서 0을 돌려주는 모양은 조용히 0을 냈어요.<br><sub>Adding crypto to a payment union, only 3 of 6 fee-function shapes raised errors under strict; the one returning 0 by default silently returned 0.</sub> | 리팩터링이 아니라 기능 추가처럼 보이지만, 값의 종류를 하나 더하는 변경은 코드 곳곳에 흩어진 분기를 찾아 고치는 일이에요. 이 일을 사람이 기억에 기대 하면 한 곳은 꼭 빠져요. 그래서 고칠 곳을 컴파일러가 알려 주는 모양으로 코드를 짜 두는 것이 중요해요. 결제 수단 유니언 Pay에 card, bank, point가 있고, 수수료를 계산하는 함수를 여섯 가지 모양으로 썼어요. ## 깔끔한 코드는 느릴까 · Is clean code slow?

다형성과 switch와 표, 작은 함수로 나누기, reduce 속 스프레드, 배열 메서드 체인, 예외와 결과 값의 비용을 Node 22의 V8에서 실측해요.

| **다형성, switch, 표**<br><sub>Polymorphism, switch and tables</sub> | 도형 100만 개의 넓이를 더하자 클래스 메서드는 종류 4개까지 10.8ns였다가 8개에서 33.6ns가 됐어요. 표와 타입 배열은 4.6~5.0ns였어요.<br><sub>Summing a million shape areas, class methods took 10.8 ns with up to 4 kinds and 33.6 ns with 8; a table over typed arrays took 4.6–5.0 ns.</sub> | 조건문 대신 다형성을 쓰라는 것은 클린 코드의 대표적인 조언이에요. 반대로 그 조언이 성능을 크게 해친다는 주장도 있어요. 둘 다 숫자로 확인했어요. 도형 100만 개의 넓이를 더하는 일을 세 가지로 짰어요. 첫째는 종류마다 area 메서드를 가진 클래스를 만들고 x.area()를 부르는 다형성이에요. 둘째는 type 필드가 있는 평범한 객체를 switch로 나누는 방식이에요. 셋째는 종류별 계수를 표에 두고, 너비와 높이를 타입 배열에 담아 계수 × 너비 × 높이로 계산하는 방식이에요. Appending the new line at the end conflicted in all 500 merges, because both branches changed the same place, after the last line, and git, unable to know which of two changes in the same place should come first, asks a person. Inserting each new line in its alphabetical position conflicted 51 times, 10.2%: the two new lines usually land in different places in the file, and git accepts both automatically. The remaining conflicts were cases where the two lines landed in the same or neighboring gaps, since git also treats changes to adjacent lines as a conflict. The difference is not limited to imports. Lists that can only grow at the end, such as changelogs, conflict endlessly, which is why some projects create a separate file per change and combine them at release. Rules like these, left to people, add review comments, while ESLint’s import sorting rules or formatter plugins that support sorting put things in order on save through autofix.
