## 무엇이 다시 만들어지는가 · What gets rebuilt

setState가 다시 만드는 범위, const 위젯, Key와 State, GlobalKey, MediaQuery의 리빌드를 Flutter 3.50의 위젯 테스트에서 build 횟수로 실측해요.  
*The range setState rebuilds, const widgets, keys and State, GlobalKey and MediaQuery rebuilds, measured as build counts in Flutter 3.50 widget tests.*

| **setState의 범위**<br><sub>The scope of setState</sub> | 부모에서 setState를 부르자 자식 100개가 모두 다시 build됐어요. 같은 상태를 작은 위젯 안으로 옮기자 그 위젯 1번, 자식은 0번이었어요.<br><sub>Calling setState in a parent rebuilt all 100 children. Moving the same state into a small widget rebuilt that widget once and the children 0 times.</sub> | Flutter의 화면은 위젯 트리예요. StatefulWidget의 State에서 setState를 부르면 Flutter는 그 State의 build를 다시 실행하고, 거기서 나온 새 위젯들을 이전 것과 비교하며 아래로 내려가요. 이 비용이 얼마나 되는지 build 호출 수로 확인했어요. 부모 StatefulWidget의 build가 버튼 하나와 StatelessWidget 자식 100개를 그려요. 자식은 const가 아닌 생성자로 만들어요. 버튼을 한 번 눌러 부모에서 setState를 부르자, 자식의 build가 100번, 생성자도 100번 불렸어요. 화면에서 바뀐 것은 버튼 위의 숫자 하나뿐이었어요. 부모의 build가 다시 돌면서 자식 위젯 객체를 모두 새로 만들었고, 새 객체는 이전과 같은지 알 수 없으니 모두 다시 build된 거예요. 이번에는 숫자와 setState를 Counter라는 작은 StatefulWidget 안으로 옮겼어요. 부모는 상태가 없는 위젯이 되고, Counter와 자식 100개를 나란히 그려요. 같은 탭에 Counter의 build는 1번, 자식 100개는 0번이었어요. 자식 생성자도 한 번도 불리지 않았어요. 부모의 build는 다시 돌지 않았으니까요. setState는 이 State 아래 전체를 다시 build하라는 표시예요. 그래서 자주 바뀌는 상태를 화면 위쪽의 큰 위젯에 두면, 그 아래가 상태와 상관없이 모두 따라 움직여요. 위젯 100개쯤이면 눈에 띄지 않을 수 있지만, 애니메이션이나 스크롤처럼 1초에 수십 번 바뀌는 상태라면 그 수를 곱해야 해요. 상태는 그것을 실제로 쓰는 가장 작은 위젯에 두는 것이 기본이에요. Provider나 Riverpod 같은 상태 관리 도구도 결국 이 범위를 좁히는 방법을 줘요.<br><sub>A Flutter screen is a widget tree. Calling setState on a StatefulWidget's State makes Flutter rerun that State's build and walk down comparing the new widgets with the old ones. The cost was checked as build call counts. A parent StatefulWidget builds one button and 100 StatelessWidget children created with a non-const constructor. One tap calling setState in the parent called the children's build 100 times and their constructors 100 times, though the only change on screen was the number on the button. Rerunning the parent's build created every child widget object anew, and since new objects cannot be known to equal the old ones, all of them were rebuilt. Next, the number and setState moved into a small StatefulWidget called Counter, leaving the parent stateless and drawing Counter beside the 100 children. The same tap built Counter once and the 100 children 0 times, without a single child constructor call, because the parent's build never reran. setState marks everything under that State for rebuilding. So frequently changing state kept in a large widget high on the screen drags everything below it along, whether or not it depends on the state. With about 100 widgets it may go unnoticed, but state changing dozens of times a second, as in animations or scrolling, multiplies that count. The basic rule is to keep state in the smallest widget that actually uses it. State management tools such as Provider and Riverpod ultimately offer ways to narrow this range as well.</sub> |
| **const 위젯**<br><sub>const widgets</sub> | 자식을 const로 만들자 부모가 다시 build돼도 자식 build는 0번이었어요. 다만 flutter test의 디버그 설정에서는 다른 줄의 const 위젯끼리 identical이 false였어요.<br><sub>With const children, they were built 0 times when the parent rebuilt. Under flutter test's debug settings, though, const widgets from different lines were not identical.</sub> | 앞 항목에서 자식 100개가 다시 build된 이유는 부모의 build가 매번 새 위젯 객체를 만들었기 때문이에요. Flutter는 새 위젯이 이전과 같은 인스턴스, 즉 identical이면 그 아래를 다시 build하지 않고 건너뛰어요. Dart의 const는 같은 값의 객체를 컴파일할 때 하나로 만들어 매번 같은 인스턴스를 줘요. 같은 부모에서 자식만 const ConstChild()로 바꾸고 부모에서 setState를 불렀어요. 자식의 build는 0번이었어요. const가 아닐 때는 100번이었어요. 그런데 확인하다 예상과 다른 점을 만났어요. 서로 다른 두 줄에 쓴 const ConstChild()를 identical로 비교하자, flutter test의 기본 설정에서는 false였어요. --no-track-widget-creation 옵션을 주자 true였어요. 함수 하나가 같은 줄에서 돌려주는 const는 두 설정 모두 true였어요. 디버그 빌드는 Flutter Inspector가 위젯을 소스 코드의 위치와 연결할 수 있도록, 위젯 생성자마다 만들어진 파일과 줄 정보를 숨은 인자로 넣어요. 위치가 인자에 들어가니 다른 줄의 const는 서로 다른 객체가 돼요. 그래도 리빌드를 건너뛰는 효과는 그대로였어요. 리빌드에서 비교하는 것은 같은 자리의 이전 위젯과 새 위젯이고, 그 둘은 소스의 같은 줄에서 나오니까요. 반복문 안의 const ConstChild()도 한 줄이라 100개 모두 같은 인스턴스였어요. 바뀌지 않는 위젯에는 const를 붙이는 것이 가장 쉬운 최적화예요. 다만 새 프로젝트가 쓰는 flutter\_lints 6.0.0에는 이를 권하는 prefer\_const\_constructors 규칙이 들어 있지 않았어요. 원하면 analysis\_options.yaml에서 직접 켜야 해요.<br><sub>The 100 children in the previous item were rebuilt because the parent's build created new widget objects every time. Flutter skips rebuilding below a new widget that is the same instance as before, that is, identical. Dart's const makes objects of equal value into one at compile time and hands out the same instance every time. In the same parent, only the children changed to const ConstChild(), and setState was called in the parent. The children were built 0 times, against 100 without const. Checking this turned up something unexpected. Comparing const ConstChild() written on two different lines with identical gave false under flutter test's default settings and true with the --no-track-widget-creation option, while const instances returned from the same line of a function were identical under both. Debug builds pass each widget constructor the file and line where it was created as a hidden argument, so that the Flutter Inspector can link widgets to source locations. With the location in the arguments, const widgets from different lines become different objects. The rebuild skipping still worked, though, because a rebuild compares the old and new widget in the same slot, and both come from the same line of source. The const ConstChild() inside the loop is a single line too, so all 100 were the same instance. Adding const to widgets that never change is the easiest optimisation there is, though flutter\_lints 6.0.0, used by new projects, did not include the prefer\_const\_constructors rule that recommends it, so it has to be enabled in analysis\_options.yaml.</sub> |
| **Key와 State**<br><sub>Keys and State</sub> | 상태 있는 타일 A, B, C의 순서를 바꾸자 키가 없을 때는 State가 자리에 남고 이름만 바뀌었어요. A를 지우면 C의 State가 dispose됐어요. ValueKey를 주자 State가 위젯을 따라갔어요.<br><sub>Reordering stateful tiles A, B and C without keys left each State in place and changed only the names. Removing A disposed C's State. With ValueKey, the States followed their widgets.</sub> | StatefulWidget의 위젯 객체는 매번 새로 만들어지지만, State는 오래 살아남아요. 화면이 다시 build될 때 Flutter는 새 위젯을 어느 이전 State와 짝지을지 정해야 해요. 기본 규칙은 같은 부모 아래에서 같은 자리, 같은 타입이면 이전 State를 다시 쓰는 거예요. StatefulWidget인 Tile 세 개 A, B, C를 세로로 놓고 확인했어요. 각 State는 initState에서 1, 2, 3 번호를 받고, 화면에 위젯 이름과 State 번호를 함께 보여 줘요. 처음 화면은 A:state1, B:state2, C:state3이었어요. 순서를 B, A, C로 바꾸자 키가 없을 때는 B:state1, A:state2, C:state3이 나왔어요. 이름만 바뀌고 State는 자리에 그대로 남았어요. 타일이 체크 표시나 입력 중인 글자를 State에 들고 있었다면, 그것이 다른 항목에 붙어 보였을 거예요. A를 지워 B, C만 남기자 결과는 B:state1, C:state2였어요. dispose된 것은 C가 만든 state3이었어요. 지운 것은 A인데 A의 State는 B에게 넘어가고, 엉뚱하게 C의 State가 사라진 거예요. 이번에는 Tile(l, key: ValueKey(l))처럼 이름을 키로 주었어요. 순서를 바꾸자 B:state2, A:state1, C:state3으로 State가 자기 위젯을 따라갔어요. A를 지우면 A의 state1이 dispose됐어요. 모든 경우에 State는 새로 만들어지지 않았고, 짝만 달라졌어요. 상태가 있는 항목을 정렬하거나 지우는 목록이라면 항목의 고유한 값으로 Key를 줘야 해요. 인덱스를 키로 쓰면 키가 없는 것과 같은 문제가 생기니, 데이터의 id 같은 값을 써요.<br><sub>A StatefulWidget's widget object is created anew every time, but its State lives on. When the screen rebuilds, Flutter must decide which previous State to pair each new widget with, and the default rule is to reuse the previous State for the same type in the same position under the same parent. This was checked with three StatefulWidget Tiles A, B and C stacked vertically. Each State took a number 1, 2 or 3 in initState, and the screen showed the widget name with its State number. The first screen read A:state1, B:state2, C:state3. Reordering to B, A, C without keys produced B:state1, A:state2, C:state3: the names moved while the States stayed in place. Had the tiles kept a check mark or text being typed in their State, it would have appeared attached to another item. Removing A to leave B and C gave B:state1 and C:state2, and the State disposed was state3, created by C. A was removed, yet A's State passed to B and C's State disappeared instead. Next, the name was given as a key, as in Tile(l, key: ValueKey(l)). Reordering then gave B:state2, A:state1, C:state3, each State following its own widget, and removing A disposed A's state1. In no case was a new State created; only the pairing changed. Lists whose stateful items get sorted or removed need keys made from each item's unique value. Using the index as a key brings back the same problem as no key, so use a value such as the data's id.</sub> |
| **GlobalKey와 부모 이동**<br><sub>GlobalKey and moving parents</sub> | 상태 있는 위젯을 다른 부모 아래로 옮기자 키가 없으면 initState가 다시 불려 State가 새로 만들어졌어요. GlobalKey를 주자 initState는 1번이었고 State가 그대로 따라갔어요.<br><sub>Moving a stateful widget under a different parent without a key reran initState and created a new State. With a GlobalKey, initState ran once and the State followed along.</sub> | 앞 항목의 Key는 같은 부모 아래의 형제들 사이에서 짝을 찾는 규칙이었어요. 위젯이 아예 다른 부모 밑으로 옮겨 가면 어떻게 되는지 확인했어요. 상태가 있는 Mover 위젯을 Row의 첫 칸 SizedBox 안에 두었다가, 다음 화면에서 둘째 칸 Padding 안으로 옮겼어요. 화면 배치가 바뀌는 반응형 레이아웃이나, 같은 위젯을 다른 컨테이너로 감싸게 되는 경우와 비슷해요. 키가 없는 const Mover()는 initState가 2번 불렸어요. 옮긴 뒤의 Mover는 새 State로 처음부터 시작했고, 원래 State는 dispose됐어요. 입력 중인 글자나 스크롤 위치, 재생 중인 애니메이션이 있었다면 모두 초기화됐을 거예요. Mover(key: globalKey)처럼 GlobalKey를 주자 initState는 1번이었어요. 부모가 SizedBox에서 Padding으로 바뀌고 자리도 바뀌었는데, 같은 State가 그대로 따라갔어요. GlobalKey는 앱 전체에서 하나뿐인 키예요. Flutter는 GlobalKey로 등록된 요소를 기억해 두었다가, 같은 키가 트리의 다른 곳에 나타나면 기존 요소와 State를 떼어 그 자리로 옮겨요. 이 기능 때문에 GlobalKey로 currentState에 접근해 폼을 검증하는 코드도 가능해요. 대신 전역으로 등록하고 찾는 비용이 있고, 같은 GlobalKey를 두 곳에 동시에 쓰면 오류가 나요. 그래서 형제 사이의 순서만 바뀌는 경우에는 ValueKey로 충분하고, 부모가 바뀌어도 상태를 지켜야 하거나 State에 직접 접근해야 할 때만 GlobalKey를 써요. 옮겨 가는 위젯이 큰 서브트리라면 State를 끌어올려 밖에서 관리하는 방법도 함께 생각해 볼 만해요.<br><sub>The keys in the previous item were a rule for matching among siblings under the same parent. This checked what happens when a widget moves under a different parent altogether. A stateful Mover widget sat inside a SizedBox in a Row's first slot, and the next screen moved it into a Padding in the second slot, much like a responsive layout rearranging the screen or the same widget ending up wrapped in a different container. The unkeyed const Mover() ran initState twice: after the move it started over with a new State, and the original State was disposed. Any text being typed, scroll position or running animation would all have been reset. Given a GlobalKey, as in Mover(key: globalKey), initState ran once. The parent changed from SizedBox to Padding and the position changed too, yet the same State followed along. A GlobalKey is unique across the whole app. Flutter remembers elements registered with a GlobalKey, and when the same key appears elsewhere in the tree, it detaches the existing element and State and moves them there. This is also what lets code reach currentState through a GlobalKey to validate a form. The price is the cost of global registration and lookup, and using the same GlobalKey in two places at once is an error. So when only the order among siblings changes, ValueKey is enough, and GlobalKey is for when state must survive a change of parent or the State must be reached directly. If the moving widget is a large subtree, lifting the state up and managing it outside is also worth considering.</sub> |
