## 암호 기술의 기초 · Cryptography basics

데이터를 숨기고, 바뀌지 않았음을 증명하고, 누가 보냈는지 확인하는 도구예요.  
*Tools to hide data, prove it hasn’t changed and confirm who sent it.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **해시 함수**<br><sub>Hash function</sub> | 어떤 데이터든 고정 길이의 값(다이제스트)으로 바꿔요. 같은 입력은 항상 같은 값, 조금만 달라도 전혀 다른 값이 나오고 거꾸로 되돌릴 수 없어요.<br><sub>Turns any data into a fixed-length digest: the same input always gives the same output, a tiny change gives a totally different one, and it can’t be reversed.</sub> | 파일 무결성 검사(체크섬), git 커밋 ID, 캐시 키, 비밀번호 저장에 써요. MD5·SHA-1은 충돌이 발견돼 보안 용도로 쓰지 마세요.<br><sub>Used for checksums, git commit ids, cache keys and password storage. MD5 and SHA-1 are broken for security use.</sub> |
| **대칭키 암호**<br><sub>Symmetric encryption</sub> | 암호화와 복호화에 같은 키를 써요. 빠르지만 양쪽이 같은 키를 미리 안전하게 나눠 가져야 해요.<br><sub>Uses the same key to encrypt and decrypt: fast, but both sides must already share the key securely.</sub> | AES가 표준이에요. 디스크·DB 암호화, HTTPS의 실제 데이터 암호화에 써요. 키 자체는 공개키 방식으로 교환해요.<br><sub>AES is the standard, used for disk and database encryption and for HTTPS bulk data; the key itself is exchanged with public-key methods.</sub> |
| **공개키 암호**<br><sub>Public-key cryptography</sub> | 공개키와 개인키 한 쌍을 써요. 공개키로 잠근 것은 짝이 되는 개인키로만 열 수 있어서, 키를 몰래 나눌 필요가 없어요.<br><sub>Uses a key pair: what the public key locks, only the matching private key opens, so no secret has to be shared in advance.</sub> | HTTPS, SSH, 이메일 암호화의 기반이에요. 개인키가 유출되면 끝이니 서버 키·SSH 키는 철저히 보관하세요.<br><sub>The basis of HTTPS, SSH and encrypted email. A leaked private key is game over, so guard server and SSH keys carefully.</sub> |
| **전자 서명**<br><sub>Digital signature</sub> | 개인키로 서명하고 공개키로 검증해요. 누가 썼는지(인증)와 내용이 바뀌지 않았음(무결성)을 함께 증명해요.<br><sub>Sign with the private key, verify with the public key: it proves both who wrote it and that it wasn’t altered.</sub> | 앱·패키지 코드 서명, JWT, 블록체인 거래, 인증서가 모두 서명을 써요.<br><sub>Code signing for apps and packages, JWTs, blockchain transactions and certificates all rely on signatures.</sub> |
| **키 교환 (디피-헬먼)**<br><sub>Key exchange · Diffie–Hellman</sub> | 서로 공개된 값만 주고받고도 양쪽이 같은 비밀 키를 만들어 내는 방법이에요. 도청자는 같은 키를 만들 수 없어요.<br><sub>Two sides exchange only public values yet end up with the same secret key; an eavesdropper can’t compute it.</sub> | TLS 1.3의 ECDHE가 이것이고, 세션마다 새 키를 만들어 나중에 키가 털려도 지난 통신은 안전해요(전방 비밀성).<br><sub>TLS 1.3 uses ECDHE with fresh keys per session, so a later key leak doesn’t expose past traffic (forward secrecy).</sub> |
| **인증서와 CA**<br><sub>Certificates · CA</sub> | 인증서는 "이 공개키는 이 도메인의 것"이라고 믿을 만한 기관(CA)이 서명한 문서예요. 브라우저는 내장된 루트 CA까지 서명이 이어지는지 확인해요.<br><sub>A certificate is a document signed by a trusted authority saying “this public key belongs to this domain”; browsers check the chain up to a built-in root.</sub> | 인증서 만료는 흔한 장애 원인이라 자동 갱신을 꼭 설정하세요. 중간 인증서를 빠뜨리면 일부 기기에서만 오류가 나요.<br><sub>Expiry is a common outage, so automate renewal. Forgetting the intermediate cert breaks only some devices.</sub> |
| **비밀번호 저장**<br><sub>Password storage</sub> | 비밀번호는 원문이 아니라 사용자마다 다른 솔트를 붙여 일부러 느린 해시(bcrypt, Argon2)로 저장해요.<br><sub>Store passwords not as text but as slow salted hashes (bcrypt, Argon2), with a different salt per user.</sub> | DB가 유출돼도 해독에 엄청난 시간이 들게 만드는 게 목표예요. 직접 암호 알고리즘을 만들지 말고 검증된 라이브러리를 쓰세요.<br><sub>The goal is that a leaked database still takes enormous effort to crack. Use vetted libraries; never invent crypto.</sub> |
| **블록 암호 운용 모드**<br><sub>Block cipher modes</sub> | AES 같은 블록 암호는 16바이트씩만 암호화해요. 긴 데이터를 어떻게 이어 붙이느냐(운용 모드)에 따라 안전성이 크게 달라져요.<br><sub>Block ciphers like AES encrypt only 16 bytes at a time; how blocks are chained (the mode) decides how secure long data is.</sub> | ECB는 블록을 따로따로 암호화해서 같은 평문 블록이 같은 암호문이 되고, 이미지의 무늬가 그대로 드러날 만큼 패턴이 새어 나가요. CBC는 IV와 앞 블록을, CTR은 카운터를 섞어 매번 다른 결과를 만들어요. 요즘 기본은 암호화와 위변조 검출 태그를 함께 주는 AEAD(AES-GCM, ChaCha20-Poly1305)이고, 같은 키로 nonce를 두 번 쓰면 안전성이 무너지니 라이브러리의 고수준 API를 써요.<br><sub>ECB encrypts each block independently, so equal plaintext blocks become equal ciphertext and patterns leak, enough to keep an image’s outline visible. CBC mixes in an IV and the previous block, CTR a counter, so every block differs. Today’s default is an AEAD (AES-GCM, ChaCha20-Poly1305) that adds a tamper-detecting tag; reusing a nonce with the same key breaks security, so use a library’s high-level API.</sub> |
| **HMAC과 메시지 인증 코드**<br><sub>HMAC and MACs</sub> | 비밀 키를 아는 쪽만 만들 수 있는 체크섬(MAC)으로, 메시지가 바뀌지 않았고 키를 가진 쪽이 보냈음을 확인해요.<br><sub>A checksum only holders of a secret key can produce, proving a message is unchanged and came from a key holder.</sub> | 해시만 붙이면 공격자가 메시지를 고친 뒤 다시 계산하면 그만이에요. H(key ‖ msg)처럼 키를 앞에 붙여도 SHA-256은 길이 확장 공격으로 키 없이 뒤에 데이터를 덧붙인 값을 계산할 수 있어요. HMAC은 H((K ⊕ opad) ‖ H((K ⊕ ipad) ‖ m))으로 키를 두 번 감싸 이를 막아요. 웹훅 서명, AWS SigV4, JWT HS256에 쓰이고, 검증할 땐 상수 시간 비교를 해요.<br><sub>A bare hash is useless: an attacker edits the message and recomputes it. Even H(key ‖ msg) fails with SHA-256, whose length-extension property lets an attacker append data and compute a valid value without the key. HMAC, H((K ⊕ opad) ‖ H((K ⊕ ipad) ‖ m)), wraps the key twice to block this. It signs webhooks, AWS SigV4 requests and JWT HS256 tokens, and verification should use a constant-time comparison.</sub> |
| **안전한 난수 (CSPRNG)**<br><sub>Secure randomness (CSPRNG)</sub> | 토큰·키·비밀번호 재설정 링크에 쓰는 난수는 출력을 아무리 봐도 다음 값을 알 수 없는 암호학적으로 안전한 생성기에서 만들어야 해요.<br><sub>Random values for tokens, keys and password-reset links must come from a cryptographically secure generator whose next output can’t be predicted.</sub> | Math.random() 같은 일반 PRNG는 빠르지만 출력 몇 개로 내부 상태를 복원해 다음 값을 예측할 수 있어요. CSPRNG는 OS가 인터럽트 타이밍, 지터, 하드웨어 RNG에서 모은 엔트로피로 시드하고 ChaCha20 같은 암호 알고리즘으로 늘려요. crypto.getRandomValues, secrets.token\_urlsafe, /dev/urandom을 쓰고, 비밀 토큰은 128비트 이상, 시간·PID로 시드를 만들지 말아요.<br><sub>Ordinary PRNGs like Math.random() are fast, but a few outputs reveal their internal state and the next values. A CSPRNG is seeded by the OS from interrupt timing, jitter and hardware RNGs, then stretched with a cipher such as ChaCha20. Use crypto.getRandomValues, secrets.token\_urlsafe or /dev/urandom, give secret tokens at least 128 bits, and never seed from the time or PIDs.</sub> |
| **타이밍 공격**<br><sub>Timing attacks</sub> | 처리 시간의 미세한 차이로 비밀을 한 조각씩 알아내는 공격이에요. 비밀 값 비교는 상수 시간으로 해야 해요.<br><sub>An attack that learns secrets piece by piece from tiny differences in processing time; compare secret values in constant time.</sub> | 첫 번째로 다른 글자에서 바로 false를 돌려주는 비교는, 첫 글자가 맞을 때 조금 더 오래 걸려요. 공격자는 측정을 반복해 한 글자씩 맞혀서, 16ⁿ번이 필요한 추측을 16 × n번으로 줄여요. 모든 글자를 끝까지 XOR로 비교하는 상수 시간 비교(crypto.timingSafeEqual, hmac.compare\_digest)로 막아요. 캐시 타이밍(Spectre), 전력 분석도 같은 계열의 부채널 공격이에요.<br><sub>A comparison that returns at the first mismatch takes slightly longer when the first character is right. Repeating measurements, an attacker guesses one character at a time, cutting 16ⁿ guesses to 16 × n. Constant-time comparison, XOR-ing every character to the end (crypto.timingSafeEqual, hmac.compare\_digest), stops it. Cache timing (Spectre) and power analysis are related side channels.</sub> |

## 인증과 인가 · Authentication and authorization

누구인지 확인하고, 무엇을 할 수 있는지 정해요.  
*Confirming who someone is and deciding what they may do.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **인증 vs 인가**<br><sub>Authentication vs authorization</sub> | 인증은 "누구인지" 확인하는 것이고, 인가는 확인된 사람이 "무엇을 할 수 있는지" 정하는 거예요.<br><sub>Authentication confirms who you are; authorization decides what you are allowed to do.</sub> | 로그인 안 됨은 401, 로그인했지만 권한 없음은 403이에요. 권한 검사는 화면이 아니라 반드시 서버에서 해야 해요.<br><sub>Not logged in is 401; logged in but not allowed is 403. Always enforce permissions on the server, not just the UI.</sub> |
| **세션 vs 토큰**<br><sub>Session vs token</sub> | 세션 방식은 서버가 로그인 정보를 저장하고 쿠키로 식별자만 줘요. 토큰 방식은 정보가 담긴 서명된 토큰을 줘서 서버가 저장하지 않아요.<br><sub>Sessions keep login state on the server and give the browser just an id cookie; tokens hand out signed data so the server stores nothing.</sub> | 웹은 HttpOnly 쿠키 세션이 단순하고 안전해요. 모바일·여러 서비스 간에는 토큰이 편하지만 취소가 어려워 만료를 짧게 둬요.<br><sub>For websites, HttpOnly cookie sessions are simple and safe. Tokens suit mobile and multi-service setups but are hard to revoke, so keep them short-lived.</sub> |
| **JWT**<br><sub>JWT · JSON Web Token</sub> | 헤더.페이로드.서명 세 부분으로 된 토큰이에요. 페이로드는 누구나 읽을 수 있고, 서명 덕분에 내용을 바꾸면 들켜요.<br><sub>A token in three parts, header.payload.signature. Anyone can read the payload, but the signature exposes any tampering.</sub> | 민감 정보를 넣지 말고, 알고리즘을 서버에서 고정하고, 만료(exp)를 꼭 확인하세요. localStorage 보관은 XSS에 취약해요.<br><sub>Keep secrets out of it, pin the algorithm server-side and always check expiry. Storing it in localStorage exposes it to XSS.</sub> |
| **OAuth 2.0 · 소셜 로그인**<br><sub>OAuth 2.0 · Social login</sub> | 비밀번호를 넘기지 않고, 다른 서비스(구글 등)가 발급한 토큰으로 정해진 범위의 권한만 위임받아요.<br><sub>Delegates limited access through a token issued by another service, such as Google, without ever sharing the password.</sub> | "구글로 로그인"은 OAuth 위의 OpenID Connect예요. 모바일·SPA는 PKCE를 꼭 쓰고, 리디렉트 URI를 정확히 등록하세요.<br><sub>“Sign in with Google” is OpenID Connect on top of OAuth. Use PKCE for mobile and SPAs and register exact redirect URIs.</sub> |
| **OpenID Connect**<br><sub>OpenID Connect</sub> | OAuth 2.0 위에 id\_token(서명된 JWT)을 더해, 앱이 “누가 로그인했는지”를 표준 방식으로 알 수 있게 한 프로토콜이에요.<br><sub>A protocol that adds an id\_token (a signed JWT) on top of OAuth 2.0 so apps learn, in a standard way, who signed in.</sub> | “구글로 로그인”을 누르면 앱(RP)은 브라우저를 IdP의 /authorize로 보내며 scope=openid email, nonce, PKCE code\_challenge를 붙여요. 사용자가 로그인하고 동의하면 IdP는 ?code=…와 함께 앱으로 돌려보내고, 앱 서버는 이 code와 code\_verifier를 IdP의 /token에 보내 id\_token과 access\_token을 받아요. id\_token은 서명된 JWT로 iss(발급한 IdP), sub(그 IdP 안에서 변하지 않는 사용자 ID), aud(이 토큰을 받을 앱의 client\_id), exp(만료), nonce, email 같은 클레임을 담아요. 앱은 JWKS 공개키(kid)로 서명을 검증하고, iss가 믿는 IdP인지, aud가 내 client\_id인지, exp가 지나지 않았는지, nonce가 내가 보낸 값인지 모두 확인한 뒤에야 그 사용자로 로그인시켜요. 이메일은 바뀔 수 있으니 계정은 (iss, sub)로 식별해요. id\_token은 “누가 로그인했나”를 앱에게 알려 주는 것이고, access\_token은 API를 호출할 권한이라 API가 읽는 거예요. access\_token을 로그인 증명으로 쓰면 다른 앱에 발급된 토큰을 받아들이는 실수가 생겨요. IdP 설정은 /.well-known/openid-configuration discovery 문서에서 엔드포인트와 jwks\_uri를 자동으로 가져오고, 검증은 직접 짜기보다 검증된 라이브러리를 써요.<br><sub>When a user clicks “sign in with Google”, the app (the relying party) redirects the browser to the IdP’s /authorize with scope=openid email, a nonce and a PKCE code\_challenge. After login and consent the IdP redirects back with ?code=…, and the app’s server sends that code with the code\_verifier to /token, receiving an id\_token and an access\_token. The id\_token is a signed JWT carrying claims such as iss (the issuing IdP), sub (a stable user ID within that IdP), aud (the client\_id of the intended app), exp (expiry), the nonce and email. The app verifies the signature with the JWKS key named by kid and checks that iss is an IdP it trusts, aud is its own client\_id, exp has not passed and the nonce matches what it sent, and only then signs the user in. Emails can change, so accounts are keyed on (iss, sub). The id\_token tells the app who signed in, while the access\_token is permission to call APIs and is meant for the API; treating an access token as proof of login risks accepting tokens issued to another app. IdP settings, including endpoints and the jwks\_uri, come from the /.well-known/openid-configuration discovery document, and validation is best left to a well-tested library.</sub> |
| **다중 인증 (MFA)**<br><sub>Multi-factor authentication</sub> | 비밀번호(아는 것)에 휴대폰 코드·보안 키(가진 것)나 지문(나 자신)을 더해 확인해요.<br><sub>Combines a password (something you know) with a phone code or key (something you have) or a fingerprint (something you are).</sub> | 비밀번호 유출 공격 대부분을 막아요. SMS보다 OTP 앱, 그보다 패스키·보안 키(FIDO2)가 피싱에 강해요.<br><sub>It stops most stolen-password attacks. OTP apps beat SMS, and passkeys or FIDO2 keys resist phishing best.</sub> |
| **권한 모델 (RBAC)**<br><sub>Role-based access control</sub> | 사용자에게 권한을 직접 주지 않고 역할(관리자, 편집자, 열람자)을 주고, 역할에 권한을 묶어요.<br><sub>Instead of granting permissions to people directly, assign roles (admin, editor, viewer) that carry permissions.</sub> | 필요한 최소한의 권한만 주는 최소 권한 원칙과 함께 써요. 조건이 복잡하면 속성 기반(ABAC)이나 정책 엔진을 써요.<br><sub>Pair it with least privilege. For complex conditions, use attribute-based control (ABAC) or a policy engine.</sub> |

## 웹 공격과 방어 · Web attacks and defenses

실제로 가장 많이 당하는 공격들과 막는 방법이에요.  
*The attacks that actually happen most, and how to stop them.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **SQL 인젝션**<br><sub>SQL injection</sub> | 사용자 입력을 문자열로 이어 붙여 쿼리를 만들면, 입력에 섞인 SQL 코드가 그대로 실행돼요.<br><sub>When user input is concatenated into a query string, SQL inside the input gets executed.</sub> | Prepared Statement(파라미터 바인딩)로 입력을 항상 값으로만 다루세요. DB 계정 권한도 최소로 두세요.<br><sub>Use prepared statements (parameter binding) so input is always data, and give the database account minimal rights.</sub> |
| **XSS**<br><sub>XSS · Cross-site scripting</sub> | 공격자가 심은 스크립트가 다른 사용자의 브라우저에서 실행돼 쿠키·정보를 훔치거나 화면을 조작해요.<br><sub>A script planted by an attacker runs in other users’ browsers, stealing cookies or altering the page.</sub> | 출력 시 HTML 이스케이프, CSP 헤더, HttpOnly 쿠키로 막아요. 사용자 HTML을 허용해야 하면 DOMPurify 같은 정화 라이브러리를 쓰세요.<br><sub>Escape output, send a CSP header and use HttpOnly cookies. If you must allow user HTML, sanitize it with something like DOMPurify.</sub> |
| **CSRF**<br><sub>CSRF · Cross-site request forgery</sub> | 로그인된 사용자가 악성 사이트를 열면, 그 사이트가 사용자 몰래 다른 사이트로 요청을 보내고 브라우저가 쿠키를 자동으로 붙여요.<br><sub>A logged-in user visits an evil page that silently sends requests to another site, and the browser attaches cookies automatically.</sub> | 쿠키에 SameSite=Lax/Strict를 설정하고, 상태를 바꾸는 요청엔 CSRF 토큰을 확인하세요. GET으로 상태를 바꾸면 안 돼요.<br><sub>Set SameSite=Lax or Strict on cookies and check CSRF tokens on state-changing requests. Never change state with GET.</sub> |
| **CORS**<br><sub>CORS · Cross-origin resource sharing</sub> | 브라우저는 다른 출처(도메인·포트)의 응답을 기본으로 JS에 주지 않아요. 서버가 허용 헤더로 특정 출처를 허락해야 해요.<br><sub>Browsers withhold cross-origin responses from JavaScript by default; the server must allow specific origins with headers.</sub> | "CORS 오류"는 브라우저가 막은 것이라 서버 헤더를 고쳐야 해요. Allow-Origin: \* 와 쿠키 인증을 함께 쓰면 안 돼요.<br><sub>A “CORS error” is the browser blocking, fixed by server headers. Never combine Allow-Origin: \* with cookie credentials.</sub> |
| **중간자 공격**<br><sub>Man-in-the-middle</sub> | 통신 중간에 끼어든 공격자가 내용을 엿보거나 바꿔치기해요. 공용 와이파이가 대표적인 위험 지점이에요.<br><sub>An attacker sitting between two parties reads or alters their traffic; public Wi-Fi is the classic risk.</sub> | 모든 곳에 HTTPS를 쓰고 HSTS로 강제하세요. 앱에서는 인증서 검증을 끄는 코드를 절대 배포하지 마세요.<br><sub>Use HTTPS everywhere and enforce it with HSTS. Never ship app code that disables certificate verification.</sub> |
| **DDoS**<br><sub>DDoS · Distributed denial of service</sub> | 수많은 기기(봇넷)가 한꺼번에 요청을 보내 서버나 네트워크를 마비시켜요.<br><sub>Huge numbers of devices (a botnet) send traffic at once to knock a server or network offline.</sub> | CDN·WAF(클라우드플레어 등)로 흡수하고, 레이트 리밋과 오토스케일링을 함께 써요. 비싼 API에 캐시가 없으면 작은 공격에도 쓰러져요.<br><sub>Absorb it with a CDN or WAF (e.g. Cloudflare), plus rate limiting and autoscaling. Expensive uncached endpoints fall to small attacks.</sub> |
| **접근 제어 실패 (IDOR)**<br><sub>Broken access control · IDOR</sub> | 로그인만 확인하고 그 데이터의 주인인지 확인하지 않아서, URL의 ID만 바꾸면 남의 데이터가 보여요.<br><sub>The server checks that you are logged in but not that you own the data, so changing an ID in the URL reveals others’ records.</sub> | OWASP Top 10의 1위예요. 모든 API에서 서버가 소유권·권한을 확인하고, 테스트에 "다른 사용자로 접근" 케이스를 넣으세요.<br><sub>It is number one in the OWASP Top 10. Check ownership on every API and test “access as another user” cases.</sub> |
| **SSRF**<br><sub>Server-side request forgery</sub> | 서버가 사용자 대신 URL을 요청하는 기능을 악용해, 밖에서는 닿을 수 없는 내부망 자원에 접근하는 공격이에요.<br><sub>An attack abusing a server-side URL fetch to reach internal resources that are unreachable from outside.</sub> | 링크 미리보기에 url=http://169.254.169.254/…를 넣으면 클라우드 서버가 메타데이터 서비스에 접속해 IAM 임시 키를 돌려줄 수 있어요(2019년 Capital One 유출). 내부 Redis, localhost 관리자 페이지도 노려지고, 리다이렉트·DNS 리바인딩·10진수 IP로 필터를 우회해요. 허용 목록, DNS 해석 후 사설 IP 차단, 리다이렉트 끄기, IMDSv2, 이그레스 방화벽으로 막아요.<br><sub>Feeding a link preview url=http://169.254.169.254/… can make a cloud server query its metadata service and return temporary IAM keys (the 2019 Capital One breach). Internal Redis instances and localhost admin pages are targets too, with filters bypassed via redirects, DNS rebinding or decimal IPs. Defend with allowlists, blocking private IPs after DNS resolution, disabling redirects, IMDSv2 and egress firewalls.</sub> |
| **경로 조작과 명령 주입**<br><sub>Path traversal and command injection</sub> | 사용자 입력이 파일 경로나 셸 명령의 구조를 바꿔, 의도하지 않은 파일을 읽거나 명령을 실행하게 만드는 공격이에요.<br><sub>Attacks where user input changes the structure of a file path or shell command, reading unintended files or running unintended commands.</sub> | path.join("/srv/files", file)에 ../../etc/passwd를 넣으면 루트까지 올라가 시스템 파일을 읽어요. exec("ping " + host)에 "8.8.8.8; cat /etc/passwd"를 넣으면 셸이 ; 뒤를 두 번째 명령으로 실행해요. 경로는 resolve로 정규화한 뒤 기준 디렉터리 안인지 확인하고, 명령은 셸 없이 인자 배열(execFile)로 넘기며, 가능하면 파일명 대신 ID를 받고 최소 권한으로 실행해요.<br><sub>Passing ../../etc/passwd into path.join("/srv/files", file) climbs to the root and reads system files. Passing "8.8.8.8; cat /etc/passwd" into exec("ping " + host) makes the shell run a second command after the semicolon. Normalize paths with resolve and check they stay under the base directory, pass commands as argument arrays without a shell (execFile), accept IDs instead of file names where possible and run with least privilege.</sub> |
| **명령 주입**<br><sub>Command injection</sub> | 사용자 입력이 셸 명령의 구조를 바꿔 공격자의 명령이 서버 권한으로 실행되는 취약점이에요. 셸 없이 인자 배열로 넘기고 인자 주입까지 막아요.<br><sub>Input reshapes a shell command so the attacker’s command runs with server privileges. Pass argument arrays without a shell, and guard against argument injection too.</sub> | exec("convert " + name + " out.png")처럼 입력을 문자열로 이어 붙여 셸에 넘기면, name = "a.jpg; rm -rf ~"일 때 셸은 ;를 명령 구분자로 읽어 convert a.jpg와 rm -rf ~ out.png 두 명령을 실행해요. ; 말고도 \|, &, &&, \|\|, $( ), 백틱, >, <, 줄바꿈 같은 메타문자 하나만 섞여도 명령의 구조가 바뀌고, 직접 이스케이프하는 방식은 빠뜨리기 쉬워요. 근본적인 방어는 셸을 거치지 않는 거예요. execFile("convert", [name, "out.png"])이나 파이썬 subprocess.run([...])처럼 인자 배열로 넘기면 입력 전체가 파일 이름 하나로 전달되어 convert가 “그런 파일 없음” 오류만 내요. 그래도 인자 주입이 남아요. -로 시작하는 값은 프로그램이 옵션으로 해석해서, git clone에 url = "--upload-pack=touch /tmp/pwn"을 넘기면 임의 명령이 실행돼요. 그래서 사용자 인자 앞에 --를 넣어 옵션의 끝을 표시하고, 허용 패턴(예: ^[\w.-]+$)으로 검사하고, 가능하면 외부 명령 대신 라이브러리를 쓰고, 최소 권한 계정으로 실행해요. ImageMagick, ffmpeg, git, ping 같은 외부 도구를 감싸는 코드가 단골 지점이에요.<br><sub>Concatenating input into a shell string, as in exec("convert " + name + " out.png"), means that with name = "a.jpg; rm -rf ~" the shell reads ; as a separator and runs two commands: convert a.jpg and rm -rf ~ out.png. Besides ;, any metacharacter such as \|, &, &&, \|\|, $( ), backticks, >, < or a newline reshapes the command, and hand-escaping is easy to get wrong. The real defence is to skip the shell: with execFile("convert", [name, "out.png"]) or Python’s subprocess.run([...]), the whole input arrives as one file name and convert merely reports that no such file exists. Argument injection remains, though: values starting with - are parsed as options, so passing url = "--upload-pack=touch /tmp/pwn" to git clone runs an arbitrary command. Put -- before user-supplied arguments to end option parsing, validate against an allowlist pattern (for example ^[\w.-]+$), prefer a library over an external command, and run with least privilege. Code wrapping tools such as ImageMagick, ffmpeg, git and ping is the usual hot spot.</sub> |

## 운영 보안 · Operational security

코드 밖에서 새는 구멍을 막아요.  
*Plugging the holes outside the code.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **비밀 정보 관리**<br><sub>Secrets management</sub> | API 키·DB 비밀번호 같은 비밀은 코드에 넣지 않고 환경 변수나 비밀 관리 서비스에 둬요.<br><sub>Keep API keys and passwords out of code, in environment variables or a secret manager.</sub> | 공개 저장소에 올라간 키는 몇 분 안에 수집돼요. git-secrets·gitleaks로 커밋 전에 막고, 유출되면 즉시 폐기·교체하세요.<br><sub>Keys pushed to public repos are harvested within minutes. Block them pre-commit with tools like gitleaks, and rotate immediately if leaked.</sub> |
| **방화벽과 네트워크 분리**<br><sub>Firewalls · Network segmentation</sub> | 외부에는 꼭 필요한 포트만 열고, DB 같은 내부 시스템은 외부에서 직접 접근할 수 없는 영역에 둬요.<br><sub>Open only the ports that must be public and keep internal systems like databases in zones unreachable from outside.</sub> | 클라우드 보안 그룹에서 0.0.0.0/0으로 DB·SSH를 여는 실수가 흔해요. 관리 접속은 VPN이나 배스천을 거치게 하세요.<br><sub>Opening DB or SSH ports to 0.0.0.0/0 in security groups is a common mistake. Route admin access through a VPN or bastion.</sub> |
| **네트워크 분리**<br><sub>Network segmentation</sub> | 시스템을 역할별 영역으로 나누고 영역 사이에는 꼭 필요한 통신만 허용해, 한 곳이 뚫려도 피해가 퍼지지 않게 해요.<br><sub>Divide systems into zones by role and allow only necessary traffic between them, so one breach does not spread.</sub> | 모든 서버가 서로 닿는 평평한 네트워크에서는 웹 서버 하나만 뚫려도 공격자가 옆으로 이동(lateral movement)해 DB, 관리자 PC, CI 서버까지 바로 접근해요. 네트워크 분리는 서버를 DMZ(로드 밸런서·웹), 앱 영역, 데이터 영역처럼 역할별로 나누고, 영역 사이에는 필요한 흐름만 한 방향으로 허용해요. 인터넷 → LB :443, LB → 웹 :8080, 웹 → 앱 :9000, 앱 → DB :5432만 열고 나머지는 모두 거부하면, 웹 서버가 뚫려도 DB로 직접 가는 길이 없어 피해(폭발 반경)가 그 영역에 머물러요. 요즘은 더 잘게 나눠요. 마이크로 세그멘테이션은 워크로드마다 정책을 걸고(쿠버네티스 NetworkPolicy, 다른 보안 그룹을 출발지로 참조하는 클라우드 보안 그룹), 나가는 트래픽도 필요한 목적지만 허용해 데이터 유출과 악성 코드의 외부 통신을 막아요. 관리 접속은 배스천 호스트나 VPN을 거치게 하고, 제로 트러스트에서는 IP 대신 mTLS 같은 신원으로 허용 여부를 정해요. 기본은 모두 거부, 규칙은 코드로 관리하고 정기적으로 검토하며, 결제 데이터(PCI DSS)처럼 규제 대상 시스템은 분리 자체가 요구사항이에요.<br><sub>In a flat network where every server can reach every other, a single compromised web server lets an attacker move laterally straight to the database, admin PCs and CI servers. Segmentation splits servers into zones by role, such as a DMZ (load balancer and web), an application zone and a data zone, and allows only the required flows between zones, in one direction. Opening just internet → LB :443, LB → web :8080, web → app :9000 and app → DB :5432 and denying everything else means a hacked web server has no direct path to the database, so the damage (the blast radius) stays in its zone. Modern setups go finer: micro-segmentation applies policy per workload (Kubernetes NetworkPolicy, cloud security groups that reference other groups as sources), and egress is limited to needed destinations to stop exfiltration and malware callbacks. Administrative access goes through a bastion host or VPN, and zero-trust designs authorize by identity, such as mTLS, rather than IP. Default deny, rules managed as code and reviewed regularly; for regulated systems such as payment data (PCI DSS), segmentation is itself a requirement.</sub> |
| **공급망 공격**<br><sub>Supply-chain attacks</sub> | 내가 쓴 코드가 아니라 가져다 쓰는 패키지·빌드 도구를 오염시켜, 그걸 쓰는 모든 곳으로 퍼지는 공격이에요.<br><sub>Attacks that poison the packages and build tools you pull in rather than your own code, spreading to everyone who uses them.</sub> | 직접 의존 몇 개가 전이 의존 수백~수천 개를 끌고 오고, 계정이 탈취된 메인테이너의 악성 버전(event-stream, ua-parser-js), 이름 바꿔치기, 설치 스크립트가 침투 경로가 돼요. 사내 패키지와 같은 이름의 높은 버전을 공개 레지스트리에 올리는 의존성 혼동도 있어요. 락파일과 무결성 해시, npm ci와 설치 스크립트 끄기, 스코프 고정, SBOM과 서명된 출처(SLSA), 검토된 자동 업데이트로 막아요.<br><sub>A few direct dependencies drag in hundreds or thousands of transitive ones, and entry points include hijacked maintainers publishing malicious versions (event-stream, ua-parser-js), typosquats and install scripts. Dependency confusion publishes a higher-versioned package under an internal name on a public registry. Defend with lockfiles and integrity hashes, npm ci with install scripts disabled, pinned scopes, SBOMs, signed provenance (SLSA) and reviewed automated updates.</sub> |
| **위협 모델링 (STRIDE)**<br><sub>Threat modeling (STRIDE)</sub> | 설계 단계에서 데이터 흐름도를 그리고 STRIDE 여섯 가지 관점으로 “무엇이 잘못될 수 있나”를 체계적으로 찾는 방법이에요.<br><sub>Drawing the data flow at design time and using STRIDE’s six lenses to find systematically what can go wrong.</sub> | STRIDE는 위장(→ 인증), 변조(→ 무결성), 부인(→ 감사 로그), 정보 노출(→ 기밀성), 서비스 거부(→ 가용성), 권한 상승(→ 인가)이에요. 사용자 → 웹 → API → DB 흐름에서 신뢰 경계를 넘는 화살표마다 위협과 대책(MFA, 속도 제한, TLS·서명, 객체 단위 인가, 암호화, 감사 로그)을 붙여요. “무엇을 만드나, 무엇이 잘못될까, 어떻게 대응할까, 잘했나”의 네 질문을 기능이 바뀔 때마다 다시 던져요.<br><sub>STRIDE covers spoofing (→ authentication), tampering (→ integrity), repudiation (→ audit logs), information disclosure (→ confidentiality), denial of service (→ availability) and elevation of privilege (→ authorization). For a user → web → API → DB flow, each arrow crossing a trust boundary gets threats and mitigations: MFA, rate limits, TLS and signing, per-object authorization, encryption and audit logs. Ask the four questions (what are we building, what can go wrong, what will we do, did we do well) again whenever features change.</sub> |
