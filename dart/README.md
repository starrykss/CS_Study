| **실행 중에도 남는 제네릭**<br><sub>Generics that survive at runtime</sub> | Object 변수에 담은 <int>[1, 2]는 실행 중에도 is List<int>가 true, is List<String>이 false였어요. 제네릭 함수 안의 T도 int, num, String으로 출력됐어요.<br><sub>A <int>[1, 2] stored in an Object variable still answered true to is List<int> and false to is List<String> at runtime. Java는 컴파일이 끝나면 타입 인자를 지워서, 실행 중에는 List<String>과 List<Integer>를 구별하지 못해요. Dart에서 확인했어요. <int>[1, 2]로 만든 리스트를 Object 변수에 담았어요. 변수의 정적 타입이 Object라서 컴파일러는 원소 타입을 모르는 상태예요. 이 변수로 is 검사를 하자 is List<int>, is List<num>, is List<Object?>는 true, is List<String>은 false였어요. runtimeType은 List<int>였어요. 리스트 객체가 자기가 만들어질 때 받은 타입 인자를 그대로 들고 있는 거예요. 함수의 타입 인자도 마찬가지였어요. JSON을 읽어 온 dynamic 값이 정말 원하는 타입인지 확인할 때도 쓸모가 있어요. 다만 [1, 2]처럼 타입을 쓰지 않은 리스트 리터럴은 원소를 보고 List<int>로 추론된다는 점을 기억해야 해요. var l = [];처럼 비어 있으면 List<dynamic>이 돼요. 그리고 타입 인자가 남아 있다는 것은 다음 항목처럼 실행 중에 타입 검사가 일어날 수 있다는 뜻이기도 해요.<br><sub>Generics are types that take types as arguments, like List<int>, and languages differ in what happens to those type arguments at runtime. Java erases them after compilation, so at runtime it cannot tell List<String> from List<Integer>. This was checked in Dart. A list made as <int>[1, 2] was stored in an Object variable; with the variable's static type being Object, the compiler did not know the element type. is checks on the variable gave true for is List<int>, is List<num> and is List<Object?>, and false for is List<String>, with runtimeType List<int>: the list object carries the type argument it was created with. Function type arguments behave the same: printing T inside T firstOf<T>(List<T> l) gave int when passing [1, 2], num for <num>[1, 2] and String for ['a']. Keeping type arguments as values at runtime like this is called reified generics. It means checks such as is List<int> can be trusted at runtime in Dart, which is also useful for confirming that a dynamic value read from JSON really has the wanted type. Remember, though, that an untyped list literal such as [1, 2] is inferred as List<int> from its elements, and an empty one, as in var l = [];, becomes List<dynamic>. And type arguments surviving also means type checks can happen at runtime, as the next item shows.</sub> |
| **공변 리스트의 틈**<br><sub>The covariant list hole</sub> | List<num> 변수에 <int>[1, 2]를 넣고 1.5를 add하자, 컴파일과 dart analyze는 조용했지만 실행 중에 type 'double' is not a subtype of type 'int' 오류가 났어요.<br><sub>Putting <int>[1, 2] into a List<num> variable and adding 1.5 passed compilation and dart analyze silently, but raised type 'double' is not a subtype of type 'int' at runtime.</sub> | Dart의 제네릭은 공변이에요. int가 num의 하위 타입이면 List<int>도 List<num>의 하위 타입으로 취급돼요. 그래서 List<num>을 받는 함수에 List<int>를 넘길 수 있어요. 읽기만 한다면 편리하고 안전해요. 넣을 때 무슨 일이 생기는지 확인했어요. List<num> nums = <int>[1, 2];로 List<num> 변수에 int 리스트를 넣고 nums.add(1.5)를 불렀어요. 변수 타입만 보면 1.5는 num이니 넣어도 되는 값이에요. dart analyze는 No issues found였고 컴파일도 통과했어요. 실행하자 \_TypeError가 났어요. 메시지는 type 'double' is not a subtype of type 'int' of 'value'였어요. 실제 객체는 여전히 List<int>이고, 앞 항목처럼 타입 인자가 실행 중에도 남아 있어요. 그래서 add는 들어오는 값이 정말 int인지 실행 중에 검사하고, 아니면 막아요. 이 검사가 없다면 int만 있어야 할 리스트에 double이 섞여, 나중에 int로 꺼내 쓰는 코드가 엉뚱한 곳에서 깨질 거예요. 공변성은 정적 타입 검사에 생긴 작은 틈이고, Dart는 그 틈을 실행 중 검사로 메워요. 이 오류는 주로 함수가 리스트를 받아 원소를 넣을 때 만나요. 넘기는 쪽에서 [1, 2]처럼 타입 없이 리스트를 만들면 List<int>로 추론되는데, 받는 쪽이 num이나 Object를 넣으려 하면 깨져요. <num>[1, 2]처럼 처음부터 원하는 원소 타입으로 리스트를 만들면 1.5를 넣어도 문제가 없었어요. 리스트를 받아 수정하는 API라면, 받은 리스트에 넣기보다 새 리스트를 만들어 돌려주는 편이 이런 문제를 피하기 쉬워요.<br><sub>Dart generics are covariant: if int is a subtype of num, List<int> is treated as a subtype of List<num>, so a List<int> can be passed to a function taking List<num>. For reading that is convenient and safe. This checked what happens when adding. List<num> nums = <int>[1, 2]; put an int list into a List<num> variable, and nums.add(1.5) was called. By the variable's type 1.5 is a num and should be allowed; dart analyze reported No issues found and compilation passed. Running it raised a \_TypeError: type 'double' is not a subtype of type 'int' of 'value'. The actual object is still a List<int>, and as in the previous item its type argument survives at runtime, so add checks at runtime that the incoming value really is an int and rejects it otherwise. Without that check, a double would slip into a list meant for ints, and code later reading it as int would break somewhere unexpected. Covariance is a small hole in static type checking, and Dart plugs it with a runtime check. The error usually appears when a function takes a list and adds to it: a list created without a type on the calling side, such as [1, 2], is inferred as List<int> and breaks when the receiving side tries to add a num or Object. Creating the list with the wanted element type from the start, as in <num>[1, 2], accepted 1.5 without trouble. APIs that modify a list they receive avoid this more easily by returning a new list instead of adding to the one passed in.</sub> |

C나 Java의 정수와 같은 동작이고, 넘치면 예외를 내는 언어와는 달라요. 넘침은 조용히 일어나서, 금액 합계나 큰 id에 곱셈을 하는 계산에서 갑자기 음수가 나와야 알아채게 돼요. 해시를 계산하거나 난수를 섞는 코드처럼 일부러 넘침을 이용하는 경우도 있어요. 정확한 큰 정수가 필요하면 BigInt를 써요. This checked what happens past that edge. With the largest value, 9223372036854775807, as the constant max, printing max + 1 gave -9223372036854775808, with no exception or warning, and max \* 2 gave -2. The high bits overflowing 64 were dropped and the remaining bits read as a negative number, behaviour called wraparound. It matches integers in C and Java and differs from languages that throw on overflow. Overflow happens silently, so it tends to be noticed only when a negative number suddenly appears in a sum of amounts or a multiplication on a large id. Some code relies on it deliberately, such as hashing or mixing random numbers. When exact large integers are needed, use BigInt: BigInt.from(max) + BigInt.one gave 9223372036854775808 exactly. It has no digit limit, but it is slower than int and cannot be mixed directly with int operators, requiring conversion. The web differs again. Compiling the same code with dart2js was refused at the constant 9223372036854775807 itself, as it cannot be represented exactly in JavaScript. Web ints are JavaScript numbers whose precision breaks above 2^53, a difference measured separately in the Flutter page's item on integers on the web and the VM. The same Dart code is limited at 2^63 on the VM and 2^53 on the web, so code that runs in both places should be reasoned about with the smaller limit.</sub> |
| **필드 승격**<br><sub>Field promotion</sub> | null 검사 뒤에도 public final 필드는 int로 승격되지 않아 dart analyze가 오류를 냈어요. private final 필드와 지역 변수에 담은 값은 승격됐어요.<br><sub>Even after a null check, a public final field was not promoted to int and dart analyze reported an error. Inside if (x != null) the compiler treats x as int, which is called type promotion. It works well for local variables, and there have long been complaints that it often fails for fields. This problem easily breeds the habit of adding !, but ! can lead to runtime errors, so the local variable is the safer path.</sub> |

Set과 Map은 먼저 hashCode로 들어갈 칸을 찾고, 그 칸 안에서 ==로 같은지 확인해요. 그래서 ==만 고치고 hashCode를 그대로 두면, 같다고 판단해야 할 두 객체가 서로 다른 칸으로 가서 Set에 중복이 생길 수 있어요. 둘은 항상 함께 고쳐야 해요. Dart 3의 레코드는 이 일을 대신 해 줘요. (1, 'a') == (1, 'a')는 true였고 두 레코드의 hashCode도 같았어요. identical은 false라서 서로 다른 객체이지만 값으로 비교된 거예요. 레코드를 Map의 키로 넣고 같은 값의 새 레코드로 찾자 값이 나왔어요. 이름 붙은 필드가 있는 레코드의 타입은 ({int age, String name})처럼 출력됐어요. 실수에는 따로 주의할 점이 있어요. double.nan == double.nan은 false였고, identical(double.nan, double.nan)은 true였어요. ## Future와 Stream이 실제로 도는 방식 · How Futures and Streams actually run

| **차례로 기다리기와 함께 기다리기**<br><sub>Waiting one by one versus together</sub> | 100ms 작업 세 개를 await로 차례로 기다리자 302~305ms, Future.wait나 레코드의 .wait로 함께 기다리자 101ms였어요.<br><sub>Awaiting three 100 ms jobs one by one took 302–305 ms; waiting on them together with Future.wait or a record's .wait took 101 ms.</sub> | 화면 하나를 그리려고 사용자 정보, 알림 수, 추천 목록을 서버에서 각각 받아 와야 한다고 해 볼게요. 세 요청은 서로의 결과가 필요 없어요. 100ms를 기다린 뒤 값을 돌려주는 job()으로 이 상황을 만들고, 세 가지 방법으로 세 번씩 쟀어요. 첫째는 final a = await job(100);을 세 줄로 이어 쓴 코드예요. 302~305ms가 걸렸어요. 첫 작업이 끝나야 둘째 작업을 만들고, 둘째가 끝나야 셋째를 만들어요. 서로 상관없는 요청인데도 차례를 기다린 거예요. 둘째는 Future.wait([job(100), job(100), job(100)])예요. 101ms였어요. 셋째는 Dart 3의 레코드를 쓴 (job(100), job(100), job(100)).wait예요. 이것도 101ms였어요. 레코드 쪽은 결과가 (int, String, bool)처럼 각자의 타입을 그대로 지닌 레코드로 와서, Future.wait의 List처럼 타입이 하나로 뭉개지지 않아요. 차이를 만드는 것은 await가 아니라 Future를 만드는 시점이에요. Dart의 Future는 만들어지는 순간 일을 시작하고, await는 그 결과가 나올 때까지 기다리는 자리일 뿐이에요. 세 Future를 먼저 모두 만들고 나서 기다리면 세 일이 동시에 진행돼서, 전체 시간은 합이 아니라 가장 긴 하나가 돼요. 다만 같은 효과가 항상 좋은 것은 아니에요. 두 번째 요청에 첫 번째 결과가 필요하다면 차례로 기다려야 하고, 서버에 수백 개를 한꺼번에 보내면 서버나 연결 수 제한에 걸릴 수 있어요. 독립된 요청 몇 개를 함께 보내는 것이 가장 쉬운 속도 개선이에요.<br><sub>Suppose one screen needs user info, a notification count and a recommendation list, each fetched separately from a server, none needing another's result. job(), which waits 100 ms and returns a value, recreated this, measured three times in each of three ways. First, three lines of final a = await job(100); took 302 to 305 ms: the second job is created only after the first ends, and the third after the second, so unrelated requests still waited their turn. Second, Future.wait([job(100), job(100), job(100)]) took 101 ms. Third, Dart 3's record form (job(100), job(100), job(100)).wait also took 101 ms; its result arrives as a record keeping each type, such as (int, String, bool), rather than collapsing them into one type as Future.wait's List does. The difference lies not in await but in when the Futures are created. A Dart Future starts its work the moment it is created, and await is merely where you wait for its result. Creating all three Futures first and waiting afterwards runs the three jobs at the same time, so the total becomes the longest one rather than the sum. The same trick is not always right: if the second request needs the first result, you must wait in turn, and sending hundreds at once can hit server or connection limits. Sending a few independent requests together is the easiest speedup there is.</sub> |
| **timeout은 작업을 멈추지 않는다**<br><sub>A timeout does not stop the work</sub> | .timeout(100ms)은 103ms에 TimeoutException을 냈지만 원래 작업은 301ms에 끝까지 돌았어요. Future.wait의 오류 처리도 쟀어요. 300ms 걸리는 작업과 50ms에 StateError로 실패하는 작업을 함께 기다리자, 오류가 301ms에 왔어요. Future.wait는 기본적으로 모든 Future가 끝날 때까지 기다린 뒤 첫 오류를 알려요. eagerError: true를 주자 50ms에 바로 오류가 왔어요. 다만 이때도 300ms 작업은 멈추지 않아요. 앞 항목처럼 Future는 만들어진 순간 시작하고, Dart의 Future에는 취소라는 개념이 없어요. 정말 멈춰야 하는 작업이라면 작업 안에서 확인하는 플래그를 두거나 package:async의 CancelableOperation을 쓰는 식으로 취소를 따로 설계해야 해요. timeout을 붙였다고 해서 서버 부하나 데이터 변경까지 막히는 것은 아니라는 점을 기억해야 해요.<br><sub>A .timeout is attached so as not to wait forever on a slow server. This checked what happens to the original work. A 300 ms slow() increments a counter and prints the time when done, and it was awaited with .timeout(const Duration(milliseconds: 100)). At 103 ms came TimeoutException after 0:00:00.100000: Future not completed. Watching 400 ms more after catching it, slow work finished anyway printed at 301 ms and the counter reached 1. A timeout only makes the waiting side stop waiting; the work inside slow() runs to the end regardless. In a real app the user may see an error while the server still processes the request, and code after the response may run with nobody aware. Future.wait's error handling was measured too. Waiting on a 300 ms job together with one failing with StateError at 50 ms delivered the error at 301 ms: by default Future.wait waits for every Future to finish before reporting the first error. With eagerError: true the error came at 50 ms, though even then the 300 ms job did not stop. As in the previous item, a Future starts when created, and Dart Futures have no notion of cancellation. Work that truly must stop needs cancellation designed in, such as a flag checked inside the work or package:async's CancelableOperation. Remember that a timeout does not prevent server load or data changes.</sub> |

Wrapping the call in try did not catch it, and the default lints were silent.</sub> | 저장이나 로그 전송처럼 결과를 기다릴 필요가 없어 보이는 작업은 await 없이 부르기 쉬워요. 그 작업이 실패하면 어떻게 되는지 확인했어요. 10ms 뒤 StateError('disk full')을 던지는 save()를 await 없이 부르고, main은 100ms를 더 기다린 뒤 end reached를 출력하게 했어요. 실행하자 Unhandled exception: Bad state: disk full과 스택이 찍히고 프로세스가 종료 코드 255로 끝났어요. end reached는 끝내 출력되지 않았어요. dart run과 AOT 실행 파일 모두 같았어요. 처리되지 않은 비동기 오류가 프로그램 전체를 끝낸 거예요. 서버 프로그램이었다면 다른 요청을 처리하던 프로세스가 함께 죽었을 거예요. 흔히 하는 대처는 호출을 try-catch로 감싸는 거예요. try { save(); } catch (e) {}로 바꿔도 결과는 똑같이 종료 코드 255였어요. save()는 Future를 돌려주며 곧바로 끝나고, 오류는 10ms 뒤 그 Future 안에서 나요. await가 없으면 그 순간에는 try 블록을 이미 지나 있어서 잡을 수가 없어요. 도구가 잡아 주는지도 봤어요. 새 프로젝트의 기본 lint인 lints 6.1.0의 recommended 설정에서 dart analyze는 No issues found였어요. analysis\_options.yaml에 unawaited\_futures 규칙을 켜자 Missing an 'await' for the 'Future' computed by this expression.이라는 정보로 찾아냈어요. 고치는 방법은 둘이에요. 결과를 기다려야 하면 await를 붙이고 그 바깥에서 오류를 처리해요. 정말 기다리지 않을 작업이라면 save().catchError(...)처럼 Future 자체에 오류 처리를 달고, dart:async의 unawaited()로 감싸 일부러 기다리지 않는다는 것을 표시해요.<br><sub>Work whose result seems not worth waiting for, such as saving or sending logs, is easily called without await. This checked what happens when that work fails. save(), which throws StateError('disk full') after 10 ms, was called without await, and main waited 100 ms more before printing end reached. Running it printed Unhandled exception: Bad state: disk full with a stack trace and ended the process with exit code 255, never printing end reached, the same under dart run and in an AOT executable. An unhandled asynchronous error ended the entire program; in a server, the process handling other requests would have died with it. The usual reaction is wrapping the call in try-catch, but try { save(); } catch (e) {} still ended with exit code 255. save() returns a Future and finishes immediately, and the error arises 10 ms later inside that Future; without await, the try block has already been left by then and cannot catch it. Whether tools catch this was checked too: with lints 6.1.0 recommended, a new project's default, dart analyze reported No issues found, and enabling the unawaited\_futures rule in analysis\_options.yaml caught it with Missing an 'await' for the 'Future' computed by this expression. There are two fixes. If the result must be awaited, add await and handle errors outside it. If the work truly need not be awaited, attach error handling to the Future itself, as in save().catchError(...), and wrap it in dart:async's unawaited() to mark the deliberate choice.</sub> |
| **스트림의 종류**<br><sub>Kinds of stream</sub> | 기본 스트림에 두 번째로 listen하자 Bad state 오류였어요. broadcast 스트림은 듣는 쪽이 생기기 전에 보낸 값을 버렸고, 단일 구독 스트림은 모아 뒀다가 모두 줬어요.<br><sub>Listening a second time to a default stream raised Bad state. A broadcast stream dropped values sent before anyone listened, while a single-subscription stream buffered them and delivered everything.</sub> | Stream은 시간에 따라 여러 값을 보내는 통로예요. 같은 Stream이라도 종류에 따라 규칙이 달라서, 잘못 고르면 값을 잃거나 오류가 나요. 먼저 StreamController()로 만든 기본 스트림에 listen을 두 번 했어요. 두 번째 listen에서 Bad state: Stream has already been listened to.가 났어요. 기본 스트림은 단일 구독이라 듣는 쪽이 하나뿐이에요. 여러 화면이나 위젯이 같은 이벤트를 들어야 한다면 broadcast 스트림을 써요. StreamController.broadcast()에 1과 2를 보낸 뒤 listen하고, 이어서 3과 4를 보냈어요. 받은 값은 [3, 4]였어요. broadcast 스트림은 값이 나오는 그 순간 듣고 있는 쪽에게만 전하고, 아무도 없으면 그냥 버려요. 같은 실험을 단일 구독 컨트롤러로 하자 [1, 2, 3]을 모두 받았어요. 듣는 쪽이 생길 때까지 값을 버퍼에 모아 뒀다가 listen하는 순간 한꺼번에 줘요. 예외처럼 보이는 경우도 있었어요. Stream.fromIterable([1, 2, 3])은 isBroadcast가 false인데, toList를 두 번 해도 두 번 다 [1, 2, 3]이었어요. 이 스트림은 listen할 때마다 리스트를 처음부터 다시 읽는 새 구독을 만들어서 두 번 들을 수 있어요. 정리하면 단일 구독은 한 명이 빠짐없이 듣는 용도, 예를 들어 파일 읽기나 HTTP 응답 본문에 맞아요. broadcast는 여러 곳이 듣되 지난 값은 놓쳐도 되는 이벤트, 예를 들어 버튼 클릭이나 연결 상태 변화에 맞아요. 나중에 듣기 시작한 쪽도 마지막 값을 받아야 한다면 broadcast만으로는 부족해서, 마지막 값을 따로 저장해 두는 구조가 필요해요.<br><sub>A Stream is a channel delivering many values over time, and its rules differ by kind, so the wrong choice loses values or raises errors. First, a default stream from StreamController() was listened to twice; the second listen raised Bad state: Stream has already been listened to. A default stream is single-subscription, with only one listener. When several screens or widgets need the same events, a broadcast stream is used. Sending 1 and 2 to StreamController.broadcast(), then listening and sending 3 and 4, received [3, 4]: a broadcast stream delivers each value only to whoever is listening at that moment and drops it if nobody is. The same experiment with a single-subscription controller received all of [1, 2, 3], the values buffered until a listener arrived and handed over the moment it did. One case looked like an exception: Stream.fromIterable([1, 2, 3]) reported isBroadcast false, yet two toList calls both gave [1, 2, 3], because this stream starts a fresh subscription reading the list from the beginning on every listen. In short, single-subscription suits one listener who must not miss anything, such as reading a file or an HTTP response body, and broadcast suits events many places hear where missed past values do not matter, such as button clicks or connection changes. When a listener that starts late must still get the latest value, broadcast alone is not enough and a structure storing the last value is needed.</sub> |
| **async\* 생성기**<br><sub>async\* generators</sub> | async\* 함수는 listen하기 전에는 본문을 한 줄도 실행하지 않았어요. 소비가 느리면 yield에서 기다렸고, 소비자가 break하자 생성기도 그 자리에서 멈췄어요.<br><sub>An async\* function ran no line of its body before listen. With a slow consumer it waited at yield, and when the consumer broke out, the generator stopped right there.</sub> | async\* 함수는 yield로 값을 하나씩 내보내는 스트림을 쉽게 만들어 줘요. 이 생성기가 언제 돌고 언제 멈추는지 확인했어요. 0부터 4까지 yield하는 async\* 함수를 만들고, 값을 만들 때마다 produce를, 마지막에 done을 기록하게 했어요. 먼저 함수를 불러 스트림을 받은 뒤 listen하지 않고 10ms를 기다렸어요. 기록은 비어 있었어요. async\* 함수를 부르면 스트림만 돌려줄 뿐, 본문은 누군가 listen할 때 비로소 시작해요. 다음으로 await for로 값을 받으며 값마다 5ms를 쉬었어요. 기록은 produce 0, consume 0, produce 1, consume 1처럼 정확히 번갈아 찍혔어요. 생성기가 앞서 값을 잔뜩 만들어 쌓아 두지 않았어요. yield에서 멈추고, 소비자가 다음 값을 원할 때까지 기다린 거예요. 이것이 생산 속도를 소비 속도에 맞추는 배압의 가장 단순한 형태예요. 값 2에서 break하자 produce 3도 done도 찍히지 않았어요. await for를 빠져나가면 구독이 취소되고, 생성기는 멈춰 있던 yield 자리에서 더 진행하지 않고 끝나요. 그래서 5개를 만들 계획이었어도 실제로는 쓰인 3개만 만들어졌어요. 큰 파일을 줄 단위로 읽거나, 페이지 단위로 서버에서 데이터를 받아 오는 코드에 잘 맞는 성질이에요. 다만 break로 멈출 때 마지막 코드가 실행되지 않으니, 파일이나 소켓을 여는 생성기라면 try-finally로 감싸 finally에서 닫아야 해요. 취소될 때도 finally는 실행돼요. 동기 버전인 sync\*는 Iterable을 같은 방식으로 게으르게 만들어 줘요.<br><sub>An async\* function makes it easy to build a stream that emits values one at a time with yield. This checked when such a generator runs and stops. An async\* function yielding 0 to 4 logged produce for each value and done at the end. First the function was called to get a stream, and 10 ms passed without listening: the log was empty. Calling an async\* function only returns a stream; its body starts when someone listens. Next, values were received with await for, pausing 5 ms per value. The log alternated exactly, produce 0, consume 0, produce 1, consume 1: the generator did not race ahead stockpiling values but paused at yield until the consumer wanted the next one, the simplest form of backpressure, matching production to consumption. Breaking out at 2 logged neither produce 3 nor done. Leaving await for cancels the subscription, and the generator ends at the paused yield without going further, so although it was written to make 5 values, only the 3 used were made. This suits reading large files line by line or fetching server data page by page. Because the final code does not run after a break, generators that open files or sockets should wrap their work in try-finally and close in finally, which runs on cancellation too. The synchronous version, sync\*, builds Iterables lazily in the same way.</sub> |
