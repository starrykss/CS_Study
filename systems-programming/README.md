## C와 메모리 · C and memory

주소와 바이트 단위로 메모리를 직접 다루는 법이에요.  
*Working with memory directly, address by address and byte by byte.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **포인터**<br><sub>Pointers</sub> | 포인터는 다른 값이 있는 메모리 주소를 담는 변수예요. &로 주소를 얻고 \*로 그 주소의 값을 읽고 써요.<br><sub>A pointer is a variable holding the memory address of another value. & takes an address; \* reads or writes what lives there.</sub> | 예: int x = 42; int \*p = &x; \*p = 7 → x가 7. p + 1은 sizeof(int) = 4바이트 뒤를 가리켜요. NULL이나 해제된 주소를 역참조하면 세그멘테이션 오류. 큰 데이터를 복사 없이 넘기거나 연결 리스트·트리 같은 자료구조를 만들 때 써요.<br><sub>int x = 42; int \*p = &x; \*p = 7 leaves x at 7. p + 1 points sizeof(int) = 4 bytes further. Dereferencing NULL or freed memory is a segmentation fault. Pointers pass large data without copying and link structures such as lists and trees.</sub> |
| **배열과 포인터 산술**<br><sub>Arrays and pointer arithmetic</sub> | 배열은 같은 크기 원소가 연속으로 놓인 메모리예요. a[i]는 \*(a + i)와 같아 주소 계산만으로 바로 접근해요.<br><sub>An array is equal-sized elements laid out contiguously. a[i] is just \*(a + i), so access is pure address arithmetic.</sub> | a[i]의 주소 = 시작 주소 + i × 원소 크기 → O(1) 접근. 배열 이름은 대부분의 식에서 첫 원소 주소로 바뀌고(decay), 함수에 넘기면 길이 정보를 잃어요. C는 범위를 검사하지 않아 a[4]는 이웃 메모리를 읽어요. 2차원 배열은 행 우선으로 펼쳐져서 행 단위 순회가 캐시에 유리해요.<br><sub>The address of a[i] is base + i × element size, giving O(1) access. In most expressions the array name decays to a pointer to element 0, and passing it to a function loses its length. C doesn’t check bounds, so a[4] reads whatever sits next door. 2D arrays are stored row-major, which is why row-by-row loops are cache-friendly.</sub> |
| **구조체 정렬과 패딩**<br><sub>Struct alignment and padding</sub> | 필드는 자기 크기의 배수 주소에 놓이고, 그 사이를 패딩 바이트가 채워요. 필드 순서만 바꿔도 크기가 달라져요.<br><sub>Each field sits at a multiple of its own size, with padding bytes filling the gaps. Reordering fields alone can change the size.</sub> | 예: { char; int; char; double; }은 24바이트, { double; int; char; char; }은 16바이트. 정렬된 주소는 CPU가 한 번에 읽고, 정렬 안 된 접근은 느리거나 일부 CPU에선 오류예요. 파일·네트워크 포맷은 패딩을 명시하거나 packed로 고정하고, offsetof와 sizeof로 확인해요.<br><sub>{ char; int; char; double; } takes 24 bytes; { double; int; char; char; } takes 16. CPUs read aligned addresses in one go, while unaligned access is slow or even faults on some CPUs. File and wire formats spell out padding or use packed layouts; check with offsetof and sizeof.</sub> |
| **힙 할당자 (malloc/free)**<br><sub>Heap allocators (malloc/free)</sub> | malloc은 힙에서 빈 블록을 찾아 잘라 주고, free는 블록을 빈 목록에 돌려놓아요. 이웃한 빈 블록은 합쳐 단편화를 줄여요.<br><sub>malloc finds a free block on the heap and carves it up; free returns blocks to the free list, merging neighbors to limit fragmentation.</sub> | 블록 앞 헤더에 크기·사용 여부를 기록해 free(p)만으로 반환할 수 있어요. 배치 전략: first fit, best fit, 크기별 풀. 작은 조각이 흩어지면 총량은 충분해도 큰 요청이 실패해요(외부 단편화). glibc ptmalloc, jemalloc, tcmalloc, mimalloc은 스레드별 캐시로 경합을 줄여요.<br><sub>A header before each block records its size and status, so free(p) needs nothing else. Placement policies include first fit, best fit and segregated size classes. Scattered small holes can make a large request fail even with enough total space (external fragmentation). glibc’s ptmalloc, jemalloc, tcmalloc and mimalloc add per-thread caches to cut contention.</sub> |
| **메모리 버그**<br><sub>Memory bugs</sub> | 누수, 해제 후 사용, 이중 해제, 댕글링 포인터는 수동 메모리 관리의 대표적 버그예요. 크래시뿐 아니라 보안 취약점이 돼요.<br><sub>Leaks, use-after-free, double free and dangling pointers are the classic bugs of manual memory management, and they become security holes, not just crashes.</sub> | 마이크로소프트와 크롬 모두 심각한 보안 버그의 약 70%가 메모리 안전성 문제라고 밝혔어요. AddressSanitizer(-fsanitize=address), Valgrind로 잡고, RAII·스마트 포인터(unique\_ptr, shared\_ptr), 러스트의 소유권·빌림 검사, GC 언어로 예방해요.<br><sub>Microsoft and Chrome have both reported that about 70% of their serious security bugs are memory-safety issues. AddressSanitizer (-fsanitize=address) and Valgrind catch them; RAII, smart pointers (unique\_ptr, shared\_ptr), Rust’s ownership and borrow checking, and garbage-collected languages prevent them.</sub> |
| **스택 프레임과 버퍼 오버플로**<br><sub>Stack frames and buffer overflows</sub> | 함수 호출마다 스택에 돌려줄 주소와 지역 변수가 쌓여요. 길이 검사 없이 배열에 쓰면 옆의 데이터와 돌려줄 주소까지 덮어써요.<br><sub>Every call pushes a return address and locals onto the stack. Writing into an array without a length check can overwrite its neighbors, including the return address.</sub> | strcpy·gets처럼 길이를 받지 않는 함수가 주원인. 방어: 스택 카나리(덮어쓰기 감지), NX(스택 실행 금지), ASLR(주소 무작위화), 길이를 받는 snprintf·strlcpy, 범위를 검사하는 언어. 1988년 모리스 웜 이후 가장 유명한 취약점 유형이에요.<br><sub>Functions that take no length, such as strcpy and gets, are the usual cause. Defenses: stack canaries (detect the overwrite), NX (non-executable stack), ASLR (randomized addresses), length-aware snprintf and strlcpy, and bounds-checked languages. It has been the most famous vulnerability class since the 1988 Morris worm.</sub> |
| **비트 연산**<br><sub>Bitwise operations</sub> | AND·OR·XOR·시프트로 정수 안의 비트를 하나씩 켜고 끄고 검사해요. 참/거짓 여러 개를 정수 하나에 담아 한 번에 처리해요.<br><sub>AND, OR, XOR and shifts set, clear and test individual bits, packing many booleans into one integer and updating them together.</sub> | 켜기 x \|= 1 << k, 끄기 x &= ~(1 << k), 뒤집기 x ^= 1 << k, 검사 (x >> k) & 1. x & (x − 1)은 가장 낮은 1을 지우고, 결과가 0이면 2의 거듭제곱. 파일 권한(chmod 755), 기능 플래그, 체스 비트보드, 블룸 필터, 서브넷 마스크, 해시 함수에 써요.<br><sub>Set x \|= 1 << k, clear x &= ~(1 << k), flip x ^= 1 << k, test (x >> k) & 1. x & (x − 1) clears the lowest set bit and is zero exactly for powers of two. Used for file permissions (chmod 755), feature flags, chess bitboards, Bloom filters, subnet masks and hash functions.</sub> |
| **정수 오버플로**<br><sub>Integer overflow</sub> | 고정 크기 정수는 범위를 넘으면 한 바퀴 돌아요. 부호 없는 정수는 mod 2ⁿ으로, C의 부호 있는 정수는 정의되지 않은 동작이에요.<br><sub>Fixed-width integers wrap around past their range: unsigned ones modulo 2ⁿ, while signed overflow in C is undefined behavior.</sub> | uint8 255 + 1 = 0, int8 127 + 1 → −128(대부분의 CPU). 크기 계산 malloc(n \* size)가 넘치면 작은 버퍼가 잡혀 오버플로로 이어져요. size\_t 0 − 1 = 2⁶⁴ − 1. 2014년 강남스타일 조회수가 2³¹ − 1을 넘어 유튜브가 64비트 카운터로 바꿨어요. \_\_builtin\_mul\_overflow, 러스트 checked\_\*, 자바 Math.\*Exact로 검사해요.<br><sub>uint8 255 + 1 = 0; int8 127 + 1 gives −128 on most CPUs. An overflowing size calculation malloc(n \* size) allocates a tiny buffer and invites an overflow. size\_t 0 − 1 is 2⁶⁴ − 1. In 2014 Gangnam Style’s view count passed 2³¹ − 1 and YouTube moved to a 64-bit counter. Check with \_\_builtin\_mul\_overflow, Rust’s checked\_\* or Java’s Math.\*Exact.</sub> |

## 빌드와 링킹 · Building and linking

소스 코드가 실행 파일이 되기까지의 과정이에요.  
*How source code becomes a running executable.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **오브젝트 파일과 섹션**<br><sub>Object files and sections</sub> | 컴파일러는 소스를 오브젝트 파일로 만들어요. 코드는 .text, 초깃값 있는 전역은 .data, 0인 전역은 .bss, 상수는 .rodata에 담기고 심볼 표가 붙어요.<br><sub>The compiler turns source into an object file: code in .text, initialized globals in .data, zeroed globals in .bss, constants in .rodata, plus a symbol table.</sub> | 과정: 전처리(cpp) → 컴파일(cc1) → 어셈블(as) → 링크(ld). 심볼 표에는 정의한 것(T, D, B)과 외부에서 가져올 것(U)이 있어요. .bss는 파일에 크기만 기록해 실행 파일이 작아요. 리눅스 ELF, 윈도우 PE, macOS Mach-O. nm, objdump -d, readelf -S로 살펴봐요.<br><sub>Pipeline: preprocess (cpp) → compile (cc1) → assemble (as) → link (ld). The symbol table lists what is defined (T, D, B) and what must come from elsewhere (U). .bss records only a size, keeping files small. Formats: ELF on Linux, PE on Windows, Mach-O on macOS. Inspect with nm, objdump -d and readelf -S.</sub> |
| **정적 링킹**<br><sub>Static linking</sub> | 링커는 여러 오브젝트 파일의 섹션을 합치고, 정의되지 않은 심볼을 다른 파일의 정의와 연결한 뒤 주소를 확정해 빈칸을 채워요(재배치).<br><sub>The linker merges the sections of several object files, connects undefined symbols to their definitions elsewhere, fixes the final addresses and patches the blanks (relocation).</sub> | “undefined reference”는 정의가 든 오브젝트나 라이브러리(-lm 등)를 빠뜨린 것, “multiple definition”은 같은 이름이 두 번 정의된 것. 정적 라이브러리(.a)는 .o 묶음이라 필요한 것만 실행 파일에 복사돼요. 실행 파일 하나로 배포가 쉽지만 크고, 라이브러리를 고치면 다시 링크해야 해요(Go는 기본이 정적 링킹).<br><sub>“undefined reference” means an object or library (-lm, …) holding the definition is missing; “multiple definition” means a name is defined twice. A static library (.a) is a bundle of .o files, and only what is needed is copied in. One self-contained binary is easy to ship but larger, and fixing a library means relinking (Go links statically by default).</sub> |
| **동적 링킹과 공유 라이브러리**<br><sub>Dynamic linking and shared libraries</sub> | 공유 라이브러리는 실행할 때 연결돼요. 첫 호출에 동적 링커가 함수 주소를 찾아 GOT에 적어 두고, 이후 호출은 그 주소로 바로 가요.<br><sub>Shared libraries are wired in at run time. On the first call the dynamic linker looks the function up and writes its address into the GOT; later calls jump straight there.</sub> | PLT(점프용 작은 코드)와 GOT(주소 표)로 지연 바인딩해요. libc 한 벌을 모든 프로세스가 메모리에서 공유하고, 보안 패치를 다시 링크 없이 적용할 수 있어요. 대신 버전이 안 맞으면 실행이 안 돼요(DLL 지옥). ldd로 의존성 확인, LD\_LIBRARY\_PATH·rpath로 찾는 위치 지정. 리눅스 .so, 윈도우 .dll, macOS .dylib.<br><sub>Lazy binding uses the PLT (small jump stubs) and the GOT (an address table). Every process shares one in-memory copy of libc, and security fixes apply without relinking, at the cost of breakage when versions don’t match (“DLL hell”). ldd lists dependencies; LD\_LIBRARY\_PATH and rpath control where they are searched. Linux .so, Windows .dll, macOS .dylib.</sub> |
| **빌드 시스템 (Make)**<br><sub>Build systems (Make)</sub> | 빌드는 파일 사이의 의존성 그래프예요. 대상이 의존 파일보다 오래됐을 때만 다시 만들어서, 바뀐 부분만 빠르게 빌드해요.<br><sub>A build is a dependency graph of files. Rebuilding a target only when it is older than its inputs keeps incremental builds fast.</sub> | Makefile 규칙 = “대상: 의존 파일” + 명령. 소스 하나를 고치면 그 위 경로만, 널리 쓰는 헤더를 고치면 많이 다시 빌드돼요. make -j로 병렬 빌드, -MMD로 헤더 의존성 자동 생성. CMake는 Makefile·Ninja 파일을 생성하고, Bazel은 내용 해시와 원격 캐시로 거대한 저장소를 빌드해요.<br><sub>A Makefile rule is “target: prerequisites” plus a command. Editing one source rebuilds only the path above it; editing a widely included header rebuilds a lot. make -j runs jobs in parallel and -MMD generates header dependencies. CMake generates Makefiles or Ninja files, and Bazel uses content hashes and remote caches for huge repositories.</sub> |
| **호출 규약 (ABI)**<br><sub>Calling conventions (ABI)</sub> | 함수 인자를 어느 레지스터·스택에 넣고 결과를 어디로 돌려줄지 정한 기계어 수준의 약속이에요. 이 약속 덕분에 다른 컴파일러로 만든 코드도 서로 부를 수 있어요.<br><sub>A machine-level contract for which registers and stack slots carry arguments and where the result returns. It lets code from different compilers call each other.</sub> | x86-64 System V(리눅스·macOS): 정수 인자 rdi, rsi, rdx, rcx, r8, r9, 나머지는 스택, 반환 rax. 윈도우 x64는 rcx, rdx, r8, r9, ARM64는 x0–x7. call이 돌려줄 주소를 넣고, 함수 머리(prologue)가 rbp 저장·지역 변수 공간 확보, leave; ret로 정리. 스택은 16바이트 정렬, rbx·rbp·r12–r15는 호출된 쪽이 보존해요.<br><sub>x86-64 System V (Linux, macOS): integer args in rdi, rsi, rdx, rcx, r8, r9, the rest on the stack, result in rax. Windows x64 uses rcx, rdx, r8, r9; ARM64 uses x0–x7. call pushes the return address, the prologue saves rbp and reserves locals, and leave; ret unwinds. The stack stays 16-byte aligned, and rbx, rbp and r12–r15 are callee-saved.</sub> |

## 프로세스와 파일 · Processes and files

유닉스가 프로그램을 실행하고 자원을 넘겨주는 방식이에요.  
*How Unix launches programs and hands them resources.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **fork와 exec**<br><sub>fork and exec</sub> | fork()는 프로세스를 복제해 두 번 반환하고(부모는 자식 PID, 자식은 0), exec()는 현재 프로그램을 새 프로그램으로 바꿔요. 셸이 명령을 실행하는 방식이에요.<br><sub>fork() clones the process and returns twice (the child’s PID to the parent, 0 to the child); exec() replaces the running program with a new one. That is how a shell runs commands.</sub> | 메모리는 바로 복사하지 않고 공유하다가 쓰는 페이지만 복사해요(copy-on-write). fork와 exec 사이에 셸이 리다이렉션·파이프를 설정해요. 부모는 wait()/waitpid()로 종료 코드를 받아요. posix\_spawn은 둘을 한 번에, 윈도우는 CreateProcess. 파이썬 multiprocessing도 리눅스에선 fork를 써요.<br><sub>Memory isn’t copied up front: pages are shared until written (copy-on-write). Between fork and exec the shell sets up redirection and pipes. The parent collects the exit status with wait()/waitpid(). posix\_spawn does both steps at once; Windows uses CreateProcess. Python’s multiprocessing forks on Linux too.</sub> |
| **좀비와 고아 프로세스**<br><sub>Zombie and orphan processes</sub> | 종료한 자식은 부모가 wait()로 확인할 때까지 종료 코드만 남은 좀비로 남아요. 부모가 먼저 죽으면 PID 1이 고아를 입양해 거둬요.<br><sub>A finished child stays a zombie, holding just its exit status, until the parent calls wait(). If the parent dies first, PID 1 adopts the orphan and reaps it.</sub> | 좀비는 메모리는 거의 안 쓰지만 PID를 차지해서, 쌓이면 새 프로세스를 못 만들어요. SIGCHLD 핸들러에서 waitpid로 거두거나, 데몬은 이중 fork로 init에 넘겨요. 컨테이너에서는 앱이 PID 1이 되기 쉬워 tini·dumb-init 같은 작은 init을 써요. ps의 상태 Z가 좀비예요.<br><sub>Zombies use almost no memory but hold a PID, so enough of them stop new processes from starting. Reap them with waitpid in a SIGCHLD handler, or let daemons double-fork to hand children to init. In containers the app often becomes PID 1, so a tiny init such as tini or dumb-init is used. State Z in ps marks a zombie.</sub> |
| **시그널**<br><sub>Signals</sub> | 커널이 프로세스에 보내는 비동기 알림이에요. 기본 동작(종료 등)을 따르거나 핸들러를 등록해 직접 처리해요.<br><sub>Asynchronous notifications from the kernel to a process. It either takes the default action, such as terminating, or runs a handler you registered.</sub> | SIGINT(Ctrl+C), SIGTERM(정중한 종료 요청), SIGKILL(강제 종료, 못 잡음), SIGSEGV(잘못된 메모리 접근), SIGCHLD(자식 상태 변화). 핸들러는 아무 때나 끼어들므로 async-signal-safe 함수만 쓰고 보통 플래그만 바꿔요. docker stop과 쿠버네티스는 SIGTERM 후 유예 시간이 지나면 SIGKILL을 보내니 SIGTERM을 처리해야 깔끔히 종료돼요.<br><sub>SIGINT (Ctrl+C), SIGTERM (polite termination), SIGKILL (forced, uncatchable), SIGSEGV (invalid memory access), SIGCHLD (a child changed state). Handlers interrupt at arbitrary points, so they may call only async-signal-safe functions and usually just set a flag. docker stop and Kubernetes send SIGTERM, then SIGKILL after a grace period, so handle SIGTERM to shut down cleanly.</sub> |
| **파일 디스크립터**<br><sub>File descriptors</sub> | 프로세스가 연 파일·소켓·파이프를 가리키는 작은 정수예요. 0, 1, 2는 표준 입력·출력·에러이고, open()은 가장 작은 빈 번호를 돌려줘요.<br><sub>Small integers naming the files, sockets and pipes a process has open. 0, 1 and 2 are standard input, output and error, and open() returns the lowest free number.</sub> | fd 표(프로세스별) → 열린 파일 표(커널, 위치·모드) → inode. dup2(fd, 1)로 stdout을 파일에 연결하는 게 셸의 > 리다이렉션. fork하면 fd 표가 복사돼 같은 열린 파일을 공유해요. 닫지 않으면 “Too many open files”(ulimit -n). 유닉스에선 소켓·장치까지 모두 파일처럼 다뤄요.<br><sub>Per-process fd table → kernel open file table (offset, mode) → inode. dup2(fd, 1) points stdout at a file, which is how the shell’s > works. fork copies the fd table, so both processes share the same open files. Leaking fds ends in “Too many open files” (ulimit -n). Unix treats sockets and devices as files too.</sub> |
| **파이프**<br><sub>Pipes</sub> | 커널 버퍼를 사이에 둔 단방향 바이트 통로예요. 한 프로세스의 출력을 다른 프로세스의 입력으로 바로 이어요.<br><sub>A one-way byte channel with a kernel buffer in the middle, connecting one process’s output directly to another’s input.</sub> | ls \| wc -l: 셸이 pipe()로 양 끝 fd를 만들고 두 번 fork해 각자 dup2로 stdout·stdin에 연결해요. 버퍼(리눅스 기본 64 KiB)가 차면 쓰는 쪽이, 비면 읽는 쪽이 멈춰 흐름이 조절돼요. 모든 쓰기 끝이 닫혀야 EOF가 와요. 이름 있는 파이프(mkfifo), 양방향은 socketpair.<br><sub>For ls \| wc -l the shell calls pipe() for two fds, forks twice and uses dup2 to wire stdout and stdin. When the buffer (64 KiB by default on Linux) is full the writer blocks; when empty the reader waits, so the flow paces itself. EOF arrives only once every write end is closed. Named pipes come from mkfifo; for two-way traffic use socketpair.</sub> |
| **메모리 매핑 파일 (mmap)**<br><sub>Memory-mapped files (mmap)</sub> | 파일을 프로세스의 주소 공간에 붙여 포인터로 읽고 써요. 실제 읽기는 처음 건드린 페이지만 페이지 폴트로 일어나요.<br><sub>Attach a file to the address space and work on it through pointers. Data is read only when a page is first touched, via a page fault.</sub> | 쓰기는 페이지 캐시에 반영되고 나중에 디스크로 써져요(msync로 강제). MAP\_SHARED로 여러 프로세스가 같은 페이지를 공유하면 공유 메모리, MAP\_PRIVATE는 copy-on-write. 실행 파일·공유 라이브러리 로딩, LMDB·SQLite, 큰 파일 임의 접근에 써요. 다만 I/O 오류가 SIGBUS로 오고 쓰기 시점을 통제하기 어려워 많은 DB는 직접 버퍼를 관리해요.<br><sub>Writes land in the page cache and reach disk later (force it with msync). With MAP\_SHARED several processes share the same pages, giving shared memory; MAP\_PRIVATE is copy-on-write. Used to load executables and shared libraries, by LMDB and SQLite, and for random access to big files. I/O errors arrive as SIGBUS and write timing is hard to control, so many databases manage their own buffers instead.</sub> |

## I/O와 동시성 · I/O and concurrency

시스템 콜을 아끼고 여러 코어를 안전하게 쓰는 법이에요.  
*Spending fewer syscalls and using many cores safely.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **버퍼링된 I/O**<br><sub>Buffered I/O</sub> | 작은 쓰기를 사용자 공간 버퍼에 모았다가 한 번의 시스템 콜로 보내요. 시스템 콜 횟수가 크게 줄어 빨라져요.<br><sub>Collect small writes in a user-space buffer and hand them to the kernel in one syscall, cutting the number of syscalls dramatically.</sub> | stdio는 터미널이면 줄 단위, 파일·파이프면 버퍼가 찰 때(보통 4~8 KiB) 비워요. 그래서 ./app \| cat은 출력이 늦게 보이고, 비정상 종료하면 버퍼 내용이 사라져요. stderr는 버퍼 없음. fflush·setvbuf로 조절하고, 자바 BufferedWriter, 파이썬 print(flush=True)도 같은 개념이에요.<br><sub>stdio flushes per line on a terminal but only when the buffer fills (typically 4–8 KiB) on files and pipes. That is why ./app \| cat shows output late and why a crash loses buffered data. stderr is unbuffered. Control it with fflush and setvbuf; Java’s BufferedWriter and Python’s print(flush=True) are the same idea.</sub> |
| **I/O 멀티플렉싱 (epoll)**<br><sub>I/O multiplexing (epoll)</sub> | 스레드 하나가 수많은 소켓을 등록해 두고, 데이터가 준비된 소켓만 받아 처리해요. 연결마다 스레드를 두지 않아도 돼요.<br><sub>One thread registers many sockets and handles only those with data ready, with no need for a thread per connection.</sub> | select·poll은 매번 모든 fd를 훑어 O(n), epoll은 준비된 것만 돌려줘요. 논블로킹 소켓 + 이벤트 루프 구조로 nginx, Node.js(libuv), Redis, Netty가 수만 연결을 처리해요. BSD·macOS는 kqueue, 윈도우는 IOCP, 리눅스 io\_uring은 제출·완료 큐로 시스템 콜까지 줄여요.<br><sub>select and poll rescan every fd each time (O(n)); epoll returns just the ready ones. Non-blocking sockets plus an event loop let nginx, Node.js (libuv), Redis and Netty juggle tens of thousands of connections. BSD and macOS use kqueue, Windows IOCP, and Linux’s io\_uring goes further with submission and completion queues that cut syscalls.</sub> |
| **제로 카피**<br><sub>Zero copy</sub> | 파일을 그대로 네트워크로 보낼 때 데이터를 사용자 공간으로 올리지 않고 커널 안에서 바로 보내요. CPU 복사와 모드 전환이 줄어요.<br><sub>When a file goes to the network unchanged, send it from inside the kernel without lifting it into user space, avoiding CPU copies and mode switches.</sub> | read() + write()는 복사 4번(CPU 2번)·모드 전환 4번, sendfile()은 복사 2번(모두 DMA)·전환 2번. nginx의 sendfile on, 카프카의 로그 전송, 자바 FileChannel.transferTo, 리눅스 splice. TLS 암호화처럼 데이터를 바꿔야 하면 커널 TLS(kTLS)가 있어야 제로 카피를 유지해요.<br><sub>read() + write() costs four copies (two by the CPU) and four mode switches; sendfile() needs two copies (both DMA) and two switches. Used by nginx’s “sendfile on”, Kafka’s log shipping, Java’s FileChannel.transferTo and Linux splice. If the data must be transformed, as with TLS, kernel TLS (kTLS) keeps it zero-copy.</sub> |
| **원자적 연산과 CAS**<br><sub>Atomic operations and CAS</sub> | CAS(compare-and-swap)는 “값이 아직 예상과 같으면 새 값으로 바꾼다”를 끊김 없이 한 번에 해요. 실패하면 다시 읽고 재시도해요.<br><sub>CAS (compare-and-swap) does “if the value is still what I expect, replace it” as one indivisible step; on failure you reread and retry.</sub> | 락 없이도 안전한 카운터·스택·큐(lock-free)의 기본 부품. 값만 비교하므로 A → B → A 변화를 놓치는 ABA 문제는 버전 태그로 막아요. 하드웨어: x86 lock cmpxchg, ARM LDXR/STXR. 언어: C++ std::atomic, 자바 AtomicInteger·LongAdder, Go sync/atomic. 경쟁이 심하면 재시도가 많아져 락보다 느려질 수 있어요.<br><sub>It is the building block of lock-free counters, stacks and queues. Because only values are compared, an A → B → A change slips past (the ABA problem), fixed with version tags. Hardware: x86 lock cmpxchg, ARM LDXR/STXR. Languages: C++ std::atomic, Java AtomicInteger and LongAdder, Go sync/atomic. Under heavy contention the retries can make it slower than a lock.</sub> |
| **메모리 순서**<br><sub>Memory ordering</sub> | 컴파일러와 CPU는 성능을 위해 메모리 접근 순서를 바꿀 수 있어서, 다른 코어에는 쓰기가 다른 순서로 보일 수 있어요. release/acquire로 순서를 약속해요.<br><sub>Compilers and CPUs may reorder memory accesses for speed, so another core can see writes in a different order. Release/acquire pairs pin the order down.</sub> | 예: data = 42; ready = 1을 다른 스레드가 ready부터 보고 data는 아직 0으로 볼 수 있어요. release 저장 이전의 쓰기는 짝이 되는 acquire 읽기 이후에 반드시 보여요(happens-before). x86은 비교적 강한 TSO, ARM·POWER는 약해요. C/C++ volatile은 동기화가 아니고, 자바 volatile은 동기화예요. 보통은 뮤텍스나 atomic으로 해결해요.<br><sub>After data = 42; ready = 1 another thread may see ready set while data still reads 0. Writes before a release store are visible after the matching acquire load (happens-before). x86 is fairly strong (TSO); ARM and POWER are weaker. volatile in C/C++ is not synchronization, while Java’s volatile is. In practice, reach for mutexes or atomics.</sub> |
| **스핀락과 뮤텍스**<br><sub>Spinlocks and mutexes</sub> | 스핀락은 CPU를 쓰며 계속 확인하고, 뮤텍스는 잠들었다가 깨어나요. 락을 아주 잠깐 쥘 때는 스핀이, 오래 쥘 때는 잠드는 쪽이 나아요.<br><sub>A spinlock burns CPU re-checking; a mutex puts the waiter to sleep and wakes it later. Spinning wins for very short holds, sleeping for long ones.</sub> | 문맥 교환은 수 µs가 들어 그보다 짧은 대기는 스핀이 유리해요. 리눅스 futex는 경쟁이 없으면 사용자 공간 원자 연산 하나로 끝나고 경쟁할 때만 커널로 가요. 적응형 뮤텍스는 잠깐 돌다 잠들어요. 커널은 인터럽트 문맥에서 스핀락을 쓰고, 코어가 하나뿐이면 스핀은 의미가 없어요.<br><sub>A context switch costs microseconds, so shorter waits favor spinning. Linux futexes finish with a single user-space atomic when uncontended and enter the kernel only under contention, and adaptive mutexes spin briefly before sleeping. Kernels spin in interrupt context; on a single core, spinning is pointless.</sub> |
