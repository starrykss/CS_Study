| **포인터와 배열**<br><sub>Pointers and arrays</sub> | 포인터는 주소를 담는 변수이고, 포인터 산술은 가리키는 타입의 크기 단위로 움직여요. 배열은 함수에 넘기면 포인터로 바뀌어 크기를 잃어요.<br><sub>A pointer is a variable holding an address, and pointer arithmetic moves in units of the pointed-to type. Arrays passed to functions decay into pointers and lose their size.</sub> | C와 C++에서 포인터는 메모리 주소를 담는 변수로, 64비트 시스템에서 8바이트예요. int arr[5]는 int 다섯 개를 메모리에 연속으로 놓고, int \*p = arr이라고 쓰면 배열 이름이 첫 원소의 주소로 바뀌어 담겨요. \*p는 그 주소의 값을 읽는 역참조예요. 포인터에 정수를 더하면 바이트가 아니라 가리키는 타입의 크기 단위로 움직여서, int 포인터 p + 2는 2 × 4 = 8바이트 뒤를 가리키고 \*(p + 2)는 3이에요. 사실 arr[2]라는 표기 자체가 \*(arr + 2)의 다른 표기라서, 배열 접근은 포인터 산술 위에 만들어져 있어요. sizeof(arr)는 배열 전체인 20이지만 sizeof(p)는 주소 크기인 8이에요. 배열을 함수 인자로 넘기면 첫 원소의 포인터로 바뀌어(decay) 크기 정보를 잃기 때문에, 함수 안에서 sizeof로 길이를 구할 수 없고 C 함수는 길이를 따로 받아요. C++에서는 std::span이나 컨테이너를 넘겨 이 문제를 피해요. 포인터의 포인터 int \*\*pp = &p는 p의 주소를 담아, \*\*pp로 두 번 따라가면 1이에요. 해제된 메모리나 NULL, 배열 범위 밖을 역참조하는 것은 정의되지 않은 동작이라 무슨 일이든 일어날 수 있어요. 모던 C++에서는 소유권을 가진 원시 포인터 대신 스마트 포인터를 쓰고, 원시 포인터는 소유하지 않는 참조 용도로만 써요.<br><sub>In C and C++, a pointer is a variable holding a memory address, 8 bytes on 64-bit systems. int arr[5] lays out five ints contiguously, and int \*p = arr converts the array name into the address of its first element. \*p dereferences, reading the value at that address. Adding an integer to a pointer moves in units of the pointed-to type, not bytes, so the int pointer p + 2 points 2 × 4 = 8 bytes ahead and \*(p + 2) is 3. In fact arr[2] is just another way of writing \*(arr + 2), so array access is built on pointer arithmetic. sizeof(arr) is 20, the whole array, but sizeof(p) is 8, the size of an address. Passing an array as a function argument converts it into a pointer to its first element (decay), losing the size, so sizeof cannot recover the length inside the function and C functions take the length separately; C++ avoids this by passing std::span or containers. The pointer-to-pointer int \*\*pp = &p holds the address of p, and following it twice with \*\*pp gives 1. Dereferencing freed memory, NULL or anything out of bounds is undefined behavior, where anything can happen. Modern C++ uses smart pointers instead of owning raw pointers and keeps raw pointers for non-owning references.</sub> |
| **구조체 패딩과 정렬**<br><sub>Struct padding and alignment</sub> | 각 필드는 자기 정렬의 배수 주소에 놓여서 사이사이에 패딩이 생겨요. 필드 순서만 바꿔도 구조체 크기가 줄어들 수 있어요.<br><sub>Each field sits at a multiple of its alignment, leaving padding in between. Just reordering fields can shrink a struct.</sub> | CPU는 4바이트 int를 4의 배수 주소에서 한 번에 읽도록 만들어져 있어서, 컴파일러는 각 타입을 자기 정렬(alignof)의 배수 주소에 놓아요. char는 1, int는 4, double과 포인터는 보통 8이에요. struct A { char c; int i; char d; }에서 c는 0번에 놓이고, i는 4의 배수인 4번에 와야 하므로 c 뒤에 3바이트가 비어요. d는 8번에 놓이고, 구조체 배열의 다음 원소에서도 i가 정렬되도록 전체 크기를 가장 큰 정렬인 4의 배수로 맞추느라 d 뒤에 3바이트가 더 붙어 12바이트가 돼요. 같은 필드를 int, char, char 순서로 놓은 struct B는 8바이트면 충분해요. 원소가 수백만 개인 배열이라면 이 차이가 그대로 메모리와 캐시 효율의 차이가 되므로, 큰 필드부터 놓는 것이 기본 요령이에요. sizeof, offsetof, alignof로 실제 배치를 확인할 수 있어요(여기 값은 x86-64의 g++로 확인했어요). 정렬되지 않은 접근은 x86에서는 느리고, 일부 ARM 같은 아키텍처에서는 오류가 나요. #pragma pack이나 \_\_attribute\_\_((packed))로 패딩을 없앨 수 있지만 접근이 느려지고 위험해서, 네트워크 패킷이나 파일 형식처럼 바이트 배치가 정해진 경우에만 써요. 반대로 여러 스레드가 쓰는 필드는 일부러 64바이트 캐시 라인으로 떨어뜨려 거짓 공유를 피하기도 해요.<br><sub>CPUs are built to load a 4-byte int from an address that is a multiple of 4 in one access, so compilers place each type at a multiple of its alignment (alignof): 1 for char, 4 for int and usually 8 for double and pointers. In struct A { char c; int i; char d; }, c goes at offset 0, and i must come at a multiple of 4, offset 4, leaving 3 empty bytes after c. d goes at offset 8, and so that i stays aligned in the next element of an array of structs, the total size is rounded up to a multiple of the largest alignment, 4, adding 3 more bytes after d for 12 in all. struct B, with the same fields ordered int, char, char, needs only 8. In an array of millions of elements this difference becomes a direct difference in memory and cache efficiency, so putting larger fields first is the basic rule. sizeof, offsetof and alignof reveal the actual layout (the values here were checked with g++ on x86-64). Misaligned access is slow on x86 and faults on some architectures, such as certain ARM chips. #pragma pack or \_\_attribute\_\_((packed)) removes padding, but access becomes slow and risky, so it is reserved for fixed byte layouts such as network packets and file formats. Conversely, fields written by different threads are sometimes deliberately separated onto different 64-byte cache lines to avoid false sharing.</sub> |
| **정의되지 않은 동작**<br><sub>Undefined behavior</sub> | 부호 있는 넘침, 범위 밖 접근, 해제 후 사용 같은 UB는 무엇이든 될 수 있어요. 컴파일러는 UB가 없다고 가정하고 최적화해서 검사 코드를 지우기도 해요.<br><sub>UB such as signed overflow, out-of-bounds access and use after free can do anything. Compilers optimize assuming UB never happens and may even delete checks.</sub> | C와 C++ 표준은 일부 동작의 결과를 정하지 않았는데, 이를 정의되지 않은 동작(UB)이라 해요. 부호 있는 정수의 넘침, 배열 범위 밖 읽기·쓰기, 해제한 메모리 사용, 널 포인터 역참조, 초기화하지 않은 변수 읽기, 동기화 없는 데이터 경쟁이 대표적이에요. 중요한 것은 UB가 "이상한 값이 나오는 정도"가 아니라 프로그램 전체의 의미가 사라진다는 점이에요. 컴파일러는 올바른 프로그램에는 UB가 없다고 가정하고 그 가정 위에서 최적화해요. 예를 들어 i + 1 > i는 부호 있는 넘침이 없다면 항상 참이므로, g++ -O2는 이 함수를 그냥 true를 돌려주게 바꿔요(여기서 직접 확인했어요). 그래서 f(INT\_MAX)도 true를 돌려주고, 넘침을 확인하려고 쓴 if (x + 1 < x) 같은 검사도 통째로 지워질 수 있어요. 범위 밖 쓰기는 옆의 변수나 함수의 반환 주소를 덮어써서, 당장은 멀쩡해 보이다가 엉뚱한 곳에서 터지는 조용한 손상과 버퍼 오버플로 같은 보안 취약점으로 이어져요. 해제 후 사용 역시 공격자가 해제된 자리에 데이터를 채워 악용하는 대표적인 취약점이에요. -Wall -Wextra 경고, AddressSanitizer와 UndefinedBehaviorSanitizer를 켠 테스트, 범위를 검사하는 .at()이나 std::span, 넘침 검사 내장 함수(\_\_builtin\_add\_overflow)로 막아요. 부호 없는 정수의 넘침은 UB가 아니라 래핑으로 정의돼 있어요.<br><sub>The C and C++ standards leave the results of some operations unspecified; this is undefined behavior (UB). Signed integer overflow, out-of-bounds reads and writes, using freed memory, null dereference, reading uninitialized variables and unsynchronized data races are the chief examples. The key point is that UB is not “a strange value” but the loss of meaning for the whole program. Compilers assume a correct program contains no UB and optimize on that assumption. For instance, i + 1 > i is always true if signed overflow cannot happen, so g++ -O2 turns the function into one that just returns true (verified here), meaning f(INT\_MAX) returns true and an overflow check such as if (x + 1 < x) may be deleted outright. Out-of-bounds writes overwrite neighboring variables or a function’s return address, causing silent corruption that looks fine now and blows up elsewhere later, and security holes such as buffer overflows. Use after free is likewise a classic vulnerability, exploited by filling the freed spot with attacker data. Defend with -Wall -Wextra warnings, tests run under AddressSanitizer and UndefinedBehaviorSanitizer, bounds-checked .at() or std::span, and overflow-checking builtins such as \_\_builtin\_add\_overflow. Unsigned overflow, by contrast, is not UB but defined to wrap.</sub> |
| **스택과 힙**<br><sub>The stack and the heap</sub> | 지역 변수는 스택에 자동으로 생기고 사라지며 거의 공짜예요. 힙은 크기와 수명이 자유롭지만 직접 해제해야 해서 누수와 이중 해제가 생겨요.<br><sub>Locals appear and vanish on the stack automatically, almost for free. The heap allows any size and lifetime but must be freed by hand, which breeds leaks and double frees.</sub> | 함수를 부르면 스택에 프레임이 쌓여 지역 변수, 반환 주소, 저장된 레지스터가 들어가요. 스택 할당은 스택 포인터 레지스터를 옮기기만 하면 되어 거의 공짜이고, 함수가 반환되면 프레임째 자동으로 사라져요. 하지만 크기가 컴파일할 때 정해져 있어야 하고(가변 길이 배열은 예외적), 함수보다 오래 살 수 없으며, 스택 자체가 리눅스 기본 8MB 정도로 작아서 큰 배열이나 깊은 재귀는 스택 오버플로를 일으켜요. 힙은 malloc(C)이나 new(C++)로 실행 중에 원하는 크기를 요청하는 영역이에요. 할당자는 빈 블록 목록에서 맞는 크기를 찾고 크기 정보를 담은 헤더를 붙여 주소를 돌려줘서, 스택보다 훨씬 비싸고 시간이 지나면 조각화도 생겨요. 대신 크기와 수명이 자유로워서 함수가 끝난 뒤에도 남아야 하는 데이터나 실행 중에 크기가 정해지는 데이터를 담아요. 힙 메모리는 free나 delete로 직접 돌려줘야 하는데, 잊으면 누수, 두 번 하면 이중 해제, 해제 뒤 다시 쓰면 해제 후 사용이 되어 셋 다 흔하고 위험한 버그예요. 지역 변수의 주소를 반환하는 것도 이미 사라진 프레임을 가리키는 댕글링 포인터가 돼요. 모던 C++에서는 vector, string 같은 컨테이너와 unique\_ptr 같은 스마트 포인터가 소멸자에서 자동으로 해제해서 직접 new와 delete를 쓸 일이 거의 없어요.<br><sub>Calling a function pushes a frame onto the stack containing locals, the return address and saved registers. Stack allocation just moves the stack-pointer register, almost free, and the whole frame disappears automatically when the function returns. But sizes must be known at compile time (variable-length arrays aside), nothing can outlive the function, and the stack itself is small, about 8 MB by default on Linux, so large arrays or deep recursion cause stack overflow. The heap is the area where malloc (C) or new (C++) requests any size at run time. The allocator finds a fitting block in its free lists and attaches a header recording the size before returning an address, which is far costlier than the stack and leads to fragmentation over time. In exchange, size and lifetime are free, so the heap holds data that must survive the function or whose size is known only at run time. Heap memory must be returned explicitly with free or delete: forgetting leaks, doing it twice is a double free, and using it afterward is use after free, all common and dangerous bugs. Returning a local’s address likewise leaves a dangling pointer into a frame that no longer exists. In modern C++, containers such as vector and string and smart pointers such as unique\_ptr free memory automatically in their destructors, so writing new and delete by hand is rarely necessary.</sub> |
| **C 문자열과 버퍼 오버플로**<br><sub>C strings and buffer overflows</sub> | C 문자열은 \0으로 끝나는 char 배열이라 크기를 프로그래머가 지켜야 해요. 크기를 모르는 strcpy는 버퍼 오버플로를 일으키고, C++의 std::string이 이를 막아요.<br><sub>A C string is a \0-terminated char array, so the programmer must guard its size. strcpy, unaware of sizes, causes buffer overflows, which C++’s std::string prevents.</sub> | C 문자열에는 길이 필드가 없어요. 문자들 뒤에 널 문자 \0을 붙인 char 배열이고, 문자열 리터럴 "hi"도 읽기 전용 메모리의 {'h', 'i', '\0'} 세 바이트예요. 길이를 알려면 \0이 나올 때까지 세야 해서 strlen은 O(n)이고, 반복해서 부르면 숨은 비용이 커요. 더 큰 문제는 대상 버퍼의 크기를 모르는 함수들이에요. strcpy(buf, "hello, world")는 원본을 \0까지 13바이트 복사하는데, buf가 8바이트라면 나머지 5바이트가 바로 옆의 변수나 스택의 반환 주소를 덮어써요. 이것이 버퍼 오버플로로, 수십 년 동안 가장 흔한 보안 취약점이었고 공격자가 반환 주소를 바꿔 원하는 코드를 실행하게 만들 수도 있어요. snprintf(buf, sizeof buf, "%s", s)처럼 크기를 받는 함수를 쓰면 공간 안에서 자르고 항상 \0으로 끝내서 안전해요. strncpy는 이름과 달리 공간이 모자라면 \0을 붙이지 않아 오히려 함정이 되고, gets는 아예 표준에서 제거됐어요. C++의 std::string은 길이와 용량을 스스로 관리하고 필요하면 늘어나서 이런 실수를 원천적으로 막아요. libstdc++의 std::string은 32바이트 객체로, 15자 이하의 짧은 문자열은 힙 할당 없이 객체 안에 바로 담는 SSO(small string optimization)를 해요. 읽기만 할 문자열을 넘길 때는 복사 없는 std::string\_view를 써요.<br><sub>C strings have no length field: they are char arrays with a null character \0 after the characters, and even the literal "hi" is the three bytes {'h', 'i', '\0'} in read-only memory. Finding the length means counting until \0, so strlen is O(n), a hidden cost when called repeatedly. The bigger problem is functions that do not know the destination’s size. strcpy(buf, "hello, world") copies 13 bytes, up to the \0, and if buf is 8 bytes, the remaining 5 overwrite the neighboring variable or the return address on the stack. This is a buffer overflow, for decades the most common security vulnerability, which can let an attacker change the return address and run code of their choosing. Functions that take sizes, such as snprintf(buf, sizeof buf, "%s", s), truncate within the space and always terminate with \0, which is safe. strncpy, despite its name, omits the \0 when space runs out and becomes a trap itself, and gets was removed from the standard altogether. C++’s std::string manages its own length and capacity and grows as needed, ruling out these mistakes. libstdc++’s std::string is a 32-byte object that stores strings of up to 15 characters inside itself without heap allocation, the small string optimization (SSO). For strings that are only read, pass a copy-free std::string\_view.</sub> |
| **컴파일과 링크**<br><sub>Compiling and linking</sub> | 소스는 전처리, 컴파일, 어셈블을 거쳐 목적 파일이 되고, 링커가 기호를 맞춰 실행 파일로 묶어요. 헤더에는 선언만, 정의는 한 곳에만 둬요.<br><sub>Source becomes object files through preprocessing, compiling and assembling, and the linker resolves symbols into an executable. C++은 오버로딩을 위해 add(int, int)를 \_Z3addii처럼 매개변수 타입을 넣은 이름으로 바꾸므로(이름 맹글링), C 코드와 연결할 때는 extern "C"로 맹글링을 끄고 써요.<br><sub>Behind the single line gcc main.c math.c hide several stages. First the preprocessor pastes the text of header files where #include appears, expands #define macros and selects code with #ifdef. The compiler turns the result into assembly, and the assembler produces a machine-code object file (.o). Each .c file compiles separately, unaware of the others, so main.c generates the call to add from the declaration int add(int, int) in math.h alone, leaving add in main.o as a needed but undefined symbol, while math.o defines it. A missing definition yields undefined reference, and two definitions of the same function yield multiple definition. Hence headers hold only declarations, with each definition in exactly one source file: the one-definition rule (ODR). Include guards or #pragma once keep a header from being included twice. Static libraries (.a, .lib) copy the needed code into the executable, while dynamic libraries (.so, .dll) are connected at run time and shared in memory by many programs. | **RAII**<br><sub>RAII</sub> | RAII는 자원을 생성자에서 얻고 소멸자에서 돌려주는 C++의 핵심 관용구예요. 예외가 나도 스택 되감기가 소멸자를 불러서 정리가 보장돼요.<br><sub>RAII acquires a resource in the constructor and releases it in the destructor, the core C++ idiom. The constructor acquires the resource, and the moment the object leaves scope its destructor returns it automatically. std::ofstream out(path) opens the file in its constructor, and at the function’s closing brace the destructor closes it. The key point is that this cleanup happens however the function ends. Whether it returns early or an exception is thrown, C++ unwinds the stack and calls the destructors of every local already constructed. With several locals, release happens in reverse order of construction, so dependencies of later objects on earlier ones are naturally respected. Since no cleanup code is written by hand, none can be forgotten. That is why C++ has no finally like Java or Python and no need for the goto-cleanup pattern common in C. unique\_ptr and shared\_ptr manage memory, vector and string manage buffers, lock\_guard and unique\_lock manage mutexes and fstream manages files, all through RAII, so the whole standard library stands on this principle. One caution: destructors must not throw. A second exception during unwinding ends the program through std::terminate, which is why destructors are noexcept by default. Rust’s Drop, C#’s using and Python’s with come from the same idea.</sub> |
| **unique\_ptr**<br><sub>unique\_ptr</sub> | unique\_ptr는 객체를 혼자 소유하는 스마트 포인터예요. 복사는 금지되고 std::move로만 소유권을 넘기며, 원시 포인터와 같은 크기에 비용이 없어요.<br><sub>unique\_ptr is a smart pointer with sole ownership of its object. Copying is forbidden and ownership moves only with std::move, at the same size as a raw pointer and with no cost.</sub> | std::unique\_ptr는 힙 객체를 혼자 소유하는 스마트 포인터예요. auto p = std::make\_unique<Widget>(42)는 Widget을 힙에 만들고 p를 유일한 소유자로 삼아서, p가 범위를 벗어나면 Widget을 자동으로 delete해요. 소유자가 항상 하나라서, 소유권은 auto q = std::move(p)처럼 이동으로만 넘길 수 있어요. 이동이 끝나면 q가 Widget을 가지고 p는 nullptr가 되므로, 두 포인터가 같은 객체를 delete하는 이중 해제가 원천적으로 막혀요. unique\_ptr의 복사 생성자와 복사 대입 연산자는 삭제(= delete)되어 있어서 auto r = q는 컴파일 오류예요. 런타임 버그를 컴파일 시간 오류로 바꾼 셈이에요. 객체를 소유하지 않고 잠깐 쓰게 할 때는 \*q로 참조를 넘기거나 q.get()으로 원시 포인터를 빌려줘요. 함수 시그니처만 봐도 의도가 드러나서, unique\_ptr를 값으로 받는 함수는 소유권을 가져가고, 참조나 원시 포인터를 받는 함수는 빌려 쓰기만 해요. unique\_ptr는 내부적으로 포인터 하나만 가지므로 64비트에서 원시 포인터와 같은 8바이트이고, 역참조도 똑같이 빨라서 추가 비용이 없어요. 커스텀 삭제자를 주면 unique\_ptr<FILE, decltype(&fclose)>처럼 C 라이브러리의 FILE\*이나 소켓 핸들도 관리할 수 있어요. new를 직접 쓰는 대신 make\_unique를 쓰면 예외 안전성도 좋아져서, 모던 C++에서는 코드에 new와 delete가 거의 나타나지 않아요. 팩토리 함수는 보통 unique\_ptr를 돌려주고, 필요하면 받는 쪽이 shared\_ptr로 바꿀 수 있어요.<br><sub>std::unique\_ptr is a smart pointer that solely owns a heap object. auto p = std::make\_unique<Widget>(42) creates a Widget on the heap with p as its only owner, and when p leaves scope the Widget is deleted automatically. Because there is always exactly one owner, ownership can be handed over only by moving, as in auto q = std::move(p). Afterwards q holds the Widget and p is nullptr, so a double delete by two pointers is impossible by construction. unique\_ptr’s copy constructor and copy assignment are deleted (= delete), so auto r = q is a compile error, turning a run-time bug into a compile-time one. To let code use the object without owning it, lend a reference through \*q or a raw pointer through q.get(). Function signatures then reveal intent: a function taking unique\_ptr by value takes ownership, while one taking a reference or raw pointer only borrows. Internally a unique\_ptr holds just one pointer, so it is 8 bytes on 64-bit systems like a raw pointer and dereferences just as fast, with no extra cost. Given a custom deleter, as in unique\_ptr<FILE, decltype(&fclose)>, it can also manage C resources such as FILE\* or socket handles. Using make\_unique instead of a bare new also improves exception safety, so new and delete rarely appear in modern C++ code. Factory functions usually return unique\_ptr, which the caller can convert to shared\_ptr if needed.</sub> |
| **shared\_ptr와 weak\_ptr**<br><sub>shared\_ptr and weak\_ptr</sub> | shared\_ptr는 참조 수를 세어 마지막 소유자가 사라질 때 객체를 지워요. weak\_ptr는 수에 포함되지 않아 순환 참조를 끊어요.<br><sub>shared\_ptr counts references and deletes the object when the last owner goes. weak\_ptr is not counted, which breaks reference cycles.</sub> | std::shared\_ptr는 여러 소유자가 하나의 객체를 함께 소유하는 스마트 포인터예요. 객체 옆에 제어 블록(control block)이 있어서 강한 참조 수와 약한 참조 수를 세요. auto b = a처럼 복사할 때마다 강한 수가 1 늘고, 소유자가 사라질 때마다 1 줄어들어, 마지막 소유자가 사라져 수가 0이 되면 객체가 삭제돼요. 여러 스레드가 같은 객체의 shared\_ptr를 동시에 복사할 수 있도록 수의 증감은 원자적 연산이라, 복사가 공짜가 아니에요. shared\_ptr 자체는 객체 포인터와 제어 블록 포인터 두 개를 가져서 64비트에서 16바이트예요. make\_shared는 객체와 제어 블록을 한 번의 할당으로 붙여 만들어서, new로 만든 뒤 넘기는 것보다 빠르고 메모리도 적게 써요. std::weak\_ptr는 객체를 가리키지만 강한 수에 포함되지 않아서 객체를 살려 두지 않아요. 쓰려면 w.lock()으로 잠시 shared\_ptr를 얻는데, 객체가 이미 사라졌으면 nullptr가 나와요. 캐시나 관찰자 목록처럼 있으면 쓰고 없으면 그만인 참조에 알맞아요. 가장 큰 함정은 순환 참조예요. 부모와 자식이 서로를 shared\_ptr로 가리키면 서로가 서로를 붙잡아 수가 영영 0이 되지 않고 둘 다 누수돼요. 그래서 트리나 그래프에서 역방향 참조는 weak\_ptr로 만들어요. 공유 소유는 소유 관계를 흐리게 만들기 때문에 기본은 unique\_ptr로 하고, 정말 수명을 여러 곳이 함께 결정해야 할 때만 shared\_ptr를 써요. 함수 인자로는 복사 비용을 피하려 const 참조로 넘겨요.<br><sub>std::shared\_ptr is a smart pointer through which several owners share one object. Beside the object sits a control block that counts strong and weak references. Every copy such as auto b = a raises the strong count by one and every owner that goes away lowers it, and when the last owner disappears and the count reaches 0, the object is deleted. So that several threads can copy shared\_ptrs to the same object at once, the count updates are atomic operations, which means copies are not free. A shared\_ptr itself holds two pointers, one to the object and one to the control block, making it 16 bytes on 64-bit systems. make\_shared builds the object and its control block in a single allocation, faster and leaner than creating with new and handing the pointer over. std::weak\_ptr points at the object without counting toward the strong total, so it does not keep the object alive. To use it, w.lock() briefly yields a shared\_ptr, or nullptr if the object is already gone, which suits references that use an object only if it still exists, such as caches and observer lists. The biggest trap is a reference cycle. If parent and child point at each other with shared\_ptr, each keeps the other alive, the counts never reach 0, and both leak. So back references in trees and graphs are made weak\_ptr. Shared ownership blurs who owns what, so the default is unique\_ptr, with shared\_ptr reserved for cases where several places genuinely decide the lifetime together. As function arguments, pass them by const reference to avoid the cost of copying.</sub> |
| **이동 의미론**<br><sub>Move semantics</sub> | 이동은 복사 대신 자원의 포인터만 넘겨받고 원본을 비워요. std::move는 rvalue로 바꾸는 캐스트일 뿐이고, 실제 이동은 이동 생성자가 해요.<br><sub>A move takes over the resource pointer instead of copying and leaves the source empty. std::move is merely a cast to an rvalue; the move constructor does the actual moving.</sub> | C++11은 복사 대신 자원을 넘기는 이동(move)을 도입했어요. std::vector<int> 객체 자체는 버퍼 포인터, 크기, 용량만 가진 24바이트짜리 작은 객체이고, 원소 백만 개(4MB)는 힙의 버퍼에 있어요. auto b = a는 복사라서 b를 위한 새 4MB 버퍼를 할당하고 원소를 모두 옮겨 O(n)이 들어요. 반면 auto c = std::move(a)는 이동이라서 c가 a의 버퍼 포인터를 그대로 넘겨받고 a는 빈 상태가 돼요. 원소 수와 상관없이 포인터 몇 개만 옮기므로 O(1)이에요. 이동된 a는 유효하지만 값이 정해지지 않은 상태(valid but unspecified)라서, 다시 대입한 뒤에 써야 해요. 이를 가능하게 하는 것이 rvalue 참조 T&&예요. 임시 객체처럼 곧 사라질 값(rvalue)은 자원을 훔쳐도 되므로, 컴파일러는 rvalue를 받을 때 복사 생성자 대신 이동 생성자 T(T&&)를 골라요. std::move 자체는 아무것도 옮기지 않고 이름 있는 변수를 rvalue 참조로 바꾸는 캐스트일 뿐이에요. 이동 생성자는 noexcept로 표시해야 해요. vector가 재할당할 때 원소를 옮기다 예외가 나면 원래 상태로 돌아갈 수 없으므로, noexcept가 아닌 이동 생성자는 쓰지 않고 안전한 복사를 택하기 때문이에요. 함수에서 지역 객체를 값으로 반환할 때는 std::move를 붙이지 않아요. 컴파일러가 복사 생략(RVO)으로 반환 객체를 호출자 자리에 바로 만들고, C++17부터 임시 객체에 대해서는 이것이 보장돼요. unique\_ptr, thread, fstream처럼 복사할 수 없는 타입도 이동으로는 넘길 수 있어요.<br><sub>C++11 introduced moves, which hand resources over instead of copying them. A std::vector<int> object itself is a small 24-byte thing holding a buffer pointer, a size and a capacity, while its million elements (4 MB) live in a heap buffer. auto b = a is a copy: it allocates a new 4 MB buffer for b and copies every element, O(n). auto c = std::move(a), by contrast, is a move: c takes over a’s buffer pointer as is and a is left empty. Only a few pointers move regardless of the element count, so it is O(1). The moved-from a is valid but unspecified, so it must be reassigned before use. The rvalue reference T&& makes this possible. A value about to vanish, such as a temporary (an rvalue), can safely have its resources stolen, so when given an rvalue the compiler picks the move constructor T(T&&) over the copy constructor. std::move itself moves nothing; it is merely a cast that turns a named variable into an rvalue reference. Move constructors should be marked noexcept. If an exception struck while vector was moving elements during reallocation, it could not restore the original state, so vector avoids non-noexcept move constructors and chooses the safe copy instead. When returning a local object by value, do not add std::move: the compiler applies copy elision (RVO) and builds the result directly in the caller’s slot, which C++17 guarantees for temporaries. Types that cannot be copied, such as unique\_ptr, thread and fstream, can still be passed along by moving.</sub> |
| **0·3·5의 규칙**<br><sub>The rules of zero, three and five</sub> | 자원을 직접 관리하는 클래스는 소멸자, 복사, 이동 연산 다섯 개를 함께 정의해야 해요. 가장 좋은 것은 자원을 RAII 멤버에 맡겨 하나도 안 쓰는 규칙 0이에요.<br><sub>A class that manages a resource directly must define the destructor and the copy and move operations, five in all. The compiler-generated copy constructor copies members one by one, and a pointer copies only its value (a shallow copy), so after Buf y = x, x.data and y.data point at the same buffer. When both objects’ destructors call delete[], the result is a double free, and modifying one changes the other. Hence the rule of three: a class that needs a hand-written destructor also needs a hand-written copy constructor and copy assignment that allocate a new buffer and copy the contents (a deep copy). If one of the three is needed, so are the other two. | **오버로딩과 이름 맹글링**<br><sub>Overloading and name mangling</sub> | 같은 이름의 함수를 매개변수 타입으로 구분해요. 컴파일러는 타입을 이름에 새기고, 호출마다 변환 순위로 가장 좋은 후보를 골라요.<br><sub>Functions with the same name are told apart by parameter types. | **가상 함수와 vtable**<br><sub>Virtual functions and the vtable</sub> | 가상 함수는 객체 속 숨은 vptr가 가리키는 vtable을 통해 실행 중에 골라져요. 객체마다 8바이트와 간접 호출 비용이 들어요.<br><sub>Virtual functions are chosen at run time through the vtable that a hidden vptr in the object points to. | **템플릿**<br><sub>Templates</sub> | 템플릿은 타입을 매개변수로 받는 코드의 틀이에요. 쓰이는 타입마다 컴파일러가 별도 코드를 생성해서 실행 비용이 없어요.<br><sub>A template is a pattern for code that takes types as parameters. The compiler generates separate code for each type used, so there is no run-time cost.</sub> | 템플릿은 타입을 매개변수로 받아 여러 타입에 쓸 수 있는 코드의 틀이에요. template <typename T> T maxOf(T a, T b)는 그 자체로는 기계어가 되지 않고, 어떤 타입으로 쓰일 때까지 기다려요. maxOf(3, 7)을 부르면 컴파일러가 인자에서 T = int를 추론해 maxOf<int>를 만들고, maxOf(2.5, 1.0)을 부르면 maxOf<double>을 따로 만들어요. 이것을 인스턴스화라고 해요. 오브젝트 파일을 nm으로 보면 \_Z5maxOfIiET\_S0\_S0\_와 \_Z5maxOfIdET\_S0\_S0\_라는 두 함수가 실제로 들어 있어요. 각 버전은 그 타입에 맞게 따로 최적화되므로 손으로 쓴 함수와 성능이 같아요. 이것이 모든 타입을 Object로 다루고 실행 중에 캐스트하는 Java 제네릭(타입 소거)과의 큰 차이예요. Calling maxOf(3, 7) makes the compiler deduce T = int from the arguments and generate maxOf<int>, and calling maxOf(2.5, 1.0) generates a separate maxOf<double>. This is called instantiation. Looking at the object file with nm shows two real functions, \_Z5maxOfIiET\_S0\_S0\_ and \_Z5maxOfIdET\_S0\_S0\_. Each version is optimized separately for its type, so it runs as fast as a hand-written function. This is the big difference from Java generics, which treat every type as Object and cast at run time (type erasure). T is deduced from the arguments, and maxOf(3, 2.5) yields int from the first and double from the second, a conflict and a compile error, fixed by spelling out the type as maxOf<double>(3, 2.5). Instantiation requires the compiler to see the whole template definition, so templates are usually defined in header files. Since code is generated per type, using many types can bloat the executable (code bloat) and lengthen compile times. And because the requirements on T are not stated, passing an unsuitable type produces long error messages from deep inside the template. | **STL 알고리즘과 ranges**<br><sub>STL algorithms and ranges</sub> | STL 알고리즘은 반복자 범위 [begin, end) 위에서 동작해요. sort는 최악도 O(n log n)인 인트로소트이고, remove는 실제로 지우지 않아 erase가 필요해요.<br><sub>STL algorithms work over the iterator range [begin, end). sort is introsort, O(n log n) even in the worst case, and remove does not actually delete, so erase is needed.</sub> | <algorithm> 헤더의 STL 알고리즘은 컨테이너가 아니라 반복자 쌍을 받아요. 그래서 같은 std::find와 std::sort를 vector, 배열, deque 등 어디에나 쓸 수 있어요. 범위는 반열린 구간 [begin, end)로, begin은 첫 원소를, end는 마지막 원소의 다음 칸을 가리켜요. 그래서 빈 범위는 begin == end이고, 원소 수는 end - begin이며, find는 찾지 못하면 end를 돌려줘요. std::sort는 인트로소트(introsort)예요. 평균적으로 빠른 퀵 정렬로 시작하되, 재귀가 log n의 몇 배보다 깊어지면 힙 정렬로 바꿔 최악의 O(n²)을 피하고, 작은 구간은 삽입 정렬로 마무리해요. 그래서 최악의 경우에도 O(n log n)이 보장돼요. 같은 값의 원래 순서를 지켜야 하면 stable\_sort를 써요. 알고리즘은 반복자만 받기 때문에 컨테이너의 크기를 바꿀 수 없어요. 그래서 std::remove\_if는 남길 원소를 앞으로 당겨 놓고 새로운 끝을 돌려줄 뿐이고, 뒤쪽의 남은 원소를 실제로 지우려면 v.erase(new\_end, v.end())를 해야 해요. 이것이 erase-remove 관용구이고, C++20의 std::erase\_if(v, pred)가 이를 한 번에 처리해요. | **async와 future**<br><sub>async and futures</sub> | std::async는 일을 다른 스레드에서 시작하고 future를 돌려줘요. get()으로 결과를 기다리고, 작업에서 난 예외도 그대로 전달받아요.<br><sub>std::async starts work on another thread and returns a future. get() waits for the result and also delivers any exception the task threw.</sub> | 스레드를 직접 만들고 결과를 공유 변수로 주고받는 대신, std::async를 쓰면 "이 일을 해서 결과를 줘"라는 식으로 동시성을 표현할 수 있어요. std::async(std::launch::async, load)는 load를 새 스레드에서 실행하고, 그 결과를 담을 std::future<int>를 곧바로 돌려줘요. future는 아직 계산 중인, 나중에 올 결과를 가리키는 손잡이예요. async가 바로 돌아오므로 main 스레드는 그동안 work() 같은 다른 일을 할 수 있고, load와 work는 서로 다른 코어에서 동시에 진행돼요. 결과가 필요해지면 f.get()을 불러요. 결과가 아직 준비되지 않았으면 준비될 때까지 기다렸다가 값을 돌려줘요. load 안에서 예외가 던져졌다면 get()이 그 예외를 다시 던지므로, 다른 스레드에서 난 오류도 평소처럼 try와 catch로 처리할 수 있어요. get()은 결과를 꺼내 가므로 한 번만 부를 수 있고, 여러 곳에서 기다리려면 shared\_future를 써요. 더 낮은 수준에서는 std::promise와 std::future가 한 쌍의 통로가 돼요. 한 스레드가 promise.set\_value(42)로 값을 넣으면 짝인 future에서 get()으로 42를 꺼내요. 주의할 함정이 있어요. std::async가 돌려준 future는 소멸자에서 작업이 끝나기를 기다리기 때문에, std::async(...)의 반환값을 변수에 담지 않고 버리면 그 문장에서 바로 기다리게 되어 사실상 동기 호출이 돼요. 또 launch 정책을 생략하면 구현이 get() 때까지 실행을 미룰 수도 있어요. 작은 작업이 아주 많다면 작업마다 스레드를 만드는 대신 스레드 풀이나 병렬 알고리즘(std::execution::par)을 써요.<br><sub>Instead of creating threads by hand and passing results through shared variables, std::async expresses concurrency as do this work and give me the result. std::async(std::launch::async, load) runs load on a new thread and immediately returns a std::future<int> that will hold the result. A future is a handle to a result still being computed. Because async returns right away, the main thread can do other work such as work() in the meantime, with load and work progressing at the same time on different cores. When the result is needed, call f.get(). If the result is not ready yet, it waits until it is and then returns the value. At a lower level, std::promise and std::future form a paired channel: one thread puts a value in with promise.set\_value(42) and the paired future yields 42 through get(). There is a trap to watch for. | **거짓 공유**<br><sub>False sharing</sub> | 서로 다른 변수라도 같은 64바이트 캐시 줄에 있으면, 다른 코어가 쓸 때마다 줄이 오가며 느려져요. 이 환경에서 약 5배 차이가 났어요.<br><sub>Even different variables, if they share one 64-byte cache line, slow down as the line bounces whenever another core writes. C++17은 이 크기를 std::hardware\_destructive\_interference\_size로 제공하고, 이 환경에서는 64였어요. 다른 방법으로는 스레드마다 지역 변수에 세다가 마지막에 한 번만 공유 변수에 합치는 것이 있어요. 거짓 공유는 코드만 봐서는 드러나지 않으므로, 멀티스레드 코드가 코어를 늘려도 빨라지지 않으면 perf 같은 프로파일러로 캐시 미스와 줄 경합을 확인해 봐요.<br><sub>CPU caches fetch memory not byte by byte but in 64-byte cache lines. Several cores can each hold a copy of the same line in their caches, but the cache coherence protocol (MESI and the like) requires a core writing to a line to invalidate every other core’s copy, so the next time another core writes the line, it must fetch it again. The catch is that this happens per line, not per variable. In struct Counters { std::atomic<long> a, b; }, a and b total 16 bytes and fit in the same line. Thread T1 increments only a and T2 only b, so logically nothing is shared, yet because the two cores take turns writing the same line, the line bounces between them nonstop. This is false sharing. In this environment, with two threads each incrementing 50 million times, the same-line layout took 1634 ms while placing them on separate lines with alignas(64) took 300 ms, about a 5× difference. C++17 exposes this size as std::hardware\_destructive\_interference\_size, which was 64 here. Another approach is to count in a per-thread local variable and fold it into the shared one just once at the end. False sharing is invisible from the code alone, so when multithreaded code fails to speed up with more cores, check cache misses and line contention with a profiler such as perf.</sub> |

| **concepts**<br><sub>Concepts</sub> | concept은 템플릿 인자가 만족해야 할 조건에 이름을 붙여요. 조건이 시그니처에 드러나고, 오류가 템플릿 속이 아니라 호출한 곳에서 짧게 나요.<br><sub>A concept gives a name to the conditions a template argument must meet. The conditions show in the signature, and errors appear briefly at the call site instead of deep inside the template.</sub> | 템플릿은 원래 어떤 타입이든 받아들여요. template <typename T> T twice(T x)에 twice("hi")를 넘기면, 컴파일러는 T = const char\*로 몸체를 인스턴스화하다가 x \* 2에서야 실패해요. 오류가 템플릿 몸체 깊은 곳에서 나기 때문에, 표준 라이브러리 템플릿을 잘못 쓰면 수십 줄의 인스턴스화 경로를 거슬러 올라가며 원인을 찾아야 했어요. 또 T에 무엇이 필요한지는 문서나 코드를 읽어야만 알 수 있었어요. C++20 ranges 알고리즘은 모두 concept으로 제약되어 있어요.<br><sub>Templates originally accept any type at all. Pass twice("hi") to template <typename T> T twice(T x), and the compiler instantiates the body with T = const char\* and fails only at x \* 2. Because the error comes from deep inside the template body, misusing a standard library template meant tracing back through dozens of lines of instantiation history to find the cause. And what T needed could be learned only by reading documentation or code. A C++20 concept is a compile-time predicate that names a condition on types. concept Number = std::integral<T> \|\| std::floating\_point<T> holds when T is an integral or floating-point type, so Number<int> and Number<double> are true and Number<const char\*> is false. Constraining a template parameter, as in template <Number T>, makes the compiler check the condition first, at the call. If it is not met, the body is never instantiated, and the error appears right at the calling line, saying constraints not satisfied and which condition failed. The requirement in the signature doubles as documentation. A requires clause can test on the spot whether particular expressions compile, as in requires (T a) { a + a; }, and the short form void f(std::integral auto x) is also available. The <concepts> header provides standard concepts such as integral, copyable, invocable and totally\_ordered, and when several overloads match, the more specifically constrained one is chosen, replacing old techniques such as SFINAE and enable\_if. Every C++20 ranges algorithm is constrained with concepts.</sub> |
| **모듈**<br><sub>Modules</sub> | 모듈은 한 번 컴파일해 바이너리 인터페이스로 저장하고 import로 가져와요. 헤더를 매번 다시 파싱하지 않고, 매크로가 새어 나가지 않아요.<br><sub>A module is compiled once into a binary interface and brought in with import. Headers are no longer reparsed every time, and macros do not leak.</sub> | #include는 헤더 파일의 텍스트를 그 자리에 그대로 붙여 넣는 전처리기 명령이에요. 이 환경의 GCC에서 #include <iostream> 한 줄은 전처리 후 43,165줄, <vector>는 26,258줄이 돼요. 각 .cpp 파일은 따로 컴파일되므로, 같은 헤더를 쓰는 파일이 100개면 그 수만 줄을 100번 파싱해요. 대형 프로젝트의 빌드 시간 대부분이 여기서 나와요. 게다가 헤더 안의 매크로가 그것을 포함한 코드로 새어 나오고, 포함 순서에 따라 결과가 달라지기도 하며, 두 번 포함을 막는 헤더 가드도 필요해요. C++20 모듈은 이 모델을 바꿔요. export module math;로 모듈을 선언하고 바깥에 보일 것에 export를 붙이면, 컴파일러는 모듈을 한 번 컴파일해 BMI(Binary Module Interface)라는 파일로 저장해요. import math;는 텍스트를 다시 파싱하지 않고 이 미리 처리된 인터페이스를 읽기만 하므로 빌드가 빨라져요. 모듈에서는 export한 이름만 보이고 내부 구현은 숨겨져요. 매크로는 모듈 밖으로 새어 나가지 않고, 가져오는 쪽의 매크로가 모듈에 영향을 주지도 않아서 import 순서가 결과를 바꾸지 않아요. 헤더 가드나 #pragma once도 필요 없어요. C++23의 import std;는 표준 라이브러리 전체를 모듈 하나로 가져와요. 다만 모듈은 빌드 도구가 파일 사이의 의존 순서를 미리 알아야 해서, 컴파일러와 CMake(3.28 이상, Ninja 생성기) 같은 빌드 시스템의 지원이 아직 무르익는 중이에요. 그래서 실무에서는 기존 헤더와 함께 쓰면서 점진적으로 도입해요.<br><sub>#include is a preprocessor command that pastes a header file’s text right where it appears. On top of that, macros inside headers leak into the code including them, results can depend on inclusion order, and include guards are needed to prevent double inclusion. In a module only exported names are visible, and internal details are hidden. Macros do not leak out of a module, and the importer’s macros do not affect it either, so import order never changes the result. No include guards or #pragma once are needed. C++23’s import std; brings in the entire standard library as one module. However, modules require the build tool to know the dependency order between files in advance, so support in compilers and build systems such as CMake (3.28 or later with the Ninja generator) is still maturing. In practice, then, modules are adopted gradually alongside existing headers.</sub> |
| **코루틴**<br><sub>Coroutines</sub> | 코루틴은 중간에 멈췄다가 이어서 실행할 수 있는 함수예요. co\_yield로 생성기를, co\_await로 스레드를 막지 않는 비동기 코드를 만들어요.<br><sub>A coroutine is a function that can pause midway and resume later. co\_yield makes generators, and co\_await makes async code that does not block threads.</sub> | C++20 코루틴은 실행 도중 멈췄다가(suspend) 나중에 멈춘 지점부터 이어서(resume) 실행할 수 있는 함수예요. 몸체에 co\_yield, co\_await, co\_return 중 하나라도 있으면 코루틴이 돼요. counter()를 부르면 몸체는 실행되지 않고, 지역 변수와 멈춘 위치를 담을 코루틴 프레임만 힙에 만들어 그 핸들을 감싼 Generator 객체를 돌려줘요. g.next()가 코루틴을 재개하면 몸체가 co\_yield i까지 실행되어 i를 내보내고 다시 멈춰요. 이때 i와 멈춘 위치는 프레임에 그대로 남아 있어서, 다음 next()는 그 자리에서 이어져 0, 1, 2…를 차례로 만들어요. 무한 수열이나 큰 파일의 줄처럼 필요할 때마다 하나씩 만드는 게으른 생성기를 자연스럽게 쓸 수 있어요. co\_await는 비동기에서 빛나요. auto d = co\_await fetch();는 결과가 준비될 때까지 코루틴을 멈추고 스레드를 돌려줘서, 그 스레드가 다른 요청을 처리할 수 있게 해요. 결과가 도착하면 이벤트 루프가 코루틴을 재개해요. 콜백을 겹겹이 중첩하지 않고 위에서 아래로 읽히는 순서대로 비동기 코드를 쓸 수 있는 거예요. C++ 코루틴은 자기만의 스택을 갖지 않는 스택 없는(stackless) 방식이라 상태가 작은 힙 프레임뿐이고, 그래서 아주 많이 만들어도 가벼워요. 대신 C++20은 promise\_type 같은 언어 장치만 제공하고, Generator나 Task 같은 실제 타입은 라이브러리가 만들어야 해요. C++23에 std::generator가 들어왔고, 비동기에는 Asio나 cppcoro 같은 라이브러리를 써요. 프레임이 멈춘 동안 참조로 받은 인자가 먼저 사라지면 댕글링이 되니 주의해야 해요.<br><sub>A C++20 coroutine is a function that can suspend partway through and later resume from where it stopped. Any body containing co\_yield, co\_await or co\_return makes a coroutine. Calling counter() runs none of the body; it only allocates a coroutine frame on the heap to hold the locals and the suspension point, and returns a Generator object wrapping its handle. When g.next() resumes the coroutine, the body runs up to co\_yield i, hands out i and suspends again. Since i and the suspension point stay in the frame, the next next() continues right there, producing 0, 1, 2 and so on. This makes lazy generators natural, producing one item at a time on demand, such as infinite sequences or the lines of a large file. co\_await shines in async code. auto d = co\_await fetch(); suspends the coroutine until the result is ready and gives the thread back so it can serve other requests, and when the result arrives an event loop resumes the coroutine. Async code can thus be written in order, reading top to bottom, without nesting callbacks. C++ coroutines are stackless, with no stack of their own, so their state is just a small heap frame, which keeps even very many of them light. On the other hand, C++20 supplies only language machinery such as promise\_type, and actual types such as Generator or Task must be built by libraries. C++23 added std::generator, and async work uses libraries such as Asio or cppcoro. Beware that if an argument taken by reference disappears while the frame is suspended, it dangles.</sub> |
| **새니타이저**<br><sub>Sanitizers</sub> | 새니타이저는 컴파일러가 검사 코드를 넣어 메모리 오류, 정의되지 않은 동작, 데이터 경쟁을 실행 중에 정확한 줄과 함께 잡아 줘요.<br><sub>Sanitizers have the compiler insert checks that catch memory errors, undefined behavior and data races at run time, pointing to the exact line.</sub> | C와 C++의 메모리 버그와 정의되지 않은 동작은 바로 터지지 않고 엉뚱한 곳에서 나중에 드러나서 찾기 어려워요. 새니타이저는 컴파일러가 프로그램에 검사 코드를 심어 이런 버그를 일어나는 순간에 잡아 주는 도구예요. -fsanitize=address로 켜는 AddressSanitizer(ASan)는 모든 메모리 읽기와 쓰기 앞에 검사를 넣고, 할당한 블록 주변에 접근하면 안 되는 레드존을 두며, 섀도 메모리에 각 바이트가 접근 가능한지를 기록해요. 4칸짜리 배열의 a[4]에 쓰면 레드존에 닿는 순간 heap-buffer-overflow, WRITE of size 4와 함께 정확한 파일과 줄, 호출 스택을 보고하고 멈춰요. 해제 후 사용(use-after-free), 이중 해제, 메모리 누수도 잡아요. -fsanitize=undefined로 켜는 UBSan은 부호 있는 정수 넘침, 널 포인터 역참조, 범위를 넘는 시프트, 잘못된 정렬 같은 정의되지 않은 동작을 잡아서, INT\_MAX에 1을 더하면 2147483647 + 1을 int로 나타낼 수 없다고 알려 줘요. -fsanitize=thread로 켜는 ThreadSanitizer(TSan)는 메모리 접근과 락, atomic 같은 동기화의 순서를 추적해서, 동기화 없이 같은 메모리를 건드리는 스레드들을 데이터 경쟁으로 보고해요. Sanitizers are tools in which the compiler plants checking code in the program to catch such bugs the moment they happen. AddressSanitizer (ASan), enabled with -fsanitize=address, inserts a check before every memory read and write, surrounds each allocation with redzones that must not be touched, and records in shadow memory whether each byte is accessible. Writing a[4] in a four-element array hits a redzone and immediately reports heap-buffer-overflow, WRITE of size 4, with the exact file, line and call stack, then stops. It also catches use-after-free, double free and memory leaks. UBSan, enabled with -fsanitize=undefined, catches undefined behavior such as signed integer overflow, null pointer dereference, out-of-range shifts and misalignment, reporting for INT\_MAX plus 1 that 2147483647 + 1 cannot be represented in an int. ThreadSanitizer (TSan), enabled with -fsanitize=thread, tracks the order of memory accesses and synchronization such as locks and atomics, and reports threads that touch the same memory without synchronization as data races. TSan cannot be enabled together with ASan, so it gets its own build. That is far lighter than Valgrind, which can be tens of times slower, so keep sanitizers on in tests and CI and turn them off only for release builds. Adding -g puts line numbers in the reports. They are especially powerful combined with fuzzing.</sub> |
| **CMake와 빌드**<br><sub>CMake and builds</sub> | CMake는 직접 컴파일하지 않고 Ninja나 Make용 빌드 파일을 만드는 생성기예요. 설정을 타깃에 붙이고 PUBLIC과 PRIVATE로 전파해요.<br><sub>CMake does not compile anything itself; it generates build files for Ninja or Make. CMakeLists.txt를 읽어 Ninja, Make, Visual Studio 같은 도구용 빌드 파일을 만들고, 실제 컴파일은 그 도구가 g++, clang++, MSVC를 불러서 해요. 그래서 같은 CMakeLists.txt로 리눅스, macOS, 윈도우에서 빌드할 수 있어요. add\_library(geo ...)와 add\_executable(app ...)은 타깃을 만들고, target\_link\_libraries(app PRIVATE geo)는 app이 core에 의존한다는 관계를 정해요. 빌드 도구는 이 의존 그래프를 보고 바뀐 파일과 그에 의존하는 것만 다시 빌드하고, 서로 독립적인 파일은 여러 코어로 병렬 컴파일해요. 모던 CMake의 핵심은 설정을 전역 변수가 아니라 타깃에 붙이는 것이에요. target\_compile\_features(geo PUBLIC cxx\_std\_20)처럼 PUBLIC으로 지정한 설정은 geo 자신과 core를 링크하는 쪽 모두에 적용되어 app도 C++20으로 컴파일돼요. PRIVATE은 그 타깃에만, INTERFACE는 쓰는 쪽에만 적용돼요. 포함 경로와 전처리기 정의도 같은 방식으로 의존 관계를 따라 흘러요. 빌드는 cmake -B build -G Ninja처럼 소스 밖의 build 디렉터리에서 해서 소스 트리를 깨끗하게 유지하고, Debug와 Release를 다른 디렉터리에 둘 수 있어요. CMAKE\_EXPORT\_COMPILE\_COMMANDS를 켜면 compile\_commands.json이 생겨서 clangd나 clang-tidy 같은 도구가 파일마다 정확한 컴파일 옵션을 알 수 있어요. 외부 라이브러리는 find\_package로 찾거나 vcpkg, Conan 같은 패키지 관리자로 가져와요.<br><sub>C and C++ have no build tool built into the language, so once there are many files, a tool is needed to describe what to compile, in what order and with which flags. CMake, the de facto standard, is a build-system generator that does not compile anything itself. It reads CMakeLists.txt and writes build files for tools such as Ninja, Make or Visual Studio, which then call g++, clang++ or MSVC to do the actual compiling, so the same CMakeLists.txt builds on Linux, macOS and Windows. add\_library(geo ...) and add\_executable(app ...) create targets, and target\_link\_libraries(app PRIVATE geo) records that app depends on geo. The build tool uses this dependency graph to rebuild only changed files and what depends on them, compiling independent files in parallel across cores. The heart of modern CMake is attaching settings to targets rather than global variables. A setting given as PUBLIC, as in target\_compile\_features(geo PUBLIC cxx\_std\_20), applies to geo itself and to anything linking geo, so app also compiles as C++20. PRIVATE applies only to that target, and INTERFACE only to its consumers. Include paths and preprocessor definitions flow along the dependencies in the same way. Builds happen in a build directory outside the sources, as in cmake -B build -G Ninja, keeping the source tree clean and allowing Debug and Release in separate directories. Turning on CMAKE\_EXPORT\_COMPILE\_COMMANDS produces compile\_commands.json, so that tools such as clangd and clang-tidy know the exact compile flags for each file.
