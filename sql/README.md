## 원하는 결과를 정확하게 · Exactly the result you want

| **CASE와 FILTER**<br><sub>CASE and FILTER</sub> | 집계 함수에 FILTER를 붙이면 한 번 훑으면서 조건별로 따로 셀 수 있어요. CASE는 같은 일을 이식성 있게 하고, 맞는 가지만 계산해 오류도 막아요.<br><sub>Attaching FILTER to an aggregate lets a single scan count separately per condition. CASE does the same portably, and because it evaluates only the matching branch, it also prevents errors.</sub> | 이 페이지의 예제는 PostgreSQL 16에서 고객 10만 명과 주문 100만 건으로 만든 데이터로 실행했어요. 주문의 상태별 개수와 결제 금액 합계를 함께 구하고 싶을 때, 상태마다 쿼리를 따로 돌리면 큰 테이블을 여러 번 읽어야 해요. 집계 함수 뒤에 FILTER (WHERE 조건)을 붙이면 집계마다 다른 조건을 걸 수 있어서, 테이블을 한 번 훑으면서 count(\*) FILTER (WHERE status = 'paid')로 599,676건, refunded 조건으로 200,091건을 함께 셌어요. FILTER는 조건에 맞는 행만 그 집계에 넣으므로 sum(amount) FILTER (WHERE status = 'paid')는 paid 행의 금액만 더해 150,086,812.94를 냈어요. FILTER는 SQL:2003 표준이고 PostgreSQL과 SQLite가 지원하지만 MySQL에는 없어요. 그래서 여러 DB에서 같은 쿼리를 써야 할 때는 CASE를 써요. CASE WHEN status = 'paid' THEN 1 END는 조건에 맞지 않는 행에서 ELSE가 없으므로 NULL이 되고, count는 NULL을 세지 않으므로 똑같이 599,676이 나왔어요. sum(CASE WHEN … THEN 1 ELSE 0 END) 형태도 흔해요. CASE는 위에서부터 조건을 확인해 처음 맞는 가지의 값만 계산한다는 성질도 있어요. 10 / x는 x가 0인 행 하나 때문에 division by zero 오류로 쿼리 전체가 실패했지만, CASE WHEN x = 0 THEN NULL ELSE 10 / x END는 그 행을 NULL로 넘기고 나머지를 계산했어요. 같은 목적이라면 NULLIF(x, 0)으로 0을 NULL로 바꿔 10 / NULLIF(x, 0)처럼 쓸 수도 있어요. 다만 상수끼리의 식은 계획 단계에서 미리 계산될 수 있어서, CASE 안에 넣은 상수 식도 오류를 낼 수 있다는 예외가 문서에 적혀 있어요.<br><sub>The examples on this page were run on PostgreSQL 16 against data built from 100,000 customers and 1 million orders. To get counts per order status alongside the sum of payments, running a separate query per status would read a big table several times. Attaching FILTER (WHERE condition) after an aggregate gives each aggregate its own condition, so one scan of the table counted 599,676 rows with count(\*) FILTER (WHERE status = 'paid') and 200,091 with the refunded condition at the same time. FILTER feeds only the matching rows into that aggregate, so sum(amount) FILTER (WHERE status = 'paid') added only the paid amounts, giving 150,086,812.94. FILTER is in the SQL:2003 standard and supported by PostgreSQL and SQLite, but MySQL lacks it, so CASE is used when the same query must run on several databases. CASE WHEN status = 'paid' THEN 1 END has no ELSE, so it becomes NULL for non-matching rows, and since count skips NULLs it also returned 599,676. The form sum(CASE WHEN … THEN 1 ELSE 0 END) is common too. CASE also checks conditions from the top and evaluates only the value of the first matching branch. 10 / x failed the whole query with division by zero because of a single row where x was 0, while CASE WHEN x = 0 THEN NULL ELSE 10 / x END passed that row as NULL and computed the rest. For the same purpose, NULLIF(x, 0) turns 0 into NULL, as in 10 / NULLIF(x, 0). The documentation does note one exception: expressions made only of constants may be computed in advance during planning, so a constant expression inside a CASE can still raise an error.</sub> |
| **UNION과 집합 연산**<br><sub>UNION and set operations</sub> | UNION ALL은 결과를 이어 붙이기만 하고, UNION은 중복을 없애려고 정렬까지 해요. 같은 데이터에서 UNION이 약 2배 느렸고 정렬이 디스크로 넘쳤어요.<br><sub>UNION ALL simply appends results, while UNION also sorts to remove duplicates. On the same data, UNION was about twice as slow and its sort spilled to disk.</sub> | 집합 연산은 같은 모양의 두 결과를 하나로 합쳐요. 예제의 paid와 refunded는 주문 100만 건 중 상태가 각각 paid, refunded인 주문의 고객 ID 목록이에요. UNION ALL은 두 결과를 그대로 이어 붙이기만 해서 실행 계획에도 Append만 나타나고, 결과는 599,676 + 200,091 = 799,767행이었어요. UNION은 결과에서 중복을 없애야 하므로, 이어 붙인 799,767행을 고객 ID로 정렬한 뒤 같은 값을 하나로 합치는 Unique 단계를 거쳐요. 정렬할 데이터가 정렬과 해시에 쓰는 메모리 한도인 work\_mem의 기본값 4MB를 넘자, EXPLAIN ANALYZE에 Sort Method: external merge Disk: 9408kB가 찍히며 디스크에 임시 파일을 썼어요. 결과는 고객 99,966명으로 줄었지만 시간은 UNION ALL이 약 120ms, UNION이 약 250ms로 2배쯤 걸렸어요. 세션에서 work\_mem을 64MB로 늘리자 계획이 정렬 대신 HashAggregate로 바뀌어 디스크를 쓰지 않았어요. 실무의 결론은 단순해요. 두 결과가 겹치지 않는다는 것을 알거나, 중복이 있어도 괜찮다면 UNION ALL을 써요. 습관적으로 UNION을 쓰면 필요 없는 정렬 비용을 내요. INTERSECT는 양쪽 결과에 모두 있는 값을, EXCEPT는 왼쪽에는 있고 오른쪽에는 없는 값을 돌려줘요. 결제와 환불이 모두 있는 고객은 86,285명, 결제만 있고 환불은 없는 고객은 13,464명이었어요. 두 연산도 ALL을 붙이지 않으면 중복을 없애요. 같은 결과는 EXISTS나 NOT EXISTS 서브쿼리로도 쓸 수 있는데, NOT IN은 오른쪽에 NULL이 하나라도 있으면 결과가 비어 버리는 함정이 있어서 EXCEPT나 NOT EXISTS가 더 안전해요. 연산 순서는 INTERSECT가 UNION과 EXCEPT보다 먼저예요.<br><sub>Set operations combine two results of the same shape into one. In the example, paid and refunded are the customer IDs of the orders, out of 1 million, whose status is paid or refunded respectively. UNION ALL merely appends the two results, so only an Append appears in the plan, and the result had 599,676 + 200,091 = 799,767 rows. UNION must remove duplicates from the result, so it sorts the appended 799,767 rows by customer ID and then goes through a Unique step that merges equal values. When the data to sort exceeded the default 4 MB of work\_mem, the memory limit for sorts and hashes, EXPLAIN ANALYZE showed Sort Method: external merge Disk: 9408kB as temporary files were written to disk. The result shrank to 99,966 customers, but the time roughly doubled, about 120 ms for UNION ALL versus about 250 ms for UNION. Raising work\_mem to 64 MB for the session switched the plan from a sort to a HashAggregate that used no disk. The practical conclusion is simple. When the two results are known not to overlap, or duplicates are acceptable, use UNION ALL; reaching for UNION out of habit pays for a sort that is not needed. INTERSECT returns values present in both results, and EXCEPT returns values on the left that are absent on the right. 86,285 customers had both a payment and a refund, and 13,464 had payments but no refunds. Without ALL, these two also remove duplicates. The same results can be written with EXISTS or NOT EXISTS subqueries, but NOT IN has a trap: a single NULL on the right side makes the result empty, so EXCEPT or NOT EXISTS is safer. In precedence, INTERSECT binds before UNION and EXCEPT.</sub> |
| **DISTINCT ON**<br><sub>DISTINCT ON</sub> | DISTINCT ON은 괄호 안 값마다 첫 행 하나만 남기고, 어느 행이 첫 행인지는 ORDER BY가 정해요. 고객별 최신 주문을 윈도 함수보다 짧고 조금 빠르게 구했어요.<br><sub>DISTINCT ON keeps only the first row for each value in parentheses, and ORDER BY decides which row is first. It found each customer’s latest order more briefly, and a little faster, than a window function.</sub> | 고객마다 가장 최근 주문 하나, 센서마다 마지막 측정값 하나처럼 그룹마다 한 행을 고르는 일은 아주 흔해요. 일반 DISTINCT는 선택한 모든 열이 같은 행만 합칠 수 있어서 이 일을 못 해요. PostgreSQL의 확장 문법인 DISTINCT ON (customer\_id)는 괄호 안 값이 같은 행들 중 첫 행 하나만 남기고, 나머지 열은 그 첫 행의 값을 그대로 가져와요. 예제는 고객 99,997명마다 한 행씩, 모두 99,997행을 돌려줬어요. 핵심은 어느 행이 첫 행인지를 ORDER BY가 정한다는 거예요. ORDER BY customer\_id, created\_at DESC로 정렬했기 때문에 각 고객의 가장 최근 주문이 남아요. 고객 1은 10월 27일, 10월 25일, 9월 22일, 8월 13일의 주문 4건이 있었고, 결과에는 10월 27일 주문 413070만 남았어요. 정렬 키가 같은 행이 여럿이면 그중 어느 것이 남을지는 정해지지 않으므로, 결과를 고정하려면 id 같은 유일한 열까지 정렬 키에 넣어요. ORDER BY에는 규칙도 있어요. 반드시 DISTINCT ON의 열로 시작해야 해서, created\_at DESC로만 정렬하자 SELECT DISTINCT ON expressions must match initial ORDER BY expressions 오류가 났어요. 같은 그룹의 행이 붙어 있어야 첫 행을 고를 수 있기 때문이에요. 같은 결과는 다른 DB에서도 통하는 표준 방식으로 만들 수 있어요. row\_number() OVER (PARTITION BY customer\_id ORDER BY created\_at DESC)로 고객마다 번호를 매긴 뒤 번호가 1인 행만 고르면 돼요. 이 데이터에서는 DISTINCT ON이 약 77ms, 윈도 함수 방식이 약 103ms였어요. 그룹 수가 적고 그룹마다 행이 아주 많다면, 다음 항목의 LATERAL 조인으로 인덱스에서 그룹마다 한 행씩만 읽는 편이 더 빠를 수 있어요.<br><sub>Picking one row per group, such as each customer’s most recent order or each sensor’s last reading, is very common. Plain DISTINCT can merge only rows whose selected columns are all equal, so it cannot do this. PostgreSQL’s extension DISTINCT ON (customer\_id) keeps only the first of the rows sharing the value in parentheses, and the other columns take their values from that first row. The example returned one row for each of 99,997 customers, 99,997 rows in all. The key point is that ORDER BY decides which row is first. Because the rows were sorted by customer\_id, created\_at DESC, each customer’s most recent order remains. Customer 1 had 4 orders, from October 27, October 25, September 22 and August 13, and only order 413070 from October 27 remained in the result. When several rows share the same sort keys, which one survives is undefined, so a unique column such as id is added to the sort keys to make the result fixed. ORDER BY also has a rule: it must begin with the DISTINCT ON columns, so sorting only by created\_at DESC produced the error SELECT DISTINCT ON expressions must match initial ORDER BY expressions. The rows of a group have to sit together for the first one to be picked. The same result can be produced in a standard way that works on other databases too: number each customer’s rows with row\_number() OVER (PARTITION BY customer\_id ORDER BY created\_at DESC) and keep the rows numbered 1. On this data DISTINCT ON took about 77 ms and the window approach about 103 ms. When there are few groups with very many rows each, reading just one row per group from an index with the LATERAL join in the next item can be faster.</sub> |
| **LATERAL 조인**<br><sub>LATERAL joins</sub> | LATERAL 서브쿼리는 바깥 행의 값을 참조할 수 있어서, 고객마다 최근 주문 3건 같은 그룹별 상위 N개를 인덱스로 빠르게 구해요.<br><sub>A LATERAL subquery can refer to values from the outer row, so per-group top-N queries such as each customer’s 3 latest orders run quickly through an index.</sub> | FROM 절에 쓴 서브쿼리는 보통 옆에 나열된 다른 테이블의 열을 참조할 수 없어요. 서브쿼리 앞에 LATERAL을 붙이면, 서브쿼리가 앞에 나온 customers의 현재 행 c.id를 볼 수 있게 돼요. 그러면 서브쿼리는 고객 한 명마다 한 번씩 실행되는 함수처럼 동작하고, 고객마다 가장 최근 주문 3건 같은 그룹별 상위 N개 쿼리를 그대로 쓸 수 있어요. 예제에서 고객 1의 최근 주문 3건은 금액 442.12, 416.50, 282.12였어요. 실행 계획은 Nested Loop예요. customers의 각 행마다 안쪽 서브쿼리를 실행하는데, orders에 (customer\_id, created\_at DESC) 인덱스가 있으므로 그 고객의 가장 최근 항목부터 인덱스를 읽다가 3개를 얻으면 Limit에서 바로 멈춰요. 그래서 고객 한 명이 주문을 몇 건 가졌든 고객당 작업량이 거의 일정해요. 같은 일을 row\_number() 윈도 함수로 하면, 해당 고객들의 주문을 모두 읽고 정렬해 번호를 매긴 뒤에야 3번까지 걸러낼 수 있어요. 고객 1,000명에 대해 LATERAL은 1.2ms, 윈도 함수 방식은 3.2ms였고, 고객 10만 명 전체로는 120ms 대 140ms였어요. 그룹당 행이 많을수록 차이는 더 커져요. 주의할 점은 조인 종류예요. CROSS JOIN LATERAL은 서브쿼리가 아무 행도 돌려주지 않으면 그 바깥 행도 결과에서 빼서, 주문이 한 건도 없는 고객 3명이 빠진 99,997행이 나왔어요. 그 고객들도 남기려면 LEFT JOIN LATERAL (…) o ON true를 써요. 그러면 100,000행이 나오고 주문 열은 NULL이 돼요. LATERAL은 jsonb\_array\_elements나 unnest처럼 행마다 여러 행을 펼치는 함수와도 자주 함께 쓰여요. FROM 절의 함수 호출은 LATERAL을 쓰지 않아도 앞 테이블을 참조할 수 있어요.<br><sub>A subquery written in the FROM clause normally cannot refer to columns of the other tables listed beside it. Putting LATERAL before the subquery lets it see c.id from the current row of the customers listed earlier. The subquery then behaves like a function run once per customer, so per-group top-N queries, such as the 3 most recent orders for each customer, can be written directly. In the example, customer 1’s 3 most recent orders had amounts of 442.12, 416.50 and 282.12. The plan is a Nested Loop. It runs the inner subquery for each row of customers, and since orders has an index on (customer\_id, created\_at DESC), it reads that customer’s entries from the most recent one and stops at the Limit as soon as it has 3. So the work per customer is nearly constant no matter how many orders a customer has. Doing the same with the row\_number() window function means reading, sorting and numbering all of those customers’ orders before up to 3 can be filtered out. For 1,000 customers, LATERAL took 1.2 ms and the window approach 3.2 ms, and across all 100,000 customers it was 120 ms versus 140 ms. The more rows per group, the larger the gap. One thing to watch is the join type. CROSS JOIN LATERAL also drops the outer row when the subquery returns nothing, so the result had 99,997 rows, missing the 3 customers with no orders at all. To keep those customers, use LEFT JOIN LATERAL (…) o ON true, which returned 100,000 rows with NULL in the order columns. LATERAL is also often used with functions that expand each row into several, such as jsonb\_array\_elements or unnest. A function call in the FROM clause can refer to earlier tables even without LATERAL.</sub> |
| **ROLLUP과 GROUPING SETS**<br><sub>ROLLUP and GROUPING SETS</sub> | ROLLUP은 세부 행과 함께 소계와 전체 합계를 한 번에 만들어요. 원래 NULL인 값과 소계의 빈칸은 grouping() 함수로 구별해요.<br><sub>ROLLUP produces subtotals and a grand total alongside the detail rows in one go. The grouping() function tells genuinely NULL values apart from the blanks of subtotals.</sub> | 보고서는 세부 행과 함께 소계와 합계를 요구하는 경우가 많아요. 예전에는 (국가, 상태)별 집계, 국가별 집계, 전체 집계의 세 쿼리를 UNION ALL로 이어 붙였어요. GROUP BY ROLLUP (country, status)는 이것을 한 번에 해요. ROLLUP은 그룹 기준을 오른쪽부터 하나씩 빼서 (country, status), (country), () 세 단계로 집계하고, 소계 행에서는 빠진 열을 NULL로 채워요. 예제에서 독일은 paid 120,277건, refunded 40,270건, 그리고 상태 열이 빈칸인 소계 행 160,547건이었어요. 마지막에는 국가와 상태가 모두 빈칸인 전체 합계 799,767건이 붙었어요. 문제는 원래부터 NULL인 값이에요. 국가 정보가 없는 고객이 2만 명 있어서, 국가가 NULL인 고객의 상태별 행과 그 소계 159,995건도 국가가 빈칸으로 나왔어요. 소계 159,995와 전체 합계 799,767이 모두 국가와 상태가 빈칸이라 겉보기로는 구별할 수 없어요. grouping(country, status) 함수는 각 열이 소계 때문에 빠졌는지를 비트로 알려 줘요. 세부 행은 0, 상태가 빠진 국가별 소계는 1, 둘 다 빠진 전체 합계는 3이라서, 이 값을 보고 빈칸이 진짜 NULL인지 소계인지를 정확히 가를 수 있어요. 화면에 보여 줄 때는 CASE WHEN grouping(country) = 1 THEN '합계' END처럼 이름을 붙여요. CUBE는 열의 모든 조합을 만들어요. 상태 3가지와 월 12개로 CUBE를 하자 (3 + 1) × (12 + 1) = 52개 그룹이 나왔어요. GROUPING SETS ((country), (status), ())처럼 원하는 조합만 직접 나열할 수도 있고, ROLLUP과 CUBE는 이 GROUPING SETS의 줄임말이에요. 세 문법 모두 데이터를 여러 번 읽지 않고, 정렬이나 해시를 단계별로 나눠 써서 한 번의 실행으로 처리해요.<br><sub>Reports often ask for subtotals and totals alongside the detail rows. This used to mean three queries, per (country, status), per country and overall, joined with UNION ALL. GROUP BY ROLLUP (country, status) does it in one go. ROLLUP removes grouping columns from the right one at a time, aggregating at three levels, (country, status), (country) and (), and fills the dropped columns with NULL in subtotal rows. In the example, Germany had 120,277 paid and 40,270 refunded, plus a subtotal row of 160,547 with a blank status column. At the end came the grand total of 799,767, with both country and status blank. The trouble is values that are NULL to begin with. 20,000 customers have no country, so the per-status rows for NULL-country customers and their subtotal of 159,995 also came out with a blank country. The subtotal of 159,995 and the grand total of 799,767 both have blank country and status, so they cannot be told apart by looking. The function grouping(country, status) reports as bits whether each column was dropped for a subtotal. Detail rows give 0, per-country subtotals with status dropped give 1, and the grand total with both dropped gives 3, so this value tells exactly whether a blank is a real NULL or a subtotal. For display, label them with something like CASE WHEN grouping(country) = 1 THEN 'Total' END. CUBE builds every combination of the columns. A CUBE over 3 statuses and 12 months gave (3 + 1) × (12 + 1) = 52 groups. GROUPING SETS ((country), (status), ()) lists exactly the combinations wanted, and ROLLUP and CUBE are shorthands for GROUPING SETS. All three read the data only once, handling everything in one execution by splitting sorts or hashes across the levels.</sub> |
| **ORDER BY와 LIMIT**<br><sub>ORDER BY and LIMIT</sub> | NULL의 정렬 위치는 DB마다 다르고, 동점인 행의 순서는 보장되지 않아요. 같은 LIMIT 쿼리가 실행 계획에 따라 다른 행을 돌려줬어요.<br><sub>Where NULLs sort differs between databases, and the order of tied rows is not guaranteed. The same LIMIT query returned different rows depending on the plan.</sub> | 정렬은 단순해 보이지만 두 가지 함정이 있어요. 첫째는 NULL의 위치예요. SQL 표준은 NULL을 어디에 둘지 정하지 않아서 DB마다 달라요. PostgreSQL은 NULL을 어떤 값보다 큰 값처럼 다뤄서 오름차순이면 마지막에, 내림차순이면 처음에 둬요. 국가가 없는 고객 2만 명도 ORDER BY country에서는 맨 뒤에, ORDER BY country DESC에서는 맨 앞에 나왔어요. MySQL과 SQL Server는 반대로 NULL을 가장 작은 값처럼 다뤄요. NULLS FIRST나 NULLS LAST를 명시하면 어느 DB에서나 같은 결과를 얻어요. 인덱스도 이 순서를 따르므로, 자주 쓰는 정렬이 NULLS FIRST라면 인덱스도 같은 방향으로 만들어야 정렬 단계를 생략할 수 있어요. 둘째는 동점이에요. SQL은 정렬 키가 같은 행끼리의 순서를 보장하지 않아요. 금액이 정확히 500.00인 주문이 8건이었는데, ORDER BY amount DESC LIMIT 3은 직렬 계획에서 845303, 40441, 874320을, 병렬 계획에서 501454, 40441, 586912를 돌려줬어요. 쿼리는 그대로인데 실행 계획만 바뀌어도 결과가 달라진 거예요. 데이터가 바뀌거나 통계가 갱신되어 계획이 바뀌면 운영 중에도 이런 일이 생겨요. 해결책은 id처럼 유일한 열을 마지막 정렬 키로 덧붙이는 거예요. ORDER BY amount DESC, id는 어떤 계획에서도 40441, 501454, 586912를 돌려줬어요. 특히 페이지 단위로 나눠 보여 줄 때 이걸 빼먹으면, 같은 행이 두 페이지에 나오거나 어떤 행은 어느 페이지에도 나오지 않아요. 동점을 모두 보여 주고 싶다면 FETCH FIRST 3 ROWS WITH TIES를 써요. 3번째 행과 정렬 키가 같은 행을 모두 함께 돌려줘서, 500.00인 8건이 모두 나왔어요. PostgreSQL 13부터 지원해요.<br><sub>Sorting looks simple but has two traps. The first is where NULLs go. The SQL standard leaves NULL placement open, so it varies between databases. PostgreSQL treats NULL as larger than any value, placing it last in ascending order and first in descending order. The 20,000 customers without a country came last under ORDER BY country and first under ORDER BY country DESC. MySQL and SQL Server do the opposite, treating NULL as the smallest value. Stating NULLS FIRST or NULLS LAST gives the same result on any database. Indexes follow this order too, so if a frequent sort is NULLS FIRST, the index must be built the same way for the sort step to be skipped. The second trap is ties. SQL does not guarantee the order among rows with equal sort keys. There were 8 orders with an amount of exactly 500.00, and ORDER BY amount DESC LIMIT 3 returned 845303, 40441 and 874320 under a serial plan but 501454, 40441 and 586912 under a parallel plan. The query was unchanged; only the plan changed, and so did the result. This can happen in production too, whenever changed data or refreshed statistics change the plan. The fix is to append a unique column such as id as the last sort key. ORDER BY amount DESC, id returned 40441, 501454 and 586912 under any plan. Leaving this out is especially harmful when showing results page by page, as the same row can appear on two pages while another appears on none. To show all the ties, use FETCH FIRST 3 ROWS WITH TIES, which also returns every row whose sort key equals the third row’s, so all 8 orders at 500.00 came back. PostgreSQL supports it from version 13.</sub> |

| **숫자 타입**<br><sub>Numeric types</sub> | float8은 0.1을 정확히 담지 못해 0.1 + 0.2가 0.3이 아니고, numeric은 10진수로 정확해요. 정수 나눗셈은 버림이고, 넘치면 오류가 나요.<br><sub>float8 cannot hold 0.1 exactly, so 0.1 + 0.2 is not 0.3, while numeric is exact decimal. Integer division truncates, and overflow raises an error.</sub> | PostgreSQL의 숫자 타입은 크게 세 가지예요. smallint, integer, bigint는 2, 4, 8바이트 정수이고, real과 double precision(float8)은 IEEE 754 2진 부동소수점, numeric은 10진수 자릿수를 그대로 저장하는 임의 정밀도 수예요. 소수 0.1은 2진수로 정확히 나타낼 수 없어서, float8로 0.1 + 0.2를 계산하면 0.30000000000000004가 되고 0.3과 같지 않다고 나와요. numeric은 0.1 + 0.2 = 0.3이 참이에요. 그래서 금액처럼 정확해야 하는 값은 numeric(10, 2)처럼 전체 자릿수와 소수 자릿수를 정해 저장해요. 정수 연산에도 함정이 있어요. 정수끼리 나누면 소수점 아래를 버려서 7 / 2는 3이고, 한쪽을 7 / 2.0처럼 numeric으로 만들어야 3.5가 나와요. 비율을 계산할 때 count(\*) / total이 0이 되는 흔한 버그의 원인이에요. 범위를 넘으면 C처럼 조용히 감싸지 않고 오류가 나서, int의 최댓값 2147483647에 1을 더하자 integer out of range가 났어요. 반올림 규칙도 타입마다 달라요. numeric의 round(2.5)는 0에서 먼 쪽으로 3이 되고, float8의 round(2.5)는 가장 가까운 짝수로 2가 됐어요. 부동소수점의 또 다른 성질은 더하는 순서에 따라 결과가 달라진다는 거예요. 주문 금액 100만 개를 numeric으로 더하면 언제나 250182450.77이었지만, float8로 바꿔 더하자 한 번은 250182450.77000302, 다음 실행에서는 250182450.77000016이 나왔어요. 병렬 실행에서 작업자들이 나눠 더한 부분합을 합치는 순서가 실행마다 달라서, 반올림 오차가 다르게 쌓였기 때문이에요. 같은 데이터에 같은 쿼리인데 결과가 바뀌면 테스트와 정산이 어려워져요. 반면 float8은 고정 8바이트에 하드웨어 연산이라 빠르고, numeric은 가변 크기로 123.45가 10바이트를 차지해요. 그래서 센서 측정값처럼 작은 오차를 허용하는 값에는 float을, 돈과 개수처럼 정확해야 하는 값에는 numeric과 정수를 써요.<br><sub>PostgreSQL’s numeric types come in three groups. smallint, integer and bigint are 2-, 4- and 8-byte integers; real and double precision (float8) are IEEE 754 binary floating point; and numeric is an arbitrary-precision number that stores decimal digits as they are. The decimal 0.1 has no exact binary representation, so computing 0.1 + 0.2 in float8 gives 0.30000000000000004, which is not equal to 0.3, while in numeric 0.1 + 0.2 = 0.3 is true. So values that must be exact, such as amounts of money, are stored as numeric with a set precision and scale, like numeric(10, 2). Integer arithmetic has traps too. Division between integers drops the fraction, so 7 / 2 is 3, and one side must be numeric, as in 7 / 2.0, to get 3.5. This is the cause of the common bug where a ratio like count(\*) / total comes out as 0. Overflow does not silently wrap as in C but raises an error, so adding 1 to int’s maximum, 2147483647, gave integer out of range. Rounding rules differ by type as well. numeric’s round(2.5) goes away from zero to 3, while float8’s round(2.5) went to the nearest even number, 2. Another property of floating point is that the result depends on the order of addition. Summing 1 million order amounts as numeric always gave 250182450.77, but cast to float8 the sum came out as 250182450.77000302 once and 250182450.77000016 on the next run. In parallel execution, the order in which the workers’ partial sums are combined varies between runs, so rounding errors accumulate differently. When the same query on the same data changes its result, testing and reconciliation become hard. On the other hand, float8 is a fixed 8 bytes computed in hardware and therefore fast, while numeric is variable-size, with 123.45 taking 10 bytes. So float suits values that tolerate small errors, such as sensor readings, and numeric and integers suit values that must be exact, such as money and counts.</sub> |
| **문자열과 콜레이션**<br><sub>Strings and collation</sub> | 글자 수와 바이트 수는 다르고, \|\|는 NULL 하나에 결과 전체가 NULL이 돼요. 정렬과 비교의 순서는 콜레이션이 정해서 C와 ICU의 결과가 달랐어요.<br><sub>Character counts differ from byte counts, and \|\| turns the whole result NULL over a single NULL. Collation decides the order of sorting and comparison, and C and ICU gave different results.</sub> | PostgreSQL의 문자열 타입은 text, varchar(n), char(n)이에요. text와 varchar는 저장 방식이 같아서 성능 차이가 없고, varchar(n)은 길이 제한 검사만 더해요. varchar(3) 열에 abcdef를 넣자 value too long for type character varying(3) 오류가 났지만, 'abcdef'::varchar(3)처럼 명시적으로 형변환하면 오류 없이 abc로 잘렸어요. char(n)은 남는 자리를 공백으로 채우고 비교할 때 끝 공백을 무시하는 오래된 타입이라 거의 쓰지 않아요. 길이도 두 가지예요. length는 글자 수, octet\_length는 UTF-8로 저장된 바이트 수를 세요. café는 4글자지만 é가 C3 A9 두 바이트라 5바이트이고, 한글은 한 글자가 3바이트라 두 글자가 6바이트였어요. 바이트 수로 제한하는 외부 시스템과 주고받을 때 이 차이가 문제가 돼요. The difference matters when exchanging data with external systems that limit by bytes. NULL handling needs care as well. The concatenation operator \|\| turns the whole result NULL if even one operand is NULL, so 'a' \|\| NULL was NULL. concat('a', NULL, 'b') skipped the NULL as if it were empty and returned ab, and concat\_ws inserts a separator while skipping NULLs. The C collation is fast and its results never change with operating system updates, while language-aware collations give users a natural order. Case-insensitive comparison uses ILIKE or lower(). | **인덱스를 살리는 조건**<br><sub>Index-friendly predicates</sub> | 열을 함수나 형변환으로 감싸면 인덱스를 쓰지 못해요. 같은 식으로 식 인덱스를 만들거나, 열은 그대로 두고 상수 쪽을 범위로 바꾸면 100배 넘게 빨라졌어요.<br><sub>Wrapping a column in a function or cast keeps the index unused. '%@Mail.com'처럼 %로 시작하는 패턴은 B-tree로는 불가능하고, pg\_trgm 확장의 GIN 인덱스가 필요해요.<br><sub>A B-tree index stores a column’s values in sorted order, so it can serve only conditions that narrow a range along that order. A condition in a form that can use an index is called sargable (Search ARGument ABLE), and the key is not wrapping the indexed column in an operation. Even with an index on email for 1 million users, writing WHERE lower(email) = 'kim400000@mail.com' to ignore case makes the planner compare lower(email) rather than email, and the index’s order is not the order of lower(email), so it cannot be used. The plan was a Parallel Seq Scan taking 106 ms. One fix is to build an index on exactly the expression in the condition. After CREATE INDEX ON users (lower(email)), the same query ran as an Index Scan in 0.2 ms. An expression index computes the expression on every write to stay current, and it is used only when the query’s expression matches the index’s exactly. Date comparisons fall into the same trap easily. Casting a timestamptz column to a date, as in signup::date = '2025-03-01', kept the signup index unused and took 49 ms. Leaving the column bare and turning the constant into a half-open range, signup >= '2025-03-01' AND signup < '2025-03-02', ran as an Index Only Scan in 0.6 ms with exactly the same 1,472 rows. The < that excludes the end keeps rows from overlapping or going missing at the midnight boundary. Attaching arithmetic or casts to the column, as in amount + 0 > 100 or id::text = '42', causes the same problem. LIKE depends on the shape of the pattern. With a fixed prefix, as in LIKE 'Kim4000%', it can turn into the range scan email >= 'Kim4000' AND email < 'Kim4001'. Under a collation other than C, however, a plain index’s sort order does not suit this conversion, and even this database’s C.UTF-8 produced a Seq Scan. | **부분 인덱스**<br><sub>Partial indexes</sub> | 조건에 맞는 행만 담는 부분 인덱스는 전체 인덱스의 60MB 대신 64kB였고, 쓰기도 2배 넘게 빨랐어요. 부분 고유 인덱스로는 조건부 규칙을 지킬 수 있어요.<br><sub>A partial index holding only matching rows was 64 kB instead of the full index’s 60 MB, and writes ran more than twice as fast. A partial unique index enforces conditional rules.</sub> | 부분 인덱스는 CREATE INDEX … WHERE 조건으로 만들어, 조건에 맞는 행만 담는 인덱스예요. 데이터가 한쪽으로 크게 치우쳐 있고 쿼리가 늘 작은 쪽만 찾을 때 효과가 커요. 작업 큐 테이블에 작업 200만 건이 있지만 대기 중인 것은 1,944건, 0.1%뿐이었어요. 워커는 늘 대기 중인 작업을 run\_at 순으로 몇 개씩 가져가므로, 완료된 약 200만 건까지 인덱스에 담을 이유가 없어요. WHERE status = 'queued'는 증명되지만, WHERE status = $1처럼 값이 매개변수이면 계획을 세울 때 값을 모르니 쓰지 못할 수 있어요. 준비된 문장 항목에서 이 일이 실제로 일어났어요. 부분 인덱스는 규칙을 지키는 데도 쓰여요. 부분 고유 인덱스는 조건에 맞는 행끼리만 고유성을 검사해요. status = 'active'인 행에만 user\_id 고유 인덱스를 두자, 사용자 1의 취소된 구독은 여러 개 들어갔지만 두 번째 활성 구독은 duplicate key 오류로 거부됐어요. 소프트 삭제를 쓰는 테이블에서 "삭제되지 않은 행 중에서만 이메일 고유" 같은 규칙도 같은 방법으로 만들어요.<br><sub>A partial index is created with CREATE INDEX … WHERE condition and holds only the rows meeting the condition. It pays off most when data is heavily skewed and queries always look for the small side. The job queue table held 2 million jobs, but only 1,944, or 0.1%, were queued. Workers always fetch a few queued jobs in run\_at order, so there is no reason to index the roughly 2 million finished ones. A regular index on (status, run\_at) was 60 MB, and a run\_at partial index with WHERE status = 'queued' was 64 kB. Both found the 10 oldest queued jobs quickly, in about 0.1 ms. Being small, it stays in memory, and VACUUM has less index to scan. The difference is clearer on writes. Inserting 1 million finished jobs took 3.70 s on the table with the full index and 1.52 s on the table with only the partial index, because a partial index needs no update when rows outside its condition are inserted or changed. There is a rule for when it can be used. The planner uses a partial index only when it can prove that the query’s WHERE logically implies the index’s condition. WHERE status = 'queued' can be proven, but when the value is a parameter, as in WHERE status = $1, the value is unknown at planning time and the index may not be usable. That actually happened in the prepared statements item. Partial indexes also enforce rules. A partial unique index checks uniqueness only among rows meeting its condition. With a unique index on user\_id only for rows where status = 'active', user 1’s canceled subscriptions went in several times, while a second active subscription was rejected with a duplicate key error. In a table with soft deletes, a rule such as "emails unique among non-deleted rows" is built the same way.</sub> |
| **통계와 행 수 추정**<br><sub>Statistics and row estimates</sub> | 플래너는 통계로 행 수를 추정해 계획을 골라요. 상관된 두 열은 5배 적게 추정됐다가 CREATE STATISTICS로 맞춰졌고, 낡은 통계는 200만 행을 1행으로 추정했어요.<br><sub>The planner picks plans from row estimates built on statistics. Two correlated columns were underestimated 5× until CREATE STATISTICS fixed it, and stale statistics estimated 2 million rows as 1.</sub> | PostgreSQL의 플래너는 비용 기반이에요. 가능한 실행 계획들의 비용을 추정해서 가장 싼 것을 고르는데, 그 비용의 출발점이 각 단계에서 몇 행이 나올지에 대한 추정이에요. 행 수 추정은 ANALYZE가 표본으로 모은 열별 통계에서 나와요. 가장 흔한 값 목록과 빈도, 값 분포의 히스토그램, 고유 값의 수 같은 것들이에요. EXPLAIN의 rows=가 추정이고, EXPLAIN ANALYZE의 actual rows=가 실제예요. 둘이 크게 다르면 계획이 틀렸을 가능성이 커요. 첫째 함정은 상관관계예요. 주소 100만 행에서 도시가 Seoul이면 나라는 언제나 KR이지만, 플래너는 조건들이 서로 독립이라고 보고 선택도를 곱해요. city = 'Seoul'의 0.1과 country = 'KR'의 0.2를 곱해 20,667행으로 추정했고, 실제는 100,000행이었어요. CREATE STATISTICS addr\_dep (dependencies) ON city, country로 두 열의 함수 종속을 수집하게 하고 ANALYZE하자, 같은 쿼리의 추정이 98,700행으로 거의 맞았어요. 확장 통계에는 열 조합의 고유 값 수를 세는 ndistinct와, 조합별 흔한 값을 기록하는 mcv 종류도 있어요. 둘째 함정은 낡은 통계예요. 자동 vacuum을 끈 이 테이블에 Daegu 행 200만 개를 넣고 통계를 갱신하지 않자, 플래너는 통계에 Daegu가 없으니 1행으로 추정했고, 실제는 2,000,000행이었어요. 조인 방식, 인덱스 사용, 메모리 배분이 모두 이 추정으로 정해지므로, 1행을 기대하고 고른 Nested Loop가 200만 행을 만나면 쿼리가 몇 배에서 수천 배까지 느려질 수 있어요. ANALYZE를 실행하자 추정이 2,002,900행으로 실제와 맞았어요. 보통은 autovacuum이 테이블의 변경량을 보고 알아서 ANALYZE하지만, 대량 적재 직후 바로 쿼리를 돌리는 배치 작업이나 임시 테이블은 자동 처리가 따라오지 못하므로 직접 실행해요. 분포가 복잡한 열은 ALTER TABLE … SET STATISTICS로 표본 크기를 키울 수 있어요.<br><sub>PostgreSQL’s planner is cost-based. It estimates the cost of possible execution plans and picks the cheapest, and the starting point of those costs is the estimate of how many rows each step will produce. Row estimates come from per-column statistics that ANALYZE gathers from a sample: lists of the most common values with their frequencies, histograms of the value distribution, the number of distinct values and so on. rows= in EXPLAIN is the estimate and actual rows= in EXPLAIN ANALYZE is reality, and when the two differ greatly, the plan is likely wrong. The first trap is correlation. In 1 million addresses, a city of Seoul always means a country of KR, but the planner treats conditions as independent and multiplies their selectivities. Multiplying 0.1 for city = 'Seoul' by 0.2 for country = 'KR' gave an estimate of 20,667 rows, while the actual count was 100,000. Having CREATE STATISTICS addr\_dep (dependencies) ON city, country collect the functional dependency between the two columns, followed by ANALYZE, brought the same query’s estimate to 98,700 rows, nearly right. Extended statistics also come in an ndistinct kind, which counts distinct values of column combinations, and an mcv kind, which records common values per combination. The second trap is stale statistics. After 2 million Daegu rows were inserted into this table with autovacuum off and its statistics left alone, the planner estimated 1 row because Daegu was absent from the statistics, while the actual count was 2,000,000. Join methods, index use and memory allocation all follow this estimate, so a Nested Loop chosen in expectation of 1 row can make a query several to thousands of times slower when it meets 2 million. Running ANALYZE brought the estimate to 2,002,900 rows, matching reality. Autovacuum normally runs ANALYZE on its own based on how much a table changed, but batch jobs that query right after a bulk load, and temporary tables, get ahead of the automatic process, so run it yourself there. For columns with complex distributions, ALTER TABLE … SET STATISTICS raises the sample size.</sub> |
| **준비된 문장과 계획 캐시**<br><sub>Prepared statements and plan caching</sub> | 준비된 문장은 파싱과 계획을 재사용해 단순 조회를 약 1.8배 빠르게 했어요. 다섯 번 뒤에는 값과 무관한 일반 계획으로 바뀌어, 부분 인덱스를 쓰지 못하게 됐어요.<br><sub>Prepared statements reuse parsing and planning, making simple lookups about 1.8× faster. After five runs they switched to a value-agnostic generic plan, which could no longer use a partial index.</sub> | 쿼리를 실행할 때마다 PostgreSQL은 SQL 문자열을 파싱하고, 테이블과 열을 확인하는 분석을 거치고, 실행 계획을 세운 다음 실행해요. 짧은 조회에서는 앞의 세 단계가 실행보다 비쌀 수도 있어요. PREPARE는 앞 단계를 한 번만 해 두고, EXECUTE는 매개변수 값만 넣어 실행해요. pgbench로 기본 키 하나를 조회하는 쿼리를 4개 연결에서 10초씩 돌리자, 매번 SQL 문자열을 보내는 단순 프로토콜은 초당 84,921건, 준비된 문장은 155,757건으로 약 1.8배였어요. 대부분의 드라이버와 ORM은 확장 프로토콜로 SQL과 값을 따로 보내고, 설정에 따라 문장을 준비해 재사용해요. 값을 SQL 문자열에 끼워 넣지 않으므로 SQL 인젝션도 막아 줘요. 준비된 문장에는 계획을 언제 다시 세울지의 문제가 있어요. 처음 다섯 번의 EXECUTE는 실제 매개변수 값을 보고 매번 맞춤 계획을 세워요. 값이 'queued'라는 걸 알기 때문에, status = 'queued' 조건으로 만든 작은 부분 인덱스 jobs\_queued를 골랐어요. 다섯 번이 지나면 PostgreSQL은 값과 무관한 일반 계획을 한 번 만들어 그 비용을 맞춤 계획들의 평균과 비교하고, 크게 나쁘지 않으면 이후로는 일반 계획을 재사용해 계획 비용을 아껴요. 여섯 번째 실행부터 계획에 Index Cond: (status = $1)이 나타났어요. 값을 모르니 부분 인덱스의 조건을 만족한다고 증명할 수 없어서, 전체 인덱스 jobs\_status\_run을 썼어요. pg\_prepared\_statements 뷰에는 일반 계획 2회, 맞춤 계획 5회가 기록됐어요. 이 예에서는 둘 다 빨랐지만, 값에 따라 최적 계획이 크게 다른 쿼리라면 일반 계획이 아주 나쁜 선택이 될 수 있어요. 흔한 값과 드문 값이 섞인 열에서, 드문 값에 맞는 인덱스 계획과 흔한 값에 맞는 순차 스캔 사이를 오가야 하는 경우예요. 그럴 때는 plan\_cache\_mode = force\_custom\_plan으로 바꿔 매번 맞춤 계획을 세우게 할 수 있고, 실제로 계획에 'done'이라는 실제 값이 다시 들어갔어요. 반대로 계획 비용이 큰 복잡한 쿼리라면 force\_generic\_plan으로 일반 계획을 강제해요.<br><sub>Every time a query runs, PostgreSQL parses the SQL string, analyzes it to resolve tables and columns, builds an execution plan and then executes it. For short lookups the first three steps can cost more than execution. PREPARE does those steps once, and EXECUTE runs with just the parameter values plugged in. Running a primary key lookup with pgbench on 4 connections for 10 seconds each gave 84,921 per second with the simple protocol, which sends the SQL string every time, and 155,757 with prepared statements, about 1.8 times as many. Most drivers and ORMs send SQL and values separately over the extended protocol and, depending on configuration, prepare and reuse statements. Since values are never spliced into the SQL string, this also prevents SQL injection. Prepared statements raise the question of when to replan. The first five EXECUTEs build a custom plan each time from the actual parameter value. Knowing the value was 'queued', the planner picked the small partial index jobs\_queued built for status = 'queued'. After five runs, PostgreSQL builds a value-agnostic generic plan once, compares its cost with the average of the custom plans, and if it is not much worse, reuses the generic plan from then on to save planning cost. From the sixth run, Index Cond: (status = $1) appeared in the plan. Not knowing the value, it could not prove the partial index’s condition held, so it used the full index jobs\_status\_run. The pg\_prepared\_statements view recorded 2 generic plans and 5 custom plans. Both were fast in this example, but for a query whose best plan varies widely with the value, the generic plan can be a very poor choice: think of a column mixing common and rare values, where a rare value suits an index plan and a common one suits a sequential scan. In that case, setting plan\_cache\_mode = force\_custom\_plan makes it build a custom plan every time, and indeed the actual value 'done' reappeared in the plan. Conversely, for complex queries with expensive planning, force\_generic\_plan forces the generic plan.</sub> |
| **VACUUM과 테이블 부풀음**<br><sub>VACUUM and bloat</sub> | UPDATE는 새 버전을 쓰고 옛 버전을 죽은 행으로 남겨 테이블이 2배가 됐어요. VACUUM이 그 공간을 재사용하게 하지만, 오래 열린 트랜잭션이 있으면 지우지 못해 169MB까지 커졌어요.<br><sub>UPDATE writes a new version and leaves the old one as a dead row, doubling the table. VACUUM makes that space reusable, but with a long-open transaction it could not remove anything and the table grew to 169 MB.</sub> | PostgreSQL은 MVCC로 읽기와 쓰기가 서로를 막지 않게 해요. 그 방법은 행을 제자리에서 고치지 않는 거예요. UPDATE는 새 버전을 다른 곳에 쓰고, 옛 버전에는 그것을 끝낸 트랜잭션 번호를 남겨 둬서, 그전에 시작한 트랜잭션은 여전히 옛 버전을 읽을 수 있어요. 대가는 공간이에요. 자동 vacuum을 끈 42MB 테이블의 100만 행을 모두 한 번 고치자 85MB로 2배가 됐고, 통계에는 죽은 행 1,000,000개가 잡혔어요. 이 죽은 행을 정리하는 것이 VACUUM이에요. VACUUM은 더 이상 어떤 트랜잭션도 볼 수 없는 죽은 행을 찾아 그 자리를 빈 공간 지도에 기록해요. 실행 뒤에도 크기는 85MB 그대로였지만, 다음 UPDATE가 그 빈 공간에 새 버전을 써서 테이블이 더 커지지 않았어요. 평소에는 autovacuum이 테이블마다 변경량을 보고 자동으로 실행해요. 문제는 VACUUM이 "더 이상 아무도 볼 수 없는" 행만 지울 수 있다는 거예요. 다른 연결이 REPEATABLE READ 트랜잭션을 열고 조회한 뒤 커밋하지 않은 채 있자, VACUUM VERBOSE가 1,000,000 are dead but not yet removable이라고 보고했어요. 그 트랜잭션의 스냅숏이 옛 버전을 볼 수 있으니 지울 수 없는 거예요. 그 상태에서 업데이트를 거듭하자 테이블은 85MB, 127MB, 169MB로 계속 커졌고 지우지 못한 죽은 행이 300만 개 쌓였어요. 연결을 닫은 뒤에야 공간이 재사용됐지만, 이미 커진 169MB는 운영체제에 돌아가지 않았어요. 실무에서는 BEGIN 후 커밋하지 않고 멈춘 idle in transaction 연결이 흔한 원인이라, pg\_stat\_activity로 찾고 idle\_in\_transaction\_session\_timeout으로 시간을 제한해요. 복제 슬롯과 오래 도는 분석 쿼리도 같은 일을 해요. 부풀음을 줄이는 방법도 있어요. 인덱스된 열을 바꾸지 않는 UPDATE는 같은 페이지에 빈자리가 있으면 인덱스를 건드리지 않고 페이지 안에서 새 버전을 이어 두는 HOT 업데이트가 돼요. 채움 비율 100%로 꽉 찬 테이블에서는 100만 건 중 HOT이 0건이었고, fillfactor = 70으로 페이지마다 30%의 여유를 두자 430,390건이 HOT이 되어 2.38초가 1.84초로 줄었어요. 자주 고치는 테이블에서는 인덱스를 꼭 필요한 열에만 두는 것도 HOT을 늘리는 방법이에요.<br><sub>PostgreSQL uses MVCC so that reads and writes do not block each other, and it does so by never modifying rows in place. UPDATE writes a new version elsewhere and stamps the old version with the ID of the transaction that ended it, so transactions that started earlier can still read the old version. The price is space. Updating all 1 million rows of a 42 MB table with autovacuum off doubled it to 85 MB, and the statistics showed 1,000,000 dead rows. Cleaning up those dead rows is VACUUM’s job. VACUUM finds dead rows that no transaction can see anymore and records their space in the free space map. Afterwards the size was still 85 MB, but the next UPDATE wrote its new versions into that free space, and the table did not grow. Normally autovacuum runs this automatically for each table based on how much it changed. The catch is that VACUUM can remove only rows that "nobody can see anymore". While another connection opened a REPEATABLE READ transaction, ran a query and sat without committing, VACUUM VERBOSE reported 1,000,000 are dead but not yet removable. That transaction’s snapshot could still see the old versions, so they could not be removed. Updating repeatedly in that state grew the table from 85 MB to 127 MB to 169 MB, with 3 million unremovable dead rows piling up. Only after the connection closed was the space reused, and the 169 MB already taken was not returned to the operating system. In practice, a connection that ran BEGIN and stalled without committing, idle in transaction, is the usual cause, so such connections are found in pg\_stat\_activity and limited with idle\_in\_transaction\_session\_timeout. Replication slots and long-running analytical queries do the same. There are ways to reduce bloat too. An UPDATE that changes no indexed column becomes a HOT update when its page has free room: the new version is chained within the page without touching the indexes. In a table packed at 100% fill, none of 1 million updates were HOT, while leaving 30% room per page with fillfactor = 70 made 430,390 of them HOT and cut the time from 2.38 s to 1.84 s. For frequently updated tables, keeping indexes only on the columns that truly need them also increases HOT updates.</sub> |

| **뷰와 구체화된 뷰**<br><sub>Views and materialized views</sub> | 뷰는 저장된 쿼리라 쓸 때마다 펼쳐지고, 구체화된 뷰는 결과를 저장해 58ms 걸리던 집계를 0.04ms로 읽었어요. 대신 REFRESH 전까지는 원본의 변화가 보이지 않아요.<br><sub>A view is a stored query expanded on every use, while a materialized view stores its result, reading an aggregate that took 58 ms in 0.04 ms. Until REFRESH, though, changes to the source do not show.</sub> | 뷰는 이름을 붙여 저장한 쿼리예요. CREATE VIEW paid\_orders AS SELECT … FROM orders WHERE status = 'paid'로 만들면, 이후 paid\_orders를 테이블처럼 조회할 수 있어요. 뷰는 데이터를 따로 저장하지 않아요. 뷰를 조회하면 PostgreSQL이 뷰의 정의를 바깥 쿼리에 펼쳐 하나의 쿼리로 합친 뒤 계획을 세워요. 그래서 paid\_orders에서 customer\_id = 7을 찾는 쿼리의 실행 계획에는 뷰가 아니라 orders 테이블이 나왔고, customer\_id 인덱스와 status 조건이 함께 쓰였어요. 뷰는 복잡한 조인이나 조건을 감춰 쿼리를 단순하게 하고, 권한을 뷰에만 주어 테이블의 일부 열과 행만 보이게 하는 데도 쓰여요. 단순한 뷰는 INSERT와 UPDATE도 통과시켜요. 구체화된 뷰는 쿼리의 결과를 실제 테이블처럼 디스크에 저장해요. 날짜별 결제 매출을 집계하는 daily\_rev를 만들고 날짜에 고유 인덱스를 두었어요. 주문 100만 건에서 하루 매출을 직접 집계하는 데 58ms가 걸렸지만, 365일치를 미리 계산해 둔 daily\_rev에서 같은 날을 찾는 데는 0.04ms였어요. 대가는 신선도예요. 저장된 결과는 원본이 바뀌어도 자동으로 따라가지 않아서, 6월 1일에 결제 주문을 하나 넣은 뒤에도 daily\_rev의 그날 주문 수는 1,641 그대로였어요. REFRESH MATERIALIZED VIEW가 쿼리를 다시 실행해 결과를 바꿔요. 기본 REFRESH는 그동안 뷰를 잠가 읽기를 막고, REFRESH … CONCURRENTLY는 고유 인덱스가 있으면 새 결과를 따로 계산한 뒤 바뀐 행만 갈아 끼워서 읽기를 막지 않아요. 166ms 뒤 주문 수가 1,642가 됐어요. CONCURRENTLY는 비교하는 만큼 일을 더 하므로, 뷰가 크고 바뀐 행이 적을 때 유리해요. 결국 REFRESH 주기가 허용할 수 있는 지연이에요. 대시보드는 몇 분마다, 일간 보고서는 하루 한 번처럼 정하고, 늘 최신 합계가 필요하다면 트리거로 갱신하는 집계 테이블을 만드는 편이 맞아요. 날짜로 자르는 집계는 세션 시간대에 따라 결과가 달라지므로, 기준 시간대를 정의에 명시해 두는 것도 좋아요.<br><sub>A view is a named, stored query. Creating CREATE VIEW paid\_orders AS SELECT … FROM orders WHERE status = 'paid' lets paid\_orders be queried like a table afterwards. A view stores no data of its own. When it is queried, PostgreSQL expands the view’s definition into the outer query, merging them into one query before planning. So the plan for finding customer\_id = 7 in paid\_orders showed the orders table rather than the view, using the customer\_id index together with the status condition. Views simplify queries by hiding complex joins and conditions, and granting permissions on a view alone exposes only some columns and rows of a table. Simple views even pass INSERT and UPDATE through. A materialized view stores a query’s result on disk as if it were a real table. We created daily\_rev, aggregating paid revenue by date, with a unique index on the date. Aggregating one day’s revenue directly over 1 million orders took 58 ms, while finding the same day in daily\_rev, with 365 days computed in advance, took 0.04 ms. The price is freshness. The stored result does not follow changes to the source automatically, so even after a paid order was inserted for June 1, daily\_rev still showed 1,641 orders for that day. REFRESH MATERIALIZED VIEW reruns the query and replaces the result. A plain REFRESH locks the view and blocks reads meanwhile, while REFRESH … CONCURRENTLY, given a unique index, computes the new result separately and swaps in only the changed rows without blocking reads. After 166 ms the count became 1,642. CONCURRENTLY does extra work comparing, so it pays off when the view is large and few rows change. In the end, the refresh interval is the staleness you accept: every few minutes for a dashboard, once a day for a daily report, and when totals must always be current, a summary table maintained by triggers fits better. Aggregates cut by date depend on the session time zone, so naming the reference zone in the definition is a good idea too.</sub> |
| **함수와 변동성**<br><sub>Functions and volatility</sub> | 함수의 변동성 표시는 플래너가 그 함수를 얼마나 믿을지를 정해요. VOLATILE 함수는 100만 번 불리며 인덱스를 막았고, STABLE로 바꾸자 한 번만 계산해 약 600배 빨라졌어요.<br><sub>A function’s volatility marking decides how far the planner can trust it. A VOLATILE function was called 1 million times and blocked the index, while declaring it STABLE computed it once and ran about 600× faster.</sub> | PostgreSQL은 SQL, PL/pgSQL 같은 언어로 함수를 만들어 쿼리 안에서 쓸 수 있게 해요. 함수를 만들 때 중요한 속성이 변동성이에요. VOLATILE은 같은 입력에도 호출할 때마다 결과가 달라질 수 있는 함수로, random()과 clock\_timestamp()가 그래요. STABLE은 한 문장을 실행하는 동안에는 같은 결과를 주는 함수로, 트랜잭션 시작 시각을 돌려주는 now()가 그래요. IMMUTABLE은 입력이 같으면 언제나 같은 결과를 주는 함수로, lower()와 산술 연산이 그래요. 플래너는 이 표시를 믿고 최적화를 정해요. 아무것도 적지 않으면 기본값은 VOLATILE이에요. 현재 고객 번호를 돌려주는 PL/pgSQL 함수 cur\_id()를 VOLATILE로 두고 WHERE customer\_id = cur\_id()를 실행하자, 플래너는 행마다 값이 바뀔 수 있다고 봐야 해서 인덱스를 쓸 수 없었어요. Seq Scan으로 100만 행을 읽으며 행마다 함수를 불렀고, 호출 횟수를 세 보니 정확히 1,000,000번이었으며 209ms가 걸렸어요. 같은 함수를 STABLE로 만들자, 플래너가 문장을 시작할 때 한 번 계산해도 된다는 걸 알고 함수를 Index Cond에 넣었어요. 0.36ms로 약 600배 빨라졌고 결과는 같은 5건이었어요. IMMUTABLE은 계획 단계에서 상수로 미리 계산될 수 있고, 식 인덱스에는 IMMUTABLE 함수만 쓸 수 있어요. 변동성은 PostgreSQL이 검증하지 않고 믿는 약속이에요. 실제로는 테이블을 읽거나 설정에 따라 결과가 바뀌는 함수를 IMMUTABLE이라고 표시하면, 식 인덱스나 미리 계산된 상수에 틀린 값이 남아 잘못된 결과가 나올 수 있어요. 그래서 함수의 실제 성질에 맞는 가장 엄격한 표시를 정직하게 붙여요. 예외도 있어요. 본문이 SELECT 한 줄인 단순한 SQL 함수는 호출 대신 쿼리에 그대로 펼쳐지는 인라이닝이 일어나서, VOLATILE로 만든 SELECT 7 함수가 상수 7로 바뀌어 인덱스를 썼어요. 함수에는 이 밖에도 PARALLEL SAFE 표시로 병렬 실행 참여 여부를, COST와 ROWS로 플래너에게 실행 비용과 반환 행 수를 알려 줄 수 있어요.<br><sub>PostgreSQL lets you write functions in languages such as SQL and PL/pgSQL and use them inside queries. An important property when creating a function is its volatility. VOLATILE functions may return a different result on every call even with the same input, as random() and clock\_timestamp() do. STABLE functions return the same result throughout one statement’s execution, as now(), which returns the transaction’s start time, does. IMMUTABLE functions always return the same result for the same input, as lower() and arithmetic do. The planner trusts this marking when choosing optimizations. With no marking, the default is VOLATILE. Leaving cur\_id(), a PL/pgSQL function returning the current customer number, as VOLATILE and running WHERE customer\_id = cur\_id() meant the planner had to assume the value could change per row, so it could not use the index. It read 1 million rows with a Seq Scan, calling the function for every row; counting the calls showed exactly 1,000,000, and it took 209 ms. Declaring the same function STABLE let the planner know it could be evaluated once at the start of the statement, so it put the function into the Index Cond. It ran in 0.36 ms, about 600 times faster, with the same 5 rows. IMMUTABLE functions can be pre-computed as constants during planning, and only IMMUTABLE functions are allowed in expression indexes. Volatility is a promise PostgreSQL trusts without verifying. Marking as IMMUTABLE a function whose result actually changes, because it reads tables or depends on settings, can leave wrong values in expression indexes or pre-computed constants and produce wrong results. So functions honestly get the strictest marking their real behavior allows. There is an exception. A simple SQL function whose body is a single SELECT can be inlined, expanded straight into the query instead of being called, so a SELECT 7 function created as VOLATILE turned into the constant 7 and used the index. Functions can also declare PARALLEL SAFE to take part in parallel execution, and COST and ROWS to tell the planner their execution cost and the number of rows they return.</sub> |
| **트리거**<br><sub>Triggers</sub> | 행 트리거는 바뀐 행마다 함수를 실행해 20만 행 UPDATE를 2배 넘게 느리게 했고, 전이 테이블을 쓰는 문장 트리거는 같은 일을 더 빨리 했어요. BEFORE 트리거는 값을 고치거나 쓰기를 거부할 수 있어요.<br><sub>A row trigger ran its function for every changed row, making a 200,000-row UPDATE more than twice as slow, while a statement trigger with transition tables did the same job faster. BEFORE triggers can change values or reject writes.</sub> | 트리거는 테이블에 INSERT, UPDATE, DELETE, TRUNCATE가 일어날 때 자동으로 실행되는 함수예요. 언제 실행할지(BEFORE, AFTER, 뷰의 INSTEAD OF)와 단위(행마다 또는 문장마다)를 정해요. 감사 기록, 수정 시각 갱신, 집계 테이블 유지처럼 어떤 경로로 쓰든 반드시 일어나야 하는 일에 써요. FOR EACH ROW 트리거는 바뀐 행마다 한 번씩 실행돼요. 계좌 20만 행 전체를 고치는 UPDATE가 트리거 없이 0.45초였는데, 행마다 이전 값과 새 값을 감사 테이블에 넣는 AFTER 행 트리거를 달자 1.02초로 2배 넘게 느려졌어요. 함수 호출과 감사 INSERT가 20만 번씩 일어났기 때문이에요. FOR EACH STATEMENT 트리거는 문장마다 한 번만 실행돼요. PostgreSQL 10부터는 REFERENCING OLD TABLE AS o NEW TABLE AS n으로, 문장이 바꾼 모든 행의 이전 상태와 이후 상태를 전이 테이블이라는 임시 테이블로 받을 수 있어요. 같은 감사 기록 20만 건을 INSERT … SELECT 한 번으로 넣자 0.79초였어요. 대량 변경이 잦은 테이블이라면 문장 트리거가 유리해요. BEFORE 행 트리거는 행이 저장되기 전에 실행돼서, 함수 안에서 NEW 레코드를 고치면 고친 값이 저장돼요. new.updated\_at := now()로 수정 시각을 채우자, 애플리케이션이 그 열을 건드리지 않았는데도 updated\_at이 방금 시각으로 바뀌었어요. BEFORE 트리거에서 예외를 던지면 그 문장 전체가 취소되므로 검증에도 쓸 수 있어요. 잔액을 -5로 바꾸려 하자 balance would be -5 오류가 났어요. 다만 단순한 조건은 CHECK 제약이 더 빠르고 분명해요. 트리거 안에서 한 쓰기도 원래 문장과 같은 트랜잭션에 속해서 함께 커밋되거나 함께 롤백돼요. 주의할 점도 분명해요. 트리거는 애플리케이션 코드에서 보이지 않는 동작이라, 많아지면 쓰기가 왜 느린지, 값이 왜 바뀌었는지 추적하기 어려워져요. 트리거가 다른 테이블을 고치고 그 테이블의 트리거가 또 실행되는 연쇄도 생길 수 있어요. 그래서 꼭 DB에서 보장해야 하는 규칙에만 쓰고, 이름과 문서로 존재를 드러내 두는 편이 좋아요.<br><sub>A trigger is a function run automatically when INSERT, UPDATE, DELETE or TRUNCATE happens on a table. You choose when it runs (BEFORE, AFTER, or INSTEAD OF for views) and its granularity (per row or per statement). Triggers are used for things that must happen whatever path a write takes, such as audit records, updating modification times and maintaining summary tables. A FOR EACH ROW trigger runs once for every changed row. An UPDATE of all 200,000 account rows took 0.45 s without triggers, and adding an AFTER row trigger that inserted the old and new values into an audit table made it 1.02 s, more than twice as slow, because the function call and the audit INSERT each happened 200,000 times. A FOR EACH STATEMENT trigger runs only once per statement. Since PostgreSQL 10, REFERENCING OLD TABLE AS o NEW TABLE AS n delivers the before and after states of every row the statement changed as temporary tables called transition tables. Inserting the same 200,000 audit records with a single INSERT … SELECT took 0.79 s, so statement triggers win on tables with frequent bulk changes. A BEFORE row trigger runs before the row is stored, so changes made to the NEW record inside the function are what gets stored. Setting new.updated\_at := now() changed updated\_at to the current time even though the application never touched that column. Raising an exception in a BEFORE trigger cancels the whole statement, so triggers can validate too: trying to set a balance to -5 failed with balance would be -5. For simple conditions, though, a CHECK constraint is faster and clearer. Writes made inside a trigger belong to the same transaction as the original statement, committing or rolling back together. The caveats are clear as well. Triggers are behavior invisible in application code, so as they multiply it becomes hard to trace why writes are slow or why a value changed. Chains can form, where a trigger modifies another table whose trigger then runs in turn. So triggers are best kept for rules the database truly must guarantee, with names and documentation that make their existence visible.</sub> |
| **파티셔닝**<br><sub>Partitioning</sub> | 테이블을 달마다 나누면 날짜 조건의 쿼리는 해당 달의 파티션만 읽고, 오래된 달은 DELETE 대신 파티션째 떼어 내 버려요. 파티션 키가 없는 조건은 모든 파티션을 훑었어요.<br><sub>Splitting a table by month lets date-filtered queries read only that month’s partition, and old months are dropped a partition at a time instead of with DELETE. A condition without the partition key scanned every partition.</sub> | 선언적 파티셔닝은 하나의 논리 테이블을 키의 범위, 목록, 해시에 따라 여러 물리 테이블로 나눠요. PARTITION BY RANGE (created\_at)로 만든 부모 테이블 op에는 데이터가 없고, 2025년 1월부터 12월까지 달마다 하나씩 파티션 12개와, 어느 범위에도 맞지 않는 행을 받는 기본 파티션을 붙였어요. 주문 100만 건을 부모에 넣자 각 행이 created\_at에 맞는 파티션으로 자동으로 들어갔어요. 가장 큰 효과는 파티션 가지치기예요. WHERE에 파티션 키의 범위가 있으면, 플래너가 결과에 기여할 수 없는 파티션을 계획에서 빼 버려요. 3월 매출 합계를 구하는 쿼리의 실행 계획에는 op\_2025\_03 하나만 나왔고, 13개 중 하나만 읽어 7.5ms였어요. 같은 데이터를 담은 일반 테이블은 created\_at 인덱스가 있어도 21ms였어요. 파티션마다 인덱스와 통계가 작아서 유지 작업도 가벼워져요. 반대로 파티션 키가 없는 조건은 가지치기를 할 수 없어요. customer\_id로 찾자 Parallel Append가 13개 파티션을 모두 훑었어요. 그래서 파티션 키는 거의 모든 쿼리가 쓰는 조건으로 골라야 해요. 고유 제약과 기본 키도 파티션 키를 포함해야만 만들 수 있다는 제한이 있어요. 파티셔닝이 가장 빛나는 일은 오래된 데이터를 버리는 거예요. 일반 테이블에서 1월 주문을 DELETE하자 39ms가 걸렸고 죽은 행이 남아 나중에 VACUUM이 치워야 했어요. 파티션 테이블에서는 ALTER TABLE … DETACH PARTITION과 DROP TABLE로 1월 파티션이 5.6ms 만에 사라졌고, 죽은 행도 VACUUM할 일도 없었어요. 데이터가 많을수록 차이는 몇 분과 몇 밀리초의 차이로 벌어져요. 보관 정책이 "13개월 지난 데이터 삭제"처럼 시간 단위라면 파티셔닝이 딱 맞아요. 대가도 있어요. 파티션이 수천 개로 많아지면 계획 시간과 메모리가 늘고, 행을 다른 파티션으로 옮기는 UPDATE는 내부적으로 삭제와 삽입이 돼요. 그래서 보통 수천만 행 이상이면서 시간순으로 쌓이고 오래된 것을 버리는 데이터에 써요.<br><sub>Declarative partitioning splits one logical table into several physical tables by ranges, lists or hashes of a key. The parent table op, created with PARTITION BY RANGE (created\_at), holds no data; it got 12 partitions, one per month from January to December 2025, plus a default partition for rows that fit no range. Inserting 1 million orders into the parent routed each row automatically to the partition matching its created\_at. The biggest benefit is partition pruning. When WHERE carries a range on the partition key, the planner drops partitions that cannot contribute to the result from the plan. The plan for March’s revenue total showed only op\_2025\_03, reading one partition of 13 in 7.5 ms. A plain table holding the same data took 21 ms even with an index on created\_at. With smaller indexes and statistics per partition, maintenance gets lighter too. Conversely, a condition without the partition key cannot prune. Searching by customer\_id made a Parallel Append scan all 13 partitions. So the partition key must be a condition nearly every query uses. There is also the restriction that unique constraints and primary keys can be created only if they include the partition key. Where partitioning shines most is discarding old data. DELETEing January’s orders from the plain table took 39 ms and left dead rows for VACUUM to clean up later. In the partitioned table, ALTER TABLE … DETACH PARTITION and DROP TABLE made the January partition vanish in 5.6 ms, with no dead rows and nothing to VACUUM. As data grows, the gap widens to minutes versus milliseconds. When the retention policy is time-based, such as "delete data older than 13 months", partitioning fits perfectly. There are costs as well. With thousands of partitions, planning time and memory grow, and an UPDATE that moves a row to another partition becomes a delete plus an insert internally. So partitioning is typically used for data of tens of millions of rows or more that accumulates in time order and whose old parts are discarded.</sub> |
| **시퀀스와 빈 번호**<br><sub>Sequences and gaps</sub> | 시퀀스는 트랜잭션 밖에서 증가해서 롤백이나 ON CONFLICT로 건너뛴 삽입에도 번호가 소모돼요. 그래서 id에는 빈 번호가 생기고, 그것이 정상이에요.<br><sub>Sequences advance outside transactions, so rollbacks and inserts skipped by ON CONFLICT still consume numbers. ids therefore have gaps, and that is normal.</sub> | 시퀀스는 nextval()을 부를 때마다 다음 정수를 내주는 데이터베이스 객체예요. GENERATED ALWAYS AS IDENTITY 열이나 예전 방식의 serial 열은 내부적으로 시퀀스를 하나 만들어 기본값으로 써요. 첫 행 A는 id 1을 받았어요. 시퀀스의 중요한 성질은 트랜잭션 밖에서 증가한다는 거예요. 트랜잭션 안에서 B를 넣고 롤백하자 행은 사라졌지만 번호 2는 돌아오지 않았어요. 만약 번호를 트랜잭션과 함께 되돌려야 한다면, 다른 세션은 앞 트랜잭션이 커밋할지 롤백할지 알 때까지 다음 번호를 받지 못하고 기다려야 해요. 시퀀스는 그 기다림을 없애려고 일부러 롤백되지 않아요. 같은 이유로 C를 넣어 3을 받은 뒤, 같은 C를 ON CONFLICT DO NOTHING으로 다시 넣자 충돌로 건너뛰었지만 번호 4는 이미 소모됐어요. 기본값은 충돌을 확인하기 전에 계산되기 때문이에요. 서버가 비정상 종료되면 미리 기록해 둔 번호가 건너뛰어지기도 하고, CACHE 설정으로 세션마다 번호를 미리 받아 두면 순서도 뒤섞여요. 결과 테이블의 id는 1, 3, 5였어요. 기본 키는 유일하기만 하면 되므로 빈 번호는 문제가 아니에요. 빈 번호를 메우려고 MAX(id) + 1을 쓰는 것은 동시성에서 중복을 만드는 잘못된 방법이에요. 세금계산서 번호처럼 법적으로 빈 번호가 없어야 하는 연번이 필요하면, 카운터를 담은 행을 SELECT … FOR UPDATE로 잠그고 번호를 매긴 뒤 같은 트랜잭션에서 증가시켜요. 대신 그 행에서 모든 쓰기가 줄을 서므로 동시성이 크게 줄어요. identity와 serial의 차이도 알아 두면 좋아요. serial 열에 id 1을 직접 넣자 시퀀스는 그 사실을 몰라서, 다음 기본값 삽입이 다시 1을 받아 duplicate key 오류가 났어요. GENERATED ALWAYS AS IDENTITY는 직접 넣기를 cannot insert a non-DEFAULT value로 막고, 꼭 필요하면 OVERRIDING SYSTEM VALUE를 명시해야 해서 이런 실수를 줄여 줘요. 새 테이블에는 SQL 표준인 identity를 써요.<br><sub>A sequence is a database object that returns the next integer every time nextval() is called. A GENERATED ALWAYS AS IDENTITY column, or an old-style serial column, creates one internally and uses it as the default. The first row, A, received id 1. The key property of sequences is that they advance outside transactions. Inserting B inside a transaction and rolling back removed the row, but number 2 never came back. If numbers had to be undone along with transactions, other sessions could not get the next number until they knew whether the earlier transaction would commit or roll back, and they would have to wait. Sequences deliberately ignore rollbacks to remove that wait. For the same reason, after C was inserted and received 3, inserting the same C again with ON CONFLICT DO NOTHING was skipped on the conflict, yet number 4 had already been consumed, because defaults are computed before the conflict check. After a crash, numbers logged in advance can be skipped, and with a CACHE setting each session reserves numbers ahead of time, which also shuffles their order. The resulting ids were 1, 3 and 5. A primary key only needs to be unique, so gaps are not a problem. Filling gaps with MAX(id) + 1 is a wrong approach that creates duplicates under concurrency. When a gapless sequence is required, as with legally mandated invoice numbers, a row holding a counter is locked with SELECT … FOR UPDATE, the number assigned, and the counter incremented in the same transaction. Every writer then queues on that row, which greatly reduces concurrency. The difference between identity and serial is worth knowing too. After id 1 was inserted manually into a serial column, the sequence did not know about it, so the next insert using the default received 1 again and failed with a duplicate key error. GENERATED ALWAYS AS IDENTITY blocks manual values with cannot insert a non-DEFAULT value and requires an explicit OVERRIDING SYSTEM VALUE when truly needed, which cuts down on such mistakes. New tables use identity, the SQL standard form.</sub> |

With the network round trips, TLS handshake and password hash check of a real service, a connection costs from several to tens of milliseconds. Connections are also capped. The default max\_connections is 100, and once 100 connections were open, the next was refused with FATAL: sorry, too many clients already. Each backend process had an RSS of about 13 MB, a figure that includes some shared memory, and the work\_mem queries use for sorts and hashes is added separately per connection. More connections also raise the cost of memory, lock management and CPU context switching, so when active connections far exceed the core count, throughput actually drops. A connection pool lends a small set of pre-opened connections to each request and takes them back. A pool inside the application is the baseline, and where many servers or function instances would exceed the cap with their combined pools, a proxy such as PgBouncer gathers thousands of client connections onto dozens of server connections. PgBouncer’s transaction pooling mode returns the server connection at the end of every transaction, so session-bound state such as SET values, prepared statements and temporary tables needs care. A bigger pool is not better. A size of a few times the database’s core count is typical, and having excess requests wait briefly in the pool gives shorter overall response times than driving the database into overload. The wait for a pooled connection gets a limit too, so requests do not pile up endlessly during an outage.</sub> |

When an accidental giant join, queries lined up waiting on locks, or connections stalled with an open transaction pile up while holding resources, connections eventually run out and the service stops. PostgreSQL cuts these off with three time limits. statement\_timeout is the longest a single statement may run. With it set to 200 ms, a large self-join was canceled at exactly 0.20 s with canceling statement due to statement timeout. It keeps a runaway query from monopolizing CPU and I/O or holding a connection for long. lock\_timeout limits not running time but only the wait for a lock. Trying to update a row another session held with FOR UPDATE gave up after 0.30 s with canceling statement due to lock timeout. With it at 0.5 s, pausing for 1 s inside a transaction made the server end the connection with terminating connection due to idle-in-transaction timeout. Code that forgets to commit or roll back in an exception handler, or that waits on an external API inside a transaction, creates such connections, and they hold locks and keep VACUUM from clearing dead rows. When a statement is canceled, the transaction it belongs to is aborted and must be rolled back, so the application rolls back on this error and retries if appropriate.
