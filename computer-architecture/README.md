## 컴퓨터가 수와 글자를 담는 방법 · How computers store numbers and text

모든 데이터는 결국 0과 1이에요. 그 약속을 알아야 이상한 버그가 이해돼요.  
*All data is 0s and 1s in the end; knowing the conventions explains strange bugs.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **2진수와 16진수**<br><sub>Binary · Hexadecimal</sub> | 컴퓨터는 0과 1(비트)로 수를 표현해요. 자리마다 2배씩 커지고, 4비트를 16진수 한 글자로 줄여 써요.<br><sub>Computers write numbers in bits; each place is worth double the previous, and hex packs 4 bits into one digit.</sub> | 색상(#FF8800), 메모리 주소, 해시값, 파일 권한(chmod 755=2진 111 101 101)이 모두 이 표기예요.<br><sub>Colours (#FF8800), memory addresses, hashes and file modes (chmod 755 = 111 101 101) all use these notations.</sub> |
| **2의 보수**<br><sub>Two’s complement</sub> | 음수는 비트를 뒤집고 1을 더해 표현해요. 덧셈 회로 하나로 뺄셈까지 처리할 수 있어요.<br><sub>Negative numbers are formed by inverting the bits and adding one, so a single adder handles subtraction.</sub> | 정수형은 범위를 넘으면 반대쪽 끝으로 넘어가요(오버플로). 32비트 int는 약 21억이 한계라 금액·ID엔 64비트를 쓰세요.<br><sub>Integers wrap around past their range (overflow). A 32-bit int tops out near 2.1 billion, so use 64-bit for money and ids.</sub> |
| **부동소수점**<br><sub>Floating point</sub> | 실수를 부호·지수·가수로 나눠 저장하는 방식(IEEE 754)이에요. 0.1처럼 2진수로 딱 떨어지지 않는 수는 근사값이 돼요.<br><sub>Real numbers are stored as sign, exponent and fraction (IEEE 754); values like 0.1 that don’t terminate in binary are approximated.</sub> | 0.1 + 0.2 ≠ 0.3 이에요. 돈 계산은 정수(최소 단위)나 Decimal 타입을 쓰고, 실수 비교는 오차 범위로 하세요.<br><sub>0.1 + 0.2 ≠ 0.3. Do money in integer minor units or Decimal, and compare floats within a tolerance.</sub> |
| **엔디언**<br><sub>Endianness</sub> | 여러 바이트로 된 값을 메모리에 큰 자리부터(빅 엔디언) 둘지, 작은 자리부터(리틀 엔디언) 둘지의 약속이에요.<br><sub>Whether a multi-byte value is stored most-significant byte first (big-endian) or least-significant first (little-endian).</sub> | 대부분의 CPU는 리틀 엔디언, 네트워크는 빅 엔디언이에요. 바이너리 파일·소켓 프로토콜을 파싱할 때 순서를 꼭 맞추세요.<br><sub>Most CPUs are little-endian; network protocols are big-endian. Match the order when parsing binary files or sockets.</sub> |
| **문자 인코딩 (UTF-8)**<br><sub>Character encoding · UTF-8</sub> | 모든 문자에 유니코드 번호를 붙이고, UTF-8은 이를 1~4바이트로 저장해요. 영문은 1바이트, 한글은 3바이트예요.<br><sub>Every character has a Unicode number, and UTF-8 stores it in 1–4 bytes: 1 for English letters, 3 for Korean syllables.</sub> | 글자가 깨지면(문자 깨짐) 저장과 읽기 인코딩이 다른 거예요. MySQL은 이모지 때문에 utf8이 아닌 utf8mb4를 써야 해요.<br><sub>Garbled text means writing and reading used different encodings. In MySQL use utf8mb4, not utf8, so emoji fit.</sub> |
| **곱셈과 나눗셈 하드웨어**<br><sub>Multiplication and division hardware</sub> | 2진 곱셈은 곱하는 수의 비트마다 “1이면 시프트해서 더하기”를 반복하는 세로 곱셈이에요. 나눗셈은 시프트와 빼기의 반복이에요.<br><sub>Binary multiplication is long multiplication: for each multiplier bit, shift and add if it is 1. Division repeats shift-and-subtract.</sub> | 1011(11) × 1101(13)은 비트 0, 2, 3이 1이라 1011을 0, 2, 3칸 시프트한 부분곱을 더해 10001111(143)이 돼요. 하드웨어는 시프트 레지스터와 가산기를 반복 사용하거나, 부스 인코딩(연속된 1을 빼기 한 번으로)과 월리스 트리(부분곱 병렬 덧셈)로 빠르게 해요. 나눗셈은 훨씬 느려서, 컴파일러는 x \* 10을 (x << 3) + (x << 1)로, 상수 나눗셈을 곱셈으로 바꿔요.<br><sub>1011 (11) × 1101 (13) has bits 0, 2 and 3 set, so adding 1011 shifted by 0, 2 and 3 gives 10001111 (143). Hardware loops a shift register and an adder, or speeds things up with Booth encoding (a run of 1s becomes one subtract) and Wallace trees (adding partial products in parallel). Division is much slower, so compilers rewrite x \* 10 as (x << 3) + (x << 1) and constant divides as multiplies.</sub> |
| **해밍 코드와 ECC**<br><sub>Hamming codes and ECC</sub> | 패리티 비트 몇 개를 정해진 자리에 끼워 넣어, 1비트 오류가 어디서 났는지 찾아 고칠 수 있게 하는 부호예요.<br><sub>A code that inserts a few parity bits at fixed positions so a single flipped bit can be located and corrected.</sub> | 해밍(7,4)은 1, 2, 4번 자리에 패리티를 두고, p1은 1·3·5·7번, p2는 2·3·6·7번, p4는 4·5·6·7번 자리의 짝수 패리티를 맞춰요. 데이터 1011은 0110011이 되고, 6번 비트가 뒤집히면 p2와 p4 검사가 실패해 신드롬 110₂ = 6이 오류 위치를 가리켜요. 서버의 ECC 메모리, SSD, 통신에서 쓰이고, 전체 패리티 비트를 하나 더하면 2비트 오류도 검출해요(SECDED).<br><sub>Hamming(7,4) puts parity at positions 1, 2 and 4: p1 covers 1·3·5·7, p2 covers 2·3·6·7 and p4 covers 4·5·6·7, each with even parity. Data 1011 becomes 0110011; if bit 6 flips, the p2 and p4 checks fail and the syndrome 110₂ = 6 points at the error. It is used in ECC server memory, SSDs and links, and one extra overall parity bit adds double-error detection (SECDED).</sub> |

## CPU의 동작 · How the CPU works

명령어 하나가 실행되는 과정과 그것을 빠르게 만드는 기법들이에요.  
*How one instruction runs, and the tricks that make it fast.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **폰 노이만 구조**<br><sub>Von Neumann architecture</sub> | 명령어와 데이터를 같은 메모리에 두고, CPU가 버스를 통해 하나씩 가져와 실행하는 구조예요. 오늘날 거의 모든 컴퓨터의 기본이에요.<br><sub>Instructions and data share one memory, and the CPU fetches them over a bus one at a time; nearly every computer works this way.</sub> | CPU는 빨라졌지만 메모리와 버스는 상대적으로 느려서 병목이 생겨요. 캐시·프리페치가 이 문제를 줄이기 위해 존재해요.<br><sub>CPUs got fast while memory and buses lagged, creating a bottleneck that caches and prefetching exist to hide.</sub> |
| **명령어 사이클**<br><sub>Instruction cycle</sub> | CPU는 PC가 가리키는 명령어를 가져오고(인출), 해석하고(해독), 실행한 뒤 다음 명령으로 넘어가는 일을 반복해요.<br><sub>The CPU fetches the instruction PC points to, decodes it, executes it and moves to the next, over and over.</sub> | 3GHz CPU는 1초에 이 사이클을 30억 번 돌려요. 디버거의 "한 줄 실행"이 이 반복을 사람 속도로 보는 거예요.<br><sub>A 3 GHz CPU turns this loop three billion times a second; stepping in a debugger watches it at human speed.</sub> |
| **파이프라인**<br><sub>Pipelining</sub> | 명령어 처리를 여러 단계로 나눠, 앞 명령이 다음 단계로 가면 바로 다음 명령을 시작해요. 동시에 여러 명령이 서로 다른 단계에 있어요.<br><sub>Instruction processing is split into stages so a new instruction starts as soon as the previous one moves on, with several in flight at once.</sub> | 명령 하나의 시간은 같지만 처리량이 크게 늘어요. 최신 CPU는 여기에 여러 명령을 동시에 내보내는 슈퍼스칼라, 순서를 바꾸는 비순차 실행까지 더해요.<br><sub>Latency per instruction is unchanged but throughput soars. Modern CPUs add superscalar issue and out-of-order execution on top.</sub> |
| **파이프라인 해저드**<br><sub>Pipeline hazards</sub> | 다음 명령이 앞 명령의 결과를 필요로 하면 파이프라인이 기다려야 해요(데이터 해저드). 포워딩으로 결과를 지름길로 넘겨 줄여요.<br><sub>When an instruction needs the result of the one before, the pipeline must wait (a data hazard); forwarding passes the result via a shortcut.</sub> | 컴파일러가 명령 순서를 바꿔(스케줄링) 기다림을 줄여요. 의존성이 긴 계산 사슬은 병렬화가 어려운 이유이기도 해요.<br><sub>Compilers reorder instructions to hide stalls. Long dependency chains are also why some code resists parallelism.</sub> |
| **분기 예측**<br><sub>Branch prediction</sub> | if문의 결과가 나오기 전에 CPU가 어느 쪽일지 예측해서 미리 실행해요. 틀리면 미리 한 일을 버리고 다시 해요.<br><sub>Before an if is resolved, the CPU guesses the outcome and runs ahead; a wrong guess means discarding that work.</sub> | 정렬된 데이터로 반복하면 예측이 잘 맞아 빨라져요(유명한 StackOverflow 질문). 스펙터 같은 보안 취약점도 이 추측 실행에서 나왔어요.<br><sub>Loops over sorted data run faster because predictions hit (a famous Stack Overflow question). Spectre-style attacks came from this speculation.</sub> |
| **CISC vs RISC**<br><sub>CISC vs RISC</sub> | CISC(x86)는 복잡하고 길이가 다양한 명령어를, RISC(ARM, RISC-V)는 단순하고 길이가 같은 명령어를 써요.<br><sub>CISC (x86) uses complex, variable-length instructions; RISC (ARM, RISC-V) uses simple, fixed-length ones.</sub> | 애플 실리콘·스마트폰은 ARM, 대부분의 서버·PC는 x86이에요. 도커 이미지와 네이티브 라이브러리는 아키텍처(amd64/arm64)를 맞춰야 해요.<br><sub>Apple silicon and phones are ARM; most servers and PCs are x86. Docker images and native libraries must match the architecture (amd64/arm64).</sub> |
| **멀티코어와 암달의 법칙**<br><sub>Multicore · Amdahl’s law</sub> | 코어를 늘려도 나눌 수 없는 순차 구간이 있으면 속도 향상에 한계가 있어요. 순차 비율이 20%면 최대 5배까지예요.<br><sub>Adding cores can only speed up the parallel part; with 20% serial work, the best possible speed-up is 5×.</sub> | 스레드를 늘리기 전에 락 경합·순차 처리 구간을 먼저 줄이세요. 서버는 요청 단위로 나눠 코어를 잘 활용해요.<br><sub>Before adding threads, cut lock contention and serial sections. Servers use cores well by splitting work per request.</sub> |
| **멀티코어 프로세서 구조**<br><sub>Multicore processor design</sub> | 한 칩에 코어 여러 개가 들어 있고, 코어마다 전용 L1·L2 캐시를, 모두가 나눠 쓰는 L3와 이를 잇는 연결망을 가져요.<br><sub>A chip holding several cores, each with private L1 and L2 caches, plus a shared L3 and the interconnect that ties them together.</sub> | 멀티코어 칩의 각 코어는 명령어를 따로 실행하는 완전한 CPU이고, 코어마다 전용 L1 명령·데이터 캐시(각 32~64 KB)와 L2 캐시(1~2 MB)를 가져요. 큰 L3 캐시는 여러 조각으로 나뉘어 링이나 메시 연결망에 붙어 있고 모든 코어가 함께 써요. 접근 지연은 대략 L1 4사이클, L2 14사이클, L3 50사이클, DRAM 250사이클 이상이라 아래로 갈수록 크게 느려져요. 한 코어가 데이터를 쓰면, 같은 캐시 줄을 가진 다른 코어의 복사본은 연결망을 통해 무효화되어 모든 코어가 같은 값을 보게 돼요(MESI 같은 캐시 일관성 프로토콜). 코어 하나가 하드웨어 스레드 두 개를 번갈아 실행하는 SMT(하이퍼스레딩)는 한 스레드가 메모리를 기다릴 때 노는 실행 유닛을 채워 15~30% 정도 처리량을 올려요. 요즘 칩은 크고 빠른 P코어와 작고 전력 효율이 좋은 E코어를 섞고, 운영체제 스케줄러가 일의 성격에 맞게 배치해요. 코어가 수십 개인 서버 칩은 링 대신 메시를, AMD는 여러 칩렛을 한 패키지로 묶어요. 먼 L3 조각이나 다른 소켓의 메모리는 더 느리기 때문에(NUMA) 스레드를 데이터 가까이에 두는 것이 중요해요.<br><sub>Each core on a multicore chip is a complete CPU running its own instruction stream, with private L1 instruction and data caches (32–64 KB each) and an L2 cache (1–2 MB). A large L3 is split into slices attached to a ring or mesh interconnect and shared by every core. Latency rises steeply down the hierarchy: roughly 4 cycles for L1, 14 for L2, 50 for L3 and 250 or more for DRAM. When one core writes, copies of that cache line in other cores are invalidated over the interconnect so every core sees the same value (a coherence protocol such as MESI). Simultaneous multithreading (SMT, Hyper-Threading) lets one core interleave two hardware threads, filling execution units that would sit idle while one thread waits on memory and raising throughput by roughly 15–30%. Recent chips mix big, fast P-cores with small, power-efficient E-cores, and the OS scheduler places work accordingly. Server chips with dozens of cores replace the ring with a mesh, and AMD packages several chiplets together. Distant L3 slices and memory on another socket are slower (NUMA), so keeping threads near their data matters.</sub> |
| **CPU 성능 식**<br><sub>The CPU performance equation</sub> | CPU 시간 = 명령어 수 × 명령당 사이클(CPI) × 클럭 주기. 셋 중 하나만 보고 성능을 판단하면 틀려요.<br><sub>CPU time = instruction count × cycles per instruction (CPI) × clock period. Judging performance by one factor alone misleads.</sub> | 10⁹개 명령, CPI 2, 2 GHz면 1초예요. 명령어 수는 알고리즘·컴파일러·ISA가, CPI는 파이프라인·캐시 미스·분기 예측이, 클럭은 공정과 전력이 좌우해요. 3 GHz지만 CPI 3.5인 CPU는 2 GHz·CPI 2인 CPU보다 느려요(1.17초 vs 1초). 전력 벽으로 클럭 상승이 멈추자 설계는 멀티코어와 IPC 향상으로 방향을 틀었어요.<br><sub>10⁹ instructions at CPI 2 on a 2 GHz clock take 1 s. Instruction count depends on the algorithm, compiler and ISA; CPI on the pipeline, cache misses and branch prediction; the clock on process and power. A 3 GHz CPU with CPI 3.5 loses to a 2 GHz one with CPI 2 (1.17 s vs 1 s). When the power wall halted clock growth, designs turned to multicore and higher IPC.</sub> |
| **명령어 형식 (MIPS)**<br><sub>Instruction formats (MIPS)</sub> | 32비트 명령어를 연산 코드(op)와 레지스터·상수·주소 필드로 나눈 약속이에요. MIPS는 R, I, J 세 형식을 써요.<br><sub>A convention splitting a 32-bit instruction into an opcode and register, constant or address fields. MIPS uses three formats: R, I and J.</sub> | R형은 op 6 · rs 5 · rt 5 · rd 5 · shamt 5 · funct 6비트로, add $t0, $s1, $s2 같은 레지스터 연산을 담아요. I형은 16비트 상수를 담아 lw $t0, 32($s3) 같은 메모리 접근과 즉시 연산에, J형은 26비트 주소로 점프에 써요. RISC는 길이가 고정이라 해독이 단순하고 파이프라인에 유리하고, x86은 1~15바이트 가변 길이예요. RISC-V도 비슷한 형식을 써요.<br><sub>R-type is op 6 · rs 5 · rt 5 · rd 5 · shamt 5 · funct 6 bits and holds register operations like add $t0, $s1, $s2. I-type carries a 16-bit constant for memory access and immediates such as lw $t0, 32($s3), and J-type a 26-bit jump address. Fixed length keeps RISC decoding simple and pipeline-friendly, while x86 instructions span 1–15 bytes. RISC-V uses similar formats.</sub> |
| **주소 지정 방식**<br><sub>Addressing modes</sub> | 명령어가 피연산자를 어디서 찾는지 정하는 규칙이에요. 즉시, 레지스터, 직접, 간접, 베이스 + 오프셋, PC 상대 등이 있어요.<br><sub>Rules for where an instruction finds its operands: immediate, register, direct, indirect, base plus offset, PC-relative and more.</sub> | 즉시(#5)와 레지스터(R2)는 메모리에 가지 않고, 직접([200])과 레지스터 간접([R2])은 주소를 정해 메모리를 읽어요([R2]는 C의 \*p). 베이스 + 오프셋(8(R3))은 배열 원소, 구조체 필드, 스택 변수 접근에 쓰이고, PC 상대는 분기와 위치 독립 코드(PIC)를 가능하게 해요. RISC는 몇 가지만 두고, x86은 [base + index×4 + disp]처럼 복잡한 조합까지 지원해요.<br><sub>Immediate (#5) and register (R2) modes never touch memory, while direct ([200]) and register indirect ([R2], like C’s \*p) compute an address and read memory. Base plus offset (8(R3)) reaches array elements, struct fields and stack slots, and PC-relative addressing enables branches and position-independent code. RISC keeps only a few modes; x86 even supports combinations like [base + index×4 + disp].</sub> |
| **단일 사이클 데이터패스**<br><sub>A single-cycle datapath</sub> | 명령어가 PC → 명령어 메모리 → 레지스터 파일 → ALU → 데이터 메모리 → 레지스터로 흘러가는 길과, 그 길을 조종하는 제어 신호예요.<br><sub>The path an instruction travels, PC → instruction memory → register file → ALU → data memory → registers, plus the control signals that steer it.</sub> | lw $t0, 32($s3)는 PC로 명령어를 읽고(PC + 4), $s3을 읽고 32를 부호 확장한 뒤, ALU가 주소를 계산해 데이터 메모리를 읽고, 그 값을 $t0에 써요. 제어 유닛은 op에 따라 RegWrite, ALUSrc, MemRead, MemToReg 같은 신호로 멀티플렉서와 쓰기를 조절해요. 단일 사이클 설계는 가장 긴 명령에 클럭을 맞춰야 해서 느리고, 그래서 단계를 겹치는 파이프라인으로 발전해요.<br><sub>For lw $t0, 32($s3), the CPU fetches at PC (and computes PC + 4), reads $s3 and sign-extends 32, lets the ALU compute the address, reads data memory and writes the value into $t0. The control unit drives signals like RegWrite, ALUSrc, MemRead and MemToReg from the opcode to set multiplexers and write enables. A single-cycle design must clock at its slowest instruction, which motivates pipelining.</sub> |
| **비순차 실행**<br><sub>Out-of-order execution</sub> | 앞 명령이 캐시 미스 등으로 멈춰도, 피연산자가 준비된 뒤쪽 명령을 먼저 실행해 빈 시간을 메우는 기법이에요.<br><sub>When an earlier instruction stalls, for example on a cache miss, later instructions whose operands are ready run first to fill the gap.</sub> | LOAD가 미스로 오래 걸리면 순서대로 실행하는 CPU는 상관없는 MUL, SUB까지 기다려요. 비순차 CPU는 이들을 먼저 실행해 전체 시간을 줄이고, 재정렬 버퍼(ROB)로 결과 확정은 원래 순서대로 해서 정확한 예외를 지켜요. 레지스터 리네이밍은 같은 레지스터 이름 때문에 생기는 가짜 의존(WAR, WAW)을 없애요. 현대 고성능 코어는 수백 개 명령을 동시에 들고 있고, Spectre 같은 취약점도 이 투기적 실행에서 나왔어요.<br><sub>If a LOAD misses the cache, an in-order CPU makes the unrelated MUL and SUB wait too; an out-of-order CPU runs them early and finishes sooner, while a reorder buffer (ROB) retires results in program order to keep exceptions precise. Register renaming removes false dependencies (WAR, WAW) caused by reused register names. Modern high-end cores keep hundreds of instructions in flight, and attacks like Spectre grew out of this speculative execution.</sub> |
| **SIMD 벡터 명령**<br><sub>SIMD vector instructions</sub> | 명령 하나로 여러 데이터(레인)를 동시에 처리하는 명령어예요. 128비트 레지스터 하나에 float 4개를 담아 한 번에 더해요.<br><sub>Instructions that process several data lanes at once, such as adding four floats held in one 128-bit register.</sub> | 배열 8개를 더할 때 스칼라는 ADD 8번, SSE의 VADDPS는 4개씩 2번이면 끝나요. AVX2(256비트), AVX-512, ARM NEON/SVE로 레인 수가 늘었어요. 보통은 컴파일러의 자동 벡터화(-O3)에 맡기는데, 연속된 메모리와 분기 없는 루프일수록 잘 돼요. 이미지 처리, simdjson, ML 추론, 영상 코덱이 SIMD로 빨라지고, GPU의 SIMT는 같은 생각을 수천 스레드로 확장한 거예요.<br><sub>Adding eight array elements takes eight scalar ADDs but only two SSE VADDPS instructions, four lanes each; AVX2 (256-bit), AVX-512 and ARM NEON/SVE widen the lanes further. Usually the compiler auto-vectorizes at -O3, which works best on contiguous data and branch-free loops. Image processing, simdjson, ML inference and video codecs speed up with SIMD, and a GPU’s SIMT stretches the idea to thousands of threads.</sub> |

## 메모리 계층과 캐시 · Memory hierarchy and caches

빠른 메모리는 작고 비싸서 여러 층으로 나눠 써요.  
*Fast memory is small and expensive, so it comes in layers.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **메모리 계층 구조**<br><sub>Memory hierarchy</sub> | 레지스터 → L1·L2·L3 캐시 → RAM → SSD → HDD 순으로 느려지고, 커지고, 싸져요.<br><sub>Registers, then L1/L2/L3 caches, RAM, SSD and HDD: each level is slower, larger and cheaper.</sub> | "L1 접근이 1초라면 RAM은 5분, SSD는 며칠"이라는 감각을 가지면 어디를 최적화할지 보여요.<br><sub>Think “if L1 took one second, RAM would take five minutes and SSD days” to see where optimization pays.</sub> |
| **캐시와 캐시 라인**<br><sub>Cache · Cache lines</sub> | CPU는 메모리를 64바이트 묶음(캐시 라인)으로 가져와 캐시에 둬요. 한 번 미스가 나면 주변 데이터는 히트가 돼요.<br><sub>The CPU pulls memory in 64-byte chunks (cache lines), so after one miss the neighbouring data hits.</sub> | 배열이 링크드 리스트보다 실제로 훨씬 빠른 이유예요. 데이터를 연속으로 배치하는 게 알고리즘 복잡도만큼 중요해요.<br><sub>This is why arrays beat linked lists in practice; laying data out contiguously matters as much as big-O.</sub> |
| **지역성**<br><sub>Locality</sub> | 최근 쓴 데이터를 곧 다시 쓰고(시간 지역성), 가까운 데이터를 이어서 쓰는(공간 지역성) 경향이에요. 캐시는 이걸 믿고 동작해요.<br><sub>Programs tend to reuse recent data (temporal locality) and touch nearby data next (spatial locality); caches bet on it.</sub> | 2차원 배열은 행 순서로 돌고, 구조체 배열(AoS)과 배열 구조체(SoA) 중 접근 패턴에 맞게 고르세요.<br><sub>Iterate 2D arrays row by row, and choose array-of-structs or struct-of-arrays to match your access pattern.</sub> |
| **거짓 공유**<br><sub>False sharing</sub> | 서로 다른 코어가 다른 변수를 쓰는데, 두 변수가 같은 캐시 라인에 있어서 캐시가 계속 서로를 무효화하는 현상이에요.<br><sub>Cores writing different variables keep invalidating each other because those variables share one cache line.</sub> | 멀티스레드 카운터·큐가 이유 없이 느리면 의심하세요. 패딩이나 @Contended, 스레드별 카운터로 해결해요.<br><sub>Suspect it when multithreaded counters or queues are inexplicably slow; fix with padding, @Contended or per-thread counters.</sub> |
| **캐시 매핑 방식**<br><sub>Cache mapping</sub> | 메모리 블록이 캐시의 어느 줄에 들어갈 수 있는지 정하는 방식이에요. 직접 사상, n-way 집합 연관, 완전 연관이 있어요.<br><sub>Rules for which cache lines a memory block may occupy: direct-mapped, n-way set associative or fully associative.</sub> | 주소는 태그 \| 인덱스 \| 오프셋으로 나뉘어요. 직접 사상은 블록마다 들어갈 줄이 하나라, 같은 줄에 대응하는 블록 0과 8을 번갈아 읽으면 매번 서로를 쫓아내요(충돌 미스). 2-way 집합 연관이면 둘이 한 집합에 공존해 처음 두 번만 미스예요. 완전 연관은 어디든 넣을 수 있지만 모든 태그를 동시에 비교해야 해 비싸요. 실제 L1은 보통 8-way이고, 미스는 처음·용량·충돌(3C)로 나눠요.<br><sub>An address splits into tag \| index \| offset. In a direct-mapped cache each block has exactly one line, so alternating between blocks 0 and 8, which share a line, evicts every time (conflict misses). With 2-way set associativity both fit in one set and only the first two accesses miss. A fully associative cache accepts any line but must compare every tag at once. Real L1 caches are typically 8-way, and misses are classed as compulsory, capacity or conflict (the 3 Cs).</sub> |
| **캐시 쓰기 정책**<br><sub>Cache write policies</sub> | 쓰기를 캐시와 메모리에 동시에 반영할지(라이트 스루), 캐시에만 하고 나중에 내릴지(라이트 백) 정하는 방식이에요.<br><sub>Whether a write updates cache and memory together (write-through) or only the cache, to be flushed later (write-back).</sub> | 라이트 스루는 x = 1, 2, 3을 쓸 때마다 메모리에도 써서 단순하고 항상 최신이지만 메모리 쓰기가 많아요(쓰기 버퍼로 지연을 숨겨요). 라이트 백은 캐시만 고치고 더티 비트를 켠 뒤, 줄이 쫓겨날 때 한 번만 메모리에 써요. 쓰기 미스 때 줄을 가져오는 write-allocate는 보통 라이트 백과 짝을 이뤄요. 현대 CPU 캐시는 대부분 라이트 백이고, 다른 코어·DMA와의 일관성은 별도 프로토콜이 맡아요.<br><sub>Write-through sends x = 1, 2, 3 to memory on every write: simple and always current, but heavy on memory traffic (a write buffer hides the delay). Write-back updates only the cache, sets a dirty bit and writes memory once when the line is evicted. Write-allocate, fetching the line on a write miss, usually pairs with write-back. Modern CPU caches are mostly write-back, and a separate coherence protocol keeps other cores and DMA consistent.</sub> |
| **캐시 일관성 (MESI)**<br><sub>Cache coherence (MESI)</sub> | 코어마다 캐시가 따로 있어도 같은 주소는 같은 값으로 보이게 하는 규칙이에요. MESI 프로토콜이 대표적이에요.<br><sub>Rules that make every core see a single value per address despite private caches; the MESI protocol is the classic example.</sub> | 각 캐시 줄은 M(수정됨), E(독점), S(공유), I(무효) 중 하나예요. Core 1만 읽으면 E, Core 2도 읽으면 둘 다 S, Core 1이 쓰면 다른 복사본을 무효화해 Core 2는 I, Core 1은 M이 되고, Core 2가 다시 읽으면 Core 1이 값을 넘기며 둘 다 S가 돼요. 스누핑 버스나 디렉터리로 구현하고, 여러 코어가 같은 줄을 번갈아 쓰면 무효화가 오가며 느려지는 거짓 공유가 생겨요.<br><sub>Each cache line is Modified, Exclusive, Shared or Invalid. If only Core 1 reads x it is E; when Core 2 reads too both are S; when Core 1 writes, other copies are invalidated, so Core 2 goes I and Core 1 M; when Core 2 reads again, Core 1 supplies the data and both return to S. It is implemented with bus snooping or directories, and cores taking turns writing one line bounce invalidations, which is false sharing.</sub> |

## 입출력과 저장 장치 · I/O and storage

데이터를 옮기고 오래 보관하는 장치들이에요.  
*Devices that move and keep data.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **DMA**<br><sub>DMA · Direct memory access</sub> | 대량 데이터 전송을 CPU 대신 전용 컨트롤러가 메모리로 직접 옮기고, 끝나면 인터럽트로 알려요.<br><sub>A dedicated controller moves bulk data straight into memory instead of the CPU, raising an interrupt when done.</sub> | 덕분에 CPU는 디스크·네트워크 전송 중에도 다른 일을 해요. 제로 카피(sendfile) 같은 고성능 I/O 기법의 바탕이에요.<br><sub>The CPU keeps working during disk and network transfers; it underpins zero-copy I/O like sendfile.</sub> |
| **SSD vs HDD**<br><sub>SSD vs HDD</sub> | HDD는 원판을 돌리고 헤드를 움직여 읽어서 흩어진 데이터에 느리고, SSD는 플래시 칩을 병렬로 읽어 수천 배 빨라요.<br><sub>HDDs spin platters and move a head, so scattered reads are slow; SSDs read flash chips in parallel and are thousands of times faster.</sub> | DB·서버 디스크는 SSD가 기본이에요. SSD는 쓰기 횟수에 수명이 있고, 클라우드 디스크는 IOPS 한도를 확인하세요.<br><sub>SSDs are the default for databases and servers. They wear with writes, and cloud disks have IOPS limits to check.</sub> |
| **CPU vs GPU**<br><sub>CPU vs GPU</sub> | CPU는 복잡한 일을 빠르게 하는 큰 코어 몇 개, GPU는 같은 단순 계산을 대량으로 하는 작은 코어 수천 개예요.<br><sub>A CPU has a few big cores for complex work; a GPU has thousands of small ones for the same simple maths on lots of data.</sub> | 딥러닝의 행렬 곱, 그래픽, 영상 인코딩에 GPU를 써요. 데이터를 GPU로 옮기는 비용이 있어서 작은 작업은 오히려 손해예요.<br><sub>Deep learning’s matrix maths, graphics and video encoding run on GPUs. Copying data to the GPU costs time, so tiny jobs lose.</sub> |
| **RAID**<br><sub>RAID</sub> | 여러 디스크를 하나처럼 묶어 속도(스트라이핑)나 안전(미러링, 패리티)을 얻는 방법이에요.<br><sub>Grouping several disks to act as one, gaining speed (striping) or safety (mirroring, parity).</sub> | RAID 0은 데이터를 나눠 써서 빠르지만 하나만 고장 나도 전부 잃고, RAID 1은 똑같이 복제해 용량이 절반이에요. RAID 5는 패리티를 디스크마다 돌아가며 저장해 용량 (n−1)/n으로 한 개 고장을 견디고, 고장 난 블록은 A3 = A1 ⊕ A2 ⊕ Ap처럼 XOR로 다시 계산해요. RAID 6은 두 개까지, RAID 10은 미러 위에 스트라이프를 얹어요. RAID는 백업이 아니라서 실수로 지운 파일이나 랜섬웨어는 그대로 복제돼요.<br><sub>RAID 0 splits data across disks for speed but loses everything if one fails; RAID 1 mirrors at half capacity. RAID 5 rotates parity across disks for (n−1)/n capacity and survives one failure, rebuilding lost blocks with XOR, e.g. A3 = A1 ⊕ A2 ⊕ Ap. RAID 6 tolerates two failures and RAID 10 stripes across mirrors. RAID is not a backup: accidental deletes and ransomware are faithfully replicated.</sub> |
