## App Router 라우팅 · App Router routing

폴더와 파일 이름으로 경로와 화면 구조를 정의하는 App Router의 규칙이에요.  
*The App Router conventions that define paths and screen structure through folders and file names.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **파일 기반 라우팅**<br><sub>File-based routing</sub> | App Router에서는 app 폴더의 구조가 곧 URL이에요. 폴더에 page.tsx가 있어야 그 경로가 화면으로 공개돼요.<br><sub>In the App Router, the structure of the app folder is the URL, and a folder becomes a public page only when it contains page.tsx.</sub> | app/about/page.tsx는 /about, app/blog/[slug]/page.tsx는 /blog/hello 같은 동적 경로가 돼요. page.tsx의 default export가 그 경로의 화면이고 기본적으로 서버 컴포넌트예요. app/api/hello/route.ts처럼 route.ts를 두면 화면 대신 HTTP 요청에 응답하는 API 엔드포인트가 돼요. 같은 폴더에 컴포넌트나 유틸 파일을 함께 둬도 page가 아니면 공개되지 않아서 관련 파일을 가까이 모아 둘 수 있어요. layout, loading, error처럼 정해진 특수 파일 이름이 각자의 역할을 해요.<br><sub>app/about/page.tsx becomes /about, and app/blog/[slug]/page.tsx a dynamic route such as /blog/hello. The default export of page.tsx is that route’s screen, a server component by default. A route.ts, as in app/api/hello/route.ts, becomes an API endpoint that answers HTTP requests instead of rendering a page. Components and utilities can sit in the same folder without becoming public unless they are pages, keeping related files together. Special file names such as layout, loading and error each have a fixed role.</sub> |
| **레이아웃**<br><sub>Layouts</sub> | layout.tsx는 여러 페이지가 공유하는 UI 틀이에요. 폴더마다 겹겹이 중첩되고, 페이지를 옮겨 다녀도 다시 렌더되지 않아 상태가 유지돼요.<br><sub>layout.tsx is a UI shell shared by several pages; layouts nest folder by folder and do not re-render during navigation, so their state persists.</sub> | 루트 app/layout.tsx는 필수이며 <html>과 <body>, 공통 내비게이션을 담아 모든 페이지를 감싸요. app/dashboard/layout.tsx를 두면 그 아래 페이지들에 Sidebar가 한 겹 더 추가돼요. /dashboard에서 /dashboard/settings로 이동하면 page 부분만 바뀌고 레이아웃은 다시 렌더되지 않아서, 사이드바의 입력값이나 스크롤 위치가 그대로 남아요. 이동할 때마다 새로 만들어야 하는 경우엔 template.tsx를 써요. 레이아웃은 params는 받지만 searchParams는 받지 않고, Next 16에서는 공유 레이아웃을 프리페치 때 한 번만 내려받아요.<br><sub>The root app/layout.tsx is required and wraps every page with <html>, <body> and shared navigation. Adding app/dashboard/layout.tsx layers a Sidebar onto every page below it. Navigating from /dashboard to /dashboard/settings swaps only the page, and the layout does not re-render, so the sidebar keeps its inputs and scroll position. When something must be recreated on every navigation, use template.tsx. Layouts receive params but not searchParams, and in Next 16 shared layouts download only once during prefetching.</sub> |
| **동적 라우트**<br><sub>Dynamic routes</sub> | [slug] 같은 대괄호 폴더는 URL의 그 자리 값을 params로 받아요. generateStaticParams로 가능한 값을 알려 주면 빌드 때 미리 만들어요.<br><sub>Bracketed folders such as [slug] receive that part of the URL as params; listing possible values in generateStaticParams prebuilds them at build time.</sub> | /blog/hello-next 요청이 오면 app/blog/[slug]/page.tsx가 실행되고, Next 15부터 Promise가 된 params를 await해 slug를 꺼내요. 해당 글이 없으면 notFound()를 불러 404 화면을 보여줘요. generateStaticParams가 글 목록의 slug들을 돌려주면 그 페이지들은 빌드 때 HTML로 미리 생성돼요. [...slug]는 /docs/a/b/c처럼 여러 단계를 배열로 받고, [[...slug]]는 세그먼트가 없는 /docs까지 매칭해요. ?q= 같은 쿼리는 searchParams로 받는데, 이를 쓰면 그 페이지는 동적 렌더링이 돼요.<br><sub>A request for /blog/hello-next runs app/blog/[slug]/page.tsx, which awaits params, a promise since Next 15, to read slug. If the post does not exist, notFound() shows the 404 screen. When generateStaticParams returns the list of slugs, those pages are generated as HTML at build time. [...slug] captures several levels as an array, as in /docs/a/b/c, and [[...slug]] also matches /docs with no segment. Query strings such as ?q= arrive as searchParams, and using them makes the page dynamically rendered.</sub> |
| **Link와 내비게이션**<br><sub>Link and navigation</sub> | <Link>는 새로고침 없이 클라이언트에서 페이지를 이동하고, 화면에 보이는 링크의 대상을 미리 가져와(prefetch) 클릭하면 바로 열려요.<br><sub><Link> navigates on the client without reloading, and prefetches destinations that appear in the viewport so clicks open instantly.</sub> | 평범한 <a>로 이동하면 페이지 전체를 다시 받고 JS도 다시 실행되지만, <Link href="/blog/hello">는 바뀐 세그먼트만 서버에서 받아 교체하고 공유 레이아웃은 그대로 둬요. 링크가 화면에 들어오면 이동할 페이지의 데이터를 미리 받아 두어서 클릭하는 순간 열려요. Next 16은 이미 캐시된 부분은 빼고 필요한 부분만 프리페치해요. 코드에서 이동할 땐 클라이언트 컴포넌트에서 useRouter().push를, 현재 경로와 쿼리는 usePathname과 useSearchParams로 읽어요. 서버에서는 redirect()를 써요.<br><sub>A plain <a> reloads the whole page and reruns JavaScript, whereas <Link href="/blog/hello"> fetches and swaps only the changed segments, keeping shared layouts. When a link enters the viewport, its destination’s data is fetched ahead so the page opens the moment it is clicked, and Next 16 prefetches only what is not already cached. To navigate in code, client components use useRouter().push, and usePathname and useSearchParams read the current path and query. On the server, use redirect().</sub> |
| **loading·error·not-found**<br><sub>loading, error and not-found</sub> | 폴더에 loading.tsx, error.tsx, not-found.tsx를 두면 Next.js가 페이지를 Suspense와 Error Boundary로 자동으로 감싸요.<br><sub>loading.tsx, error.tsx and not-found.tsx in a folder make Next.js wrap the page in Suspense and an error boundary automatically.</sub> | Next.js는 page를 layout > error > loading 순서로 감싸요. loading.tsx는 Suspense의 fallback이 되어 데이터를 기다리는 동안 바로 보여요. error.tsx는 Error Boundary가 되어 오류가 난 세그먼트만 대체 화면으로 바꾸고 레이아웃은 살려 두며, reset()으로 다시 시도할 수 있어요 · 이벤트를 다뤄야 해서 반드시 클라이언트 컴포넌트예요. 코드에서 notFound()를 부르면 가장 가까운 not-found.tsx가 404 화면으로 보여요. 루트 레이아웃 자체의 오류는 global-error.tsx로 잡아요.<br><sub>Next.js wraps a page as layout > error > loading. loading.tsx becomes the Suspense fallback, shown immediately while data loads. error.tsx becomes an error boundary that replaces only the failing segment while keeping the layout, with reset() to retry; it must be a client component because it handles events. Calling notFound() in code renders the nearest not-found.tsx as the 404 screen. Errors in the root layout itself are caught by global-error.tsx.</sub> |
| **라우트 그룹·병렬·가로채기 라우트**<br><sub>Route groups, parallel and intercepting routes</sub> | (그룹) 폴더는 URL에 나타나지 않고, @슬롯은 한 화면에 여러 페이지를 동시에, (.) 가로채기는 같은 URL을 모달로 보여줘요.<br><sub>Folders in (parentheses) stay out of the URL, @slots render several pages at once, and (.) intercepting routes show the same URL as a modal.</sub> | (marketing)/about과 (shop)/cart는 URL이 /about, /cart이지만 영역마다 다른 레이아웃을 줄 수 있어요. \_components처럼 밑줄로 시작하는 폴더는 라우팅에서 빠져 컴포넌트를 정리해 두기 좋아요. @modal 슬롯을 두면 레이아웃이 { children, modal }을 받아 두 페이지를 함께 그려요(병렬 라우트). @modal/(.)photo/[id]는 목록에서 사진을 누를 때는 모달로 가로채 보여주고, 링크를 새로고침하거나 공유하면 photo/[id] 전체 페이지로 열려요. Next 16부터 병렬 라우트 슬롯에는 default.tsx가 필수예요.<br><sub>(marketing)/about and (shop)/cart map to /about and /cart while giving each area its own layout. Folders starting with an underscore, such as \_components, are excluded from routing, handy for organizing components. A @modal slot makes the layout receive { children, modal } and render both pages together: parallel routes. @modal/(.)photo/[id] intercepts clicks from the list to show a modal, while refreshing or sharing the link opens the full photo/[id] page. Since Next 16, parallel route slots require a default.tsx.</sub> |
| **proxy(미들웨어)**<br><sub>The proxy (middleware)</sub> | proxy.ts는 요청이 페이지나 API에 닿기 전에 먼저 실행되어 리다이렉트·리라이트·헤더 수정을 해요. Next 16에서 middleware.ts의 새 이름이에요.<br><sub>proxy.ts runs before requests reach pages or APIs, redirecting, rewriting and editing headers; it is Next 16’s new name for middleware.ts.</sub> | export function proxy(req)는 req.cookies와 req.nextUrl.pathname을 읽어, 세션 쿠키 없이 /dashboard에 오면 NextResponse.redirect로 /login에 보내고 아니면 NextResponse.next()로 통과시켜요. rewrite로 URL은 그대로 두고 다른 경로를 보여줄 수도 있고, A/B 테스트나 언어 감지에 쓰여요. config.matcher로 실행할 경로를 좁히고, 모든 요청을 느리게 하지 않도록 무거운 작업은 피해요. proxy.ts는 Node.js 런타임에서 돌아요. 무엇보다 proxy는 빠른 1차 관문일 뿐이라 데이터 접근 지점에서 권한을 다시 확인해야 해요.<br><sub>export function proxy(req) reads req.cookies and req.nextUrl.pathname, redirecting visitors without a session cookie from /dashboard to /login with NextResponse.redirect and letting others through with NextResponse.next(). rewrite serves another path while keeping the URL, useful for A/B tests and language detection. config.matcher narrows where it runs, and heavy work should be avoided because it slows every request. proxy.ts runs on the Node.js runtime. Above all, it is only a quick first gate, so authorization must be checked again where data is accessed.</sub> |

## 렌더링 전략 · Rendering strategies

HTML을 언제 어디서 만들지, 그리고 정적·동적·스트리밍·하이드레이션이 어떻게 맞물리는지예요.  
*When and where HTML is made, and how static, dynamic, streaming and hydration fit together.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **CSR·SSR·SSG**<br><sub>CSR, SSR and SSG</sub> | HTML을 브라우저에서(CSR), 요청 때 서버에서(SSR), 빌드 때 미리(SSG) 만드는 세 가지 렌더링 방식이에요. App Router는 페이지마다 알맞은 방식을 골라요.<br><sub>Three ways of producing HTML: in the browser (CSR), on the server per request (SSR) or ahead of time at build (SSG); the App Router picks per route.</sub> | CSR은 빈 HTML을 받은 뒤 JS가 실행되고 데이터를 가져와야 화면이 보여서 첫 화면이 늦고 검색 엔진에 불리해요. SSR은 요청마다 서버에서 최신 데이터로 HTML을 만들어 보내 개인화된 페이지에 알맞아요. SSG는 빌드 때 HTML을 만들어 CDN에서 바로 보내므로 가장 빠르지만 데이터는 빌드 시점 기준이에요. ISR은 SSG 페이지를 정해진 주기나 요청에 따라 다시 만들어 둘의 중간을 줘요. App Router는 페이지가 쿠키·검색어 같은 요청별 데이터를 쓰는지 보고 정적·동적을 스스로 정하고, PPR로 한 페이지 안에서 둘을 섞을 수도 있어요.<br><sub>With CSR, an empty HTML page waits for JavaScript and data before anything appears, slowing the first view and hurting SEO. SSR builds HTML on the server with fresh data for each request, suiting personalized pages. SSG builds HTML at build time and serves it straight from a CDN, the fastest option but with data as of the build. ISR regenerates SSG pages on a schedule or on demand, sitting in between. The App Router chooses static or dynamic per route based on whether it uses request data such as cookies or search params, and PPR can mix both within one page.</sub> |
| **정적 vs 동적 렌더링**<br><sub>Static versus dynamic rendering</sub> | 요청별 데이터를 쓰지 않는 페이지는 빌드 때 한 번 렌더하는 정적 페이지, cookies·headers·searchParams를 쓰면 요청마다 렌더하는 동적 페이지가 돼요.<br><sub>Pages that use no request data render once at build as static pages; reading cookies, headers or searchParams makes a page render per request as a dynamic page.</sub> | 글 목록처럼 모두에게 같은 페이지는 빌드 때 렌더해 CDN에 저장하므로 빠르고 서버 비용이 거의 없어요. 페이지 안에서 await cookies(), await headers(), searchParams처럼 요청마다 달라지는 값을 읽으면 그 페이지는 요청 때 렌더되는 동적 페이지가 돼요. next build 결과에서 ○는 정적, ƒ는 동적 경로이니, 정적이어야 할 페이지가 ƒ라면 어디서 동적 API를 썼는지 찾아요. 동적 API를 트리의 아래쪽 작은 컴포넌트에서 쓰면 정적인 부분이 넓어지고, PPR을 쓰면 정적 셸 안에 동적 부분만 끼워 넣을 수 있어요.<br><sub>Pages that are the same for everyone, such as a post list, render at build and are stored on a CDN: fast, with almost no server cost. Reading per-request values in the page, such as await cookies(), await headers() or searchParams, makes it dynamic, rendered at request time. In next build output ○ marks static routes and ƒ dynamic ones, so a supposedly static page showing ƒ means a dynamic API sneaked in. Using dynamic APIs in small components deep in the tree keeps more of the page static, and PPR slots only the dynamic parts into a static shell.</sub> |
| **ISR과 재검증**<br><sub>ISR and revalidation</sub> | ISR은 정적 페이지를 배포 없이 다시 만드는 방식이에요. 정해진 시간이 지나면 옛 페이지를 먼저 주면서 뒤에서 새로 만들어요.<br><sub>ISR regenerates static pages without redeploying: after a set time, it serves the old page first while rebuilding in the background.</sub> | export const revalidate = 60이면 정적 HTML을 캐시해 두고 60초 동안은 그대로 보내요. 60초가 지난 뒤의 요청에도 기다리게 하지 않고 옛 HTML을 즉시 주면서 백그라운드에서 새 버전을 만들고, 그다음 요청부터 새 HTML이 나가요(stale-while-revalidate). 시간을 기다리지 않고 글을 발행하는 순간 revalidatePath("/blog")나 revalidateTag("posts", "max")로 바로 무효화할 수도 있어요. Next 16부터 revalidateTag는 cacheLife 프로필을 두 번째 인자로 받고, 서버 액션에서 바로 새 값을 읽어야 하면 updateTag를 써요.<br><sub>With export const revalidate = 60, the static HTML is cached and served as is for 60 seconds. A request after that still gets the old HTML immediately while a new version is built in the background, and later requests receive the new HTML: stale-while-revalidate. Instead of waiting, publishing can invalidate right away with revalidatePath("/blog") or revalidateTag("posts", "max"). Since Next 16, revalidateTag takes a cacheLife profile as its second argument, and updateTag provides read-your-writes freshness in server actions.</sub> |
| **스트리밍**<br><sub>Streaming</sub> | 서버가 HTML을 한 번에 보내지 않고 준비된 조각부터 흘려보내요. 느린 데이터가 페이지 전체를 붙잡지 않게 해요.<br><sub>The server sends HTML in pieces as they become ready instead of all at once, so slow data no longer holds the whole page back.</sub> | 상품 정보는 빠르고 리뷰는 3초 걸리는 페이지를 스트리밍 없이 렌더하면 3초 동안 아무것도 보이지 않아요. <Suspense fallback={<Skel />}>로 Reviews를 감싸면 셸과 상품 정보를 먼저 보내고 리뷰 자리에는 스켈레톤을 둬요. 리뷰가 준비되면 같은 HTTP 응답에 이어서 HTML 조각을 흘려보내 스켈레톤을 실제 내용으로 바꿔요. 폴더의 loading.tsx도 페이지 전체를 Suspense로 감싸는 같은 원리예요. 첫 바이트와 첫 화면이 빨라지고, 검색 엔진도 스트리밍된 HTML을 끝까지 읽어요.<br><sub>Rendering a page with fast product info and 3-second reviews without streaming shows nothing for 3 seconds. Wrapping Reviews in <Suspense fallback={<Skel />}> sends the shell and product info first with a skeleton where the reviews go. When reviews are ready, more HTML streams down the same HTTP response and replaces the skeleton. A folder’s loading.tsx applies the same idea to the whole page. Time to first byte and first paint improve, and search engines still read the full streamed HTML.</sub> |
| **하이드레이션**<br><sub>Hydration</sub> | 서버가 보낸 정적인 HTML에 브라우저가 JS를 입혀 클릭할 수 있게 만드는 과정이에요. 서버와 첫 렌더 결과가 다르면 오류가 나요.<br><sub>Hydration is the browser attaching JavaScript to server-rendered static HTML to make it interactive; if the first client render differs from the server, it errors.</sub> | 서버 HTML은 바로 보이지만 JS가 붙기 전까지는 버튼을 눌러도 반응하지 않아요. | **서버·클라이언트 경계**<br><sub>The server/client boundary</sub> | "use client"가 표시하는 지점이 서버와 클라이언트의 경계예요. 경계를 넘는 props는 직렬화할 수 있어야 하고, 경계 아래 import는 모두 브라우저 번들에 들어가요.<br><sub>The point marked "use client" is the server/client boundary: props crossing it must be serializable, and everything imported below it joins the browser bundle.</sub> | 서버 컴포넌트인 page가 클라이언트 컴포넌트 LikeButton에 postId={42} 같은 값은 넘길 수 있지만, onLike={() => …} 같은 일반 함수는 넘길 수 없어요(서버 액션은 예외). Per-post titles and cover images come from generateMetadata, which reads params and fetches data. openGraph data becomes the preview card shown when a link is pasted into chats or social media. Files such as opengraph-image.tsx, sitemap.ts, robots.ts and icon.png in the app folder make Next.js generate the right tags and routes automatically. Layout metadata cascades to child pages, and title.template sets a format such as “%s \| Site name” once.</sub> |
| **번들 최적화**<br><sub>Bundle optimization</sub> | 처음 받는 JS를 줄이면 로딩과 반응 속도가 함께 좋아져요. 동적 import, 작은 클라이언트 경계, 서버 컴포넌트로 무거운 일 옮기기가 핵심이에요.<br><sub>Shipping less first-load JavaScript speeds up both loading and responsiveness; dynamic imports, small client boundaries and moving heavy work to server components are the key levers.</sub> | 차트처럼 무겁고 당장 필요 없는 컴포넌트는 dynamic(() => import("./Chart"))로 분리해 필요할 때 내려받아요. "use client" 파일 아래로 import한 모든 것이 브라우저 번들에 들어가므로, 경계는 버튼 같은 잎 컴포넌트에만 작게 둬요. 마크다운 변환이나 날짜 처리처럼 무거운 라이브러리는 서버 컴포넌트에서 쓰고 결과만 보내면 브라우저 JS는 0KB예요. @next/bundle-analyzer로 어떤 라이브러리가 큰지 눈으로 확인하고, 아이콘·유틸 라이브러리는 필요한 것만 import해요. next build의 First Load JS 크기를 꾸준히 지켜봐요.<br><sub>Heavy components not needed right away, such as charts, split out with dynamic(() => import("./Chart")) and load on demand. Everything imported below a "use client" file joins the browser bundle, so keep boundaries small around leaf components such as buttons. Heavy libraries for markdown conversion or date handling belong in server components, which send only results and cost the browser 0 KB. @next/bundle-analyzer shows which libraries are large, and icon and utility libraries should be imported selectively. Keep an eye on First Load JS in next build output.</sub> |
| **Core Web Vitals**<br><sub>Core Web Vitals</sub> | 로딩(LCP), 반응성(INP), 시각 안정성(CLS)을 재는 구글의 사용자 경험 지표예요. 실제 사용자 데이터로 측정하고 검색 순위에도 영향을 줘요.<br><sub>Google’s user-experience metrics for loading (LCP), responsiveness (INP) and visual stability (CLS), measured on real users and used in search ranking.</sub> | LCP는 가장 큰 콘텐츠(대표 이미지, 제목)가 보이기까지의 시간으로 2.5초 이내가 좋고, 이미지 priority와 스트리밍이 도움이 돼요. INP는 클릭·입력 뒤 다음 화면이 그려지기까지로 200ms 이내가 좋고, JS를 줄이고 긴 작업을 쪼개면 좋아져요. CLS는 읽는 도중 레이아웃이 밀리는 정도로 0.1 이하가 좋고, 이미지 크기 예약과 next/font가 막아 줘요. useReportWebVitals로 실제 사용자의 값을 모아 분석 도구로 보내고, 75번째 백분위수로 판단해요. Lighthouse는 실험실 값, CrUX는 실제 사용자 값이에요.<br><sub>LCP is the time until the largest content, such as a hero image or headline, appears; under 2.5 s is good, helped by image priority and streaming. INP is the delay from a click or input to the next paint; under 200 ms is good, improved by shipping less JavaScript and splitting long tasks. CLS measures layout shifts while reading; 0.1 or less is good, prevented by reserved image sizes and next/font. useReportWebVitals collects real users’ values for analytics, judged at the 75th percentile. Lighthouse reports lab values and CrUX real-user field data.</sub> |

## 빌드, 배포, 운영 · Building, deploying and operating

빌드 결과를 읽는 법, 배포 선택지, 인증과 국제화 같은 실무 패턴, 그리고 두 라우터의 차이예요.

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **빌드와 출력**<br><sub>Builds and output</sub> | next build는 컴파일·타입 검사·사전 렌더를 하고 경로마다 정적(○)·SSG(●)·동적(ƒ) 여부와 크기를 보여줘요.<br><sub>next build compiles, type-checks and prerenders, reporting for each route whether it is static (○), SSG (●) or dynamic (ƒ), along with its size.</sub> | Next 16부터 Turbopack이 기본 번들러라 빌드가 더 빨라졌어요. 결과 표에서 ○는 빌드 때 HTML이 완성된 정적 페이지, ●는 generateStaticParams로 미리 만든 동적 경로, ƒ는 요청마다 서버에서 렌더하는 경로예요. 정적이어야 할 페이지가 ƒ로 나오면 cookies나 searchParams 같은 동적 API를 어디서 썼는지 찾아봐요. output: "standalone"은 실행에 필요한 파일만 모아 작은 Docker 이미지를 만들게 해 줘요. next start로 빌드 결과를 실행해 프로덕션 동작을 확인하고, 린트는 next build가 더 이상 하지 않으니 ESLint나 Biome을 따로 돌려요.<br><sub>Since Next 16, Turbopack is the default bundler and builds are faster. In the output table, ○ marks static pages whose HTML is finished at build, ● dynamic routes prebuilt via generateStaticParams, and ƒ routes rendered on the server per request. A page that should be static but shows ƒ has a dynamic API such as cookies or searchParams somewhere. output: "standalone" gathers only the files needed to run, enabling small Docker images. next start runs the build to check production behavior, and since next build no longer lints, run ESLint or Biome separately.</sub> |
| **배포와 런타임**<br><sub>Deployment and runtimes</sub> | Next.js는 Vercel 같은 관리형 플랫폼, Node 서버, Docker, 정적 내보내기로 배포할 수 있어요. 앱이 쓰는 기능에 따라 선택지가 달라져요.<br><sub>Next.js deploys to managed platforms such as Vercel, Node servers, Docker or static export, with the choice depending on the features the app uses.</sub> | Vercel에 연결하면 git push마다 자동으로 빌드·배포하고 브랜치마다 미리보기 URL을 만들어 줘요. 어디서든 next build 후 next start로 Node 서버를 띄우거나, standalone 출력으로 Docker 이미지를 만들어 AWS·GCP·자체 서버에 올려요. output: "export"는 순수 정적 파일만 만들어 S3나 GitHub Pages에도 올릴 수 있지만, SSR·서버 액션·proxy 같은 서버 기능은 못 써요. 라우트별로 runtime을 "edge"로 정하면 사용자 가까운 곳에서 빠르게 시작하지만 일부 Node API를 쓸 수 없어요. 자체 호스팅에서는 이미지 최적화와 ISR 캐시 설정이 더 필요해요.<br><sub>Connected to Vercel, every git push builds and deploys automatically, with a preview URL per branch. Anywhere else, run next start after next build on a Node server, or build a Docker image from standalone output for AWS, GCP or your own servers. output: "export" produces purely static files that can live on S3 or GitHub Pages, but without server features such as SSR, server actions or the proxy. Setting a route’s runtime to "edge" starts quickly near users at the cost of some Node APIs. Self-hosting needs extra setup for image optimization and ISR caching.</sub> |
| **인증 패턴**<br><sub>Authentication patterns</sub> | 로그인하면 httpOnly 세션 쿠키를 발급하고, proxy로 빠르게 1차 검사한 뒤, 데이터에 접근하는 모든 곳에서 세션과 권한을 다시 확인해요.<br><sub>Issue an httpOnly session cookie on login, run a quick first check in the proxy, then re-verify the session and permissions wherever data is accessed.</sub> | 서버 액션에서 사용자를 확인한 뒤 (await cookies()).set("session", …, { httpOnly: true, secure: true })로 쿠키를 발급하면 JS로 읽을 수 없어 XSS에 강해요. proxy는 쿠키가 없으면 /login으로 보내는 빠른 1차 관문이지만, 2025년의 미들웨어 우회 취약점(CVE-2025-29927)처럼 이것만 믿으면 위험해요. 그래서 데이터를 읽고 바꾸는 서버 컴포넌트·서버 액션·Route Handler에서 getSession()으로 매번 다시 확인하고, 이 검사를 데이터 접근 계층(DAL)에 모아 두면 빠뜨리지 않아요. 직접 구현하기보다 Auth.js, Better Auth, Clerk 같은 검증된 도구를 쓰는 편이 안전해요.<br><sub>Verifying the user in a server action and setting the cookie with (await cookies()).set("session", …, { httpOnly: true, secure: true }) keeps it unreadable from JavaScript and resistant to XSS. The proxy is a quick first gate redirecting cookie-less visitors to /login, but relying on it alone is dangerous, as the 2025 middleware bypass (CVE-2025-29927) showed. Server components, server actions and route handlers that read or change data should check getSession() every time, and centralizing these checks in a data access layer keeps them from being missed. Proven tools such as Auth.js, Better Auth or Clerk are safer than rolling your own.</sub> |
| **국제화 라우팅**<br><sub>Internationalized routing</sub> | 언어를 [lang] URL 세그먼트로 두고, 번역 사전은 서버에서 읽고, 첫 방문 언어는 proxy가 Accept-Language로 정해요.<br><sub>Keep the language in a [lang] URL segment, read translation dictionaries on the server, and let the proxy pick the first visit’s language from Accept-Language.</sub> | app/[lang]/page.tsx로 두면 /ko/about, /en/about처럼 언어가 URL에 들어가 검색 엔진도 언어별 페이지를 구분해요. generateStaticParams가 [{ lang: "ko" }, { lang: "en" }]를 돌려주면 언어별 페이지를 빌드 때 미리 만들어요. getDictionary(lang)으로 번역 사전을 서버 컴포넌트에서 읽으면 사전이 브라우저 번들에 들어가지 않아요. 첫 방문자는 proxy가 Accept-Language 헤더를 보고 /ko 같은 알맞은 언어 경로로 보내요. 복수형·날짜·숫자 형식은 next-intl 같은 라이브러리가 도와주고, <html lang>과 hreflang 링크도 언어별로 맞춰요.<br><sub>With app/[lang]/page.tsx, the language appears in URLs such as /ko/about and /en/about, letting search engines distinguish language versions. When generateStaticParams returns [{ lang: "ko" }, { lang: "en" }], every language’s pages are prebuilt. Reading dictionaries with getDictionary(lang) in server components keeps them out of the browser bundle. For first visits, the proxy reads the Accept-Language header and redirects to the matching path, such as /ko. Libraries such as next-intl handle plurals, dates and number formats, and <html lang> and hreflang links should match each language.</sub> |
| **Pages Router와 App Router**<br><sub>Pages Router and App Router</sub> | Pages Router는 페이지 단위 데이터 함수(getServerSideProps 등)로, App Router는 서버 컴포넌트가 직접 데이터를 가져오는 방식으로 동작해요. 둘은 한 프로젝트에 공존할 수 있어요.<br><sub>The Pages Router works through page-level data functions such as getServerSideProps, while the App Router lets server components fetch their own data; both can coexist in one project.</sub> | Pages Router에서는 pages 폴더의 파일이 경로가 되고, getServerSideProps나 getStaticProps 같은 페이지 단위 함수가 데이터를 props로 넘기며, 모든 컴포넌트가 클라이언트에서 하이드레이션돼요. App Router는 서버 컴포넌트가 기본이라 필요한 컴포넌트가 직접 데이터를 await하고, 중첩 레이아웃·스트리밍·서버 액션을 지원해 보내는 JS가 적어요. 두 라우터는 한 프로젝트에 함께 있을 수 있어서 페이지 단위로 천천히 옮길 수 있지만, 같은 경로를 동시에 둘 수는 없어요. 새 프로젝트는 App Router로 시작하고, \_app과 \_document의 역할은 루트 레이아웃이 맡아요.<br><sub>In the Pages Router, files under pages become routes, page-level functions such as getServerSideProps and getStaticProps pass data as props, and every component hydrates on the client. The App Router defaults to server components that await their own data, with nested layouts, streaming and server actions, and ships less JavaScript. The two routers can live in one project for gradual page-by-page migration, though the same path cannot exist in both. New projects start with the App Router, where the root layout takes over the roles of \_app and \_document.</sub> |
