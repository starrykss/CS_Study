## 네트워크 계층 모델 · Network layer models

복잡한 통신을 층으로 나눠 각 층이 한 가지 일만 하게 만들었어요.  
*Communication is split into layers so each does one job.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **OSI 7계층 · TCP/IP**<br><sub>OSI model · TCP/IP</sub> | 네트워크 기능을 물리 → 데이터 링크 → 네트워크 → 전송 → 세션 → 표현 → 응용 7개 층으로 나눈 참조 모델이에요. 실제 인터넷은 4계층 TCP/IP 모델로 동작해요.<br><sub>A reference model splitting networking into seven layers from physical up to application. The real internet runs the four-layer TCP/IP model.</sub> | 장애를 볼 때 "몇 계층 문제인가"로 좁혀 가요. 케이블(1), IP·라우팅(3), 포트·방화벽(4), 앱(7) 순서로 확인하면 빨라요. L4/L7 로드 밸런서라는 말도 여기서 나와요.<br><sub>When debugging, narrow it down by layer: cable (1), IP and routing (3), ports and firewalls (4), then the app (7). “L4/L7 load balancer” comes from here.</sub> |
| **캡슐화**<br><sub>Encapsulation</sub> | 데이터가 아래 계층으로 내려가며 TCP, IP, 이더넷 헤더가 차례로 붙고, 받는 쪽에서는 하나씩 벗겨져요.<br><sub>As data goes down the stack it gains TCP, IP and Ethernet headers in turn; the receiver strips them one by one.</sub> | 와이어샤크로 패킷을 열어 보면 이 헤더들이 층별로 보여요. 헤더만큼 오버헤드가 생겨서 MTU(보통 1500바이트)를 넘으면 쪼개져요.<br><sub>Open a packet in Wireshark and you see these headers layer by layer. Headers add overhead, and anything over the MTU (usually 1500 bytes) is fragmented.</sub> |
| **회선 교환 vs 패킷 교환**<br><sub>Circuit vs packet switching</sub> | 회선 교환은 통신 전에 길을 예약해 끝날 때까지 혼자 쓰고, 패킷 교환은 데이터를 잘게 나눠 각자 공유된 길로 보내요. 인터넷은 패킷 교환이에요.<br><sub>Circuit switching reserves a path for the whole conversation; packet switching chops data into packets that travel independently over shared links. The internet is packet switched.</sub> | 전화망 같은 회선 교환은 대역이 보장되고 지연이 일정하지만, 말이 없는 동안에도 회선을 차지해 낭비가 생겨요. 패킷 교환은 여러 사용자의 패킷이 같은 링크를 나눠 쓰는 통계적 다중화로 훨씬 효율적이지만, 지연이 변하고 순서가 바뀌거나 손실이 생길 수 있어요. 그 빈틈은 TCP가 재정렬과 재전송으로 메워요.<br><sub>A circuit-switched phone network guarantees capacity and steady delay but holds the line even during silence. Packet switching shares links among many users through statistical multiplexing, which is far more efficient, at the cost of variable delay, reordering and loss. TCP covers those gaps with reordering and retransmission.</sub> |

## 주소와 길 찾기 · Addresses and routing

같은 네트워크 안에서는 MAC 주소로, 네트워크 사이에서는 IP 주소로 찾아가요.  
*MAC addresses work inside a network; IP addresses work between networks.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **MAC 주소와 스위치**<br><sub>MAC address · Switch</sub> | MAC 주소는 네트워크 카드마다 붙은 고유 주소예요. 스위치는 어떤 MAC이 어느 포트에 있는지 배워서 필요한 곳으로만 프레임을 보내요.<br><sub>A MAC address is a unique ID burned into each network card. A switch learns which MAC sits on which port and forwards frames only there.</sub> | 같은 공유기·스위치에 연결된 기기끼리는 MAC으로 통신해요. 클라우드의 가상 네트워크(VPC)도 이 개념을 소프트웨어로 흉내 내요.<br><sub>Devices on the same router or switch talk by MAC. Cloud virtual networks (VPCs) imitate the same idea in software.</sub> |
| **ARP**<br><sub>ARP</sub> | IP 주소는 아는데 MAC 주소를 모를 때, 네트워크 전체에 "이 IP 가진 분?" 하고 물어 MAC을 알아내요.<br><sub>When you know an IP but not its MAC, ARP asks the whole network “who has this IP?” and learns the MAC.</sub> | 다른 네트워크로 가는 패킷은 게이트웨이의 MAC으로 보내요. ARP 응답을 위조하는 ARP 스푸핑 공격이 있어서 공용 와이파이는 조심해야 해요.<br><sub>Packets for other networks go to the gateway’s MAC. Forged replies (ARP spoofing) are why public Wi-Fi needs care.</sub> |
| **IP 주소와 서브넷**<br><sub>IP address · Subnet</sub> | IPv4 주소는 32비트이고, /24 같은 서브넷 마스크로 앞부분은 네트워크, 뒷부분은 호스트를 나타내요.<br><sub>An IPv4 address is 32 bits; a mask like /24 says which leading bits are the network and which are the host.</sub> | 클라우드에서 VPC·서브넷을 만들 때 CIDR(10.0.0.0/16 등)을 정해요. 10.x, 172.16~31.x, 192.168.x는 사설 IP 대역이에요.<br><sub>You choose CIDR blocks (like 10.0.0.0/16) when creating cloud VPCs and subnets. 10.x, 172.16–31.x and 192.168.x are private ranges.</sub> |
| **라우팅**<br><sub>Routing</sub> | 라우터는 패킷의 목적지 IP를 보고 라우팅 테이블에서 다음으로 보낼 곳(다음 홉)을 골라요. 경로가 끊기면 다른 길로 돌아가요.<br><sub>A router looks at the destination IP and picks the next hop from its routing table; if a path breaks, traffic goes around.</sub> | traceroute로 패킷이 거치는 라우터들을 볼 수 있어요. 회사 간·국가 간 경로는 BGP가 정하고, 잘못 설정되면 대규모 장애가 나요.<br><sub>traceroute shows the routers on the path. Paths between networks are set by BGP, and BGP mistakes cause huge outages.</sub> |
| **NAT**<br><sub>NAT · Network address translation</sub> | 공유기가 사설 IP 기기들의 출발 주소를 하나의 공인 IP와 포트로 바꿔 내보내고, 돌아오는 응답을 표를 보고 원래 기기에 돌려줘요.<br><sub>The router rewrites private source addresses to one public IP and port, and maps replies back using a table.</sub> | 집 안 기기를 외부에서 바로 접속할 수 없는 이유예요. 서버를 열려면 포트 포워딩이 필요하고, P2P·화상통화는 NAT 통과 기술(STUN/TURN)을 써요.<br><sub>This is why home devices are not reachable from outside: you need port forwarding, and P2P or video calls use NAT traversal (STUN/TURN).</sub> |
| **DHCP**<br><sub>DHCP</sub> | 새 기기가 네트워크에 들어오면 DHCP 서버가 IP 주소, 게이트웨이, DNS 서버 주소를 자동으로 빌려줘요.<br><sub>When a device joins, the DHCP server lends it an IP address plus gateway and DNS settings automatically.</sub> | 와이파이에 연결만 하면 인터넷이 되는 이유예요. 서버처럼 주소가 바뀌면 안 되는 기기는 고정 IP나 예약(reservation)을 써요.<br><sub>It is why joining Wi-Fi “just works”. Servers that must keep their address use static IPs or reservations.</sub> |
| **ICMP · ping · traceroute**<br><sub>ICMP, ping and traceroute</sub> | ICMP는 IP의 제어·오류 메시지예요. ping은 에코 요청으로 왕복 시간을 재고, traceroute는 TTL을 1씩 늘려 경로의 라우터를 하나씩 드러내요.<br><sub>ICMP carries IP’s control and error messages. ping times round trips with echo requests, and traceroute reveals each router on the path by raising the TTL one step at a time.</sub> | TTL은 라우터를 지날 때마다 1씩 줄고, 0이 되면 그 라우터가 패킷을 버리며 ICMP “시간 초과”를 돌려줘요. traceroute는 TTL=1, 2, 3…으로 보내 각 홉의 주소와 지연을 알아내고, 목적지에 닿으면 응답을 받아요. ICMP를 막는 라우터는 \* \* \*로 보여요. ICMP를 통째로 막으면 경로 MTU 탐색이 깨져 이상한 장애가 나니 주의해요.<br><sub>Each router decrements the TTL; when it hits zero, the router drops the packet and returns an ICMP “time exceeded”. traceroute sends TTL = 1, 2, 3, … to learn each hop’s address and delay until the destination answers, while routers that block ICMP appear as \* \* \*. Blocking ICMP entirely breaks path MTU discovery and causes puzzling outages.</sub> |
| **IPv6**<br><sub>IPv6</sub> | 128비트 주소로 IPv4 주소 고갈을 끝낸 차세대 IP예요. 2001:db8::ff00:42:8329처럼 16진수 8묶음으로 적어요.<br><sub>The next-generation IP that ends IPv4 exhaustion with 128-bit addresses, written as eight hex groups such as 2001:db8::ff00:42:8329.</sub> | IPv4는 약 43억 개라 2011년 IANA 풀이 바닥났지만, IPv6는 약 3.4 × 10³⁸개예요. 각 묶음 앞의 0은 생략하고, 연속된 0 묶음은 ::로 한 번만 줄여 써요. 보통 앞 64비트는 네트워크 접두사, 뒤 64비트는 인터페이스 ID이고, SLAAC로 기기가 스스로 주소를 만들어요. NAT 없이 모든 기기가 전역 주소를 갖지만 방화벽은 여전히 필요하고, 듀얼 스택으로 IPv4와 함께 쓰여요.<br><sub>IPv4 offers about 4.3 billion addresses and IANA’s pool ran dry in 2011; IPv6 offers about 3.4 × 10³⁸. Leading zeros in each group are dropped and one run of zero groups collapses to ::. Typically the first 64 bits are the network prefix and the last 64 the interface ID, and SLAAC lets devices build their own addresses. Every device can have a global address without NAT, though firewalls still matter, and dual stack keeps IPv4 running alongside.</sub> |
| **거리 벡터 vs 링크 상태 라우팅**<br><sub>Distance-vector vs link-state routing</sub> | 라우터가 경로를 계산하는 두 방식이에요. 이웃과 거리 표를 주고받거나(RIP), 링크 정보를 모두에게 뿌려 전체 지도로 계산해요(OSPF).<br><sub>Two ways routers compute paths: trade distance tables with neighbors (RIP) or flood link information so everyone computes on the full map (OSPF).</sub> | 거리 벡터는 이웃이 알려 준 거리에 링크 비용을 더해 표를 고쳐 가는 벨만-포드 방식이라 단순하지만 수렴이 느리고 무한 카운트 문제가 있어요(split horizon으로 완화). 링크 상태는 각 라우터가 자기 링크 정보(LSA)를 전체에 퍼뜨리고, 모두가 같은 지도에서 다익스트라로 최단 경로를 구해 빠르게 수렴하지만 메모리와 CPU를 더 써요. 조직 사이의 경로는 경로 벡터 프로토콜인 BGP가 맡아요.<br><sub>Distance vector updates its table from neighbors’ distances plus link costs (Bellman–Ford): simple, but slow to converge and prone to count-to-infinity, eased by split horizon. Link state has every router flood its own links (LSAs) so all build the same map and run Dijkstra, converging fast at the cost of memory and CPU. Between organizations, BGP, a path-vector protocol, takes over.</sub> |
| **VLAN**<br><sub>VLANs</sub> | 물리 배선은 그대로 두고, 스위치 포트에 번호를 매겨 하나의 네트워크를 논리적으로 여러 개로 나누는 기술이에요.<br><sub>Logically splitting one physical network into several by numbering switch ports, without rewiring.</sub> | 한 스위치의 모든 기기는 하나의 방송 영역이라 ARP 같은 브로드캐스트가 전부에게 퍼지지만, 포트를 VLAN 10과 20으로 나누면 서로 다른 방송 영역이 돼요. 트렁크 포트는 802.1Q 태그(VID)를 붙여 여러 VLAN을 한 선으로 다른 스위치에 넘기고, 다른 VLAN끼리는 라우터나 L3 스위치를 거쳐야 통신해요. 직원망·게스트망 분리, 데이터센터 테넌트 분리에 쓰이고, 클라우드 VPC와 VXLAN이 같은 생각을 확장했어요.<br><sub>Every device on a switch shares one broadcast domain, so broadcasts like ARP reach everyone; assigning ports to VLAN 10 and 20 creates separate domains. Trunk ports add 802.1Q tags (VIDs) to carry many VLANs over one link to another switch, and traffic between VLANs must pass through a router or L3 switch. VLANs separate staff and guest networks or data-center tenants, and cloud VPCs and VXLAN scale the idea up.</sub> |
| **MTU와 단편화**<br><sub>MTU and fragmentation</sub> | MTU는 한 링크가 한 번에 실을 수 있는 최대 크기예요(이더넷 1500 B). 더 큰 IP 패킷은 쪼개거나(IPv4), 거절하고 알려 줘요(IPv6, DF).<br><sub>The MTU is the largest frame a link can carry (1500 B on Ethernet); bigger IP packets are fragmented (IPv4) or refused with a notice (IPv6, DF).</sub> | 4000 B 패킷이 MTU 1500 링크를 만나면 1480 B씩 데이터를 나눠 각 조각에 IP 헤더를 붙이고, offset(8바이트 단위)과 MF 플래그로 위치를 표시해요. 재조립은 목적지에서만 하며, 조각 하나만 잃어도 패킷 전체를 다시 보내야 해 비효율적이에요. 그래서 DF를 켜고 ICMP “너무 큼”을 받아 크기를 줄이는 경로 MTU 탐색을 쓰고, TCP는 MSS(보통 1460 B)로 맞춰 보내요. VPN·터널은 MTU를 줄이니 MSS 클램핑이 필요해요.<br><sub>When a 4000 B packet meets a 1500 B MTU link, its data is cut into 1480 B pieces, each with its own IP header, marked with an offset (in 8-byte units) and the MF flag. Only the destination reassembles, and losing one fragment means resending the whole packet. Hence path MTU discovery: set DF, receive ICMP “too big” and shrink, while TCP sizes segments to the MSS (typically 1460 B). VPNs and tunnels lower the MTU, so MSS clamping is needed.</sub> |

## TCP와 UDP · TCP and UDP

프로그램과 프로그램 사이에서 데이터를 믿을 수 있게, 또는 빠르게 전달해요.  
*Moving data between programs, reliably or quickly.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **TCP 3-way 핸드셰이크**<br><sub>TCP three-way handshake</sub> | SYN → SYN+ACK → ACK 세 번의 메시지로 양쪽이 순서 번호를 맞추고 연결을 열어요.<br><sub>Three messages, SYN, SYN+ACK and ACK, sync sequence numbers on both sides and open the connection.</sub> | 연결마다 왕복 1번이 더 들어서, 서버가 멀면 느려져요. Keep-Alive로 연결을 재사용하고, 커넥션 풀을 쓰는 이유예요.<br><sub>Each connection costs an extra round trip, which hurts with distant servers. That is why keep-alive and connection pools reuse connections.</sub> |
| **연결 종료 (4-way)**<br><sub>Connection teardown</sub> | 각자 FIN을 보내고 ACK를 받아 양방향을 따로 닫아요. 먼저 닫은 쪽은 TIME\_WAIT 상태로 잠시 기다려요.<br><sub>Each side sends FIN and gets an ACK, closing each direction separately; the closer waits briefly in TIME\_WAIT.</sub> | 짧은 연결을 너무 많이 만들면 TIME\_WAIT가 쌓여 포트가 부족해져요. 연결 재사용이 해법이에요.<br><sub>Too many short-lived connections pile up TIME\_WAIT and exhaust ports. Reuse connections instead.</sub> |
| **TCP vs UDP**<br><sub>TCP vs UDP</sub> | TCP는 순서와 도착을 보장하고 잃은 것은 다시 보내요. UDP는 확인 없이 보내서 빠르지만 잃거나 순서가 바뀔 수 있어요.<br><sub>TCP guarantees order and delivery and resends losses. UDP sends without checks: faster, but packets may be lost or reordered.</sub> | 웹·DB·파일은 TCP, 실시간 영상·게임·DNS는 UDP를 써요. 늦게 온 영상 프레임은 쓸모없어서 재전송보다 빠른 게 낫거든요.<br><sub>Web, databases and files use TCP; live video, games and DNS use UDP, because a late video frame is useless anyway.</sub> |
| **재전송**<br><sub>Retransmission</sub> | 보낸 데이터의 확인(ACK)이 정해진 시간 안에 오지 않으면 잃어버린 것으로 보고 다시 보내요.<br><sub>If no acknowledgement arrives in time, the data is presumed lost and sent again.</sub> | 패킷 손실이 1%만 있어도 재전송 대기 때문에 속도가 크게 떨어져요. 모바일 망에서 지연이 튀는 원인 중 하나예요.<br><sub>Even 1% packet loss slows throughput a lot because of retransmission waits; it is one reason mobile latency spikes.</sub> |
| **슬라이딩 윈도우**<br><sub>Sliding window</sub> | ACK를 하나씩 기다리지 않고 정해진 개수(윈도우)만큼 연달아 보내고, 확인되는 만큼 창을 밀어요.<br><sub>Send a window of segments without waiting for each ACK, sliding the window forward as acks arrive.</sub> | 받는 쪽이 감당할 수 있는 양만 보내는 흐름 제어에 써요. 멀고 빠른 회선에선 윈도우가 커야 대역폭을 다 써요.<br><sub>It provides flow control, sending only what the receiver can take. Long, fast links need large windows to use their bandwidth.</sub> |
| **혼잡 제어**<br><sub>Congestion control</sub> | 보내는 양(cwnd)을 처음엔 빠르게 늘리다가, 손실이 생기면 네트워크가 막힌 것으로 보고 크게 줄여요.<br><sub>The sender grows its window (cwnd) quickly at first, then cuts it sharply when loss signals congestion.</sub> | 모든 TCP가 이렇게 양보해서 인터넷이 마비되지 않아요. 구글의 BBR은 손실 대신 대역폭과 지연을 재서 더 빨라요.<br><sub>Because every TCP backs off like this, the internet does not collapse. Google’s BBR measures bandwidth and delay instead of loss.</sub> |
| **포트와 소켓**<br><sub>Port · Socket</sub> | IP 주소로 컴퓨터를 찾고, 포트 번호로 그 안의 프로그램을 찾아요. IP와 포트의 조합이 소켓 주소예요.<br><sub>An IP address finds the computer; a port number finds the program inside it. Together they form a socket address.</sub> | 22 SSH, 80 HTTP, 443 HTTPS, 3306 MySQL, 5432 PostgreSQL처럼 잘 알려진 포트가 있어요. "Address already in use" 오류는 그 포트를 이미 누가 쓰고 있다는 뜻이에요.<br><sub>Well-known ports: 22 SSH, 80 HTTP, 443 HTTPS, 3306 MySQL, 5432 PostgreSQL. “Address already in use” means something already holds the port.</sub> |
| **네트워크 지연과 BDP**<br><sub>Network delay and BDP</sub> | 패킷 하나의 지연은 처리 + 큐잉 + 전송 + 전파 지연의 합이에요. 대역폭 × 왕복 시간(BDP)은 “선 위에 떠 있는 데이터 양”이에요.<br><sub>A packet’s delay is processing + queuing + transmission + propagation; bandwidth × round-trip time (the BDP) is how much data is “in flight” on the wire.</sub> | 전송 지연은 패킷 크기 ÷ 대역폭(1500 B ÷ 100 Mbps = 0.12 ms), 전파 지연은 거리 ÷ 신호 속도(서울→뉴욕 약 55 ms)라 먼 거리에선 전파가 압도적이고, 그래서 CDN으로 거리를 줄여요. 큐잉 지연은 혼잡에 따라 출렁이고, 버퍼가 너무 크면 늘 차서 지연만 커지는 버퍼블로트가 생겨요. 1 Gbps × 100 ms면 12.5 MB가 날아다니므로, TCP 윈도우가 BDP보다 작으면 대역폭을 다 쓰지 못해요.<br><sub>Transmission delay is size ÷ bandwidth (1500 B ÷ 100 Mbps = 0.12 ms), propagation is distance ÷ signal speed (about 55 ms Seoul to New York), so propagation dominates over long distances, which is why CDNs move content closer. Queuing delay swings with congestion, and oversized buffers that stay full cause bufferbloat. At 1 Gbps × 100 ms, 12.5 MB is in flight, so a TCP window smaller than the BDP can’t fill the pipe.</sub> |

## 웹을 움직이는 프로토콜 · Protocols that run the web

브라우저와 서버가 실제로 주고받는 대화예요.  
*The actual conversations between browsers and servers.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **DNS**<br><sub>DNS · Domain Name System</sub> | 도메인 이름을 IP 주소로 바꿔요. 리졸버가 루트 → TLD → 권한 서버 순서로 물어보고 답을 캐시해요.<br><sub>Turns domain names into IP addresses. A resolver asks root, then TLD, then authoritative servers, and caches the answer.</sub> | DNS를 바꿔도 TTL 동안은 예전 주소가 남아 있어요. 배포 전에 TTL을 줄여 두세요. "It's always DNS"라는 말이 있을 만큼 장애 원인으로 흔해요.<br><sub>After a DNS change, old answers live on until the TTL expires, so lower it before a migration. Outages are so often DNS that “it’s always DNS” is a saying.</sub> |
| **HTTP 요청과 응답**<br><sub>HTTP request · response</sub> | 클라이언트가 메서드, 경로, 헤더로 요청하면 서버가 상태 코드, 헤더, 본문으로 응답해요. 각 요청은 독립적이에요(무상태).<br><sub>The client sends a method, path and headers; the server replies with a status code, headers and a body. Each request stands alone (stateless).</sub> | 개발자 도구 Network 탭이나 curl -v로 헤더를 직접 보면 캐시·인증·CORS 문제를 빨리 찾아요.<br><sub>Reading headers in DevTools’ Network tab or with curl -v quickly reveals caching, auth and CORS problems.</sub> |
| **TLS 핸드셰이크**<br><sub>TLS handshake</sub> | HTTPS 연결 전에 암호 방식을 정하고, 서버 인증서를 검증하고, 양쪽이 같은 세션 키를 만들어요. 이후 모든 통신은 암호화돼요.<br><sub>Before HTTPS traffic flows, both sides agree on ciphers, verify the server certificate and derive a shared session key.</sub> | 인증서가 만료되면 사이트 전체가 막혀요. Let's Encrypt와 자동 갱신을 꼭 설정하세요. TLS 1.3은 왕복 1번으로 끝나 빨라요.<br><sub>An expired certificate takes the whole site down, so automate renewal (e.g. Let’s Encrypt). TLS 1.3 finishes in one round trip.</sub> |
| **HTTP/1.1 · 2 · 3**<br><sub>HTTP/1.1 · 2 · 3</sub> | HTTP/1.1은 한 연결에서 응답을 차례로 받고, HTTP/2는 여러 요청을 한 연결에 섞어 보내며, HTTP/3은 UDP 기반 QUIC을 써요.<br><sub>HTTP/1.1 receives responses one by one per connection, HTTP/2 interleaves many on one connection, and HTTP/3 runs on QUIC over UDP.</sub> | HTTP/2부터는 파일을 하나로 합치거나 도메인을 나누는 옛 최적화가 덜 필요해요. 대부분의 CDN이 HTTP/3을 지원해요.<br><sub>With HTTP/2, old tricks like bundling files or sharding domains matter less. Most CDNs support HTTP/3.</sub> |
| **웹소켓**<br><sub>WebSocket</sub> | HTTP로 시작한 연결을 업그레이드해서, 서버와 브라우저가 언제든 서로 메시지를 보낼 수 있는 양방향 통로로 써요.<br><sub>Upgrades an HTTP connection into a two-way channel where either side can send messages at any time.</sub> | 채팅, 실시간 알림, 협업 편집에 써요. 서버에서 보내기만 하면 SSE가 더 간단하고, 연결이 많으면 로드 밸런서 설정을 신경 써야 해요.<br><sub>Used for chat, live notifications and collaborative editing. For server-to-client only, SSE is simpler; many connections need load balancer care.</sub> |
| **URL을 입력하면 생기는 일**<br><sub>What happens when you enter a URL</sub> | DNS 조회 → TCP 연결 → TLS 협상 → HTTP 요청 → 응답 수신 → 화면 렌더링 순서로 진행돼요.<br><sub>DNS lookup, TCP connect, TLS, HTTP request, response, then rendering.</sub> | 면접 단골 질문이자 성능 개선의 지도예요. 어느 구간이 긴지 워터폴로 보고 DNS 캐시, 연결 재사용, CDN, 압축으로 줄여요.<br><sub>A classic interview question and a map for performance work: find the long phase in the waterfall, then shorten it with DNS caching, connection reuse, CDNs and compression.</sub> |
| **포워드 vs 리버스 프록시**<br><sub>Forward vs reverse proxies</sub> | 프록시는 요청을 대신 받아 전달하는 중간자예요. 포워드 프록시는 클라이언트 편, 리버스 프록시는 서버 편에 서요.<br><sub>A proxy is a middleman that receives and forwards requests; a forward proxy acts for clients and a reverse proxy for servers.</sub> | 포워드 프록시는 회사망 같은 곳에서 클라이언트를 숨기고, 접속을 거르고, 캐시해요. 리버스 프록시는 서버 앞에서 요청을 받아 TLS 종료, 로드 밸런싱, 캐시, 압축, 경로별 라우팅(/api → 서비스), WAF·속도 제한을 해 줘요. 원래 클라이언트 IP는 X-Forwarded-For, 원래 호스트는 Host 헤더로 넘겨요. Nginx, HAProxy, Envoy, Cloudflare가 대표적이고, API 게이트웨이도 리버스 프록시의 일종이에요.<br><sub>A forward proxy, as in a company network, hides clients, filters access and caches. A reverse proxy fronts the servers, handling TLS termination, load balancing, caching, compression, path routing (/api → service), WAF rules and rate limits. The original client IP travels in X-Forwarded-For and the host in the Host header. Nginx, HAProxy, Envoy and Cloudflare are common, and an API gateway is a kind of reverse proxy.</sub> |
| **이메일: SMTP · IMAP · SPF**<br><sub>Email: SMTP, IMAP and SPF</sub> | 보내기는 SMTP, 받아 읽기는 IMAP/POP3, 받는 서버 찾기는 DNS의 MX 레코드가 맡고, SPF·DKIM·DMARC로 사칭 메일을 걸러요.<br><sub>SMTP sends, IMAP/POP3 read, DNS MX records find the receiving server, and SPF, DKIM and DMARC filter spoofed mail.</sub> | 앱은 SMTP(587, 인증)로 내 메일 서버에 제출하고, 서버는 받는 도메인의 MX 레코드를 찾아 SMTP(25)로 전달해요. 받는 서버가 메일함에 저장하면 IMAP(서버에 두고 여러 기기 동기화)이나 POP3(내려받고 삭제)로 읽어요. SMTP는 원래 인증이 없어 발신자를 위조할 수 있었기에, SPF(허용된 발송 IP), DKIM(헤더 전자 서명), DMARC(실패 시 정책)가 DNS 레코드로 추가되었어요.<br><sub>The app submits mail to its own server over SMTP (587, authenticated), and the server looks up the recipient domain’s MX record and relays over SMTP (25). The receiving server stores it in a mailbox, read via IMAP (kept on the server, synced across devices) or POP3 (downloaded and deleted). SMTP originally lacked authentication, so senders could be forged; SPF (allowed sending IPs), DKIM (header signatures) and DMARC (failure policy) were added as DNS records.</sub> |
