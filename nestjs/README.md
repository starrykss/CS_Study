## 모듈·컨트롤러·프로바이더 · Modules, controllers and providers

Nest 앱의 뼈대인 모듈 그래프와 컨트롤러, 의존성 주입 컨테이너, 프로바이더의 범위와 앱의 수명 주기예요.  
*The skeleton of a Nest app: the module graph, controllers, the dependency injection container, provider scopes and the app lifecycle.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **모듈**<br><sub>Modules</sub> | @Module은 관련된 컨트롤러와 프로바이더를 기능 단위로 묶어요. imports로 다른 모듈을 가져오고 exports한 프로바이더만 바깥에 공개해요.<br><sub>The @Module decorator groups related controllers and providers into feature units, imports other modules, and exposes only exported providers.</sub> | Nest 앱은 AppModule을 루트로 하는 모듈 그래프예요. OrdersModule처럼 기능마다 모듈을 두고, 그 안에 컨트롤러(요청 처리)와 프로바이더(로직)를 등록해요. 프로바이더는 기본적으로 모듈 안에 캡슐화되어 있어서 exports에 적어야만 이 모듈을 import한 다른 모듈이 주입받을 수 있어요. 이렇게 공개 범위를 명시하니 모듈 사이 의존 관계가 코드에 드러나고, 큰 앱도 경계를 유지하기 쉬워요. 어디서나 쓰는 설정·DB 모듈은 @Global()로 등록할 수 있지만, 남발하면 의존성이 숨어 버려 권장되지 않아요. 모듈끼리 서로 import하는 순환은 forwardRef로 풀 수 있지만 보통 경계를 다시 나누라는 신호예요.<br><sub>A Nest app is a module graph rooted at AppModule. Each feature, such as OrdersModule, gets a module registering its controllers (request handling) and providers (logic). Providers are encapsulated by default, so only those listed in exports can be injected by modules that import it. Declaring visibility explicitly makes inter-module dependencies visible in code and keeps boundaries intact as apps grow. Ubiquitous config or database modules can be marked @Global(), but overuse hides dependencies and is discouraged. Modules importing each other in a cycle can be untangled with forwardRef, though it usually signals that boundaries need redrawing.</sub> |
| **컨트롤러와 라우팅**<br><sub>Controllers and routing</sub> | @Controller('orders')와 @Get(':id') 같은 데코레이터로 경로와 HTTP 메서드를 선언해요. 핸들러가 반환한 값은 자동으로 JSON 응답이 돼요.<br><sub>Decorators such as @Controller('orders') and @Get(':id') declare paths and HTTP methods, and whatever a handler returns becomes a JSON response automatically.</sub> | @Controller('orders')는 클래스의 모든 라우트 앞에 /orders를 붙이고, @Get(':id'), @Post(), @Patch(':id'), @Delete(':id')가 메서드별 라우트를 만들어요. @Param, @Query, @Body, @Headers로 요청의 각 부분을 꺼내 인자로 받아요. 반환한 객체나 배열은 JSON으로 직렬화되고, Promise나 Observable도 기다려서 응답해요. 기본 상태 코드는 GET 200, POST 201이며 @HttpCode로 바꿔요. @Req()로 Express 요청 객체를 직접 받을 수도 있지만 플랫폼에 묶이므로 데코레이터를 우선해요. 컨트롤러는 HTTP 세부 사항만 다루고 비즈니스 로직은 주입받은 서비스에 맡기는 얇은 계층으로 유지해요.<br><sub>@Controller('orders') prefixes every route in the class with /orders, while @Get(':id'), @Post(), @Patch(':id') and @Delete(':id') create per-method routes. @Param, @Query, @Body and @Headers pull parts of the request into arguments. Returned objects or arrays are serialized to JSON, and promises or observables are awaited. Default status codes are 200 for GET and 201 for POST, changed with @HttpCode. @Req() exposes the raw Express request, but it ties code to the platform, so decorators are preferred. Controllers stay thin, handling only HTTP details and delegating business logic to injected services.</sub> |
| **프로바이더와 의존성 주입**<br><sub>Providers and dependency injection</sub> | @Injectable() 클래스는 Nest의 IoC 컨테이너가 만들어 생성자에 넣어 줘요. 직접 new 하지 않고 필요한 것을 생성자 타입으로 선언해요.<br><sub>Nest’s IoC container builds @Injectable() classes and passes them into constructors, so you declare needs as constructor types instead of calling new.</sub> | 서비스, 저장소, 헬퍼처럼 주입 가능한 모든 것이 프로바이더예요. 모듈의 providers에 등록하면 컨테이너가 생성자 매개변수의 타입을 TypeScript 메타데이터(emitDecoratorMetadata)로 읽어 필요한 의존성을 먼저 만들고 주입해요. 기본 범위가 싱글턴이라 앱 전체에서 한 인스턴스를 공유하고, 앱 시작 때 한 번만 만들어져요. 클래스가 의존성을 직접 만들지 않으니 결합도가 낮고, 테스트에서는 저장소를 가짜로 바꿔 끼우기 쉬워요. 인터페이스는 런타임에 사라지므로 인터페이스 타입으로 주입하려면 토큰과 @Inject를 써요. 의존성이 순환하면 forwardRef로 미룰 수 있지만, 공통 부분을 새 프로바이더로 떼어내는 편이 좋아요.<br><sub>Anything injectable, such as services, repositories and helpers, is a provider. Once registered in a module’s providers, the container reads constructor parameter types from TypeScript metadata (emitDecoratorMetadata), builds dependencies first and injects them. The default scope is singleton, so one instance is created at startup and shared app-wide. Because classes never construct their own dependencies, coupling stays low and tests can swap a repository for a fake. Interfaces vanish at run time, so injecting by interface requires a token with @Inject. Circular dependencies can be deferred with forwardRef, but extracting the shared part into a new provider is usually better.</sub> |
| **커스텀 프로바이더**<br><sub>Custom providers</sub> | 프로바이더는 “토큰 → 만드는 방법”의 짝이에요. useValue, useClass, useFactory, useExisting으로 무엇을 어떻게 주입할지 직접 정해요.<br><sub>A provider pairs a token with a recipe, and useValue, useClass, useFactory and useExisting decide what gets injected and how.</sub> | providers: [OrdersService]는 사실 { provide: OrdersService, useClass: OrdersService }의 줄임이에요. useValue는 설정 객체나 테스트용 목을 그대로 등록하고, useClass는 토큰은 유지하면서 환경에 따라 RedisCache와 MemoryCache처럼 구현을 바꿔요. useFactory는 inject로 받은 ConfigService 같은 의존성으로 값을 만들고, async 팩토리면 DB 연결처럼 준비가 끝날 때까지 앱 시작을 기다려요. useExisting은 기존 프로바이더에 다른 토큰으로 별칭을 붙여요. 클래스가 아닌 토큰은 @Inject(API\_KEY)로 주입받으며, 오타를 막기 위해 문자열보다 Symbol이나 상수를 써요. 동적 모듈과 테스트 코드의 대부분이 이 문법으로 이뤄져요.<br><sub>providers: [OrdersService] is shorthand for { provide: OrdersService, useClass: OrdersService }. useValue registers a config object or test mock as is, and useClass keeps the token while swapping implementations per environment, such as RedisCache versus MemoryCache. useFactory builds a value from dependencies listed in inject, such as ConfigService, and an async factory delays startup until it resolves, as with a database connection. useExisting aliases an existing provider under another token. Non-class tokens are injected with @Inject(API\_KEY), using Symbols or constants rather than strings to avoid typos. Most dynamic modules and test code are built from this syntax.</sub> |
| **주입 범위**<br><sub>Injection scopes</sub> | 프로바이더의 수명은 DEFAULT(싱글턴), REQUEST(요청마다), TRANSIENT(소비자마다) 중 하나예요. REQUEST 범위는 주입받는 쪽으로 번져 성능에 영향을 줘요.<br><sub>A provider lives as DEFAULT (singleton), REQUEST (per request) or TRANSIENT (per consumer), and REQUEST scope bubbles up to consumers, affecting performance.</sub> | 기본 싱글턴은 앱 시작 때 한 번 만들어 모든 요청이 공유하므로 가장 빠르고 대부분의 경우에 맞아요. Scope.REQUEST는 요청이 올 때마다 새 인스턴스를 만들고 @Inject(REQUEST)로 요청 객체를 받을 수 있어 요청별 테넌트나 사용자 정보를 다룰 때 써요. Scope.TRANSIENT는 주입받는 클래스마다 별도 인스턴스를 줘서 로거처럼 소비자별 상태가 필요할 때 써요. REQUEST 범위 프로바이더를 주입받는 컨트롤러와 서비스도 자동으로 요청 범위가 되어, 체인 전체가 매 요청 새로 만들어지는 비용이 생겨요. 싱글턴 필드에 요청별 값을 저장하면 동시 요청끼리 섞이는 버그가 나니 피해야 해요. 요청 문맥 전달만 필요하면 AsyncLocalStorage 기반 nestjs-cls 같은 방식이 더 가벼워요.<br><sub>The default singleton is built once at startup and shared by every request, the fastest choice and right for most cases. Scope.REQUEST builds a new instance per request and can inject the request via @Inject(REQUEST), useful for per-request tenant or user data. Scope.TRANSIENT gives each injecting class its own instance, for consumer-specific state such as loggers. Controllers and services that inject a REQUEST-scoped provider become request-scoped too, so the whole chain is rebuilt on every request. Storing per-request values in singleton fields mixes data between concurrent requests and must be avoided. When only request context needs to travel, AsyncLocalStorage-based tools such as nestjs-cls are lighter.</sub> |
| **부트스트랩과 수명 주기 훅**<br><sub>Bootstrap and lifecycle hooks</sub> | main.ts의 NestFactory.create가 모듈을 훑어 의존성 그래프를 만들고, onModuleInit 같은 훅을 거쳐 listen으로 요청을 받기 시작해요. 종료 때는 정리 훅이 돌아요.<br><sub>NestFactory.create in main.ts scans modules and builds the dependency graph, runs hooks such as onModuleInit, and starts accepting requests with listen; shutdown hooks run on exit.</sub> | NestFactory.create(AppModule)는 루트부터 모든 모듈을 스캔해 프로바이더를 만들고 연결해요. 그다음 onModuleInit(각 모듈 의존성이 준비된 뒤)과 onApplicationBootstrap(모든 모듈 초기화 뒤) 훅이 실행되어 DB 연결이나 캐시 예열 같은 준비를 해요. 초기화가 끝나야 app.listen이 포트를 열어 요청을 받아요. app.enableShutdownHooks()를 켜면 SIGTERM 같은 신호에 onModuleDestroy, beforeApplicationShutdown, onApplicationShutdown이 차례로 실행돼 연결을 깔끔히 닫아요. 컨테이너 환경에서 무중단 배포를 하려면 이 종료 처리가 중요해요. HTTP 계층은 기본 Express 어댑터 대신 Fastify 어댑터로 바꿀 수 있고, Nest 12부터 훅은 컴포넌트 계층 순서로 호출돼요.<br><sub>NestFactory.create(AppModule) scans every module from the root, then builds and wires providers. Next, onModuleInit (after a module’s dependencies are ready) and onApplicationBootstrap (after all modules initialize) run setup such as database connections or cache warming. Only after initialization does app.listen open the port. With app.enableShutdownHooks(), signals such as SIGTERM trigger onModuleDestroy, beforeApplicationShutdown and onApplicationShutdown in turn to close connections cleanly. This shutdown handling matters for zero-downtime deploys in containers. The HTTP layer can switch from the default Express adapter to Fastify, and since Nest 12 hooks run in component hierarchy order.</sub> |
| **동적 모듈**<br><sub>Dynamic modules</sub> | forRoot·forFeature처럼 설정을 받아 프로바이더를 만들어 주는 모듈이에요. 데이터베이스, 설정, 메일 같은 재사용 라이브러리 모듈의 표준 형태예요.<br><sub>Dynamic modules such as forRoot and forFeature take options and build providers, the standard shape of reusable library modules for databases, config and mail.</sub> | 일반 모듈은 내용이 고정이지만, 동적 모듈은 정적 메서드가 옵션을 받아 { module, providers, exports }로 이뤄진 DynamicModule을 돌려줘요. forRoot는 루트 모듈에서 한 번 호출해 DB 연결 같은 전역 설정을 하고, forFeature는 기능 모듈마다 필요한 엔티티나 저장소만 등록해요. 설정값이 다른 프로바이더에서 와야 하면 forRootAsync({ useFactory, inject: [ConfigService] })를 써요. 쓰는 곳마다 설정이 달라야 하면 register라는 이름을 관례로 써요. isGlobal 옵션은 모든 모듈에서 import 없이 쓰게 해 줘요. 직접 만들 때는 ConfigurableModuleBuilder가 forRoot/forRootAsync 보일러플레이트를 생성해 줘요.<br><sub>A regular module’s contents are fixed, but a dynamic module’s static method takes options and returns a DynamicModule of { module, providers, exports }. forRoot is called once in the root module for global setup such as a database connection, while forFeature registers only the entities or repositories each feature module needs. When options come from another provider, use forRootAsync({ useFactory, inject: [ConfigService] }). register is the conventional name when each consumer needs different options. The isGlobal option makes a module available everywhere without imports. When writing your own, ConfigurableModuleBuilder generates the forRoot and forRootAsync boilerplate.</sub> |

## 요청이 지나는 단계들 · The stages a request passes through

미들웨어, 가드, 인터셉터, 파이프, 예외 필터가 어떤 순서로 실행되고 각각 무엇을 맡는지, 그리고 커스텀 데코레이터예요.  
*The order in which middleware, guards, interceptors, pipes and exception filters run, what each is for, and custom decorators.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **요청 수명 주기**<br><sub>The request lifecycle</sub> | 요청은 미들웨어 → 가드 → 인터셉터 → 파이프 → 핸들러 → 인터셉터 순으로 흐르고, 예외가 나면 필터가 응답으로 바꿔요.<br><sub>Requests flow through middleware, guards, interceptors, pipes, the handler and interceptors again, and filters turn exceptions into responses.</sub> | 미들웨어는 라우팅 전에 원시 요청을 다루고, 가드는 핸들러에 닿을지 여부를 결정해요. 인터셉터의 앞부분이 실행된 뒤 파이프가 인자를 검증·변환하고, 핸들러가 실행되면 인터셉터의 뒷부분이 응답을 가공해요. 어느 단계에서든 예외가 던져지면 예외 필터가 받아 HTTP 응답으로 바꿔요. 가드·인터셉터·파이프·필터는 전역(app.useGlobal\* 또는 APP\_\* 토큰), 컨트롤러, 메서드 수준으로 걸 수 있고, 전역 → 컨트롤러 → 메서드 순서로 실행돼요(필터는 가까운 쪽이 먼저 잡아요). 인증은 가드, 로깅·캐시는 인터셉터, 입력 검증은 파이프, 오류 형식은 필터처럼 역할에 맞는 단계를 고르는 것이 Nest 설계의 핵심이에요. 이 구조가 Express 미들웨어 하나에 모든 걸 넣는 방식과의 가장 큰 차이예요.<br><sub>Middleware handles the raw request before routing, and guards decide whether the handler may run. The first half of interceptors runs, pipes validate and transform arguments, the handler executes, and the second half of interceptors shapes the response. An exception at any stage is caught by exception filters and converted into an HTTP response. Guards, interceptors, pipes and filters bind globally (app.useGlobal\* or APP\_\* tokens), per controller or per method, running global, then controller, then method (filters catch closest first). Choosing the right stage, guards for auth, interceptors for logging and caching, pipes for input validation and filters for error formats, is the heart of Nest design. This structure is the biggest difference from cramming everything into Express middleware.</sub> |
| **미들웨어**<br><sub>Middleware</sub> | 라우팅 전에 (req, res, next)로 요청을 다루는 단계예요. 로깅, 요청 ID, 보안 헤더에 알맞고 next()를 불러야 다음으로 넘어가요.<br><sub>Middleware handles requests as (req, res, next) before routing, suits logging, request IDs and security headers, and must call next() to continue.</sub> | NestMiddleware를 구현한 클래스나 일반 함수로 만들고, 모듈의 configure(consumer)에서 consumer.apply(LoggerMw).forRoutes('orders')처럼 경로를 지정해요. exclude로 특정 경로를 빼고, 전역은 main.ts에서 app.use()로 등록해요. Express 생태계의 cors, helmet, compression 같은 미들웨어를 그대로 쓸 수 있어요. next()를 부르지 않으면 요청이 다음 단계로 넘어가지 않고 멈춰요. 미들웨어는 어떤 컨트롤러 메서드가 실행될지 모르기 때문에 핸들러 메타데이터가 필요한 인증·권한 판단은 가드에서 해야 해요. Fastify 어댑터에서는 req·res 객체의 모양이 Express와 달라 주의해요.<br><sub>Write it as a class implementing NestMiddleware or a plain function, and pick routes in a module’s configure(consumer), as in consumer.apply(LoggerMw).forRoutes('orders'). exclude skips specific paths, and global middleware is registered in main.ts with app.use(). Middleware cannot see which controller method will run, so authorization decisions needing handler metadata belong in guards. Under the Fastify adapter, req and res differ in shape from Express.</sub> |
| **가드**<br><sub>Guards</sub> | 가드는 CanActivate를 구현해 요청이 핸들러에 닿을지 true/false로 결정해요. 인증과 권한 검사의 자리이고 false면 403이에요.<br><sub>Guards implement CanActivate and decide with true or false whether a request reaches its handler; they host authentication and authorization, and false means 403.</sub> | canActivate(ctx: ExecutionContext)는 요청 객체뿐 아니라 곧 실행될 핸들러와 컨트롤러 클래스 정보도 받아서, Reflector로 @Roles 같은 메타데이터를 읽을 수 있어요. true나 true로 끝나는 Promise·Observable을 돌려주면 통과하고, false면 Nest가 ForbiddenException(403)을 던져요. 401을 원하면 UnauthorizedException을 직접 던져요. @UseGuards로 메서드나 컨트롤러에 걸고, { provide: APP\_GUARD, useClass: AuthGuard }로 전역에 걸면 모든 라우트가 기본으로 보호돼요. 이때 로그인처럼 열어 둘 경로는 @Public() 메타데이터를 달고 가드가 확인해 통과시켜요. 미들웨어 다음, 인터셉터와 파이프보다 먼저 실행돼서 권한 없는 요청에 불필요한 검증 비용이 들지 않아요.<br><sub>canActivate(ctx: ExecutionContext) receives not only the request but the target handler and controller class, so Reflector can read metadata such as @Roles. Returning true, or a promise or observable resolving to true, lets the request pass, while false makes Nest throw ForbiddenException (403). For a 401, throw UnauthorizedException yourself. @UseGuards binds a guard to methods or controllers, and { provide: APP\_GUARD, useClass: AuthGuard } protects every route by default. Routes that must stay open, such as login, carry @Public() metadata that the guard checks. Guards run after middleware and before interceptors and pipes, so unauthorized requests never pay for validation.</sub> |
| **인터셉터**<br><sub>Interceptors</sub> | 인터셉터는 핸들러를 앞뒤로 감싸 공통 로직을 끼워 넣어요. next.handle()이 돌려주는 Observable에 RxJS 연산자로 응답을 바꾸거나 시간을 재요.<br><sub>Interceptors wrap handlers on both sides to insert shared logic, transforming responses or timing them with RxJS operators on the Observable from next.handle().</sub> | intercept(ctx, next) 안에서 next.handle()을 부르기 전의 코드는 핸들러보다 먼저 실행되고, 반환된 Observable에 pipe(map, tap, catchError, timeout)를 붙여 뒤처리를 해요. 응답을 { data } 형태로 통일하거나, 걸린 시간을 기록하거나, 예외를 다른 예외로 바꾸거나, 일정 시간 넘게 걸리면 끊는 데 써요. handle()을 부르지 않고 캐시된 값을 of()로 바로 돌려주면 핸들러 자체를 건너뛸 수 있어 캐시 인터셉터가 이렇게 동작해요. 관점 지향 프로그래밍(AOP)처럼 여러 핸들러에 걸친 관심사를 한곳에 모으는 도구예요. ClassSerializerInterceptor, CacheInterceptor가 대표적인 내장 인터셉터예요. @UseInterceptors나 APP\_INTERCEPTOR로 등록해요.<br><sub>Inside intercept(ctx, next), code before next.handle() runs ahead of the handler, and pipe(map, tap, catchError, timeout) on the returned Observable handles the aftermath. Typical uses are wrapping responses as { data }, logging elapsed time, mapping exceptions, or cutting off slow calls. Returning a cached value with of() without calling handle() skips the handler entirely, which is how cache interceptors work. Like aspect-oriented programming (AOP), they gather cross-cutting concerns in one place. ClassSerializerInterceptor and CacheInterceptor are typical built-ins. Register them with @UseInterceptors or APP\_INTERCEPTOR.</sub> |
| **파이프**<br><sub>Pipes</sub> | 파이프는 핸들러에 들어가기 직전의 인자를 변환하거나 검증해요. ParseIntPipe는 "42"를 42로 바꾸고, 바꿀 수 없으면 400을 돌려줘요.<br><sub>Pipes transform or validate arguments right before the handler; ParseIntPipe turns "42" into 42 and returns 400 when it cannot.</sub> | 경로와 쿼리 값은 항상 문자열이라 @Param('id', ParseIntPipe)처럼 파이프로 숫자로 바꿔 받아요. 변환이나 검증에 실패하면 핸들러는 실행되지 않고 400 Bad Request가 돌아가요. ParseUUIDPipe, ParseBoolPipe, ParseArrayPipe, ParseEnumPipe, ParseDatePipe 같은 내장 파이프가 있고, DefaultValuePipe처럼 앞에 두어 기본값을 채우는 것도 있어요. 여러 파이프를 나열하면 왼쪽부터 차례로 적용돼요. PipeTransform의 transform(value, metadata) 하나만 구현하면 공백 제거, 슬러그 변환 같은 파이프를 직접 만들 수 있어요. DTO 객체 전체 검증은 ValidationPipe가 맡고, 전역으로 거는 경우가 많아요.<br><sub>Path and query values are always strings, so pipes convert them, as in @Param('id', ParseIntPipe). Implementing PipeTransform’s single transform(value, metadata) method creates pipes such as trimming or slug conversion. Whole-DTO validation is ValidationPipe’s job, often applied globally.</sub> |
| **예외 필터**<br><sub>Exception filters</sub> | NotFoundException처럼 던진 예외를 필터가 받아 HTTP 응답으로 바꿔요. @Catch로 특정 예외를 골라 원하는 형식의 오류 응답을 만들어요.<br><sub>Filters catch thrown exceptions such as NotFoundException and turn them into HTTP responses, and @Catch picks specific exceptions to shape custom error replies.</sub> | BadRequestException(400), UnauthorizedException(401), ForbiddenException(403), NotFoundException(404), ConflictException(409) 같은 내장 HTTP 예외를 던지면 기본 필터가 { statusCode, message, error } 형태의 JSON으로 응답해요. HttpException이 아닌 알 수 없는 에러는 500 Internal server error로 바뀌어 스택 같은 내부 정보가 새지 않아요. @Catch(QueryFailedError) 같은 커스텀 필터는 ArgumentsHost에서 응답 객체를 꺼내 중복 키를 409로 바꾸는 식으로 도메인·DB 예외를 HTTP 의미로 번역해요. APP\_FILTER로 전역 등록하면 앱 전체의 오류 형식이 통일되고, 로깅이나 오류 추적 도구 전송도 여기서 해요. Nest 12부터 HttpExceptionOptions에 errorCode를 넣어 클라이언트가 구분할 수 있는 오류 코드를 줄 수 있어요. 서비스는 HTTP를 모르는 도메인 예외를 던지고 필터가 번역하게 하면 계층이 깔끔해져요.<br><sub>Throwing built-in HTTP exceptions such as BadRequestException (400), UnauthorizedException (401), ForbiddenException (403), NotFoundException (404) and ConflictException (409) makes the default filter answer with JSON shaped like { statusCode, message, error }. Unknown errors that are not HttpExceptions become 500 Internal server error, keeping stack traces private. Custom filters such as @Catch(QueryFailedError) take the response from ArgumentsHost and translate domain or database errors into HTTP meaning, such as duplicate keys into 409. Registering with APP\_FILTER unifies error formats app-wide, and it is also where errors get logged or sent to tracking tools. Since Nest 12, HttpExceptionOptions can carry an errorCode that clients can distinguish. Letting services throw HTTP-agnostic domain errors that filters translate keeps layers clean.</sub> |
| **커스텀 데코레이터**<br><sub>Custom decorators</sub> | createParamDecorator로 @User() 같은 매개변수 데코레이터를, applyDecorators로 여러 데코레이터를 묶은 @Auth()를 만들어요.<br><sub>createParamDecorator builds parameter decorators such as @User(), and applyDecorators bundles several decorators into one, such as @Auth().</sub> | 인증 가드가 req.user에 넣은 사용자 정보를 핸들러마다 @Req()로 꺼내는 대신, createParamDecorator((data, ctx) => …)로 @User()를 만들면 me(@User() user)처럼 선언적으로 받아요. @User('email')처럼 넘긴 data로 특정 필드만 꺼낼 수 있고, 파이프도 함께 적용돼요. SetMetadata나 Reflector.createDecorator로 만든 데코레이터는 핸들러에 메타데이터만 붙이고, 그 값을 읽어 판단하는 쪽은 가드나 인터셉터예요. applyDecorators(Roles(r), UseGuards(JwtGuard, RolesGuard))처럼 자주 함께 쓰는 데코레이터를 하나로 묶으면 실수가 줄어요. 데코레이터는 Nest 코드를 선언적으로 만드는 핵심 도구예요. 남용하면 흐름이 숨겨지니 이름을 의미 있게 지어요.<br><sub>Instead of pulling req.user, set by the auth guard, out of @Req() in every handler, createParamDecorator((data, ctx) => …) creates @User() so handlers declare me(@User() user). Passing data, as in @User('email'), extracts a single field, and pipes still apply. Decorators made with SetMetadata or Reflector.createDecorator only attach metadata to handlers; guards or interceptors read it and decide. Bundling decorators used together, as in applyDecorators(Roles(r), UseGuards(JwtGuard, RolesGuard)), reduces mistakes. Decorators are the key tool that makes Nest code declarative. Overuse hides control flow, so give them meaningful names.</sub> |

| **DTO와 ValidationPipe**<br><sub>DTOs and ValidationPipe</sub> | DTO 클래스에 class-validator 데코레이터로 규칙을 달고 ValidationPipe를 걸면, 잘못된 요청은 핸들러 전에 400으로 걸러져요.<br><sub>Adding class-validator rules to DTO classes and applying ValidationPipe filters invalid requests out with a 400 before the handler runs.</sub> | CreateUserDto의 email에 @IsEmail(), name에 @Length(2, 20)처럼 규칙을 달면 DTO가 “들어올 데이터의 계약”이 돼요. app.useGlobalPipes(new ValidationPipe(...))로 전역에 걸면 규칙을 어긴 요청은 필드별 오류 메시지와 함께 400으로 돌아가요. whitelist: true는 DTO에 없는 필드를 지워서 role: "admin" 같은 값을 몰래 넣는 대량 할당 공격을 막고, forbidNonWhitelisted는 아예 거부해요. transform: true는 일반 객체를 DTO 인스턴스로 바꾸고 "30" 같은 문자열을 선언된 number로 변환해요. 중첩 객체는 @ValidateNested와 @Type(() => Address)로 검증해요. @nestjs/mapped-types의 PartialType, PickType, OmitType으로 수정용 DTO를 파생시켜 중복을 줄여요.<br><sub>Rules such as @IsEmail() on email and @Length(2, 20) on name turn CreateUserDto into the contract for incoming data. | **Standard Schema 검증**<br><sub>Standard Schema validation</sub> | Nest 12부터 @Body, @Query, @Param에 Zod·Valibot·ArkType 스키마를 schema 옵션으로 넘겨 검증해요. 스키마 하나로 타입과 런타임 검증을 함께 얻어요.<br><sub>Since Nest 12, @Body, @Query and @Param accept Zod, Valibot or ArkType schemas through a schema option, so one schema provides both the type and runtime validation.</sub> | Standard Schema는 여러 검증 라이브러리가 함께 구현하는 공통 인터페이스(~standard 속성)라서, Nest는 특정 라이브러리에 묶이지 않고 어떤 스키마든 받아요. const CreateUser = z.object({...})를 정의하고 z.infer로 타입을 뽑으면 DTO 클래스 없이도 타입과 검증 규칙이 한곳에 있어요. @Body({ schema: CreateUser })는 스키마를 메타데이터로 붙이기만 하고, 실제 검증은 app.useGlobalPipes(new StandardSchemaValidationPipe())로 등록한 파이프가 해요. 응답 쪽도 StandardSchemaSerializerInterceptor와 @SerializeOptions({ schema })로 스키마에 맞춰 내보낼 수 있어요. @nestjs/config의 validationSchema도 같은 스키마를 받아 환경 변수 검증을 통일할 수 있어요. 기존 class-validator 방식은 계속 지원되므로 프로젝트 상황에 맞게 고르면 돼요.<br><sub>Standard Schema is a shared interface (the ~standard property) implemented by many validation libraries, so Nest accepts any schema without tying itself to one library. | **설정 관리**<br><sub>Configuration</sub> | ConfigModule이 .env와 환경 변수를 모아 검증하고, ConfigService를 주입받아 타입 있게 읽어요. 잘못된 설정은 앱 시작 때 바로 실패해요.<br><sub>ConfigModule gathers and validates .env files and environment variables, ConfigService is injected to read them with types, and bad config fails at startup.</sub> | ConfigModule.forRoot({ isGlobal: true, envFilePath: ['.env.local', '.env'] })는 여러 파일과 process.env를 읽고, 목록 앞쪽 파일이 우선해요. validationSchema로 필수 값과 형식을 검사하면 DATABASE\_URL이 빠진 채 배포됐을 때 요청 처리 중이 아니라 시작 단계에서 실패해 원인을 바로 알 수 있어요. 서비스에서는 ConfigService를 주입받아 getOrThrow('DB\_URL')처럼 읽어서 값이 없을 때 undefined가 조용히 퍼지지 않게 해요. registerAs('db', () => ({...}))로 주제별 설정 묶음을 만들어 필요한 모듈에만 주입하고, forRootAsync의 팩토리에서 쓰기도 해요. 비밀번호와 API 키는 저장소에 커밋하지 않고 배포 환경의 시크릿으로 주입하는 12-Factor 원칙을 따라요. 테스트에서는 ConfigService를 가짜 값으로 바꿔 끼워요.<br><sub>ConfigModule.forRoot({ isGlobal: true, envFilePath: ['.env.local', '.env'] }) reads several files plus process.env, with earlier files taking priority. | **TypeORM 연동**<br><sub>TypeORM integration</sub> | @Entity 클래스가 테이블, @Column이 컬럼이 되고, @InjectRepository로 주입받은 Repository로 SQL 없이 조회·저장해요.<br><sub>@Entity classes become tables and @Column fields columns, and a Repository injected with @InjectRepository queries and saves without SQL.</sub> | TypeOrmModule.forRoot(또는 forRootAsync)로 DB 연결을 설정하고, 기능 모듈에서 forFeature([User])로 엔티티를 등록하면 Repository<User>를 주입받아 find, findOne, save, delete를 써요. @OneToMany, @ManyToOne, @ManyToMany로 관계를 선언하면 외래 키와 조인을 TypeORM이 처리하고, find({ relations: ['orders'] })나 QueryBuilder로 함께 읽어요. 목록을 돌며 관계를 하나씩 읽으면 N+1 쿼리가 생기니 relations나 join으로 한 번에 가져와요. synchronize: true는 개발 중 스키마를 자동으로 맞춰 편하지만 운영에서는 데이터 손실 위험이 있어 마이그레이션으로 변경 이력을 관리해요. 여러 쓰기를 하나로 묶을 땐 dataSource.transaction()을 써요. Group multiple writes with dataSource.transaction(). Other ORMs such as MikroORM and Drizzle are also popular with Nest.</sub> |
| **Prisma 연동**<br><sub>Prisma integration</sub> | schema.prisma에 모델을 적고 prisma generate로 타입 있는 클라이언트를 만든 뒤, PrismaService로 감싸 Nest 어디서든 주입해요.<br><sub>Prisma models live in schema.prisma, prisma generate builds a typed client, and a PrismaService wrapper makes it injectable anywhere in Nest.</sub> | Prisma는 데코레이터 대신 schema.prisma라는 별도 스키마 파일을 단일 출처로 써요. prisma generate가 이 스키마로 타입 있는 클라이언트를 만들고, findMany({ include: { posts: true } })처럼 쓰면 반환 타입에 posts까지 정확히 들어가 자동 완성과 타입 검사가 돼요. | **응답 직렬화**<br><sub>Response serialization</sub> | ClassSerializerInterceptor와 @Exclude·@Expose로 응답 직전에 password 같은 민감한 필드를 빼고 계산된 값을 더해요.<br><sub>ClassSerializerInterceptor with @Exclude and @Expose drops sensitive fields such as password and adds computed values right before responding.</sub> | DB에서 읽은 사용자 객체를 그대로 돌려주면 비밀번호 해시 같은 필드까지 응답에 실릴 수 있어요. 엔티티나 응답 클래스의 password에 @Exclude()를 달고 ClassSerializerInterceptor를 걸면 응답 직전에 class-transformer의 instanceToPlain으로 변환되며 그 필드가 빠져요. @Expose()를 단 getter는 fullName 같은 계산된 값을 응답에 더해요. 이 규칙은 클래스 인스턴스에만 적용되므로 일반 객체라면 new UserEntity(data)로 감싸서 돌려줘야 해요. @SerializeOptions({ groups: ['admin'] })로 역할에 따라 노출 필드를 바꿀 수도 있어요. 엔티티와 분리된 응답 전용 DTO를 두는 방식도 많이 쓰이고, Nest 12에서는 Standard Schema 기반 직렬화도 가능해요.<br><sub>Returning a user object straight from the database can leak fields such as the password hash. Marking password with @Exclude() on the entity or response class and applying ClassSerializerInterceptor converts results with class-transformer’s instanceToPlain right before responding, dropping that field. Getters marked @Expose() add computed values such as fullName. | **캐싱**<br><sub>Caching</sub> | CacheModule과 CacheInterceptor로 GET 응답을 자동 캐시하거나, CACHE\_MANAGER로 get·set·del을 직접 다뤄요. 데이터가 바뀌면 캐시도 지워야 해요.<br><sub>CacheModule and CacheInterceptor cache GET responses automatically, CACHE\_MANAGER exposes get, set and del directly, and caches must be cleared when data changes.</sub> | @nestjs/cache-manager의 CacheModule.register({ ttl })는 기본으로 메모리 캐시를 쓰고, 서버가 여러 대면 Redis 같은 공유 저장소를 연결해요. CacheInterceptor를 걸면 GET 응답이 URL을 키로 저장돼 같은 요청은 DB를 거치지 않고, @CacheTTL과 @CacheKey로 엔드포인트별로 조정해요. 직접 제어할 때는 CACHE\_MANAGER를 주입받아 “캐시에 있으면 반환, 없으면 DB에서 읽고 저장”하는 캐시 어사이드 패턴을 구현해요. 데이터를 바꾸는 쓰기 뒤에는 del로 관련 키를 지워야 오래된 값이 나가지 않아요. 사용자별 데이터가 URL 키 자동 캐시에 섞이면 다른 사람에게 보일 수 있으니 주의해요. TTL은 밀리초 단위이고, 캐시 무효화는 키 설계부터 고민하는 게 좋아요.<br><sub>@nestjs/cache-manager’s CacheModule.register({ ttl }) uses an in-memory cache by default, with a shared store such as Redis across servers. CacheInterceptor stores GET responses keyed by URL so repeat requests skip the database, tuned per endpoint with @CacheTTL and @CacheKey. For manual control, inject CACHE\_MANAGER and implement cache-aside: return a hit, or read the database and store the result. After writes that change data, del the related keys or stale values will be served. Per-user data mixed into URL-keyed automatic caching can leak to other users, so be careful. TTLs are in milliseconds, and invalidation is best planned starting from key design.</sub> |

| **JWT 인증**<br><sub>JWT authentication</sub> | 로그인 때 사용자 ID를 담은 서명된 토큰을 발급하고, 이후 요청의 Bearer 토큰을 가드가 검증해 req.user를 채워요. 서버가 세션을 저장하지 않는 무상태 방식이에요.<br><sub>A signed token carrying the user ID is issued at login, and a guard verifies the Bearer token on later requests to fill req.user, a stateless scheme with no server sessions.</sub> | 로그인 엔드포인트는 이메일과 비밀번호를 받아 저장된 bcrypt·argon2 해시와 비교하고, @nestjs/jwt의 JwtService.signAsync({ sub: user.id })로 토큰을 발급해요. 토큰은 header.payload.signature 구조이고, payload는 누구나 디코딩할 수 있으니 비밀 정보를 넣지 않아요. 클라이언트는 이후 Authorization: Bearer 헤더에 토큰을 실어 보내고, AuthGuard가 verifyAsync로 서명과 만료를 확인해 req.user에 담아요. 가드를 APP\_GUARD로 전역에 걸고 로그인·회원가입만 @Public()으로 여는 방식이 안전한 기본값이에요. 액세스 토큰은 15분처럼 짧게 두고 리프레시 토큰으로 갱신하며, 브라우저에서는 httpOnly 쿠키에 두면 XSS 위험이 줄어요. @nestjs/passport의 JwtStrategy와 AuthGuard('jwt')로도 같은 흐름을 만들 수 있어요.<br><sub>The login endpoint compares the email and password against a stored bcrypt or argon2 hash and issues a token with @nestjs/jwt’s JwtService.signAsync({ sub: user.id }). Applying the guard globally via APP\_GUARD and opening only login and sign-up with @Public() is a safe default. | **역할 기반 접근 제어**<br><sub>Role-based access control</sub> | @Roles('admin')로 필요한 역할을 메타데이터로 붙이고, RolesGuard가 Reflector로 읽어 사용자 역할과 비교해요. 맞지 않으면 403이에요.<br><sub>@Roles('admin') attaches required roles as metadata, and RolesGuard reads it with Reflector and compares it with the user’s roles, answering 403 on a mismatch.</sub> | SetMetadata('roles', r)나 Reflector.createDecorator로 만든 @Roles 데코레이터는 핸들러에 필요한 역할 정보만 붙여요. Data-level rules such as “edit only your own posts” are hard to express with roles alone, so policy-based access control such as CASL complements it. Authorization must be enforced on the server regardless of hidden buttons in the UI.</sub> |
| **기본 보안 설정**<br><sub>Baseline hardening</sub> | helmet으로 보안 헤더를, enableCors로 허용 출처를, ThrottlerModule로 호출 횟수 제한을 걸어요. 앱 시작 때 켜 두는 기본 방어선이에요.<br><sub>helmet adds security headers, enableCors restricts origins and ThrottlerModule limits call rates, a baseline defense switched on at startup.</sub> | helmet()은 Content-Security-Policy, Strict-Transport-Security, X-Content-Type-Options 같은 응답 헤더를 한 번에 설정해 XSS와 클릭재킹 같은 공격면을 줄여요. app.enableCors({ origin: [...] })는 허용한 출처의 브라우저만 API를 호출하게 하고, 쿠키 인증이라면 credentials: true와 정확한 출처 지정이 필요해요(와일드카드 불가). @nestjs/throttler의 ThrottlerModule.forRoot([{ ttl: 60\_000, limit: 10 }])와 전역 ThrottlerGuard는 한도를 넘는 요청에 429 Too Many Requests를 돌려줘 무차별 대입과 남용을 막아요. 헬스 체크는 @SkipThrottle로 빼고, 로그인처럼 민감한 경로는 @Throttle로 더 엄격하게 해요. 서버가 여러 대면 속도 제한 카운터를 Redis에 공유해야 정확해요. 여기에 입력 검증, 의존성 취약점 점검, 오류 메시지 최소화를 더하면 기본기가 갖춰져요.<br><sub>helmet() sets response headers such as Content-Security-Policy, Strict-Transport-Security and X-Content-Type-Options at once, shrinking the attack surface for XSS and clickjacking. app.enableCors({ origin: [...] }) lets only browsers from allowed origins call the API, and cookie-based auth needs credentials: true with exact origins (no wildcard). @nestjs/throttler’s ThrottlerModule.forRoot([{ ttl: 60\_000, limit: 10 }]) with a global ThrottlerGuard answers excess requests with 429 Too Many Requests, curbing brute force and abuse. Health checks are exempted with @SkipThrottle, and sensitive routes such as login tightened with @Throttle. Across multiple servers, rate-limit counters must be shared in Redis to stay accurate. Add input validation, dependency vulnerability checks and minimal error messages for solid basics.</sub> |
| **OpenAPI 문서화**<br><sub>OpenAPI documentation</sub> | @nestjs/swagger가 컨트롤러와 DTO의 데코레이터를 읽어 OpenAPI 명세를 만들고 /docs에 Swagger UI로 띄워요. 문서가 코드와 따로 놀지 않아요.<br><sub>@nestjs/swagger reads controller and DTO decorators to build an OpenAPI spec served as Swagger UI at /docs, so docs never drift from code.</sub> | DocumentBuilder로 제목, 버전, addBearerAuth 같은 인증 방식을 정하고, SwaggerModule.createDocument가 라우트·매개변수·DTO 정보를 모아 openapi.json을 만들어요. | **마이크로서비스**<br><sub>Microservices</sub> | 서비스끼리 메시지로 통신해요. emit은 응답 없는 이벤트, send는 요청-응답이고, 받는 쪽은 @EventPattern과 @MessagePattern으로 구독해요.<br><sub>Services talk through messages: emit sends reply-less events, send is request-response, and receivers subscribe with @EventPattern and @MessagePattern.</sub> | @nestjs/microservices는 TCP, Redis, NATS, MQTT, RabbitMQ, Kafka, gRPC 같은 전송 계층(transport)을 같은 프로그래밍 모델로 감싸요. ClientProxy’s emit('order.created', order) fires an event without waiting for any subscribers, while send('stock.check', data) returns an Observable reply awaited via firstValueFrom. Receiving services handle messages with @EventPattern and @MessagePattern handlers, reading content and transport details with @Payload and @Ctx. Handler code barely changes across transports, so a system can start on TCP and move to Kafka later. A hybrid app can serve HTTP and message listeners together. | **GraphQL**<br><sub>GraphQL</sub> | @ObjectType 클래스에서 스키마를 자동 생성하고, @Query·@Mutation·@ResolveField 리졸버로 클라이언트가 원하는 모양의 응답을 조립해요.<br><sub>Schemas are generated from @ObjectType classes, and @Query, @Mutation and @ResolveField resolvers assemble responses in exactly the shape clients request.</sub> | @nestjs/graphql의 코드 우선 방식은 @ObjectType과 @Field를 단 클래스에서 GraphQL 스키마 파일을 만들어, 타입을 한 번만 정의하게 해요. @Resolver 클래스의 @Query는 조회 진입점, @Mutation은 변경 진입점이고, 클라이언트는 필요한 필드만 골라 요청해 과하거나 모자란 응답이 없어요. @ResolveField는 author처럼 연결된 필드를 따로 풀어서, 책 N권을 조회하면 저자 조회가 N번 일어나는 N+1 문제가 생겨요. DataLoader로 한 요청 안의 조회를 모아 IN 쿼리 한 번으로 처리하면 해결돼요. 가드·인터셉터·파이프는 GqlExecutionContext를 통해 그대로 쓸 수 있어요. Nest 12는 기본 IDE로 GraphiQL을, 구독에는 graphql-ws를 써요. SDL을 먼저 쓰는 스키마 우선 방식도 선택할 수 있어요.<br><sub>The code-first approach in @nestjs/graphql generates the GraphQL schema from classes marked @ObjectType and @Field, so types are defined once. In a @Resolver class, @Query is the read entry point and @Mutation the write entry point, and clients pick exactly the fields they need, avoiding over- and under-fetching. @ResolveField resolves linked fields such as author separately, so fetching N books triggers N author lookups, the N+1 problem. DataLoader batches lookups within one request into a single IN query to fix it. Guards, interceptors and pipes work through GqlExecutionContext. Nest 12 defaults to GraphiQL as the IDE and graphql-ws for subscriptions. A schema-first approach starting from SDL is also available.</sub> |
| **WebSocket 게이트웨이**<br><sub>WebSocket gateways</sub> | @WebSocketGateway로 연결이 유지되는 실시간 통신을 만들어요. @SubscribeMessage 핸들러가 메시지를 받고, 서버는 방(room) 단위로 브로드캐스트해요.<br><sub>@WebSocketGateway builds realtime communication over persistent connections, @SubscribeMessage handlers receive messages, and the server broadcasts by room.</sub> | HTTP는 요청이 있어야 응답하지만 WebSocket은 연결을 유지해 서버가 먼저 메시지를 보낼 수 있어 채팅, 알림, 협업 편집에 써요. @WebSocketGateway({ namespace: 'chat' })가 Socket.IO(또는 ws 어댑터) 연결을 받고, @SubscribeMessage('send') 핸들러가 @MessageBody와 @ConnectedSocket으로 내용과 연결을 받아요. @WebSocketServer로 얻은 서버의 to(room).emit()은 같은 방에 들어온 클라이언트에게만 보내요. OnGatewayConnection, OnGatewayDisconnect로 연결 수명을 다루고, 연결 시 토큰을 검증해 인증해요. 서버가 여러 대면 Redis 어댑터로 방과 메시지를 공유해야 다른 서버에 붙은 사용자에게도 전달돼요. 서버 → 클라이언트 단방향 갱신만 필요하면 @Sse로 Server-Sent Events를 쓰는 편이 단순해요.<br><sub>HTTP replies only to requests, while WebSockets keep connections open so the server can push first, suiting chat, notifications and collaborative editing. @WebSocketGateway({ namespace: 'chat' }) accepts Socket.IO (or ws adapter) connections, and an @SubscribeMessage('send') handler receives content and the connection via @MessageBody and @ConnectedSocket. On the server from @WebSocketServer, to(room).emit() sends only to clients in that room. OnGatewayConnection and OnGatewayDisconnect manage connection lifetimes, and tokens are verified on connect for authentication. With several servers, a Redis adapter shares rooms and messages so users on other servers receive them. For one-way server-to-client updates, Server-Sent Events via @Sse are simpler.</sub> |
| **작업 큐**<br><sub>Job queues</sub> | 메일 발송처럼 오래 걸리는 일은 BullMQ 큐에 넣고 바로 응답해요. @Processor 워커가 꺼내 처리하고, 실패하면 간격을 두고 재시도해요.<br><sub>Slow work such as sending mail goes into a BullMQ queue so requests return at once, @Processor workers handle it, and failures retry with backoff.</sub> | @nestjs/bullmq의 BullModule.registerQueue({ name: 'email' })로 Redis 기반 큐를 만들고, @InjectQueue로 주입받아 add('welcome', data, { attempts: 3, backoff: 5000 })로 작업을 넣어요. API는 작업을 넣자마자 202처럼 응답해서 사용자가 외부 메일 서버를 기다리지 않아요. WorkerHost를 상속한 @Processor('email') 클래스의 process(job)가 작업을 처리하고, 워커는 별도 프로세스나 서버로 늘려 처리량을 키울 수 있어요. 실패하면 backoff 간격을 두고 재시도하고, 끝내 실패한 작업은 따로 모여 원인을 확인하고 다시 돌릴 수 있어요. delay로 지연 실행, repeat로 반복 작업, limiter로 외부 API 호출 속도 조절도 해요. 같은 작업이 두 번 실행돼도 문제없도록 멱등하게 만드는 것이 중요해요.<br><sub>@nestjs/bullmq’s BullModule.registerQueue({ name: 'email' }) creates a Redis-backed queue, injected with @InjectQueue, and add('welcome', data, { attempts: 3, backoff: 5000 }) enqueues jobs. The API responds as soon as the job is queued, for example with 202, so users never wait on an external mail server. process(job) in an @Processor('email') class extending WorkerHost runs the work, and workers scale out as separate processes or servers. Failures retry after backoff delays, and jobs that keep failing are kept aside for inspection and replay. delay defers jobs, repeat schedules recurring ones, and limiter throttles calls to external APIs. Making jobs idempotent, safe to run twice, is essential.</sub> |
| **스케줄과 이벤트**<br><sub>Scheduling and events</sub> | @nestjs/schedule의 @Cron·@Interval로 정해진 시각과 간격에 작업을 돌리고, @nestjs/event-emitter의 @OnEvent로 앱 내부 이벤트에 반응해요.<br><sub>Scheduling with @Cron and @Interval from @nestjs/schedule runs work at set times and intervals, and @OnEvent from @nestjs/event-emitter reacts to in-app events.</sub> | @Cron('0 3 \* \* \*')는 매일 새벽 3시에 오래된 데이터 정리 같은 작업을 실행하고, @Interval(10\_000)은 10초마다, @Timeout은 시작 후 한 번 실행해요. SchedulerRegistry로 실행 중에 작업을 추가·중지할 수도 있어요. 서버가 여러 대면 모든 인스턴스에서 cron이 동시에 돌기 때문에 분산 잠금이나 큐의 반복 작업으로 한 번만 실행되게 해요. 이벤트 쪽은 EventEmitter2로 'order.created'를 내보내면 영수증 발송, 통계 갱신 같은 @OnEvent 리스너가 서로를 모른 채 각자 반응해서 주문 서비스가 부수 작업을 몰라도 돼요. { async: true } 리스너는 응답 흐름을 막지 않아요. 이 이벤트는 같은 프로세스 안에서만 전달되고 재시도가 없으므로, 서비스 간 통신이나 반드시 성공해야 하는 일은 메시지 브로커나 작업 큐를 써요.<br><sub>@Cron('0 3 \* \* \*') runs jobs such as purging old data daily at 3 a.m., @Interval(10\_000) every 10 seconds, and @Timeout once after startup. SchedulerRegistry can add or stop jobs at run time. With several servers, cron fires on every instance, so distributed locks or repeatable queue jobs keep it to one run. On the event side, emitting 'order.created' with EventEmitter2 lets @OnEvent listeners such as receipts and stats react independently, so the order service need not know about side work. { async: true } listeners do not block the response. These events stay within one process and have no retries, so cross-service communication or must-succeed work belongs in a message broker or job queue.</sub> |
| **CQRS**<br><sub>CQRS</sub> | @nestjs/cqrs는 상태를 바꾸는 명령과 조회를 CommandBus·QueryBus와 전용 핸들러로 분리해요. 처리 뒤 이벤트로 후속 작업을 느슨하게 이어요.<br><sub>@nestjs/cqrs separates state-changing commands from queries through CommandBus, QueryBus and dedicated handlers, then loosely chains follow-ups with events.</sub> | 명령(Command)은 PlaceOrder처럼 의도를 담은 객체이고, commandBus.execute(new PlaceOrder(items))를 하면 그 명령 전용 @CommandHandler가 도메인 로직과 저장을 맡아요. 조회는 queryBus.execute(new GetOrder(id))로 @QueryHandler가 처리해서 읽기에 최적화된 모델(비정규화 테이블, 캐시)을 따로 쓸 수 있어요. 명령 처리 중 AggregateRoot가 발생시킨 OrderPlaced 같은 이벤트는 @EventsHandler가 받아 메일, 재고 갱신, 읽기 모델 갱신을 하고, 사가(saga)는 이벤트 흐름을 RxJS로 받아 다음 명령을 내보내요. 서비스 하나에 모든 로직이 쌓이는 걸 막고 기능마다 핸들러가 명확해지지만, 파일과 개념이 늘어나 단순한 CRUD에는 과해요. 도메인이 복잡하거나 읽기·쓰기 부하가 크게 다를 때 고려하고, 이벤트 소싱과 함께 쓰기도 해요.<br><sub>A command is an object carrying intent, such as PlaceOrder, and commandBus.execute(new PlaceOrder(items)) hands it to its dedicated @CommandHandler for domain logic and persistence. Queries go through queryBus.execute(new GetOrder(id)) to a @QueryHandler, free to use read-optimized models such as denormalized tables or caches. Events raised by an AggregateRoot during a command, such as OrderPlaced, reach @EventsHandler classes for mail, stock and read-model updates, while sagas consume the event stream with RxJS and dispatch the next commands. It stops all logic piling into one service and gives each feature a clear handler, but adds files and concepts that are overkill for simple CRUD. Consider it for complex domains or very different read and write loads, sometimes alongside event sourcing.</sub> |
