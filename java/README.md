The eight primitives, byte, short, int, long, float, double, char and boolean, hold the value itself, so int a = 128 inside a method puts 128 straight into a local-variable slot of the stack frame. Every other type is a reference to an object on the heap. Generic collections can only hold objects, so an int must be boxed into an Integer, and the compiler calls Integer.valueOf for you (autoboxing). Integer.valueOf returns preallocated cached objects from −128 to 127, so with Integer b = 127, c = 127, b == c is true. But 128 creates a new object each time, making d == e false, a bug where the same code behaves differently depending on the value. For references, == checks for the same object, so values must always be compared with equals. Conversely, assigning an Integer to an int unboxes it by calling intValue(), throwing NullPointerException if it is null. Memory differs a lot too: an int is 4 bytes, while an Integer is a 16-byte object plus a reference. For bulk numbers, use int[], IntStream or primitive-specialized collections. Project Valhalla is preparing value objects to narrow this gap.</sub> |
| **String과 문자열 풀**<br><sub>String and the string pool</sub> | String은 불변이고 리터럴은 상수 풀에서 공유돼요. ==는 같은 객체인지만 보니 비교는 equals로, 루프 연결은 StringBuilder로 해요.<br><sub>String is immutable, and literals are shared from the constant pool. == only checks for the same object, so compare with equals and concatenate in loops with StringBuilder.</sub> | 자바의 String은 한번 만들면 바뀌지 않는 불변 객체예요. 소스의 문자열 리터럴 "hi"는 클래스 상수 풀에서 한 번만 만들어져 인터닝되고, 같은 리터럴을 쓰는 s1과 s2는 그 객체를 함께 가리켜요. new String("hi")는 내용이 같아도 힙에 별개의 객체를 만들어요. 그래서 s1 == s2는 true, s1 == s3은 false예요. ==는 참조형에서 같은 객체인지를 비교하므로 문자열은 항상 equals로 비교해야 하고, 입력이나 계산으로 만든 문자열은 내용이 같아도 대개 다른 객체예요. s3.intern()은 풀의 객체를 돌려줘요. 불변이라 해시값을 한 번 계산해 캐시하고, 여러 스레드가 동기화 없이 안전하게 공유하며, 해시맵의 키로 쓰기 좋아요. 대신 문자열을 고치는 모든 연산은 새 객체를 만들어서, 루프에서 s += x를 반복하면 매번 지금까지의 내용을 새 문자열로 복사해 O(n²)이 돼요. StringBuilder는 늘어나는 버퍼 하나에 덧붙이므로 O(n)이에요(루프 밖의 단순한 + 연결은 컴파일러가 알아서 최적화해요). JDK 9부터는 라틴 문자만 있는 문자열을 글자당 1바이트로 저장하는 compact strings로 메모리를 크게 아껴요.<br><sub>A Java String is immutable once created. A literal such as "hi" in the source is created once from the class constant pool and interned, so s1 and s2, using the same literal, share that object. new String("hi") creates a separate heap object even with the same content. So s1 == s2 is true and s1 == s3 is false. For references, == compares object identity, so strings must always be compared with equals, and strings built from input or computation are usually distinct objects even when equal; s3.intern() returns the pooled object. Immutability lets the hash be computed once and cached, lets threads share strings safely without synchronization, and makes them good hash-map keys. On the other hand, every operation that changes a string creates a new object, so repeating s += x in a loop copies everything so far into a new string each time, O(n²). StringBuilder appends into one growing buffer, O(n) (simple + concatenation outside loops is optimized by the compiler anyway). Since JDK 9, compact strings store Latin-1-only strings in one byte per character, saving a great deal of memory.</sub> |
| **equals와 hashCode**<br><sub>equals and hashCode</sub> | 해시 컬렉션은 hashCode로 버킷을 고르고 그 안에서 equals로 비교해요. equals만 재정의하면 같은 값도 찾지 못하니, 둘을 같은 필드로 함께 재정의해요.<br><sub>Hash collections pick a bucket by hashCode and compare with equals inside it. Overriding only equals means equal values go missing, so override both over the same fields.</sub> | Object의 기본 equals는 같은 객체인지(==)를 비교하고, 기본 hashCode는 객체마다 다른 값을 줘요. 값으로 비교하고 싶어 equals만 재정의한 클래스 Q를 HashSet에 넣으면 문제가 생겨요. HashSet과 HashMap은 먼저 hashCode로 버킷을 고르고, 그 버킷 안에 있는 원소들과만 equals로 비교하기 때문이에요. 첫 Q(1)은 기본 hashCode에 따라 2번 버킷에 들어갔는데, 새로 만든 Q(1)로 찾으면 다른 hashCode 때문에 6번 버킷만 보고 없다고 해요. equals가 true를 돌려줄 기회조차 없죠. 그래서 계약은 "a.equals(b)이면 a.hashCode() == b.hashCode()"예요. 반대는 성립하지 않아도 돼서, 서로 다른 객체가 같은 해시를 가질 수 있어요("Aa"와 "BB"는 둘 다 2112). equals는 반사성, 대칭성, 추이성, 일관성을 지키고 null과의 비교는 false여야 해요. 두 메서드는 같은 필드로 함께 만들어야 하므로 IDE 생성 기능, Objects.equals와 Objects.hash, 또는 둘을 자동으로 만들어 주는 record를 써요. 키로 쓰는 동안 equals와 hashCode에 쓰이는 필드를 바꾸면 객체가 엉뚱한 버킷에 남아 다시 찾을 수 없으니, 키는 불변 객체로 만드는 것이 안전해요.<br><sub>Object’s default equals compares identity (==), and its default hashCode differs per object. Trouble starts when a class Q overrides only equals to compare by value and is put into a HashSet. HashSet and HashMap first pick a bucket by hashCode and only compare with equals against the elements in that bucket. The first Q(1) went into bucket 2 according to its default hashCode, but looking up a freshly made Q(1) checks only bucket 6 because of its different hashCode and reports it missing; equals never even gets a chance to return true. Hence the contract: if a.equals(b), then a.hashCode() == b.hashCode(). The converse need not hold, so different objects may share a hash ("Aa" and "BB" both hash to 2112). equals must be reflexive, symmetric, transitive and consistent, and comparing with null must return false. Since the two methods must be built over the same fields, use the IDE’s generator, Objects.equals and Objects.hash, or a record, which generates both. Changing fields used by equals and hashCode while an object serves as a key leaves it stranded in the wrong bucket, never to be found again, so keys are safest as immutable objects.</sub> |
| **제네릭과 타입 소거**<br><sub>Generics and type erasure</sub> | 제네릭은 컴파일할 때 타입을 검사하고 바이트코드에서는 지워져요. 기본은 무공변이고, 읽을 땐 ? extends, 쓸 땐 ? super를 써요(PECS).<br><sub>Generics are checked at compile time and erased in the bytecode. They are invariant by default; read through ? extends and write through ? super (PECS).</sub> | 제네릭은 List<String>처럼 컬렉션에 담을 타입을 지정해, 잘못된 타입을 넣는 실수를 실행 전에 컴파일러가 잡게 해요. 자바 5에서 기존 코드와의 호환을 위해 타입 소거 방식으로 도입되어, 컴파일러는 타입을 검사한 뒤 바이트코드에서는 타입 인자를 지우고 값을 꺼내는 곳에 (String) 같은 캐스트를 넣어요. 그래서 실행 중에는 List<String>과 List<Integer>가 같은 ArrayList 클래스이고, new T[], instanceof List<String>, 기본형 타입 인자(List<int>) 같은 코드는 쓸 수 없어요. 제네릭 타입은 무공변이라 Integer가 Number의 하위 타입이어도 List<Integer>는 List<Number>가 아니에요. 허용하면 List<Number>로 보면서 Double을 넣어 Integer 목록을 깨뜨릴 수 있기 때문이에요. 유연성은 와일드카드로 되찾아요. sum(List<? extends Number> xs)는 Integer, Double 목록을 모두 받아 Number로 꺼내 읽을 수 있지만 넣을 수는 없고, fill(List<? super Integer> xs)는 Integer를 넣을 수 있는 목록(Integer, Number, Object)을 받아요. 값을 내주는 쪽은 extends, 받아들이는 쪽은 super라는 PECS 규칙으로 기억하며, Collections.copy(dst, src)의 시그니처가 대표적인 예예요.<br><sub>Generics let you specify the element type of a collection, as in List<String>, so the compiler catches wrong types before the program runs. They arrived in Java 5 through type erasure for compatibility with existing code: the compiler checks the types, then erases the type arguments from the bytecode and inserts casts such as (String) where values are read. So at run time List<String> and List<Integer> are the same ArrayList class, and code such as new T[], instanceof List<String> or primitive type arguments (List<int>) is impossible. Generic types are invariant: although Integer is a subtype of Number, List<Integer> is not a List<Number>, since allowing it would let a Double be added through the List<Number> view and corrupt the list of Integers. Wildcards restore flexibility. sum(List<? extends Number> xs) accepts lists of Integer or Double and can read Numbers from them but not add, while fill(List<? super Integer> xs) accepts any list that can take Integers (of Integer, Number or Object). The PECS rule, producer extends and consumer super, sums it up, and the signature of Collections.copy(dst, src) is the classic example.</sub> |
| **레코드, sealed, 패턴 매칭**<br><sub>Records, sealed types and pattern matching</sub> | record는 불변 데이터 클래스를 한 줄로, sealed는 닫힌 타입 계층을 만들어요. 패턴 매칭 switch와 함께 쓰면 모든 경우를 빠짐없이 다루는지 컴파일러가 확인해요.<br><sub>Records make immutable data classes in one line and sealed types close hierarchies. With a pattern-matching switch, the compiler checks that every case is handled.</sub> | 최근 자바는 데이터를 다루는 코드를 크게 줄였어요. record Circle(double r)(자바 16)은 private final 필드, 모든 필드를 받는 생성자, 접근자 r(), 그리고 값 기반 equals·hashCode·toString을 자동으로 만들어서, 수십 줄의 반복 코드를 한 줄로 바꿔요. 레코드는 불변이고 다른 클래스를 상속할 수 없지만 인터페이스는 구현할 수 있어요. sealed interface Shape permits Circle, Sq(자바 17)는 이 인터페이스를 구현할 수 있는 타입을 명시한 목록으로 닫아요. 그러면 컴파일러가 Shape의 하위 타입을 모두 알게 되어, 자바 21의 패턴 매칭 switch가 Circle과 Sq를 모두 다루면 default 없이도 완전하다고 판단해요. case Circle c는 타입을 확인하면서 변수에 담고, case Sq(double s)는 레코드 패턴으로 구성 요소를 바로 꺼내요. 나중에 Triangle을 추가하면 default 없는 switch마다 컴파일 오류가 나서, 처리를 빠뜨린 곳을 컴파일러가 전부 알려줘요. 이 조합은 함수형 언어의 대수적 데이터 타입과 같아서, 방문자 패턴 없이도 타입별 처리를 안전하고 간결하게 쓸 수 있어요. when 절로 조건을 붙이는 가드 패턴도 지원해요.<br><sub>Recent Java has cut data-handling code dramatically. record Circle(double r) (Java 16) automatically generates a private final field, a constructor taking all fields, the accessor r(), and value-based equals, hashCode and toString, replacing dozens of lines of boilerplate with one. Records are immutable and cannot extend other classes, though they can implement interfaces. sealed interface Shape permits Circle, Sq (Java 17) closes the interface to an explicit list of implementations. The compiler then knows every subtype of Shape, so a Java 21 pattern-matching switch that covers Circle and Sq is judged exhaustive without default. case Circle c checks the type and binds a variable, and case Sq(double s) pulls out the components directly with a record pattern. Adding a Triangle later turns every switch without default into a compile error, so the compiler points out each place that needs handling. The combination equals the algebraic data types of functional languages, making per-type logic safe and concise without the visitor pattern. Guarded patterns with when clauses add conditions too.</sub> |
| **예외와 try-with-resources**<br><sub>Exceptions and try-with-resources</sub> | 검사 예외는 컴파일러가 처리를 강제하고, RuntimeException 계열은 강제하지 않아요. 자원은 try-with-resources로 예외가 나도 자동으로 닫아요.<br><sub>The compiler forces checked exceptions to be handled but not RuntimeExceptions. try-with-resources closes resources automatically, even when exceptions occur.</sub> | 자바의 모든 예외는 Throwable 아래에 있어요. Error는 OutOfMemoryError나 StackOverflowError처럼 보통 복구할 수 없는 심각한 문제이고, Exception은 프로그램이 처리할 대상이에요. Exception 중 RuntimeException 계열(NullPointerException, IllegalArgumentException 등)은 비검사 예외로 프로그래밍 오류를 뜻하고, 나머지(IOException, SQLException 등)는 검사 예외예요. 컴파일러는 검사 예외를 catch로 잡거나 메서드 시그니처에 throws로 선언하도록 강제해서, 파일이나 네트워크처럼 실패할 수 있는 작업을 호출자가 의식하게 만들어요. 다만 람다와 스트림에서는 검사 예외를 던지기 불편해서 UncheckedIOException 같은 비검사 예외로 감싸는 일이 흔한데, 이때 원인 e를 넘겨야 원래 스택 트레이스가 이어져요. 자바 7의 try-with-resources는 괄호 안에 선언한 AutoCloseable 자원을 블록이 끝날 때 선언의 역순으로 자동으로 닫아요. 본문이 정상 종료하든 예외가 나든 close가 불리고, 본문과 close 모두에서 예외가 나면 close 쪽 예외는 getSuppressed()로 보존돼 정보를 잃지 않아요. 예외를 만들 때는 스택 트레이스를 채우는 비용이 크므로, 정상적인 흐름 제어에 예외를 쓰는 것은 피해요.<br><sub>All Java exceptions descend from Throwable. Errors, such as OutOfMemoryError and StackOverflowError, are serious problems that usually cannot be recovered from, while Exceptions are for programs to handle. Among Exceptions, the RuntimeException branch (NullPointerException, IllegalArgumentException and so on) is unchecked and signals programming errors, and the rest (IOException, SQLException and so on) are checked. The compiler forces checked exceptions to be caught or declared with throws in the method signature, making callers aware of operations that can fail, such as file or network access. Lambdas and streams make throwing checked exceptions awkward, though, so they are often wrapped in unchecked ones such as UncheckedIOException, and passing the cause e keeps the original stack trace. Java 7’s try-with-resources automatically closes the AutoCloseable resources declared in its parentheses when the block ends, in reverse order of declaration. close runs whether the body completes normally or throws, and if both the body and close throw, the close exception is preserved through getSuppressed() so no information is lost. Creating an exception is expensive because the stack trace is filled in, so avoid using exceptions for normal control flow.</sub> |

## 바이트코드가 기계어가 되기까지 · From bytecode to machine code

부모 위임으로 클래스를 찾는 클래스 로더, 스택·힙·Metaspace로 나뉜 메모리, 인터프리터에서 C1·C2로 올라가는 JIT 컴파일, 대부분의 객체가 금방 죽는다는 가정 위의 세대별 GC, 그리고 리전 기반 G1과 초저지연 ZGC를 봐요.

| **클래스 로딩**<br><sub>Class loading</sub> | 클래스는 처음 쓸 때 로딩돼요. 로더는 부모에게 먼저 위임하고, 읽은 클래스는 검증·준비·해석을 거쳐 static 초기화가 한 번 실행돼요.<br><sub>Classes load on first use. A loader delegates to its parent first, and a loaded class is verified, prepared and resolved before its static initialization runs exactly once.</sub> | JVM은 프로그램 시작 시 모든 클래스를 읽지 않고, 클래스를 처음 쓸 때 로딩해요. 클래스 로더는 계층을 이뤄요. 부트스트랩 로더는 java.base처럼 JVM 핵심 모듈을, 플랫폼 로더는 java.sql 같은 나머지 JDK 모듈을, 애플리케이션(시스템) 로더는 클래스패스나 모듈 경로의 내 코드를 맡아요. 부트스트랩 로더는 네이티브 코드라 String.class.getClassLoader()는 null을 돌려줘요. 로더는 요청을 받으면 먼저 부모에게 위임하고, 부모가 찾지 못할 때만 직접 찾아요. 그래서 누가 java.lang.String을 만들어 클래스패스에 넣어도 부트스트랩의 진짜 String이 쓰여 핵심 클래스를 바꿔치기할 수 없어요. 클래스 파일을 읽어 Class 객체를 만든 뒤에는 링크 단계로, 바이트코드가 스택이나 타입 규칙을 어기지 않는지 검증하고, static 필드에 기본값을 준비하고, 다른 클래스와 메서드를 가리키는 기호 참조를 실제 참조로 해석해요(대개 처음 쓸 때). 마지막 초기화 단계에서는 static 필드 초기화와 static 블록을 모은 <clinit>이 단 한 번, JVM이 락을 걸어 스레드 안전하게 실행해요. 지연 홀더 싱글턴 관용구가 이 보장을 이용해요. 클래스의 정체는 이름과 그것을 로딩한 로더의 쌍이라, 같은 이름도 로더가 다르면 서로 캐스트할 수 없는 다른 클래스예요. 앱 서버, 플러그인 시스템, 개발 중 핫 리로드가 이 성질로 여러 버전을 나란히 띄우거나 다시 불러와요.<br><sub>The JVM does not read every class at startup; it loads each class when first used. Class loaders form a hierarchy. The bootstrap loader handles core JVM modules such as java.base, the platform loader the remaining JDK modules such as java.sql, and the application (system) loader your code on the class path or module path. The bootstrap loader is native code, so String.class.getClassLoader() returns null. On a request, a loader first delegates to its parent and searches itself only when the parent fails. So even if someone puts their own java.lang.String on the class path, the bootstrap loader’s real String is used, and core classes cannot be replaced. After reading a class file into a Class object, the linking phase verifies that the bytecode breaks no stack or type rules, prepares static fields with default values, and resolves symbolic references to other classes and methods into real ones, usually on first use. In the final initialization phase, <clinit>, gathering static field initializers and static blocks, runs exactly once, made thread-safe by a JVM lock; the lazy-holder singleton idiom relies on this guarantee. A class’s identity is its name paired with the loader that loaded it, so the same name under different loaders is a different class that cannot be cast to the other. App servers, plugin systems and hot reload during development use this to run several versions side by side or reload them.</sub> |
| **JVM 메모리 구조**<br><sub>JVM memory layout</sub> | 스레드마다 스택이 있고 모든 스레드가 힙을 공유해요. 힙 밖에는 클래스 메타데이터의 Metaspace와 JIT 기계어의 코드 캐시가 있어요.<br><sub>Each thread has a stack and all threads share the heap. Outside the heap sit Metaspace for class metadata and the code cache for JIT-compiled machine code.</sub> | JVM 메모리는 스레드마다 따로 쓰는 영역과 모두가 공유하는 영역으로 나뉘어요. 스레드마다 있는 스택에는 메서드를 부를 때마다 프레임이 쌓이고, 프레임은 지역 변수 배열과 바이트코드가 계산에 쓰는 피연산자 스택을 가져요. int n = 3 같은 기본형 지역 변수는 프레임에 값으로, new Point(1, 2)의 참조도 프레임에 들어가고, 메서드가 끝나면 프레임째 사라져요. 객체 자체는 모든 스레드가 공유하는 힙에 생겨요. 힙은 다시 새 객체가 태어나는 Young 세대(Eden과 Survivor 두 개)와 오래 살아남은 객체의 Old 세대로 나뉘고, GC가 이를 관리해요. 힙 밖의 네이티브 메모리에는 클래스 구조와 메서드 정보 같은 메타데이터를 담는 Metaspace(JDK 8에서 고정 크기의 PermGen을 대체)와 JIT 컴파일러가 만든 기계어를 담는 코드 캐시, 그리고 스레드 스택, 다이렉트 버퍼 등이 있어요. 영역마다 고유한 오류가 있어서, 재귀가 너무 깊으면 StackOverflowError, 살아 있는 객체가 -Xmx를 넘으면 OutOfMemoryError: Java heap space, 클래스를 계속 생성하면 OutOfMemoryError: Metaspace가 나요. -Xss로 스레드 스택, -Xms와 -Xmx로 힙, -XX:MaxMetaspaceSize로 Metaspace를 조절하고, 컨테이너에서는 힙 밖 메모리까지 더해 한도를 정해야 프로세스가 강제 종료되지 않아요.<br><sub>JVM memory splits into areas private to each thread and areas shared by all. Each thread’s stack gains a frame per method call, holding a local-variable array and the operand stack that bytecode computes with. A primitive local such as int n = 3 sits in the frame as a value, as does the reference from new Point(1, 2), and the frame disappears when the method returns. Objects themselves are created on the heap shared by all threads. The heap divides into the Young generation (Eden and two Survivors), where new objects are born, and the Old generation for long-lived ones, all managed by the GC. Outside the heap, native memory holds Metaspace for metadata such as class structures and method information (replacing the fixed-size PermGen in JDK 8), the code cache for machine code produced by the JIT compiler, plus thread stacks, direct buffers and more. Each area has its own failure: recursion too deep gives StackOverflowError, live objects exceeding -Xmx give OutOfMemoryError: Java heap space, and endlessly generated classes give OutOfMemoryError: Metaspace. -Xss sets thread stacks, -Xms and -Xmx the heap and -XX:MaxMetaspaceSize Metaspace, and in containers the limit must include off-heap memory or the process gets killed.</sub> |
| **JIT 컴파일**<br><sub>JIT compilation</sub> | JVM은 바이트코드를 처음엔 인터프리터로 실행하며 프로파일을 모으고, 뜨거운 코드를 C1, C2로 컴파일해요. 추측이 틀리면 탈최적화해요.<br><sub>The JVM first interprets bytecode while gathering profiles, then compiles hot code with C1 and C2. When a speculation proves wrong, it deoptimizes.</sub> | javac는 자바 소스를 플랫폼과 무관한 바이트코드로만 바꿔요. add(a, b)는 iload\_0, iload\_1, iconst\_2, imul, iadd, ireturn이라는 스택 기반 명령 여섯 개가 되고, 실제 기계어는 실행 중에 JVM이 만들어요. 처음에는 인터프리터가 바이트코드를 한 명령씩 실행하면서 메서드 호출 횟수, 반복 횟수, 분기 방향, 실제로 들어온 타입 같은 프로파일을 모아요. 호출이나 반복이 문턱을 넘어 따뜻해지면 C1 컴파일러가 빠르게 기계어로 바꾸고, 더 뜨거워지면 C2가 모은 프로파일을 바탕으로 공격적으로 최적화한 기계어를 만들어요. 이를 계층형 컴파일이라 해요. C2의 대표적인 최적화는 작은 메서드를 호출부에 펼쳐 호출 비용을 없애고 다른 최적화의 기회를 여는 인라이닝, 메서드 밖으로 나가지 않는 객체를 힙에 할당하지 않고 필드를 레지스터에 두는 이스케이프 분석, 구현이 하나뿐인 인터페이스 호출을 직접 호출로 바꾸는 탈가상화예요. 이런 최적화는 지금까지 관찰한 것에 기댄 추측이라, 새 하위 클래스가 로딩되는 등 가정이 깨지면 컴파일된 코드를 버리고 인터프리터로 돌아가는 탈최적화를 해요. 그래서 JVM은 처음 얼마간 느렸다가 빨라지는 워밍업이 있고, 성능은 JMH 같은 도구로 워밍업 뒤에 재야 해요.<br><sub>javac only turns Java source into platform-independent bytecode: add(a, b) becomes six stack-based instructions, iload\_0, iload\_1, iconst\_2, imul, iadd and ireturn, and the JVM produces actual machine code at run time. At first the interpreter executes the bytecode one instruction at a time while gathering profiles: how often methods are called and loops run, which way branches go and which types actually arrive. When calls or loops cross a threshold and become warm, the C1 compiler quickly produces machine code, and when they get hotter, C2 uses the gathered profiles to generate aggressively optimized code. This is tiered compilation. C2’s signature optimizations include inlining, which expands small methods into their call sites to remove call overhead and open up further optimizations; escape analysis, which keeps objects that never leave a method off the heap, holding their fields in registers; and devirtualization, which turns interface calls with a single implementation into direct calls. These optimizations are speculations based on what has been observed, so when an assumption breaks, as when a new subclass is loaded, the compiled code is discarded and execution returns to the interpreter: deoptimization. The JVM therefore has a warm-up period, slow at first and fast later, and performance must be measured after warm-up with tools such as JMH.</sub> |
| **세대별 GC**<br><sub>Generational GC</sub> | 대부분의 객체는 금방 죽는다는 가정에 따라 힙을 Young과 Old로 나눠요. Minor GC는 살아 있는 객체만 복사해서 죽은 객체에는 비용이 들지 않아요.<br><sub>Following the hypothesis that most objects die young, the heap is split into Young and Old. Minor GCs copy only live objects, so dead ones cost nothing.</sub> | 자바는 객체를 직접 해제하지 않고 가비지 컬렉터가 더 이상 닿을 수 없는 객체를 회수해요. 많은 GC가 "대부분의 객체는 금방 죽는다"는 세대 가설을 이용해요. 힙을 Young 세대(Eden과 Survivor 두 개)와 Old 세대로 나누고, 새 객체는 Eden에 할당해요. 할당은 스레드마다 받은 TLAB에서 포인터를 밀기만 하면 되어 아주 빨라요. Eden이 차면 Minor GC가 일어나요. 스택의 지역 변수, static 필드 같은 루트에서 출발해 닿는 객체만 살아 있는 것으로 보고, 이들을 Survivor로 복사한 뒤 Eden을 통째로 비워요. 비용은 살아 있는 객체 수에 비례하므로, 루프에서 만든 임시 객체처럼 대부분이 죽어 있으면 아주 싸요. 살아남은 객체는 Minor GC마다 두 Survivor 사이를 오가며 나이가 늘고, 문턱(최대 15, 상황에 따라 조정)을 넘으면 Old 세대로 승격돼요. Old 세대가 차면 더 큰 Major GC나 Full GC가 힙 전체를 표시하고 압축해서 멈춤 시간이 길어져요. Old 객체가 Young 객체를 가리키면 Minor GC가 Old 전체를 훑지 않도록, 그런 참조가 생긴 영역을 카드 테이블에 표시해 두는 쓰기 배리어를 써요. 그래서 짧게 쓰고 버리는 객체는 생각보다 싸고, 오래 들고 있는 캐시나 리스너 누수가 Old 영역을 채워 문제를 일으켜요.<br><sub>Java never frees objects explicitly; a garbage collector reclaims those that can no longer be reached. Many collectors exploit the generational hypothesis that most objects die young. The heap is divided into the Young generation (Eden and two Survivors) and the Old generation, and new objects are allocated in Eden. Allocation just bumps a pointer within a per-thread TLAB, so it is very fast. When Eden fills, a minor GC runs: starting from roots such as local variables on stacks and static fields, only reachable objects count as live, and they are copied to a Survivor before Eden is wiped whole. The cost scales with the number of live objects, so it is very cheap when most are dead, as with temporaries created in a loop. Surviving objects bounce between the two Survivors at each minor GC, gaining age, and past a threshold (at most 15, adjusted dynamically) they are promoted to the Old generation. When Old fills, a larger major or full GC marks and compacts the whole heap, with longer pauses. So that minor GCs need not scan all of Old when old objects point to young ones, a write barrier marks such areas in a card table. Short-lived objects are thus cheaper than they look, while long-held caches and leaked listeners fill Old and cause trouble.</sub> |
| **G1과 ZGC**<br><sub>G1 and ZGC</sub> | G1은 힙을 리전으로 나눠 쓰레기가 많은 곳부터 정해진 멈춤 시간 안에 회수해요. ZGC는 로드 배리어로 객체 이동까지 동시에 해서 멈춤이 1ms 미만이에요.<br><sub>G1 divides the heap into regions and reclaims the most garbage-laden ones within a pause target. ZGC relocates objects concurrently with load barriers, keeping pauses under 1 ms.</sub> | JDK 9부터 기본 GC인 G1(Garbage First)은 힙을 1~32MB 크기의 리전 수천 개로 나누고, 각 리전이 그때그때 Eden, Survivor, Old, 아주 큰 객체를 담는 Humongous 역할을 맡아요. 세대 구분은 유지하되 연속된 큰 영역이 아니라 리전의 집합으로 관리하는 거예요. 동시 표시 단계에서 리전별로 살아 있는 객체의 양을 알아 두고, 회수할 때는 이름처럼 쓰레기가 가장 많은 리전부터 골라 살아 있는 객체를 빈 리전으로 옮기며 압축해요. MaxGCPauseMillis(기본 200ms) 목표 안에 끝낼 만큼만 리전을 골라서 멈춤 시간을 예측할 수 있게 해요. ZGC는 지연을 극단적으로 줄인 GC예요. 표시뿐 아니라 객체를 옮기는 재배치까지 앱 스레드와 동시에 하는데, 객체가 옮겨지는 중에도 참조를 읽을 때마다 로드 배리어가 포인터의 색 비트를 보고 최신 주소로 고쳐 줘요. 그래서 짧은 멈춤만 남아 힙이 수 테라바이트여도 멈춤이 1ms 미만이에요. JDK 15에서 정식이 되었고, JDK 21에 세대별 모드가 추가되어 처리량이 좋아졌으며 이후 기본 모드가 됐어요. 작은 힙과 단일 코어는 Serial, 배치 작업처럼 처리량이 우선이면 Parallel, 대부분의 서비스는 G1, 응답 지연이 중요한 서비스는 ZGC나 Shenandoah를 써요. 어떤 GC든 -Xlog:gc 로그로 실제 멈춤 시간을 확인하며 조정해요.<br><sub>G1 (Garbage First), the default GC since JDK 9, divides the heap into thousands of 1–32 MB regions, each taking the role of Eden, Survivor, Old or Humongous (for very large objects) as needed: generations remain, but as sets of regions rather than large contiguous areas. A concurrent marking phase learns how much live data each region holds, and collection then picks the regions with the most garbage first, as the name says, evacuating their live objects into empty regions and compacting as it goes. It picks only as many regions as fit the MaxGCPauseMillis target (200 ms by default), keeping pauses predictable. ZGC pushes latency to the extreme. It performs not only marking but also relocation concurrently with application threads; while objects move, a load barrier checks the color bits of each pointer as it is read and fixes it to the current address. Only brief pauses remain, under 1 ms even for multi-terabyte heaps. ZGC became production-ready in JDK 15 and gained a generational mode in JDK 21 that improved throughput and later became the default. Serial suits small heaps and single cores, Parallel puts throughput first for batch work, G1 fits most services, and ZGC or Shenandoah serve latency-sensitive ones. Whatever the collector, tune it while checking real pause times in -Xlog:gc logs.</sub> |

| **스레드와 상태**<br><sub>Threads and their states</sub> | 스레드는 NEW에서 start()로 RUNNABLE이 되고, 락을 기다리면 BLOCKED, 신호를 기다리면 WAITING을 거쳐 TERMINATED로 끝나요. 플랫폼 스레드는 OS 스레드와 1:1이에요.<br><sub>A thread goes from NEW to RUNNABLE with start(), through BLOCKED when waiting for a lock and WAITING when waiting for a signal, and ends TERMINATED. | **Optional**<br><sub>Optional</sub> | Optional은 값이 없을 수 있음을 반환 타입으로 드러내 null 실수를 줄여요. map과 orElseGet으로 null 검사 없이 처리하고, 반환 타입에만 써요.<br><sub>Optional makes “maybe absent” visible in the return type, reducing null mistakes. map and orElseGet replace null checks, and it belongs in return types only.</sub> | null은 "값이 없음"을 뜻하지만 타입에 드러나지 않아서, 확인을 잊으면 NullPointerException이 나요. 자바 8의 Optional<T>는 값이 있을 수도 없을 수도 있다는 사실을 타입으로 드러내는 상자예요. repo.findById(id)가 Optional<User>를 돌려주면 호출하는 쪽은 비어 있는 경우를 처리하지 않고는 User를 꺼낼 수 없어요. map은 값이 있으면 변환하고 비어 있으면 그냥 건너뛰어서, u.map(User::name).orElse("guest")는 사용자가 있으면 이름을, 없으면 "guest"를 줘요. 변환 결과가 다시 Optional이면 flatMap을, 조건으로 거르려면 filter를, 있을 때만 무언가 하려면 ifPresent를 써요. 주의할 점은 orElse의 인자가 Optional의 상태와 상관없이 먼저 계산된다는 거예요. orElse(createUser())는 값이 있어도 createUser()를 실행하므로, 비싸거나 부수 효과가 있는 기본값은 비어 있을 때만 실행되는 orElseGet(() -> createUser())를 써요. 없으면 예외를 던지려면 orElseThrow를 써요. Optional은 메서드 반환 타입으로 쓰도록 설계되어서, 필드나 메서드 파라미터, 컬렉션 원소로 쓰면 오히려 복잡해지고, 결과가 여러 개일 수 있다면 Optional<List>가 아니라 빈 List를 돌려주는 것이 맞아요. 확인 없이 get()을 부르면 null을 쓰는 것과 다를 바 없어요.<br><sub>null means “no value”, but nothing in the type says so, and forgetting to check causes NullPointerException. To build one, make every field private final, make the class final so subclasses cannot alter its behavior, and provide no methods that change state. The most common hole is storing a mutable object exactly as received: putting a constructor’s ArrayList argument straight into a field shares it with the caller, so when the caller later edits the list, the object’s contents change behind its back. So a record’s compact constructor, or an ordinary constructor, makes a defensive copy, such as an unmodifiable List.copyOf, and stores that; being unmodifiable, it can be returned from the accessor as is. To change a value, return a new object holding the changed value instead of modifying the object: when o1.add("d") makes a new o2, o1 is untouched, so other threads or code holding o1 are unaffected. Immutable objects can be shared by many threads without synchronization, are safe as map keys and in caches because their hash never changes, and are easy to reason about because no invalid intermediate state can exist. The Java Memory Model guarantees that final fields are seen fully initialized by other threads once the constructor finishes. Creating new objects often is very cheap in the young-generation GC, so it is rarely a problem.</sub> |

Gradle은 기본적으로 가장 높은 버전을 고르고, Maven은 의존성 트리에서 루트에 가장 가까운 선언을 골라요(같은 깊이면 먼저 선언한 것). 그래서 Maven에서는 깊이에 따라 더 낮은 버전이 선택되어 실행 중 NoSuchMethodError가 날 수 있어요. mvn dependency:tree나 gradle dependencies로 해결된 트리를 확인하고, BOM(Bill of Materials)이나 버전 카탈로그, 제약으로 함께 쓰는 라이브러리들의 버전을 맞춰요. Gradle의 implementation은 의존성을 내 라이브러리 사용자에게 노출하지 않고, api는 노출해서 재컴파일 범위를 줄이는 데 도움이 돼요.<br><sub>Java projects are built with Maven or Gradle. Dependencies are declared as coordinates of group, artifact and version, such as org.acme:json:1.5, and the build tool downloads them from repositories such as Maven Central into a local cache (~/.m2, ~/.gradle) and assembles the class path. Libraries bring along the libraries they need (transitive dependencies), so when web 2.0 needs json 1.2 and the app uses json 1.5 directly, two versions of one library collide. Only one can go on the class path, so the build tool chooses. Gradle picks the highest version by default, while Maven picks the declaration nearest the root of the dependency tree (the first declared at equal depth). In Maven, depth can therefore select an older version and cause NoSuchMethodError at run time. Inspect the resolved tree with mvn dependency:tree or gradle dependencies, and align versions of libraries used together with a BOM (bill of materials), version catalogs or constraints. Maven runs fixed lifecycle phases such as compile, test, package, install and deploy in order, while Gradle builds a graph of tasks, reruns only those whose inputs changed and caches results for faster builds. Gradle’s implementation keeps a dependency hidden from your library’s consumers, whereas api exposes it, which helps limit recompilation.</sub> |
| **모듈 시스템**<br><sub>The module system</sub> | 자바 9의 모듈은 requires로 의존을, exports로 공개 패키지를 선언해요. 공개하지 않은 패키지는 public이어도 밖에서 쓸 수 없고, 구성 오류는 시작할 때 드러나요.<br><sub>Java 9 modules declare dependencies with requires and public packages with exports. Unexported packages are unusable from outside even when public, and configuration errors surface at startup.</sub> | 자바 9에서 도입된 모듈 시스템(JPMS, Project Jigsaw)은 패키지들을 이름 있는 모듈로 묶고, module-info.java에 이 모듈이 필요로 하는 모듈(requires)과 다른 모듈에 공개할 패키지(exports)를 선언하게 해요. 클래스패스에서는 public 클래스라면 누구나 쓸 수 있어서 내부 구현용 public 클래스까지 외부에서 의존하는 일이 흔했어요. 모듈에서는 exports하지 않은 패키지의 클래스는 public이어도 다른 모듈에서 컴파일과 실행 모두 접근할 수 없어서, 진짜 캡슐화가 돼요. 필요한 모듈이 빠져 있거나 같은 패키지가 두 모듈에 있으면 실행 중 어딘가가 아니라 시작할 때 바로 오류가 나는데, 이를 신뢰할 수 있는 구성이라 해요. jlink는 앱이 실제로 쓰는 모듈만 담은 작은 맞춤 런타임 이미지를 만들어 컨테이너 크기를 줄여요. JDK 자체도 java.base, java.sql, java.net.http 같은 모듈로 나뉘었고, JDK 내부 API는 기본적으로 막혀 있어요. 리플렉션으로 비공개 멤버에 접근하는 프레임워크를 위해서는 opens로 패키지를 열어 주거나 실행 옵션 --add-opens를 써요. 다만 생태계 전환이 더뎌서 많은 애플리케이션은 여전히 클래스패스에서 모든 것이 하나의 이름 없는 모듈로 실행되고, 라이브러리는 자동 모듈 이름으로 호환성을 유지해요.<br><sub>The module system introduced in Java 9 (JPMS, Project Jigsaw) groups packages into named modules and has module-info.java declare which modules a module needs (requires) and which packages it exposes to others (exports). On the class path, any public class is usable by anyone, so outside code often came to depend on public classes meant for internal use. With modules, classes in packages that are not exported cannot be accessed from other modules at compile time or run time, even when public, giving real encapsulation. A missing required module, or the same package in two modules, fails immediately at startup rather than somewhere mid-run, which is called reliable configuration. jlink builds a small custom runtime image containing only the modules the app actually uses, shrinking containers. The JDK itself is divided into modules such as java.base, java.sql and java.net.http, and JDK-internal APIs are blocked by default. The ecosystem has moved slowly, though, so many applications still run on the class path, everything in one unnamed module, while libraries stay compatible through automatic module names.</sub> |
| **JUnit 5와 Mockito**<br><sub>JUnit 5 and Mockito</sub> | JUnit 5는 애너테이션으로 테스트 생명주기를 정하고, Mockito는 협력 객체를 가짜로 바꿔 반환값을 정하고 호출을 검증해요.<br><sub>JUnit 5 defines the test lifecycle with annotations, and Mockito replaces collaborators with fakes whose return values you set and whose calls you verify.</sub> | JUnit 5(Jupiter)는 자바의 표준 테스트 프레임워크예요. @Test가 붙은 메서드가 테스트이고, @BeforeAll과 @AfterAll은 클래스 전체에서 한 번, @BeforeEach와 @AfterEach는 각 테스트의 앞뒤에서 실행돼요. 기본적으로 테스트 메서드마다 테스트 클래스의 새 인스턴스를 만들어서, 한 테스트가 필드에 남긴 상태가 다른 테스트에 새지 않아요. assertEquals, assertThrows 같은 단언으로 결과를 확인하고, @ParameterizedTest는 @ValueSource나 @CsvSource의 값마다 같은 테스트를 따로 실행해요. 단위 테스트에서 결제 API나 데이터베이스 같은 협력 객체를 진짜로 부르면 느리고 불안정하니, Mockito로 가짜 객체(mock)를 만들어요. @Mock PaymentClient pay는 호출을 기록만 하는 가짜이고, when(pay.charge(100)).thenReturn(true)로 특정 호출의 반환값을 정해요. @InjectMocks는 그 mock을 테스트 대상 OrderService에 넣어 줘요. 결과를 assertTrue로 확인한 뒤 verify(pay, times(1)).charge(100)로 협력 객체를 정확히 한 번, 올바른 인자로 불렀는지까지 검증해요. 다만 mock을 너무 많이 쓰면 구현에 얽매인 깨지기 쉬운 테스트가 되니 네트워크나 결제 같은 경계에 주로 써요. 통합 테스트는 Testcontainers로 실제 데이터베이스나 메시지 브로커를 컨테이너로 띄워 시험하고, 단위 테스트를 많이, 통합 테스트를 적당히, E2E 테스트를 조금 두는 테스트 피라미드를 기본으로 해요.<br><sub>JUnit 5 (Jupiter) is Java’s standard test framework. Methods annotated @Test are tests; @BeforeAll and @AfterAll run once per class, and @BeforeEach and @AfterEach run around each test. By default each test method gets a new instance of the test class, so state one test leaves in fields does not leak into another. Assertions such as assertEquals and assertThrows check results, and @ParameterizedTest runs the same test separately for each value from @ValueSource or @CsvSource. Calling real collaborators such as a payment API or a database from unit tests is slow and flaky, so Mockito creates fakes (mocks). @Mock PaymentClient pay is a fake that just records calls, and when(pay.charge(100)).thenReturn(true) sets the return value for a specific call. @InjectMocks injects the mock into OrderService, the class under test. After checking the result with assertTrue, verify(pay, times(1)).charge(100) confirms that the collaborator was called exactly once with the right argument. Overusing mocks produces brittle tests tied to implementation details, so they belong mainly at boundaries such as networks and payments. Integration tests use Testcontainers to start real databases or message brokers in containers, and the usual shape is a test pyramid: many unit tests, a moderate number of integration tests and a few end-to-end tests.</sub> |
| **JVM 모니터링과 진단**<br><sub>JVM monitoring and diagnostics</sub> | 스레드 덤프로 락 경합과 교착을, 힙 덤프로 메모리 누수를 찾고, JFR로 낮은 부하의 상시 기록을 남겨요. 평소엔 지표와 프로파일러로 지켜봐요.<br><sub>Thread dumps reveal lock contention and deadlocks, heap dumps reveal memory leaks, and JFR keeps a low-overhead continuous record. Taking several dumps a few seconds apart when responses hang shows where things are stuck. When memory keeps growing, take a heap dump with jcmd GC.heap\_dump and open it in a tool such as Eclipse MAT. Its dominator tree shows which objects keep others alive and block their release, revealing leaks such as an ever-growing cache HashMap. With -XX:+HeapDumpOnOutOfMemoryError, a dump is written automatically when OOM strikes. JDK Flight Recorder (JFR), built into the JVM, continuously records events such as CPU samples, allocations, GC, lock waits, I/O and exceptions at about 1% overhead, so it can stay on in production, and JDK Mission Control analyzes the recordings. jstat -gcutil shows GC area usage periodically. | **시작 시간과 네이티브 이미지**<br><sub>Startup time and native images</sub> | JVM은 시작이 느리고 정점 성능이 높아요.
