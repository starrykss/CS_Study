## 서버 구조와 런타임 · Server structure and runtime

계층형·헥사고날·모듈러 모놀리스 구조와, 동시성 모델·커넥션 풀·타임아웃·우아한 종료처럼 서버가 실제로 돌아가는 방식이에요.  
*Layered, hexagonal and modular-monolith structures, plus how servers actually run: concurrency models, connection pools, timeouts and graceful shutdown.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **계층형 구조**<br><sub>Layered architecture</sub> | 컨트롤러(HTTP)·서비스(업무 규칙)·저장소(데이터 접근)로 관심사를 나누고, 의존은 위에서 아래로만 흘러요. 가장 흔한 백엔드 구조예요.<br><sub>Layered architecture separates controllers (HTTP), services (business rules) and repositories (data access), with dependencies flowing only downward, the most common backend structure.</sub> | 컨트롤러는 HTTP 요청에서 입력을 꺼내 서비스를 부르고 결과를 응답으로 바꾸는 일만 해요. 서비스는 “재고보다 많이 주문할 수 없다” 같은 업무 규칙과 트랜잭션을 맡고 HTTP 상태 코드나 SQL을 몰라요. 저장소(Repository)는 DB 접근만 담당해서 저장 방식이 바뀌어도 위 계층은 그대로예요. 의존이 위에서 아래로만 흐르기 때문에 테스트에서는 저장소를 가짜로 바꿔 서비스 규칙만 빠르게 검증할 수 있어요. 흔한 실수는 컨트롤러에 업무 규칙이 새거나, 서비스가 요청 객체를 그대로 받는 거예요. 서비스가 수천 줄로 비대해지면 규칙을 도메인 객체로 옮기는 것이 다음 단계예요.<br><sub>Controllers only extract input from HTTP requests, call services and turn results into responses. Services own business rules such as “cannot order more than stock” and transactions, knowing nothing of status codes or SQL. Repositories handle only database access, so storage changes leave the upper layers untouched. Because dependencies flow downward only, tests can swap repositories for fakes and verify service rules quickly. Common mistakes are business rules leaking into controllers and services accepting raw request objects. When services bloat to thousands of lines, moving rules into domain objects is the next step.</sub> |
| **헥사고날 아키텍처**<br><sub>Hexagonal architecture</sub> | 도메인이 필요한 바깥 기능을 포트(인터페이스)로 정하고, 실제 기술은 어댑터로 구현해요. 의존이 기술에서 도메인 쪽으로 뒤집혀요.<br><sub>Hexagonal architecture lets the domain define the outside capabilities it needs as ports (interfaces) implemented by technology adapters, inverting dependencies toward the domain.</sub> | 포트와 어댑터라고도 불러요. 결제, 저장, 메일처럼 도메인이 바깥에 요구하는 기능을 PaymentPort 같은 인터페이스로 도메인 쪽에서 정의해요. PgAdapter, PostgresRepository 같은 어댑터가 그 인터페이스를 실제 기술로 구현하므로, 의존 방향이 “기술 → 도메인”으로 뒤집혀요(의존성 역전 원칙). 테스트에서는 FakePayment 같은 가짜 어댑터를 끼워 외부 시스템 없이 도메인 규칙을 검증하고, 결제사나 DB를 바꿀 때는 어댑터만 새로 써요. 들어오는 쪽(REST 컨트롤러, 큐 소비자)도 어댑터라서 같은 도메인을 HTTP와 메시지로 함께 쓸 수 있어요. 클린 아키텍처, 어니언 아키텍처도 같은 생각에서 나왔어요. 단순한 CRUD에는 과할 수 있고, 규칙이 복잡하고 오래 살 시스템에서 효과가 커요.<br><sub>Also called ports and adapters, it has the domain define what it needs from outside, payment, storage, mail, as interfaces such as PaymentPort. Adapters such as PgAdapter or PostgresRepository implement those interfaces with real technology, inverting dependencies so technology points at the domain (the dependency inversion principle). Tests plug in fake adapters such as FakePayment to check domain rules without external systems, and switching payment providers or databases means writing a new adapter. Inbound sides, REST controllers or queue consumers, are adapters too, so one domain serves HTTP and messages alike. Clean architecture and onion architecture share the idea. It can be overkill for simple CRUD and pays off in complex, long-lived systems.</sub> |
| **모듈러 모놀리스**<br><sub>Modular monoliths</sub> | 하나로 배포하지만 안쪽은 기능 모듈로 엄격히 나눠요. 모듈끼리는 공개 API로만 호출해서, 필요할 때 한 모듈만 서비스로 떼어내기 쉬워요.<br><sub>A modular monolith deploys as one unit but divides strictly into feature modules that call each other only through public APIs, making it easy to extract a single module later.</sub> | 처음부터 마이크로서비스로 나누면 네트워크 호출, 분산 트랜잭션, 배포 파이프라인 같은 비용을 너무 일찍 떠안아요. 모듈러 모놀리스는 orders, billing, catalog처럼 기능 모듈을 나누고, 모듈 사이 호출은 api.ts 같은 공개 인터페이스로만 허용해요. 데이터도 모듈별 스키마로 나누고 다른 모듈 테이블에 직접 조인하지 않아야 진짜 경계가 생겨요. 경계 규칙은 ArchUnit, eslint-plugin-boundaries, Spring Modulith 같은 도구로 자동 검사해요. 한 프로세스 안이라 디버깅과 트랜잭션이 쉽고, 트래픽이나 팀이 커지면 그 모듈만 마이크로서비스로 떼어내요. 많은 팀이 이 구조를 기본 출발점으로 권해요.<br><sub>Starting with microservices takes on network calls, distributed transactions and deployment pipelines far too early. A modular monolith splits feature modules such as orders, billing and catalog and allows calls between them only through public interfaces such as api.ts. Data is split into per-module schemas with no direct joins into other modules’ tables, creating real boundaries. Tools such as ArchUnit, eslint-plugin-boundaries or Spring Modulith check the rules automatically. Running in one process keeps debugging and transactions simple, and when traffic or teams grow, that one module is extracted into a microservice. Many teams recommend this structure as the default starting point.</sub> |
| **동시성 모델**<br><sub>Concurrency models</sub> | 요청당 스레드, 이벤트 루프, 가벼운 스레드(고루틴·가상 스레드)는 I/O를 기다리는 동안 다른 요청을 처리하는 방식이 달라요.<br><sub>Thread-per-request, event loops and lightweight threads (goroutines, virtual threads) differ in how they serve other requests while waiting on I/O.</sub> | 대부분의 백엔드는 CPU보다 DB나 외부 API를 기다리는 시간이 길어요. 요청당 OS 스레드 모델(전통적인 Spring MVC 등)은 코드가 단순하지만 스레드가 기다리며 놀고, 스레드마다 메모리를 써서 동시 연결 수에 한계가 있어요. Node.js의 이벤트 루프는 스레드 하나가 여러 요청을 번갈아 처리하고 I/O는 운영체제에 맡겨서 적은 자원으로 많은 연결을 다뤄요. Go의 고루틴과 Java 21의 가상 스레드는 아주 가벼운 스레드를 수십만 개 만들어 소수의 OS 스레드에 올리므로, 동기 코드처럼 쓰면서도 효율이 높아요. 이벤트 루프에서 무거운 계산을 하면 모든 요청이 멈추니 CPU 작업은 워커 스레드나 별도 서비스로 옮겨요. 어떤 모델이든 처리량의 상한은 결국 DB 같은 병목이 정해요.<br><sub>Most backends spend more time waiting on databases or external APIs than on CPU. Thread-per-request with OS threads, as in classic Spring MVC, keeps code simple but leaves threads idle while waiting, each costing memory and capping concurrency. Node.js’s event loop interleaves many requests on one thread and hands I/O to the operating system, serving many connections with few resources. Go goroutines and Java 21 virtual threads run hundreds of thousands of lightweight threads on a few OS threads, keeping synchronous-style code with high efficiency. Heavy computation on an event loop stalls every request, so CPU work moves to worker threads or separate services. Whatever the model, throughput is ultimately capped by bottlenecks such as the database.</sub> |
| **커넥션 풀**<br><sub>Connection pools</sub> | DB 연결을 미리 열어 두고 요청이 빌려 쓰고 반납해요. 반납을 잊으면 풀이 고갈되고, 인스턴스 수 × 풀 크기는 DB 최대 연결 안이어야 해요.<br><sub>A connection pool opens database connections ahead of time for requests to borrow and return; forgotten returns exhaust it, and instances × pool size must fit the database’s connection limit.</sub> | DB 연결은 TCP, TLS, 인증을 거쳐야 해서 매 요청마다 새로 만들면 느려요. 커넥션 풀은 연결을 미리 열어 두고 요청이 빌려 쓰게 해서 그 비용을 없애요. 쿼리가 끝나면 finally에서 반드시 반납해야 하고, 빠뜨리면 연결이 새어 풀이 고갈되고 새 요청은 줄을 서다 connectionTimeout으로 실패해요. 풀 크기는 클수록 좋은 게 아니에요 · DB는 코어 수에 비례한 동시 쿼리에서 가장 효율적이라 과한 연결은 오히려 느려져요. 서버를 10대로 늘리면 10 × max만큼 연결이 생기므로 DB의 max\_connections를 넘지 않게 하고, 넘으면 PgBouncer 같은 연결 프록시로 모아요. 풀 대기 시간과 사용률은 꼭 지표로 봐요.<br><sub>Database connections go through TCP, TLS and authentication, so creating one per request is slow. A pool keeps connections open for requests to borrow, removing that cost. Connections must be returned in finally after the query; forgetting leaks them until the pool is exhausted and new requests queue and fail on connectionTimeout. Bigger is not better: databases are most efficient with concurrency proportional to their cores, so excess connections slow things down. Scaling to ten servers creates ten times max connections, which must stay under the database’s max\_connections, or be funneled through a proxy such as PgBouncer. Always monitor pool wait time and utilization.</sub> |
| **타임아웃과 데드라인**<br><sub>Timeouts and deadlines</sub> | 모든 외부 호출에 시간 상한을 걸고, 요청 전체의 남은 시간(데드라인)을 하위 호출에 전달해요. 느린 의존성 하나가 서버 전체를 멈추지 않게 해요.<br><sub>Put a time limit on every outbound call and pass the request’s remaining time (deadline) downstream, so one slow dependency cannot freeze the whole server.</sub> | 타임아웃 없는 호출은 상대가 응답하지 않으면 끝없이 기다릴 수 있어요. 그동안 스레드와 DB 연결이 묶여 쌓이고, 결국 서버 전체가 새 요청을 받지 못하는 연쇄 장애가 생겨요. 그래서 HTTP 호출, DB 쿼리, 잠금 대기까지 모든 기다림에 AbortSignal.timeout 같은 상한을 걸어요. 요청 하나에 2초 같은 전체 예산을 정하고, 하위 호출에는 남은 시간만 넘기면 이미 늦은 요청을 위해 헛수고하지 않아요(gRPC는 데드라인을 자동 전파해요). 클라이언트가 연결을 끊었다면 진행 중인 하위 작업도 취소해 자원을 아껴요. 타임아웃 값은 평소 p99 지연보다 조금 길게 잡고, 재시도까지 합친 시간이 예산을 넘지 않게 해요.<br><sub>A call without a timeout can wait forever if the other side never answers. Meanwhile threads and database connections pile up, until a cascading failure leaves the server unable to accept new requests. So every wait, HTTP calls, database queries, even lock waits, gets a limit such as AbortSignal.timeout. Setting an overall budget such as 2 seconds per request and passing only the remaining time downstream avoids wasted work on requests that are already late (gRPC propagates deadlines automatically). When the client has disconnected, in-flight downstream work is cancelled to save resources. Set timeouts a little above normal p99 latency, and keep retries within the budget.</sub> |
| **우아한 종료**<br><sub>Graceful shutdown</sub> | SIGTERM을 받으면 새 요청을 막고, 처리 중인 요청을 끝내고, 연결을 정리한 뒤 종료해요. 무중단 배포의 전제 조건이에요.<br><sub>On SIGTERM, stop accepting new requests, finish in-flight ones, release connections and exit, the prerequisite for zero-downtime deploys.</sub> | 쿠버네티스 같은 오케스트레이터는 배포나 축소 때 컨테이너에 SIGTERM을 보내고, 유예 시간(기본 30초)이 지나면 SIGKILL로 강제 종료해요. 신호를 받자마자 꺼지면 처리 중이던 요청이 끊겨 사용자가 오류를 봐요. 먼저 readiness 검사를 실패시켜 로드밸런서가 새 요청을 보내지 않게 하고, 라우팅 갱신이 퍼질 짧은 시간을 기다려요. server.close()로 새 연결은 거절하면서 이미 받은 요청은 끝까지 처리하고, 큐 소비자와 DB 연결을 정리한 뒤 종료해요. 오래 걸리는 작업은 체크포인트를 남겨 다른 인스턴스가 이어받게 해요. liveness 검사는 “프로세스가 살아 있나”, readiness 검사는 “요청을 받을 준비가 됐나”를 묻는 서로 다른 질문이에요.<br><sub>Orchestrators such as Kubernetes send SIGTERM during deploys or scale-down and force SIGKILL after a grace period (30 seconds by default). Exiting immediately cuts off in-flight requests, and users see errors. First fail the readiness check so the load balancer stops sending new requests, and wait briefly for routing updates to propagate. server.close() refuses new connections while finishing accepted requests, then queue consumers and database connections are closed before exiting. Long jobs leave checkpoints so another instance can take over. Liveness asks “is the process alive?” while readiness asks “is it ready for traffic?”, two different questions.</sub> |

## 오래 쓰는 API 설계 · Designing APIs that last

*Recurring practical API designs: versioning, error formats, idempotency keys, webhooks, file uploads, asynchronous job APIs and input validation.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **API 버전 관리**<br><sub>API versioning</sub> | 필드 추가처럼 호환되는 변경은 그 자리에서 하고, 삭제·이름 변경처럼 깨는 변경은 새 버전으로 해요. 옛 버전은 예고하고 사용량을 보며 종료해요.<br><sub>Make compatible changes such as adding fields in place, put breaking ones such as removals or renames in new versions, and retire old versions with notice while watching usage.</sub> | 앱 스토어에 남은 옛 앱처럼 API 클라이언트는 한 번에 바뀌지 않아서, 여러 버전이 한동안 함께 살아요. 버전은 /v1/ 같은 URL이나 Accept 헤더로 구분해요. 응답에 필드를 추가하거나 선택 매개변수를 더하는 건 하위 호환이고, 클라이언트가 모르는 필드를 무시하게 만들어 두면 자유롭게 늘릴 수 있어요. 필드 삭제, 이름 변경, 타입이나 의미 변경, 필수 매개변수 추가는 기존 클라이언트를 깨뜨리므로 새 버전에서만 해요. 옛 버전은 Deprecation·Sunset 헤더와 문서, 이메일로 종료 일정을 알리고, 버전별 호출량을 측정해 충분히 줄었을 때 내려요. 버전을 자주 올리기보다 처음부터 호환을 지키도록 설계하고 계약 테스트로 깨는 변경을 미리 잡는 게 더 중요해요.<br><sub>API clients, like old apps lingering in app stores, never change all at once, so several versions coexist for a while, distinguished by URLs such as /v1/ or the Accept header. Adding response fields or optional parameters is backward compatible, especially when clients ignore unknown fields. Removing or renaming fields, changing types or meanings, or adding required parameters breaks existing clients, so those happen only in new versions. Old versions announce their end through Deprecation and Sunset headers, docs and email, and are retired once per-version traffic has dropped enough. Designing for compatibility from the start and catching breaking changes with contract tests matters more than frequent version bumps.</sub> |
| **오류 응답 설계**<br><sub>Error response design</sub> | 정확한 상태 코드에 RFC 9457 Problem Details 형식(type·title·status·detail·instance)으로 모든 오류를 같은 모양으로 돌려줘요.<br><sub>Return every error in one shape: the right status code plus the RFC 9457 Problem Details format of type, title, status, detail and instance.</sub> | 먼저 상태 코드를 정확히 골라요 · 400(형식 오류), 401(인증 필요), 403(권한 없음), 404(없음), 409(충돌), 422(규칙 위반), 429(너무 많음)는 클라이언트가 고칠 문제이고, 5xx는 서버 문제라 재시도할 수 있어요. RFC 9457 Problem Details는 application/problem+json으로 type(오류 종류 URI), title, status, detail, instance를 담는 표준 형식이에요. 클라이언트 코드는 바뀌지 않는 type으로 분기하고, title과 detail은 사람이 읽을 설명이라 문구를 고쳐도 프로그램이 깨지지 않아요. 검증 오류처럼 필드별 정보가 필요하면 errors 같은 확장 필드를 더해요. 응답에는 로그를 찾을 수 있는 추적 ID를 넣되, 스택 트레이스나 SQL 같은 내부 정보는 절대 넣지 않아요. 모든 엔드포인트가 같은 형식을 쓰도록 오류 변환을 한 곳(예외 필터, 미들웨어)에서 해요.<br><sub>Start by choosing status codes precisely: 400 (malformed), 401 (authentication needed), 403 (forbidden), 404 (missing), 409 (conflict), 422 (rule violation) and 429 (too many) are for clients to fix, while 5xx are server problems that may be retried. RFC 9457 Problem Details is a standard application/problem+json shape carrying type (an error-kind URI), title, status, detail and instance. Client code branches on the stable type, while title and detail are human-readable, so rewording never breaks programs. Per-field information, such as validation errors, goes in extension fields such as errors. Responses include a trace ID for finding logs but never internals such as stack traces or SQL. Convert errors in one place, an exception filter or middleware, so every endpoint matches.</sub> |
| **멱등 키**<br><sub>Idempotency keys</sub> | 클라이언트가 Idempotency-Key 헤더를 붙이면 서버는 키별 결과를 저장해 두고, 같은 키의 재시도에는 저장된 응답을 돌려줘서 결제가 두 번 되지 않아요.<br><sub>With an Idempotency-Key header from the client, the server stores results per key and replays the stored response on retries, so payments never happen twice.</sub> | POST로 결제를 요청했는데 응답이 네트워크에서 끊기면, 클라이언트는 결제가 됐는지 알 수 없어 재시도해야 할지 고민하게 돼요. 클라이언트가 요청마다 UUID로 Idempotency-Key를 만들어 보내면, 서버는 처음 처리한 결과를 키와 함께 저장하고 같은 키의 재시도에는 저장된 응답을 그대로 돌려줘요. 같은 키가 거의 동시에 두 번 도착하면 잠금이나 DB 고유 제약으로 하나만 처리하고, 나머지는 기다리게 하거나 409로 돌려보내요. 같은 키에 다른 본문이 오면 실수이므로 422로 거부해요. 키는 24시간처럼 정해진 기간 보관하고 지워요. 결제·주문·송금처럼 중복이 치명적인 POST에는 사실상 필수인 패턴이고, 큰 결제 API들이 널리 쓰는 방식이에요.<br><sub>When a POST payment succeeds but the reply is lost on the network, the client cannot tell whether it was charged and hesitates to retry. If the client sends a UUID Idempotency-Key with each request, the server stores the first result with the key and replays it for retries with the same key. When the same key arrives twice almost simultaneously, a lock or a unique constraint lets only one proceed while the other waits or gets a 409. A reused key with a different body is a client mistake and is rejected with 422. Keys are kept for a set period such as 24 hours. The pattern is practically mandatory for POSTs where duplicates hurt, such as payments, orders and transfers, and major payment APIs use it widely.</sub> |
| **웹훅**<br><sub>Webhooks</sub> | 이벤트가 생기면 상대 서비스가 우리 URL로 HTTP 요청을 보내요. 서명을 검증하고, 빠르게 200을 돌려주고, 이벤트 id로 중복을 걸러요.<br><sub>Webhooks have another service call our URL when events happen; verify signatures, return 200 quickly, and dedupe by event id.</sub> | 결제 완료, 배송 상태 변경처럼 다른 서비스에서 일어난 일을 계속 조회(폴링)하는 대신 상대가 우리 URL로 알려주는 방식이에요. 그 URL은 누구나 호출할 수 있으니 공유 비밀키로 만든 HMAC 서명과 타임스탬프를 확인해 위조와 재전송 공격을 막고, 비교는 타이밍 안전 함수로 해요. 받은 쪽은 무거운 처리를 큐에 넘기고 몇 초 안에 200을 돌려줘요 · 응답이 늦거나 실패하면 보내는 쪽이 간격을 늘리며 다시 보내요. 그래서 같은 이벤트가 여러 번 올 수 있어 이벤트 id로 처리 여부를 기록해 중복을 걸러요. 이벤트 순서가 뒤바뀔 수도 있으니 중요한 상태는 받은 뒤 상대 API로 다시 조회해 확정하기도 해요. 우리가 웹훅을 보낼 때도 서명, 재시도, 이벤트 id, 수동 재전송 기능을 제공해요.<br><sub>Instead of repeatedly polling another service for events such as completed payments or shipping updates, webhooks have it notify our URL. Since anyone can call that URL, verify an HMAC signature made with a shared secret plus a timestamp to block forgery and replays, comparing with a timing-safe function. Receivers queue heavy work and return 200 within seconds, because slow or failed replies make senders retry with growing delays. That means the same event can arrive several times, so record processed event ids to filter duplicates. Events may also arrive out of order, so important state is sometimes confirmed by querying the provider’s API afterward. When we send webhooks, we provide signatures, retries, event ids and manual redelivery too.</sub> |
| **파일 업로드**<br><sub>File uploads</sub> | 서버는 짧게 유효한 서명 URL만 발급하고, 브라우저가 스토리지로 파일을 직접 올려요. 업로드 완료 이벤트로 검사·썸네일 같은 후처리를 해요.<br><sub>The server only issues short-lived signed URLs, the browser uploads straight to storage, and upload events trigger post-processing such as scanning and thumbnails.</sub> | 파일을 앱 서버를 거쳐 올리면 서버의 대역폭과 메모리가 파일 크기만큼 들고, 큰 파일이 몰리면 다른 API까지 느려져요. 대신 서버는 S3 같은 객체 스토리지에 올릴 수 있는 presigned URL을 몇 분짜리로 만들어 주고, 브라우저가 그 URL로 직접 PUT해요. 서명 조건에 허용 크기와 Content-Type을 넣어 다른 파일은 스토리지가 거부하게 하고, 파일 키는 사용자 입력이 아닌 서버가 정한 값으로 만들어 경로 조작을 막아요. 수백 MB 이상은 멀티파트 업로드로 조각내 병렬로 올리고 실패한 조각만 다시 보내요. 업로드 완료 이벤트로 바이러스 검사, 이미지 리사이즈, 메타데이터 추출을 하고, 검사가 끝나기 전에는 비공개로 둬요. 다운로드도 기간이 제한된 서명 URL로 제공해요.<br><sub>Proxying files through the app server spends bandwidth and memory per file, and a burst of large uploads slows every other API. Instead the server issues a presigned URL valid for a few minutes for object storage such as S3, and the browser PUTs to it directly. Allowed size and Content-Type go into the signature conditions so storage rejects other files, and file keys are server-generated rather than user-supplied to prevent path tricks. Files of hundreds of megabytes use multipart uploads, sending chunks in parallel and retrying only failed ones. Upload-complete events trigger virus scans, resizing and metadata extraction, keeping files private until checked. Downloads are served through time-limited signed URLs too.</sub> |
| **비동기 작업 API**<br><sub>Asynchronous job APIs</sub> | 오래 걸리는 작업은 202 Accepted로 접수만 하고 상태 URL을 돌려줘요. 클라이언트는 상태를 확인하거나 웹훅·SSE로 완료 알림을 받아요.<br><sub>Long-running work is accepted with 202 and a status URL, and clients poll the status or receive completion via webhook or SSE.</sub> | 리포트 생성이나 대용량 내보내기처럼 수십 초 이상 걸리는 일을 요청 안에서 처리하면 로드밸런서나 브라우저의 타임아웃에 걸려요. POST에 202 Accepted와 Location: /jobs/77을 돌려주고 실제 작업은 큐의 워커가 맡아요. 클라이언트는 Retry-After 간격으로 상태 URL을 확인하고, 서버는 queued, running, done, failed 같은 상태와 진행률을 알려줘요. 완료되면 결과 리소스의 위치를 주고, 실패하면 Problem Details 형식의 오류를 담아요. 폴링 대신 웹훅이나 SSE로 완료를 밀어줄 수도 있어요. 작업 상태는 DB에 저장해서 어느 서버가 받든 조회되게 하고, 같은 요청의 중복 접수는 멱등 키로, 취소는 DELETE /jobs/77 같은 엔드포인트로 제공해요.<br><sub>Running work that takes tens of seconds, such as report generation or large exports, inside a request hits load balancer or browser timeouts. The POST returns 202 Accepted with Location: /jobs/77 while a queue worker does the real work. Clients poll the status URL at the Retry-After interval, and the server reports states such as queued, running, done and failed along with progress. On completion it points to the result resource, and on failure it carries a Problem Details error. Webhooks or SSE can push completion instead of polling. Job state lives in the database so any server can answer, duplicate submissions are prevented with idempotency keys, and cancellation is offered through an endpoint such as DELETE /jobs/77.</sub> |
| **입력 검증**<br><sub>Input validation</sub> | 신뢰 경계에서 입력을 한 번 파싱해 믿을 수 있는 타입으로 바꾸고, 그 뒤 코드는 타입을 믿어요. 허용 목록과 크기 제한으로 남용도 막아요.<br><sub>Parse input once at trust boundaries into trusted types so later code can rely on them, and block abuse with allowlists and size limits.</sub> | isValid(input)로 검사만 하고 원본을 계속 넘기면, 안쪽 함수들은 그 값이 검사됐는지 알 수 없어 다시 의심하거나 검사를 빠뜨려요. “검증 말고 파싱하라(Parse, don’t validate)”는 경계에서 Zod 같은 스키마로 파싱해 Order 같은 타입으로 바꾸고, 실패하면 바로 400을 돌려주는 방식이에요. 그 뒤 코드는 타입 시스템이 보장하는 값만 다뤄서 방어 코드가 줄어요. 경계는 HTTP 요청뿐 아니라 큐 메시지, 업로드 파일, 외부 API 응답, 환경 변수처럼 신뢰 수준이 바뀌는 모든 곳이에요. 알려진 필드만 받는 허용 목록으로 role 같은 값을 몰래 넣는 대량 할당을 막고, 본문 크기·배열 길이·문자열 길이에 상한을 둬 서비스 거부 공격을 줄여요. 검증과 별개로 SQL은 매개변수 바인딩, HTML 출력은 이스케이프로 처리해요.<br><sub>Checking with isValid(input) while passing the raw input on leaves inner functions unsure whether it was checked, so they re-check or forget to. “Parse, don’t validate” means parsing at the edge with a schema such as Zod into a type such as Order, returning 400 immediately on failure. Later code then handles only values guaranteed by the type system, shrinking defensive code. Boundaries include not only HTTP requests but queue messages, uploaded files, external API responses and environment variables, anywhere trust changes. Allowlists of known fields block mass assignment of smuggled values such as role, and limits on body size, array length and string length reduce denial of service. Separately from validation, SQL uses parameter binding and HTML output is escaped.</sub> |

| **ORM · 쿼리 빌더 · SQL**<br><sub>ORMs, query builders and SQL</sub> | ORM은 생산성, 쿼리 빌더는 타입 있는 SQL, 원시 SQL은 완전한 통제를 줘요. 쿼리 성격에 맞게 섞어 쓰고, 값은 언제나 매개변수로 바인딩해요.<br><sub>ORMs give productivity, query builders give typed SQL and raw SQL gives full control; mix them by query type and always bind values as parameters.</sub> | ORM(TypeORM, Prisma, Hibernate 등)은 테이블을 객체로 다뤄 CRUD와 관계 탐색이 빠르지만, 실제로 나가는 SQL이 가려져 N+1 쿼리나 필요 없는 컬럼까지 읽는 과한 조회가 생기기 쉬워요. Kysely, Drizzle, jOOQ 같은 쿼리 빌더는 SQL과 비슷한 모양으로 쓰면서 테이블·컬럼 이름과 결과 타입을 컴파일 단계에서 검사해 줘요. 윈도 함수, CTE, 복잡한 리포트처럼 SQL이 가장 잘 표현하는 쿼리는 원시 SQL로 쓰는 게 읽기도 성능도 좋아요. 한 프로젝트에서 섞어 써도 되고, 개발 중에는 실행되는 SQL을 로그로 확인하는 습관이 중요해요. 어떤 방식이든 사용자 입력은 문자열로 이어 붙이지 말고 $1 같은 매개변수로 바인딩해 SQL 인젝션을 막아요.<br><sub>ORMs such as TypeORM, Prisma or Hibernate treat tables as objects for fast CRUD and relation navigation, but they hide the SQL they emit, inviting N+1 queries and overfetching of unneeded columns. Query builders such as Kysely, Drizzle or jOOQ stay close to SQL while checking table and column names and result types at compile time. Queries SQL expresses best, such as window functions, CTEs and complex reports, read and perform better as raw SQL. Mixing them in one project is fine, and logging executed SQL during development is a valuable habit. Whatever the style, never concatenate user input into strings; bind it as parameters such as $1 to prevent SQL injection.</sub> |
| **무중단 스키마 변경**<br><sub>Zero-downtime schema changes</sub> | 컬럼 추가(확장) → 같이 쓰기·백필 → 읽기 전환 → 옛 컬럼 삭제(축소)로 나눠 배포해요. 옛·새 앱이 함께 돌아도 깨지지 않아요.<br><sub>Deploy schema changes in steps, add the column (expand), dual-write and backfill, switch reads, then drop the old column (contract), so old and new app versions both keep working.</sub> | 배포 중에는 옛 버전과 새 버전 앱이 잠시 함께 돌아요. 그래서 name 컬럼을 full\_name으로 한 번에 바꾸면 옛 버전이 없는 컬럼을 찾다 오류를 내요. 확장-축소(expand-contract) 방식은 먼저 새 컬럼을 NULL 허용으로 추가하고, 다음 배포에서 앱이 두 컬럼에 모두 쓰게 한 뒤 기존 데이터를 작은 묶음으로 백필해요. 데이터가 맞춰지면 읽기를 새 컬럼으로 옮기고, 한동안 지켜본 뒤 아무 버전도 옛 컬럼을 쓰지 않을 때 삭제해요. 각 단계는 따로 배포되고 언제든 되돌릴 수 있어요. 큰 테이블에 인덱스를 만들 땐 CREATE INDEX CONCURRENTLY로 쓰기 잠금을 피하고, NOT NULL 제약은 데이터를 채운 뒤에 걸어요. 마이그레이션 파일은 코드와 함께 버전 관리하고 앱 배포 전에 적용해요.<br><sub>During a deploy, old and new app versions briefly run side by side, so renaming name to full\_name in one step makes the old version fail looking for a missing column. The expand-contract approach first adds the new column as nullable, then deploys an app that writes both columns while existing rows are backfilled in small batches. Once the data matches, reads move to the new column, and after a watch period the old column is dropped when no version uses it. Each step is deployed separately and can be rolled back. Building indexes on big tables with CREATE INDEX CONCURRENTLY avoids write locks, and NOT NULL constraints come only after the data is filled. Migration files are versioned with the code and applied before app deploys.</sub> |
| **트랜잭션 경계**<br><sub>Transaction boundaries</sub> | 함께 원자적이어야 할 DB 작업만 짧은 트랜잭션으로 묶고, 결제 API 같은 외부 호출은 커밋 뒤에 해요. 실패는 보상 처리나 아웃박스로 다뤄요.<br><sub>Wrap only database work that must be atomic in short transactions, make external calls such as payment APIs after commit, and handle failures with compensation or an outbox.</sub> | 주문 저장과 재고 차감처럼 둘 중 하나만 반영되면 안 되는 작업을 하나의 트랜잭션으로 묶어요. 트랜잭션 안에서 결제 API처럼 몇 초 걸리는 외부 호출을 하면 그동안 행 잠금과 DB 연결을 붙잡아 다른 요청이 줄을 서고, 교착 상태도 늘어요. 게다가 DB를 롤백해도 이미 처리된 결제는 취소되지 않아서 원자성이 오히려 거짓이 돼요. 그래서 트랜잭션은 DB 작업만으로 짧게 끝내고, 외부 호출은 커밋한 뒤에 해요. 커밋 뒤의 작업이 실패하면 주문 취소 같은 보상 처리를 하고, 이벤트 발행처럼 반드시 일어나야 하는 일은 같은 트랜잭션에 아웃박스 행을 써 두고 나중에 보내는 패턴으로 보장해요. 트랜잭션은 보통 서비스 메서드 단위로 열고, 저장소는 받은 트랜잭션 안에서만 동작하게 해요.<br><sub>Work where partial application is unacceptable, such as saving an order and decrementing stock, goes in one transaction. Making a seconds-long external call such as a payment API inside it holds row locks and connections, queueing other requests and raising deadlocks. Worse, a database rollback never undoes a payment already processed, so the atomicity becomes a lie. Transactions therefore contain only database work and finish quickly, with external calls after commit. When post-commit work fails, compensate, for instance by cancelling the order, and guarantee must-happen work such as event publishing by writing an outbox row in the same transaction and sending it later. Transactions usually open per service method, with repositories operating only inside the transaction they are given.</sub> |
| **캐시 전략**<br><sub>Cache strategies</sub> | 읽기는 캐시 어사이드, 쓰기는 write-through·write-behind 중에서, 위치는 프로세스 메모리 → Redis → DB 계층으로 데이터의 신선도 요구에 맞게 골라요.<br><sub>Choose read (cache-aside) and write (write-through, write-behind) strategies and layers (process memory, Redis, database) according to how fresh the data must be.</sub> | 캐시 어사이드는 읽을 때 캐시에 없으면 DB에서 가져와 저장하는 가장 흔한 방식이에요. write-through는 DB에 쓸 때 캐시도 함께 갱신해서 읽기가 항상 최신이지만 쓰기가 조금 느려지고, write-around는 쓰기 때 캐시를 비워 다음 읽기에 채우게 해요. write-behind는 캐시에 먼저 쓰고 DB 반영은 모아서 나중에 해서 빠르지만, 반영 전에 캐시가 죽으면 데이터를 잃어요. 프로세스 메모리(L1)는 마이크로초, Redis(L2)는 밀리초, DB는 수십 밀리초 단위라 뜨거운 키는 가까운 층에 둬요. 서버마다 있는 L1은 변경 알림(pub/sub)으로 함께 무효화하고, TTL에 무작위 지터를 더해 한꺼번에 만료되며 DB로 몰리는 걸 피해요. 캐시는 원본이 아니라서 사라져도 시스템이 동작해야 해요.<br><sub>Cache-aside, the most common approach, loads from the database and stores on a miss. Write-through updates the cache alongside database writes so reads are always fresh at the cost of slower writes, while write-around evicts on write and refills on the next read. Write-behind writes to the cache first and flushes to the database in batches, fast but lossy if the cache dies before flushing. Process memory (L1) answers in microseconds, Redis (L2) in milliseconds and the database in tens of milliseconds, so hot keys live in nearer layers. Per-server L1 caches are invalidated together through pub/sub, and random jitter on TTLs avoids synchronized expiry stampeding the database. A cache is not the source of truth, so the system must work without it.</sub> |
| **Redis 활용**<br><sub>Using Redis</sub> | Redis는 캐시를 넘어 원자적 카운터, 순위표(정렬 집합), 간단한 잠금, 세션, 스트림 큐까지 맡아요. 알맞은 자료구조를 고르는 게 핵심이에요.<br><sub>Beyond caching, Redis handles atomic counters, leaderboards (sorted sets), simple locks, sessions and stream queues, and choosing the right data structure is key.</sub> | Redis는 메모리 기반 키-값 저장소로, 명령 하나하나가 단일 스레드에서 원자적으로 실행돼요. INCR과 EXPIRE를 함께 쓰면 사용자별 요청 수를 세는 속도 제한 카운터가 되고, 정렬 집합(ZADD, ZREVRANGE)은 점수 순서를 유지해 순위표를 명령 한 줄로 만들어요. SET key value NX PX 5000은 “없을 때만 저장, 5초 뒤 자동 만료”라서 간단한 분산 잠금으로 쓰이고, SETEX로 세션을 만료 시간과 함께 저장해요. 해시는 객체 필드 저장, 스트림(XADD, 소비자 그룹)은 작업 큐와 이벤트 로그에 써요. 모든 키에 만료 시간을 두는 습관이 메모리 폭증을 막고, KEYS 같은 전체 탐색 명령이나 거대한 키는 서버 전체를 멈추게 할 수 있어 피해요. 영속화(RDB, AOF)는 옵션이므로 유일한 원본 데이터를 맡길 땐 신중해야 해요.<br><sub>Redis is an in-memory key-value store whose commands each run atomically on a single thread. INCR with EXPIRE makes per-user rate-limit counters, and sorted sets (ZADD, ZREVRANGE) keep score order so a leaderboard is one command. SET key value NX PX 5000 means “store only if absent, expire in 5 s”, a simple distributed lock, and SETEX stores sessions with expiry. Hashes store object fields, and streams (XADD with consumer groups) back job queues and event logs. Giving every key an expiry prevents memory blowups, while full scans such as KEYS or huge keys can stall the whole server and should be avoided. Persistence (RDB, AOF) is optional, so be careful using Redis as the only copy of data.</sub> |
| **소프트 삭제와 감사 로그**<br><sub>Soft deletes and audit logs</sub> | 행을 지우는 대신 deleted\_at에 삭제 시각을 기록해 복구할 수 있게 하고, 누가 무엇을 바꿨는지는 감사 로그로 남겨요.<br><sub>Instead of deleting rows, record the deletion time in deleted\_at so data can be restored, and keep audit logs of who changed what.</sub> | 소프트 삭제는 DELETE 대신 deleted\_at = now()로 표시해서 실수로 지운 데이터를 되살리고, 삭제 이력을 분석할 수 있게 해요. 대신 모든 조회에 deleted\_at IS NULL 조건이 빠짐없이 붙어야 해서 ORM의 전역 필터, 뷰, 행 수준 보안으로 강제해요. 지운 계정의 이메일로 다시 가입하면 고유 제약에 걸리므로, 살아 있는 행에만 적용되는 부분 인덱스(WHERE deleted\_at IS NULL)로 고유성을 정의해요. 연관된 댓글이나 주문을 함께 숨길지, 오래된 삭제 행을 언제 아카이브할지도 정책으로 정해요. 감사 로그는 누가, 언제, 무엇을, 이전 값과 이후 값으로 남겨 보안 사고 조사와 규정 준수에 써요. 개인정보 삭제 요청처럼 법적으로 지워야 하는 경우에는 소프트 삭제가 아니라 진짜 삭제(또는 익명화)를 해야 해요.<br><sub>Soft deletion marks rows with deleted\_at = now() instead of DELETE, allowing accidental deletions to be restored and deletion history to be analyzed. In return, every query must include deleted\_at IS NULL, enforced with ORM global filters, views or row-level security. Re-signing up with a deleted account’s email trips the unique constraint, so uniqueness is defined with a partial index covering only live rows (WHERE deleted\_at IS NULL). Policies decide whether related comments or orders are hidden too and when old deleted rows are archived. Audit logs record who, when, what, and before and after values, supporting incident investigation and compliance. Legal erasure, such as personal data deletion requests, requires true deletion or anonymization rather than soft deletion.</sub> |
| **멀티테넌시**<br><sub>Multitenancy</sub> | 여러 고객사가 한 시스템을 함께 써요. 공유 테이블 + tenant\_id(+RLS), 테넌트별 스키마, 테넌트별 DB 중 격리 수준과 비용에 맞게 골라요.<br><sub>Multitenancy lets many customer organizations share one system, choosing shared tables with tenant\_id (plus RLS), schema per tenant or database per tenant by isolation and cost.</sub> | B2B SaaS는 여러 회사(테넌트)의 데이터를 한 시스템에서 다뤄요. 가장 흔한 공유 테이블 방식은 모든 행에 tenant\_id를 두고 쿼리마다 조건을 거는데, 저렴하고 운영이 쉽지만 WHERE 하나만 빠져도 다른 회사 데이터가 새요. PostgreSQL의 행 수준 보안(RLS)은 연결에 설정한 테넌트의 행만 보이도록 DB가 강제해서 앱의 실수를 막아요. 테넌트별 스키마나 테넌트별 DB로 갈수록 격리, 백업·복구, 고객별 맞춤이 쉬워지지만 마이그레이션 관리와 비용이 커져요. 그래서 대부분은 공유로 시작하고 큰 고객만 전용 DB로 떼어내는 혼합 방식을 써요. 한 테넌트가 자원을 독차지하는 noisy neighbor 문제는 테넌트별 사용량 제한과 지표로 다뤄요. 테넌트 정보는 인증 토큰에서 꺼내 요청 문맥에 두고, 캐시 키와 로그에도 포함해요.<br><sub>B2B SaaS handles data from many companies (tenants) in one system. The common shared-table approach puts a tenant\_id on every row and filters every query, cheap and easy to run, but one missing WHERE leaks another company’s data. PostgreSQL row-level security makes the database show only rows for the tenant set on the connection, guarding against app mistakes. Schema-per-tenant or database-per-tenant improve isolation, backup and restore, and per-customer customization, at higher migration and cost overhead. Most teams start shared and move only large customers to dedicated databases, a hybrid model. Noisy neighbors hogging resources are handled with per-tenant quotas and metrics. The tenant comes from the auth token into request context and is included in cache keys and logs.</sub> |

| **회복 탄력성 패턴**<br><sub>Resilience patterns</sub> | 외부 호출을 타임아웃 → 재시도 → 서킷 브레이커 → 벌크헤드 → 폴백으로 겹겹이 감싸 한 의존성의 장애가 전체로 번지지 않게 해요.<br><sub>Wrap outbound calls in layers, timeouts, retries, circuit breakers, bulkheads and fallbacks, so one dependency’s failure does not spread.</sub> | 외부 API는 언제든 느려지거나 실패하므로, 첫 방어는 모든 호출에 타임아웃을 거는 거예요. 일시적 오류(503, 연결 끊김)는 지수 백오프와 무작위 지터로 간격을 두고 재시도하되, 같은 요청을 두 번 해도 안전한(멱등한) 호출에만 해요. 계속 실패하면 서킷 브레이커가 열려 한동안 호출 자체를 막고 즉시 실패시켜, 상대가 회복할 시간을 주고 우리 쪽 자원도 아껴요. 벌크헤드는 의존성마다 동시 호출 수를 따로 제한해서, 결제사가 느려져도 검색이나 로그인이 쓸 스레드와 연결은 남아 있게 해요. 그래도 실패하면 캐시된 값, 기본값, “나중에 처리” 대기열 같은 폴백으로 기능을 줄여서라도 응답해요. 재시도가 겹겹이 쌓이면 재시도 폭주로 상대를 더 괴롭히니, 재시도는 한 계층에서만 하고 전체 시간 예산 안에서 해요.<br><sub>External APIs can slow down or fail at any moment, so the first defense is a timeout on every call. Transient errors such as 503s or dropped connections are retried with exponential backoff and random jitter, but only for calls that are safe to repeat (idempotent). Persistent failure opens a circuit breaker that blocks calls for a while and fails fast, giving the dependency time to recover and saving our resources. Bulkheads cap concurrent calls per dependency, so a slow payment provider leaves threads and connections for search or login. When all else fails, fallbacks such as cached values, defaults or a “process later” queue keep responding in degraded mode. Retries stacked across layers create retry storms that hammer the dependency, so retry at one layer only and within the overall time budget.</sub> |
| **결제 연동**<br><sub>Payment integration</sub> | 금액은 서버가 정해 저장하고, 승인 직전에 다시 비교하고, 웹훅과 매일의 대사로 최종 상태를 맞춰요. 주문 상태는 상태 기계로 관리해요.<br><sub>The server sets and stores the amount, re-checks it right before confirming, and reconciles final state through webhooks and daily matching, with order status as a state machine.</sub> | 결제는 보통 “주문 생성 → 결제창 인증 → 서버 승인 → 최종 확인” 흐름이에요. 주문을 PENDING으로 만들 때 결제 금액을 서버가 계산해 저장하고, 클라이언트가 보낸 금액은 믿지 않아요. 결제창 인증 뒤 서버가 PG의 승인 API를 부를 때 저장해 둔 금액과 결제 금액을 다시 비교해서, 브라우저에서 금액을 1,000원으로 바꾸는 조작을 막아요. 승인 응답은 네트워크에서 끊길 수 있으니 결제사의 웹훅이나 조회 API로 최종 상태를 확정하고, 상태 변경은 멱등하게 처리해요. 주문 상태는 PENDING → PAID → CANCELED/REFUNDED처럼 허용된 전이만 가능한 상태 기계로 관리해요. 매일 우리 DB와 PG의 정산 기록을 대조(대사)해서 어긋난 건을 찾아 환불이나 상태 보정을 하고, 카드 정보는 직접 저장하지 않고 PG에 맡겨요.<br><sub>Payments usually flow from order creation to authentication in the provider’s window, server confirmation and final verification. When the order is created as PENDING, the server computes and stores the amount, never trusting a client-sent value. After authentication, the server re-compares the stored amount with the payment amount before calling the provider’s confirm API, blocking tampering such as changing the price to 1,000 in the browser. Confirmation replies can drop on the network, so final state is settled via the provider’s webhook or lookup API with idempotent status changes. Order status is a state machine allowing only valid transitions such as PENDING → PAID → CANCELED/REFUNDED. Daily reconciliation compares our database with the provider’s settlement records to find mismatches for refunds or corrections, and card data is left to the provider rather than stored.</sub> |
| **알림 시스템**<br><sub>Notification systems</sub> | 업무 코드는 notify() 한 줄만 부르고, 알림 시스템이 설정 확인 → 템플릿 → 채널별 큐 → 발송 기록을 맡아요.<br><sub>Business code calls a single notify(), and the notification system handles preferences, templates, per-channel queues and delivery logs.</sub> | 주문, 결제, 배송 코드가 각자 메일과 푸시를 보내면 문구, 수신 동의, 재시도 처리가 제각각이 돼요. 알림을 공용 시스템으로 모으면 업무 코드는 notify(user, 'order.shipped', data)만 부르면 돼요. 먼저 사용자의 채널 설정, 마케팅 수신 동의, 방해 금지 시간을 확인하고, 템플릿과 사용자의 언어로 메시지를 만들어요 · 문구를 코드에서 분리하면 배포 없이 고칠 수 있어요. 이메일, 푸시, SMS를 채널별 큐로 나누면 한 공급자가 장애여도 다른 채널은 계속 나가고, 실패한 발송은 간격을 두고 재시도해요. 같은 이벤트로 두 번 보내지 않도록 중복 방지 키를 쓰고, 발송·도착·열람 상태를 기록해 문의에 답해요. 비슷한 알림이 쏟아지면 묶어서(다이제스트) 보내고, 수신 거부 링크와 동의 기록은 법적 요구사항이라 꼭 챙겨요.<br><sub>When order, payment and shipping code each send their own email and push messages, copy, consent and retries become inconsistent. Centralizing notifications lets business code simply call notify(user, 'order.shipped', data). The system first checks channel preferences, marketing consent and quiet hours, then renders templates in the user’s language, and keeping copy out of code allows edits without deploys. Per-channel queues for email, push and SMS keep one provider’s outage from blocking others, and failed sends retry with delays. Dedupe keys prevent sending twice for the same event, and sent, delivered and opened states are logged to answer support questions. Floods of similar notifications are batched into digests, and unsubscribe links and consent records are legal requirements.</sub> |
| **도메인 이벤트**<br><sub>Domain events</sub> | “주문이 결제됐다” 같은 사실을 이벤트로 발행하고, 영수증·포인트·창고 알림 같은 후속 작업은 핸들러가 구독해요. 기능을 느슨하게 연결해요.<br><sub>Publish facts such as “order paid” as events and let follow-ups such as receipts, points and warehouse alerts subscribe as handlers, loosely coupling features.</sub> | 결제 처리 코드가 영수증 발송, 포인트 적립, 창고 알림을 모두 직접 부르면 기능이 늘 때마다 결제 코드를 고쳐야 하고 하나의 실패가 전체를 막아요. 도메인 이벤트는 order.markPaid() 같은 상태 변경과 함께 OrderPaid라는 과거형 사실을 기록하고, 저장에 성공한 뒤 발행해요. 각 후속 작업은 핸들러로 이벤트를 구독해서, 결제 코드는 누가 듣는지 몰라도 되고 새 기능은 핸들러만 추가하면 돼요. 저장과 발행을 확실히 함께 하려면 같은 트랜잭션에 아웃박스 행을 써 두고 따로 보내는 패턴을 써요. 서비스 사이로 넓히면 Kafka 같은 메시지 브로커를 통한 이벤트 주도 아키텍처가 돼요. 대신 흐름이 여러 곳에 흩어져 보이니 이벤트 목록과 스키마를 문서화하고 버전을 관리하며, 핸들러는 재실행돼도 안전하게(멱등하게) 만들어요.<br><sub>When payment code directly calls receipts, points and warehouse alerts, every new feature means editing payment code, and one failure blocks everything. Domain events record a past-tense fact such as OrderPaid alongside a state change such as order.markPaid(), published after the save succeeds. Each follow-up subscribes as a handler, so payment code need not know who listens and new features only add handlers. To guarantee saving and publishing together, write an outbox row in the same transaction and send it separately. Extended across services, this becomes event-driven architecture over a message broker such as Kafka. In return, flows scatter across places, so document and version the event catalog and schemas, and keep handlers safe to rerun (idempotent).</sub> |
| **배치 작업**<br><sub>Batch jobs</sub> | 큰 데이터를 id 순서의 묶음으로 처리하고, 묶음마다 체크포인트를 남기고, 멱등하게 만들고, 쉬어 가며 운영 DB 부하를 조절해요.<br><sub>Process large data in id-ordered chunks with checkpoints after each, idempotent logic, and pauses that protect the production database.</sub> | 수백만 행을 한 번에 읽으면 메모리가 부족해지고 긴 트랜잭션이 잠금과 복제 지연을 일으켜요. 그래서 WHERE id > 마지막\_id ORDER BY id LIMIT 1000처럼 키 기준으로 묶음을 읽어요 · OFFSET 방식은 뒤로 갈수록 느려져요. 묶음을 처리할 때마다 마지막 id를 체크포인트로 저장하면, 중간에 배포나 장애로 멈춰도 그 지점부터 다시 시작해요. 처리 로직을 멱등하게 만들면 체크포인트 직전 묶음이 두 번 처리돼도 결과가 같아요. 묶음 사이에 잠깐 쉬거나 처리 속도를 제한해 운영 DB의 부하와 복제 지연을 지키고, 가능하면 읽기 복제본에서 읽어요. 진행률, 예상 종료 시간, 실패 건수를 기록하고, 본 실행 전에 소량으로 시험 실행(dry run)해 결과를 확인해요.<br><sub>Reading millions of rows at once exhausts memory, and long transactions cause locking and replication lag. So read chunks by key, as in WHERE id > last\_id ORDER BY id LIMIT 1000, since OFFSET slows down as it goes deeper. Saving the last id as a checkpoint after each chunk lets a job interrupted by a deploy or failure resume from that point. Idempotent processing makes the chunk just before the checkpoint harmless if it runs twice. Short pauses between chunks or rate limits protect the production database from load and replication lag, and reading from a replica helps where possible. Progress, ETA and failure counts are logged, and a small dry run precedes the real execution.</sub> |
| **분산 환경의 정기 작업**<br><sub>Scheduled jobs in distributed systems</sub> | 인스턴스가 여러 대면 앱 안의 cron도 여러 번 돌아요. 잠금·리더 선출·중앙 스케줄러로 하나만 실행하고, 작업 자체도 멱등하게 만들어요.<br><sub>With several instances, in-app crons run several times; use locks, leader election or a central scheduler so only one runs, and keep the job itself idempotent.</sub> | 앱에 들어 있는 cron 라이브러리는 인스턴스마다 따로 돌기 때문에, 서버를 3대로 늘리면 매일 새벽 리포트가 3번 만들어지고 메일도 3번 나가요. 가장 간단한 해결은 실행 직전에 Redis SET NX나 DB 잠금으로 잠금을 얻은 인스턴스 하나만 실행하고 나머지는 건너뛰게 하는 거예요. 잠금에는 만료 시간을 두어 실행 중 죽어도 풀리게 하고, 작업이 길면 주기적으로 연장해요. 잠금이 만료된 뒤 겹칠 수 있으니 작업 자체도 멱등하게 만들어 두 번 돌아도 결과가 같게 해요. 쿠버네티스 CronJob, BullMQ의 반복 작업, 리더 선출처럼 실행을 한 곳에서 정하는 방식도 좋아요. 실행 이력을 남겨 서버가 내려가 있던 시간에 놓친 실행을 찾아 보충하고, 시간대와 서머타임 처리를 명확히 해요.<br><sub>In-app cron libraries run on every instance, so scaling to three servers builds the nightly report three times and sends its email three times. The simplest fix has instances take a Redis SET NX or database lock right before running, letting one run while others skip. Locks get an expiry so they release if the holder dies, extended periodically for long jobs. Since runs may overlap after a lock expires, the job itself should be idempotent, giving the same result if run twice. Centralizing schedules with Kubernetes CronJobs, BullMQ repeatable jobs or leader election also works. Run history helps catch and backfill executions missed while servers were down, and time zones and daylight saving must be handled explicitly.</sub> |

## 측정하고 개선하기 · Measuring and improving

부하 테스트로 한계를 재고, 프로파일링·트레이싱·힙 분석·쿼리 통계로 병목을 찾는 방법이에요.  
*Measuring limits with load tests and finding bottlenecks with profiling, tracing, heap analysis and query statistics.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **부하 테스트**<br><sub>Load testing</sub> | k6 같은 도구로 사용자를 서서히 늘리며 처리량과 지연을 재요. 처리량은 멈추고 지연만 치솟는 포화 지점에서 병목을 찾아요.<br><sub>Load testing tools such as k6 ramp users up while measuring throughput and latency, revealing bottlenecks at the saturation point where throughput stalls and latency soars.</sub> | 부하 테스트는 출시 전에 “몇 명까지 버티는가”를 숫자로 확인하는 일이에요. k6 스크립트로 2분 동안 가상 사용자를 200명까지 늘리고 5분 유지하는 식의 단계를 정하고, thresholds에 “p95 지연 300ms 미만, 오류율 1% 미만” 같은 기준을 걸어 넘으면 실패하게 해요. 부하를 올리면 처음엔 처리량(RPS)이 함께 늘다가, 어느 순간 처리량은 멈추고 지연만 치솟는 포화 지점(무릎)이 나와요 · 그때 CPU, DB 연결, 잠금 대기 같은 서버 지표를 함께 봐야 원인을 찾아요. 의미 있는 결과를 얻으려면 운영과 비슷한 데이터 크기와 인프라에서, 로그인·검색·주문처럼 실제 사용자 흐름을 닮은 시나리오로 돌려요. 갑작스러운 급증(스파이크)과 몇 시간 동안의 지속 부하(soak)는 따로 테스트해 메모리 누수 같은 문제도 찾아요.<br><sub>Load testing confirms in numbers how much traffic a system handles before launch. A k6 script defines stages such as ramping to 200 virtual users over 2 minutes and holding for 5, with thresholds such as “p95 under 300 ms, errors under 1%” that fail the run when exceeded. As load rises, throughput (RPS) first grows with it, then reaches a saturation point (the knee) where throughput stalls and latency soars, and server metrics such as CPU, database connections and lock waits reveal why. Meaningful results need production-like data volume and infrastructure and scenarios mirroring real flows such as login, search and checkout. Sudden spikes and hours-long soak tests run separately, catching problems such as memory leaks.</sub> |
| **프로파일링**<br><sub>Profiling</sub> | 짐작 대신 프로파일러로 CPU 시간을 기록하고, 플레임 그래프에서 가장 넓은 꼭대기 막대를 고쳐요. 고친 뒤 다시 측정해요.<br><sub>Instead of guessing, record CPU time with a profiler and fix the widest top bar in the flame graph, then remeasure.</sub> | 느린 원인을 짐작으로 고치면 엉뚱한 곳을 최적화하느라 시간을 쓰기 쉬워요. node --cpu-prof, 0x, Go의 pprof, Java의 async-profiler 같은 도구로 실제 CPU 사용을 기록해요. 플레임 그래프는 아래가 호출한 함수, 위가 불린 함수이고 막대 너비가 그 함수가 CPU를 쓴 시간이에요. 가장 넓은 꼭대기 막대가 진짜 병목으로, 예상과 달리 큰 객체를 JSON으로 직렬화하거나 정규식, 로깅에서 시간을 다 쓰는 경우가 흔해요. 고친 뒤에는 같은 부하와 조건으로 다시 측정해 개선을 확인해요. CPU 외에 메모리 할당과 잠금 대기도 프로파일할 수 있고, 운영 환경에서는 부담이 적은 상시 샘플링 프로파일러로 실제 트래픽의 병목을 봐요. 대부분의 지연은 I/O 대기라서 CPU 프로파일과 함께 트레이스도 봐야 전체 그림이 나와요.<br><sub>Fixing slowness by guesswork easily spends time optimizing the wrong place. Tools such as node --cpu-prof, 0x, Go’s pprof or Java’s async-profiler record real CPU usage. In a flame graph, callers sit below and callees above, and bar width shows the CPU time of that function. The widest top bar is the real hotspot, and surprisingly often it is serializing a large object to JSON, regular expressions or logging. After fixing, remeasure under the same load and conditions to confirm the gain. Memory allocation and lock waits can be profiled as well, and low-overhead continuous sampling profilers reveal hotspots under real production traffic. Since most latency is I/O waiting, traces complete the picture alongside CPU profiles.</sub> |
| **코드 계측 (OpenTelemetry)**<br><sub>Instrumenting code (OpenTelemetry)</sub> | 작업을 스팬으로 감싸 시간·속성·예외를 기록하고, 로그에 trace\_id를 남기고, traceparent 헤더로 서비스 간에 이어 붙여요.<br><sub>Wrap work in spans that record timing, attributes and exceptions, put trace\_id in logs, and connect services through the traceparent header.</sub> | OpenTelemetry는 트레이스, 메트릭, 로그를 만드는 벤더 중립 표준이에요. tracer.startSpan('checkout')으로 작업을 스팬으로 감싸면 시작·끝 시간과 order.id 같은 속성이 기록되고, 안쪽 작업은 자식 스팬으로 중첩돼 하나의 트레이스가 돼요. 예외를 recordException으로 스팬에 남기면 트레이스 화면에서 어느 단계가 실패했는지 바로 보여요. 구조화 로그에 trace\_id를 함께 남기면 느린 트레이스에서 관련 로그로, 로그에서 트레이스로 오갈 수 있어요. 다른 서비스를 HTTP로 부를 때 traceparent 헤더로 trace\_id가 전파되어 여러 서비스를 거친 요청이 한 트레이스로 이어져요. HTTP 서버, DB 드라이버, 큐 클라이언트는 자동 계측 패키지로 코드 수정 없이 스팬을 만들 수 있고, 업무 단계는 직접 스팬을 더해요. 속성에 개인정보를 넣지 않고, 샘플링으로 비용을 조절해요.<br><sub>OpenTelemetry is a vendor-neutral standard for producing traces, metrics and logs. Wrapping work with tracer.startSpan('checkout') records start and end times and attributes such as order.id, with inner work nesting as child spans into one trace. recordException attaches errors to spans so the trace view shows which step failed. Logging the trace\_id in structured logs lets you jump between slow traces and their logs. When calling other services over HTTP, the traceparent header propagates the trace\_id, joining a request across services into one trace. HTTP servers, database drivers and queue clients get spans without code changes through auto-instrumentation, while business steps get manual spans. Keep personal data out of attributes and control cost with sampling.</sub> |
| **메모리 누수 찾기**<br><sub>Finding memory leaks</sub> | GC 후에도 메모리 바닥이 계속 올라가면 누수예요. 힙 스냅숏 두 개를 비교해 늘어나는 객체와 그것을 붙잡는 참조를 찾아요.<br><sub>If the memory floor keeps rising after garbage collection, it is a leak; diff two heap snapshots to find the growing objects and the references holding them.</sub> | 가비지 컬렉터가 있어도 어딘가에서 객체를 계속 참조하면 메모리는 회수되지 않아요. 메모리 그래프는 GC 때마다 톱니처럼 내려가는데, 내려간 바닥이 시간이 지날수록 올라가면 누수 신호예요 · 결국 OOM으로 재시작돼요. 시간 차를 두고 힙 스냅숏 두 개를 떠서 비교하면 개수가 계속 늘어나는 객체와, 그것을 붙잡고 있는 참조 경로(retainer)가 보여요. 가장 흔한 원인은 상한 없는 Map 캐시, 제거하지 않은 이벤트 리스너와 타이머, 요청 데이터를 붙잡는 전역 배열이나 클로저예요. 캐시는 최대 개수와 만료 시간이 있는 LRU로 바꾸고, 리스너는 등록한 곳에서 반드시 해제해요. 키 객체가 사라지면 함께 정리되는 WeakMap도 도움이 돼요. 메모리 사용량에 알림을 걸어 재시작이 반복되기 전에 알아채요.<br><sub>Even with a garbage collector, memory is never reclaimed while something still references objects. Memory saws down at each collection, and a floor that rises over time signals a leak that ends in out-of-memory restarts. Taking two heap snapshots some time apart and comparing them shows which objects keep multiplying and the retainer paths holding them. The usual causes are unbounded Map caches, event listeners and timers never removed, and global arrays or closures holding request data. Replace caches with an LRU bounded by size and TTL, and always remove listeners where they were added. A WeakMap, whose entries vanish with their keys, also helps. Alert on memory usage to catch leaks before restarts become routine.</sub> |
| **느린 쿼리 찾기**<br><sub>Finding slow queries</sub> | pg\_stat\_statements와 느린 쿼리 로그로 쿼리별 호출 수와 시간을 모아 누적 시간 순으로 우선순위를 정하고, 실행 계획을 보고 고쳐요.<br><sub>Collect per-query calls and timings with pg\_stat\_statements and slow query logs, prioritize by total time, and fix after reading execution plans.</sub> | DB가 느려지면 먼저 어떤 쿼리가 시간을 쓰는지 데이터로 확인해요. PostgreSQL의 pg\_stat\_statements는 같은 모양의 쿼리를 묶어 호출 수, 평균 시간, 누적 시간을 모아 주고, log\_min\_duration\_statement는 기준 시간을 넘는 쿼리를 로그로 남겨요(MySQL은 slow query log). 한 번에 2ms인 쿼리도 120만 번 불리면 가끔 도는 4초짜리 리포트보다 DB를 훨씬 많이 쓰므로, 누적 시간 순으로 우선순위를 정해요. 범인을 찾으면 EXPLAIN ANALYZE로 실제 실행 계획을 보고 인덱스 추가, 쿼리 수정, 결과 캐시, 호출 횟수 줄이기(N+1 제거) 중에서 고쳐요. 고친 뒤 통계를 초기화하고 같은 기간을 다시 비교해 효과를 확인해요. 인덱스는 쓰기 비용과 저장 공간을 늘리니 읽기 이득과 균형을 봐요.<br><sub>When the database slows down, first confirm with data which queries consume time. PostgreSQL’s pg\_stat\_statements groups queries by shape and tracks calls, mean time and total time, while log\_min\_duration\_statement logs queries over a threshold (MySQL has the slow query log). A 2 ms query called 1.2 million times uses far more of the database than an occasional 4-second report, so prioritize by total time. Once found, EXPLAIN ANALYZE shows the real plan, guiding a choice among adding indexes, rewriting queries, caching results or reducing calls (removing N+1). After fixing, reset the statistics and compare the same period again to confirm the effect. Indexes add write cost and storage, so weigh them against read gains.</sub> |
