| **무작위 입력과 경계값**<br><sub>Random inputs and boundaries</sub> | 50,000원 경계를 >로 잘못 쓴 버그를 무작위 입력 1,000개짜리 테스트는 1,000번 중 2번 잡았어요. 경계 앞뒤의 입력 3개는 단번에 잡았어요.<br><sub>A bug writing the 50,000 KRW boundary as > was caught by a 1,000-random-input test only twice in 1,000 runs. Three inputs around the boundary caught it at once.</sub> | 테스트할 입력을 고르는 일은 생각보다 어려워요. 입력이 될 수 있는 값은 대개 셀 수 없이 많고, 그 가운데 몇 개만 테스트할 수 있기 때문이에요. 흔한 직관은 무작위로 많이 넣으면 언젠가 걸린다는 거예요. 이 직관을 확인했어요. 명세는 주문 금액이 50,000원 이상이면 배송비가 무료이고, 그보다 적으면 3,000원이에요. 그런데 코드는 a >= 50000이 아니라 a > 50000으로 쓰여 있어요. 정확히 50,000원일 때만 3,000원을 받고, 그 밖의 모든 금액에서는 맞게 동작하는 버그예요. 0부터 1,000,000 사이의 정수 금액을 무작위로 1,000개 뽑아 명세와 비교하는 테스트를 만들고, 이 테스트를 1,000번 돌렸어요. 버그를 잡은 것은 2번이었어요. 버그를 드러내는 입력은 100만 1개 가운데 하나뿐이라, 1,000개를 뽑아도 걸릴 확률이 약 0.1%이기 때문이에요. 테스트는 거의 늘 통과하고, 개발자는 안심해요. 경계값 분석은 반대로 생각해요. 동작이 바뀌는 자리, 곧 조건문의 경계 바로 아래, 그 자리, 바로 위를 골라요. 49,999, 50,000, 50,001 세 개를 넣자 50,000에서 배송비가 0이 아니라 3,000이 나와 단번에 실패했어요. 0과 최댓값 1,000,000까지 다섯 개를 넣어도 비용은 무작위 1,000개의 200분의 1이에요. 버그는 입력 공간에 고르게 퍼져 있지 않아요. 비교 연산의 등호, 반복문의 첫 번째와 마지막 번째, 배열의 빈 경우와 한 개인 경우, 자료형의 최댓값처럼 동작이 바뀌는 자리에 몰려 있어요. 하나 차이 오류가 대표적이에요. 그래서 명세를 읽고 동작이 바뀌는 자리를 찾아 그 앞뒤를 테스트하는 것이 먼저예요. 비슷하게 동작하는 입력들을 한 무리로 보고 무리마다 대표 하나씩을 고르는 동등 분할도 같은 생각이에요. 무작위 입력이 쓸모없다는 뜻은 아니에요. 사람이 생각하지 못한 영역을 살피는 데는 유용하고, 속성 기반 테스트와 퍼징은 경계와 특이한 값을 자주 만들도록 무작위를 다듬은 방법이에요. 다만 무작위는 고른 경계값을 대신하지 못하고 그 밖의 넓은 영역을 보완해요.<br><sub>Choosing inputs to test is harder than it looks: possible values are usually countless, and only a few can be tested. A common intuition is that enough random inputs will hit any bug eventually, so it was checked. The spec makes shipping free for orders of 50,000 KRW or more and 3,000 KRW otherwise, but the code was written as a > 50000 instead of a >= 50000, charging 3,000 KRW only at exactly 50,000 and behaving correctly for every other amount. A test drawing 1,000 random integer amounts between 0 and 1,000,000 and comparing against the spec was run 1,000 times, and it caught the bug twice. Only one input in 1,000,001 reveals the bug, so drawing 1,000 gives about a 0.1% chance of hitting it: the test nearly always passes, and developers feel reassured. Boundary value analysis thinks the other way, picking inputs just below, at and just above where behavior changes. With 49,999, 50,000 and 50,001, the fee at 50,000 came out 3,000 instead of 0, failing at once; even adding 0 and the maximum 1,000,000 costs one two-hundredth of the 1,000 random inputs. Bugs are not spread evenly across the input space but cluster where behavior changes: the equality in comparisons, the first and last iterations of loops, the empty and single-element cases of arrays, the maximum values of types, with off-by-one errors the classic example. Reading the spec to find where behavior changes and testing both sides comes first. Equivalence partitioning, grouping inputs that behave alike and picking one representative per group, follows the same idea. Random inputs are not useless: they help explore areas people did not think of, and property-based testing and fuzzing refine randomness to produce boundaries and unusual values often. But randomness complements chosen boundary values across the remaining space rather than replacing them.</sub> |
| **쌍 테스트**<br><sub>Pairwise testing</sub> | 매개변수 6개의 조합 648가지를 쌍 테스트 17개로 줄이자, 두 값이 만나야 생기는 버그 두 개는 모두 잡았고 세 값이 만나야 생기는 버그는 놓쳤어요.<br><sub>Cutting 648 combinations of six parameters to 17 pairwise tests caught both bugs that needed two values together but missed the bug that needed three.</sub> | 결제 화면을 브라우저 세 가지, 운영체제 세 가지, 언어 네 가지, 결제 수단 세 가지, 쿠폰 사용 여부 두 가지, 기기 세 가지로 확인해야 한다고 해요. 모든 조합은 3 × 3 × 4 × 3 × 2 × 3 = 648가지예요. 매개변수가 하나 늘 때마다 곱으로 불어나므로 금방 손으로도 자동으로도 감당할 수 없어져요. 쌍 테스트는 어떤 두 매개변수를 고르든 그 값의 모든 쌍이 적어도 한 번 나오는 최소한의 조합을 고르는 방법이에요. 파이썬의 allpairspy로 만들자 17개였어요. 매개변수 두 개씩의 값 쌍은 모두 134개이고, 17개가 그 134개를 빠짐없이 덮었어요. 버그 세 개를 심어 확인했어요. 첫째는 운영체제가 mac이고 결제 수단이 카드일 때 실패하는 버그로, 648가지 중 72가지에서 나타나요. 둘째는 언어가 일본어이고 기기가 태블릿일 때 실패하는 버그로 54가지에서 나타나요. 셋째는 브라우저가 safari, 결제 수단이 paypal, 쿠폰을 쓸 때만 실패하는 세 값의 버그로 36가지에서 나타나요. 쌍 테스트 17개는 첫째와 둘째를 모두 잡았어요. 두 값의 쌍을 모두 덮으니 두 값이 만나야 생기는 버그는 반드시 잡혀요. 셋째는 놓쳤어요. 쌍 테스트는 세 값의 조합까지는 보장하지 않기 때문이에요. 비교하려고 648가지 가운데 17개를 무작위로 뽑는 실험을 2,000번 했어요. 첫째 버그는 86.0%, 둘째는 76.6%, 셋째는 63.1%의 확률로 잡았어요. 무작위 17개는 세 값 버그를 가끔 잡았지만 두 값 버그를 가끔 놓쳤고, 쌍은 평균 85.3%만 덮었어요. 쌍 테스트의 바탕에는 실제 조합 버그의 대부분이 두 매개변수 사이의 상호작용에서 생긴다는 경험적 관찰이 있어요. 적은 테스트로 두 값 조합을 빠짐없이 보장하는 대신, 세 값 이상의 조합은 따로 챙겨야 해요. 위험한 조합을 알고 있다면 그 조합을 직접 추가하거나, 강도를 3-way로 올려 세 값의 조합까지 덮는 집합을 만들어요. 테스트 수는 늘지만 모든 조합보다는 훨씬 적어요. 함께 쓸 수 없는 조합, 예를 들어 safari와 windows 같은 제약도 도구에 알려 줘야 의미 없는 테스트가 생기지 않아요.<br><sub>Suppose a checkout screen must be verified across three browsers, three operating systems, four languages, three payment methods, two coupon states and three devices. All combinations number 3 × 3 × 4 × 3 × 2 × 3 = 648, and every added parameter multiplies the count, quickly beyond what people or automation can handle. Pairwise testing picks a minimal set of combinations in which, for any two parameters, every pair of their values appears at least once. Python’s allpairspy produced 17 tests. There are 134 value pairs across all pairs of parameters, and the 17 covered every one. Three bugs were planted to check. The first fails when the OS is mac and the payment is card, appearing in 72 of the 648 combinations; the second fails when the language is Japanese and the device a tablet, appearing in 54; the third is a three-value bug that fails only with safari, paypal and a coupon, appearing in 36. The 17 pairwise tests caught the first and second: covering every pair guarantees catching bugs that need two values together. They missed the third, since pairwise testing does not guarantee three-value combinations. For comparison, 17 of the 648 were drawn at random 2,000 times: the first bug was caught 86.0% of the time, the second 76.6% and the third 63.1%. Random sets sometimes caught the three-value bug but sometimes missed two-value bugs, covering only 85.3% of pairs on average. Pairwise testing rests on the empirical observation that most real interaction bugs arise between two parameters. It guarantees every two-value combination with few tests, leaving combinations of three or more to be handled separately: known risky combinations are added directly, or the strength is raised to 3-way to build a set covering three-value combinations, more tests but still far fewer than all combinations. Constraints on combinations that cannot occur together, such as safari with windows, must also be given to the tool so meaningless tests are not generated.</sub> |
| **줄 커버리지와 분기 커버리지**<br><sub>Line and branch coverage</sub> | 양수 하나만 확인한 테스트로 모든 줄이 실행돼 줄 커버리지는 100%였지만, 0 이하에서 나는 오류는 그대로였어요. 분기 커버리지는 원시 V8이 100%, Vitest와 istanbul이 50%로 도구마다 달랐어요.<br><sub>A test checking only a positive input executed every line for 100% line coverage, yet the error for zero or less remained. Branch coverage differed by tool: 100% in raw V8, 50% in Vitest and istanbul.</sub> | 코드 커버리지는 테스트가 코드의 얼마를 실행했는지를 재요. 숫자로 나오고 CI에서 기준을 걸기 쉬워서 널리 쓰여요. 그런데 무엇을 세느냐에 따라 같은 테스트도 다르게 보여요. firstValue 함수는 y를 null로 두고, x가 양수면 y를 { v: x }로 바꾼 뒤, 마지막에 y.v를 돌려줘요. x가 0 이하면 y가 그대로 null이라 y.v에서 오류가 나요. 테스트는 firstValue(5)가 5인지 확인하는 하나뿐이에요. 이 테스트를 세 가지 방법으로 쟀어요. 줄 커버리지와 문장 커버리지는 모든 도구에서 100%였어요. 함수의 네 줄이 모두 실행됐기 때문이에요. 그런데 firstValue(-1)을 부르자 Cannot read properties of null (reading v) 오류가 났어요. 커버리지 100% 안에 확실한 버그가 숨어 있었던 거예요. 분기 커버리지는 도구마다 달랐어요. c8로 Node.js의 원시 V8 커버리지를 보자 분기도 100%였어요. V8의 블록 커버리지는 else가 없는 if에서 조건이 거짓인 빈 길을 따로 세지 않았어요. Vitest 5의 v8 제공자는 같은 V8 데이터를 소스 구조와 맞춰 다시 해석해서 분기 50%, 2개 중 1개로 보고하고 3번 줄을 덜 덮인 줄로 표시했어요. 코드를 계측하는 istanbul도 50%였어요. 같은 테스트가 도구에 따라 완벽해 보이기도, 절반만 덮은 것으로 보이기도 한 거예요. 줄 커버리지만 보면 이런 빈 길은 절대 드러나지 않아요. 그래서 커버리지는 줄보다 분기로 봐야 하고, 쓰는 도구가 무엇을 분기로 세는지 알아야 해요. 덜 덮인 분기는 그 길을 지나는 테스트가 없다는 확실한 신호이므로, 리뷰에서 새 코드의 덮이지 않은 분기를 확인하는 습관이 숫자 기준보다 효과적이에요. 그리고 커버리지에는 근본적인 한계가 있어요. 커버리지는 코드가 실행됐는지만 셀 뿐, 결과가 맞는지는 확인하지 않아요. 다음 항목처럼 결과를 전혀 확인하지 않는 테스트도 커버리지 100%를 만들 수 있어요. 커버리지가 낮으면 테스트가 부족하다는 것은 확실하지만, 높다고 테스트가 충분하다는 뜻은 아니에요. 커버리지 목표를 높게 강제하면 의미 없는 테스트로 숫자를 채우는 일이 생기기도 해요.<br><sub>Code coverage measures how much of the code tests execute. It produces a number and is easy to gate in CI, so it is widely used, yet the same test looks different depending on what is counted. The firstValue function sets y to null, replaces it with { v: x } when x is positive, and finally returns y.v; when x is zero or less, y stays null and y.v throws. The only test checks that firstValue(5) is 5. Measured three ways, line and statement coverage were 100% in every tool, because all four lines of the function ran. Yet calling firstValue(-1) threw Cannot read properties of null (reading v): a certain bug hiding inside 100% coverage. Branch coverage differed by tool. Viewing Node.js’s raw V8 coverage through c8 showed 100% branches too, since V8 block coverage did not count the empty false path of an if without else separately. Vitest 5’s v8 provider reinterprets the same V8 data against the source structure and reported 50% branches, 1 of 2, flagging line 3 as partly covered, and istanbul, which instruments the code, also reported 50%. The same test looked complete under one tool and half covered under others. Line coverage alone never reveals such empty paths, so coverage should be read as branches, knowing what the tool in use counts as a branch. An uncovered branch is a sure sign that no test takes that path, so checking new code’s uncovered branches in review is more effective than numeric thresholds. Coverage also has a fundamental limit: it counts only whether code ran, not whether results were right. As the next item shows, tests that check no results at all can reach 100% coverage. Low coverage surely means missing tests, but high coverage does not mean sufficient tests, and forcing high coverage targets can lead to meaningless tests written to fill the number.</sub> |
| **단언 없는 테스트**<br><sub>Tests without assertions</sub> | 결과를 확인하지 않는 스위트와 확인하는 스위트가 모두 커버리지 100%였어요. 연산자를 바꾼 변이 14개 가운데 앞의 스위트는 0개, 뒤의 스위트는 13개를 잡았어요.<br><sub>A suite that checks no results and one that does both reached 100% coverage. The first suite calls the four functions with various inputs but checks no results, a smoke test that passes as long as nothing throws. The second calls the same functions and asserts results along with boundaries such as 99,999 and 100,000 or 49,999 and 50,000. Measured with Vitest, both suites reached statements 10/10, branches 6/6, functions 4/4 and 100% of lines: by coverage, the two are identical. Coverage was the same 100%, but bug-catching power was 0 versus 13. The single survivor was meaningful too: it changed t - discount to t + discount where the final price decides shipping. | **속성 기반 테스트의 생성기와 축소**<br><sub>Generators and shrinking</sub> | 속성 기반 테스트는 문자열 순서로 정렬하는 버그를 몇 번 만에 찾아 [2, 100]으로 줄였어요. 10번 이상 반복될 때만 깨지는 버그는 a/b 무작위 생성기로 2,177번째에야, 반복 생성기로는 첫 번째에 찾았어요.<br><sub>Property-based testing found the string-order sort bug within a few runs and shrank it to [2, 100]. JavaScript’s array sort, given no comparison function, compares numbers as strings, so 100 comes before 2. Checking with fast-check that sorting integer arrays between 0 and 1,000 yields ascending output, five seeds found a failure between the first and sixth input, a bug example-based tests using only single digits such as [3, 1, 2] would have missed. The first failing inputs were long and messy, such as [384, 221, 405, 369, 58, 101, 213, 582], hard to diagnose as is. fast-check shrinks inputs while keeping the failure: removing elements and making numbers smaller, checking each time that it still fails, 10 to 40 times, it produced two-element cases such as [2, 100] and [10, 2], where the reason 100 precedes 2 is obvious at a glance. Shrinking is the key feature that makes property-based failures debuggable. Generators matter just as much. A run-length encoding that replaces repeated characters with counts had a bug: once a character repeats 10 or more times, decoding 10a reads it wrongly as 1 and 0a. Uniform randomness does not necessarily pass where bugs live. Failing seeds are saved and rerun to reproduce the same failure.</sub> |
| **메타모픽 테스트**<br><sub>Metamorphic testing</sub> | 분산을 한 번에 계산하는 함수는 값을 10억만큼 옮기자 -128을 냈어요. 정답 없이 이동해도 분산이 같아야 한다는 관계만으로 두 번째 입력에서 잡았고, 순서를 뒤집는 관계로는 잡지 못했어요.<br><sub>A one-pass variance function returned −128 after shifting values by a billion. The relation that shifting must keep the variance caught it on the second input without any answer, while a reverse-order relation missed it.</sub> | 테스트는 기대하는 정답을 알아야 실패를 판단할 수 있어요. 이것을 오라클이라고 해요. 그런데 수치 계산, 검색 순위, 추천, 이미지 처리, 머신러닝처럼 정답을 미리 알기 어려운 프로그램이 많아요. 정답을 계산하려면 같은 프로그램을 하나 더 만들어야 하는 셈이에요. 메타모픽 테스트는 정답 대신, 입력을 이렇게 바꾸면 출력은 이렇게 바뀌어야 한다는 관계를 확인해요. 분산을 예로 들었어요. 분산은 값들이 평균에서 얼마나 퍼져 있는지예요. 한 번에 계산하는 흔한 식은 제곱의 평균에서 평균의 제곱을 빼는 거예요. [4, 7, 13, 16]의 분산은 22.5이고, 이 식도 22.5를 냈어요. 그런데 모든 값에 1억을 더하자 22, 10억을 더하자 -128이 나왔어요. 값들을 똑같이 옮겼으니 퍼진 정도는 그대로 22.5여야 하고, 분산은 음수가 될 수도 없어요. 아주 큰 두 수, 제곱의 평균과 평균의 제곱을 빼는 과정에서 부동소수점의 유효 자릿수가 사라지는 문제예요. 이 버그를 정답 없이 잡으려고, 모든 값에 같은 수를 더해도 분산은 같아야 한다는 관계를 fast-check로 확인했어요. 정수 배열과 -10억에서 10억 사이의 이동값을 무작위로 만들었어요. 두 번째 입력에서 관계가 깨졌고, 축소 23번으로 [0, 73]에 47,453,097을 더하는 예가 됐어요. 평균을 먼저 구한 뒤 각 값에서 빼고 제곱하는 두 번 도는 계산은 1,000번 모두 관계를 지켰어요. 반대로 값의 순서를 뒤집어도 분산은 같아야 한다는 관계로도 확인했어요. 이번에는 두 구현 모두 1,000번을 통과했어요. 버그가 값의 순서가 아니라 크기에 반응하기 때문이에요. 메타모픽 테스트의 힘은 버그를 건드리는 관계를 고르는 데서 나와요. 그래서 하나가 아니라 여러 관계를 함께 써요. 수치 계산에는 이동, 크기 조절, 순서 바꾸기, 입력을 나눠 계산한 뒤 합치기 같은 관계를 쓰고, 검색에는 조건을 더하면 결과가 줄거나 같아야 한다는 관계를, 이미지 분류에는 밝기를 조금 바꿔도 분류가 같아야 한다는 관계를 써요. 정답을 모르는 영역에서도 테스트를 만들 수 있게 해 주는 방법이에요.<br><sub>Tests need the expected answer to judge failure, which is called the oracle. Yet many programs, such as numerical computation, search ranking, recommendations, image processing and machine learning, make answers hard to know in advance; computing them would mean writing the same program twice. Metamorphic testing checks, instead of answers, relations of the form: change the input this way, and the output must change that way. Variance served as the example, measuring how far values spread from their mean. A common one-pass formula subtracts the square of the mean from the mean of the squares. The variance of [4, 7, 13, 16] is 22.5, and the formula gave 22.5 too. But adding 100 million to every value gave 22, and adding a billion gave −128. Shifting all values equally should leave the spread at 22.5, and variance can never be negative; the significant digits of floating point vanish when subtracting two very large numbers, the mean of squares and the square of the mean. To catch this without an answer, fast-check checked the relation that adding the same number to every value keeps the variance, generating integer arrays and shifts between −1 billion and 1 billion. The relation broke on the second input and shrank in 23 steps to [0, 73] shifted by 47,453,097. A two-pass computation, which first finds the mean, then subtracts it from each value before squaring, kept the relation across all 1,000 runs. The relation that reversing the order keeps the variance was checked as well, and this time both implementations passed 1,000 runs, because the bug reacts to the magnitude of values, not their order. Metamorphic testing’s power comes from choosing relations that touch the bug, so several are used together: numerical code uses shifting, scaling, reordering, and splitting inputs then combining results; search uses relations such as adding a condition must shrink or keep the results; image classification uses relations such as slightly changing brightness must keep the label. It lets tests be written even where answers are unknown.</sub> |

| **경쟁 탐지기**<br><sub>Race detectors</sub> | 잠금 없이 같은 카운터를 올리는 Go 코드가 220번 모두 통과했어요. go test -race는 결과가 맞았는데도 첫 실행에서 DATA RACE를 알리고 테스트를 실패시켰어요.<br><sub>Go code incrementing the same counter without locks passed all 220 runs. go test -race reported a DATA RACE on the first run and failed the test, even though the results were right.</sub> | 동시성 버그는 테스트로 잡기 가장 어려운 버그예요. 결과가 우연히 맞으면 테스트가 통과하고, 실패는 서버가 바쁠 때 드물게만 나타나요.
