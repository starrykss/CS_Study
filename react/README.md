## JSX와 컴포넌트 · JSX and components

UI를 작은 함수로 나누고 조립하는 방법, 그리고 React가 바뀐 부분만 화면에 반영하는 원리예요.  
*Splitting UI into small functions and assembling them, and how React updates only what changed.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **JSX**<br><sub>JSX</sub> | HTML처럼 보이지만 실제로는 자바스크립트 함수 호출로 바뀌는 문법이에요. 결과는 “무엇을 그릴지” 적은 React 요소 객체예요.<br><sub>Syntax that looks like HTML but compiles to JavaScript function calls returning React element objects that describe what to draw.</sub> | <h1 className="title">Hi, {name}</h1>은 빌드 때 jsx("h1", { className: "title", children: [...] }) 같은 호출로 바뀌고, { type: "h1", props: {...} } 모양의 평범한 객체를 돌려줘요. class 대신 className, onclick 대신 onClick처럼 JS 이름을 쓰고, 중괄호 안에는 삼항 연산자나 map 같은 “값이 되는 표현식”만 넣을 수 있어요. 모든 태그는 닫아야 하고 루트는 하나여야 해서 여러 요소는 <>…</>(Fragment)로 묶어요. { } 안의 문자열은 자동으로 이스케이프되어 XSS를 막아 줘요.<br><sub>At build time <h1 className="title">Hi, {name}</h1> becomes a call such as jsx("h1", { className: "title", children: [...] }), which returns a plain object shaped like { type: "h1", props: {...} }. It uses JavaScript names such as className instead of class and onClick instead of onclick, and braces accept only expressions that produce values, such as ternaries and map. Every tag must close and there must be one root, so siblings are wrapped in <>…</> (a Fragment). Strings inside braces are escaped automatically, preventing XSS.</sub> |
| **컴포넌트와 props**<br><sub>Components and props</sub> | 컴포넌트는 props를 받아 JSX를 돌려주는 대문자 이름의 함수예요. 데이터는 props로 부모에서 자식으로만 흘러요.<br><sub>A component is a capitalized function that takes props and returns JSX; data flows down through props, from parent to child only.</sub> | function Avatar({ user, size = 48 })처럼 props를 구조 분해해서 받고, 생략된 값은 기본값으로 채워요. 부모 Profile은 <Avatar user={user} size={64} />처럼 태그 속성으로 props를 넘겨요. props는 읽기 전용이라 자식이 바꿀 수 없고, 값을 바꾸려면 부모의 상태를 바꿔 새 props가 내려오게 해야 해요(단방향 데이터 흐름). 같은 props면 같은 결과를 내는 순수 함수처럼 작성하는 게 원칙이에요. 소문자 태그는 HTML 요소, 대문자 태그는 컴포넌트로 구분돼요.<br><sub>function Avatar({ user, size = 48 }) destructures its props, with defaults for omitted values, and the parent Profile passes props as attributes, as in <Avatar user={user} size={64} />. Props are read-only, so a child cannot change them; changes come from the parent’s state sending new props down, which is one-way data flow. Components should behave like pure functions: same props, same output. Lowercase tags are HTML elements and capitalized tags are components.</sub> |
| **가상 DOM과 재조정**<br><sub>The virtual DOM and reconciliation</sub> | 상태가 바뀌면 React는 새 요소 트리를 만들어 이전 트리와 비교하고, 바뀐 부분만 실제 DOM에 반영해요. 이 비교 과정을 재조정이라 해요.<br><sub>When state changes, React builds a new element tree, diffs it against the previous one and applies only the differences to the real DOM; this diffing is reconciliation.</sub> | 목록에 C가 추가되면 컴포넌트가 다시 실행되어 새 트리가 나오고, React는 이전 트리와 비교해 같은 자리의 같은 타입(li A, li B)은 그대로 두고 li C만 새로 만들어요. 실제 DOM 조작은 appendChild 한 번뿐이에요. 같은 자리의 요소 타입이 div에서 section으로 바뀌면 그 아래를 통째로 버리고 새로 만들어서, 안에 있던 Counter의 상태도 초기화돼요. 그래서 렌더 함수 안에서 컴포넌트를 정의하면 매번 새 타입이 되어 상태가 날아가요. 목록 항목은 key로 짝을 맞춰요.<br><sub>When C is added to a list, the component reruns and produces a new tree; React keeps li A and li B, which have the same type in the same place, and creates only li C, so the real DOM sees a single appendChild. If an element’s type in the same place changes from div to section, the whole subtree is discarded and rebuilt, resetting the state of the Counter inside. That is why defining a component inside a render function loses state: it is a new type every time. List items are matched by key.</sub> |
| **리스트와 key**<br><sub>Lists and keys</sub> | map으로 목록을 그릴 때 key로 각 항목을 구별해요. 재조정 때 이전과 다음 목록의 항목을 짝짓는 이름표예요.<br><sub>When rendering lists with map, key identifies each item, pairing items between the previous and next lists during reconciliation.</sub> | {todos.map(t => <Item key={t.id} todo={t} />)}처럼 데이터의 고유 id를 key로 써요. 배열 index를 key로 쓰고 맨 앞에 항목을 추가하면, 체크 상태 같은 내부 상태가 엉뚱한 항목에 남는 버그가 생겨요. Math.random()은 렌더마다 key가 바뀌어 매번 컴포넌트를 새로 만들어 버려요. key는 형제 사이에서만 고유하면 되고 props로 전달되지 않아요. 반대로 <Form key={userId} />처럼 key를 일부러 바꾸면 사용자가 바뀔 때 폼 상태를 깨끗하게 초기화할 수 있어요.<br><sub>Use the data’s unique id as the key, as in {todos.map(t => <Item key={t.id} todo={t} />)}. With array indexes as keys, prepending an item leaves internal state such as checkboxes on the wrong item. Math.random() changes the key every render, recreating the component each time. Keys only need to be unique among siblings and are not passed as props. Conversely, deliberately changing a key, as in <Form key={userId} />, cleanly resets a form when the user changes.</sub> |
| **조건부 렌더링**<br><sub>Conditional rendering</sub> | JSX도 값이라 삼항 연산자, &&, if 반환 같은 평범한 JS로 무엇을 그릴지 골라요. && 왼쪽의 숫자 0은 조심해요.<br><sub>JSX is just values, so ordinary JavaScript such as ternaries, && and early returns decides what to draw; watch out for a numeric 0 before &&.</sub> | {isLoggedIn ? <Dashboard /> : <Login />}은 둘 중 하나를, {error && <Alert />}는 오류가 있을 때만 그려요. 그런데 {count && <Badge />}에서 count가 0이면 false가 아니라 숫자 0이 화면에 찍혀요. false, null, undefined, true는 아무것도 그리지 않지만 0과 NaN은 그려지기 때문이에요. 그래서 count > 0처럼 불리언으로 만들어요. 조건이 복잡하면 if (!user) return <Spinner />처럼 일찍 반환하고, 아무것도 그리지 않을 땐 null을 돌려줘요.<br><sub>{isLoggedIn ? <Dashboard /> : <Login />} renders one of two options and {error && <Alert />} renders only when there is an error. But in {count && <Badge />}, a count of 0 prints the number 0 rather than nothing, because false, null, undefined and true render nothing while 0 and NaN do render. Make it boolean, as in count > 0. For complex conditions, return early, as in if (!user) return <Spinner />, and return null to render nothing.</sub> |
| **children과 합성**<br><sub>children and composition</sub> | 여는 태그와 닫는 태그 사이의 내용은 children prop으로 전달돼요. 컴포넌트를 상속이 아니라 합성으로 조립하는 React의 기본 방식이에요.<br><sub>Content between the opening and closing tags arrives as the children prop; composing components this way, rather than through inheritance, is React’s default approach.</sub> | function Card({ title, children })는 테두리와 제목만 책임지고, <Card title="프로필"><Avatar /><Bio /></Card>처럼 안에 무엇이 올지는 쓰는 쪽이 정해요. 자리가 여러 개면 <Layout side={<Nav />} main={<Feed />} />처럼 JSX를 props로 넘겨 슬롯처럼 써요. 데이터를 여러 층 내려보내는 대신 완성된 컴포넌트를 넘기면, 중간 컴포넌트는 그 데이터를 몰라도 돼서 prop drilling이 줄어요. Context를 꺼내기 전에 합성으로 해결되는지 먼저 살펴보는 게 좋아요.<br><sub>function Card({ title, children }) handles only the frame and title, and callers decide what goes inside, as in <Card title="Profile"><Avatar /><Bio /></Card>. For several slots, pass JSX as props, as in <Layout side={<Nav />} main={<Feed />} />. Passing finished components instead of threading data through layers means middle components never need that data, which cuts prop drilling. Check whether composition solves the problem before reaching for Context.</sub> |
| **이벤트 처리**<br><sub>Handling events</sub> | onClick={handleClick}처럼 함수 자체를 넘기면 React가 이벤트가 일어날 때 호출해요. 괄호를 붙여 즉시 실행하는 실수를 조심해요.<br><sub>Passing the function itself, as in onClick={handleClick}, lets React call it when the event fires; beware of calling it immediately with parentheses.</sub> | onClick={save}는 클릭될 때 save를 부르지만, onClick={save()}는 렌더하는 순간 save를 실행하고 그 반환값(undefined)을 넘겨요. 인자가 필요하면 onClick={() => remove(id)}처럼 화살표 함수로 감싸요. 핸들러는 브라우저 이벤트를 감싼 합성 이벤트 e를 받고, 폼 제출에서는 e.preventDefault()로 새로고침을 막아요. React의 onChange는 브라우저와 달리 글자를 입력할 때마다 실행돼요. React는 루트 하나에서 이벤트를 위임받아 처리해요.<br><sub>onClick={save} calls save on click, but onClick={save()} runs save during render and passes its return value, undefined. To pass arguments, wrap the call in an arrow, as in onClick={() => remove(id)}. Handlers receive a synthetic event e wrapping the browser event, and form submits call e.preventDefault() to stop the page reload. Unlike the browser’s change event, React’s onChange fires on every keystroke. React handles events through a single delegated listener at the root.</sub> |

## 상태와 렌더링 · State and rendering

상태가 어디에 저장되고, 언제 다시 렌더되며, 어떻게 안전하게 바꾸는지예요.  
*Where state is stored, when components re-render, and how to change state safely.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **useState와 렌더링**<br><sub>useState and rendering</sub> | useState는 렌더 사이에 기억되는 값과 그 값을 바꾸는 함수를 줘요. set 함수를 부르면 컴포넌트가 새 값으로 다시 렌더돼요.<br><sub>useState provides a value remembered between renders and a function to change it; calling the setter re-renders the component with the new value.</sub> | const [count, setCount] = useState(0)에서 count는 React가 컴포넌트 밖에 보관하는 값이에요. 버튼을 눌러 setCount(1)을 부르면 React가 값을 바꾸고 다시 렌더를 예약해요. 다시 렌더한다는 건 Counter 함수를 새 count로 다시 호출해 새 JSX를 얻는다는 뜻이에요. let n = 0 같은 일반 변수는 함수가 실행될 때마다 처음부터 다시 만들어져서 바꿔도 화면이 갱신되지 않아요. 훅은 컴포넌트 최상위에서 항상 같은 순서로 불러야 하고, 같은 컴포넌트를 두 번 쓰면 상태도 각자 따로 가져요.<br><sub>In const [count, setCount] = useState(0), count is kept by React outside the component. Clicking a button that calls setCount(1) updates the stored value and schedules a render, which means calling Counter again with the new count to get fresh JSX. A plain variable such as let n = 0 is recreated on every call, so changing it never updates the screen. Hooks must be called at the top level in the same order, and two instances of a component each get their own state.</sub> |
| **상태 스냅숏과 배칭**<br><sub>State snapshots and batching</sub> | 한 렌더 안의 상태는 고정된 스냅숏이에요. set은 값을 바로 바꾸지 않고 대기열에 쌓이며, 여러 번의 set은 한 번의 렌더로 모여요.<br><sub>State inside one render is a fixed snapshot; set does not change it immediately but queues an update, and multiple sets are batched into one render.</sub> | onClick 안에서 setCount(count + 1)을 두 번 불러도, 두 줄 모두 이번 렌더의 count(0)를 읽어서 결과는 2가 아니라 1이에요. 바로 아래의 console.log(count)도 여전히 0을 찍어요. 이전 값을 기준으로 바꾸려면 setCount(c => c + 1)처럼 갱신 함수를 넘기면 대기열에서 0 → 1 → 2로 차례로 적용돼요. 그리고 같은 이벤트 안의 여러 set은 모아서 한 번만 다시 렌더하는데, React 18부터는 setTimeout이나 Promise 안에서도 자동으로 배칭돼요.<br><sub>Calling setCount(count + 1) twice in a click handler reads this render’s count (0) both times, so the result is 1, not 2, and a console.log(count) right after still prints 0. To build on the previous value, pass an updater such as setCount(c => c + 1), which the queue applies in order: 0 → 1 → 2. Multiple sets in the same event are batched into one re-render, and since React 18 this also happens inside setTimeout and promises.</sub> |
| **불변 업데이트**<br><sub>Immutable updates</sub> | 객체·배열 상태는 직접 고치지 않고 새로 만들어 set해요. React는 Object.is로 참조가 바뀌었는지만 보고 변화를 판단해요.<br><sub>Object and array state is never edited in place but recreated and set; React detects changes only by whether the reference changed (Object.is).</sub> | user.age = 21로 고치고 setUser(user)를 부르면 같은 객체라서 React는 바뀐 게 없다고 보고 렌더하지 않아요. setUser({ ...user, age: 21 })처럼 전개 연산자로 새 객체를 만들면 참조가 달라져 변화를 알아채요. 배열도 추가는 [...todos, x], 삭제는 filter, 수정은 map 안에서 { ...t, done: !t.done }으로 새 배열을 만들고, push·splice·sort처럼 원본을 바꾸는 메서드는 피해요. 깊게 중첩된 구조는 Immer를 쓰면 고치듯이 써도 새 객체를 만들어 줘요. 이전 상태가 보존되어 되돌리기와 메모이제이션도 쉬워져요.<br><sub>Mutating user.age = 21 and calling setUser(user) passes the same object, so React sees no change and skips the render. Spreading into a new object, as in setUser({ ...user, age: 21 }), changes the reference and React notices. For arrays, add with [...todos, x], remove with filter and update with map returning { ...t, done: !t.done }, avoiding mutating methods such as push, splice and sort. For deeply nested data, Immer lets you write mutations while producing new objects. Preserved previous states also make undo and memoization easy.</sub> |
| **렌더링이 일어나는 때**<br><sub>When components render</sub> | 컴포넌트는 자기 상태가 바뀌거나, 부모가 렌더되거나, 읽는 Context가 바뀌면 다시 렌더돼요. 렌더는 계산일 뿐 DOM 변경과는 달라요.<br><sub>A component re-renders when its state changes, its parent renders or a context it reads changes; rendering is calculation, not DOM mutation.</sub> | App의 q가 바뀌면 App이 다시 실행되고, 그 안의 Search, Results, Footer는 q를 쓰든 말든 모두 다시 렌더돼요. 하지만 결과가 같으면 실제 DOM은 바뀌지 않아요 · 렌더는 함수를 호출해 계산하는 일이고, DOM 변경은 커밋에서 바뀐 부분에만 일어나요. 대부분의 렌더는 충분히 빨라서 걱정할 필요가 없어요. 정말 느린 컴포넌트는 memo로 감싸 props가 같을 때 건너뛰거나, 상태를 쓰는 곳 가까이 내려 렌더 범위를 줄여요. React DevTools의 Profiler로 무엇이 왜 렌더됐는지 확인할 수 있어요.<br><sub>When q in App changes, App reruns and Search, Results and Footer all render again, whether or not they use q. If the output is unchanged, the real DOM is untouched: rendering is calling functions to calculate, and DOM changes happen only at commit, only where something differs. Most renders are fast enough not to worry about. For genuinely slow components, wrap them in memo to skip renders with equal props, or move state closer to where it is used to shrink the render area. The React DevTools Profiler shows what rendered and why.</sub> |
| **상태 끌어올리기**<br><sub>Lifting state up</sub> | 여러 컴포넌트가 함께 맞춰야 하는 상태는 가장 가까운 공통 부모로 옮기고, 값은 props로 내리고 변경은 콜백으로 올려요.<br><sub>State that several components must share moves to their closest common parent; values flow down as props and changes come back up through callbacks.</sub> | 두 Panel이 각자 isOpen 상태를 가지면 서로를 몰라서 둘 다 열릴 수 있어요. active 상태를 공통 부모 Accordion으로 끌어올리면, 부모가 isActive={active === 0}처럼 값을 내려보내고, 자식은 onShow={() => setActive(0)} 같은 콜백으로 “나를 열어 주세요”라고 요청해요. 이렇게 하면 상태의 주인이 한 곳(single source of truth)이라 항상 일관돼요. 다만 너무 높이 올리면 렌더 범위가 넓어지니 필요한 만큼만 올리고, 멀리 떨어진 컴포넌트끼리는 Context나 상태 관리 도구를 고려해요.<br><sub>If two Panels each own an isOpen state, they cannot coordinate and both may open. Lifting active into the common parent Accordion lets the parent pass values down, as in isActive={active === 0}, while children request changes through callbacks such as onShow={() => setActive(0)}. With a single owner, a single source of truth, the UI stays consistent. Lift only as far as needed, since higher state widens re-renders, and consider Context or a state library for distant components.</sub> |
| **제어 컴포넌트와 폼**<br><sub>Controlled components and forms</sub> | value를 React 상태에 묶고 onChange로 상태를 갱신하는 입력이 제어 컴포넌트예요. 화면의 값은 언제나 상태가 정해요.<br><sub>An input whose value is bound to React state and updated through onChange is a controlled component; state always decides what it shows.</sub> | <input value={email} onChange={e => setEmail(e.target.value)} />에서 글자를 칠 때마다 onChange → setEmail → 다시 렌더 → value 반영이 한 바퀴 돌아요. 값이 상태에 있으니 const valid = email.includes("@")처럼 검증과 버튼 활성화를 렌더 중에 바로 계산할 수 있어요. defaultValue만 준 비제어 입력은 DOM이 값을 가지고, 제출할 때 FormData로 한 번에 읽어요. 입력이 많은 큰 폼은 비제어 기반의 React Hook Form이 렌더를 줄여 주고, value만 주고 onChange를 빼먹으면 입력이 막혀요.<br><sub>In <input value={email} onChange={e => setEmail(e.target.value)} />, every keystroke loops through onChange, setEmail, a re-render and the new value. With the value in state, validation and button states are computed right in render, as in const valid = email.includes("@"). An uncontrolled input with only defaultValue keeps its value in the DOM, read once on submit with FormData. Large forms benefit from uncontrolled-based libraries such as React Hook Form, and value without onChange makes an input read-only.</sub> |
| **파생 상태**<br><sub>Derived state</sub> | 다른 props나 state에서 계산할 수 있는 값은 state로 따로 두지 않고 렌더 중에 계산해요. 상태는 최소한으로 유지해요.<br><sub>Values computable from other props or state are calculated during render rather than stored in separate state, keeping state minimal.</sub> | items와 별도로 count 상태를 두고 useEffect로 setCount(items.length)를 하면, 렌더 → 이펙트 → 다시 렌더로 느려지고 잠깐 틀린 값이 보이기도 해요. const count = items.length처럼 렌더 중에 그냥 계산하면 언제나 최신이고 추가 렌더도 없어요. 검색 결과처럼 걸러 낸 목록도 items.filter(...)로 계산해요. 정렬처럼 정말 비싼 계산만 useMemo로 캐시하는데, 대부분은 그냥 계산해도 충분히 빨라요. React 공식 문서의 “이펙트가 필요 없을 수도 있다”가 바로 이 이야기예요.<br><sub>Keeping a count state beside items and syncing it in useEffect with setCount(items.length) costs render, effect and render again, and can flash a stale value. Computing const count = items.length during render is always current with no extra render. Filtered lists such as search results are computed with items.filter(...) too. Only truly expensive work such as sorting is cached with useMemo, and most calculations are fast enough as is. This is the heart of the React docs’ advice that you might not need an effect.</sub> |

## 이펙트와 훅 · Effects and hooks

React 바깥과 동기화하는 이펙트, 렌더와 무관한 ref, 메모이제이션, 그리고 로직을 재사용하는 훅이에요.  
*Effects that sync with the outside world, refs, memoization, and hooks for reusing logic.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **useEffect와 의존성 배열**<br><sub>useEffect and dependencies</sub> | useEffect는 화면을 그린 뒤 실행되어 React 바깥(네트워크, 구독, DOM)과 동기화해요. 의존성 배열이 언제 다시 실행할지 정해요.<br><sub>useEffect runs after painting to sync with systems outside React (network, subscriptions, the DOM), and its dependency array decides when it reruns.</sub> | 의존성 배열이 없으면 이펙트는 렌더할 때마다, [roomId]면 roomId가 이전 렌더와 달라졌을 때만, 빈 배열 []이면 처음 마운트된 뒤 한 번만 실행돼요. 실행 순서는 렌더 → 커밋 → 페인트 → 이펙트라서 화면을 막지 않아요. 이펙트 안에서 쓰는 props·state 같은 반응형 값은 모두 의존성에 넣어야 하고, eslint-plugin-react-hooks가 빠진 것을 알려 줘요. 버튼 클릭처럼 특정 이벤트 때문에 일어나는 일은 이펙트가 아니라 이벤트 핸들러에 써요.<br><sub>With no dependency array an effect runs after every render; with [roomId] only when roomId differs from the previous render; and with an empty [] once after mounting. The order is render, commit, paint, then effect, so effects do not block the screen. Every reactive value the effect uses, such as props and state, belongs in the dependencies, and eslint-plugin-react-hooks flags omissions. Work triggered by a specific event such as a click belongs in the event handler, not an effect.</sub> |
| **정리 함수와 Strict Mode**<br><sub>Cleanup and Strict Mode</sub> | 이펙트가 돌려주는 함수는 정리 함수예요. 다음 실행 전과 컴포넌트가 사라질 때 호출되어, 연결·구독·타이머를 되돌려요.<br><sub>The function an effect returns is its cleanup, called before the next run and on unmount to undo connections, subscriptions and timers.</sub> | connect(roomId)에는 return () => conn.disconnect()를 짝지어 둬요. roomId가 a에서 b로 바뀌면 React는 a 연결을 먼저 정리하고 b로 다시 연결하며, 컴포넌트가 사라질 때 마지막으로 정리해요. 개발 모드의 Strict Mode는 일부러 실행 → 정리 → 실행을 한 번 더 해서 정리를 빠뜨린 버그를 드러내요(프로덕션에서는 한 번만). setInterval, 이벤트 리스너, 웹소켓 구독은 정리하지 않으면 계속 남아 메모리 누수와 중복 실행이 돼요. 목표는 설정과 정리가 몇 번 반복돼도 문제없는 이펙트예요.<br><sub>Pair connect(roomId) with return () => conn.disconnect(). When roomId changes from a to b, React cleans up a before connecting to b, and cleans up one last time on unmount. In development, Strict Mode deliberately runs setup, cleanup and setup again to expose missing cleanups; production runs it once. Intervals, event listeners and websocket subscriptions linger as leaks and duplicate work unless cleaned up. The goal is an effect that works through any number of setup and cleanup cycles.</sub> |
| **이펙트로 데이터 가져오기**<br><sub>Fetching data in effects</sub> | 이펙트 안에서 fetch로 데이터를 가져올 수 있지만, 경쟁 상태를 정리 함수로 막아야 하고 캐시가 없어요. 실무에서는 전용 도구를 써요.<br><sub>Effects can fetch data, but races must be prevented with cleanup and there is no cache, so dedicated tools are used in practice.</sub> | useEffect 안에서 fetch(`/api/user/${id}`)를 하고 결과를 setUser로 넣어요. 그런데 id가 1에서 2로 빠르게 바뀌면, 느린 요청 1이 나중에 도착해 최신 사용자 2를 덮어쓰는 경쟁 상태가 생겨요. let ignore = false를 두고 정리 함수에서 ignore = true로 바꾸면 지나간 요청의 응답을 버릴 수 있고, AbortController로 요청 자체를 취소할 수도 있어요. 하지만 캐시, 중복 요청 제거, 재시도, 로딩 상태까지 직접 만들기는 어려워서 TanStack Query·SWR이나 프레임워크의 데이터 로딩, 서버 컴포넌트를 써요.<br><sub>Inside useEffect, fetch(`/api/user/${id}`) and store the result with setUser. If id changes quickly from 1 to 2, the slow request 1 can arrive last and overwrite user 2, a race condition. Declaring let ignore = false and setting ignore = true in the cleanup discards stale responses, and AbortController can cancel the request itself. Building caching, deduplication, retries and loading states by hand is hard, so TanStack Query, SWR, framework data loading or server components are used instead.</sub> |
| **useRef**<br><sub>useRef</sub> | useRef는 렌더와 무관하게 유지되는 { current } 상자예요. DOM 요소를 담거나, 화면에 보이지 않는 값을 보관할 때 써요.<br><sub>useRef is a { current } box that persists independently of rendering, used to hold DOM elements or values that never appear on screen.</sub> | const inputRef = useRef(null)을 <input ref={inputRef} />에 넘기면 inputRef.current에 DOM 요소가 담겨 focus(), 스크롤, 크기 측정 같은 명령형 작업을 할 수 있어요. 렌더가 몇 번 일어나도 같은 상자가 유지되므로 setInterval의 id나 이전 값처럼 화면과 무관한 값을 보관하기 좋아요. 다만 ref를 바꿔도 다시 렌더되지 않아서, 화면에 보여야 하는 값이라면 state를 써야 해요. 렌더 중에 ref를 읽거나 쓰는 것도 피해요. React 19부터는 ref를 일반 prop처럼 자식 컴포넌트에 넘길 수 있어 forwardRef가 필요 없어요.<br><sub>Passing const inputRef = useRef(null) to <input ref={inputRef} /> stores the DOM element in inputRef.current for imperative work such as focus(), scrolling and measuring. The same box survives every render, ideal for values unrelated to the screen such as an interval id or a previous value. Changing a ref never re-renders, so values that should appear on screen belong in state, and refs should not be read or written during render. Since React 19, ref can be passed to child components like any prop, without forwardRef.</sub> |
| **useMemo·useCallback·memo**<br><sub>useMemo, useCallback and memo</sub> | 같은 입력이면 이전 결과를 재사용하는 메모이제이션 도구예요. useMemo는 값, useCallback은 함수, memo는 컴포넌트 렌더를 캐시해요.<br><sub>Memoization tools reuse previous results for the same inputs: useMemo caches values, useCallback functions and memo component renders.</sub> | useMemo(() => sum(...), [items])는 items가 같은 동안 계산 결과를 재사용해요. 렌더마다 새로 만들어지는 함수는 참조가 매번 달라서, memo로 감싼 자식에 넘기면 props가 바뀐 것으로 보여 memo가 무용지물이 돼요. 그래서 useCallback으로 함수 참조를 유지해요. memo는 props를 Object.is로 하나씩 비교해 같으면 렌더를 건너뛰어요. 메모이제이션도 메모리와 비교 비용이 있으니 Profiler로 측정한 뒤 느린 곳에만 쓰고, React Compiler를 켜면 이 작업을 자동으로 해 줘요.<br><sub>useMemo(() => sum(...), [items]) reuses its result while items is unchanged. A function created on every render has a new reference each time, so passing it to a memo-wrapped child makes props look changed and defeats memo; useCallback keeps the reference stable. memo compares each prop with Object.is and skips the render when all match. Memoization costs memory and comparisons, so apply it to slow spots found with the Profiler, or enable React Compiler to do it automatically.</sub> |
| **커스텀 훅**<br><sub>Custom hooks</sub> | use로 시작하는 이름의 함수 안에서 다른 훅을 조합해 상태 있는 로직을 재사용해요. 로직은 공유되지만 상태는 호출마다 따로예요.<br><sub>Functions named use… combine other hooks to reuse stateful logic; the logic is shared, but each call gets its own state.</sub> | function useOnline()은 useState와 useEffect로 online·offline 이벤트를 구독해 현재 연결 상태를 돌려줘요. 여러 컴포넌트가 const online = useOnline() 한 줄로 가져다 쓰지만, 상태는 공유되지 않고 호출한 컴포넌트마다 따로 생겨요. 훅의 규칙에 따라 훅은 컴포넌트나 커스텀 훅의 최상위에서만, 항상 같은 순서로 불러야 하며 if·반복문·콜백 안에서 부르면 안 돼요. useFetch, useDebounce, useLocalStorage가 대표적인 예이고, 외부 저장소 구독은 useSyncExternalStore로 하면 더 안전해요.<br><sub>function useOnline() uses useState and useEffect to subscribe to online and offline events and returns the current status. Many components can call const online = useOnline() in one line, but each gets its own state rather than sharing one. By the rules of hooks, hooks are called only at the top level of components or custom hooks, always in the same order, never inside conditions, loops or callbacks. useFetch, useDebounce and useLocalStorage are classic examples, and useSyncExternalStore is the safer way to subscribe to external stores.</sub> |
| **useReducer**<br><sub>useReducer</sub> | 상태를 어떻게 바꿀지를 (state, action) → 새 state 순수 함수 한 곳에 모으는 훅이에요. 컴포넌트는 무슨 일이 일어났는지만 dispatch해요.<br><sub>A hook that gathers how state changes into one pure (state, action) → new state function; components only dispatch what happened.</sub> | 클릭 핸들러는 dispatch({ type: "add", item })처럼 액션만 보내고, reducer(state, a)가 switch로 액션 종류에 따라 새 배열을 만들어 돌려줘요. const [todos, dispatch] = useReducer(reducer, [])로 연결하면 새 상태로 다시 렌더돼요. 갱신 규칙이 한 곳에 모여 흐름을 추적하기 쉽고, reducer는 순수 함수라 UI 없이도 테스트할 수 있어요. 갱신 종류가 많고 상태가 복잡할수록 useState보다 유리하고, Context와 함께 쓰면 작은 전역 상태 관리가 돼요. Redux도 같은 아이디어예요.<br><sub>A click handler only dispatches an action such as { type: "add", item }, and reducer(state, a) switches on the action type to build and return a new array. Wiring it with const [todos, dispatch] = useReducer(reducer, []) re-renders with each new state. Update rules live in one place, making the flow easy to follow, and the pure reducer can be tested without any UI. It beats useState as update kinds and complexity grow, and with Context it becomes lightweight global state management. Redux is built on the same idea.</sub> |

## 상태 관리와 앱 구조 · State management and app structure

깊은 곳으로 값을 전달하는 방법, 서버 상태와 클라이언트 상태, 그리고 로딩·오류·떠 있는 UI·우선순위를 다루는 도구예요.  
*Passing values deep down, server versus client state, and tools for loading, errors, floating UI and priorities.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **Context**<br><sub>Context</sub> | Context는 props를 거치지 않고 트리 깊은 곳까지 값을 전달하는 통로예요. 테마, 로그인 사용자, 언어 같은 앱 전체 값에 써요.<br><sub>Context is a channel that carries values deep into the tree without props, for app-wide values such as theme, the signed-in user or language.</sub> | 깊은 Button이 theme을 쓰려면 Page, Sidebar처럼 쓰지도 않는 중간 컴포넌트가 계속 props를 전달해야 해요(prop drilling). createContext로 ThemeContext를 만들고 <ThemeContext value={theme}>로 감싸면, 그 아래 어디서든 use(ThemeContext)나 useContext로 가장 가까운 값을 바로 읽어요. 값이 바뀌면 그 Context를 읽는 모든 컴포넌트가 다시 렌더되므로, 자주 바뀌는 값은 Context를 나누거나 상태 관리 도구를 써요. React 19부터는 .Provider 없이 <Context value>로 쓰고, 먼저 합성으로 해결되는지 살펴보는 게 좋아요.<br><sub>For a deep Button to use theme, intermediate components such as Page and Sidebar must relay props they never use: prop drilling. Creating ThemeContext with createContext and wrapping the tree in <ThemeContext value={theme}> lets anything below read the nearest value with use(ThemeContext) or useContext. When the value changes, every component reading it re-renders, so split contexts or use a state library for fast-changing values. Since React 19 you write <Context value> without .Provider, and composition is worth trying first.</sub> |
| **서버 상태와 클라이언트 상태**<br><sub>Server state and client state</sub> | 상태는 서버에 원본이 있는 서버 상태와 브라우저에만 있는 클라이언트 상태로 나뉘고, 각각 알맞은 도구가 달라요.<br><sub>State splits into server state, whose source lives on the server, and client state that exists only in the browser, each with its own tools.</sub> | 할 일 목록, 사용자 정보 같은 서버 상태는 “원격 데이터의 복사본”이라 캐시, 신선도, 재요청이 핵심이에요. TanStack Query의 useQuery({ queryKey: ["todos", page], staleTime: 60\_000 })는 키별로 캐시하고, 신선한 동안은 재사용하다가 오래되면 다시 가져와요. 모달 열림이나 장바구니 같은 클라이언트 상태는 useState, Context, 또는 Zustand 같은 작은 저장소로 관리하고, useCart(s => s.items.length)처럼 필요한 조각만 구독하면 그 값이 바뀔 때만 렌더돼요. 서버 데이터를 전역 저장소에 복사하면 두 원본이 어긋나니 피해요.<br><sub>Server state such as todo lists and user profiles is a copy of remote data, so caching, freshness and refetching are what matter. TanStack Query’s useQuery({ queryKey: ["todos", page], staleTime: 60\_000 }) caches per key, reusing data while fresh and refetching once stale. Client state such as an open modal or a cart lives in useState, Context or a small store such as Zustand, and subscribing to just a slice, as in useCart(s => s.items.length), re-renders only when that value changes. Copying server data into a global store creates two drifting sources, so avoid it.</sub> |
| **Suspense와 lazy**<br><sub>Suspense and lazy</sub> | Suspense는 아직 준비되지 않은 부분 대신 fallback을 보여주는 경계예요. lazy와 함께 코드 분할에, 데이터 로딩 대기에도 써요.<br><sub>Suspense is a boundary that shows a fallback for parts that are not ready yet, used with lazy for code splitting and for awaiting data.</sub> | const Chart = lazy(() => import("./Chart"))는 Chart 코드를 별도 파일로 나눠 처음 필요할 때만 내려받아요(코드 스플리팅). <Suspense fallback={<Spinner />}>로 감싸면 코드나 데이터가 준비되는 동안 스피너를 보여주고, 준비되면 그 경계 안만 실제 내용으로 바뀌어요. 헤더처럼 경계 밖의 부분은 처음부터 그대로예요. 경계를 여러 개 두면 준비된 순서대로 화면이 채워지고, 서버 렌더링에서는 HTML을 경계 단위로 흘려보내요(스트리밍). 로딩 상태를 컴포넌트 안의 if 대신 바깥에서 선언적으로 다루는 방식이에요.<br><sub>const Chart = lazy(() => import("./Chart")) splits Chart into its own file, downloaded only on first use: code splitting. Wrapping it in <Suspense fallback={<Spinner />}> shows the spinner while code or data loads, then swaps in the real content inside that boundary only, while parts outside such as the header stay put. Multiple boundaries fill the screen in the order things become ready, and server rendering streams HTML boundary by boundary. Loading states become declarative, handled from outside instead of with ifs inside the component.</sub> |
| **Error Boundary**<br><sub>Error boundaries</sub> | Error Boundary는 자식 트리의 렌더 오류를 잡아 그 영역만 대체 화면으로 바꾸는 경계예요. 한 부분의 오류가 앱 전체를 하얗게 만드는 것을 막아요.<br><sub>An error boundary catches rendering errors in its subtree and replaces just that region with a fallback, so one failure does not blank the whole app.</sub> | 렌더 중 오류가 나면 React는 트리 전체를 내려서 화면이 하얗게 비어요. <ErrorBoundary fallback={…}>로 Comments를 감싸면 Comments에서 오류가 나도 그 자리만 “오류가 났어요 · 다시 시도”로 바뀌고 헤더와 본문은 살아남아요. 경계는 getDerivedStateFromError로 오류를 상태로 바꾸는데, 아직 클래스 컴포넌트로만 만들 수 있어 react-error-boundary 패키지를 많이 써요. 이벤트 핸들러나 비동기 코드의 오류는 렌더 밖이라 잡지 못하니 try/catch로 처리해요. 위젯·섹션 단위로 여러 개 두면 장애 범위가 작아져요.<br><sub>A rendering error unmounts the whole tree, leaving a blank page. Wrapping Comments in <ErrorBoundary fallback={…}> means an error there replaces only that spot with “Oops, try again” while the header and article survive. Boundaries turn errors into state with getDerivedStateFromError and still require class components, which is why the react-error-boundary package is popular. Errors in event handlers and async code happen outside rendering and are not caught, so handle them with try/catch. Several boundaries around widgets or sections keep failures contained.</sub> |
| **포털**<br><sub>Portals</sub> | createPortal은 컴포넌트의 논리적 위치는 그대로 두고 DOM만 body 같은 다른 곳에 렌더해요. 모달·툴팁처럼 떠 있는 UI에 써요.<br><sub>createPortal renders DOM somewhere else, such as body, while the component keeps its logical place; it suits floating UI such as modals and tooltips.</sub> | 모달을 카드 안에서 그리면 부모의 overflow: hidden에 잘리거나 쌓임 맥락 때문에 다른 요소 아래에 깔리기 쉬워요. createPortal(<div className="modal">…</div>, document.body)는 DOM 노드를 body 바로 아래에 만들어 이런 제약에서 벗어나요. 그래도 React 트리에서는 여전히 Card의 자식이라 클릭 이벤트는 Card로 버블링되고 Context도 그대로 읽혀요. 모달, 툴팁, 드롭다운, 토스트에 쓰며, 포커스 가두기와 Esc 닫기 같은 접근성 처리를 함께 챙겨요. 요즘은 <dialog>와 popover 속성으로 최상위 레이어를 쓰는 방법도 있어요.<br><sub>A modal rendered inside a card is easily clipped by the parent’s overflow: hidden or buried by stacking contexts. createPortal(<div className="modal">…</div>, document.body) creates the DOM nodes directly under body, escaping those limits. In the React tree it is still Card’s child, so clicks bubble to Card and context is read as usual. Use it for modals, tooltips, dropdowns and toasts, together with accessibility details such as focus trapping and closing on Esc. Native <dialog> and the popover attribute now offer the top layer as well.</sub> |
| **useTransition과 동시성**<br><sub>useTransition and concurrency</sub> | 동시성 렌더링은 렌더를 중단·재개할 수 있게 해서, 급한 업데이트(입력)를 먼저 처리하고 급하지 않은 렌더는 뒤로 미뤄요.<br><sub>Concurrent rendering lets React interrupt and resume rendering, handling urgent updates such as typing first and deferring non-urgent renders.</sub> | 무거운 목록을 렌더하는 동안에는 메인 스레드가 막혀 입력창에 글자가 늦게 찍혀요. startTransition(() => setTab(next))처럼 감싼 업데이트는 “급하지 않음”으로 표시되어, 새 입력이 오면 진행 중이던 렌더를 버리고 다시 시작해요. useDeferredValue(q)는 q의 늦은 버전을 만들어 입력창은 즉시, 느린 목록은 여유가 있을 때 갱신해요. isPending으로 준비 중 표시도 할 수 있어요. 이 도구들은 네트워크가 아니라 렌더 비용 문제를 다루고, 정말 큰 목록은 가상화(react-window)도 함께 고려해요.<br><sub>While a heavy list renders, the main thread is blocked and typed characters lag. Updates wrapped in startTransition(() => setTab(next)) are marked non-urgent, so React abandons and restarts that render when new input arrives. useDeferredValue(q) makes a lagging copy of q, updating the input immediately and the slow list when there is time, and isPending can drive a pending hint. These tools address rendering cost, not network delay, and very large lists also call for virtualization such as react-window.</sub> |

## 최신 React와 품질 · Modern React and quality

렌더·커밋을 나누는 엔진, 서버 컴포넌트와 Actions, use()와 컴파일러, 그리고 테스트예요.

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **Fiber와 렌더·커밋**<br><sub>Fiber, render and commit</sub> | React는 렌더 단계에서 새 트리를 계산하고(중단 가능), 커밋 단계에서 DOM에 한 번에 반영해요. 그래서 렌더 함수는 순수해야 해요.<br><sub>React computes a new tree in the interruptible render phase and applies it to the DOM in one go in the commit phase, which is why render functions must be pure.</sub> | 상태가 바뀌면 렌더 단계에서 컴포넌트 함수를 호출해 새 트리를 계산하는데, Fiber는 이 일을 작은 단위로 쪼개 급한 일이 오면 중간에 양보하고 나중에 다시 시작해요. 계산이 끝나면 커밋 단계에서 바뀐 부분을 실제 DOM에 끊김 없이 한 번에 반영해요. 그 뒤 useLayoutEffect가 브라우저가 그리기 전에, useEffect가 그린 뒤에 실행돼요. 렌더 단계는 버려지거나 여러 번 실행될 수 있어서, 렌더 중에 외부 값을 바꾸거나 요청을 보내면 안 되고 같은 입력에 같은 결과를 내야 해요. Strict Mode의 이중 렌더도 이를 검사하기 위해서예요.<br><sub>After a state change, the render phase calls components to compute a new tree, and Fiber splits this work into small units that can yield to urgent work and resume later. The commit phase then applies the changes to the real DOM in one uninterrupted pass, after which useLayoutEffect runs before the browser paints and useEffect after. Because render work may be discarded or repeated, rendering must not mutate outside values or send requests, and must give the same output for the same input. Strict Mode’s double render exists to check exactly this.</sub> |
| **서버 컴포넌트**<br><sub>Server Components</sub> | 서버에서만 실행되는 컴포넌트예요. DB를 바로 읽고 코드가 브라우저로 가지 않으며, 상호작용이 필요한 부분만 "use client"로 표시해요.<br><sub>Components that run only on the server: they read databases directly and ship no code to the browser, while interactive parts are marked "use client".</sub> | export default async function Page()에서 await db.post.findMany()로 데이터를 바로 읽고, 그 코드와 쓰인 라이브러리는 브라우저 번들에 들어가지 않아요. 좋아요 버튼처럼 useState나 onClick이 필요한 컴포넌트만 파일 맨 위에 "use client"를 적어 클라이언트 컴포넌트로 만들어요. 서버는 렌더 결과를 RSC 페이로드로 보내고, 클라이언트 컴포넌트 자리에는 그 JS가 내려와 하이드레이션돼요. 서버에서 클라이언트로 넘기는 props는 직렬화할 수 있어야 하고, 클라이언트 컴포넌트 안에 서버 컴포넌트를 넣으려면 children으로 전달해요. Next.js App Router가 대표적인 구현이에요.<br><sub>In export default async function Page(), await db.post.findMany() reads data directly, and neither that code nor its libraries enter the browser bundle. Only components needing useState or onClick, such as a like button, get "use client" at the top of the file to become client components. The server sends its output as an RSC payload, and client components’ JavaScript downloads into their slots and hydrates. Props crossing to client components must be serializable, and server components go inside client ones as children. The Next.js App Router is the best-known implementation.</sub> |
| **Actions와 useActionState**<br><sub>Actions and useActionState</sub> | React 19의 Actions는 폼 제출 같은 비동기 작업의 진행 중·오류·결과·낙관적 상태를 React가 관리하게 해 줘요.<br><sub>React 19 Actions let React manage the pending, error, result and optimistic states of async work such as form submissions.</sub> | <form action={action}>에 함수를 넘기면 제출 때 FormData로 호출되어 preventDefault나 입력별 useState가 필요 없어요. const [state, action, pending] = useActionState(save, null)은 진행 중 여부를 자동으로 알려 줘서 버튼을 잠가 중복 제출을 막고, save의 반환값이 state가 되어 오류 메시지나 결과를 그려요. useOptimistic은 서버 응답 전에 성공한 것처럼 먼저 보여주고 실패하면 원래대로 되돌려요. 서버 함수("use server")를 action에 바로 넘기면 JS가 로드되기 전에도 폼이 동작해요. 폼 안의 자식은 useFormStatus로 pending을 읽어요.<br><sub>Passing a function to <form action={action}> calls it with FormData on submit, with no preventDefault or per-field useState. const [state, action, pending] = useActionState(save, null) reports pending automatically so the button can be disabled against double submits, and save’s return value becomes state for rendering errors or results. useOptimistic shows the expected result before the server responds and reverts on failure. Passing a server function ("use server") straight to action makes the form work even before JavaScript loads, and children inside the form read pending with useFormStatus.</sub> |
| **use()**<br><sub>use()</sub> | use()는 렌더 중에 Promise나 Context를 읽는 React 19의 API예요. Promise가 아직이면 컴포넌트가 일시 정지되고 Suspense가 fallback을 보여줘요.<br><sub>use() is the React 19 API for reading promises or context during render; a pending promise suspends the component and Suspense shows its fallback.</sub> | const list = use(promise)는 Promise가 끝났으면 결과를 바로 꺼내고, 아직이면 컴포넌트를 일시 정지시켜 가장 가까운 Suspense의 fallback이 보이게 해요. 실패하면 Error Boundary가 받아요. use는 다른 훅과 달리 if나 반복문 안에서도 부를 수 있고, use(ThemeContext)처럼 Context를 읽는 데도 써요. 주의할 점은 렌더할 때마다 새 Promise를 만들면 끝없이 정지한다는 것이에요. 그래서 서버 컴포넌트에서 await하지 않은 Promise를 만들어 클라이언트 컴포넌트에 넘기는 패턴으로 데이터를 스트리밍해요.<br><sub>const list = use(promise) returns the result immediately if the promise has settled, and otherwise suspends the component so the nearest Suspense shows its fallback; failures go to an error boundary. Unlike other hooks, use may be called inside if statements and loops, and use(ThemeContext) reads context too. The catch is that creating a new promise every render suspends forever, so the pattern is to create an un-awaited promise in a server component and pass it to a client component, streaming the data.</sub> |
| **React Compiler**<br><sub>React Compiler</sub> | React Compiler는 빌드 단계에서 컴포넌트를 분석해 메모이제이션을 자동으로 넣어 줘요. useMemo·useCallback·memo를 손으로 쓸 일이 크게 줄어요.<br><sub>React Compiler analyzes components at build time and inserts memoization automatically, largely removing hand-written useMemo, useCallback and memo.</sub> | items.filter(...)와 <Rows rows={shown} />를 평범하게 쓴 List 컴포넌트는 관련 없는 렌더에도 계산과 자식 렌더를 반복해요. 컴파일러는 빌드 때 값이 무엇에 의존하는지 분석해, items와 q가 같으면 shown을 재사용하고 rows가 같으면 Rows 렌더를 건너뛰는 코드를 자동으로 만들어요. 손으로 관리하던 의존성 배열의 실수도 사라지고 코드는 더 단순해져요. 단, 렌더 중 값을 바꾸지 않고 훅 규칙을 지키는 등 React의 규칙을 따른 컴포넌트만 최적화하고, 어긴 컴포넌트는 건너뛰어요. Vite·Next.js 플러그인으로 점진적으로 켤 수 있어요.<br><sub>A List component written plainly with items.filter(...) and <Rows rows={shown} /> repeats its calculation and child render even on unrelated renders. The compiler analyzes dependencies at build time and generates code that reuses shown while items and q match and skips rendering Rows while rows matches. Dependency-array mistakes disappear and code gets simpler. It only optimizes components that follow the rules of React, such as no mutation during render and the rules of hooks, and skips those that do not. It can be enabled incrementally through Vite or Next.js plugins.</sub> |
| **컴포넌트 테스트**<br><sub>Testing components</sub> | React Testing Library는 구현 세부가 아니라 사용자가 보고 하는 행동을 기준으로 컴포넌트를 검증해요.<br><sub>React Testing Library verifies components by what users see and do rather than by implementation details.</sub> | render(<Login />)로 컴포넌트를 jsdom 같은 가짜 DOM에 그리고, getByLabelText("이메일"), getByRole("button", { name: "로그인" })처럼 사용자가 인식하는 라벨과 역할로 요소를 찾아 user.type, user.click으로 행동해요. 결과도 findByRole("alert")처럼 화면에 보이는 것으로 확인하고, findBy는 비동기로 나타날 때까지 기다려요. 클래스 이름이나 내부 상태로 찾지 않으니 리팩터링해도 테스트가 깨지지 않아요. 네트워크는 MSW로 가짜 응답을 주고, getByRole은 접근성 트리를 쓰므로 접근성 점검 효과도 있어요. 전체 흐름은 Playwright 같은 E2E 테스트로 보완해요.<br><sub>render(<Login />) draws the component into a simulated DOM such as jsdom, and queries such as getByLabelText("Email") and getByRole("button", { name: "Log in" }) find elements the way users perceive them before acting with user.type and user.click. Results are checked by what appears, as in findByRole("alert"), and findBy waits for async content. Because nothing is found by class names or internal state, refactors do not break the tests. MSW supplies fake network responses, and getByRole doubles as an accessibility check since it uses the accessibility tree. End-to-end tests such as Playwright cover whole flows.</sub> |
