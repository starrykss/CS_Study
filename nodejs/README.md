At the bottom, libuv is a library written in C that provides the event loop, asynchronous I/O, timers and the thread pool. V8 is the same JavaScript engine as Chrome’s; it interprets code as bytecode and optimizes the frequently executed parts into machine code. Node’s C++ bindings and core modules such as fs, net, http and crypto connect the two. Here, process.versions reported Node 22.23, V8 12.4 and libuv 1.51. Node is often called single-threaded, but precisely, that means JavaScript code runs only on a single main thread. Counting the threads in /proc for a Node process that did nothing but wait on a timer found 7, including V8 threads that help with garbage collection and optimizing compilation in the background. Still, your code never runs in two places at once, so shared variables need no locks. I/O is handled in two ways. Network sockets are registered with the OS’s event notification facility, epoll on Linux or kqueue on macOS, and the main thread handles only sockets whose data is ready, which lets one thread manage tens of thousands of connections. On the other hand, work for which the OS offers no usable asynchronous interface, such as reading ordinary files, along with dns.lookup, zlib compression and CPU-heavy calls such as crypto.pbkdf2, runs on libuv’s thread pool. The pool has 4 threads by default and is created when first needed, so the first pbkdf2 call raised the thread count from 7 to 11. When work finishes, its result returns to the event loop and reaches JavaScript through a callback or a Promise. Thanks to this structure, Node is strong at I/O-centric servers that spend most of their time waiting, and weak at CPU computation that occupies the main thread for long. | **이벤트 루프의 단계**<br><sub>Event loop phases</sub> | libuv 루프는 timers, poll, check, close 단계를 차례로 돌아요. I/O 콜백 안에서는 setImmediate가 늘 setTimeout(0)보다 먼저였고, 메인 모듈에서는 200번 중 순서가 갈렸어요.<br><sub>The libuv loop cycles through the timers, poll, check and close phases. Inside an I/O callback setImmediate always ran before setTimeout(0), while in the main module the order varied across 200 runs.</sub> | 브라우저의 이벤트 루프는 태스크 큐 하나를 도는 모델로 설명되지만, Node의 이벤트 루프는 libuv가 돌리며 여러 단계를 정해진 순서로 지나요. timers 단계는 만료된 setTimeout과 setInterval 콜백을 실행해요. pending callbacks 단계를 지나 poll 단계에서는 새 I/O 이벤트를 기다리고, 파일 읽기 완료나 소켓 데이터 도착 같은 I/O 콜백을 실행해요. check 단계는 setImmediate로 등록한 콜백을, close 단계는 소켓의 close 이벤트 같은 콜백을 실행하고, 다시 timers로 돌아가요. 할 일이 없으면 루프는 poll 단계에서 다음 타이머 시각까지 잠들어 CPU를 쓰지 않아요. 이 단계 구조 때문에 setTimeout(fn, 0)과 setImmediate(fn)의 순서가 상황에 따라 달라져요. fs.readFile의 콜백은 poll 단계에서 실행되므로, 그 안에서 두 콜백을 등록하면 poll 바로 다음이 check 단계라 setImmediate가 먼저 실행되고, setTimeout은 다음 바퀴의 timers 단계에서야 실행돼요. 실제 출력도 nextTick → promise → immediate → timeout이었어요. 콜백이 끝나자마자 nextTick과 Promise 마이크로태스크가 먼저 비워진 것도 보여요. 반면 메인 모듈에서 두 콜백을 등록하면 순서가 정해지지 않아요. setTimeout(fn, 0)은 실제로는 1ms 타이머가 되는데, 프로그램을 준비하고 루프에 들어가는 데 1ms가 넘게 걸렸다면 첫 timers 단계에서 이미 만료되어 먼저 실행되고, 아니면 check 단계의 setImmediate가 먼저예요. 새 프로세스로 200번 실행하자 immediate가 195번, timeout이 5번 먼저 실행됐어요. 컴퓨터의 부하에 따라 이 비율은 바뀌므로, 이런 순서에 기대는 코드는 쓰지 않아야 해요. 루프에 양보해 다른 I/O를 먼저 처리하게 하고 싶다면 setImmediate가 의도를 가장 분명하게 드러내요.<br><sub>The browser’s event loop is often explained as a single task queue, but Node’s event loop, driven by libuv, passes through several phases in a fixed order. The timers phase runs expired setTimeout and setInterval callbacks. After the pending callbacks phase, the poll phase waits for new I/O events and runs I/O callbacks such as a completed file read or data arriving on a socket. The check phase runs callbacks registered with setImmediate, and the close phase runs callbacks such as a socket’s close event, before returning to timers. When there is nothing to do, the loop sleeps in the poll phase until the next timer is due, using no CPU. Because of this phase structure, the order of setTimeout(fn, 0) and setImmediate(fn) depends on the situation. fs.readFile’s callback runs in the poll phase, so when it registers both callbacks, setImmediate runs first, since check comes right after poll, while setTimeout runs only in the timers phase of the next lap. The actual output was nextTick → promise → immediate → timeout, which also shows the nextTick and Promise microtasks draining as soon as the callback ended. Registering both callbacks from the main module, however, leaves the order undefined. setTimeout(fn, 0) actually becomes a 1 ms timer, and if preparing the program and entering the loop took more than 1 ms, the timer has already expired at the first timers phase and runs first; otherwise setImmediate in the check phase goes first. Running it 200 times in fresh processes put immediate first 195 times and timeout first 5 times. This ratio shifts with machine load, so code must never depend on such an order. When you want to yield to the loop and let other I/O go first, setImmediate states that intent most clearly.</sub> |
| **process.nextTick**<br><sub>process.nextTick</sub> | Node는 콜백마다 nextTick 큐를 Promise 마이크로태스크보다 먼저 비워요. 그래서 nextTick을 재귀로 걸면 큐가 비지 않아, 0ms 타이머가 107ms 뒤에야 실행됐어요.<br><sub>Node drains the nextTick queue ahead of Promise microtasks after every callback. So recursive nextTick kept the queue from emptying, and a 0 ms timer fired only after 107 ms.</sub> | Node에는 브라우저에 없는 실행 큐가 하나 더 있어요. process.nextTick으로 등록한 콜백의 큐예요. Node는 JavaScript 콜백 하나가 끝날 때마다, 이벤트 루프의 다음 단계로 넘어가기 전에 두 큐를 비워요. 먼저 nextTick 큐를 완전히 비우고, 그다음 Promise의 then과 queueMicrotask로 등록한 마이크로태스크 큐를 비워요. 마이크로태스크를 실행하다 새 nextTick이 생기면 다시 nextTick 큐로 돌아가요. 그래서 Promise를 먼저 등록하고 nextTick을 나중에 등록해도 nextTick이 먼저 실행돼요. 실제 출력은 tick1 → tick2 → tick-from-tick → promise1 → microtask → promise-from-tick이었어요. tick2 안에서 새로 건 nextTick까지 promise1보다 먼저 실행됐고, tick2 안에서 등록한 Promise는 마이크로태스크 큐의 맨 뒤에 붙었어요. 이름과 달리 nextTick은 이벤트 루프의 다음 바퀴가 아니라, 지금 실행 중인 콜백이 끝난 바로 직후를 뜻해요. 반대로 setImmediate는 이름과 달리 즉시가 아니라 이번 바퀴의 check 단계를 뜻해서, 둘의 이름이 서로 바뀐 것 같다는 말이 Node 문서에도 있어요. nextTick 큐는 빌 때까지 비우므로 위험한 성질이 있어요. 콜백이 자기 자신을 계속 nextTick으로 다시 걸면 큐가 끝내 비지 않고, 이벤트 루프는 다음 단계로 넘어가지 못해요. 2,000,000번 재귀로 걸자 0ms로 걸어 둔 타이머가 107ms 뒤에야 실행됐고, 끝없이 걸었다면 I/O와 타이머가 영원히 굶었을 거예요. Promise 마이크로태스크도 같은 성질이 있지만, nextTick은 그보다도 앞서 실행된다는 점이 다르죠. 그래서 Node 문서는 대부분의 경우 표준 API인 queueMicrotask를 쓰고, 루프에 양보하려면 setImmediate를 쓰라고 권해요. nextTick은 콜백을 받는 API가 상황에 따라 동기로 부르거나 비동기로 부르지 않고 늘 비동기로 부르도록 만들 때, 또는 이벤트 리스너가 등록될 기회를 준 뒤 이벤트를 내보낼 때처럼 좁은 용도에 써요.<br><sub>Node has one more execution queue that browsers lack: the queue of callbacks registered with process.nextTick. After each JavaScript callback finishes, and before the event loop moves to its next phase, Node drains two queues. First it empties the nextTick queue completely, then the microtask queue of Promise then callbacks and queueMicrotask registrations. If running microtasks creates a new nextTick, it goes back to the nextTick queue. So even with a Promise registered first and a nextTick registered later, the nextTick runs first. The actual output was tick1 → tick2 → tick-from-tick → promise1 → microtask → promise-from-tick. A nextTick scheduled from inside tick2 also ran before promise1, while the Promise registered inside tick2 went to the back of the microtask queue. Despite its name, nextTick means not the next lap of the event loop but right after the currently running callback ends. Conversely, setImmediate, despite its name, means not immediately but the check phase of this lap, and even the Node documentation remarks that the two names seem swapped. Because the nextTick queue drains until empty, it has a dangerous property. If a callback keeps re-scheduling itself with nextTick, the queue never empties and the event loop cannot move to its next phase. Recursing 2,000,000 times delayed a timer set for 0 ms until 107 ms, and recursing forever would starve I/O and timers indefinitely. Promise microtasks share this property, but nextTick runs even before them. So the Node documentation recommends using the standard queueMicrotask in most cases and setImmediate to yield to the loop. nextTick is kept for narrow uses, such as making a callback-taking API always call back asynchronously rather than sometimes synchronously, or emitting an event only after listeners have had a chance to register.</sub> |

In real environments, the load balancer or Kubernetes removes the instance from its targets meanwhile, so new requests go to other instances; switching a readiness endpoint to failing speeds this up. Second, finish requests already in progress. close() does not cut in-flight requests, so the /slow request received its slow done response in full. Once every connection closed, the close callback ran and the process exited with code 0 at 1,402 ms after SIGTERM. Third, in that callback, release resources such as the database connection pool, message queue consumers and open files, then exit. In older Node, idle keep-alive connections that had finished their responses held close() open for seconds, so shutdown often waited for keepAliveTimeout. Since Node 19, close() closes idle connections too, and in this experiment keep-alive connections did not delay shutdown. Still, connections that never finish, such as streaming responses or hung requests, can exist. So the handler also sets a force-exit timer shorter than Kubernetes’ grace period, letting the process wrap up on its own before SIGKILL cuts cleanup short. The timer is created with unref() so it does not hold up a normal exit.</sub> |

CLI라면 --help를 출력하는 데 쓰지도 않는 압축 라이브러리나 클라우드 SDK를 불러올 이유가 없어요. 대부분의 실행에서 쓰이지 않는 코드가 시작 시간에서 빠져요. 다만 서버에서는 첫 요청이 그 비용을 떠안게 되므로, 요청 경로에서 쓰이는 모듈은 시작할 때 미리 불러오는 편이 나아요. 번들러로 실제로 쓰는 코드만 하나의 파일로 묶으면 파일 탐색과 파싱이 줄어 같은 효과를 내고, 서버리스 환경에서 특히 많이 써요.<br><sub>For a long-running server, startup time barely matters, but for CLI tools that start fresh for every command, serverless functions that may spin up a new instance per request, and development tools that run tests hundreds of times, startup time is exactly the time users wait. Requiring the 8.7 MB typescript package took 156–175 ms, mostly not reading from disk but V8 parsing that much JavaScript and compiling it to bytecode. An app loading a framework and dozens of packages can spend over a second just starting. Node has a module compile cache (the environment variable since 22.1, the function since 22.8). Giving a folder in the NODE\_COMPILE\_CACHE environment variable, or calling module.enableCompileCache() in code, makes V8 save its compilation results to disk and reuse them on later runs. The first run took a little longer, 193 ms, writing the cache and producing 2.4 MB of cache files. From the next run on, the same require took 76–91 ms, about half. The cache is rebuilt automatically when source files or the Node version change. The second technique is lazy loading. Heavy modules that are rarely used are not loaded at the top of the file but required or import()ed inside the function the first time their feature is used. A CLI has no reason to load a compression library or a cloud SDK it does not use just to print --help, so code most runs never touch drops out of startup. On a server, though, the first request would absorb that cost, so modules used on request paths are better loaded at startup.
