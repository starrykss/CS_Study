| **스키마**<br><sub>The schema</sub> | 스키마는 서버가 줄 수 있는 타입과 필드를 적은 계약서예요. 스키마에 없는 필드를 묻자 실행 전에 검증에서 막혔고, 타입 뒤의 !는 null이 아니라는 약속이에요.<br><sub>The schema is a contract listing the types and fields a server offers. Asking for a field outside it failed validation before execution, and a ! after a type promises the value is never null.</sub> | GraphQL 서버는 스키마로 시작해요. 스키마 정의 언어인 SDL로 type Book { id: ID!, title: String!, author: Author!, tags: [Tag!]! }처럼 타입과 필드, 각 필드의 타입을 적어요. 그리고 Query라는 특별한 타입에 클라이언트가 처음 물어볼 수 있는 입구, 예를 들어 book(id: ID!): Book과 books(first: Int = 10): [Book!]!을 적어요. 인자에는 타입과 기본값을 줄 수 있어요. 데이터를 바꾸는 입구는 Mutation, 실시간 알림의 입구는 Subscription 타입에 적어요. 스키마는 서버와 클라이언트 사이의 계약서예요. 서버는 스키마에 적힌 것만 줄 수 있고, 클라이언트는 스키마에 적힌 것만 물을 수 있어요. 이 계약은 실행 전에 강제돼요. 스키마에 없는 필드 nope을 묻자 Cannot query field "nope" on type "A".라는 오류가 났고, 리졸버는 하나도 실행되지 않았으며 응답에는 data가 아예 없었어요. 오타나 잘못된 인자 타입이 서버 코드에 닿기 전에 걸러지는 거예요. 타입 뒤의 !는 null이 될 수 없다는 뜻이에요. String은 문자열이거나 null이고, String!은 언제나 문자열이에요. 목록은 두 겹으로 표시해요. [Book]은 목록도 항목도 null일 수 있고, [Book!]!은 목록 자체도 null이 아니고 그 안의 항목도 null이 아니에요. 클라이언트는 이 약속을 믿고 null 검사를 생략할 수 있어요. 다만 !를 붙이면 그 필드가 실패했을 때 영향이 커지는데, 이것은 오류 항목과 스키마 설계 섹션에서 재요. 이 계약 하나에서 많은 것이 나와요. 서버는 요청을 검증하고, GraphiQL 같은 도구는 문서와 자동 완성을 보여 주고, 클라이언트는 코드 생성기로 TypeScript 타입을 만들어요. 스키마를 만드는 방식은 두 가지예요. SDL로 스키마를 먼저 쓰고 리졸버를 맞추는 스키마 우선 방식과, TypeGraphQL이나 Pothos, Strawberry처럼 코드의 클래스나 함수에서 스키마를 만들어 내는 코드 우선 방식이에요. 어느 쪽이든 최종 결과는 같은 SDL로 출력할 수 있어서, 스키마 파일을 저장소에 두고 변경을 리뷰하는 것이 좋아요.<br><sub>A GraphQL server starts with a schema. In the schema definition language, SDL, types, fields and each field’s type are written, as in type Book { id: ID!, title: String!, author: Author!, tags: [Tag!]! }. A special type, Query, lists the entry points clients can ask first, such as book(id: ID!): Book and books(first: Int = 10): [Book!]!, and arguments can carry types and defaults. Entry points that change data go in the Mutation type, and those for real-time notifications in Subscription. The schema is the contract between server and clients: the server can provide only what the schema lists, and clients can ask only for what it lists. The contract is enforced before execution. Asking for nope, a field not in the schema, produced the error Cannot query field "nope" on type "A"., with no resolver running at all and no data in the response. Typos and wrong argument types are filtered out before reaching server code. A ! after a type means it can never be null: String is a string or null, while String! is always a string. Lists are marked in two layers: in [Book] both the list and its items may be null, while in [Book!]! neither the list nor its items are null. Clients can rely on this promise and skip null checks. Adding ! widens the impact when that field fails, though, as measured in the errors item and the schema design section. Much flows from this one contract: the server validates requests, tools such as GraphiQL show docs and autocompletion, and clients generate TypeScript types with code generators. There are two ways to build a schema: schema-first, writing SDL and fitting resolvers to it, and code-first, generating the schema from classes or functions in code, as TypeGraphQL, Pothos or Strawberry do. Either way the result can be printed as the same SDL, so keeping the schema file in the repository and reviewing changes to it is a good practice.</sub> |
| **요청한 모양의 응답**<br><sub>Responses shaped by requests</sub> | 응답은 요청한 필드 그대로의 모양으로 왔어요. 책, 저자, 태그가 필요한 화면에서 REST는 요청 3번에 107ms와 1,398바이트, GraphQL은 1번에 55ms와 114바이트였어요.<br><sub>Responses came back in exactly the shape of the requested fields. For a screen needing a book, its author and tags, REST took 3 requests, 107 ms and 1,398 bytes; GraphQL took 1 request, 55 ms and 114 bytes.</sub> | GraphQL에서는 클라이언트가 필요한 필드를 직접 적어 보내요. { book(id: 5) { title author { name } } }를 보내자, 응답은 {"data":{"book":{"title":"Book 4","author":{"name":"Author 4"}}}}였어요. 요청의 중괄호 구조가 응답의 JSON 구조와 똑같고, 묻지 않은 가격, 설명, 날짜 같은 필드는 오지 않았어요. 클라이언트 코드는 응답의 모양을 쿼리만 보고 알 수 있어요. REST와 비교했어요. 책 제목, 저자 이름, 태그 이름을 보여 주는 화면을 두 방식으로 만들고, 서버가 요청마다 50ms를 기다리게 해서 네트워크 왕복 지연을 흉내 냈어요. REST에서는 /books/5를 받아야 저자 id를 알 수 있으므로, 그다음에 /authors/4와 /books/5/tags를 동시에 보냈어요. 요청 3번에 왕복 2번이 필요했고 107ms가 걸렸어요. GraphQL은 요청 1번으로 55ms였어요. 서버 안에서 리졸버들이 데이터를 모아 한 번에 돌려주기 때문이에요. 전송량도 차이가 났어요. REST의 각 응답은 그 리소스의 모든 필드, 예를 들어 책의 ISBN, 400자 설명, 생성일과 저자의 600자 소개, 사진 주소를 담아 합계 1,398바이트였어요. GraphQL은 필요한 필드만 담아 114바이트로 12분의 1이었어요. 필요 이상을 받는 것을 과다 가져오기, 한 번에 부족해 여러 번 묻는 것을 과소 가져오기라고 하는데, GraphQL은 둘 다 줄여요. 지연이 큰 모바일 네트워크에서는 왕복 횟수의 차이가 체감 속도를 크게 바꿔요. 화면이 필요한 데이터를 화면 쪽에서 정하므로, 새 화면이 생길 때마다 서버에 맞춤 엔드포인트를 만들 필요도 줄어요. 모바일 앱과 웹이 같은 API에서 각자 필요한 만큼만 가져갈 수 있어요. 대신 비용은 서버로 옮겨 가요. 서버는 클라이언트가 보낼 수 있는 어떤 조합의 요청도 감당해야 하고, REST처럼 URL마다 캐시하거나 요청 비용을 미리 알기 어려워요. 이 비용은 실행 섹션의 N+1과 보안 섹션의 깊은 쿼리, HTTP와 캐시 섹션에서 차례로 재요.<br><sub>In GraphQL, the client writes out the fields it needs. Sending { book(id: 5) { title author { name } } } returned {"data":{"book":{"title":"Book 4","author":{"name":"Author 4"}}}}. The brace structure of the request matches the JSON structure of the response, and unrequested fields such as price, description and dates never came, so client code knows the response’s shape just by reading the query. It was compared with REST. A screen showing a book’s title, its author’s name and its tags was built both ways, with the server waiting 50 ms per request to mimic network round-trip latency. With REST, the author id is known only after receiving /books/5, so /authors/4 and /books/5/tags were then sent together: 3 requests over 2 round trips, taking 107 ms. GraphQL took a single request and 55 ms, because resolvers inside the server gather the data and return it at once. Payloads differed too. Each REST response carried all fields of its resource, such as the book’s ISBN, a 400-character description and timestamps, and the author’s 600-character bio and photo URL, 1,398 bytes in total. GraphQL carried only the needed fields in 114 bytes, one twelfth. Receiving more than needed is called over-fetching, and asking repeatedly because one response is not enough is under-fetching; GraphQL reduces both. On high-latency mobile networks, the difference in round trips changes perceived speed considerably. Since screens decide the data they need, there is less need to build a custom server endpoint for each new screen, and mobile apps and the web can take just what each needs from the same API. The cost moves to the server, though. The server must handle any combination of requests a client can send, and unlike REST, it is hard to cache per URL or know a request’s cost in advance. These costs are measured in turn in the N+1 item of the execution section, deep queries in the security section, and the HTTP and caching section.</sub> |
| **리졸버**<br><sub>Resolvers</sub> | 리졸버는 필드 하나를 채우는 함수이고, 부모의 결과가 자식의 인자가 돼요. 리졸버가 없는 title은 기본 리졸버가 0ms에 읽었고, 저자 리졸버는 책마다 따로 불렸어요.<br><sub>A resolver fills one field, and a parent’s result becomes its children’s argument. title, without its own resolver, was read by the default resolver in 0 ms, while the author resolver ran separately for each book.</sub> | 스키마는 무엇을 줄 수 있는지만 말하고, 실제 값은 리졸버가 만들어요. 리졸버는 스키마의 필드 하나를 채우는 함수예요. Query.books 리졸버는 SQL로 책 목록을 가져오고, Book.author 리졸버는 그 책의 저자를 가져와요. 실행기는 요청의 트리를 위에서부터 따라 내려가며 리졸버를 불러요. 부모 리졸버가 돌려준 값은 자식 리졸버의 첫 번째 인자가 되고, 필드의 인자, 요청마다 공유되는 컨텍스트, 실행 정보가 함께 넘어가요. Book.author 리졸버는 부모인 책 객체를 받아 그 author\_id로 저자를 찾는 식이에요. 책 3권과 각 저자를 묻는 요청에서 리졸버마다 걸린 시간과 횟수를 쟀어요. Query.books는 한 번 불려 8.6ms, Book.title은 세 번 불려 각각 0ms, Book.author는 세 번 불려 각각 11.7ms였어요. title처럼 리졸버를 따로 쓰지 않은 필드는 기본 리졸버가 처리해요. 부모 객체에서 같은 이름의 속성을 읽거나, 그것이 함수면 불러서 돌려줘요. 대부분의 스칼라 필드는 이렇게 거의 비용 없이 채워져요. 중요한 점은 리졸버들이 서로를 모르고 따로 불린다는 거예요. Book.author 리졸버는 지금 몇 권의 책이 함께 처리되는지 모르고, 자기에게 주어진 책 하나만 봐요. 그래서 목록 아래에 있는 리졸버는 목록의 항목 수만큼 실행되고, 각자 DB에 쿼리를 보내요. 책 3권이면 저자 쿼리가 3번, 책 100권이면 100번이에요. 이것이 다음 섹션의 N+1 문제이고, DataLoader로 해결해요. 리졸버가 값을 어디서 가져오는지는 자유예요. 같은 스키마 안에서 어떤 필드는 PostgreSQL에서, 어떤 필드는 다른 마이크로서비스의 REST API에서, 어떤 필드는 Redis 캐시에서 가져올 수 있어요. 계산된 필드, 예를 들어 할인된 가격이나 읽기 시간도 리졸버에서 만들어요. 스키마는 저장소의 구조를 그대로 드러내는 것이 아니라 클라이언트에게 보여 줄 모양이므로, 표의 열 이름이 바뀌어도 리졸버만 고치면 클라이언트는 영향을 받지 않아요. 같은 이유로 여러 서비스를 하나의 그래프로 묶는 게이트웨이로도 많이 쓰여요.<br><sub>The schema only says what can be provided; resolvers produce the actual values. A resolver is a function filling one field of the schema: the Query.books resolver fetches the book list with SQL, and the Book.author resolver fetches that book’s author. The executor walks down the request tree from the top, calling resolvers. A parent resolver’s return value becomes the child resolver’s first argument, passed along with the field’s arguments, a context shared per request and execution info; Book.author receives its parent book object and looks up the author by its author\_id. For a request asking for 3 books with their authors, the time and count of each resolver were measured: Query.books was called once in 8.6 ms, Book.title three times at 0 ms each, and Book.author three times at 11.7 ms each. Fields without their own resolver, such as title, are handled by the default resolver, which reads the same-named property of the parent object, or calls it if it is a function, so most scalar fields are filled at almost no cost. The key point is that resolvers are called independently, unaware of each other. Book.author does not know how many books are being processed together; it sees only the one book given to it. So a resolver beneath a list runs once per item in the list, each sending its own database query: 3 author queries for 3 books, 100 for 100 books. This is the N+1 problem of the next section, solved with DataLoader. Where a resolver gets its value is up to it. Within one schema, some fields can come from PostgreSQL, some from another microservice’s REST API and some from a Redis cache. Computed fields, such as a discounted price or reading time, are produced in resolvers too. The schema is not a direct exposure of storage structure but the shape shown to clients, so when a table’s column names change, only resolvers change and clients are unaffected. For the same reason GraphQL is widely used as a gateway uniting several services into one graph.</sub> |
| **오류와 부분 성공**<br><sub>Errors and partial success</sub> | 한 필드가 실패해도 나머지 데이터는 오고, 실패한 자리는 null과 path로 표시됐어요. null이 될 수 없는 필드가 실패하자 그 부모가 통째로 null이 됐어요.<br><sub>Even when one field failed, the rest of the data arrived, with the failed spot marked by null and a path. When a non-null field failed, its whole parent became null.</sub> | REST의 응답은 대개 성공 아니면 실패이지만, GraphQL에는 부분 성공이 있어요. 하나의 요청이 여러 필드를 묻고, 각 필드는 서로 다른 리졸버와 데이터 소스에서 오므로, 일부만 실패하는 일이 자연스러워요. 필드 a 안의 bad 리졸버가 예외를 던지게 했어요. 응답의 data에는 a.ok의 "fine"과 b의 "b"가 그대로 있었고, a.bad만 null이었어요. 그리고 errors 배열에 오류 메시지, 쿼리에서의 위치(locations), 그리고 path: ["a", "bad"]가 들어 있었어요. 클라이언트는 path로 어느 필드가 실패했는지 정확히 알 수 있으므로, 화면의 그 부분만 오류 상태로 보여 주고 나머지는 정상으로 그릴 수 있어요. 추천 상품 목록이 실패해도 상품 상세는 보여 주는 식이에요. null이 될 수 없는 필드가 실패하면 달라져요. ## 요청 하나가 처리되기까지 · How one request is processed

| **파싱, 검증, 실행**<br><sub>Parse, validate, execute</sub> | 요청은 파싱, 검증, 실행을 거쳐요. 같은 쿼리를 2,000번 재자 파싱 14.8µs, 검증 155µs, 실행 78µs로 검증이 가장 비쌌고, 그래서 같은 쿼리의 검증 결과를 캐시해요.<br><sub>Requests go through parsing, validation and execution. First, parsing reads the query string and turns it into a document tree, an AST; malformed syntax produces a Syntax Error here. Second, validation checks that tree against the schema using dozens of rules defined in the specification: whether fields exist on their types, whether argument names and types are right, whether same-named fields overlap with different arguments, whether every declared variable is used, whether fragments form cycles, and more. Third, execution walks the tree calling resolvers to build the result. If either of the first two steps fails, execution never happens. The cost of each step was measured with a query for 20 books and each author’s id and name, repeating each step 2,000 times. The averages were 14.8 µs for parsing, 155 µs for validation and 78 µs for execution, with execution returning in-memory data and no database. Validation was the most expensive, twice execution, because every field is looked up in the schema and run through several rules; large queries in real services can spend milliseconds on validation alone. Fortunately, validation results depend only on the query string and the schema, not on variable values. The same query string always yields the same result, so it can be cached and reused. Depth limits and cost analysis from the security section are added as validation rules, and more rules mean longer validation, but they stop executions that would take hundreds of milliseconds before they start, so they usually pay off. To see execution’s own cost without data fetching, 10,000 books holding id, title, price and an author’s id and name were built in memory in advance and returned as is by a query. Filling 60,000 fields, 5 per book plus an author object each, took 37–66 ms over three measurements. Serializing the same array with JSON.stringify took 2.5–3.1 ms, so GraphQL execution took over 15 times longer with no database and no network. The executor repeats the same work for every field: finding and calling its resolver, reading the property from the parent object for default resolvers, checking whether the return value is a Promise, checking it against the schema type, coercing scalars such as Int or String, descending into the fields below for objects, and placing it into the result object. Each step takes under a microsecond, but they add up in direct proportion to the field count. For a typical screen showing about 20 books this costs tens of microseconds and is negligible. Returning large results through GraphQL, though, such as admin tables of thousands of rows, full lists or CSV exports, becomes noticeable in server CPU, and in Node.js the event loop is blocked meanwhile, so other requests in the same process wait too. There are several remedies. Large lists are split with the cursor-based pagination of the next section, returning tens to hundreds of rows at a time; users rarely need 10,000 rows on one screen anyway. Bulk exports get a separate download endpoint outside GraphQL that streams the file. The executor itself can also change: graphql-jit analyzes a query document in advance and compiles it into a JavaScript function dedicated to that query, reducing the generic work repeated per field, which pays off on servers where the same queries repeat. Reducing execution cost matters, but preventing a single request from asking for too many fields matters most, which is covered by depth limits in the security section and cost analysis in the operations section.</sub> |
| **구독**<br><sub>Subscriptions</sub> | 웹소켓 하나로 구독을 등록하자 서버가 이벤트마다 next 메시지를 밀어 줬어요. 다른 상품의 이벤트는 걸러졌고, 도착까지 1ms 안팎이었어요.<br><sub>Registering a subscription over one WebSocket made the server push a next message per event. GraphQL’s third operation type, the subscription, does this. Writing subscription { priceChanged(id: "7") } makes the client receive a result every time item 7’s price changes from then on. Subscriptions usually run over a WebSocket with the graphql-ws protocol. The messages exchanged between client and server were recorded. The client sent connection\_init and the server answered connection\_ack, establishing the connection. When the client sent its subscription query in a subscribe message, the server sent a next message with the result for each event. One WebSocket connection can carry several subscriptions at once, each identified by the id in its messages, and ending a subscription exchanges a complete message. On the server, the subscription field’s resolver returns an async iterable that yields events one by one; here an async function\* awaited price events on an event bus and yielded only those with a matching id. Firing price events for items 7, 8, 7 and 7 delivered only item 7’s 100, 110 and 120 to the client, with item 8 filtered out. Each event runs through the subscription query again, so the client receives exactly the requested shape. On the same machine, the time from event to arrival was 0.8–1.3 ms: unlike periodic polling, updates arrive only on change and almost immediately. Production brings many considerations. With several servers, clients connected to other servers must also receive an event raised on one, so events must spread through a shared message channel such as Redis Pub/Sub; an in-memory event bus works on a single server only. Every open WebSocket connection uses server memory, and load balancers and proxies must support WebSockets and not cut long-lived connections. Permissions must be checked per subscription too. So for data that changes only occasionally, polling every 30 seconds is often simpler and sufficient. Where data only needs to flow from server to client, delivering subscriptions over server-sent events (SSE) on HTTP is also used.</sub> |

| **null 허용과 !**<br><sub>Nullability and !</sub> | !는 클라이언트에게 편한 약속이지만 실패하면 null이 부모로 번져요. 출력 필드에 나중에 !를 더하는 것은 안전했고, 빼거나 입력을 필수로 바꾸는 것은 깨지는 변경이었어요.<br><sub>The ! is a convenient promise for clients, but when it fails the null spreads to the parent. String means a string or null, and only String! with an exclamation mark promises it can never be null. When first building a schema, it is tempting to put ! on every field: clients need fewer null checks, and types generated for languages such as TypeScript look cleaner. That promise has a price, though. In the errors item of the basics section, when the resolver of the non-null field strict failed, null could not be placed there, so it travelled up to the nearest nullable parent. The parent a became null entirely, taking its healthy sibling ok, which had returned a value, along with it. Had the parent also been non-null, the null would keep climbing, and if it reached the top the whole of data would be null. A single field’s failure can blank an entire screen. So whether to add ! is decided by how likely the value is to fail. Values that always exist when the object exists, such as ids, creation times and columns of the same row, are safe as !. Fields fetched from other services or databases, such as reviews, recommendations or stock, and fields that may be hidden by permissions, stay nullable. Then, if that service fails, only that field becomes null and the rest still renders. Lists have two layers: [Review!] means the list itself may be null but its items never are, and [Review]! means the list is always there but items may be null. The direction of change matters too. Comparing with graphql-js’s findBreakingChanges, changing the output field price from Int to Int! went unreported, because clients already handling null are fine when null stops arriving. Changing title from String! to String, on the other hand, was a breaking FIELD\_CHANGED\_KIND, since clients trusting that null never arrives may crash when it does. Inputs run the other way. Changing argument n from Int to Int! and input field q from String to String! were both reported as breaking, because existing requests that never sent those values now fail validation. In short, outputs are easier to change later if they start nullable and gain ! once you are sure, and inputs if they start optional with defaults.</sub> |

The simplest way is to take how many items to skip, as in books(limit: 20, offset: 40), and pass it to SQL’s LIMIT and OFFSET. | **깨지지 않게 진화하기**<br><sub>Evolving without breaking</sub> | 필드를 지우거나 필수 인자를 더하자 깨지는 변경 2개가 보고됐어요. 같은 목적을 새 필드, 선택 인자, @deprecated로 이루자 깨지는 변경은 0개였어요.<br><sub>Removing a field and adding a required argument reported 2 breaking changes. Measured with a 40-alias query, the JSON body with the full query was 1,515 bytes, and the hash-only body 127 bytes. The hash is always 64 characters regardless of query size, so the bigger the query, the bigger the gain. The flow goes like this. At first the server does not know the hash: sending only the hash, Apollo Server returned 200 with a PERSISTED\_QUERY\_NOT\_FOUND error. Seeing this error, the client resends the hash together with the query. The server hashes the query itself, checks that it matches the hash sent, stores it and runs it. Sending the same hash again returned data immediately. Only the first request costs one extra round trip, after which every user sends just the hash. The store defaults to an in-memory LRU cache on the server; with several servers, a shared store such as Redis lets queries registered on one server be known to the others. Hash-only requests also make GET practical. Putting long queries in URLs hits length limits and produces different URLs every time, whereas the hash is short and the same query always maps to the same URL. Sending the hash in a GET query string ran just the same. Combined with the cache hints of the next item, CDNs can cache GraphQL responses by URL. In Apollo Client, enabling useGETForHashedQueries on the persisted query link sends hashed requests by GET. APQ is purely a performance feature, though. Since the server accepts and registers any query sent with its hash, an attacker’s deep query gets registered and executed just the same. Registering only the app’s queries in advance at build time and rejecting everything else requires the trusted documents, that is allow-lists, from the operations section.</sub> |
| **캐시 힌트와 Cache-Control**<br><sub>Cache hints and Cache-Control</sub> | 필드마다 @cacheControl 힌트를 적자 응답마다 가장 짧은 maxAge로 Cache-Control이 계산됐어요. PRIVATE 필드는 private, 힌트 없는 루트 필드가 섞이면 no-store였어요.<br><sub>With @cacheControl hints on each field, each response’s Cache-Control was computed from the shortest maxAge. GraphQL serves differently shaped responses per query from the same endpoint, so the server cannot choose a single value. Apollo Server has the @cacheControl directive record maxAge and scope per type and field in the schema, and computes a Cache-Control header for each response from the fields it actually contains. The Book type and book field got maxAge 300, the stock field maxAge 10, the user type Me maxAge 60 with scope: PRIVATE, and now, which returns the current time, no hint. Asking for book { id title } gave max-age=300, public. Adding stock to the same query cut it to max-age=10, public: a response is only as fresh as its fastest-aging field, so it takes the minimum maxAge among the fields included. Asking for me gave max-age=60, private. A single PRIVATE field makes the whole response private, and shared caches such as CDNs do not store private responses, so one user’s data never reaches another, though it may remain in the browser’s own cache. Asking for the unhinted root field now gave no-store, because root fields and fields returning object types default to maxAge 0 without a hint, whereas fields returning scalars, such as title, inherit their parent’s value. Asking for book and now in one query made the entire response no-store: data cacheable for five minutes loses caching altogether when mixed with a single uncacheable field. Designs that split fast-changing or per-user fields into separate queries therefore favor caching. The header was attached to POST responses too, but CDNs and browser caches usually store only GET responses, so actually using a CDN cache means turning queries into short hashes with APQ from the previous item and sending them by GET. The same computed policy also drives the server’s own response cache plugin, which can store responses per query and variables in server memory or Redis even without a CDN.</sub> |
| **정규화된 클라이언트 캐시**<br><sub>The normalized client cache</sub> | Apollo Client의 캐시는 객체를 \_\_typename과 id로 한 번만 저장해, 상세 쿼리의 결과가 목록 화면까지 바꿨어요. id가 없는 객체와 새 항목은 자동으로 반영되지 않았어요.<br><sub>Apollo Client’s cache stores each object once by \_\_typename and id, so a detail query’s result also updated the list screen. Objects without ids and new items were not reflected automatically.</sub> | GraphQL 클라이언트의 캐시는 브라우저의 HTTP 캐시와 달라요. 대부분의 요청이 POST라 HTTP 캐시를 쓰기 어렵고, 같은 책이 목록 쿼리, 상세 쿼리, 검색 쿼리에 각각 다른 모양으로 나타나기 때문이에요. Book:1에는 그 책의 필드가 들어 있고, ROOT\_QUERY의 books에는 객체 대신 { \_\_ref: "Book:1" }과 { \_\_ref: "Book:2" }라는 참조가 들어 있었어요. 키는 \_\_typename과 id를 합쳐 만들어요. 이것을 정규화라고 해요. DB의 정규화처럼 같은 데이터를 한 곳에만 둬요. 그 효과를 확인하려고 목록 쿼리를 지켜보는 감시자를 걸고, 상세 쿼리의 결과로 Book:2의 가격을 25로 썼어요. 목록 감시자는 정확히 한 번 알림을 받았고, 목록의 가격은 [10, 25]가 됐어요. 목록 쿼리를 다시 보내지 않았는데도요. 뮤테이션이 바뀐 객체의 id와 필드를 돌려주기만 하면, 그 객체를 보여 주는 모든 화면이 자동으로 바뀌는 거예요. 반대로 id 없이 쓴 책들은 정규화되지 않았어요. 캐시 키는 ROOT\_QUERY 하나뿐이었고, 책은 그 안에 통째로 들어갔어요. 다른 쿼리가 같은 책의 가격을 25로 써도 목록은 20 그대로였어요. 캐시는 두 객체가 같은지 알 방법이 없기 때문이에요. 그래서 쿼리마다 id를 함께 묻는 습관이 중요하고, id 대신 isbn 같은 다른 키를 쓰는 타입은 typePolicies의 keyFields로 알려 줘요. 또 캐시가 객체를 구분하려면 \_\_typename이 필요하므로 Apollo Client는 보내는 쿼리마다 \_\_typename을 자동으로 더해요. 정규화로 해결되지 않는 경우도 있어요. 새 책 Book:3을 쓰자 캐시의 키는 4개가 됐지만, 목록의 길이는 여전히 2였어요. 새 객체가 어느 목록에, 어느 위치에 들어가야 하는지는 캐시가 알 수 없어요. 정렬과 필터가 있는 목록이라면 더욱 그래요. 항목을 추가하거나 삭제한 뒤에는 cache.modify로 해당 목록 필드에 참조를 직접 넣거나 빼고, 간단하게는 refetchQueries로 목록 쿼리를 다시 가져와요. 삭제한 객체는 cache.evict로 캐시에서 지워요.<br><sub>A GraphQL client cache differs from the browser’s HTTP cache. Most requests are POSTs, which HTTP caches handle poorly, and the same book appears in different shapes across list, detail and search queries. Apollo Client’s InMemoryCache does not store responses whole per query but splits them into objects. Writing a list of two books produced three keys: Book:1, Book:2 and ROOT\_QUERY. Book:1 held that book’s fields, and ROOT\_QUERY’s books held references instead of objects, { \_\_ref: "Book:1" } and { \_\_ref: "Book:2" }. Keys combine \_\_typename and id. This is called normalization: like database normalization, the same data lives in one place only. To see the effect, a watcher was put on the list query, and a detail query’s result wrote Book:2’s price as 25. The list watcher was notified exactly once, and the list’s prices became [10, 25], without the list query being sent again. As long as a mutation returns the changed object’s id and fields, every screen showing that object updates automatically. Books written without ids, by contrast, were not normalized: the only key was ROOT\_QUERY, with the books stored whole inside it, and when another query wrote the same book’s price as 25, the list stayed at 20, because the cache has no way of knowing the two are the same object. Asking for id in every query is therefore an important habit, and types keyed by something else, such as isbn, declare it with keyFields in typePolicies. The cache also needs \_\_typename to tell objects apart, which is why Apollo Client automatically adds \_\_typename to every query it sends. Some cases normalization cannot solve. Writing a new book Book:3 raised the cache to four keys, but the list’s length stayed 2: the cache cannot know which lists, and at which positions, a new object belongs to, all the more for sorted and filtered lists. After adding or deleting items, references are put into or taken out of the relevant list field directly with cache.modify, or more simply the list query is fetched again with refetchQueries, while deleted objects are removed from the cache with cache.evict.</sub> |
| **요청 배치**<br><sub>Request batching</sub> | 쿼리 배열을 한 요청에 담자 기본 설정의 Apollo Server는 400으로 거절했고, 옵션을 켜자 결과 배열이 왔어요. 가장 느린 연산을 기다리고 속도 제한을 우회할 수 있어 기본으로 꺼져 있어요.<br><sub>With default settings, Apollo Server rejected an array of queries in one request with 400; enabling an option returned an array of results. It waits for the slowest operation and can bypass rate limits, so it is off by default.</sub> | 한 화면이 여러 컴포넌트로 이루어지고 각 컴포넌트가 자기 쿼리를 보내면, 화면을 열 때 요청 여러 개가 동시에 나가요. 배치는 이런 연산들을 JSON 배열에 담아 한 번의 HTTP 요청으로 보내는 방식이에요. 서버는 배열의 각 연산을 실행하고 결과를 같은 순서의 배열로 돌려줘요. 같은 쿼리 두 개를 배열로 보내자, 기본 설정의 Apollo Server는 400과 Operation batching disabled.라는 메시지로 거절했어요. allowBatchedHttpRequests: true를 켜고 다시 보내자 200과 함께 두 결과가 배열로 왔어요. 클라이언트에서는 Apollo Client의 BatchHttpLink가 짧은 시간 창 안에 나가는 연산들을 모아 한 요청으로 묶어 줘요. 배치가 주는 이점은 요청 수가 줄어드는 거예요. HTTP/1.1에서는 브라우저가 한 도메인에 동시에 여는 연결 수가 제한되어 있어서 요청이 많으면 줄을 서야 했고, 그래서 배치의 효과가 컸어요. 하지만 HTTP/2와 HTTP/3는 연결 하나로 여러 요청을 동시에 주고받으므로, 요청을 따로 보내도 대기가 거의 없어요. 남는 이점은 요청마다 붙는 헤더와 인증 처리 같은 고정 비용 정도예요. 대가도 있어요. 배열의 응답은 모든 연산이 끝나야 한꺼번에 오므로 가장 느린 연산이 나머지를 붙잡아요. 빠른 쿼리 결과를 먼저 그릴 수 없게 되는 거예요. 배열로 보낸 POST는 앞 항목들의 GET 기반 CDN 캐시도 쓸 수 없고, 한 요청 안에서 어떤 연산이 느렸는지 추적하기도 어려워져요. 보안 면에서는 보안 섹션의 별칭과 같은 문제가 있어요. 배열에 로그인 뮤테이션을 수천 개 담으면, HTTP 요청의 수를 세는 속도 제한은 이것을 요청 1개로 세요. 배열의 각 원소가 별도의 연산이라 별칭 수 제한에도 걸리지 않아요. 이런 이유로 Apollo Server 4부터 배치가 기본으로 꺼졌어요. 꼭 켜야 한다면 배열의 최대 길이를 정하고, 속도 제한과 비용 분석을 요청이 아니라 연산 단위로 적용해야 해요. 요청 수를 줄이는 것이 목적이라면, 화면의 쿼리들을 프래그먼트로 합쳐 쿼리 하나로 만드는 편이 GraphQL다운 해결책이에요. 여러 컴포넌트가 각자의 프래그먼트를 정의하고 화면의 쿼리가 그것들을 모으면, 요청은 하나이고 캐시와 추적도 그대로 쓸 수 있어요.<br><sub>When a screen consists of several components that each send their own query, opening the screen sends several requests at once. Batching puts those operations into a JSON array sent as a single HTTP request, and the server runs each operation in the array and returns the results as an array in the same order. Sending two identical queries as an array, Apollo Server with default settings rejected it with 400 and the message Operation batching disabled. After turning on allowBatchedHttpRequests: true and resending, both results came back as an array with 200. On the client, Apollo Client’s BatchHttpLink gathers operations sent within a short time window into one request. Batching’s benefit is fewer requests. In HTTP/1.1, browsers limit simultaneous connections per domain, so many requests had to queue and batching paid off greatly. HTTP/2 and HTTP/3, however, exchange many requests concurrently over one connection, so separate requests barely wait, leaving only fixed per-request costs such as headers and authentication as a benefit. There are costs too. An array response arrives only when every operation has finished, so the slowest operation holds back the rest and fast query results cannot be drawn first. An array POST cannot use the GET-based CDN caching from the previous items, and tracing which operation was slow inside one request becomes harder. Security-wise it shares the alias problem from the security section: put thousands of login mutations in an array, and rate limits counting HTTP requests see one request, while each element, being a separate operation, also escapes alias limits. For these reasons batching has been off by default since Apollo Server 4. If it must be enabled, cap the array length and apply rate limits and cost analysis per operation rather than per request. If the goal is fewer requests, the more GraphQL-like solution is to combine a screen’s queries into one through fragments: each component defines its own fragment and the screen’s query gathers them, giving a single request while keeping caching and tracing intact.</sub> |

The email field of the user type got a check that returns the value only when the asker is that user or an admin and otherwise throws a Forbidden error. With the context of user 1, user 2’s name and email were requested. name came back as lee, but email was null, with a Forbidden error carrying code FORBIDDEN and path ["user", "email"] in errors. Because email is nullable, the error stopped at that field, letting the screen show the name and leave the email blank; had email been non-null, as the design section showed, the null would have spread to the parent and erased the whole user, which is why fields that may be hidden by permissions stay nullable. Sending the same query with a context whose role was admin showed the email as lee@x.io. The query and schema are the same; only the context differs. Permissions are decided by the context at execution time, not by the shape of the schema. Where to put authorization checks is an important design question in GraphQL, because many paths lead to the same object: the user(id:) root field, node(id:) from the design section, search, and relation fields on other objects such as an order’s buyer can all return the same user. A check placed only on the user root field leaks through the other paths. Checks therefore go on the object’s fields themselves or in the business layer that resolvers share, so every path passes the same check. The DataLoaders from the execution section belong in the context too. Loaders cache results within a request, so sharing one across the whole server could leak data loaded by an admin into another user’s request through the cache, which is why a new loader must be created per request and stored in the context.</sub> |
