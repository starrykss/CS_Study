| **JIT 워밍업**<br><sub>JIT warmup</sub> | 같은 함수를 2만 번 부르자 첫 호출은 50µs, 100번째부터는 1.6µs로 30배 빨라졌어요. 처음 몇 번을 재면 컴파일 과정을 재게 돼요.<br><sub>Calling one function 20,000 times, the first call took 50 µs and calls from the 100th on 1.6 µs, 30× faster; timing the first few measures compilation.</sub> | JavaScript 엔진 V8은 코드를 처음부터 빠르게 실행하지 않아요. 처음에는 인터프리터 Ignition이 바이트코드를 한 줄씩 실행하고, 자주 불리는 함수를 점점 빠른 컴파일러로 다시 컴파일해요. 기본 컴파일러 Sparkplug, 중간 단계 Maglev, 최적화 컴파일러 TurboFan 순서예요. 이 과정이 측정에 어떻게 보이는지 쟀어요. 정수 1,000개를 더하는 함수를 2만 번 부르며 호출마다 시간을 기록했어요. 첫 호출은 50~54µs였어요. 처음 10번의 중간값은 24.8~33.5µs였고, 100번째쯤부터 1.6~1.9µs로 떨어져 끝까지 그대로였어요. 세 번 실행해 모두 같은 모양이었어요. 단계를 하나씩 꺼서 어느 단계가 빠른 속도를 만드는지 확인했어요. --jitless로 인터프리터만 쓰면 끝까지 24.4~24.8µs였어요. Maglev와 TurboFan을 끄고 Sparkplug까지만 쓰면 13.7~14.3µs, TurboFan만 끄면 13.4~14.2µs였어요. 1.6µs는 TurboFan이 만든 속도예요. 그러니 함수를 몇 번만 불러 시간을 재면, 코드의 성능이 아니라 인터프리터와 컴파일 과정을 잰 셈이 돼요. 두 구현을 이렇게 비교하면 먼저 최적화된 쪽이 이기는 엉뚱한 결과도 나와요. 그래서 tinybench나 mitata 같은 벤치마크 도구는 본 측정 전에 데우는 반복을 돌려요. 직접 잴 때도 충분히 반복해 시간이 안정된 다음부터 재요. 반대로 차가운 상태가 곧 실제 성능인 경우도 있어요. 한 번 실행하고 끝나는 명령줄 도구, 요청 몇 개만 받고 사라지는 서버리스 함수, 배포 직후의 첫 요청이 그래요. 이런 코드는 데운 성능만 보면 사용자가 겪는 시간을 놓쳐요. 그래서 차가운 성능과 데운 성능을 따로 재고, 사용자가 실제로 겪는 쪽을 기준으로 삼아요. 첫 요청의 비용은 다음 섹션에서 다시 다뤄요.<br><sub>V8, the JavaScript engine, does not run code fast from the start. At first the Ignition interpreter executes bytecode step by step, and frequently called functions are recompiled by progressively faster compilers: the baseline compiler Sparkplug, the mid-tier Maglev and the optimizing compiler TurboFan. To see how this shows up in measurements, a function summing 1,000 integers was called 20,000 times, recording the time of every call. The first call took 50 to 54 µs, the first ten had a median of 24.8 to 33.5 µs, and from about the 100th call it dropped to 1.6 to 1.9 µs and stayed there to the end, the same shape in all three runs. Turning tiers off one at a time showed which tier produces the speed: interpreter only, via --jitless, stayed at 24.4 to 24.8 µs throughout; Sparkplug without Maglev and TurboFan gave 13.7 to 14.3 µs; and only disabling TurboFan gave 13.4 to 14.2 µs. The 1.6 µs is TurboFan’s work. Timing a function after only a few calls therefore measures the interpreter and the compilation process rather than the code, and comparing two implementations this way can produce the absurd result that whichever got optimized first wins. Benchmark tools such as tinybench and mitata therefore run warmup iterations before measuring, and hand-rolled measurements also repeat until times settle before recording. Conversely, sometimes the cold state is the real performance: command-line tools that run once and exit, serverless functions that handle a few requests and disappear, and the first request after a deploy. Looking only at warm performance for such code misses what users go through, so cold and warm performance are measured separately and the one users actually experience is the yardstick. The cost of the first request returns in the next section.</sub> |
| **사라지는 벤치마크**<br><sub>Benchmarks that vanish</sub> | 결과를 쓰지 않는 반복은 한 번에 0.7ns로 재졌는데, 결과를 더해 내보내자 77~82ns였어요. 컴파일러가 쓰이지 않는 계산을 지운 거예요.<br><sub>A loop discarding its results measured 0.7 ns per call; summing and exporting the results gave 77–82 ns, because the compiler had deleted unused work.</sub> | 벤치마크를 처음 짜면 흔히 이런 모양이 돼요. for 문 안에서 함수를 부르기만 하고 결과는 버려요. 이렇게 재면 무엇이 재질까요. 제곱근과 사인을 곱하고 나머지를 더하는 함수를 1,000만 번 불러 한 번에 걸린 시간을 쟀어요. 세 가지로 불렀어요. 결과를 버리는 반복, 늘 42를 넣고 결과를 더하는 반복, 반복 변수 i를 넣고 결과를 더해 전역 변수로 내보내는 반복이에요. 결과를 버리는 반복은 한 번에 0.68~0.73ns였어요. 사인과 제곱근을 계산하는 시간이라기에는 너무 짧아요. CPU가 1ns 동안 할 수 있는 일은 명령 몇 개뿐이에요. 늘 42를 넣는 반복도 0.83~0.88ns였어요. 결과를 모아 밖으로 내보내자 76.7~82.1ns가 나왔어요. 이것이 진짜 비용이에요. 100배 차이예요. 이유는 최적화 컴파일러에 있어요. TurboFan은 결과가 쓰이지 않고 부수 효과도 없는 계산을 통째로 지워요. 이를 죽은 코드 제거라고 해요. 같은 입력으로 되풀이되는 계산은 한 번만 하도록 바꿀 수 있어요. 실제 프로그램에서는 고마운 최적화지만, 벤치마크에서는 재려던 일을 없애 버려요. 그러면 실제로는 아무 일도 하지 않는 반복문의 시간을 재고, 그 숫자로 두 구현을 비교하게 돼요. 이런 실수를 막는 방법은 단순해요. 첫째, 결과를 반드시 써요. 합산해 전역 변수나 반환값으로 내보내거나, 결과를 검사해요. 벤치마크 도구가 함수의 반환값을 받아 두는 이유도 이것이에요. 둘째, 입력을 실제처럼 바꿔 가며 넣어요. 늘 같은 값이면 컴파일러가 결과를 미리 계산하거나, 분기 예측과 캐시가 비현실적으로 잘 맞아요. 셋째, 결과가 의심스러울 만큼 빠르면 먼저 의심해요. 한 번에 1ns 아래라면 대개 무언가 지워진 거예요.<br><sub>A first benchmark often looks like this: a for loop that just calls a function and throws the result away. What does that actually measure? A function multiplying a square root by a sine and adding a remainder was called 10 million times and timed per call in three ways: a loop that discards the result, a loop that always passes 42 and sums the result, and a loop that passes the loop variable i, sums the results and exports the sum to a global variable. The discarding loop took 0.68 to 0.73 ns per call, far too short for computing a sine and a square root, since a CPU manages only a few instructions in a nanosecond. The loop always passing 42 took 0.83 to 0.88 ns. Collecting the results and exporting them gave 76.7 to 82.1 ns, the real cost, a hundredfold difference. The reason lies in the optimizing compiler: TurboFan deletes computations whose results go unused and that have no side effects, called dead code elimination, and can turn a computation repeated with the same input into a single one. In real programs these optimizations are welcome, but in a benchmark they erase the very work being measured, so the time of a loop that does nothing gets recorded and used to compare implementations. Preventing the mistake is simple. First, always use the result, summing it into a global variable or return value, or checking it, which is why benchmark tools hold on to what a function returns. Second, vary inputs as they would vary in reality, since a constant value lets the compiler precompute the result or makes branch prediction and caches unrealistically accurate. Third, distrust results that look suspiciously fast: under a nanosecond per call usually means something was deleted.</sub> |
| **시계의 간격과 비용**<br><sub>The step and cost of clocks</sub> | Date.now로 80ns짜리 호출을 재자 1만 번 가운데 9,999번이 0ms였어요. 나노초 시계도 한 번 읽는 데 53~70ns가 들었어요.<br><sub>Timing an 80 ns call with Date.now read 0 ms 9,999 times in 10,000; even nanosecond clocks cost 53–70 ns per read.</sub> | 시간을 재려면 시계를 읽어야 해요. 그런데 시계에는 눈금의 간격이 있고, 읽는 데도 시간이 들어요. Node에는 시계가 세 가지 있어요. Date.now는 밀리초 단위 정수를 돌려주고, performance.now는 소수점 아래까지 있는 밀리초를, process.hrtime.bigint는 나노초 정수를 돌려줘요. 각 시계에서 값이 바뀌는 가장 작은 간격과, 한 번 읽는 데 드는 시간을 쟀어요. Date.now의 가장 작은 간격은 1ms였어요. 약 80ns 걸리는 함수 호출 하나를 Date.now로 앞뒤에서 재자, 1만 번 가운데 9,999번이 0ms, 1번만 1ms가 나왔어요. 1만 번을 평균 내면 0.1µs라는 그럴듯한 숫자가 나오지만, 실제로는 호출이 밀리초 경계에 걸렸는지라는 우연이 만든 값이에요. performance.now와 hrtime은 간격이 49ns, 99ns로 촘촘했어요. 이 간격도 사실 시계의 해상도라기보다 두 번 읽는 데 걸린 시간에 가까워요. 한 번 읽는 비용을 따로 재자 performance.now 70.4ns, hrtime 66.9ns, Date.now 52.6ns였어요. 80ns짜리 일을 재려고 앞뒤로 시계를 읽으면 시계 비용이 잴 일만큼 커져요. 결과의 절반이 측정 도구 자체의 시간이 되는 거예요. 그래서 짧은 일은 하나씩 재지 않아요. 수백만 번 반복하는 묶음 하나의 시간을 재고, 그 시간을 횟수로 나눠요. 묶음 하나가 적어도 수 밀리초는 걸리게 하면 시계의 간격과 읽기 비용이 전체의 아주 작은 부분이 돼요. 이 페이지의 나노초 숫자도 모두 이렇게 잰 값이에요. 반대로 요청 하나의 지연처럼 밀리초 단위 일을 잴 때는 performance.now로 충분해요. 브라우저에서는 보안 때문에 performance.now의 정밀도를 일부러 낮추기도 해요. 그러니 측정 환경의 시계가 얼마나 촘촘한지 먼저 확인하고, 그보다 훨씬 큰 단위로 재요.<br><sub>Measuring time means reading a clock, and clocks have a step between ticks and a cost to read. Node has three: Date.now returns whole milliseconds, performance.now fractional milliseconds and process.hrtime.bigint integer nanoseconds. For each, the smallest step between changing values and the time to read it once were measured. Date.now’s smallest step was 1 ms. Timing a single roughly 80 ns function call with Date.now before and after read 0 ms 9,999 times out of 10,000 and 1 ms once; averaging those 10,000 yields a plausible 0.1 µs, but the number is really produced by the chance of a call straddling a millisecond boundary. performance.now and hrtime had fine steps of 49 ns and 99 ns, steps that reflect the time between two reads more than the clock’s resolution. Measured separately, one read cost 70.4 ns for performance.now, 66.9 ns for hrtime and 52.6 ns for Date.now. Reading a clock before and after an 80 ns job adds as much time as the job itself, so half of the result is the measuring tool. Short work is therefore never timed one call at a time: a batch repeated millions of times is timed and the total divided by the count, each batch lasting at least several milliseconds so the clock’s step and read cost become a tiny fraction of the whole. Every nanosecond figure on this page was measured this way. For millisecond-scale work, such as the latency of one request, performance.now is fine. Browsers sometimes deliberately coarsen performance.now for security reasons, so the first step is to check how fine the clock in the measuring environment is and then measure in units far larger than that.</sub> |
| **같은 코드의 흔들림**<br><sub>Noise in identical code</sub> | 같은 벤치마크를 30번 실행하자 28.4ns부터 51.6ns까지 1.82배 차이가 났어요. 같은 코드를 5번씩 두 묶음으로 나누자 중간값 4.1% 차이였어요.<br><sub>The same benchmark run 30 times ranged from 28.4 to 51.6 ns, 1.82×; two batches of 5 runs of identical code differed by 4.1% at the median.</sub> | 두 구현을 비교해 B가 5% 빠르다는 결과를 얻었다면 그 5%를 믿어도 될까요. 그 전에 알아야 할 것이 있어요. 아무것도 바꾸지 않은 같은 코드를 다시 재면 얼마나 달라지느냐예요. 사인과 제곱근 계산을 200만 번 하고 한 번에 걸린 시간을 내는 벤치마크를 새 프로세스로 30번 실행했어요. 코드도 입력도 기계도 같았어요. 가장 빠른 실행은 28.36ns, 중간값은 32.39ns, 가장 느린 실행은 51.56ns였어요. 최댓값이 최솟값의 1.82배예요. 표준편차는 4.18ns로 평균의 12.6%였어요. 같은 기계의 다른 프로세스, CPU 스케줄링과 주파수, JIT가 내리는 결정, GC가 일어나는 시점이 실행마다 달라질 수 있어요. 이 30개를 무작위로 섞어 5개씩 두 묶음을 만들고 각 묶음의 중앙값을 비교하기를 1,000번 했어요. 둘 다 같은 코드인데도 차이의 중간값이 4.1%, 상위 5%는 9.0%였고, 가장 크게는 28.2%였어요. 5% 빨라졌다는 결과는 이 잡음 안에 쉽게 들어가요. 바꾸지 않은 코드끼리 비교하는 것을 A/A 비교라고 해요. 개선을 주장하기 전에 A/A 비교로 잡음의 크기를 먼저 알면, 그보다 큰 차이만 의미 있다고 말할 수 있어요. 잡음을 다루는 실천도 몇 가지 있어요. 실행은 새 프로세스로 여러 번 해서 JIT의 우연한 결정이 한 번에 몰리지 않게 해요. 평균 하나 대신 중앙값과 범위, 가능하면 분포를 보여 줘요. 두 버전을 번갈아 실행해 그사이 기계 상태가 바뀐 영향을 양쪽에 나눠요. 같은 기계에서 다른 무거운 작업이 돌지 않게 해요. 클라우드의 공유 기계는 특히 잡음이 커서, CI에서 성능을 비교할 때는 같은 실행 안에서 두 버전을 함께 재는 방법을 써요. 그래도 남는 잡음을 얼마나 많이 재서 이겨 낼지는 다음 항목에서 다뤄요.<br><sub>If comparing two implementations shows B is 5% faster, can that 5% be trusted? First comes another question: how much does identical, unchanged code vary when measured again? A benchmark computing sines and square roots two million times and reporting the time per call was run 30 times in fresh processes, with the same code, inputs and machine. The fastest run took 28.36 ns, the median 32.39 ns and the slowest 51.56 ns, the maximum 1.82 times the minimum, with a standard deviation of 4.18 ns, 12.6% of the mean. Other processes on the machine, CPU scheduling and frequency, the JIT’s decisions and the timing of GC can all differ from run to run. Shuffling these 30 at random into two batches of five and comparing their medians 1,000 times, the identical code differed by 4.1% at the median, 9.0% at the 95th percentile and as much as 28.2%. A result showing a 5% speedup easily fits inside this noise. Comparing unchanged code with itself is called an A/A comparison; knowing the size of the noise from one before claiming an improvement makes it possible to say that only larger differences mean anything. A few practices help with noise: runs are repeated in fresh processes so a chance JIT decision does not dominate; medians with ranges, and ideally distributions, are reported instead of a single average; the two versions are run alternately so changes in machine state during the session are shared by both; and no other heavy work runs on the same machine. Shared cloud machines are especially noisy, so performance comparisons in CI measure both versions within the same job. How many measurements it takes to overcome the noise that remains is the next item.</sub> |
| **몇 번 재야 할까**<br><sub>How many runs to take</sub> | 잰 잡음으로 모의 실험하자, 정말 5% 빠른 코드도 한 번씩 재면 30%는 더 느리게 나왔어요. 유의하게 잡으려면 20~30번씩 재야 했어요.<br><sub>Simulating with measured noise, code truly 5% faster looked slower 30% of the time with one run each; significance took 20–30 runs each.</sub> | 잡음이 있다는 것을 알았다면 다음 질문은 몇 번 재야 하느냐예요. 앞 항목에서 잰 30번의 실행 시간을 그대로 써서 모의 실험을 했어요. 실제로 잰 잡음의 모양을 그대로 쓰기 위해서예요. A는 그 30개에서 n개를 뽑고, B는 뽑은 값에 0.95를 곱해 정말로 5% 빠르게 만들었어요. 이 비교를 2,000번 되풀이하며 B를 찾아내는 비율을 셌어요. 한 번씩만 재면 B가 더 빠르게 나온 비율은 70.2%였어요. 열에 셋은 더 빠른 코드가 더 느리다는 결론이 나온 거예요. 5번씩이면 85.0%, 10번씩이면 92.1%, 20번씩이면 97.7%, 30번씩이면 98.9%였어요. 하지만 중앙값이 더 작게 나왔다는 것만으로는 우연이 아니라고 말할 수 없어요. 그래서 맨-휘트니 U 검정으로 B가 A보다 빠르다는 가설을 검정해 p가 0.05보다 작게 나온 비율도 셌어요. 이를 검정력이라고 해요. 5번씩이면 24.8%, 10번씩이면 41.5%, 20번씩이면 70.0%, 30번씩이면 85.5%였어요. 이 잡음 속에서 5% 차이를 믿을 만하게 잡으려면 20~30번씩은 재야 했어요. 필요한 횟수는 두 가지가 정해요. 찾으려는 차이의 크기와 잡음의 크기예요. 차이가 50%라면 몇 번만으로도 분명하지만, 5% 차이를 12.6% 잡음 속에서 찾으려면 수십 번이 필요해요. 대략 차이가 절반으로 줄면 필요한 횟수는 네 배로 늘어요. 그래서 실무에서는 두 가지를 함께 해요. 하나는 잡음을 줄이는 거예요. 조용한 전용 기계를 쓰고, CPU 주파수를 고정하고, 다른 작업을 멈추고, 측정 단위를 충분히 길게 잡아요. 다른 하나는 충분히 재는 거예요. hyperfine 같은 도구는 실행을 여러 번 하고 평균과 표준편차, 최솟값과 최댓값을 함께 보여 줘요. 그리고 차이가 잡음보다 작다면, 그 최적화는 측정할 수 없을 만큼 작다는 뜻이기도 해요. 그런 최적화에 복잡도를 더할 가치가 있는지는 다시 생각해 봐요.<br><sub>Once noise is known, the next question is how many measurements to take. A simulation reused the 30 run times measured in the previous item, to keep the real shape of the noise: A drew n of those 30, and B multiplied its draws by 0.95, making it truly 5% faster. Repeating the comparison 2,000 times counted how often B was found. With one run each, B came out faster 70.2% of the time, so three times in ten the faster code was judged slower. With five runs each it was 85.0%, ten 92.1%, twenty 97.7% and thirty 98.9%. A smaller median alone, however, cannot rule out chance, so the share of Mann-Whitney U tests of the hypothesis that B is faster than A coming out with p below 0.05 was counted as well, a quantity called statistical power: 24.8% with five runs each, 41.5% with ten, 70.0% with twenty and 85.5% with thirty. Reliably catching a 5% difference in this noise took 20 to 30 runs each. Two things set the number needed: the size of the difference sought and the size of the noise. A 50% difference is obvious in a few runs, but finding 5% in 12.6% noise takes dozens, and roughly, halving the difference quadruples the runs needed. In practice two things are done together. One is reducing noise: a quiet dedicated machine, a fixed CPU frequency, other work stopped and measurement units long enough. The other is measuring enough: tools such as hyperfine run a command many times and report the mean and standard deviation along with the minimum and maximum. And when a difference is smaller than the noise, the optimization is too small to measure, which is a reason to reconsider whether it is worth the complexity it adds.</sub> |
| **GC가 만드는 튀는 값**<br><sub>Spikes caused by GC</sub> | 객체를 만드는 반복을 3,000번 재자 중간값은 52µs인데 1%는 900µs 안팎이었어요. 가장 느린 24번 가운데 19~21번이 GC와 겹쳤어요.<br><sub>Timing 3,000 allocating iterations, the median was 52 µs but 1% took about 900 µs; 19–21 of the slowest 24 overlapped a GC.</sub> | 객체를 많이 만드는 코드를 재면 측정값이 고르게 나오지 않아요. 대부분은 비슷한데 가끔 크게 튀는 값이 섞여요. 원인을 확인했어요. 반복마다 객체 2,000개를 만들고 50번에 한 번은 결과를 붙잡아 두는 코드를 3,000번 돌리며 반복마다 시간을 쟀어요. perf\_hooks의 PerformanceObserver로 가비지 컬렉션이 언제 얼마나 일어났는지도 함께 기록했어요. 처음 500번은 워밍업으로 뺐어요. 반복의 중간값은 52~53µs, p90은 109~113µs였어요. 그런데 p99는 858~944µs, 가장 느린 반복은 2.7~7.0ms였어요. 같은 일을 하는 반복인데 1%가 17배 넘게 느렸어요. 같은 시간 동안 GC는 82~83번 일어났고 대부분은 젊은 세대를 정리하는 Scavenge였어요. 가장 느린 1%, 24번의 반복 가운데 19~21번이 GC와 시간이 겹쳤어요. 느린 반복의 원인은 그 반복의 코드가 아니라, 그 순간 일어난 메모리 정리였어요. GC는 할당한 만큼 언젠가 일어나요. 그리고 그 비용은 할당한 반복이 아니라 GC가 시작된 순간의 반복이 치러요. 그래서 짧게 재면 GC가 들어간 실행과 안 들어간 실행이 크게 갈려 결과가 흔들리고, 평균은 이 튀는 값에 끌려가요. 할당을 많이 하는 구현이 짧은 측정에서는 빠르게 나오는 일도 생겨요. GC 비용을 아직 치르지 않았기 때문이에요. 정직하게 재려면 GC가 여러 번 포함될 만큼 길게 재요. 그래야 할당의 비용이 결과에 고르게 들어가요. 결과는 평균 하나 대신 분포와 백분위수로 보고, 측정하는 동안 GC 횟수와 시간도 함께 기록해 원인을 가려요. node --trace-gc로 GC 기록을 출력하는 방법도 있어요. 측정을 시작하기 전에 global.gc()로 힙을 정리해 두면 실행마다 출발점이 같아지지만, 실제 서비스는 그렇게 깨끗한 상태로 돌지 않는다는 점도 기억해요. 서비스의 지연 시간에 나타나는 꼬리도 상당 부분 이런 GC에서 나와요.<br><sub>Measuring code that creates many objects does not produce even numbers: most are similar, with occasional large spikes mixed in. To find the cause, code creating 2,000 objects per iteration and holding on to the result every 50th time was run 3,000 times with each iteration timed, while a perf\_hooks PerformanceObserver recorded when and for how long garbage collection ran, the first 500 iterations dropped as warmup. The median iteration took 52 to 53 µs and p90 109 to 113 µs, but p99 was 858 to 944 µs and the slowest iteration 2.7 to 7.0 ms: 1% of identical iterations ran more than 17 times slower. Over the same period there were 82 to 83 GCs, mostly Scavenges of the young generation, and 19 to 21 of the slowest 1%, 24 iterations, overlapped a GC in time. The cause of the slow iterations was not their code but the memory cleanup happening at that moment. GC eventually comes in proportion to allocation, and its cost is paid not by the iterations that allocated but by whichever iteration is running when it starts. Short measurements therefore split sharply between runs that include a GC and runs that do not, results wobble, and averages get dragged by the spikes; an implementation that allocates heavily can even look fast in a short measurement because it has not yet paid for its GC. Honest measurement runs long enough to include several GCs, so the cost of allocation enters the result evenly. Results are read as distributions and percentiles rather than one average, and GC counts and times are recorded during measurement to separate causes, node --trace-gc being another way to print a GC log. Calling global.gc() before measuring makes every run start from the same clean heap, though real services never run in such a clean state. Much of the tail in a service’s latency comes from GC like this as well.</sub> |

| **평균이 숨기는 꼬리**<br><sub>The tail an average hides</sub> | 요청 100개 중 1개만 느린 서버를 재자 평균은 0.99ms, 중앙값은 0.41ms, p99는 50.3ms였어요. 평균만큼 걸린 요청은 거의 없었어요.<br><sub>Measuring a server where 1 request in 100 is slow, the mean was 0.99 ms, the median 0.41 ms and p99 50.3 ms; almost no request took as long as the mean.</sub> | 서버가 얼마나 빠른지 물으면 흔히 평균 응답 시간으로 답해요. 그런데 평균은 지연 시간을 설명하기에 나쁜 숫자예요. 이를 확인하려고 요청 100개 중 1개에서만 50ms 동안 CPU를 쓰고 나머지는 0.2ms만 쓰는 서버를 만들었어요. 캐시를 놓친 요청이나 큰 결과를 만드는 요청을 흉내 낸 거예요. 클라이언트가 요청을 하나씩 15초 동안 보내 14,799개의 지연 시간을 모았어요. 평균은 0.99ms였어요. 중앙값인 p50은 0.41ms, p90은 0.66ms였어요. 평균이 중앙값의 2.4배인데, 실제로 1ms 가까이 걸린 요청은 거의 없어요. 평균은 아무도 겪지 않은 시간을 말하고 있어요. p99는 50.31ms, p99.9는 51.26ms, 가장 느린 요청은 56.0ms였어요. 요청은 빠른 무리와 50ms가 넘는 무리로 갈려 있었고, 평균 하나로는 두 무리가 보이지 않아요. 평균이 0.99ms라는 말을 들은 사람은 서버가 고르게 1ms쯤 걸린다고 생각하지만, 실제로는 절반이 0.41ms 안에, 90%가 0.66ms 안에 끝나고 100번에 한 번은 50ms가 넘어요. 꼬리는 생각보다 자주 사용자에게 닿아요. 웹 페이지 하나가 API 요청 수십 개를 부르면, 그 가운데 하나라도 느린 무리에 걸릴 확률이 커져요. 사용자 대부분이 느린 쪽을 한 번은 만나는 거예요. 그래서 지연 시간은 p50, p90, p99, 최댓값 같은 백분위수로 보고, 목표도 p99를 몇 ms 아래로처럼 정해요. p50은 보통의 경험을, p99는 운이 나쁜 경험을, 최댓값은 최악을 보여 줘요. 백분위수를 고를 때는 사용자 한 명이 겪는 요청 수를 생각해요. 요청을 많이 하는 화면일수록 더 깊은 꼬리가 중요해요. 평균에도 쓸모는 있어요. 전체 처리 시간과 처리량을 계산할 때예요. 하지만 사용자가 겪는 시간을 말할 때는 쓰지 않아요. 분포를 한눈에 보려면 히스토그램이나 백분위수 그래프를 그려요. 이 그림은 다음 항목들에서 보듯 측정 방법에 따라서도 크게 달라져요.<br><sub>Asked how fast a server is, people often answer with the mean response time, but the mean is a poor number for describing latency. To show this, a server was built that burns 50 ms of CPU on only 1 request in 100 and 0.2 ms on the rest, imitating requests that miss a cache or build a large result. A client sending one request at a time for 15 seconds collected 14,799 latencies. The mean was 0.99 ms, against a median p50 of 0.41 ms and a p90 of 0.66 ms. The mean is 2.4 times the median, yet almost no request actually took close to 1 ms: the mean describes a time nobody experienced. p99 was 50.31 ms, p99.9 51.26 ms and the slowest request 56.0 ms. The requests split into a fast group and a group over 50 ms, and a single average shows neither. Someone told the mean is 0.99 ms pictures a server taking about 1 ms evenly, when really half finish within 0.41 ms, 90% within 0.66 ms, and one in a hundred takes over 50 ms. Tails reach users more often than expected: when one web page triggers dozens of API requests, the chance that at least one lands in the slow group grows, so most users meet the slow side at least once. Latency is therefore reported as percentiles such as p50, p90, p99 and the maximum, and targets are set as p99 below some number of milliseconds. p50 shows the typical experience, p99 an unlucky one and the maximum the worst. Choosing a percentile means thinking about how many requests one user makes, deeper tails mattering more for screens that make many requests. The mean has its uses, for computing total processing time and throughput, but not for describing what users experience. A histogram or a percentile plot shows the distribution at a glance, and as the following items show, that picture also depends heavily on how it was measured.</sub> |
| **조정된 누락**<br><sub>Coordinated omission</sub> | 10초마다 1초씩 멈추는 서버를 응답을 기다리는 생성기로 재자 p99 5.16ms, 정해진 시각에 보내는 생성기로 재자 989ms였어요.<br><sub>A server freezing 1 s every 10 s showed p99 5.16 ms to a generator that waits for replies and 989 ms to one sending on a fixed schedule.</sub> | 부하 테스트 도구가 보고하는 지연 시간도 틀릴 수 있어요. 가장 흔한 함정을 재현했어요. 서버가 10초마다 1초씩 이벤트 루프를 막도록 만들었어요. 긴 GC나 무거운 동기 작업으로 서버가 잠깐 멈추는 상황이에요. 같은 서버를 두 가지 부하 생성기로 30초씩 쟀어요. 닫힌 루프 생성기는 클라이언트 10개가 각자 응답을 받으면 다음 요청을 보내요. 많은 벤치마크 도구가 기본으로 이렇게 동작해요. 열린 루프 생성기는 응답과 상관없이 초당 500개를 정해진 시각에 보내고, 지연을 요청을 보내려던 시각부터 재요. 닫힌 루프는 요청 113,524개를 보냈고 p50 2.10ms, p99 5.16ms, p99.9 11.5ms였어요. 서버가 세 번이나 1초씩 멈췄는데 꼬리가 거의 보이지 않았어요. 가장 느린 요청 몇 개만 1,005.6ms였어요. 열린 루프는 요청 15,000개를 보냈고 p50 1.36ms, p90 68.9ms, p99 989ms, p99.9 1,022ms였어요. 같은 서버, 같은 30초인데 p99가 190배 넘게 달라요. 차이는 서버가 멈춘 1초 동안 일어난 일에 있어요. 닫힌 루프의 클라이언트 10개는 그 1초 동안 응답을 기다리느라 새 요청을 보내지 않았어요. 그래서 느린 기록은 10개만 남았고, 10만 개가 넘는 빠른 기록 속에 묻혔어요. 열린 루프는 그 1초 동안 보내야 했던 500개를 예정대로 보냈고, 그 500개가 모두 길게 기다린 기록으로 남았어요. 실제 사용자는 서버가 멈췄다고 요청을 미루지 않아요. 그러니 열린 루프 쪽이 사용자가 겪는 시간에 가까워요. 측정 도구가 느려진 시스템에 맞춰 스스로 속도를 늦춰 가장 나쁜 순간의 표본을 놓치는 현상을 조정된 누락이라고 해요. 지연을 정직하게 재려면 정해진 속도로 보내는 열린 루프 생성기를 쓰고, 지연은 실제로 보낸 시각이 아니라 보내려던 시각부터 재요. wrk2, k6의 고정 도착률 실행기, Gatling 같은 도구가 이 방식을 지원해요. 닫힌 루프 결과를 볼 때는 처리량과 함께 가장 느린 값이 얼마나 오래였는지를 꼭 확인해요.<br><sub>Even the latency a load testing tool reports can be wrong, and the most common trap was reproduced here. A server was made to block its event loop for 1 second every 10 seconds, a server briefly freezing from a long GC or heavy synchronous work, and was measured for 30 seconds each with two load generators. The closed-loop generator has 10 clients each send the next request after receiving a reply, the default behavior of many benchmark tools. The open-loop generator sends 500 requests per second on a fixed schedule regardless of replies and times each from its intended send time. The closed loop sent 113,524 requests with p50 at 2.10 ms, p99 at 5.16 ms and p99.9 at 11.5 ms: the server froze for a second three times, yet the tail barely showed, with only the few slowest requests at 1,005.6 ms. The open loop sent 15,000 requests with p50 at 1.36 ms, p90 at 68.9 ms, p99 at 989 ms and p99.9 at 1,022 ms. Same server, same 30 seconds, and p99 differs by more than 190 times. The difference lies in what happened during each frozen second. The 10 closed-loop clients were waiting for replies and sent nothing new, so only 10 slow samples were recorded, buried among more than 100,000 fast ones. The open loop sent the 500 requests due in that second on schedule, and all 500 were recorded as long waits. Real users do not hold back requests because a server froze, so the open loop is closer to what users experience. A measuring tool slowing itself to match a stalled system and missing the samples from the worst moments is called coordinated omission. Honest latency measurement uses open-loop generators sending at a fixed rate and times latency from the intended send time rather than the actual one, an approach supported by tools such as wrk2, k6’s constant arrival rate executor and Gatling. When reading closed-loop results, check how long the slowest values were alongside throughput.</sub> |
| **백분위수를 평균 내는 실수**<br><sub>Averaging percentiles</sub> | 서버 4대 중 1대만 느릴 때 서버별 p99를 평균 내면 2.69ms였지만, 전체 요청을 합친 진짜 p99는 4.96ms였어요.<br><sub>With one slow server in four, averaging per-server p99s gave 2.69 ms, while the true p99 of all requests combined was 4.96 ms.</sub> | 서버가 여러 대이면 대시보드는 흔히 서버별 p99를 구한 뒤 그 평균을 보여 줘요. 계산이 쉽고 그럴듯해 보이지만 틀린 숫자예요. 서버 4대 가운데 3대는 요청마다 0.2ms, 1대는 3ms 동안 CPU를 쓰게 만들었어요. 설정이 잘못됐거나 같은 기계의 다른 프로세스에 시달리는 서버를 흉내 낸 거예요. 서버마다 요청을 하나씩 8초 동안 보내 지연 시간을 모았어요. 서버별 p99는 1.50ms, 1.08ms, 1.72ms, 6.48ms였어요. 이 넷을 평균 내면 2.69ms예요. 그런데 부하 분산기가 요청을 똑같이 나눈다고 보고 네 서버의 요청을 같은 수만큼 합쳐 p99를 구하자 4.96ms였어요. 평균 낸 값이 진짜 값의 절반을 조금 넘었어요. 이유는 분명해요. 느린 서버가 요청의 4분의 1을 받으니, 합친 데이터에서는 p75부터 이미 3.37ms, p90은 3.65ms였어요. 사용자 넷 중 하나가 느린 서버를 만나요. 서버별 p99의 평균은 이 사실을 가려요. 백분위수는 값을 줄 세운 순서에서 나온 값이라, 더하거나 평균 낼 수 없어요. p99의 평균은 어떤 요청 집합의 p99도 아니에요. 같은 실수는 시간에도 일어나요. 1분마다 구한 p99를 한 시간 동안 평균 내도 그 시간의 p99가 되지 않아요. 여러 서버나 시간 구간을 합치려면 원래 값을 모으거나, 합칠 수 있는 형태로 기록해야 해요. 지연 시간을 구간별 개수로 세는 히스토그램은 서버끼리, 시간 구간끼리 칸마다 더하기만 하면 합쳐지고, 합친 히스토그램에서 백분위수를 다시 구할 수 있어요. Of four servers, three were made to burn 0.2 ms of CPU per request and one 3 ms, imitating a misconfigured server or one troubled by another process on the same machine. Latencies were collected by sending one request at a time to each server for 8 seconds. The per-server p99s were 1.50, 1.08, 1.72 and 6.48 ms, averaging to 2.69 ms. Merging equal numbers of requests from the four servers, as a load balancer splitting evenly would, gave a p99 of 4.96 ms, so the averaged figure was only a little over half the true one. The reason is clear: with the slow server receiving a quarter of requests, the merged data was already at 3.37 ms by p75 and 3.65 ms at p90, one user in four meeting the slow server, a fact the average of per-server p99s hides. Percentiles come from the order of sorted values, so they cannot be added or averaged; an average of p99s is not the p99 of any set of requests. The same mistake happens over time: averaging per-minute p99s over an hour does not give the hour’s p99. Combining servers or time windows requires pooling raw values or recording them in a mergeable form. A histogram counting latencies per bucket merges across servers and time windows by simply adding bucket counts, and percentiles can be computed again from the merged histogram; Prometheus histograms, HdrHistogram and t-digest serve this purpose. Dashboards show merged percentiles rather than per-server ones, with per-server lines drawn separately to find slow servers.</sub> |
| **서버가 모르는 대기 시간**<br><sub>Waiting the server never sees</sub> | 요청마다 2ms를 쓰는 서버가 잰 p99는 부하와 상관없이 4ms 아래였지만, 한계를 조금 넘자 클라이언트가 본 p99는 3.3초, 8.6초였어요.<br><sub>A server spending 2 ms per request reported p99 under 4 ms at every load, but just past capacity the client saw p99 at 3.3 s and 8.6 s.</sub> | 서버의 응답 시간은 흔히 핸들러 안에서 재요. 요청 처리를 시작할 때 시계를 읽고, 응답을 보낼 때 다시 읽어 그 차이를 로그와 지표로 남겨요. 이 방법이 무엇을 놓치는지 쟀어요. 요청마다 CPU 2ms를 쓰는 서버에 열린 루프 생성기로 초당 200, 400, 450, 480, 520개를 10초씩 보냈어요. 서버는 핸들러 안에서 시간을 재고, 클라이언트는 요청을 보내려던 시각부터 응답을 받을 때까지를 재요. 같은 요청을 두 곳에서 잰 거예요. 서버가 잰 시간은 부하와 상관없이 p50 2.04~2.10ms, p99 3.0~4.1ms였어요. 서버의 로그와 대시보드만 보면 모든 부하에서 건강해 보여요. 클라이언트가 본 시간은 달랐어요. 초당 200개에서 p50 3.40ms, p99 10.7ms였고, 450개에서 p99 25.4ms였어요. 처리 한계를 조금 넘는 480개에서는 p50 133ms, p99 3,317ms, 520개에서는 p50 190ms, p99 8,562ms로 치솟았어요. 초당 처리할 수 있는 양보다 조금이라도 많이 들어오면 남는 요청이 대기열에 쌓이고, 대기열은 계속 길어져요. 늘어난 시간은 모두 요청이 소켓과 이벤트 루프의 대기열에서 차례를 기다린 시간이에요. 핸들러는 차례가 온 뒤에야 시계를 읽으니, 이 기다림은 서버의 측정에 하나도 들어가지 않아요. 그래서 서버 지표만 보면 과부하가 시작된 순간을 알아채지 못해요. 사용자는 몇 초씩 기다리는데 서버는 2ms라고 보고해요. 지연 시간은 사용자에 가까운 곳에서 재야 해요. 클라이언트, 부하 분산기, 리버스 프록시가 보는 시간이 사용자가 겪는 시간에 가까워요. 서버 쪽에서는 핸들러 시간과 함께 대기열의 상태를 봐요. Node라면 perf\_hooks의 monitorEventLoopDelay로 이벤트 루프 지연을 재고, 처리 중인 요청 수와 대기 중인 요청 수를 지표로 남겨요. 그리고 대기열이 끝없이 쌓이지 않도록 한도를 두고, 넘치면 빨리 거절하는 편이 사용자에게 나아요.<br><sub>Server response time is usually measured inside the handler: read a clock when processing starts, again when the response is sent, and record the difference in logs and metrics. What this misses was measured. An open-loop generator sent 200, 400, 450, 480 and 520 requests per second for 10 seconds each to a server burning 2 ms of CPU per request, the server timing inside its handler and the client from each request’s intended send time until the response arrived, the same requests measured in two places. The server’s timing stayed at p50 2.04 to 2.10 ms and p99 3.0 to 4.1 ms at every load, so its logs and dashboards looked healthy throughout. The client saw something else: at 200 per second p50 was 3.40 ms and p99 10.7 ms, at 450 p99 was 25.4 ms, and just past capacity, at 480, it shot to p50 133 ms and p99 3,317 ms, and at 520 to p50 190 ms and p99 8,562 ms. When even slightly more arrives than can be processed per second, the excess piles up in a queue that keeps growing, and all the added time is spent by requests waiting their turn in socket and event loop queues. The handler reads its clock only after its turn comes, so none of that waiting enters the server’s measurement, and server metrics alone miss the moment overload begins: users wait seconds while the server reports 2 ms. Latency must be measured close to users, and what clients, load balancers and reverse proxies see is closer to what users experience. On the server side, queue state is watched alongside handler time: in Node, perf\_hooks’ monitorEventLoopDelay measures event loop delay, and the number of requests in progress and waiting are recorded as metrics. A limit that keeps the queue from growing without bound, rejecting quickly when it overflows, also serves users better.</sub> |
| **첫 요청의 비용**<br><sub>The cost of the first request</sub> | 서버를 켜자마자 받은 첫 요청은 30~81ms로 안정된 뒤의 0.7ms보다 40배 넘게 느렸어요. 국제화 데이터와 모듈을 미리 불러 두자 15~21ms로 줄었어요.<br><sub>The first request right after startup took 30–81 ms, over 40× the settled 0.7 ms; preloading Intl data and modules cut it to 15–21 ms.</sub> | 벤치마크는 대개 서버를 충분히 데운 뒤에 재요. 하지만 서버가 막 켜진 순간에도 요청은 들어와요. 배포 직후, 자동 확장으로 새 인스턴스가 뜬 직후, 서버리스 함수가 처음 깨어난 순간이에요. 이때의 비용을 쟀어요. 상품 200개를 걸러 가격을 ko-KR 형식으로 붙이고, JSON으로 만들어 gzip으로 압축해 돌려주는 서버를 만들었어요. zlib 모듈은 첫 요청 때 불러오게 했어요. 서버를 켜자마자 요청 2,000개를 하나씩 보내 각 요청의 지연을 쟀고, 세 번 되풀이했어요. 첫 요청은 30~81ms였어요. 2~10번째 요청의 중간값은 1.45~1.76ms, 10~100번째는 0.88~1.02ms, 1,000번째 이후는 0.66~0.78ms였어요. 첫 요청이 안정된 뒤보다 40배 넘게 느렸고, 그 뒤로도 수백 번에 걸쳐 조금씩 빨라졌어요. 첫 요청에 몰린 일을 하나씩 쟀어요. ko-KR 형식으로 숫자를 처음 바꾸는 데 12.24ms가 들었고, 두 번째는 0.067ms였어요. 국제화 데이터를 처음 불러와 준비하는 비용이에요. zlib을 불러오는 데는 2.03ms가 들었어요. 이 둘을 서버가 시작할 때 미리 해 두자 첫 요청은 15~21ms로 줄었어요. 남은 시간은 JIT 컴파일, HTTP 파서와 URL 파서의 첫 사용, 첫 TCP 연결 같은 준비 비용이에요. 이 비용은 인스턴스가 새로 뜰 때마다 누군가 치러요. 그 누군가는 대개 사용자예요. 인스턴스가 많고 자주 교체될수록 첫 요청을 겪는 사용자도 늘어요. 대책은 몇 가지예요. 무거운 모듈과 데이터는 요청 때가 아니라 시작할 때 불러요. 국제화 형식기 같은 비싼 객체도 시작할 때 만들어 다시 써요. 트래픽을 받기 전에 대표적인 요청 몇 개를 스스로 보내 코드를 데우고, 그 뒤에 준비 완료 상태를 알려 부하 분산기가 요청을 보내게 해요. 쿠버네티스라면 준비 상태 검사가 이 역할을 해요. The first request took 30 to 81 ms, requests 2 to 10 had a median of 1.45 to 1.76 ms, requests 10 to 100 0.88 to 1.02 ms and requests after the 1,000th 0.66 to 0.78 ms: the first request was over 40 times slower than the settled time, and the server kept speeding up gradually over hundreds of requests after that. Heavy modules and data are loaded at startup rather than on request, and expensive objects such as internationalization formatters are created at startup and reused. Node’s own startup time can also be reduced with the compile cache or snapshots.</sub> |

| **프로파일러의 부하**<br><sub>Profiler overhead</sub> | --cpu-prof를 기본 간격 1ms로 켜자 프로그램이 5% 느려졌고, 간격을 10µs로 좁히자 32% 느려졌어요.<br><sub>Turning on --cpu-prof at its default 1 ms interval slowed the program by 5%; narrowing the interval to 10 µs slowed it by 32%.</sub> | 프로파일러는 프로그램이 어디서 시간을 쓰는지 알려 주는 도구지만, 그 자체도 프로그램 안에서 돌아요. 얼마나 방해하는지 쟀어요. V8의 CPU 프로파일러는 정해진 간격마다 실행 중인 호출 스택을 하나씩 기록하는 표본 방식이에요. 주문 2만 개를 만들고, 가격을 매기고, 정렬하고, JSON으로 만드는 일을 40번 하는 프로그램을 프로파일러 없이, 그리고 간격 1ms, 100µs, 10µs로 각각 7번씩 실행했어요. 프로파일러 없이는 중앙값 689ms였어요. --cpu-prof를 기본 간격인 1ms로 켜자 723ms로 5% 느려졌고, 프로파일 파일은 실행 하나에 약 19KB였어요. 간격을 100µs로 좁히자 799ms로 16%, 10µs로 좁히자 906ms로 32% 느려졌어요. 파일도 약 58KB, 97KB로 커졌어요. 표본을 촘촘히 모을수록 짧은 함수까지 잡을 수 있지만, 그만큼 프로그램을 자주 멈춰 세우고 기록하느라 실행 자체가 달라져요. 32% 느려진 프로그램에서는 함수들의 상대적인 비중도 원래와 조금 달라질 수 있어요. 표본 방식의 장점은 함수 호출을 하나하나 기록하지 않는다는 거예요. 그래서 기본 간격에서는 부하가 작아, 운영 서버에서 문제가 생긴 동안 잠깐 켜 보는 것도 가능해요. Node에서는 --cpu-prof 외에도 inspector 모듈이나 --inspect로 실행 중인 프로세스에 붙어 프로파일을 받을 수 있어요. 리눅스의 perf처럼 운영체제 수준에서 표본을 모으는 도구도 비슷한 원리로 가벼워요. 다만 간격을 좁힐 때는 그 부하가 결과를 얼마나 바꾸는지 함께 봐야 해요. 반대로 간격이 넓으면 표본이 적어서 작은 함수의 비율이 흔들려요. 이 표본 오차는 다음 항목에서 재요. 적당한 간격은 실행 시간과 찾는 함수의 크기로 정해요. 몇 초짜리 실행이라면 기본 간격으로 표본 수천 개를 모을 수 있고, 그 정도면 비중이 큰 함수를 찾기에 충분해요.<br><sub>A profiler shows where a program spends its time, but it runs inside that program too, so how much it disturbs things was measured. V8’s CPU profiler is a sampling profiler that records the running call stack once per fixed interval. A program that 40 times builds 20,000 orders, prices them, sorts them and serializes them to JSON was run seven times each without a profiler and with intervals of 1 ms, 100 µs and 10 µs. Without a profiler the median was 689 ms. Turning on --cpu-prof at its default interval of 1 ms gave 723 ms, 5% slower, with a profile file of about 19 KB per run. Narrowing the interval to 100 µs gave 799 ms, 16% slower, and to 10 µs 906 ms, 32% slower, with files growing to about 58 KB and 97 KB. Denser sampling catches even short functions, but stopping the program more often to record changes the run itself, and in a program slowed by 32% the relative weight of functions can shift somewhat too. The strength of sampling is that it does not record every function call, so at the default interval the overhead is small enough to switch a profiler on briefly on a production server during an incident. Besides --cpu-prof, Node can attach to a running process through the inspector module or --inspect to capture a profile, and operating-system-level samplers such as Linux perf are light for the same reason. Narrowing the interval, though, means watching how much the overhead changes the result, while a wide interval yields few samples so the shares of small functions wobble, a sampling error measured in the next item. A suitable interval follows from the run length and the size of the functions sought: a run of a few seconds gathers thousands of samples at the default interval, enough to find the functions that carry real weight.</sub> |
| **프로파일의 표본 오차**<br><sub>Sampling error in profiles</sub> | 같은 프로그램을 5번 프로파일링하자 전체의 1% 안팎인 함수가 실행마다 0.4~1.2%로 세 배씩 흔들렸어요. 표본이 5개 남짓이기 때문이에요.<br><sub>Profiling the same program five times, a function around 1% of the total swung threefold between runs, from 0.4 to 1.2%, because it got only about 5 samples.</sub> | 프로파일은 측정이 아니라 표본이에요. 정해진 간격마다 그 순간 실행 중인 함수를 하나씩 기록해 비율을 내니, 표본이 적으면 우연이 끼어들어요. 같은 프로그램을 1ms 간격으로 5번 프로파일링하고, 함수마다 self 시간, 곧 그 함수 자신이 CPU 위에 있던 표본의 비율을 셌어요. 실행마다 표본은 459~514개였고 프로그램도 입력도 같았어요. 정렬 비교 함수 byPrice는 8.8~13.0%, GC는 21.6~25.1%로 실행마다 몇 %씩 달랐어요. 전체의 1% 안팎인 smallHelper는 0.4~1.2%로 세 배씩 흔들렸어요. 표본 500개의 1%는 5개라서, 표본 한두 개가 비율을 크게 바꿔요. 간격을 100µs로 좁혀 표본을 2,817~3,382개로 6배쯤 모으자 smallHelper는 0.8~1.2%로 좁아졌어요. 하지만 앞 항목에서 봤듯 그 대가로 프로그램이 16% 느려져요. 가격을 계산하는 아주 짧은 함수 priceOf는 두 간격 모두 0.0~0.4%였어요. 짧게 끝나는 함수는 표본에 잘 잡히지 않아요. 그래서 프로파일에서 0%로 보인다고 그 함수가 공짜라는 뜻은 아니에요. 이 결과를 읽는 법은 이래요. 비율이 큰 함수, 예를 들어 10%가 넘는 함수는 표본이 충분해서 믿을 만해요. 프로파일은 그런 큰 덩어리를 찾는 데 가장 좋아요. 반대로 몇 % 아래의 함수끼리 비교하거나, 고친 뒤 1% 줄었다고 판단하는 것은 표본 오차 안에 있을 수 있어요. 작은 차이를 확인하려면 여러 번 프로파일링해 범위로 보거나, 더 오래 실행해 표본을 늘리거나, 그 부분만 떼어 따로 벤치마크해요. 고친 효과는 결국 프로파일의 비율이 아니라 전체 실행 시간이나 지연 시간으로 확인해요.<br><sub>A profile is a sample, not a measurement: it records the function running at each fixed interval and turns those records into shares, so with few samples chance creeps in. The same program was profiled five times at a 1 ms interval, counting each function’s self time, the share of samples in which the function itself was on the CPU, with 459 to 514 samples per run and the same program and input each time. The sort comparator byPrice varied from 8.8 to 13.0% and GC from 21.6 to 25.1% between runs, while smallHelper, around 1% of the total, swung threefold, from 0.4 to 1.2%: 1% of 500 samples is five, and one or two samples change the share a lot. Narrowing the interval to 100 µs gathered about six times as many samples, 2,817 to 3,382, and narrowed smallHelper to 0.8 to 1.2%, at the cost seen in the previous item of a program running 16% slower. The very short price function priceOf read 0.0 to 0.4% at both intervals: functions that finish quickly rarely land in a sample. Appearing as 0% in a profile does not make a function free. The way to read such results: functions with large shares, say above 10%, have enough samples to be trustworthy, and finding such big chunks is what profiles do best. Comparing functions of a few percent, or concluding that a fix cut 1%, can fall within sampling error. Checking small differences means profiling several times and reading ranges, running longer to gather more samples, or benchmarking that part on its own. The effect of a fix is ultimately confirmed by total run time or latency rather than by shares in a profile.</sub> |
| **CPU 프로파일에 안 보이는 시간**<br><sub>Time a CPU profile cannot see</sub> | 요청 하나가 DB를 50ms 기다리고 CPU를 2ms 쓰자, CPU 프로파일의 96.6%는 idle이었고 DB 기다림은 표본의 0.04%로만 보였어요.<br><sub>With each request waiting 50 ms on a DB and using 2 ms of CPU, 96.6% of the CPU profile was idle and the DB wait appeared as only 0.04% of samples.</sub> | 요청이 느리다는 신고를 받으면 많은 사람이 먼저 CPU 프로파일을 떠요. 그런데 CPU 프로파일이 보여 줄 수 없는 시간이 있어요. 요청 하나가 데이터베이스를 50ms 기다린 뒤 화면을 그리는 데 CPU 2ms를 쓰는 상황을 만들었어요. 데이터베이스 기다림은 타이머로 흉내 냈어요. 요청 100개를 차례로 처리하며 --cpu-prof로 프로파일링했어요. 전체 5,234ms가 걸렸고 요청 하나의 중간값은 52.31ms였어요. 그동안 프로세스가 쓴 CPU 시간은 459ms였어요. 프로파일의 표본 4,496개 가운데 96.6%가 idle, 곧 이벤트 루프가 할 일 없이 기다린 표본이었어요. 프로파일 도구는 보통 idle을 빼고 플레임 그래프를 그려요. 그러면 가장 넓은 막대는 화면을 그리는 renderPage예요. queryDb는 idle을 뺀 표본의 1.29%, 전체의 0.04%였어요. 요청 시간의 96%를 차지한 기다림이 CPU 프로파일에서는 거의 보이지 않아요. 이 프로파일만 보고 renderPage를 두 배 빠르게 고치면 요청은 52ms에서 51ms가 돼요. 이유는 단순해요. CPU 프로파일은 CPU 위에 있던 시간만 기록해요. 네트워크 응답, 디스크 읽기, 잠금, 다른 서비스, 커넥션 풀의 빈자리를 기다린 시간은 CPU를 쓰지 않으니 기록되지 않아요. 이런 시간을 오프 CPU 시간이라고 해요. 느린 요청을 조사할 때는 먼저 경과 시간과 CPU 시간을 비교해요. 요청 하나가 52ms 걸렸는데 CPU는 2ms만 썼다면 문제는 기다림에 있어요. 그때는 분산 추적이 필요해요. OpenTelemetry 같은 도구로 요청 안의 데이터베이스 호출, 외부 API 호출, 캐시 조회마다 구간을 기록하면 어디서 얼마나 기다렸는지 시간 순서로 보여요. 반대로 경과 시간과 CPU 시간이 비슷하다면 CPU 프로파일이 답을 줘요. 두 도구는 서로 다른 질문에 답해요.<br><sub>Told that requests are slow, many people capture a CPU profile first, but there is time a CPU profile cannot show. A situation was built in which each request waits 50 ms for the database, simulated with a timer, and then spends 2 ms of CPU rendering a page, and 100 requests were handled in a row under --cpu-prof. The run took 5,234 ms in all, with a median of 52.31 ms per request, during which the process used 459 ms of CPU. Of the profile’s 4,496 samples, 96.6% were idle, samples in which the event loop waited with nothing to do. Profiling tools usually draw flame graphs without idle, and then the widest bar is renderPage, while queryDb accounted for 1.29% of non-idle samples and 0.04% of all. The wait that made up 96% of request time is almost invisible in the CPU profile; fixing renderPage to run twice as fast on the strength of this profile would take a request from 52 ms to 51 ms. The reason is simple: a CPU profile records only time spent on the CPU. Waiting for a network response, a disk read, a lock, another service or a free slot in a connection pool uses no CPU and leaves no record, time known as off-CPU time. Investigating a slow request therefore starts by comparing wall time with CPU time: if a request took 52 ms and used only 2 ms of CPU, the problem lies in waiting, and distributed tracing is needed. Recording a span for each database call, external API call and cache lookup inside a request with a tool such as OpenTelemetry shows in time order where and how long it waited. If wall time and CPU time are close, the CPU profile holds the answer. The two tools answer different questions.</sub> |
| **계측이 바꾸는 결과**<br><sub>Instrumentation that changes results</sub> | 함수마다 performance.now로 감싸 재자 프로그램이 4배 느려졌고, 짧은 비교 함수에는 실제의 열 배쯤 되는 900ms 안팎이 매겨졌어요.<br><sub>Wrapping every function in performance.now made the program 4× slower and charged a short comparator about 900 ms, roughly ten times its real cost.</sub> | 프로파일러 대신 함수마다 시계를 감싸 직접 재는 방법도 흔해요. 원하는 함수만 골라 정확한 시간을 얻을 수 있을 것 같기 때문이에요. 이 방법이 얼마나 정확한지 쟀어요. 앞의 프로그램에서 함수 다섯 개를 모두 performance.now로 감싸고, 함수가 끝날 때마다 걸린 시간을 함수별로 더했어요. 정렬에 쓰는 비교 함수 byPrice도 감쌌어요. 감싸지 않은 프로그램은 685~710ms였는데, 감싼 프로그램은 2,520~2,973ms였어요. 네 배쯤 느려졌어요. 함수 호출 수백만 번마다 시계를 두 번씩 읽고 더하는 비용이 붙었기 때문이에요. 함수별 기록은 더 크게 어긋났어요. 시계는 byPrice에 829~975ms를 매겼어요. 그런데 감싸지 않은 프로그램을 표본 방식으로 프로파일링하면 byPrice는 전체의 8.8~15.4%, 700ms 가운데 60~110ms였어요. 시계로 잰 값이 열 배쯤 부풀었어요. byPrice는 한 번에 수십 ns 걸리는 짧은 함수인데 정렬 중에 수백만 번 불려요. 시계를 한 번 읽는 데만 50~70ns가 드니, 측정 비용이 함수 자신보다 커진 거예요. 이렇게 재는 행위가 재는 대상을 바꾸는 것을 관찰자 효과라고 해요. 이 결과로 byPrice를 고치는 데 시간을 쓰면, 실제로는 크지 않은 곳을 고치게 돼요. 직접 계측은 쓸모가 있어요. 요청 하나, 데이터베이스 쿼리 하나, 외부 API 호출 하나처럼 한 번에 밀리초 단위가 걸리는 굵은 단위에서는 시계 비용이 무시할 만큼 작고, 표본 프로파일러가 놓치는 기다림까지 잴 수 있어요. 반대로 짧고 자주 불리는 함수는 표본 프로파일러로 봐요. 계측을 더한 뒤에는 전체 실행 시간이나 지연 시간이 얼마나 늘었는지 꼭 확인해요. 늘어난 만큼 결과가 왜곡돼 있어요. 운영 환경의 추적 도구가 요청 중 일부만 표본으로 기록하는 것도 계측 비용을 줄이기 위해서예요.<br><sub>Instead of a profiler, wrapping every function in a clock is a common approach, since it seems to give exact times for exactly the functions one cares about, so its accuracy was measured. All five functions of the earlier program were wrapped with performance.now, adding up each function’s elapsed time whenever it finished, the sort comparator byPrice included. The unwrapped program took 685 to 710 ms and the wrapped one 2,520 to 2,973 ms, about four times slower, because reading a clock twice and adding on each of millions of function calls added up. The per-function records were even further off: the timers charged 829 to 975 ms to byPrice, while sampling the unwrapped program put byPrice at 8.8 to 15.4% of the total, 60 to 110 ms of 700. The clock-based figure was inflated about tenfold. byPrice is a short function taking tens of nanoseconds per call, called millions of times during sorting, and since one clock read alone costs 50 to 70 ns, measuring it cost more than running it. Measuring that changes what is measured is called the observer effect, and acting on this result means spending time fixing something that is not actually large. Manual instrumentation has its uses: at coarse units that take milliseconds each, such as one request, one database query or one external API call, the clock cost is negligible, and it can even capture waits that sampling profilers miss. Short, frequently called functions, on the other hand, are left to sampling profilers. After adding instrumentation, always check how much total run time or latency grew, since the result is distorted by that much. Production tracing tools record only a sample of requests for the same reason, to keep instrumentation cost down.</sub> |
| **꺼진 로그의 비용**<br><sub>The cost of disabled logs</sub> | debug 레벨이 꺼져 있어도 템플릿 문자열로 넘긴 로그는 반복 한 번을 21ns에서 1,227ns로 58배 느리게 했어요. 함수로 넘기면 23ns였어요.<br><sub>With debug off, a log given a template string still slowed each iteration from 21 ns to 1,227 ns, 58×; passing a function kept it at 23 ns.</sub> | 로그 레벨을 info로 두면 debug 로그는 찍히지 않으니 비용도 없다고 생각하기 쉬워요. 정말 그런지 쟀어요. 주문 하나를 처리하는 반복 안에 debug 로그를 넣고, 로그 레벨은 info로 두었어요. 네 가지를 비교했어요. 로그가 없을 때, log.debug에 템플릿 문자열과 JSON.stringify(order)를 넘길 때, 그 문자열을 만드는 함수를 넘길 때, if (log.isDebug)로 레벨을 먼저 확인할 때예요. 로그가 없을 때 반복 한 번은 21.0ns였어요. 템플릿 문자열을 넘기자 1,226.8ns가 됐어요. 58배예요. 로그는 한 줄도 찍히지 않았는데도요. 문자열을 만드는 함수를 넘기자 23.1ns, if로 감싸자 18.3ns로 로그가 없을 때와 같았어요. 이유는 JavaScript의 평가 순서에 있어요. 함수를 부르기 전에 인자를 먼저 계산해요. log.debug 안에서 레벨을 확인해 아무것도 하지 않고 돌아오더라도, 그 전에 이미 주문 객체를 JSON으로 바꾸고 문자열을 이어 붙이는 일이 끝나 있어요. 로그 라이브러리가 레벨을 아무리 빠르게 확인해도 이 비용은 줄지 않아요. 이 문제는 뜨거운 경로에서만 드러나요. 요청마다 한 번 찍는 로그라면 1µs는 보이지 않지만, 반복문 안이나 초당 수십만 번 불리는 함수 안이라면 그 로그가 전체 시간의 대부분을 차지해요. 대책은 세 가지예요. 첫째, 문자열을 직접 만들지 말고 값을 그대로 넘겨 직렬화를 라이브러리에 맡겨요. pino 같은 라이브러리는 객체를 따로 받아 레벨이 켜져 있을 때만 직렬화해요. 둘째, 값을 만드는 함수를 넘겨 필요할 때만 계산하게 해요. 셋째, 비싼 인자가 필요한 로그는 if로 레벨을 먼저 확인해요. 같은 원리는 assert나 메트릭 이름을 만드는 코드에도 적용돼요. 꺼져 있다는 것과 비용이 없다는 것은 다른 이야기예요.<br><sub>With the log level at info, debug logs are never printed, so it is tempting to think they cost nothing, which was put to the test. The reason is JavaScript’s order of evaluation: arguments are computed before a function is called. Even if log.debug checks the level and returns without doing anything, converting the order to JSON and concatenating the string have already happened, and no matter how quickly a logging library checks its level, that cost remains. The problem only shows on hot paths: for a log written once per request, a microsecond is invisible, but inside a loop or a function called hundreds of thousands of times per second, the log can take most of the time. There are three remedies. First, pass raw values instead of building strings and leave serialization to the library; libraries such as pino take objects as separate arguments and serialize them only when the level is enabled. Second, pass a function that produces the value so it is computed only when needed. Third, guard logs with expensive arguments by checking the level with if first. The same principle applies to code that builds assertion messages or metric names. Being disabled and being free are two different things.</sub> |

| **작은 n의 탐색**<br><sub>Lookups at small n</sub> | 원소 16개까지는 배열 includes, 이진 탐색, Set이 모두 4~7ns로 같았어요. 4,096개에서는 includes가 2,191ns로 Set의 320배였어요.<br><sub>Up to 16 elements, array includes, binary search and a Set all took 4–7 ns; at 4,096, includes took 2,191 ns, 320× the Set.</sub> | 알고리즘 수업에서는 선형 탐색이 O(n), 이진 탐색이 O(log n), 해시 조회가 O(1)이라고 배워요. 그렇다면 언제나 해시를 쓰는 게 맞을까요. 값이 목록에 있는지 확인하는 세 가지 방법을 원소 수를 바꿔 가며 쟀어요. 배열의 includes는 처음부터 차례로 보고, 이진 탐색은 정렬된 배열을 반씩 나누고, Set은 해시로 바로 찾아요. 원소 4, 16, 64, 256, 4,096개에서 조회 200만 번의 평균을 냈어요. 원소 4개에서는 includes 4.0ns, 이진 탐색 3.7ns, Set 4.0ns였어요. 16개에서도 6.1ns, 6.9ns, 7.1ns로 비슷했어요. 이 크기에서는 빅오의 차이보다 함수 호출, 해시 계산, 비교 몇 번 같은 상수가 시간을 정해요. 원소가 늘자 갈렸어요. includes는 64개에서 15.4ns, 256개에서 78.3ns, 4,096개에서 2,191ns로 원소 수에 비례해 늘었어요. 이진 탐색은 4,096개에서도 16.8ns, Set은 6.8ns에 머물렀어요. 4,096개에서 includes는 Set의 320배예요. 빅오는 n이 충분히 커질 때 비용이 어떻게 늘어나는지를 말해요. 작은 n에서는 상수가 더 중요하고, 교차점은 언어와 엔진, 데이터 모양에 따라 달라요. 그래서 판단은 데이터가 얼마나 커질 수 있느냐로 해요. 요일, 상태 몇 개, 설정 값 몇 개처럼 늘 작은 목록은 배열이 읽기 쉽고 충분히 빨라요. 굳이 Set으로 바꿀 이유가 없어요. 사용자 수, 상품 수, 로그 줄 수처럼 커질 수 있는 목록은 처음부터 Set이나 Map을 써요. 지금 작더라도 내일 커질 수 있는 데이터에 선형 탐색을 쓰면, 운영 데이터가 쌓인 뒤에야 느려지는 코드가 돼요. 정렬된 배열의 이진 탐색은 해시보다 조금 느리지만 메모리를 적게 쓰고 범위 검색도 할 수 있어서, 읽기가 대부분인 큰 정적 데이터에 어울려요.<br><sub>Algorithms classes teach that linear search is O(n), binary search O(log n) and hash lookup O(1), so should hashing always be used? Three ways of checking whether a value is in a list were measured as the element count varied: includes scanning an array from the start, binary search halving a sorted array, and a Set finding it by hash, averaging two million lookups at 4, 16, 64, 256 and 4,096 elements. With 4 elements, includes took 4.0 ns, binary search 3.7 ns and the Set 4.0 ns, and with 16 they were a similar 6.1, 6.9 and 7.1 ns: at this size, constants such as a function call, a hash computation and a few comparisons set the time rather than big-O. As elements grew, they parted ways. includes rose in proportion to the count, to 15.4 ns at 64, 78.3 ns at 256 and 2,191 ns at 4,096, while binary search stayed at 16.8 ns and the Set at 6.8 ns even at 4,096, includes being 320 times the Set. Big-O describes how cost grows once n is large enough; at small n constants matter more, and the crossover depends on the language, engine and data shape. The decision therefore rests on how large the data can grow. Lists that always stay small, such as weekdays, a handful of states or a few settings, read easily as arrays and are fast enough, with no reason to switch to a Set. Lists that can grow, such as users, products or log lines, use a Set or Map from the start, because a linear search over data that is small today but may grow tomorrow becomes code that slows down only after production data accumulates. Binary search over a sorted array is slightly slower than hashing but uses less memory and supports range queries, suiting large static data that is mostly read.</sub> |

The structure brings a new trap, however. | **객체 풀**<br><sub>Object pools</sub> | 메시지 100만 개에 객체 풀을 쓰자 GC 횟수는 63% 줄었지만 전체 시간은 1~6%만 빨라졌어요. Eight million sine-times-square-root calculations were split evenly across 1, 2, 3, 4, 8 and 16 workers, timing from creating the workers to receiving the results. The machine has 2 cores, as os.availableParallelism() reports, and running on the main thread with no workers took 518 ms for comparison. One worker took 696 ms, slower than the main thread, because the cost of starting a worker and exchanging messages was added to the same calculation; creating a worker and receiving its first message alone took 33 ms. Two workers were fastest at 423 ms, both cores working at once. Three and four workers took 519 to 520 ms, eight 484 ms and sixteen 618 ms: threads beyond the core count only take turns on the same cores, computing no faster while adding the cost of creating threads, switching between them and sharing memory, and since each worker has its own V8 instance and heap, memory also grows with the number of workers. The parallelism of CPU-bound work is capped by the core count, so worker pool sizes follow os.availableParallelism(), sometimes one fewer so the main thread can keep accepting requests. Workers are created ahead and reused rather than started per request, since paying a 33 ms startup for a job of a few milliseconds makes using a worker a loss. Containers need one more check: even on a machine with many cores, the CPU quota assigned to the container may be smaller, and then workers sized to the core count merely take turns within the quota. Conversely, I/O work that mostly waits needs no workers; sending asynchronous requests concurrently, as in the previous item, is enough. Workers are the tool to reach for when computation would otherwise block the main thread for long.</sub> |
