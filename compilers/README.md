## 앞단: 읽고 이해하기 · Front end: reading and understanding

소스 코드를 토큰과 트리로 바꾸고 의미를 검사해요.  
*Turning source into tokens and trees, then checking meaning.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **어휘 분석 (렉서)**<br><sub>Lexical analysis</sub> | 렉서는 문자의 흐름을 키워드·이름·숫자·연산자 같은 토큰으로 묶어요. 공백과 주석은 여기서 사라져요.<br><sub>The lexer groups a stream of characters into tokens such as keywords, names, numbers and operators; whitespace and comments vanish here.</sub> | 예: let total = price \* 2 + 10; → let, total, =, price, \*, 2, +, 10, ; (토큰 9개). 각 토큰에 줄·열 위치를 기록해 오류 메시지에 써요. 가능한 한 길게 읽는 최장 일치로 >=를 하나로, iffy를 식별자로 인식해요.<br><sub>let total = price \* 2 + 10; becomes nine tokens: let, total, =, price, \*, 2, +, 10, ;. Each carries its line and column for error messages. The longest-match rule reads >= as one token and iffy as an identifier.</sub> |
| **렉서와 유한 오토마타**<br><sub>Lexers as automata</sub> | 렉서는 상태와 전이로 된 유한 오토마타(DFA)예요. 글자마다 전이를 따라가고 받아들이는 상태에서 토큰이 정해져요.<br><sub>A lexer is a finite automaton (DFA): each character follows a transition, and accepting states decide the token.</sub> | 키워드는 일단 식별자로 읽은 뒤 키워드 표에서 구분해요. 정규식으로 토큰 규칙을 쓰면 lex·flex·re2c가 정규식 → NFA → DFA로 렉서를 생성해요. 실제 대형 컴파일러(GCC, Clang, Go, Rust)는 오류 메시지와 속도를 위해 손으로 짠 렉서가 많아요.<br><sub>Keywords are scanned as identifiers and then looked up in a keyword table. Write token rules as regular expressions and lex, flex or re2c generate the lexer via regex → NFA → DFA. Production compilers (GCC, Clang, Go, Rust) often hand-write theirs for better errors and speed.</sub> |
| **문맥 자유 문법**<br><sub>Context-free grammars</sub> | 문법은 기호를 바꿔 쓰는 규칙 모음으로 언어의 모양을 정확히 정의해요. 규칙의 층이 연산자 우선순위와 결합 방향을 정해요.<br><sub>A grammar is a set of rewrite rules that pins down a language’s shape. Its layering encodes operator precedence and associativity.</sub> | expr → expr + term \| term, term → term \* factor \| factor, factor → NUM \| ( expr ). \*가 더 깊은 층에 있어 먼저 묶이고, 왼쪽 재귀는 왼쪽 결합을 뜻해요. BNF·EBNF로 JSON·SQL·파이썬 문법이 명세되고, ANTLR·yacc·bison 같은 파서 생성기의 입력이 돼요.<br><sub>expr → expr + term \| term, term → term \* factor \| factor, factor → NUM \| ( expr ). \* sits in a deeper layer so it binds tighter, and left recursion means left associativity. BNF and EBNF specify JSON, SQL and Python, and feed parser generators such as ANTLR, yacc and bison.</sub> |
| **모호한 문법**<br><sub>Ambiguous grammars</sub> | 한 입력에 파스 트리가 둘 이상 나오면 모호한 문법이에요. 1 + 2 \* 3이 9가 될 수도 7이 될 수도 있어요.<br><sub>A grammar is ambiguous when one input has two parse trees: 1 + 2 \* 3 could mean 9 or 7.</sub> | E → E + E \| E \* E 같은 문법은 우선순위를 정하지 않아요. 우선순위별로 규칙 층을 나누거나, 파서 생성기에 %left·%right로 우선순위와 결합을 선언해 해결해요. 고전적 예: 매달린 else는 가장 가까운 if에 붙이기로 약속해요.<br><sub>Rules such as E → E + E \| E \* E leave precedence open. Fix it by layering rules by precedence, or by declaring %left and %right precedence to the parser generator. The classic case is the dangling else, resolved by attaching it to the nearest if.</sub> |
| **재귀 하강 파서**<br><sub>Recursive descent parsing</sub> | 문법 규칙 하나를 함수 하나로 옮겨 서로 부르게 하는 파서예요. 연산자 우선순위가 호출 깊이로 자연스럽게 표현돼요.<br><sub>Write each grammar rule as a function and let them call one another; precedence falls out of the call depth.</sub> | expr()는 term()을, term()은 factor()를 불러요. 왼쪽 재귀는 무한 호출이 되므로 while 반복으로 바꿔요. 오류 메시지를 다루기 쉬워 GCC·Clang·Go·Rust·V8 모두 손으로 짠 재귀 하강 파서를 써요. 연산자가 많으면 프랫(Pratt) 파싱으로 우선순위 표를 써요.<br><sub>expr() calls term(), which calls factor(). Left recursion would recurse forever, so it becomes a while loop. Because it makes error handling easy, GCC, Clang, Go, Rust and V8 all use hand-written recursive descent; with many operators, Pratt parsing drives it from a precedence table.</sub> |
| **LR 파싱 (시프트-리듀스)**<br><sub>LR (shift-reduce) parsing</sub> | 토큰을 스택에 쌓다가(shift) 규칙의 오른쪽이 보이면 왼쪽 기호로 줄여(reduce) 아래에서 위로 트리를 만들어요.<br><sub>Push tokens onto a stack (shift) and, when a rule’s right side appears, replace it with its head (reduce), building the tree bottom-up.</sub> | 1 + 2 \* 3에서 \* 앞에서는 E + T를 줄이지 않고 계속 쌓아 곱셈을 먼저 묶어요. 언제 shift하고 reduce할지는 문법에서 계산한 표(LR(1)·LALR)가 정해요. yacc·bison이 이 표를 생성하고, 결정이 둘이면 shift/reduce 충돌을 경고해요.<br><sub>For 1 + 2 \* 3 it keeps shifting before \* instead of reducing E + T, so the multiplication groups first. A table computed from the grammar (LR(1) or LALR) decides each move; yacc and bison generate it and warn about shift/reduce conflicts when two moves are possible.</sub> |
| **추상 구문 트리 (AST)**<br><sub>Abstract syntax trees</sub> | 파스 트리에서 의미에 필요 없는 노드를 걷어 낸 간결한 트리예요. 이후의 모든 단계가 AST를 순회하며 일해요.<br><sub>A compact tree with the parse tree’s bookkeeping nodes removed. Every later stage walks the AST.</sub> | x = (a + b) \* 2;는 파스 트리로 20개 노드지만 AST는 Assign(x, Mul(Add(a, b), 2))의 7개. 괄호·세미콜론은 트리 모양에 녹아들어요. Babel·ESLint·Prettier, 파이썬 ast 모듈, tree-sitter가 AST를 다루고, astexplorer.net에서 직접 볼 수 있어요.<br><sub>x = (a + b) \* 2; takes 20 parse-tree nodes but only seven AST nodes: Assign(x, Mul(Add(a, b), 2)). Parentheses and semicolons melt into the shape. Babel, ESLint, Prettier, Python’s ast module and tree-sitter all work on ASTs; try astexplorer.net.</sub> |
| **심볼 테이블과 스코프**<br><sub>Symbol tables and scopes</sub> | 선언된 이름과 그 정보(타입, 위치)를 스코프별 표에 기록해요. 이름은 가장 안쪽 스코프부터 바깥으로 찾아요.<br><sub>Each declared name and its information (type, location) is recorded in a per-scope table, and lookups search from the innermost scope outward.</sub> | 함수·블록마다 새 표를 바깥 표에 연결해요. 안쪽 선언이 바깥 이름을 가리고(shadowing), 스코프를 나오면 그 이름들은 사라져요. “선언되지 않은 변수”, “중복 선언” 오류가 여기서 나오고, IDE의 정의로 이동·이름 바꾸기도 같은 정보를 써요.<br><sub>Every function or block chains a new table to its parent. Inner declarations shadow outer names, and leaving a scope drops its entries. “Undeclared variable” and “duplicate declaration” errors come from here, and IDE go-to-definition and rename rely on the same data.</sub> |
| **타입 검사**<br><sub>Type checking</sub> | 트리의 잎부터 타입을 붙이고 규칙(int + int → int 같은)을 적용해 전체 타입을 구해요. 맞는 규칙이 없으면 위치와 함께 오류를 내요.<br><sub>Type the leaves, then apply rules such as int + int → int up the tree. If no rule fits, report an error with its location.</sub> | len(name) + 1: name은 string, len은 string → int이므로 len(name)은 int, 1은 int, 덧셈 결과도 int. 정적 타입 언어(TypeScript, Java, Rust, Go)는 실행 전에 오류를 잡고 코드 생성에 크기·레이아웃 정보를 줘요. 동적 타입 언어는 같은 검사를 실행 중에 해요.<br><sub>In len(name) + 1, name is a string and len is string → int, so len(name) is an int, 1 is an int and the sum is an int. Statically typed languages (TypeScript, Java, Rust, Go) catch errors before running and tell code generation sizes and layouts; dynamic languages check the same things at run time.</sub> |
| **타입 추론**<br><sub>Type inference</sub> | 타입을 적지 않아도 쓰임새에서 제약을 모아 풀어 타입을 알아내요. 제약이 남지 않으면 제네릭 타입이 돼요.<br><sub>Infer types from how values are used, collecting and solving constraints without annotations; whatever stays unconstrained becomes generic.</sub> | x => x + 1: x에 α를 붙이고 +가 int를 요구하니 α = int → int → int. x => x는 ∀α. α → α. 힌들리-밀너 추론(ML, OCaml, Haskell)이 대표적이고, Rust·TypeScript·Kotlin·Swift는 지역 추론으로 let x = 5 같은 곳의 표기를 줄여요.<br><sub>For x => x + 1, give x a type α; + demands ints, so α = int and the function is int → int. x => x is ∀α. α → α. Hindley–Milner inference (ML, OCaml, Haskell) is the classic; Rust, TypeScript, Kotlin and Swift use local inference to drop annotations like those in let x = 5.</sub> |
| **FIRST·FOLLOW와 LL(1) 파싱 표**<br><sub>FIRST, FOLLOW and LL(1) parse tables</sub> | 하향식 파서가 다음 토큰 하나만 보고 규칙을 고를 수 있게, 문법에서 FIRST·FOLLOW 집합을 구해 파싱 표를 만들어요.<br><sub>To let a top-down parser choose a rule from a single lookahead token, compute FIRST and FOLLOW sets from the grammar and build a parse table.</sub> | E → T E′, E′ → + T E′ \| ε 처럼 왼쪽 재귀를 없앤 문법에서, FIRST는 각 기호로 시작할 수 있는 첫 토큰들(E, T, F는 { (, id })이고 FOLLOW는 그 기호 바로 뒤에 올 수 있는 토큰들(E′는 { ), $ })이에요. 표 M[A, a]에는 a ∈ FIRST(α)인 규칙 A → α를 넣고, α가 ε을 만들 수 있으면 FOLLOW(A)의 토큰 칸에도 넣어요. 모든 칸에 규칙이 하나 이하면 LL(1) 문법이라 스택과 표만으로 결정적으로 파싱해요. 한 칸에 두 규칙이 들어가면 좌인수분해나 왼쪽 재귀 제거로 문법을 고치거나 LR 파서를 써요.<br><sub>In a grammar without left recursion such as E → T E′, E′ → + T E′ \| ε, FIRST is the set of tokens that can start each symbol (E, T and F give { (, id }) and FOLLOW the tokens that can appear right after it (E′ gives { ), $ }). The table M[A, a] gets rule A → α wherever a ∈ FIRST(α), and, if α can derive ε, in the columns of FOLLOW(A) too. If no cell holds more than one rule the grammar is LL(1), and a stack plus the table parse it deterministically. A cell with two rules means left-factoring or removing left recursion, or switching to an LR parser.</sub> |
| **구문 오류 복구와 진단**<br><sub>Syntax error recovery and diagnostics</sub> | 좋은 컴파일러는 첫 오류에서 멈추지 않고 다시 파싱을 이어 가 진짜 오류를 한 번에 최대한 많이 보고해요. 메시지도 위치와 고칠 방법까지 알려 줘요.<br><sub>Good compilers don’t stop at the first error; they recover and keep parsing to report as many real errors as possible, with messages that show where and how to fix them.</sub> | 첫 오류에서 멈추면 하나 고치고 다시 빌드하는 일을 반복해야 해요. 패닉 모드 복구는 오류가 나면 ;나 다음 문장 키워드 같은 동기화 토큰까지 건너뛰고 다시 시작해, let x = (1 + 2;의 빠진 )와 다음 줄의 빠진 ;를 한 번에 보고해요. 구 수준 복구는 빠진 )를 있었던 것처럼 끼워 넣고 계속해서 엉뚱한 연쇄 오류를 막고, AST에는 오류 노드를 남겨요. 좋은 진단은 줄:열 위치, 문제 지점 밑줄과 이유, 짝이 맞지 않는 여는 괄호, 고치는 방법(help)까지 보여 줘요(Rust, Elm, Clang). IDE는 작성 중인 코드를 계속 파싱하므로 복구가 특히 중요해요.<br><sub>Stopping at the first error forces a fix-rebuild loop. Panic-mode recovery skips to a synchronizing token such as ; or the next statement keyword and resumes, so the missing ) in let x = (1 + 2; and the missing ; on the next line are reported together. Phrase-level recovery inserts the missing ) as if it were there, avoiding a cascade of bogus errors and leaving an error node in the AST. Good diagnostics show line:column, underline the spot with a reason, point at the unclosed bracket and suggest a fix (Rust, Elm, Clang). IDEs reparse half-written code constantly, so recovery matters even more there.</sub> |

## 중간 표현과 최적화 · Intermediate representation and optimization

CPU와 무관한 형태로 바꿔 더 빠르고 작게 다듬어요.  
*A CPU-neutral form where code is made faster and smaller.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **3주소 코드**<br><sub>Three-address code</sub> | 각 명령이 “결과 = 피연산자 연산 피연산자” 꼴인 중간 표현이에요. 트리를 아래에서 위로 돌며 연산마다 임시 변수를 만들어요.<br><sub>An intermediate form where every instruction is “result = operand op operand”, built by walking the tree bottom-up with one temporary per operation.</sub> | a = b \* c + d \* e → t1 = b \* c; t2 = d \* e; t3 = t1 + t2; a = t3. 기계어와 가깝지만 레지스터 수 제한이 없고 CPU와 무관해 최적화하기 좋아요. LLVM IR, JVM 바이트코드, 파이썬 바이트코드도 비슷한 중간 표현이에요.<br><sub>a = b \* c + d \* e becomes t1 = b \* c; t2 = d \* e; t3 = t1 + t2; a = t3. Close to machine code but CPU-neutral with unlimited temporaries, it is easy to optimize. LLVM IR, JVM bytecode and Python bytecode are relatives.</sub> |
| **기본 블록과 제어 흐름 그래프**<br><sub>Basic blocks and control-flow graphs</sub> | 중간에 들어오거나 나가는 점프가 없는 코드 덩어리(기본 블록)를 노드로, 가능한 실행 흐름을 간선으로 그린 그래프예요.<br><sub>A graph whose nodes are straight-line chunks of code (basic blocks) with no jumps in or out mid-way, and whose edges are possible control flow.</sub> | 점프 목적지와 점프 바로 다음 줄에서 블록을 끊어요. 뒤로 가는 간선이 반복문을 드러내요. 블록 안(지역) 최적화와 그래프 전체(전역) 최적화, 도달 불가능 코드 찾기, 지배자(dominator) 분석의 기본 틀이에요.<br><sub>Blocks are cut at jump targets and right after jumps. A backward edge reveals a loop. It frames local (per-block) and global (whole-graph) optimization, unreachable-code detection and dominator analysis.</sub> |
| **SSA 형식**<br><sub>SSA form</sub> | 모든 변수가 딱 한 번만 대입되도록 이름에 버전을 붙인 형식이에요. 흐름이 합쳐지는 곳에는 φ 함수가 값을 골라요.<br><sub>A form where every variable is assigned exactly once by versioning names; where paths merge, a φ function chooses the value.</sub> | x = 1; if (c) x = 2 else x = 3; y = x + 1 → x1, x2, x3, x4 = φ(x2, x3), y1 = x4 + 1. 정의가 하나뿐이라 값의 출처가 바로 보여 상수 전파·죽은 코드 제거·레지스터 할당이 쉬워져요. LLVM IR, GCC GIMPLE, V8·HotSpot JIT 모두 SSA 기반이에요.<br><sub>x = 1; if (c) x = 2 else x = 3; y = x + 1 becomes x1, x2, x3, x4 = φ(x2, x3), y1 = x4 + 1. With one definition each, a value’s origin is obvious, easing constant propagation, dead code elimination and register allocation. LLVM IR, GCC’s GIMPLE and the V8 and HotSpot JITs are SSA-based.</sub> |
| **상수 접기와 전파**<br><sub>Constant folding and propagation</sub> | 컴파일할 때 값을 아는 식은 미리 계산하고(접기), 상수인 변수를 쓰는 곳에 값을 넣어(전파) 다시 접어요.<br><sub>Compute expressions whose values are known at compile time (folding) and substitute known constants at their uses (propagation), then fold again.</sub> | const SECS = 60 \* 60 \* 24 → 86400, t = SECS \* 2 → 172800, if (DEBUG)에서 DEBUG가 false면 가지 전체 삭제. 최적화들이 서로를 부르며 반복돼요. C++ constexpr, Rust const fn이 이를 언어 차원에서 보장해요. 실수 연산은 반올림 규칙 때문에 함부로 접지 않아요.<br><sub>const SECS = 60 \* 60 \* 24 becomes 86400 and t = SECS \* 2 becomes 172800; with DEBUG false, an if (DEBUG) branch disappears. Optimizations feed each other, so passes repeat. C++ constexpr and Rust const fn guarantee this at language level. Floating point isn’t folded freely because of rounding rules.</sub> |
| **죽은 코드 제거**<br><sub>Dead code elimination</sub> | 결과에 영향을 주지 않는 코드(아무도 읽지 않는 계산, 실행될 수 없는 코드)를 지워요.<br><sub>Remove code that cannot affect the result: computations nobody reads and code that can never run.</sub> | 생존 분석으로 읽히지 않는 대입을, 제어 흐름 그래프로 도달 불가능한 블록을 찾아요. 부작용이 있는 코드(함수 호출, 입출력, volatile)는 지우면 안 돼요. JS 번들러의 트리 셰이킹은 모듈 단위의 죽은 코드 제거. 벤치마크 코드가 통째로 지워지는 함정도 여기서 생겨요.<br><sub>Liveness finds assignments that are never read; the control-flow graph finds unreachable blocks. Code with side effects (calls, I/O, volatile) must stay. Tree shaking in JavaScript bundlers is module-level dead code elimination, and it is also why naive benchmarks sometimes get optimized away entirely.</sub> |
| **공통 부분식 제거**<br><sub>Common subexpression elimination</sub> | 같은 식이 여러 번 계산되면 한 번만 계산해 임시 변수에 두고 다시 써요.<br><sub>When the same expression is computed more than once, compute it once into a temporary and reuse it.</sub> | a = b \* c + g; d = b \* c \* e → t = b \* c; a = t + g; d = t \* e. 사이에 피연산자가 바뀌거나, 포인터 별칭으로 메모리가 바뀌었을 수 있으면 할 수 없어요. SSA 위의 전역 값 번호 매기기(GVN)가 함수 전체로 일반화해요. 레지스터가 부족하면 다시 계산이 나을 때도 있어요.<br><sub>a = b \* c + g; d = b \* c \* e becomes t = b \* c; a = t + g; d = t \* e. It is blocked if an operand changes in between or memory might change through aliasing pointers. Global value numbering (GVN) on SSA generalizes it across a function; with scarce registers, recomputing can win.</sub> |
| **루프 최적화**<br><sub>Loop optimizations</sub> | 반복문 안에서 매번 같은 계산은 밖으로 꺼내고(루프 불변 코드 이동), 규칙적으로 변하는 곱셈은 덧셈으로 바꿔요(강도 감소).<br><sub>Hoist computations that never change out of the loop (loop-invariant code motion) and turn regularly growing multiplies into adds (strength reduction).</sub> | a[i] = x \* y + i \* 4 → 반복문 앞에서 t = x \* y, 안에서는 p += 4. 반복 횟수만큼 이득이 쌓여 효과가 가장 큰 최적화 영역이에요. 이 밖에 반복문 펼치기, SIMD 벡터화(4~16개씩), 합치기·나누기, 캐시를 위한 타일링이 있어요.<br><sub>a[i] = x \* y + i \* 4 becomes t = x \* y before the loop and p += 4 inside. Savings multiply by the iteration count, making loops the richest target. Others include unrolling, SIMD vectorization (4–16 elements at a time), fusion, fission and cache tiling.</sub> |
| **함수 인라이닝**<br><sub>Function inlining</sub> | 함수 호출 자리에 함수 몸체를 펼쳐 넣어 호출 비용을 없애고, 다른 최적화가 함수 안까지 보게 해요.<br><sub>Paste a function’s body into its call site to remove call overhead and let other optimizations see inside.</sub> | sq(a + 1) → t = a + 1; t \* t, sq(3) → 9(인라인 후 상수 접기). 대가는 코드 크기 증가와 명령어 캐시 부담이라, 작고 자주 불리는 함수 위주로 휴리스틱이 정해요(inline 키워드는 힌트). 가상 호출은 탈가상화가 필요하고, JIT은 실제로 불리는 대상을 보고 인라인해요.<br><sub>sq(a + 1) becomes t = a + 1; t \* t, and sq(3) folds to 9 after inlining. The cost is code growth and instruction-cache pressure, so heuristics favor small, hot functions (the inline keyword is just a hint). Virtual calls need devirtualization first; JITs inline the targets they actually observe.</sub> |
| **생존 분석**<br><sub>Liveness analysis</sub> | 각 지점에서 나중에 값이 읽힐 변수(살아 있는 변수)를 거꾸로 계산하는 데이터 흐름 분석이에요.<br><sub>A backward dataflow analysis that finds, at each point, which variables will still be read later (are live).</sub> | in = use ∪ (out − def)를 끝에서부터 계산하고, 반복문이 있으면 변화가 없을 때까지 반복해요(고정점). 살아 있는 구간이 겹치는 변수는 같은 레지스터를 못 써요. 레지스터 할당, 죽은 코드 제거, 초기화하지 않은 변수 경고가 이 분석을 써요.<br><sub>Compute in = use ∪ (out − def) from the end, iterating to a fixpoint when loops exist. Variables with overlapping live ranges cannot share a register. Register allocation, dead code removal and uninitialized-variable warnings all build on it.</sub> |
| **탈출 분석**<br><sub>Escape analysis</sub> | 포인터가 함수 밖으로 “탈출”하는지 분석해서, 탈출하지 않는 객체는 힙 대신 스택이나 레지스터에 둬요. 할당과 GC 부담이 줄어요.<br><sub>Escape analysis checks whether a pointer can leave its function; objects that don’t escape go on the stack or in registers instead of the heap, saving allocations and GC work.</sub> | p := &Point{x, y}로 만든 객체의 포인터가 반환되지도, 전역 변수에 저장되지도, 다른 고루틴·스레드로 넘어가지도 않으면 함수가 끝날 때 함께 사라져도 되므로 스택에 할당해요. 반대로 return &Point{x, y}처럼 포인터를 돌려주면 함수가 끝나도 살아 있어야 해서 탈출로 보고 힙에 할당해요. 한 걸음 더 나아가 객체를 필드로 쪼개 레지스터에 두면 할당 자체가 사라지는데, 이를 스칼라 치환이라고 해요. Go는 go build -gcflags=-m으로 결과를 보여 주고, 자바 HotSpot과 .NET도 GC 부담을 줄이려고 써요.<br><sub>If the pointer from p := &Point{x, y} is never returned, stored in a global or passed to another goroutine or thread, the object can die with the function, so it is allocated on the stack. If the pointer is returned, as in return &Point{x, y}, it must outlive the call, so it escapes and is allocated on the heap. Going further, splitting the object into its fields held in registers removes the allocation entirely, which is called scalar replacement. Go reports the decisions with go build -gcflags=-m, and Java HotSpot and .NET use the same analysis to reduce GC pressure.</sub> |
| **자동 벡터화 (SIMD)**<br><sub>Auto-vectorization (SIMD)</sub> | 컴파일러가 반복문을 SIMD 명령으로 바꿔, 레지스터 하나에 담긴 값 여러 개를 명령 하나로 동시에 처리하게 해요.<br><sub>The compiler turns a loop into SIMD instructions so that one instruction processes several values packed into a register at once.</sub> | c[i] = a[i] + b[i]를 그대로 컴파일하면 덧셈 명령 하나가 원소 하나를 처리해 16번 반복해요. AVX2의 256비트 레지스터에는 float 8개가 들어가므로 vaddps 한 번에 8개를 더해 2번이면 끝나요. 이렇게 하려면 반복끼리 의존이 없어야 하고(c[i] = c[i-1] + a[i]는 불가), 배열이 서로 겹치지 않아야 해요(C에서는 restrict로 약속). n이 8의 배수가 아니면 남은 원소는 스칼라 반복이나 마스크로 처리해요. -O3와 -march=native로 켜고 -fopt-info-vec 보고서나 어셈블리로 확인해요.<br><sub>Compiled as-is, c[i] = a[i] + b[i] adds one element per instruction, 16 times. An AVX2 256-bit register holds 8 floats, so one vaddps adds 8 at once and two are enough. This requires iterations to be independent (c[i] = c[i-1] + a[i] cannot be vectorized) and the arrays not to overlap (promised with restrict in C). When n isn’t a multiple of 8, a scalar tail loop or masking handles the rest. Enable it with -O3 and -march=native, and confirm with the -fopt-info-vec report or the assembly.</sub> |

## 뒷단: 기계어로 · Back end: down to machine code

중간 표현을 실제 CPU 명령으로 바꾸고 다듬어요.  
*Turning IR into real CPU instructions and polishing them.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **명령어 선택**<br><sub>Instruction selection</sub> | 중간 표현의 트리를 CPU 명령 “타일”로 덮어 기계어로 바꿔요. 여러 노드를 한 번에 처리하는 명령을 고르면 코드가 짧아져요.<br><sub>Cover the IR tree with CPU instruction “tiles” to produce machine code; instructions that handle several nodes at once make it shorter.</sub> | load(add(p, 8)) + 1 → x86의 주소 모드로 mov rax, [rdi + 8]; add rax, 1 두 줄. 비용이 가장 작은 덮기를 동적 계획법이나 최대 먹기로 찾아요. CPU마다 고르는 명령이 달라요(x86 lea, ARM 곱셈-덧셈). LLVM SelectionDAG·GlobalISel, 명령 설명은 TableGen.<br><sub>load(add(p, 8)) + 1 becomes two x86 instructions via an addressing mode: mov rax, [rdi + 8]; add rax, 1. The cheapest covering is found by dynamic programming or maximal munch. Choices differ per CPU (x86 lea, ARM multiply-add). LLVM uses SelectionDAG or GlobalISel with TableGen descriptions.</sub> |
| **레지스터 할당**<br><sub>Register allocation</sub> | 무한한 임시 변수를 몇 개 안 되는 실제 레지스터에 배정해요. 동시에 살아 있는 변수끼리 다른 레지스터를 쓰도록 그래프를 색칠해요.<br><sub>Map unlimited temporaries onto a handful of real registers, coloring a graph so that variables live at the same time get different registers.</sub> | 간섭 그래프에서 이웃끼리 다른 색 = 다른 레지스터. 색이 모자라면 일부를 스택으로 내려(spill) 메모리 읽기·쓰기가 늘어요. 차이틴의 그래프 색칠, JIT이 쓰는 빠른 선형 스캔, LLVM greedy 할당기. x86-64는 범용 레지스터 16개, ARM64는 31개.<br><sub>In the interference graph, neighbors get different colors, meaning different registers. With too few colors, some values spill to the stack, adding memory traffic. Approaches: Chaitin’s graph coloring, the fast linear scan used by JITs, LLVM’s greedy allocator. x86-64 has 16 general-purpose registers; ARM64 has 31.</sub> |
| **명령어 스케줄링**<br><sub>Instruction scheduling</sub> | 결과가 늦게 나오는 명령(메모리 읽기 등) 뒤에 독립된 명령을 끼워 넣어 파이프라인이 멈추는 시간을 줄여요.<br><sub>Fill the wait after slow instructions (such as memory loads) with independent work so the pipeline stalls less.</sub> | 예: load 두 개를 앞당겨 겹치면 8사이클 → 5사이클. 비순차 실행 CPU는 하드웨어가 일부를 대신하지만, 순차 실행 코어(많은 ARM·임베디드), GPU, VLIW에서는 컴파일러가 중요해요. 의존성 그래프 위의 리스트 스케줄링이 기본이에요.<br><sub>Overlapping two loads turns 8 cycles into 5. Out-of-order CPUs partly do this in hardware, but in-order cores (many ARM and embedded chips), GPUs and VLIW designs depend on the compiler. List scheduling over a dependency graph is the standard method.</sub> |
| **핍홀 최적화**<br><sub>Peephole optimization</sub> | 몇 줄짜리 창을 기계어 위로 미끄러뜨리며 알려진 비효율 패턴을 더 나은 것으로 바꿔요.<br><sub>Slide a small window over the machine code and replace known inefficient patterns with better ones.</sub> | mov eax, 0 → xor eax, eax(더 짧음), imul ×8 → shl 3, 저장 직후 같은 값 다시 읽기 삭제, 다음 줄로 가는 jmp 삭제. 단순하지만 효과적이라 거의 모든 컴파일러의 마지막 단계에 있어요. Compiler Explorer(godbolt.org)에서 실제 출력을 확인해 보세요.<br><sub>mov eax, 0 becomes xor eax, eax (shorter), multiplying by 8 becomes shl 3, a reload right after a store goes away, and a jmp to the next line is dropped. Simple but effective, it runs near the end of almost every compiler. See real output on Compiler Explorer (godbolt.org).</sub> |

## 실제 컴파일러 · Real-world compilers

오늘날의 컴파일러 인프라와 JIT이에요.  
*Today’s compiler infrastructure and JITs.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **LLVM 구조**<br><sub>The LLVM architecture</sub> | 언어마다 앞단이 공통 중간 표현(LLVM IR)을 만들고, 공용 최적화 패스와 CPU별 뒷단이 나머지를 맡는 구조예요.<br><sub>Each language’s front end emits a shared intermediate form (LLVM IR); common optimization passes and per-CPU back ends do the rest.</sub> | Clang(C/C++), rustc, Swift, Zig, Julia가 LLVM IR을 만들고, -O2에서 mem2reg·inline·GVN·LICM·벡터화 등 수십 개 패스를 거쳐 x86-64·ARM64·RISC-V·WebAssembly로 내려가요. 언어 M개 × CPU N개를 M + N개 구현으로 줄여요. GCC(GIMPLE·RTL), Cranelift, MLIR도 비슷한 구조예요.<br><sub>Clang (C/C++), rustc, Swift, Zig and Julia emit LLVM IR; at -O2 it passes through dozens of passes (mem2reg, inline, GVN, LICM, vectorization) before reaching x86-64, ARM64, RISC-V or WebAssembly. M languages × N CPUs need only M + N implementations. GCC (GIMPLE, RTL), Cranelift and MLIR share the shape.</sub> |
| **JIT과 투기적 최적화**<br><sub>JITs and speculative optimization</sub> | JIT은 실행하며 관찰한 타입·모양을 “가정”으로 삼아 빠른 기계어를 만들고, 가정이 깨지면 인터프리터로 되돌아가요(탈최적화).<br><sub>A JIT compiles fast machine code under assumptions about the types and shapes it has observed, falling back to the interpreter when an assumption breaks (deoptimization).</sub> | 인라인 캐시: 객체 모양(hidden class)이 S1인지 확인하고 고정 오프셋에서 필드를 읽어요. 다른 모양이 오면 탈최적화 후 다시 최적화. V8: Ignition → Sparkplug → Maglev → TurboFan, 자바 HotSpot: 인터프리터 → C1 → C2, PyPy, LuaJIT. 객체 필드를 같은 순서로 만들면 빨라져요.<br><sub>An inline cache checks that an object has hidden class S1 and reads the field at a fixed offset; a different shape triggers deoptimization and later reoptimization. V8 runs Ignition → Sparkplug → Maglev → TurboFan; Java HotSpot runs interpreter → C1 → C2; PyPy and LuaJIT work similarly. Creating objects with fields in a consistent order keeps them fast.</sub> |
| **프로필 기반 최적화 (PGO)**<br><sub>Profile-guided optimization (PGO)</sub> | 프로그램을 실제처럼 실행해 모은 통계(어느 분기·함수가 자주 쓰이는지)를 컴파일러에 알려 줘서, 추측 대신 데이터로 최적화하게 해요.<br><sub>PGO feeds statistics gathered from realistic runs, such as which branches and functions are hot, back to the compiler so it optimizes from data rather than guesses.</sub> | 프로필이 없으면 컴파일러는 if (err) 같은 분기가 얼마나 자주 실행될지 짐작해야 해요. PGO는 먼저 계측 코드를 넣어 빌드하고(-fprofile-generate), 대표적인 작업으로 실행해 간선·함수별 실행 횟수를 모은 뒤, 그 프로필로 다시 빌드해요(-fprofile-use). 그러면 자주 가는 경로를 메모리에 붙여 배치하고 드문 오류 처리 코드는 차가운 영역으로 보내며, 뜨거운 호출은 인라인하고 레지스터 할당도 뜨거운 코드에 집중해요. 보통 10~20% 빨라지고, AutoFDO는 계측 없이 운영 서버의 perf 샘플링 프로필을 써요. 크롬, 파이어폭스, 클랭 자신, Go 1.21 이상이 PGO를 써요.<br><sub>Without a profile the compiler has to guess how often a branch such as if (err) is taken. PGO first builds with instrumentation (-fprofile-generate), runs a representative workload to count executions per edge and function, then rebuilds with that profile (-fprofile-use). The hot path is laid out contiguously while rare error handling moves to a cold section, hot calls are inlined and register allocation focuses on hot code. Gains of 10–20% are typical, and AutoFDO skips instrumentation by using perf sampling profiles from production. Chrome, Firefox, Clang itself and Go 1.21+ use PGO.</sub> |
