## 플랫폼과 앱 구조 · Platforms and app structure

앱이 어떻게 만들어지고, 실행되고, 서로 격리되는지예요.  
*How apps are built, run and kept apart.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **네이티브와 크로스플랫폼**<br><sub>Native and cross-platform</sub> | 네이티브 앱은 iOS는 Swift, Android는 Kotlin으로 따로 만들고, 크로스플랫폼은 한 코드로 두 플랫폼을 함께 만들어요.<br><sub>Native apps are built separately per platform (Swift for iOS, Kotlin for Android); cross-platform frameworks build both from one codebase.</sub> | Flutter는 Dart 위젯을 자체 엔진(Impeller)으로 직접 그려 어디서나 똑같이 보이고, React Native는 JavaScript 로직으로 진짜 네이티브 컴포넌트를 조종해요. Kotlin Multiplatform은 비즈니스 로직만 공유하고 UI는 각 플랫폼에 맡겨요. 웹 앱(PWA)은 설치 없이 열리지만 기기 기능 접근이 제한적이에요. 성능, 팀의 기술, 필요한 기기 기능, 출시 속도를 보고 골라요.<br><sub>Flutter paints Dart widgets with its own engine (Impeller), so it looks identical everywhere; React Native drives real native components from JavaScript. Kotlin Multiplatform shares business logic while each platform keeps its own UI. Web apps (PWAs) need no install but get limited device access. Choose by performance, team skills, device needs and time to market.</sub> |
| **앱 생명주기**<br><sub>App lifecycle</sub> | 앱 화면은 생성 → 시작 → 재개 → 일시 정지 → 정지 → 파괴 단계를 오가고, OS가 단계마다 콜백을 불러 줘요.<br><sub>A screen moves through created, started, resumed, paused, stopped and destroyed, and the OS calls back at each step.</sub> | Android Activity는 onCreate, onStart, onResume, onPause, onStop, onDestroy를 받아요. 전화가 오면 일시 정지, 홈으로 나가면 정지, 메모리가 부족하면 OS가 프로세스를 통째로 정리할 수도 있어서 상태는 미리 저장해야 해요. 화면 회전 같은 구성 변경도 Activity를 새로 만들어요. iOS는 Active, Inactive, Background, Suspended 상태가 같은 역할을 해요.<br><sub>An Android Activity receives onCreate, onStart, onResume, onPause, onStop and onDestroy. A phone call pauses it, going home stops it, and under memory pressure the OS may kill the whole process, so state must be saved ahead of time. Configuration changes such as rotation also recreate the Activity. On iOS the active, inactive, background and suspended states play the same role.</sub> |
| **샌드박스와 권한**<br><sub>Sandboxing and permissions</sub> | 모바일 앱은 저마다 격리된 상자(샌드박스) 안에서 돌고, 카메라·위치 같은 민감한 기능은 사용자가 허락해야 쓸 수 있어요.<br><sub>Every mobile app runs in an isolated sandbox, and sensitive features such as the camera or location need the user’s permission.</sub> | Android는 앱마다 다른 리눅스 사용자 ID와 전용 폴더를 주고, iOS도 앱 컨테이너 밖을 읽지 못하게 막아요. 권한은 Manifest나 Info.plist에 선언한 뒤 실행 중에 물어봐요(런타임 권한). 위치는 대략·정확, 사진은 고른 것만, “이번만 허용”처럼 범위를 좁힐 수 있고 사용자는 언제든 철회할 수 있어요. 다른 앱과의 공유는 공유 시트, 콘텐츠 제공자, 인텐트 같은 OS 통로로만 해요.<br><sub>Android gives each app its own Linux user ID and private folder; iOS likewise blocks reads outside the app’s container. Permissions are declared in the Manifest or Info.plist and then requested at runtime. Scope can be narrowed (approximate location, selected photos, allow once) and the user can revoke access at any time. Sharing with other apps goes only through OS channels such as the share sheet, content providers and intents.</sub> |
| **빌드·서명·배포**<br><sub>Build, sign and ship</sub> | 소스 코드를 기기용으로 컴파일해 패키지(AAB, IPA)로 묶고, 개발자 키로 서명한 뒤 스토어 심사를 거쳐 배포해요.<br><sub>Source is compiled for the device, bundled into a package (AAB, IPA), signed with the developer’s key and released through store review.</sub> | Android는 Kotlin을 DEX 바이트코드로, iOS는 Swift를 ARM64 기계어로 컴파일해요. 서명은 누가 만들었는지와 변조되지 않았음을 증명해서 한 바이트만 바뀌어도 설치가 거부돼요. 업데이트는 같은 키로 서명하고 버전 번호를 올려야 하며, Play 앱 서명이나 Apple 인증서·프로비저닝 프로파일이 키를 관리해요. Fastlane, Xcode Cloud, GitHub Actions 같은 CI로 이 과정을 자동화해요.<br><sub>Android compiles Kotlin to DEX bytecode; iOS compiles Swift to ARM64 machine code. The signature proves who built the app and that it hasn’t been altered: change one byte and installation is refused. Updates must carry the same key and a higher version number, with Play App Signing or Apple certificates and provisioning profiles managing the keys. CI tools such as Fastlane, Xcode Cloud and GitHub Actions automate the pipeline.</sub> |
| **메인 스레드와 프레임**<br><sub>Main thread and frames</sub> | 화면은 메인(UI) 스레드 하나가 그려요. 60Hz 화면이면 16.7ms 안에 한 프레임을 끝내야 버벅이지 않아요.<br><sub>A single main (UI) thread draws the screen; on a 60 Hz display each frame must finish within 16.7 ms to stay smooth.</sub> | 네트워크, 디스크, 이미지 디코딩, 큰 JSON 파싱을 메인에서 하면 프레임을 놓쳐 화면이 멈칫해요(jank). 입력에 5초 넘게 응답하지 않으면 Android는 ANR 창을 띄우고, iOS는 오래 멈춘 앱을 워치독이 종료해요. 무거운 일은 백그라운드 스레드나 코루틴에서 하고 결과만 메인으로 보내 UI를 고쳐요. 120Hz 화면에서는 예산이 8.3ms로 줄어요.<br><sub>Doing network, disk, image decoding or big JSON parsing on the main thread drops frames and causes visible stutter (jank). If input goes unanswered for five seconds Android shows an ANR dialog, and iOS’s watchdog terminates apps that hang too long. Heavy work belongs on background threads or coroutines, with only the result posted back to update the UI. At 120 Hz the budget shrinks to 8.3 ms.</sub> |

## 화면 그리기 · Drawing the UI

레이아웃부터 터치와 애니메이션까지, 화면이 만들어지는 과정이에요.  
*From layout to touch and animation: how a screen comes together.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **레이아웃: 측정과 배치**<br><sub>Layout: measure and place</sub> | UI 트리는 부모가 제약을 내려보내고, 자식이 크기를 정해 올리고, 부모가 위치를 정한 뒤에야 그려져요.<br><sub>A UI tree is drawn only after parents pass constraints down, children report sizes up and parents assign positions.</sub> | Android View는 measure → layout → draw 순서로, Flutter는 “제약은 내려가고 크기는 올라오고 위치는 부모가 정한다”는 규칙으로, Compose는 자식을 한 번만 측정한다는 규칙으로 동작해요. 트리가 깊거나 자식을 여러 번 측정하면(중첩된 가중치, 내재 크기 계산) 프레임 시간이 늘어요. 그래서 평평한 레이아웃(ConstraintLayout)과 고정 크기 지정이 성능에 도움이 돼요. iOS는 Auto Layout이 제약식을 풀어 위치를 계산해요.<br><sub>Android Views go measure → layout → draw; Flutter’s rule is “constraints go down, sizes go up, parents set position”; Compose measures each child only once. Deep trees and repeated measuring (nested weights, intrinsic sizes) inflate frame time, so flat layouts such as ConstraintLayout and fixed sizes help performance. On iOS, Auto Layout solves a system of constraints to place views.</sub> |
| **선언형 UI**<br><sub>Declarative UI</sub> | “상태가 이러면 화면은 이렇게”라고 적으면, 상태가 바뀔 때 프레임워크가 필요한 부분만 다시 그려 줘요.<br><sub>You describe what the screen looks like for a given state, and when the state changes the framework redraws only what depends on it.</sub> | UI = f(상태). Jetpack Compose는 재구성(recomposition), SwiftUI는 body 재평가, Flutter는 build 재호출로 바뀐 상태를 읽는 부분만 갱신해요. 명령형 방식은 데이터가 바뀔 때마다 뷰를 찾아 setText처럼 직접 고쳐야 해서 하나만 빠뜨려도 화면과 데이터가 어긋나요. 대신 상태를 어디에 두고 얼마나 자주 바꾸는지가 성능을 좌우해요.<br><sub>UI = f(state). Jetpack Compose recomposes, SwiftUI re-evaluates body and Flutter calls build again, touching only the parts that read the changed state. The imperative style finds views and patches them by hand (setText), and missing a single spot leaves the screen out of sync with the data. In exchange, where state lives and how often it changes now drives performance.</sub> |
| **리스트 재활용**<br><sub>List recycling</sub> | 긴 목록도 화면에 보이는 몇 줄만 뷰로 만들고, 스크롤로 밖에 나간 뷰를 새 데이터로 다시 써요.<br><sub>Even for a long list, only the visible rows get views; rows that scroll off are reused with new data.</sub> | 천 개 항목에 뷰 천 개를 만들면 메모리와 생성 시간이 폭발해요. RecyclerView는 ViewHolder를 재사용하며 onBindViewHolder에서 데이터만 바꿔 끼우고, Compose LazyColumn, iOS UICollectionView, Flutter ListView.builder도 같은 원리예요. 바인드 중엔 무거운 작업을 피하고, 항목마다 고유 key를 주면 DiffUtil이나 diffable data source가 바뀐 줄만 갱신해요.<br><sub>A thousand items with a thousand views would explode memory and setup time. RecyclerView reuses ViewHolders and only rebinds data in onBindViewHolder; Compose LazyColumn, iOS UICollectionView and Flutter’s ListView.builder work the same way. Keep binding cheap, and give each item a stable key so DiffUtil or diffable data sources update only the rows that changed.</sub> |
| **화면 밀도와 단위**<br><sub>Screen density and units</sub> | 화면마다 1인치에 든 픽셀 수(dpi)가 달라서, 크기는 픽셀 대신 밀도와 무관한 단위(dp, pt)로 정해요.<br><sub>Screens pack different numbers of pixels per inch, so sizes are given in density-independent units (dp, pt) rather than pixels.</sub> | px = dp × (dpi ÷ 160). 48dp 버튼은 1x 화면에서 48px, 3x 화면에서 144px이지만 실제 크기는 같아요. 이미지는 1x·2x·3x 여러 벌이나 벡터로 넣고, 글자는 sp(Android)나 Dynamic Type(iOS)으로 사용자 글꼴 크기 설정을 따라요. 터치 영역은 최소 48dp(Android), 44pt(iOS)를 권장해요.<br><sub>px = dp × (dpi ÷ 160): a 48 dp button is 48 px on a 1x screen and 144 px on a 3x screen, yet the same physical size. Images ship in 1x/2x/3x sets or as vectors, and text uses sp (Android) or Dynamic Type (iOS) to honor the user’s font size. Touch targets should be at least 48 dp on Android and 44 pt on iOS.</sub> |
| **터치와 제스처**<br><sub>Touch and gestures</sub> | 손가락이 닿으면 히트 테스트로 그 아래의 뷰를 찾고, 움직임을 보고 탭인지 스크롤인지 판정해요.<br><sub>When a finger lands, hit testing finds the view underneath, and the movement decides whether it is a tap or a scroll.</sub> | 터치는 DOWN → MOVE → UP 이벤트로 오고, 터치 슬롭(약 8dp)보다 적게 움직이면 아직 탭 후보예요. 그 이상 움직이면 스크롤하는 부모가 이벤트를 가로채고(intercept) 버튼에는 CANCEL이 가요. 손을 뗄 때의 속도로 플링 애니메이션이 이어져요. GestureDetector, UIGestureRecognizer가 탭·길게 누르기·스와이프·핀치를 구분해 줘요.<br><sub>Touches arrive as DOWN, MOVE and UP events; moving less than the touch slop (about 8 dp) keeps it a possible tap. Beyond that, a scrolling parent intercepts the stream and the button receives CANCEL. The release velocity carries into a fling animation. GestureDetector and UIGestureRecognizer tell taps, long presses, swipes and pinches apart.</sub> |
| **애니메이션과 이징**<br><sub>Animation and easing</sub> | 애니메이션은 시간에 따른 값의 곡선이에요. 매 프레임 곡선에서 값을 읽어 위치·크기·투명도를 바꿔요.<br><sub>An animation is a curve of values over time; each frame samples the curve to set position, size or opacity.</sub> | linear는 기계적으로 보여서 보통 ease-out(들어올 때), ease-in(나갈 때), 스프링을 써요. 스프링은 시간이 아니라 강성·감쇠로 정의돼 손가락을 따라가다 놓았을 때 자연스럽고 도중에 끊겨도 이어져요. 레이아웃을 다시 계산하는 속성보다 transform과 opacity를 움직이면 GPU 합성만으로 처리돼 부드러워요. Compose의 animate\*AsState, SwiftUI의 withAnimation, Lottie가 대표 도구예요.<br><sub>Linear motion looks mechanical, so interfaces favor ease-out for entering, ease-in for leaving, and springs. Springs are defined by stiffness and damping rather than duration, so they feel natural after a drag and stay smooth when interrupted. Animating transform and opacity lets the GPU compositor do the work instead of re-running layout. Compose’s animate\*AsState, SwiftUI’s withAnimation and Lottie are common tools.</sub> |

## 상태와 아키텍처 · State and architecture

데이터가 화면까지 흐르는 길을 정리하는 방법이에요.  
*Ways to organize how data reaches the screen.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **단방향 데이터 흐름**<br><sub>Unidirectional data flow</sub> | 상태는 한곳에서만 바꾸고, UI는 그 상태를 그리기만 하며 사용자 동작은 이벤트로 올려 보내요.<br><sub>State changes in exactly one place, the UI only renders it, and user actions travel up as events.</sub> | View → 이벤트 → ViewModel → 새 상태 → View로 데이터가 한 방향으로만 흘러 “누가 화면을 바꿨지?”를 쉽게 추적해요. 로딩·데이터·오류를 UiState 하나로 묶으면 화면이 불가능한 조합에 빠지지 않아요. 여러 위젯이 공유하는 상태는 공통 부모로 끌어올리고(state hoisting), 위젯은 상태를 받고 콜백을 내보내는 형태로 만들어요. Redux, MVI, TCA(The Composable Architecture)가 같은 생각이에요.<br><sub>Data flows one way (View → event → ViewModel → new state → View), so “who changed the screen?” is easy to answer. Bundling loading, data and error into a single UiState keeps the screen out of impossible combinations. State shared by several widgets is hoisted to a common parent, and widgets take state in and send callbacks out. Redux, MVI and The Composable Architecture share the same idea.</sub> |
| **MVVM과 ViewModel**<br><sub>MVVM and the ViewModel</sub> | ViewModel이 화면의 데이터와 로직을 들고, 화면(View)은 그것을 관찰해 그리기만 해요.<br><sub>The ViewModel holds the screen’s data and logic; the View just observes it and draws.</sub> | Android ViewModel은 화면 회전 같은 구성 변경에도 살아남아 데이터를 다시 받지 않아요. ViewModel은 View를 참조하지 않으니 메모리 누수가 없고 기기 없이 단위 테스트할 수 있어요. 프로세스가 통째로 정리될 때를 대비해 작은 값은 SavedStateHandle에 저장해요. MVC → MVP → MVVM → MVI는 화면 로직을 화면 밖으로 꺼내는 방향으로 발전해 왔어요.<br><sub>An Android ViewModel survives configuration changes such as rotation, so data isn’t reloaded. Since it never references the View, it can’t leak it and can be unit-tested without a device. Small values go in SavedStateHandle to survive process death. MVC → MVP → MVVM → MVI has steadily moved screen logic out of the screen.</sub> |
| **내비게이션과 백 스택**<br><sub>Navigation and the back stack</sub> | 화면을 열면 스택에 쌓고(push), 뒤로 가면 맨 위를 꺼내요(pop). 딥 링크로 열어도 자연스러운 스택을 만들어 줘요.<br><sub>Opening a screen pushes it onto a stack and back pops the top; deep links get a sensible stack built for them.</sub> | “상품 목록 → 상세”처럼 쌓인 순서대로 뒤로 가기가 동작해요. 알림이나 링크(shop://product/42, 유니버설 링크·앱 링크)로 상세 화면을 바로 열면 그 밑에 홈을 깔아 뒤로 가기가 앱 밖으로 튀지 않게 해요. 하단 탭마다 별도 스택을 두고, 화면 사이엔 객체 대신 ID 같은 작은 값만 넘겨요. Android Navigation, iOS NavigationStack, Flutter go\_router가 이 일을 해요.<br><sub>Back follows the order screens were stacked, such as list → detail. When a notification or link (shop://product/42, universal or app links) opens a detail screen directly, a home screen is placed beneath it so back doesn’t drop out of the app. Each bottom tab keeps its own stack, and screens pass small values such as IDs rather than whole objects. Android Navigation, iOS NavigationStack and Flutter’s go\_router handle this.</sub> |
| **코루틴과 async/await**<br><sub>Coroutines and async/await</sub> | 기다리는 동안 스레드를 붙잡지 않고 잠시 멈췄다가, 결과가 오면 멈춘 곳부터 이어서 실행하는 비동기 코드예요.<br><sub>Async code that pauses without holding a thread while it waits, then resumes right where it left off when the result arrives.</sub> | suspend 함수나 await은 네트워크 응답을 기다리는 동안 메인 스레드를 비켜 줘서 화면은 계속 그려져요. 코드가 위에서 아래로 읽혀 콜백이 안쪽으로 파고드는 “콜백 지옥”이 없어요. 구조적 동시성 덕분에 화면이 닫히면 viewModelScope나 Task가 진행 중인 작업을 함께 취소해요. Dispatchers.IO 같은 디스패처로 어느 스레드에서 실행할지 정해요.<br><sub>A suspend function or await steps off the main thread while the network responds, so the screen keeps drawing. The code reads top to bottom, with no callbacks nesting ever deeper (“callback hell”). Structured concurrency lets viewModelScope or a Task cancel in-flight work when the screen closes. Dispatchers such as Dispatchers.IO choose which threads the work runs on.</sub> |
| **반응형 스트림**<br><sub>Reactive streams</sub> | 시간에 따라 오는 값의 흐름(스트림)을 연산자로 거르고 바꾸고 합쳐서 처리해요.<br><sub>Streams of values arriving over time are filtered, transformed and combined with operators.</sub> | 검색창 입력에 debounce(300ms)를 걸면 타이핑이 멈췄을 때만 요청하고, switchMap(flatMapLatest)은 새 입력이 오면 이전 요청을 취소해 늦게 온 옛 결과가 화면을 덮지 않게 해요. combine으로 여러 스트림을 합치고, distinctUntilChanged로 같은 값을 거를 수 있어요. Kotlin Flow, Swift Combine, RxJava·RxSwift, Dart Stream이 대표적이에요. 구독을 해제하지 않으면 누수가 생겨요.<br><sub>Applying debounce(300 ms) to a search box fires a request only when typing pauses, and switchMap (flatMapLatest) cancels the previous request when new input arrives, so stale results never overwrite fresh ones. combine merges several streams and distinctUntilChanged drops repeats. Kotlin Flow, Swift Combine, RxJava/RxSwift and Dart Streams are the main libraries. Forgetting to unsubscribe causes leaks.</sub> |

## 데이터와 네트워크 · Data and network

기기 안에 저장하고, 불안정한 망에서 주고받는 법이에요.  
*Storing on the device and talking over unreliable networks.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **로컬 저장소**<br><sub>Local storage</sub> | 저장할 데이터의 크기와 성격에 따라 키-값 저장소, 데이터베이스, 파일, 보안 저장소 중에서 골라요.<br><sub>Depending on size and kind, data goes in a key–value store, a database, files or secure storage.</sub> | 작은 설정값은 DataStore·UserDefaults, 많고 검색해야 하는 데이터는 SQLite(Room, Core Data, SwiftData), 사진·동영상 같은 큰 파일은 앱 전용 폴더나 캐시 폴더에 둬요. 비밀번호와 토큰은 Android Keystore의 키로 암호화하거나 iOS Keychain에 넣어요. 캐시 폴더는 공간이 부족하면 OS가 지울 수 있고 앱을 지우면 모두 사라지니, 중요한 데이터는 서버에도 백업해요.<br><sub>Small settings belong in DataStore or UserDefaults, large queryable data in SQLite (Room, Core Data, SwiftData), and big files such as photos and video in the app’s files or cache directory. Passwords and tokens are encrypted with an Android Keystore key or kept in the iOS Keychain. The OS may clear the cache directory when space runs low and uninstalling wipes everything, so important data should also live on a server.</sub> |
| **오프라인 우선과 동기화**<br><sub>Offline-first and sync</sub> | 화면은 로컬 DB를 기준으로 그리고, 서버와의 동기화는 뒤에서 처리해서 연결이 끊겨도 앱이 동작해요.<br><sub>The screen renders from a local database and syncing with the server happens in the background, so the app works without a connection.</sub> | 쓰기는 먼저 로컬 DB에 반영해 화면이 즉시 바뀌고, 변경 사항은 대기열(outbox)에 쌓였다가 연결되면 순서대로 서버로 가요. 다른 기기에서 같은 데이터를 고쳤다면 마지막 쓰기 우선, 필드별 병합, CRDT 같은 규칙으로 충돌을 풀어요. WorkManager 같은 작업 예약기가 연결이 돌아오면 재시도해요. 지하철이나 비행기에서도 쓸 수 있고, 온라인에서도 기다림이 줄어요.<br><sub>Writes land in the local database first so the screen updates instantly, and changes wait in an outbox until a connection returns and they are sent in order. If another device edited the same data, rules such as last-write-wins, field-level merges or CRDTs resolve the conflict. A scheduler like WorkManager retries once the network is back. The app works on the subway or a plane and feels faster online too.</sub> |
| **네트워크 요청과 재시도**<br><sub>Requests and retries</sub> | 모바일 망은 자주 느려지고 끊겨요. 타임아웃, 간격을 늘려 가는 재시도, HTTP 캐시로 버텨요.<br><sub>Mobile networks slow down and drop often; timeouts, retries with growing gaps and HTTP caching keep apps working.</sub> | 실패하면 1초, 2초, 4초처럼 간격을 두 배씩 늘려 재시도하고(지수 백오프), 무작위 지터를 더해 수많은 기기가 한꺼번에 몰리지 않게 해요. 자동 재시도는 GET처럼 여러 번 보내도 안전한(멱등) 요청에만 해요. ETag와 If-None-Match로 바뀌지 않은 응답은 본문 없는 304로 받아 데이터와 배터리를 아껴요. gzip 압축, 페이지 나누기, 필요한 필드만 받기도 중요해요.<br><sub>Failed requests retry after 1, 2, 4 seconds and so on (exponential backoff), with random jitter so millions of devices don’t retry in lockstep. Only idempotent requests such as GET are retried automatically. ETag and If-None-Match turn unchanged responses into a bodiless 304, saving data and battery. gzip compression, pagination and fetching only the needed fields matter as well.</sub> |
| **이미지 로딩과 캐시**<br><sub>Image loading and caching</sub> | 사진은 보일 크기에 맞춰 줄여서 디코딩하고, 메모리 → 디스크 → 네트워크 순서로 찾아 다시 받지 않아요.<br><sub>Photos are decoded at the size they will be shown and looked up in memory, then disk, then the network, so they aren’t downloaded twice.</sub> | 4000×3000 사진을 그대로 풀면 픽셀당 4바이트로 48MB예요. 400×300 뷰에 맞춰 1/8로 줄여 디코딩하면 1MB도 안 돼요. 메모리 캐시는 LRU로 오래 안 쓴 것부터 버리고, 디스크 캐시는 앱을 다시 켜도 남아요. 리스트가 재활용되면 이전 요청을 취소해야 엉뚱한 사진이 뜨지 않아요. Glide, Coil, Kingfisher, SDWebImage가 이 일을 대신해요.<br><sub>A 4000×3000 photo decoded at full size takes 48 MB at 4 bytes per pixel; downsampled by 8 for a 400×300 view it is under 1 MB. The memory cache evicts least recently used images, while the disk cache survives restarts. When a list row is recycled, its old request must be cancelled or the wrong photo appears. Glide, Coil, Kingfisher and SDWebImage handle all of this.</sub> |
| **푸시 알림**<br><sub>Push notifications</sub> | 서버가 보낸 메시지를 애플(APNs)·구글(FCM)의 푸시 서버가 기기까지 전달해, 앱이 꺼져 있어도 알림이 떠요.<br><sub>Apple’s (APNs) and Google’s (FCM) push services deliver a server’s message to the device, so notifications appear even when the app is closed.</sub> | 앱은 OS에 등록해 기기 토큰을 받고, 그 토큰을 우리 서버에 보내 사용자와 묶어 둬요. 보낼 일이 생기면 서버가 토큰과 내용을 APNs·FCM에 보내고, 푸시 서버는 기기가 유지하는 상시 연결 하나로 전달해요. 앱마다 연결을 따로 열지 않으니 배터리가 절약돼요. 알림 권한이 필요하고, 토큰은 바뀔 수 있어 갱신되면 서버에 다시 알려야 해요.<br><sub>The app registers with the OS to get a device token and sends it to our server, tied to the user. When something happens, the server sends the token and message to APNs or FCM, which delivers it over the single always-on connection the device keeps. Because apps don’t each hold a connection open, battery is saved. Notification permission is required, and tokens can change, so refreshed tokens must be re-sent.</sub> |

## 성능·품질·출시 · Performance, quality and release

배터리와 메모리를 아끼고, 테스트하고, 안전하게 내보내는 법이에요.  
*Saving battery and memory, then testing and shipping safely.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **배터리와 백그라운드 작업**<br><sub>Battery and background work</sub> | 셀룰러 무선은 전송 후에도 몇 초간 고전력으로 남아서, 요청을 흩어 보내면 배터리가 빨리 닳아요.<br><sub>The cellular radio stays in high power for seconds after each transfer, so scattered requests drain the battery quickly.</sub> | 작은 요청을 자주 보내면 무선이 잠들 틈이 없어요. 요청을 모아 한 번에 보내고, 급하지 않은 일은 WorkManager(Android)나 BGTaskScheduler(iOS)에 맡기면 충전 중이나 와이파이일 때 실행돼요. Android 잠자기(Doze)와 iOS 백그라운드 제한은 깨움을 정해진 창으로 모아요. 화면, GPS, 무선이 가장 큰 소비원이라 위치는 필요한 정확도만 요청해요.<br><sub>Small, frequent requests never let the radio sleep. Batch requests together, and hand deferrable work to WorkManager (Android) or BGTaskScheduler (iOS) so it runs while charging or on Wi-Fi. Android’s Doze and iOS background limits fold wake-ups into maintenance windows. The screen, GPS and radios are the biggest consumers, so request only the location accuracy you need.</sub> |
| **모바일 메모리 관리**<br><sub>Mobile memory management</sub> | 메모리가 모자라면 OS가 우선순위가 낮은 백그라운드 앱부터 정리해요. 앱은 누수 없이 가볍게 써야 해요.<br><sub>When memory runs short the OS kills low-priority background apps first, so apps must stay lean and leak-free.</sub> | 보이는 앱 > 서비스 > 캐시된 앱 순으로 우선순위가 높고, 메모리가 부족하면 가장 오래 안 쓴 캐시 앱부터 Android lmkd나 iOS jetsam이 정리해요. 정리돼도 사용자가 눈치채지 못하게 상태를 저장·복원해요. 닫힌 화면을 정적 필드나 리스너가 붙잡으면 GC가 치우지 못하는 누수가 생겨요. Android는 GC, iOS(Swift)는 ARC 참조 카운트라서 순환 참조는 weak로 끊어요.<br><sub>Visible apps outrank services, which outrank cached apps; under pressure Android’s lmkd or iOS’s jetsam reclaims the least recently used cached app first. Save and restore state so a kill goes unnoticed. A closed screen held by a static field or listener can’t be collected: a leak. Android relies on garbage collection while Swift on iOS uses ARC reference counting, so cycles must be broken with weak references.</sub> |
| **모바일 테스트**<br><sub>Mobile testing</sub> | 빠른 단위 테스트를 많이, 통합 테스트를 적당히, 느린 UI 테스트는 핵심 흐름만 두는 피라미드로 쌓아요.<br><sub>A pyramid: many fast unit tests, a moderate layer of integration tests and only a few slow UI tests for key flows.</sub> | 단위 테스트는 ViewModel과 로직을 기기 없이 몇 초 만에 돌리고, UI 테스트(Espresso, XCUITest, Compose 테스트)는 실제 화면을 탭해 확인하지만 느리고 잘 깨져요. 화면 크기, 폴더블, OS 버전 조합이 수백 가지라 Firebase Test Lab 같은 클라우드 기기 팜에서 병렬로 돌려요. 스크린샷 테스트로 UI 회귀를 잡고, TestFlight나 내부 테스트 트랙으로 실제 사용을 검증해요.<br><sub>Unit tests run ViewModels and logic in seconds without a device; UI tests (Espresso, XCUITest, Compose testing) tap the real screen but are slow and flaky. With hundreds of combinations of screen sizes, foldables and OS versions, teams run tests in parallel on cloud device farms such as Firebase Test Lab. Screenshot tests catch UI regressions, and TestFlight or internal testing tracks verify real-world use.</sub> |
| **단계적 출시와 모니터링**<br><sub>Staged rollout and monitoring</sub> | 새 버전을 일부 사용자에게만 먼저 내보내고, 크래시 지표를 보며 조금씩 넓혀요. 문제가 보이면 멈춰요.<br><sub>New versions go to a small share of users first and widen as crash metrics stay healthy; trouble halts the rollout.</sub> | 앱은 웹처럼 즉시 롤백할 수 없어서 1% → 5% → 20% → 100%로 넓혀 가며 크래시 없는 사용자 비율을 지켜봐요. Crashlytics, Sentry가 스택 트레이스를 기기·OS·버전별로 모아 원인을 찾게 해 줘요. 원격 기능 플래그로 문제 기능만 끄면 새 빌드 없이 바로 회복할 수 있어요. 고친 버전도 다시 단계적으로 배포해요.<br><sub>Apps can’t roll back instantly like the web, so releases widen from 1% to 5%, 20% and 100% while the crash-free rate is watched. Crashlytics and Sentry group stack traces by device, OS and version to pinpoint causes. A remote feature flag can switch off just the faulty feature for an instant recovery without a new build. The fix is then rolled out gradually as well.</sub> |
