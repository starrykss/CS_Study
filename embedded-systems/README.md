## 칩 하나 위의 컴퓨터 · A computer on one chip

MCU와 MPU의 차이, 메모리 맵과 레지스터, 리셋에서 main까지의 부팅 과정, 크로스 컴파일과 링커 스크립트, 그리고 슈퍼 루프까지, 펌웨어가 칩 위에서 어떻게 돌아가는지부터 봐요.  
*MCUs versus MPUs, memory maps and registers, the boot path from reset to main, cross-compiling and linker scripts, and the superloop: how firmware actually runs on a chip.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **MCU와 MPU**<br><sub>MCU vs MPU</sub> | MCU는 CPU·메모리·주변장치를 칩 하나에 담아 펌웨어를 바로 돌리고, MPU는 외부 메모리를 붙여 리눅스 같은 OS를 돌려요.<br><sub>An MCU packs CPU, memory and peripherals onto one chip and runs firmware directly; an MPU adds external memory and runs an OS such as Linux.</sub> | MCU(마이크로컨트롤러)는 CPU 코어, 수백 KB의 Flash, 수십~수백 KB의 SRAM, GPIO·UART·ADC·타이머 같은 주변장치를 칩 하나에 담아요. 전원을 넣으면 ms 안에 Flash의 펌웨어를 실행하고, 잠들면 µA 수준만 써서 배터리 기기에 맞아요. MPU나 SoC는 GHz급 코어와 MMU, 캐시를 갖고 DRAM과 eMMC를 칩 밖에 붙여 리눅스를 돌려요. 화면, 네트워크, 복잡한 앱이 필요하면 MPU를, 정확한 타이밍과 저전력이 필요하면 MCU를 고르고, 둘을 함께 쓰는 제품도 많아요.<br><sub>An MCU (microcontroller) puts a CPU core, hundreds of KB of flash, tens to hundreds of KB of SRAM and peripherals such as GPIO, UART, ADC and timers on one chip. It runs firmware from flash within milliseconds of power-on and sleeps at microamps, ideal for battery devices. An MPU or SoC has GHz cores with an MMU and caches and attaches DRAM and eMMC externally to run Linux. Choose an MPU for screens, networking and complex apps and an MCU for precise timing and low power; many products use both.</sub> |
| **메모리 맵과 레지스터**<br><sub>Memory maps and registers</sub> | Flash, RAM, 주변장치 레지스터가 하나의 주소 공간에 있어요. 장치 제어는 정해진 주소에 값을 읽고 쓰는 일이에요.<br><sub>Flash, RAM and peripheral registers share one address space, so controlling a device means reading and writing fixed addresses.</sub> | MCU는 메모리 맵 I/O를 써서 Flash는 0x0800\_0000, SRAM은 0x2000\_0000, 주변장치는 0x4000\_0000 근처처럼 하나의 주소 공간에 배치해요. GPIOA의 출력 레지스터 ODR이 0x4002\_0014에 있다면 그 주소의 비트 5를 1로 쓰는 것만으로 PA5 핀이 3.3V가 돼요. 하드웨어 레지스터는 컴파일러가 접근을 없애거나 합치지 못하게 volatile 포인터로 다뤄요. \|=처럼 읽고-수정-쓰기를 하면 중간에 인터럽트가 끼어 다른 비트를 덮어쓸 수 있어서, 비트 하나를 바꿀 때는 BSRR 같은 원자적 set/reset 레지스터를 써요.<br><sub>MCUs use memory-mapped I/O, placing flash near 0x0800\_0000, SRAM at 0x2000\_0000 and peripherals around 0x4000\_0000 in one address space. If GPIOA’s output register ODR sits at 0x4002\_0014, setting bit 5 at that address drives pin PA5 to 3.3 V. Hardware registers are accessed through volatile pointers so the compiler cannot drop or merge accesses. A read-modify-write such as \|= can be interrupted and clobber other bits, so single-bit changes use atomic set/reset registers like BSRR.</sub> |
| **리셋에서 main까지**<br><sub>From reset to main</sub> | 리셋되면 벡터 테이블에서 스택과 시작 주소를 읽고, .data 복사와 .bss 초기화, 클럭 설정을 마친 뒤 main을 불러요.<br><sub>On reset the CPU reads the stack pointer and start address from the vector table, copies .data, zeroes .bss, sets up clocks and only then calls main.</sub> | Cortex-M은 리셋되면 벡터 테이블의 첫 워드를 스택 포인터로, 두 번째 워드를 Reset\_Handler 주소로 읽어요. 시작 코드는 초깃값이 있는 전역 변수(.data)를 Flash에서 RAM으로 복사하고, 초깃값이 없는 전역 변수(.bss)를 0으로 채워 C 언어의 약속을 지켜요. 이어서 SystemInit이 PLL을 설정해 내부 16 MHz 클럭을 168 MHz 등으로 올리고, C++이면 전역 생성자까지 부른 다음에야 main()이 실행돼요. 이 과정은 main 이전이라 눈에 안 띄지만, 전역 변수가 이상하거나 부팅이 멈출 때 가장 먼저 확인할 곳이에요.<br><sub>On reset a Cortex-M reads the first word of the vector table as the stack pointer and the second as the address of Reset\_Handler. The startup code copies initialized globals (.data) from flash to RAM and zero-fills uninitialized ones (.bss), keeping the promises of the C language. SystemInit then programs the PLL to raise the internal 16 MHz clock to something like 168 MHz, C++ global constructors run, and only then does main() start. It all happens before main and goes unnoticed, but it is the first place to look when globals misbehave or boot hangs.</sub> |
| **크로스 컴파일과 링커 스크립트**<br><sub>Cross-compiling and linker scripts</sub> | PC에서 ARM용 코드를 만들고, 링커 스크립트로 각 섹션을 Flash와 RAM의 어느 주소에 둘지 정해요.<br><sub>Build ARM code on a PC with a cross compiler, and use a linker script to place each section at an address in flash or RAM.</sub> | 임베디드 개발은 x86 PC에서 arm-none-eabi-gcc 같은 크로스 컴파일러로 대상 CPU용 코드를 만들어요. 링커 스크립트는 MEMORY 블록에 Flash와 RAM의 시작 주소와 크기를 적고, SECTIONS에서 벡터 테이블과 코드(.text)는 Flash에, 변수(.data, .bss)는 RAM에 놓아요. .data는 RAM에서 쓰지만 초깃값은 Flash에 둬야 해서 “> RAM AT > FLASH”처럼 실행 주소와 적재 주소를 나눠요. 만들어진 ELF는 size로 Flash·RAM 사용량을 확인하고, objcopy로 순수 바이너리를 뽑아 디버그 프로브로 Flash에 써요.<br><sub>Embedded development builds code for the target CPU on an x86 PC with a cross compiler such as arm-none-eabi-gcc. A linker script lists the start and size of flash and RAM in its MEMORY block, and SECTIONS places the vector table and code (.text) in flash and variables (.data, .bss) in RAM. Because .data runs from RAM but its initial values must live in flash, “> RAM AT > FLASH” separates the run address from the load address. The size tool reports flash and RAM usage of the ELF, and objcopy extracts a raw binary that a debug probe writes to flash.</sub> |
| **슈퍼 루프**<br><sub>The superloop</sub> | OS 없는 펌웨어의 기본 구조로, 무한 루프 안에서 할 일을 차례로 불러요. 가장 느린 작업이 응답 시간을 정해요.<br><sub>The basic shape of firmware without an OS: an endless loop calling each job in turn, where the slowest job sets the response time.</sub> | 슈퍼 루프는 초기화 후 while(1) 안에서 센서 읽기, 제어, 화면 갱신 같은 함수를 차례로 부르는 구조예요. 단순하고 디버깅하기 쉬워 작은 장치의 대부분이 이렇게 만들어져요. 하지만 화면 갱신처럼 30 ms 걸리는 작업이 있으면 그 도중에 눌린 버튼은 루프가 한 바퀴 돌아올 때까지 확인되지 않아, 최악 응답 시간이 루프 전체 길이가 돼요. 긴 작업은 상태 머신으로 잘게 나누고, 급한 사건은 인터럽트에 맡기고, 작업이 많아지면 RTOS로 옮겨 가요.<br><sub>A superloop initializes and then calls functions such as reading sensors, running control and refreshing a display in turn inside while(1). It is simple and easy to debug, which is why most small devices are built this way. But with a 30 ms display refresh, a button pressed meanwhile is not noticed until the loop comes back around, so the worst-case response becomes the length of the whole loop. Break long jobs into state-machine steps, hand urgent events to interrupts, and move to an RTOS as tasks multiply.</sub> |

## 핀과 신호 다루기 · Working with pins and signals

GPIO와 풀업 저항, 스위치 채터링을 거르는 디바운싱, PWM으로 밝기와 속도 조절하기, ADC의 샘플링과 양자화, 하드웨어 타이머, 그리고 멈춘 장치를 살리는 워치독까지 다뤄요.  
*GPIO and pull-up resistors, debouncing switch contacts, controlling brightness and speed with PWM, ADC sampling and quantization, hardware timers, and the watchdog that revives a hung device.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **GPIO와 풀업 저항**<br><sub>GPIO and pull-ups</sub> | 핀마다 입력·출력과 풀업을 레지스터로 정해요. 떠 있는 입력은 풀업 저항으로 붙잡고, 버튼은 “눌림 = 0”으로 읽어요.<br><sub>Registers set each pin’s direction and pull. A pull-up holds a floating input steady, so a button reads as “pressed = 0”.</sub> | GPIO 핀은 모드 레지스터로 입력이나 출력을 정하고, 출력이면 3.3V나 0V를 내보내 LED 같은 부하를 구동해요. LED에는 (3.3 − 2.0) V / 330 Ω ≈ 4 mA처럼 전류 제한 저항이 필요하고, 핀 하나가 낼 수 있는 전류는 보통 수~20 mA라 모터는 트랜지스터로 구동해요. 아무 데도 연결되지 않은 입력은 떠서 잡음에 따라 0과 1을 오가므로, 풀업 저항으로 평소 1로 붙잡고 버튼이 GND로 당기면 0이 되게 해요. 출력은 0과 1을 모두 구동하는 푸시풀과 0만 당기는 오픈 드레인이 있고, 오픈 드레인은 I2C처럼 여러 장치가 한 선을 공유할 때 써요.<br><sub>A GPIO pin is configured as input or output through its mode register; as an output it drives 3.3 V or 0 V to loads such as LEDs. An LED needs a current-limiting resistor, for example (3.3 − 2.0) V / 330 Ω ≈ 4 mA, and since a pin sources only a few to 20 mA, motors go through a transistor. An input connected to nothing floats between 0 and 1 with noise, so a pull-up holds it at 1 until a button pulls it to ground. Outputs are push-pull, driving both levels, or open-drain, pulling only low, which lets many devices share one line as in I2C.</sub> |
| **스위치 채터링과 디바운싱**<br><sub>Contact bounce and debouncing</sub> | 기계식 스위치는 누르는 순간 수 ms 동안 튀어요. 일정 시간 안정된 뒤에만 변화를 인정해 한 번 누름을 한 번으로 세요.<br><sub>Mechanical switches bounce for a few milliseconds. Accept a change only after it has been stable for a while, so one press counts once.</sub> | 버튼을 누르거나 뗄 때 금속 접점은 수 ms 동안 붙었다 떨어지기를 반복해서, 에지를 그대로 세면 한 번 누름이 여러 번으로 잡혀요. 소프트웨어 디바운싱은 1 ms마다 핀을 읽고, 새 값이 20 ms처럼 정한 시간 동안 그대로일 때만 상태를 바꿔요. 인터럽트로 버튼을 받으면 튈 때마다 ISR이 불리므로 타이머 기반 샘플링이 더 안정적이에요. 하드웨어로는 RC 저역통과 필터와 슈미트 트리거 입력으로 걸러요.<br><sub>When a button is pressed or released, its metal contacts make and break for several milliseconds, so counting raw edges registers one press as several. Software debouncing samples the pin every millisecond and changes state only when the new value has held for a set time such as 20 ms. Interrupt-driven buttons fire the ISR on every bounce, so timer-based sampling is more robust. In hardware, an RC low-pass filter and a Schmitt-trigger input clean up the signal.</sub> |
| **PWM**<br><sub>PWM</sub> | 핀을 빠르게 켰다 껐다 하며 켜진 비율로 평균 출력을 조절해요. LED 밝기, 모터 속도, 서보 각도를 PWM으로 다뤄요.<br><sub>Switch a pin quickly and set the average output by the on fraction. LED brightness, motor speed and servo angles all use PWM.</sub> | PWM은 일정한 주기로 핀을 켰다 끄고, 한 주기에서 켜진 비율인 듀티 사이클로 평균 전압을 정해요. 타이머의 ARR이 주기를, CCR이 켜진 길이를 정해서 84 MHz 클럭을 1 MHz로 나누고 ARR을 999로 두면 1 kHz PWM이 되고, CCR 250이면 듀티 25%로 평균 약 0.83 V예요. LED의 밝기나 모터 속도는 이 평균을 따르고, 모터 드라이버는 소리가 안 들리게 20 kHz 이상을 써요. 서보 모터는 20 ms 주기의 펄스 폭 1~2 ms로 각도를 받아요.<br><sub>PWM switches a pin on and off at a fixed period, and the duty cycle, the fraction of each period spent on, sets the average voltage. A timer’s ARR sets the period and CCR the on-time: dividing 84 MHz to 1 MHz with ARR = 999 gives 1 kHz, and CCR = 250 gives 25% duty, about 0.83 V on average. LED brightness and motor speed follow that average, and motor drivers run above 20 kHz to stay inaudible. Servos read their angle from a 1–2 ms pulse in a 20 ms period.</sub> |
| **ADC**<br><sub>Analog-to-digital conversion</sub> | 정해진 간격으로 전압을 찍고(샘플링) 가장 가까운 단계로 반올림해(양자화) 숫자로 바꿔요.<br><sub>Measure the voltage at fixed intervals (sampling) and round to the nearest level (quantization) to turn it into numbers.</sub> | ADC는 아날로그 전압을 일정한 시간 간격으로 측정하고 2ⁿ개의 단계 중 가장 가까운 값으로 바꿔요. 12비트 ADC는 0~3.3V를 4096단계로 나눠 한 단계가 약 0.8 mV이고, 1.65V는 2048이 돼요. 신호의 최고 주파수보다 2배 넘게 빨리 샘플링해야 에일리어싱이 없어서, 입력 앞에 저역통과 필터를 두기도 해요. 실제 정확도는 기준 전압의 잡음과 신호원 임피던스에 좌우되고, 여러 번 평균 내거나 오버샘플링하면 잡음이 줄어요.<br><sub>An ADC measures an analog voltage at regular intervals and maps it to the nearest of 2ⁿ levels. A 12-bit ADC divides 0–3.3 V into 4096 steps of about 0.8 mV, so 1.65 V reads 2048. Sampling must run faster than twice the signal’s highest frequency to avoid aliasing, which is why a low-pass filter often precedes the input. Real accuracy depends on reference noise and source impedance, and averaging or oversampling reduces noise.</sub> |
| **하드웨어 타이머**<br><sub>Hardware timers</sub> | 클럭을 세는 하드웨어로 정확한 주기 인터럽트, PWM 출력, 펄스 폭 측정을 CPU 부담 없이 해요.<br><sub>Clock-counting hardware delivers precise periodic interrupts, PWM output and pulse measurement without loading the CPU.</sub> | 타이머는 프리스케일러로 나눈 클럭에 맞춰 카운터를 올리고, ARR에 닿으면 0으로 돌아가며 업데이트 인터럽트를 내요. 84 MHz를 8400으로 나눠 10 kHz로 세고 ARR을 9999로 두면 정확히 1초마다 인터럽트가 와요. 카운터를 비교 레지스터 CCR과 비교해 핀을 바꾸면 CPU 개입 없이 PWM이 나오고, 입력 캡처는 에지가 들어온 순간의 카운터 값을 기록해 펄스 폭이나 주파수를 재요. delay 루프보다 정확하고 CPU를 다른 일에 쓸 수 있어요.<br><sub>A timer counts a prescaled clock and, on reaching ARR, wraps to zero and raises an update interrupt. Dividing 84 MHz by 8400 to count at 10 kHz with ARR = 9999 yields an interrupt exactly every second. Comparing the count with a compare register CCR and toggling a pin produces PWM with no CPU involvement, while input capture records the count when an edge arrives to measure pulse widths and frequencies. It is far more precise than delay loops and frees the CPU.</sub> |
| **워치독 타이머**<br><sub>Watchdog timers</sub> | 주기적으로 킥하지 않으면 칩을 리셋하는 카운터예요. 펌웨어가 멈춰도 스스로 다시 살아나게 하는 마지막 안전망이에요.<br><sub>A counter that resets the chip unless it is kicked regularly: the last safety net that brings hung firmware back to life.</sub> | 워치독은 CPU와 별개의 클럭으로 줄어드는 카운터이고, 0에 닿으면 칩을 리셋해요. 정상 동작하는 코드는 주 루프에서 주기적으로 키 값을 써서 카운터를 다시 채우고, 무한 루프나 하드웨어 멈춤으로 킥이 끊기면 정해진 시간 뒤 자동으로 재시작돼요. ISR이나 타이머에서 기계적으로 킥하면 main이 멈춰도 잡지 못하므로, 중요한 작업이 모두 돌았는지 확인한 뒤에 킥해요. 너무 일찍 킥해도 리셋하는 윈도 워치독도 있고, 리셋 후에는 원인 레지스터를 기록해 두면 현장 문제를 추적하기 쉬워요.<br><sub>A watchdog is a counter running down on a clock separate from the CPU, resetting the chip when it reaches zero. Healthy code writes a key value from the main loop to reload it, and if an endless loop or hardware hang stops the kicks, the chip restarts after a set time. Kicking mechanically from an ISR or timer misses a dead main loop, so kick only after confirming every critical task ran. Window watchdogs also reset on kicks that come too early, and logging the reset-cause register afterward makes field failures traceable.</sub> |

## 사건에 반응하기 · Reacting to events

ISR이 불리는 과정, 우선순위와 중첩, volatile과 공유 변수의 경쟁 조건, CPU 대신 데이터를 옮기는 DMA, 그리고 ISR과 main을 잇는 링 버퍼까지, 펌웨어의 동시성을 다뤄요.

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **인터럽트와 ISR**<br><sub>Interrupts and ISRs</sub> | 하드웨어 사건이 생기면 CPU가 하던 일을 멈추고 ISR을 불러요. ISR은 짧게 끝내고 무거운 일은 main이나 태스크에 넘겨요.<br><sub>A hardware event makes the CPU stop and call an ISR. Keep the ISR short and leave heavy work to main or a task.</sub> | 인터럽트가 걸리면 Cortex-M은 R0~R3, R12, LR, PC, xPSR 8개 레지스터를 스택에 자동으로 저장하고 벡터 테이블에서 ISR 주소를 찾아 약 12사이클 만에 실행을 시작해요. ISR은 인터럽트 플래그를 지우고 표시만 남긴 뒤 빨리 끝내야 해요. 오래 기다리기, printf, malloc을 ISR에서 하면 다른 인터럽트가 늦어지고, 플래그를 안 지우면 ISR이 끝나자마자 다시 불려요. 끝나면 저장한 레지스터가 복원되어 main은 멈춘 자리부터 이어 가요.<br><sub>When an interrupt fires, a Cortex-M automatically stacks eight registers (R0–R3, R12, LR, PC, xPSR), fetches the ISR address from the vector table and starts executing in about 12 cycles. The ISR should clear the interrupt flag, leave a marker and return quickly. Long waits, printf or malloc inside an ISR delay other interrupts, and forgetting to clear the flag re-enters the ISR immediately. On return the saved registers are restored and main resumes exactly where it stopped.</sub> |
| **우선순위와 중첩**<br><sub>Priorities and nesting</sub> | 인터럽트마다 우선순위를 둬서 더 급한 인터럽트가 실행 중인 낮은 ISR까지 선점해요.<br><sub>Each interrupt has a priority, and a more urgent one preempts even a running lower-priority ISR.</sub> | Cortex-M의 NVIC는 인터럽트마다 우선순위를 두고, 숫자가 작을수록 높아요. 우선순위 5인 UART ISR이 실행 중일 때 우선순위 1인 타이머 인터럽트가 오면 UART ISR을 멈추고 먼저 처리한 뒤 돌아가는데, 이를 중첩이라고 해요. 같은 우선순위끼리는 선점하지 않고 차례를 기다리고, 연달아 오면 복원과 저장을 건너뛰는 테일 체이닝으로 빨라져요. RTOS를 쓸 때는 RTOS API를 부르는 ISR의 우선순위를 정해진 값보다 낮게 둬야 해요.<br><sub>The Cortex-M NVIC assigns each interrupt a priority, with smaller numbers meaning higher priority. If a priority-1 timer interrupt arrives while a priority-5 UART ISR runs, the UART ISR is suspended, the timer is served, and then the UART ISR resumes: nesting. Equal priorities never preempt each other but queue, and back-to-back interrupts chain without restoring and re-saving context. With an RTOS, ISRs that call RTOS APIs must sit below a configured priority.</sub> |
| **volatile과 공유 변수**<br><sub>volatile and shared variables</sub> | ISR과 공유하는 변수는 volatile로 매번 메모리에서 읽게 해요. 하지만 volatile만으로는 읽고-수정-쓰기 경쟁을 못 막아요.<br><sub>Mark variables shared with an ISR volatile so they are re-read every time, but volatile alone does not stop read-modify-write races.</sub> | 컴파일러는 루프 안에서 바뀌지 않는 것처럼 보이는 변수를 레지스터에 한 번만 읽어 두는데, ISR이 바꾸는 플래그라면 루프가 영원히 끝나지 않아요. volatile은 접근할 때마다 실제 메모리를 읽고 쓰게 해서 이 문제를 막아요. 하지만 count++는 읽기, 더하기, 쓰기 세 단계라 그 사이에 ISR이 같은 변수를 바꾸면 한쪽 증가가 사라져요. 짧게 인터럽트를 막는 임계 구역, LDREX/STREX나 C11 atomic 같은 원자적 연산, 또는 쓰는 쪽을 하나로 정하는 설계로 해결해요.<br><sub>Compilers cache a variable that seems not to change inside a loop in a register, so a flag set by an ISR can leave the loop spinning forever. volatile forces every access to go to real memory, fixing that. But count++ is a load, an add and a store, and an ISR touching the same variable in between makes one increment vanish. Short critical sections that mask interrupts, atomic operations such as LDREX/STREX or C11 atomics, or a design with a single writer solve it.</sub> |
| **DMA**<br><sub>DMA</sub> | 주변장치와 메모리 사이의 데이터 이동을 CPU 대신 하드웨어가 해요. 더블 버퍼로 받으면서 처리할 수 있어요.<br><sub>Hardware moves data between peripherals and memory instead of the CPU, and double buffering processes data while it streams in.</sub> | DMA 컨트롤러는 출발지, 목적지, 개수만 설정하면 ADC 결과나 UART 수신 바이트를 CPU 없이 메모리로 옮겨요. 그동안 CPU는 계산을 계속하고, 전송이 끝나면 인터럽트로 알려 줘요. 순환 모드로 버퍼를 둘로 나누면 DMA가 뒤쪽을 채우는 동안 CPU가 앞쪽을 처리하는 더블 버퍼링이 되어 끊김 없이 연속 처리할 수 있어요. 처리가 절반 시간 안에 끝나야 덮어쓰이지 않고, 캐시가 있는 칩에서는 캐시 정리와 무효화로 일관성을 맞춰야 해요.<br><sub>Given a source, destination and count, a DMA controller moves ADC results or received UART bytes into memory without the CPU, which keeps computing and is notified by an interrupt when the transfer completes. Splitting a circular buffer in two gives double buffering: DMA fills one half while the CPU processes the other, allowing seamless continuous processing. Processing must finish within half a buffer or data is overwritten, and chips with caches need explicit clean and invalidate operations for coherency.</sub> |
| **링 버퍼**<br><sub>Ring buffers</sub> | ISR이 넣고 main이 꺼내는 고정 크기 원형 큐예요. 생산자와 소비자가 각자 인덱스만 바꿔 잠금 없이 안전해요.<br><sub>A fixed-size circular queue that an ISR fills and main drains, lock-free because each side updates only its own index.</sub> | UART 바이트처럼 아무 때나 들어오는 데이터는 ISR이 받은 즉시 링 버퍼의 head 자리에 넣고, main은 여유가 있을 때 tail 자리에서 꺼내요. 생산자는 head만, 소비자는 tail만 바꾸므로 생산자와 소비자가 하나씩이면 잠금 없이 안전하고, 인덱스는 volatile로 선언해요. 크기를 2의 거듭제곱으로 하면 인덱스를 끝없이 늘리고 & (N − 1)로 위치를 구할 수 있어 빈 상태(head == tail)와 가득 찬 상태(head − tail == N)를 쉽게 구분해요. 가득 차면 새 바이트를 버리거나 오류로 알리고, 자주 넘치면 버퍼를 키우거나 DMA를 써요.<br><sub>Data that arrives at any moment, like UART bytes, is stored by the ISR at head right away, and main takes bytes from tail when it has time. The producer touches only head and the consumer only tail, so with one of each no lock is needed, as long as the indices are volatile. A power-of-two size lets the indices grow freely with & (N − 1) giving the position, which cleanly separates empty (head == tail) from full (head − tail == N). When full, new bytes are dropped or flagged, and frequent overflow calls for a larger buffer or DMA.</sub> |

## 칩과 칩이 대화하는 법 · How chips talk

| 개념 | 설명 | 실무 팁 |

| **UART**<br><sub>UART</sub> | 클럭 선 없이 미리 정한 속도로 시작 비트, 데이터 8비트, 정지 비트를 보내는 비동기 직렬 통신이에요.<br><sub>Asynchronous serial with no clock wire: a start bit, 8 data bits and a stop bit at a pre-agreed speed.</sub> | UART는 쉬는 동안 선을 1로 두고, 시작 비트 0, 데이터 8비트(LSB 먼저), 정지 비트 1로 한 바이트를 보내요. 115200 보드면 비트 하나가 약 8.68 µs이고 한 바이트에 10비트가 들어 초당 약 11,520바이트를 보내요. 수신 쪽은 시작 비트에 맞춰 각 비트의 한가운데를 읽기 때문에 양쪽 클럭이 2~3% 넘게 다르면 뒤쪽 비트를 잘못 읽어 프레이밍 오류가 나요. 프레임은 같아도 전압 규격은 TTL(0/3.3V), RS-232(±12V), RS-485(차동, 장거리)로 달라요.<br><sub>UART holds the line at 1 when idle and sends each byte as a 0 start bit, eight data bits least significant first, and a 1 stop bit. The receiver syncs on the start bit and samples mid-bit, so clocks that differ by more than 2–3% misread later bits and cause framing errors. The framing stays the same while voltage standards differ: TTL (0/3.3 V), RS-232 (±12 V) and differential, long-range RS-485.</sub> |
| **SPI**<br><sub>SPI</sub> | 클럭, MOSI, MISO, CS 네 선으로 보내면서 동시에 받는 빠른 전이중 직렬 통신이에요.<br><sub>Fast full-duplex serial over four wires, clock, MOSI, MISO and CS, sending and receiving at once.</sub> | SPI는 마스터가 만드는 클럭(SCLK)에 맞춰 MOSI로 보내고 MISO로 받으며, CS를 0으로 내려 대화할 장치를 골라요. 클럭마다 한 비트씩 양방향으로 동시에 이동하는 전이중 방식이라, Flash에 ID 읽기 명령 0x9F를 보내는 동안 이어지는 클럭에서 제조사 ID 0xEF가 들어와요. 클럭의 기본 극성과 샘플링 에지(CPOL, CPHA)에 따라 4가지 모드가 있어 장치와 맞춰야 하고, 주소가 없어서 장치마다 CS 선이 따로 필요해요. 수십 MHz까지 빨라서 Flash, 디스플레이, SD 카드에 많이 써요.<br><sub>SPI sends on MOSI and receives on MISO in step with a clock (SCLK) driven by the master, which selects a device by pulling its CS low. One bit moves each way on every clock, so while the flash read-ID command 0x9F goes out, the manufacturer ID 0xEF comes back on the following clocks. Four modes follow from the clock’s idle polarity and sampling edge (CPOL, CPHA) and must match the device, and since there are no addresses each device needs its own CS line. Speeds of tens of MHz make it the choice for flash, displays and SD cards.</sub> |
| **I2C**<br><sub>I2C</sub> | 두 선을 여러 장치가 공유하고, 7비트 주소와 ACK로 상대를 골라 대화하는 버스예요.<br><sub>A bus where many devices share two wires and pick each other out with 7-bit addresses and ACKs.</sub> | I2C는 SDA(데이터)와 SCL(클럭) 두 선만 쓰고, 오픈 드레인이라 장치는 0만 당기고 1은 풀업 저항이 만들어요. SCL이 1일 때 SDA가 떨어지면 시작 신호이고, 이어서 7비트 주소와 읽기/쓰기 비트를 보내면 주소가 맞는 장치가 9번째 클럭에 SDA를 0으로 당겨 ACK해요. 레지스터 번호를 쓰고 반복 시작으로 읽기로 바꿔 데이터를 받는데, 온도 센서 TMP102는 0x19 0x00을 돌려줘 25.0 °C를 뜻해요. 보통 100 kHz나 400 kHz로 느리지만 선 두 개로 센서 여러 개를 붙일 수 있고, 느린 장치는 SCL을 붙잡아 기다리게 할 수 있어요.<br><sub>I2C uses just SDA (data) and SCL (clock); lines are open-drain, so devices only pull low and pull-up resistors make the 1s. SDA falling while SCL is high is the start condition, followed by a 7-bit address and a read/write bit, and the device with that address pulls SDA low on the ninth clock to acknowledge. Writing a register number and switching to read with a repeated start returns data; a TMP102 temperature sensor returns 0x19 0x00, meaning 25.0 °C. It is slow, usually 100 or 400 kHz, but hangs many sensors off two wires, and slow devices may hold SCL low to make the master wait.</sub> |
| **CAN 버스**<br><sub>The CAN bus</sub> | 차동 두 선으로 여러 노드가 연결되고, ID를 비트 단위로 비교해 충돌 없이 우선순위대로 보내요.<br><sub>Nodes share two differential wires and compare IDs bit by bit, so messages go out by priority without collisions.</sub> | CAN은 CAN\_H와 CAN\_L 두 선의 전압 차로 신호를 보내 잡음에 강하고, 버스에서는 0(우성)이 1(열성)을 이겨요. 여러 노드가 동시에 보내기 시작하면 각자 ID를 한 비트씩 내보내며 버스를 읽고, 1을 보냈는데 0이 보이면 즉시 물러나요. 그래서 ID가 가장 작은 메시지가 손실 없이 끝까지 전송되고, ID 자체가 우선순위가 돼요. 프레임에는 0~8바이트 데이터와 CRC, ACK가 있어 오류를 바로 잡고, 자동차 ECU 수십 개가 500 kbit/s 버스 하나를 공유해요. CAN FD는 최대 64바이트와 더 빠른 데이터 구간을 지원해요.<br><sub>CAN signals with the voltage difference between CAN\_H and CAN\_L, which shrugs off noise, and on the bus a 0 (dominant) overrides a 1 (recessive). When several nodes start at once, each sends its ID bit by bit while reading the bus and backs off the moment it sends 1 but sees 0. The message with the lowest ID therefore completes without loss, making the ID itself the priority. Frames carry 0–8 data bytes plus a CRC and ACK so errors are caught at once, and dozens of car ECUs share one 500 kbit/s bus; CAN FD extends this to 64 bytes and a faster data phase.</sub> |
| **BLE**<br><sub>Bluetooth Low Energy</sub> | 광고로 찾고 짧은 연결 이벤트로 주고받은 뒤 대부분의 시간을 잠들어 지내는 저전력 무선이에요.<br><sub>Low-power radio that discovers by advertising, exchanges data in brief connection events and sleeps the rest of the time.</sub> | BLE 장치는 광고 채널 37, 38, 39에 짧은 광고 패킷을 수십 ms~수 초마다 뿌리고, 스캔하던 스마트폰이 연결을 요청해요. 연결되면 둘은 7.5 ms~4 s 사이의 연결 간격마다 잠깐 깨어 데이터를 주고받고, 데이터 채널을 바꿔 가며 간섭을 피해요. 데이터는 GATT의 서비스와 특성 트리로 정리되어, 심박 서비스 0x180D의 측정값 특성 0x2A37을 notify로 보내면 표준 앱이 바로 알아봐요. 라디오가 켜진 시간이 1% 남짓이라 코인 전지로도 수개월에서 수년을 버텨요.<br><sub>A BLE device broadcasts short advertising packets on channels 37, 38 and 39 every tens of milliseconds to several seconds, and a scanning phone requests a connection. Once connected, both wake briefly at each connection interval, between 7.5 ms and 4 s, to exchange data, hopping data channels to avoid interference. Data is organized as a GATT tree of services and characteristics; sending the heart rate service 0x180D’s measurement characteristic 0x2A37 as notifications lets standard apps recognize it instantly. With the radio on about 1% of the time, a coin cell lasts months to years.</sub> |

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **RTOS 스케줄러**<br><sub>The RTOS scheduler</sub> | 일을 우선순위가 있는 태스크로 나누고, 준비된 태스크 중 가장 높은 것을 항상 먼저 실행해요.<br><sub>Work is split into prioritized tasks, and the highest-priority ready task always runs first.</sub> | RTOS는 펌웨어를 태스크로 나누고 각 태스크에 우선순위와 자기 스택을 줘요. 스케줄러는 준비된 태스크 중 우선순위가 가장 높은 것을 실행하고, 더 높은 태스크가 준비되면 실행 중인 낮은 태스크를 그 자리에서 선점해요. vTaskDelay나 큐 대기 중인 태스크는 블록 상태라 CPU를 쓰지 않아서 낮은 태스크도 실행 기회를 얻어요. 틱 인터럽트가 시간을 세고, 할 일이 없으면 idle 태스크가 저전력 모드에 들어가며, FreeRTOS, Zephyr, ThreadX가 대표적이에요.<br><sub>An RTOS splits firmware into tasks, each with a priority and its own stack. The scheduler runs the highest-priority ready task and, when a higher one becomes ready, preempts the running lower task on the spot. Tasks waiting in vTaskDelay or on a queue are blocked and use no CPU, giving lower tasks their chance. A tick interrupt keeps time, the idle task can enter low-power mode when nothing is ready, and FreeRTOS, Zephyr and ThreadX are common choices.</sub> |
| **Rate Monotonic 스케줄링**<br><sub>Rate monotonic scheduling</sub> | 주기가 짧은 태스크에 높은 우선순위를 줘요. 사용률이 상한 이하면 모든 마감이 보장돼요.<br><sub>Give shorter-period tasks higher priority; below the utilization bound every deadline is guaranteed.</sub> | 주기적인 태스크들에 고정 우선순위를 줄 때는 주기가 짧을수록 높게 주는 Rate Monotonic이 최적이에요. 리우와 레일랜드는 CPU 사용률 U = ΣC/T가 n(2^(1/n) − 1) 이하면 모든 마감을 지킨다는 걸 증명했고, 태스크 2개면 0.828, 많아지면 ln 2 ≈ 0.693으로 줄어요. 이 상한은 충분조건일 뿐이라 넘어도 스케줄 가능할 수 있어서, 이때는 각 태스크의 최악 응답 시간을 직접 계산해 확인해요. 마감이 가까운 순으로 매번 정하는 EDF는 U ≤ 1까지 가능하지만 과부하 때 어떤 태스크가 놓칠지 예측하기 어려워요.<br><sub>Among fixed-priority assignments for periodic tasks, rate monotonic, giving shorter periods higher priority, is optimal. Liu and Layland proved that if utilization U = ΣC/T stays below n(2^(1/n) − 1), every deadline is met; the bound is 0.828 for two tasks and approaches ln 2 ≈ 0.693 as tasks multiply. The bound is only sufficient, so a task set above it may still be schedulable, which is checked by computing each task’s worst-case response time. EDF, which always runs the nearest deadline, reaches U ≤ 1, but under overload it is harder to predict which task misses.</sub> |
| **우선순위 역전**<br><sub>Priority inversion</sub> | 낮은 태스크가 쥔 자원 때문에 높은 태스크가 중간 태스크에 밀려요. 우선순위 상속으로 막아요.<br><sub>A high-priority task stalls behind a medium one because a low task holds its resource; priority inheritance prevents it.</sub> | 낮은 태스크 L이 mutex를 잡은 상태에서 높은 태스크 H가 같은 mutex를 기다리면, H는 L이 놓을 때까지 블록돼요. 여기까지는 정상이지만, mutex와 상관없는 중간 태스크 M이 L을 선점해 오래 돌면 L이 mutex를 놓지 못해 H가 M보다 늦게 실행되는 역전이 일어나요. 1997년 화성 탐사선 패스파인더가 이 문제로 워치독 리셋을 반복했고, 지구에서 우선순위 상속 옵션을 켜서 고쳤어요. 우선순위 상속은 mutex를 쥔 태스크를 기다리는 태스크의 순위로 잠시 올려 빨리 놓게 하고, 임계 구역을 짧게 유지하는 것도 중요해요.<br><sub>When a low task L holds a mutex and a high task H waits for it, H blocks until L releases it, which is normal. But if a medium task M, unrelated to the mutex, preempts L and runs on, L cannot release and H ends up running after M: priority inversion. In 1997 Mars Pathfinder kept resetting through its watchdog because of exactly this, and engineers fixed it from Earth by enabling priority inheritance. Inheritance temporarily raises the holder to the waiter’s priority so it releases quickly, and short critical sections matter as well.</sub> |
| **세마포어·mutex·큐**<br><sub>Semaphores, mutexes and queues</sub> | 신호는 세마포어, 데이터 전달은 큐, 공유 자원 보호는 mutex로 해요.<br><sub>Semaphores signal, queues carry data, and mutexes guard shared resources.</sub> | ISR은 오래 일할 수 없으니 이진 세마포어를 give해서 기다리던 태스크를 깨우고 일을 넘겨요. 값 자체를 넘길 때는 큐를 쓰며, 큐는 데이터를 복사해 순서대로 전달하고 비어 있으면 받는 태스크를 블록시켜 바쁜 대기를 없애요. mutex는 공유 자원을 한 번에 한 태스크만 쓰게 하는데, 잡은 태스크만 놓을 수 있고 우선순위 상속이 붙어 있어서 ISR에서는 쓰지 않아요. 여러 잠금을 쓸 때는 항상 같은 순서로 잡아 교착 상태를 피하고, 기다림에는 타임아웃을 줘요.<br><sub>Since ISRs cannot do long work, they give a binary semaphore to wake a waiting task and hand off. To pass values, use a queue, which copies data in order and blocks the receiver when empty instead of busy-waiting. A mutex lets one task at a time use a shared resource; only the owner can release it and it carries priority inheritance, so it is not used from ISRs. When taking several locks, always take them in the same order to avoid deadlock, and give waits a timeout.</sub> |
| **실시간과 WCET**<br><sub>Real time and WCET</sub> | 실시간은 빠른 게 아니라 항상 제때 끝나는 거예요. 평균이 아니라 최악 실행 시간으로 설계해요.<br><sub>Real time means always on time, not just fast, so design for the worst-case execution time, not the average.</sub> | 제어 루프의 응답 시간을 사이클 카운터로 수천 번 재면 평균은 63 µs여도 드물게 145 µs가 나와 120 µs 마감을 넘길 수 있어요. 실시간 시스템은 이런 꼬리까지 포함한 최악 실행 시간(WCET)으로 설계해요. 마감을 놓치면 사고인 에어백·브레이크는 경성, 늦은 결과를 버리는 센서 융합은 준경성, 품질만 떨어지는 영상은 연성 실시간이에요. 꼬리는 캐시 미스, Flash 대기 상태, 다른 인터럽트에서 오므로 핵심 코드를 RAM에서 실행하고 인터럽트 우선순위를 정리해 줄여요.<br><sub>Timing a control loop thousands of times with the cycle counter may show a 63 µs mean yet a rare 145 µs that breaks a 120 µs deadline. Real-time systems are designed around the worst-case execution time (WCET), tails included. Airbags and brakes, where a miss is an accident, are hard real time; sensor fusion that discards late results is firm; video that merely degrades is soft. Tails come from cache misses, flash wait states and other interrupts, so critical code runs from RAM and interrupt priorities are tidied up.</sub> |
| **정적 메모리와 스택**<br><sub>Static memory and stacks</sub> | 동적 할당 대신 정적 배열과 고정 블록 풀을 쓰고, 스택 사용량을 측정해 넘침을 막아요.<br><sub>Use static arrays and fixed-size pools instead of dynamic allocation, and measure stack usage to stop overflows.</sub> | malloc과 free를 오래 반복하면 빈 공간이 조각나서 합계는 충분해도 큰 블록 요청이 예측할 수 없는 순간에 실패해요. 그래서 펌웨어는 필요한 메모리를 빌드 때 정하는 정적 배열이나 같은 크기 블록 풀을 써서 단편화를 없애고 할당 시간을 일정하게 해요. 태스크 스택은 0xA5 같은 패턴으로 칠해 두고, 덮어쓰인 깊이로 최대 사용량(최고 수위)을 확인해 크기를 정해요. 스택이 넘치면 옆 메모리를 조용히 망가뜨리므로 MPU 가드 영역이나 카나리로 넘치는 순간 폴트가 나게 해요.<br><sub>Long-running malloc and free fragment the heap, so a large request can fail at an unpredictable moment even with enough total space. Firmware therefore fixes its memory at build time with static arrays or pools of equal-size blocks, eliminating fragmentation and making allocation time constant. Task stacks are painted with a pattern such as 0xA5, and the depth of overwriting reveals peak usage, the high-water mark, used to size them. A stack overflow silently corrupts neighboring memory, so an MPU guard region or canary makes it fault the moment it happens.</sub> |

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **저전력 설계**<br><sub>Low-power design</sub> | 대부분 잠들고 잠깐 깨서 일해요. 평균 전류는 시간 가중 평균이라 깨어 있는 시간을 줄이는 게 핵심이에요.<br><sub>Sleep most of the time and wake briefly. Average current is time-weighted, so cutting awake time is what matters.</sub> | 배터리 장치는 깨어 있을 때 10 mA, 잘 때 5 µA처럼 수천 배 차이가 나는 상태를 오가요. 평균 전류는 각 상태의 전류에 시간 비율을 곱해 더한 값이라, 1초에 10 ms 깨면 10 × 0.01 + 0.005 × 0.99 ≈ 0.105 mA가 되고 220 mAh 코인 전지로 약 2100시간, 87일을 가요. 10초에 한 번 5 ms만 깨면 평균이 약 0.01 mA로 떨어져 2년 넘게 버텨요. 깨는 빈도와 시간을 줄이고, 안 쓰는 주변장치의 클럭을 끄고, 레귤레이터의 대기 전류와 누설까지 따져야 실제 수명이 나와요.<br><sub>Battery devices alternate between states thousands of times apart, such as 10 mA awake and 5 µA asleep. Average current is each state’s current times its share of time, so waking 10 ms per second gives 10 × 0.01 + 0.005 × 0.99 ≈ 0.105 mA, about 2,100 hours or 87 days from a 220 mAh coin cell. Waking for 5 ms every 10 s drops the average to about 0.01 mA and stretches it past two years. Real lifetimes also depend on gating unused peripheral clocks and on regulator quiescent current and leakage.</sub> |
| **고정소수점**<br><sub>Fixed-point arithmetic</sub> | 정수에 소수점 위치를 약속해 두고 정수 연산만으로 실수를 계산해요. FPU가 없는 MCU에서 빠르고 정확해요.<br><sub>Agree on where the binary point sits and compute with integers only; fast and exact on MCUs without an FPU.</sub> | Q15 형식은 16비트 정수를 32768로 나눈 값으로 보고 −1 이상 1 미만을 1/32768 간격으로 표현해요. 0.5는 16384, 0.25는 8192이고, 곱하면 소수 자리가 30비트가 되니 32비트로 곱한 뒤 15비트 오른쪽으로 밀어 4096, 즉 0.125를 얻어요. 더해서 범위를 넘으면 0.75 + 0.5가 −0.75로 뒤집히므로 최댓값에서 멈추는 포화 연산을 써요. FPU가 없는 Cortex-M0, 오디오 필터, 제어기에 쓰이고, ARM의 DSP 명령은 Q15 곱셈-누산을 한 번에 처리해요.<br><sub>The Q15 format treats a 16-bit integer as that integer divided by 32768, covering −1 up to just below 1 in steps of 1/32768. 0.5 is 16384 and 0.25 is 8192, and since their product has 30 fraction bits, multiplying in 32 bits and shifting right by 15 yields 4096, which is 0.125. Overflowing the range flips the sign, turning 0.75 + 0.5 into −0.75, so saturating arithmetic clamps at the maximum. It is used on FPU-less Cortex-M0 parts, in audio filters and controllers, and ARM DSP instructions do Q15 multiply-accumulate in one step.</sub> |
| **부트로더와 OTA**<br><sub>Bootloaders and OTA updates</sub> | Flash를 두 슬롯으로 나눠 새 펌웨어를 받고, 서명을 확인한 뒤 시험 부팅해서 문제가 있으면 롤백해요.<br><sub>Split flash into two slots, download into one, verify the signature, trial-boot it and roll back on failure.</sub> | A/B 방식은 현재 펌웨어가 슬롯 A에서 돌아가는 동안 새 이미지를 슬롯 B에 받아요. 부트로더나 업데이트 코드는 이미지의 해시와 제조사 서명을 공개 키로 확인해서 서명이 없는 악성 펌웨어를 거부해요. B를 시험 중으로 표시하고 재부팅하면 부트로더가 B를 실행해 보고, 새 펌웨어가 스스로 정상임을 확인(confirm)해야 확정돼요. 확인 전에 멈추거나 워치독 리셋이 일어나면 A로 롤백하므로 도중에 전원이 꺼져도 장치가 벽돌이 되지 않고, 버전 카운터로 구버전으로 되돌리는 공격도 막아요.<br><sub>In an A/B scheme the new image downloads into slot B while the current firmware keeps running from slot A. The bootloader or updater checks the image’s hash and the vendor’s signature with a public key, rejecting unsigned, malicious firmware. B is marked as pending and the device reboots into it, and only when the new firmware confirms itself healthy does it become permanent. A hang or watchdog reset before confirmation rolls back to A, so even a power cut midway never bricks the device, and a version counter blocks downgrade attacks.</sub> |
| **JTAG·SWD 디버깅**<br><sub>JTAG and SWD debugging</sub> | 디버그 프로브와 GDB로 CPU를 멈추고 레지스터와 메모리를 보며, 로직 분석기로 실제 파형을 확인해요.<br><sub>Halt the CPU and inspect registers and memory with a debug probe and GDB, and check real waveforms with a logic analyzer.</sub> | ST-LINK나 J-Link 같은 디버그 프로브가 SWD의 두 선(SWDIO, SWCLK)으로 MCU의 디버그 포트에 붙고, OpenOCD가 이를 GDB 서버로 열어 줘요. Flash에서 실행되는 코드에는 하드웨어 중단점을 쓰는데 Cortex-M4에는 비교기가 6개 있고, 멈추면 레지스터, 변수, 호출 스택을 볼 수 있어요. 감시점은 특정 변수에 쓰는 순간 멈춰서 값을 망가뜨리는 코드를 찾는 데 좋아요. 타이밍이나 통신 문제는 로직 분석기로 핀 파형을 기록해 UART나 SPI를 해석해 보고, 양산 제품은 디버그 포트를 읽기 보호로 잠가요.<br><sub>A debug probe such as an ST-LINK or J-Link attaches to the MCU’s debug port over the two SWD wires (SWDIO, SWCLK), and OpenOCD exposes it as a GDB server. Code running from flash uses hardware breakpoints, of which a Cortex-M4 has six comparators, and a halted CPU reveals registers, variables and the call stack. Watchpoints halt the moment a variable is written, ideal for catching whatever corrupts it. Timing and communication bugs call for a logic analyzer that records pin waveforms and decodes UART or SPI, and production units lock the debug port with read-out protection.</sub> |
| **HardFault와 고장 대응**<br><sub>HardFaults and failure handling</sub> | 폴트가 나면 스택에 쌓인 PC와 원인 레지스터로 위치와 이유를 찾고, 안전한 상태로 만든 뒤 재시작해요.<br><sub>On a fault, the stacked PC and the cause registers reveal where and why; make outputs safe, then restart.</sub> | 잘못된 포인터로 없는 주소에 쓰면 버스 폴트가 나고, 처리기가 없으면 HardFault로 올라가요. CPU는 예외 직전에 레지스터 8개를 스택에 쌓으므로 sp[6]의 PC 값을 addr2line에 넣으면 문제가 된 소스 줄이 나와요. CFSR 레지스터는 원인을 비트로 알려 주는데, PRECISERR와 BFARVALID가 켜져 있으면 BFAR에 문제의 주소가 들어 있어요. 현장에서는 리셋 후에도 남는 RAM에 로그를 남기고, 모터나 히터 같은 출력을 안전 상태로 둔 뒤 재시작하며, 전압이 떨어지면 브라운아웃 감지가 칩을 리셋해요.<br><sub>Writing through a bad pointer to an unmapped address raises a bus fault, which escalates to HardFault if no handler is enabled. The CPU stacks eight registers just before the exception, so passing the PC at sp[6] to addr2line names the faulting source line. The CFSR register reports the cause in bits; with PRECISERR and BFARVALID set, BFAR holds the offending address. In the field, log to RAM that survives reset, put outputs such as motors and heaters in a safe state and restart, while a brown-out detector resets the chip when the supply sags.</sub> |
