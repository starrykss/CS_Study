| **ref와 reactive**<br><sub>ref and reactive</sub> | reactive는 객체를 Proxy로 감싸 읽기와 쓰기를 가로채요. 프록시는 원본과 다른 객체였고, 안쪽 객체는 읽을 때 감싸졌어요. ref는 .value 하나를 감싼 상자예요.<br><sub>reactive wraps an object in a Proxy that intercepts reads and writes. The proxy was a different object from the original, and nested objects were wrapped when read. A ref is a box around a single .value.</sub> | Vue의 반응성은 자바스크립트의 Proxy 위에 만들어져 있어요. reactive(raw)를 부르면 Vue는 원본 객체를 Proxy로 감싼 객체를 돌려줘요. 이 프록시의 속성을 읽으면 Vue는 지금 실행 중인 효과, 예를 들어 컴포넌트의 렌더링 함수가 그 속성에 의존한다고 기록하고, 속성에 값을 쓰면 그 속성에 의존하는 효과들을 다시 실행하도록 예약해요. 개발자는 평범한 객체처럼 읽고 쓰기만 하면 돼요. 프록시는 원본과 다른 객체예요. st !== raw가 true였고, toRaw(st)는 원본을 그대로 돌려줬어요. 같은 원본을 reactive로 다시 감싸자 새 프록시가 아니라 이미 만든 같은 프록시가 나왔어요. Vue가 원본과 프록시의 짝을 기억하기 때문이에요. 그래서 배열에서 indexOf나 includes로 찾을 때, 원본과 프록시를 섞어 비교하면 못 찾는 일이 생기니 프록시끼리 비교해요. 안쪽 객체는 처음부터 감싸지 않고, 읽는 순간 감싸요. st.nested를 읽자 isReactive(st.nested)가 true였어요. 거대한 객체라도 만들 때 비용이 없고, 실제로 접근한 부분만 프록시가 돼요. 주의할 점은 원본을 직접 고치는 거예요. 프록시를 거치지 않고 raw.a = 2처럼 원본을 바꾸면 Vue는 알 수 없어서 화면이 바뀌지 않아요. reactive에 넘긴 뒤에는 원본 변수를 쓰지 않는 습관이 안전해요. ref(0)는 .value라는 속성 하나를 가진 상자예요. 숫자, 문자열, 불리언 같은 원시값은 Proxy로 감쌀 수 없으므로 이렇게 객체로 한 번 감싸요. ref의 .value를 완전히 다른 객체로 바꿔도 반응이 유지되고, 객체를 넣으면 그 안쪽은 reactive로 감싸져서 isReactive(r.value)가 true였어요. 반면 reactive 객체는 변수 자체를 새 객체로 바꾸면 연결이 끊겨요. 템플릿에서는 최상위 ref가 자동으로 풀려서 .value 없이 써요. 이런 이유로 Vue 공식 문서는 상태를 선언할 때 ref를 기본으로 권해요. reactive는 여러 필드를 가진 폼 상태처럼 한 덩어리로 다루는 객체에 쓰기 좋아요.<br><sub>Vue’s reactivity is built on JavaScript’s Proxy. Calling reactive(raw) makes Vue return a Proxy wrapping the original object. Reading a property of this proxy makes Vue record that the currently running effect, such as a component’s render function, depends on that property; writing a value schedules the effects that depend on that property to run again. Developers simply read and write as with an ordinary object. The proxy is a different object from the original: st !== raw was true, and toRaw(st) returned the original as is. Wrapping the same original with reactive again returned not a new proxy but the same one already made, because Vue remembers the pairing of originals and proxies. So when searching arrays with indexOf or includes, mixing originals and proxies can fail to find items; compare proxies with proxies. Nested objects are not wrapped up front but at the moment they are read: after reading st.nested, isReactive(st.nested) was true. Even a huge object costs nothing to create, and only the parts actually accessed become proxies. The pitfall is mutating the original directly. Changing it without going through the proxy, as in raw.a = 2, leaves Vue unaware, so the screen does not update. After passing an object to reactive, it is safer not to use the original variable again. ref(0) is a box with a single property, .value. Primitives such as numbers, strings and booleans cannot be wrapped in a Proxy, so they are wrapped once in an object this way. A ref stays reactive even when .value is replaced with an entirely different object, and an object put inside is wrapped with reactive, so isReactive(r.value) was true. A reactive object, by contrast, loses its link if the variable itself is reassigned to a new object. In templates, top-level refs are unwrapped automatically and used without .value. For these reasons the official Vue docs recommend ref as the default for declaring state. reactive suits objects handled as a single unit, such as form state with several fields.</sub> |
| **의존성 추적**<br><sub>Dependency tracking</sub> | 효과가 실행되며 읽은 속성만 의존성이 돼요. 읽지 않은 속성을 바꾸거나 같은 값을 다시 넣으면 다시 실행되지 않았고, 조건에 따라 의존성이 실행마다 바뀌었어요.<br><sub>Only properties read during an effect’s run become dependencies. Changing unread properties or writing the same value caused no re-run, and dependencies changed per run according to conditions.</sub> | Vue는 의존성을 미리 선언하게 하지 않아요. 대신 효과를 실행하면서 그 안에서 어떤 반응형 속성을 읽었는지 기록해요. 이것이 의존성 추적이에요. s.a + s.b를 계산하는 효과를 만들고 실행 횟수를 셌어요. 처음 만들 때 한 번 실행되며 a와 b가 의존성으로 기록됐어요. 읽지 않은 c를 30으로 바꾸자 실행 횟수는 그대로 1이었어요. a를 10으로 바꾸자 효과가 다시 실행되어 2가 됐어요. 그리고 같은 값 10을 다시 넣자 실행되지 않았어요. Vue는 Object.is로 이전 값과 비교해 실제로 바뀌었을 때만 알리기 때문에, 같은 값을 반복해서 넣어도 낭비가 없어요. 의존성은 실행할 때마다 새로 모아요. t.ok ? t.x : t.y를 계산하는 효과에서 ok가 true일 때는 ok와 x만 읽으므로, y를 바꿔도 효과는 실행되지 않았어요. ok를 false로 바꾸자 효과가 다시 실행되면서 이번에는 ok와 y를 읽었고, 의존성이 ok와 y로 바뀌었어요. 그 뒤에는 x를 바꿔도 실행되지 않고 y를 바꾸자 실행됐어요. 지금 실제로 쓰는 값에만 반응하므로, 조건부 렌더링이 많은 컴포넌트에서도 불필요한 다시 그리기가 생기지 않아요. Vue의 많은 기능이 이 효과 위에 있어요. 컴포넌트의 렌더링 함수는 템플릿에서 읽은 값에 의존하는 효과이고, computed는 결과를 캐시하는 효과이고, watch와 watchEffect는 콜백을 부르는 효과예요. 그래서 어떤 값이 바뀌면 그 값을 실제로 읽은 컴포넌트만 다시 그려지고, 상위 컴포넌트 전체가 다시 그려지지 않아요. 개발자가 shouldComponentUpdate나 메모이제이션을 직접 챙길 일이 적은 이유예요. 반대로 생각하면, 렌더링이나 계산에 쓰지 않는 값을 반응형으로 만들어 둘 필요는 없어요. 타이머 ID나 외부 라이브러리 인스턴스처럼 화면과 상관없는 값은 일반 변수에 두면 추적 비용이 들지 않아요. 큰 데이터의 추적 비용은 shallowRef 항목에서 실제로 재요.<br><sub>Vue does not ask for dependencies to be declared up front. Instead, it records which reactive properties are read while an effect runs; this is dependency tracking. An effect computing s.a + s.b was created and its runs counted. On creation it ran once, recording a and b as dependencies. Changing c, never read, to 30 left the run count at 1. Changing a to 10 re-ran the effect, bringing it to 2. Writing the same value 10 again did not run it. Vue compares with the previous value using Object.is and notifies only on real changes, so repeatedly writing the same value wastes nothing. Dependencies are re-collected on every run. In an effect computing t.ok ? t.x : t.y, while ok was true only ok and x were read, so changing y did not run the effect. Switching ok to false re-ran the effect, which this time read ok and y, changing the dependencies to ok and y. After that, changing x did nothing and changing y ran it. Because it reacts only to values currently in use, components with lots of conditional rendering avoid unnecessary re-renders too. Many Vue features sit on top of such effects. A component’s render function is an effect depending on the values the template reads, computed is an effect that caches its result, and watch and watchEffect are effects that call callbacks. So when a value changes, only the components that actually read it re-render, not the whole parent tree. That is why developers rarely need to manage shouldComponentUpdate or memoization by hand. Seen the other way, values never used in rendering or computation need not be reactive. Values unrelated to the screen, such as timer IDs or instances of external libraries, cost no tracking when kept in ordinary variables. The tracking cost of large data is measured concretely in the shallowRef item.</sub> |
| **computed**<br><sub>computed</sub> | computed는 결과를 캐시해 세 번 읽어도 한 번만 계산했어요. 의존성이 바뀌어도 읽을 때까지 계산을 미뤘고, 다시 계산한 결과가 같으면 뒤의 효과를 깨우지 않았어요.<br><sub>computed caches its result, computing once even when read three times. It deferred computation until read after dependencies changed, and an unchanged recomputed result did not wake downstream effects.</sub> | computed는 다른 반응형 값에서 계산한 값을 캐시해요. base.value \* 2를 돌려주는 computed를 만들고 계산 함수가 불린 횟수를 셌어요. dbl.value를 세 번 읽자 계산 함수는 한 번만 불렸어요. 처음 읽을 때 계산하고, 그 뒤에는 의존성이 바뀌지 않았으므로 캐시를 돌려준 거예요. 같은 계산을 일반 함수, 즉 컴포넌트의 메서드로 만들어 세 번 부르자 세 번 모두 실행됐어요. 템플릿에서 같은 값을 여러 곳에 보여 주거나, 컴포넌트가 다른 이유로 자주 다시 그려진다면 이 차이가 쌓여요. computed는 게으르게 계산해요. base를 2로 바꾼 직후에는 계산 횟수가 그대로 1이었어요. 의존성이 바뀌면 computed는 캐시가 낡았다는 표시만 해 두고, 누군가 .value를 다시 읽을 때 계산해요. 다시 읽자 그제야 두 번째 계산이 일어났어요. 그래서 화면에 보이지 않는 탭의 computed는 아무도 읽지 않는 동안 계산되지 않아요. Vue 3.4부터는 한 가지 최적화가 더해졌어요. 다시 계산한 결과가 이전 결과와 같으면, 그 computed에 의존하는 효과를 깨우지 않아요. base % 2, 즉 짝수인지를 계산하는 computed를 두고 그것을 읽는 효과의 실행 횟수를 셌어요. base를 2에서 4, 6으로 바꾸는 동안 computed는 다시 계산됐지만 결과는 계속 0이었고, 효과는 처음 한 번 말고는 실행되지 않았어요. 세밀한 값에서 굵은 값을 뽑아내는 computed를 중간에 두면, 굵은 값이 바뀔 때만 화면이 다시 그려지게 할 수 있어요. computed의 계산 함수는 값을 돌려주기만 하는 순수한 함수여야 해요. 그 안에서 다른 상태를 바꾸거나, 요청을 보내거나, DOM을 건드리면 안 돼요. 언제, 몇 번 실행될지는 누가 읽느냐에 달려 있어서 그런 부수 효과는 예측할 수 없게 돼요. 그런 일은 다음 항목의 watch에 둬요. 목록의 필터와 정렬, 합계, 포맷한 문자열처럼 입력에서 계산되는 값은 computed에 두면, 입력이 바뀔 때만 다시 계산되고 나머지 경우에는 캐시를 써요. 쓰기가 필요한 경우에는 get과 set을 가진 쓰기 가능한 computed도 만들 수 있어요.<br><sub>computed caches a value derived from other reactive values. A computed returning base.value \* 2 was created and calls to its function counted. Reading dbl.value three times called the function only once: it computed on the first read and afterwards returned the cache, since dependencies had not changed. The same computation as an ordinary function, a component method, called three times ran all three times. When a template shows the same value in several places, or a component re-renders often for other reasons, this difference adds up. computed evaluates lazily. Right after base changed to 2, the compute count was still 1. When a dependency changes, computed only marks its cache as stale and computes when someone reads .value again. Only on the next read did the second computation happen. So computed values in a tab that is not on screen are not computed while nobody reads them. Vue 3.4 added one more optimization: if a recomputed result equals the previous result, effects depending on that computed are not woken. A computed of base % 2, whether base is odd, was read by an effect whose runs were counted. While base went from 2 to 4 to 6, the computed recomputed but the result stayed 0, and the effect never ran beyond the first time. Placing a computed that extracts a coarse value from fine-grained data in between makes the screen re-render only when the coarse value changes. A computed getter must be a pure function that only returns a value. It must not change other state, send requests or touch the DOM; when and how often it runs depends on who reads it, so such side effects become unpredictable. Such work belongs in watch, the next item. Values derived from inputs, such as filtered and sorted lists, totals and formatted strings, belong in computed, recalculated only when inputs change and served from cache otherwise. When writing is needed, a writable computed with get and set can be made too.</sub> |

| **템플릿 컴파일**<br><sub>Template compilation</sub> | 템플릿은 빌드할 때 렌더 함수로 바뀌어요. 동적인 노드에는 TEXT나 CLASS 같은 패치 플래그가 붙고, 정적인 노드와 이벤트 핸들러는 한 번 만들어 캐시해요.<br><sub>Templates become render functions at build time. Advanced settings most users never open, details shown only on errors and admin menus shown only with permission make the first screen faster and use less memory with v-if. State matters too. Sometimes that is the desired behaviour, as when reopening a modal should start with a clean form. When state must survive occasional toggles, use v-show, or for dynamic components, KeepAlive from the components section. v-if can be chained with v-else-if and v-else and used on <template>, while v-show works only on a single element. The parent passes values down to the child through props, and the child tells the parent that something happened through emit. When the parent changes a value, the child’s props follow, but the path for a child to affect the parent by changing props is blocked. This is called one-way data flow. The props object handed to a child is a read-only proxy. Running props.count++ in the child produced the dev-mode warning Set operation on key "count" failed: target is readonly, and the parent’s count stayed 1. If any child receiving a shared value could change it, finding who changed it when it goes wrong would be hard. This protection is shallow, though. When a child that received an object, props.user, changed props.user.name, it changed without a warning. What the parent passed was the object itself, so the parent’s user.name also became changed by child. Read-only applies only to the top-level properties of the props object, while the objects inside are still the parent’s reactive objects. It looks convenient, but makes it hard to tell from the code where state changes, which is why the official Vue docs advise avoiding such mutations. Data then flows down and events flow up, keeping a single owner for each piece of state. When the child needs a copy to edit internally, it copies the prop once at the start, as in const local = ref(props.initial), connecting it with computed or watch if it must follow the parent’s changes. | **슬롯**<br><sub>Slots</sub> | 슬롯 내용은 함수로 컴파일되어 자식에게 넘어가요. 자식은 자기 데이터를 넘기며 그 함수를 부르고, 부모의 다른 값이 바뀌어도 슬롯이 읽지 않으면 자식은 그대로였어요.<br><sub>Slot content compiles to functions passed to the child, which calls them with its own data. Roles can be divided so the child loads, sorts and paginates data while the parent decides how each item looks. Being functions also makes re-rendering precise. ## 로직을 함수로 나누기 · Splitting logic into functions

상태와 로직을 묶는 컴포저블, watch 안의 비동기 요청이 일으키는 경쟁 조건, 부모와 자식의 생명주기 순서, 템플릿 ref와 expose, 그리고 await 뒤에 만든 효과와 effectScope를 실측해요.

| **컴포저블**<br><sub>Composables</sub> | 컴포저블은 상태와 로직을 묶은 평범한 함수예요. 함수 안에서 만든 ref는 부를 때마다 따로였고, 모듈에서 만든 ref는 모든 사용처가 하나를 나눠 썼어요.<br><sub>A composable is a plain function bundling state and logic. When a user first clicks the /admin link, the browser downloads that chunk, keeping the previous screen while it downloads and switching when ready. The browser caches a downloaded chunk, so there is no waiting from the second visit on. The example’s Admin is a single table and therefore small, but a real admin screen using a chart library, Excel export and a rich-text editor takes hundreds of kilobytes out of the first screen. Ordinary users never enter the admin screen, so they have no reason to download its code. Building an app using only Vue without the router, with the same settings, gave 63.12 KB, 24.87 KB gzipped, so Vue Router added about 10.6 KB gzipped. Templates were compiled at build time, so these sizes contain no template compiler. The first screen’s size depends more on app code and libraries than on Vue itself, so the heavier a library, the more it pays to defer it to the routes or components using it. The criterion for splitting is usage frequency: split screens used by few users or rarely, such as admin, settings, statistics and help, and do not split the route users see first, since deferring the first screen too means waiting for one more chunk, which is slower. One caveat: deploying a new version changes the hashes in chunk file names, and tabs opened before the deploy may request old chunk names and fail to find them. A common remedy detects chunk-loading failures in router.onError and reloads the page.</sub> |
