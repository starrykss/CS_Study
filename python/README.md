| **이름과 객체**<br><sub>Names and objects</sub> | 파이썬 변수는 값을 담는 상자가 아니라 객체에 붙인 이름이에요. 대입은 복사하지 않고 참조를 늘리며, ==는 값을, is는 같은 객체인지를 비교해요.<br><sub>A Python variable is not a box holding a value but a name attached to an object. Assignment copies nothing and adds a reference; == compares values and is compares identity.</sub> | 파이썬에서는 숫자, 문자열, 함수, 클래스, 모듈까지 모든 것이 객체예요. 객체는 고유한 정체(id), 바뀌지 않는 타입, 그리고 값을 가지고, 변수는 그 객체에 붙인 이름이에요. a = [1, 2]는 힙에 리스트 객체를 만들고 이름 a를 연결해요. b = a는 리스트를 복사하지 않고 같은 객체에 이름 b를 하나 더 붙이므로, b.append(3)을 하면 a에서도 보여요. CPython은 객체마다 자신을 가리키는 참조 수를 세서 지금은 2이고, 0이 되면 바로 메모리를 돌려줘요. c = [1, 2]는 값이 같은 새 리스트를 따로 만들어요. 그래서 값을 비교하는 a == c는 True지만, 같은 객체인지 비교하는 a is c는 False예요. ==는 \_\_eq\_\_ 메서드로 동작해 타입마다 의미를 정할 수 있고, is는 id만 비교해 빠르지만 값 비교에 쓰면 안 돼요. CPython은 -5부터 256까지의 작은 정수를 미리 만들어 두고 함께 쓰기 때문에, 이 범위에서는 is가 우연히 True가 되기도 해서 혼란을 줘요. is는 x is None처럼 유일한 객체와 비교할 때만 써요. 함수에 인자를 넘길 때도 객체 참조가 전달되므로, 함수 안에서 가변 객체를 고치면 호출한 쪽에서도 보여요.<br><sub>In Python everything is an object, from numbers and strings to functions, classes and modules. An object has a unique identity (id), a fixed type and a value, and a variable is a name attached to it. a = [1, 2] creates a list object on the heap and binds the name a. b = a does not copy the list but binds a second name to the same object, so b.append(3) shows up through a as well. CPython counts the references to each object, now 2, and frees the memory as soon as the count reaches 0. c = [1, 2] builds a separate list with an equal value. So a == c, which compares values, is True, while a is c, which checks for the same object, is False. == works through the \_\_eq\_\_ method, so each type defines its meaning, while is compares only ids: fast, but wrong for comparing values. CPython preallocates and shares small integers from −5 to 256, so is can happen to be True in that range, which confuses people. Use is only to compare against a unique object, as in x is None. Function arguments are passed as object references too, so mutating a mutable object inside a function is visible to the caller.</sub> |
| **가변성과 복사**<br><sub>Mutability and copying</sub> | 리스트·딕셔너리·집합은 제자리에서 바뀌고, 정수·문자열·튜플은 바꾸면 새 객체가 생겨요. 얕은 복사는 안쪽 객체를 공유하고, 깊은 복사는 모든 단계를 새로 만들어요.<br><sub>Lists, dicts and sets change in place, while ints, strings and tuples produce new objects when changed. A shallow copy shares the inner objects; a deep copy rebuilds every level.</sub> | 가변 객체(list, dict, set, 사용자 클래스 대부분)는 제자리에서 내용이 바뀌고, 불변 객체(int, float, str, tuple, frozenset)는 바꾸는 연산이 항상 새 객체를 만들어요. 문자열 s에 s += "!"를 하면 원래 문자열은 그대로고 새 문자열이 만들어져 s가 그것을 가리켜요. 가변 객체를 여러 이름이 공유하면 한쪽의 변경이 다른 쪽에도 보여서 버그의 원인이 돼요. a.copy(), a[:], list(a)는 얕은 복사로 바깥 리스트만 새로 만들고 안의 참조는 그대로 복사하므로, 2차원 리스트를 얕게 복사한 b에서 b[0][0] = 9를 하면 a[0][0]도 9가 돼요. [[0] \* 3] \* 3으로 만든 격자도 같은 안쪽 리스트를 세 번 가리켜서 한 칸을 고치면 한 열 전체가 바뀌니, [[0] \* 3 for \_ in range(3)]으로 만들어야 해요. copy.deepcopy는 안쪽 객체까지 재귀적으로 새로 만들어 완전히 독립된 사본을 줘요(순환 참조도 처리해요). 튜플은 불변이지만 안에 든 리스트는 여전히 바뀔 수 있고, 그런 튜플은 해시할 수 없어 딕셔너리 키가 될 수 없어요. 함수의 기본 인자로 가변 객체를 쓰면 호출 사이에 공유되는 것도 같은 원리예요.<br><sub>Mutable objects (list, dict, set and most user classes) change their contents in place, while operations on immutable objects (int, float, str, tuple, frozenset) always create new objects. For a string s, s += "!" leaves the original string untouched, builds a new one and points s at it. When several names share a mutable object, a change through one is visible through the others, a common source of bugs. a.copy(), a[:] and list(a) are shallow copies: a new outer list holding the same references, so setting b[0][0] = 9 on a shallow copy b of a 2-D list makes a[0][0] 9 too. A grid built as [[0] \* 3] \* 3 likewise points at one inner list three times, so changing one cell changes a whole column; build it as [[0] \* 3 for \_ in range(3)] instead. copy.deepcopy rebuilds inner objects recursively for a fully independent copy, handling cycles as well. A tuple is immutable, but a list inside it can still change, and such a tuple is unhashable and cannot be a dict key. A mutable default argument shared across function calls is the same principle at work.</sub> |
| **리스트: 동적 배열**<br><sub>Lists: dynamic arrays</sub> | 리스트는 객체 포인터의 동적 배열이에요. 여유 공간을 과할당해서 끝에 추가하기는 평균 O(1)이지만, 맨 앞에 넣거나 빼기는 O(n)이에요.<br><sub>A list is a dynamic array of object pointers. Over-allocating spare room keeps append amortized O(1), while inserting or removing at the front is O(n).</sub> | CPython의 리스트는 연결 리스트가 아니라 객체를 가리키는 포인터들의 연속된 배열이에요. 원소가 포인터라서 정수, 문자열, 다른 리스트가 섞여도 되고, 인덱스 접근은 주소 계산 한 번이라 O(1)이에요. 리스트는 실제 원소 수(size)와 확보해 둔 칸 수(allocated)를 따로 기억해요. 꽉 찬 상태에서 append하면 새 크기의 약 1.125배에 몇 칸을 더한 만큼 더 큰 블록을 잡고 포인터를 옮기므로, 빈 리스트에 계속 추가하면 용량이 0, 4, 8, 16, 24, 32, 40, 52, 64, 76…으로 늘어요. 가끔 일어나는 재할당 비용을 나눠 보면 append는 평균 O(1)이에요. 끝에서 pop()도 O(1)이지만, insert(0, x)나 pop(0)은 뒤의 모든 원소를 한 칸씩 옮겨야 해서 O(n)이에요. 큐처럼 양쪽 끝을 쓰려면 collections.deque를 써요. x in xs는 처음부터 하나씩 비교하는 O(n)이라, 포함 검사가 잦으면 평균 O(1)인 set을 써요. 크기를 미리 알면 [None] \* n으로 한 번에 만들 수 있고, 같은 타입의 숫자를 대량으로 다룰 때는 객체마다 포인터와 헤더가 붙는 리스트보다 array 모듈이나 NumPy 배열이 메모리와 속도 모두 유리해요.<br><sub>A CPython list is not a linked list but a contiguous array of pointers to objects. Because elements are pointers, ints, strings and other lists can mix, and indexing is a single address computation, O(1). A list tracks its actual size and its allocated capacity separately. Appending to a full list allocates a larger block, about 1.125 times the new size plus a few slots, and moves the pointers over, so repeatedly appending to an empty list grows the capacity 0, 4, 8, 16, 24, 32, 40, 52, 64, 76 and so on. Spread over all appends, the occasional reallocation makes append amortized O(1). pop() from the end is O(1) too, but insert(0, x) and pop(0) shift every later element by one, O(n); for queue-like use at both ends, use collections.deque. x in xs compares one element at a time, O(n), so frequent membership tests call for a set, O(1) on average. When the size is known, [None] \* n builds the list at once, and for large amounts of same-typed numbers, the array module or NumPy arrays beat lists, which carry a pointer and an object header per element, in both memory and speed.</sub> |
| **딕셔너리: 해시 테이블**<br><sub>Dicts: hash tables</sub> | 키의 해시값으로 칸을 정하는 해시 테이블이에요. 3.6부터는 번호만 담는 indices와 삽입 순서대로 쌓는 entries로 나뉘어 메모리를 아끼고 순서를 지켜요.<br><sub>A hash table that picks slots from key hashes. Since 3.6 it is split into indices holding small numbers and entries stacked in insertion order, saving memory and preserving order.</sub> | 딕셔너리는 파이썬의 핵심 자료구조로, 객체의 속성, 모듈의 전역 변수, 키워드 인자가 모두 딕셔너리로 구현돼요. 키를 넣으면 hash(key)를 계산하고 그 아래 비트로 칸을 정해요. 크기가 8인 표에서 해시가 13인 키는 13 & 7 = 5번 칸으로 가요(여기서 해시값은 예시예요). 이미 다른 키가 차지했으면 해시의 윗비트(perturb)를 섞은 수식 i = (5i + perturb + 1) mod 8로 다음 칸을 찾아가는 개방 주소법을 써요. 3.6부터 CPython은 표를 두 부분으로 나눴어요. indices는 칸마다 작은 항목 번호만 담고, 실제 해시·키·값은 entries 배열에 삽입 순서대로 촘촘히 쌓아요. 빈 칸에 큰 항목을 낭비하지 않아 메모리가 줄고, 순회 순서가 삽입 순서와 같아져서 3.7부터는 순서 보장이 언어 규칙이 됐어요. 찾을 때는 같은 칸 순서를 따라가며 해시가 같고 키가 ==로 같은 항목을 찾아요. 표가 2/3 정도 차면 더 큰 표로 옮겨 다시 배치해서 찾기, 넣기, 지우기가 평균 O(1)이에요. 그래서 키는 해시 가능해야 하고, 같은 키는 같은 해시를 가져야 하며, 해시가 바뀌는 가변 객체는 키가 될 수 없어요. 문자열의 해시는 실행할 때마다 무작위로 섞여 충돌을 노린 공격을 막아요.<br><sub>The dict is Python’s central data structure: object attributes, module globals and keyword arguments are all dicts. Inserting a key computes hash(key) and uses its low bits to choose a slot: in a table of size 8, a key with hash 13 goes to slot 13 & 7 = 5 (the hashes here are illustrative). If another key already holds it, open addressing finds the next slot with i = (5i + perturb + 1) mod 8, mixing in the hash’s upper bits through perturb. Since 3.6, CPython splits the table in two. The indices array holds only a small entry number per slot, and the actual hashes, keys and values are packed into an entries array in insertion order. Empty slots no longer waste room for full entries, saving memory, and iteration follows insertion order, which became a language guarantee in 3.7. A lookup follows the same probe sequence until it finds an entry with an equal hash and a key equal under ==. When the table is about two-thirds full, it moves to a larger table and reinserts everything, so lookups, inserts and deletes are O(1) on average. Keys must therefore be hashable, equal keys must share a hash, and mutable objects whose hash could change cannot be keys. String hashes are randomized per process to resist collision attacks.</sub> |
| **문자열과 인코딩**<br><sub>Strings and encoding</sub> | str은 불변 유니코드 시퀀스로, 가장 큰 글자에 맞춰 글자당 1·2·4바이트로 저장돼요. 바이트로는 encode로 바꾸고, 여러 조각은 join으로 한 번에 합쳐요.<br><sub>str is an immutable Unicode sequence stored at 1, 2 or 4 bytes per character to fit its largest character. encode turns it into bytes, and join combines many pieces in one pass.</sub> | 파이썬 3의 str은 유니코드 코드 포인트의 불변 시퀀스예요. CPython은 문자열마다 가장 큰 코드 포인트를 보고 저장 폭을 정해서(PEP 393), 영어와 라틴 문자만 있으면 글자당 1바이트, "안녕"처럼 기본 다국어 평면(U+FFFF 이하)의 글자가 있으면 2바이트, 이모지처럼 그 밖의 글자가 있으면 4바이트를 써요. 그래서 인덱스 접근은 항상 O(1)이에요. 파일, 네트워크, 데이터베이스와 주고받을 때는 바이트가 필요해서 encode로 bytes로 바꾸고 decode로 되돌려요. UTF-8에서 한글 한 글자는 3바이트라 "안녕".encode("utf-8")은 EC 95 88 EB 85 95의 6바이트예요. 경계에서만 변환하고 프로그램 안에서는 str로 다루는 것이 원칙이에요. 문자열은 고칠 수 없어서 s[0] = "H"는 TypeError이고, 루프에서 +=를 반복하면 매번 새 문자열로 복사해 O(n²)가 될 수 있어요(CPython이 경우에 따라 제자리 최적화를 하지만 보장되지 않아요). 조각을 리스트에 모아 "".join(parts)로 한 번에 합치면 전체 길이를 먼저 계산해 O(n)이에요. 불변이라 해시를 한 번 계산해 캐시할 수 있어 딕셔너리 키로 쓰기 좋고, 식별자 같은 짧은 문자열은 인터닝되어 같은 객체를 함께 써서 비교가 빨라요.<br><sub>A Python 3 str is an immutable sequence of Unicode code points. CPython picks each string’s storage width from its largest code point (PEP 393): 1 byte per character for ASCII and Latin-1 text, 2 bytes when it contains Basic Multilingual Plane characters such as "안녕" (up to U+FFFF), and 4 bytes when it contains others such as emoji, so indexing is always O(1). Files, networks and databases need bytes, so encode converts to bytes and decode converts back. In UTF-8 each Hangul syllable takes 3 bytes, so "안녕".encode("utf-8") is the 6 bytes EC 95 88 EB 85 95. The rule is to convert only at the boundaries and use str inside the program. Strings cannot be modified, so s[0] = "H" raises TypeError, and repeated += in a loop may copy into a new string each time, O(n²) (CPython sometimes optimizes this in place, but it is not guaranteed). Collecting pieces in a list and calling "".join(parts) computes the total length first and builds the result once, O(n). Immutability lets the hash be computed once and cached, which suits dict keys, and short identifier-like strings are interned to share one object, making comparisons fast.</sub> |
| **정렬: 팀소트**<br><sub>Sorting: Timsort</sub> | 이미 정렬된 구간(run)을 찾아 삽입 정렬로 다듬고 병합하는 안정 정렬이에요. 거의 정렬된 데이터는 O(n), 최악에도 O(n log n)이에요.<br><sub>A stable sort that finds already sorted runs, extends them with insertion sort and merges them: O(n) on nearly sorted data and O(n log n) at worst.</sub> | list.sort()와 sorted()는 팀 피터스가 2002년 파이썬을 위해 만든 팀소트를 써요. 실제 데이터에는 이미 정렬된 구간이 많다는 점을 이용해, 먼저 배열을 훑으며 오름차순이나 엄격한 내림차순으로 이어진 구간(run)을 찾아요. [1, 2, 3, 7, 9, 8, 6, 4, 5]에서는 [1 2 3 7 9], [8 6 4], [5]가 run이에요. 내림차순 run은 제자리에서 뒤집고, 너무 짧은 run은 삽입 정렬로 최소 길이(minrun, 보통 32~64)까지 늘려요. run들을 스택에 쌓으며 길이가 균형을 이루도록 병합하는데, 3.11부터는 이 병합 순서를 Powersort 규칙으로 정해요. 병합 중 한쪽 run의 원소가 연달아 이기면 질주(galloping) 모드로 들어가 지수적으로 건너뛰며 비교 횟수를 줄여요. 그래서 이미 정렬되거나 거의 정렬된 입력은 O(n), 최악에도 O(n log n)이에요. 팀소트는 안정 정렬이라 키가 같은 원소의 원래 순서를 지켜서, 점수로 정렬해도 90점인 kim과 park의 순서가 그대로예요. 덕분에 이름으로 정렬한 뒤 점수로 다시 정렬하는 식으로 여러 기준을 차례로 적용할 수 있어요. key 함수는 원소마다 한 번만 호출되고, 비교 함수가 필요하면 functools.cmp\_to\_key로 감싸요. list.sort()는 제자리에서 None을 돌려주고, sorted()는 어떤 반복 가능 객체든 받아 새 리스트를 만들어요. 자바의 객체 정렬과 안드로이드, V8 엔진도 팀소트를 써요.<br><sub>list.sort() and sorted() use Timsort, which Tim Peters designed for Python in 2002. It exploits the sorted stretches common in real data by first scanning for runs that are ascending or strictly descending: in [1, 2, 3, 7, 9, 8, 6, 4, 5], the runs are [1 2 3 7 9], [8 6 4] and [5]. Descending runs are reversed in place, and runs that are too short are extended to a minimum length (minrun, usually 32 to 64) with insertion sort. Runs are pushed on a stack and merged so their lengths stay balanced, and since 3.11 that merge order follows the Powersort rule. When one run keeps winning during a merge, galloping mode skips ahead exponentially to cut comparisons. As a result, sorted or nearly sorted input takes O(n), and the worst case is O(n log n). Timsort is stable, keeping equal keys in their original order, so sorting by score leaves kim ahead of park among the 90s. That lets you apply several criteria in turn, sorting by name and then by score. The key function is called once per element, and a comparison function can be wrapped with functools.cmp\_to\_key. list.sort() sorts in place and returns None, while sorted() accepts any iterable and builds a new list. Java’s object sort, Android and the V8 engine use Timsort as well.</sub> |

Scopes are per function, so if, for and with blocks create no new scope, and a loop variable survives after the loop. If a name is assigned anywhere in a function, the compiler makes it local to that function, so reading it before the assignment raises UnboundLocalError. Rebinding a variable of an enclosing function needs nonlocal, and rebinding a module variable needs global. | **인자 규칙과 기본값**<br><sub>Arguments and defaults</sub> | 파라미터는 위치 전용, 위치·키워드 겸용, \*args, 키워드 전용, \*\*kwargs로 나뉘어요. 기본값은 def 때 한 번 계산돼서 가변 기본값은 호출 사이에 공유돼요.<br><sub>Parameters are positional-only, positional-or-keyword, \*args, keyword-only or \*\*kwargs. Calling add(1, 2) runs wrapper first, which logs, calls fn(1, 2) and returns the result. This layers concerns shared by many functions, such as logging, timing, caching (functools.cache), permission checks and retries, on top without editing their bodies. Plain wrapping would make add.\_\_name\_\_ "wrapper" and lose the docstring, so functools.wraps copies the name, the docstring and \_\_wrapped\_\_. | **이터레이션 프로토콜**<br><sub>The iteration protocol</sub> | for 문은 iter()로 이터레이터를 얻고 next()를 StopIteration이 날 때까지 불러요. 반복 가능 객체와 진행 상태를 가진 이터레이터는 서로 다른 객체예요.<br><sub>A for loop gets an iterator with iter() and calls next() until StopIteration. The iterable and the iterator, which holds the progress, are different objects.</sub> | for x in xs는 내부적으로 it = iter(xs)를 부른 뒤, 반복마다 x = next(it)를 하고 StopIteration 예외가 나면 끝나요. 이 약속이 이터레이션 프로토콜로, for 문뿐 아니라 언패킹, list(), sum(), in, zip, 컴프리헨션이 모두 이를 써요. \_\_iter\_\_를 가진 객체는 반복 가능(iterable)하고, \_\_iter\_\_가 돌려주는 이터레이터는 \_\_next\_\_로 값을 하나씩 내며 현재 위치를 기억해요. 리스트 [10, 20, 30]에 iter를 부르면 위치 0의 list\_iterator가 생기고, next를 부를 때마다 10, 20, 30을 돌려주며 위치를 옮기다가 끝나면 StopIteration을 던져요. 진행 상태가 리스트가 아니라 이터레이터에 있어서 한 리스트로 여러 반복을 동시에 돌릴 수 있지만, 이터레이터는 한 번 다 쓰면 끝이라 다시 돌리려면 iter()로 새로 만들어야 해요. 파일 객체, 딕셔너리, range, map, zip도 모두 이 프로토콜을 따르고, 특히 map, zip, filter, 파일은 그 자체가 이터레이터라 두 번 돌릴 수 없어요. 직접 만들 때는 \_\_iter\_\_와 \_\_next\_\_를 구현한 클래스도 되지만, 대개 제너레이터 함수가 훨씬 간단해요. itertools 모듈은 chain, islice, groupby처럼 이터레이터를 조합하는 도구를 줘요.<br><sub>Under the hood, for x in xs calls it = iter(xs), then does x = next(it) on every pass and stops at a StopIteration exception. This contract is the iteration protocol, used not only by for loops but by unpacking, list(), sum(), in, zip and comprehensions. An object with \_\_iter\_\_ is iterable, and the iterator its \_\_iter\_\_ returns produces values one at a time through \_\_next\_\_ while remembering its position. Calling iter on the list [10, 20, 30] creates a list\_iterator at position 0; each next returns 10, 20 and 30 in turn, advancing the position, and then raises StopIteration. Because progress lives in the iterator rather than the list, one list can drive several loops at once, but an exhausted iterator stays exhausted, so another pass needs a fresh one from iter(). File objects, dicts, range, map and zip all follow the protocol, and map, zip, filter and files are themselves iterators that cannot be traversed twice. A class implementing \_\_iter\_\_ and \_\_next\_\_ works for custom iteration, but a generator function is usually far simpler. The itertools module offers tools such as chain, islice and groupby for combining iterators.</sub> |
| **제너레이터**<br><sub>Generators</sub> | yield가 있는 함수는 부르면 제너레이터 객체를 돌려주고, next마다 다음 yield까지 실행했다가 멈춰요. 값을 필요할 때 하나씩 만들어 메모리를 아껴요.<br><sub>A function containing yield returns a generator object; each next runs it to the following yield and pauses. Values are made one at a time, on demand, saving memory.</sub> | 함수 본문에 yield가 있으면 그 함수는 제너레이터 함수가 돼요. countdown(3)을 불러도 본문은 실행되지 않고 제너레이터 객체만 생겨요. next(g)를 부르면 첫 yield까지 실행해 3을 내보내고, 지역 변수 n과 실행 위치를 담은 프레임을 그대로 얼려 둔 채 멈춰요. 다음 next는 멈춘 지점에서 이어서 n -= 1을 하고 2를, 그다음엔 1을 내보내며, 함수가 끝나면 StopIteration을 던져요. 그래서 제너레이터는 이터레이터를 만드는 가장 쉬운 방법이고, for 문에 바로 쓸 수 있어요. 값을 미리 다 만들지 않고 필요할 때 하나씩 만드는 지연 계산이라, 백만 개의 제곱을 담은 리스트는 포인터만 8.4MB(정수 객체는 별도)를 쓰지만 같은 제너레이터 표현식은 200바이트예요. 끝이 없는 수열, 큰 로그 파일을 한 줄씩 읽어 거르고 변환하는 파이프라인, 페이지 단위 API 결과 순회에 잘 맞아요. yield from은 다른 이터러블이나 하위 제너레이터에 위임하고, send()로 제너레이터 안에 값을 보낼 수도 있어요. 이 멈췄다 이어지는 장치는 이후 async/await 코루틴의 바탕이 되었어요. 단, 제너레이터도 이터레이터라서 한 번 다 쓰면 다시 쓸 수 없어요.<br><sub>A function whose body contains yield becomes a generator function. The following next resumes there, runs n -= 1 and emits 2, then 1, and when the function ends it raises StopIteration. That makes generators the easiest way to write iterators, usable directly in for loops. Values are produced lazily, one at a time, rather than all up front, so a list of a million squares needs 8.4 MB for its pointers alone (the int objects come on top), while the equivalent generator expression takes 200 bytes. Standard ABCs in collections.abc, such as Iterable, Mapping and Sequence, provide isinstance checks and default method implementations. typing.Protocol (3.8) is structural: a Quacks protocol describes only the shape of a quack method, and a type checker such as mypy treats Robot as compatible because it has a matching method, without inheriting. That also works for types whose inheritance you cannot change, such as third-party classes. @runtime\_checkable enables isinstance(x, Quacks), though it only checks that the method names exist. In short, duck typing enforces the contract at run time, ABCs through inheritance and Protocols through static checking.</sub> |
| **컨텍스트 매니저**<br><sub>Context managers</sub> | with 문은 \_\_enter\_\_로 자원을 얻고, 예외가 나도 \_\_exit\_\_로 반드시 정리해요. contextmanager를 쓰면 yield 하나로 매니저를 만들어요.<br><sub>A with statement acquires a resource through \_\_enter\_\_ and always cleans up through \_\_exit\_\_, even on errors. contextmanager builds one from a single yield.</sub> | 파일, 락, 데이터베이스 연결처럼 열었으면 반드시 닫아야 하는 자원은 예외가 나는 경로에서 정리를 빠뜨리기 쉬워요. with open("a.txt") as f:는 파일 객체의 \_\_enter\_\_를 불러 그 반환값을 f에 묶고 본문을 실행해요. 본문이 정상적으로 끝나든, 예외가 나든, return이나 break로 빠져나가든 블록을 나갈 때 \_\_exit\_\_(예외 타입, 값, 트레이스백)이 불려 파일이 닫혀요. \_\_exit\_\_가 참을 돌려주면 예외를 삼키고, 그렇지 않으면 예외가 계속 전파돼요. 즉 with 문은 \_\_enter\_\_를 부르고 본문을 try로, \_\_exit\_\_를 finally로 감싼 코드와 거의 같아요. 직접 클래스를 만들어도 되지만, contextlib.contextmanager를 쓰면 제너레이터 함수 하나로 매니저를 만들 수 있어요. yield 앞의 코드가 enter, 뒤의 코드가 exit 역할이고, 예외에도 정리하려면 yield를 try/finally로 감싸요. with a, b:로 여러 자원을 한 번에 다루고, 개수가 실행 중에 정해지면 contextlib.ExitStack을 써요. threading.Lock, 데이터베이스 트랜잭션, tempfile.TemporaryDirectory, decimal.localcontext 등 표준 라이브러리 곳곳이 컨텍스트 매니저이고, 비동기 자원은 \_\_aenter\_\_와 \_\_aexit\_\_를 쓰는 async with로 다뤄요.<br><sub>Resources that must be closed once opened, such as files, locks and database connections, are easy to leak on error paths. with open("a.txt") as f: calls the file object’s \_\_enter\_\_, binds its return value to f and runs the body. Whether the body finishes normally, raises, or leaves through return or break, \_\_exit\_\_(exception type, value, traceback) is called on the way out and the file is closed. If \_\_exit\_\_ returns true the exception is swallowed; otherwise it keeps propagating. A with statement is thus nearly the same as calling \_\_enter\_\_ and wrapping the body in try with \_\_exit\_\_ in finally. | **바이트코드와 가상 머신**<br><sub>Bytecode and the virtual machine</sub> | CPython은 소스를 AST로, 다시 바이트코드로 컴파일하고, 값 스택을 쓰는 평가 루프가 명령을 하나씩 실행해요. 3.11부터는 명령이 타입에 맞게 특수화돼요.<br><sub>CPython compiles source into an AST and then bytecode, and an evaluation loop with a value stack executes the instructions one by one. Since 3.11 instructions specialize to the types they see.</sub> | 파이썬을 "인터프리터 언어"라고 하지만 CPython은 소스를 그대로 해석하지 않아요. 먼저 토큰으로 나누고 구문 분석해 추상 구문 트리(AST)를 만들고, 이를 바이트코드라는 가상 머신 명령어로 컴파일해 함수마다 코드 객체에 담아요. 그런 다음 C로 작성된 평가 루프(ceval)가 명령을 하나씩 꺼내 실행해요. dis 모듈로 이 바이트코드를 볼 수 있는데, a + b \* 2는 a와 b, 상수 2를 불러오고 곱하고 더하고 돌려주는 여섯 개 남짓의 명령이 돼요. CPython 가상 머신은 스택 기반이라, 불러오기 명령은 값을 스택에 넣고 연산 명령은 피연산자를 꺼내 계산한 결과를 다시 넣어요. a = 3, b = 4이면 스택이 [3], [3, 4], [3, 4, 2]로 쌓였다가 곱셈 뒤 [3, 8], 덧셈 뒤 [11]이 돼요. 명령 하나하나가 타입 검사와 디스패치를 거치는 것이 파이썬이 느린 이유 중 하나라서, 3.11의 적응형 특수화 인터프리터(PEP 659)는 실제로 정수만 더해지는 자리의 BINARY\_OP를 BINARY\_OP\_ADD\_INT로 바꾸는 식으로 명령을 특수화해 평균 약 25% 빨라졌어요. 바이트코드는 버전마다 바뀌는 내부 구현이라 .pyc 파일도 버전별로 따로 만들어지고, PyPy처럼 같은 언어를 JIT 컴파일러로 실행하는 다른 구현도 있어요.<br><sub>Python is called an interpreted language, but CPython does not interpret source text directly. It tokenizes and parses the source into an abstract syntax tree (AST), compiles that into bytecode, virtual-machine instructions stored in a code object per function, and then an evaluation loop written in C (ceval) fetches and executes the instructions one at a time. The dis module shows this bytecode: a + b \* 2 becomes about six instructions that load a, b and the constant 2, multiply, add and return. The CPython virtual machine is stack-based: load instructions push values, and operation instructions pop their operands and push the result. With a = 3 and b = 4, the stack grows to [3], [3, 4] and [3, 4, 2], becomes [3, 8] after the multiplication and [11] after the addition. Each instruction going through type checks and dispatch is one reason Python is slow, so the specializing adaptive interpreter of 3.11 (PEP 659) rewrites instructions for the types they actually see, turning a BINARY\_OP that only ever adds ints into BINARY\_OP\_ADD\_INT, which made Python about 25% faster on average. Bytecode is an internal detail that changes between versions, so .pyc files are built per version, and other implementations such as PyPy run the same language with a JIT compiler.</sub> |
| **참조 카운팅과 가비지 컬렉션**<br><sub>Reference counting and garbage collection</sub> | 객체는 참조 카운트가 0이 되는 순간 해제돼요. 서로를 가리키는 순환은 카운팅으로 풀리지 않아서, 순환 가비지 컬렉터가 바깥에서 닿지 않는 무리를 찾아 지워요.<br><sub>Objects are freed the moment their reference count hits 0. Cycles of mutual references defeat counting, so a cycle collector finds and frees groups unreachable from outside.</sub> | CPython의 기본 메모리 관리는 참조 카운팅이에요. 객체마다 자신을 가리키는 참조 수를 세서, 이름에 대입하거나 리스트에 넣으면 늘고 이름이 사라지거나 함수가 끝나면 줄어요. 카운트가 0이 되는 순간 바로 해제되므로 메모리 회수가 예측 가능하고, 파일이나 소켓 같은 자원도 대개 즉시 닫혀요. 하지만 a와 b가 서로를 담으면 순환이 생겨요. 이름 a, b가 각각 하나, 서로가 하나씩 가리켜 카운트가 2인데, del a, b로 이름을 지워도 서로의 참조가 남아 1로 멈춰요. 아무도 쓸 수 없는 객체인데 카운팅만으로는 영원히 해제되지 않죠. 그래서 CPython에는 순환 가비지 컬렉터(gc 모듈)가 따로 있어요. 리스트, 딕셔너리, 사용자 객체처럼 다른 객체를 담을 수 있는 컨테이너들을 추적하다가, 각 객체의 카운트에서 컨테이너끼리의 내부 참조를 빼 봐요. 남는 값이 0인 무리는 바깥에서 닿지 않는다는 뜻이라 함께 회수해요. 대부분의 객체는 금방 죽는다는 관찰에 따라 새 객체는 자주, 오래 살아남은 객체는 드물게 검사하는 세대별 방식을 쓰고, 최근 버전은 한 번에 멈추는 시간을 줄이는 쪽으로 다듬어지고 있어요. 순환을 만들지 않으려면 부모 참조 같은 곳에 weakref를 쓰고, 자원 정리는 소멸에 기대기보다 with 문으로 명시하는 것이 안전해요.<br><sub>CPython’s main memory management is reference counting. Each object counts the references to it: binding a name or adding it to a list raises the count, and a name disappearing or a function returning lowers it. The object is freed the instant the count reaches 0, so reclamation is predictable and resources such as files and sockets usually close immediately. But when a and b contain each other, they form a cycle. Each is referenced once by its name and once by the other, a count of 2, and after del a, b the mutual references leave both at 1. Nobody can use these objects, yet counting alone would never free them. CPython therefore has a separate cyclic garbage collector (the gc module). It tracks containers that can hold other objects, such as lists, dicts and user objects, and subtracts the references among those containers from each object’s count. Groups left at 0 cannot be reached from outside and are freed together. Following the observation that most objects die young, it is generational, scanning new objects often and long-lived ones rarely, and recent versions keep refining it to shorten individual pauses. To avoid cycles, use weakref for links such as parent pointers, and rather than relying on destruction, make cleanup explicit with with.</sub> |
| **GIL**<br><sub>The GIL</sub> | CPython은 한 프로세스에서 한 번에 한 스레드만 바이트코드를 실행해요. I/O는 스레드로 잘 겹치지만 CPU 작업은 프로세스나 네이티브 코드로 나눠야 하고, GIL 없는 빌드도 나왔어요.<br><sub>CPython runs bytecode on only one thread per process at a time. I/O overlaps well with threads, but CPU work needs processes or native code, and a free-threaded build has arrived.</sub> | 전역 인터프리터 락(GIL)은 CPython 인터프리터 전체를 감싸는 락으로, 한 프로세스 안에서는 한 번에 한 스레드만 파이썬 바이트코드를 실행하게 해요. 모든 객체의 참조 카운트를 세밀한 락 없이 안전하게 고치고, C 확장을 단순하게 만들기 위한 설계였어요. 그래서 순수 파이썬으로 된 CPU 작업은 스레드를 여러 개 띄워도 스레드들이 약 5ms(sys.getswitchinterval)마다 GIL을 번갈아 잡을 뿐이라, 한 스레드로 돌린 것과 비슷하거나 오히려 느려요. 반면 네트워크 응답이나 디스크를 기다리는 동안에는 GIL을 놓기 때문에, 웹 요청 여러 개를 보내는 I/O 작업은 스레드로 잘 겹쳐요. CPU 병렬이 필요하면 프로세스마다 인터프리터와 GIL이 따로 있는 multiprocessing이나 concurrent.futures.ProcessPoolExecutor를 쓰거나, 계산 중 GIL을 놓는 NumPy 같은 C 확장에 맡겨요. 이런 제약을 풀기 위해 PEP 703의 GIL 없는(free-threaded) 빌드가 3.13에서 실험적으로 나왔고, 3.14부터 공식 지원 단계가 됐어요(아직 기본 빌드는 아니에요). 3.12부터는 서브인터프리터마다 GIL을 따로 두는 방식(PEP 684)도 생겼어요. GIL은 개별 바이트코드 실행만 보호할 뿐 x += 1 같은 연산의 원자성을 보장하지 않아서, 공유 데이터에는 GIL이 있든 없든 락이 필요해요.<br><sub>The global interpreter lock (GIL) is a lock around the whole CPython interpreter that lets only one thread per process execute Python bytecode at a time. It was designed to let every object’s reference count be updated safely without fine-grained locks and to keep C extensions simple. So for pure-Python CPU work, multiple threads merely take turns holding the GIL about every 5 ms (sys.getswitchinterval), running about as fast as a single thread or slower. While waiting on network responses or disk, however, a thread releases the GIL, so I/O-bound work such as sending many web requests overlaps well with threads. For CPU parallelism, use multiprocessing or concurrent.futures.ProcessPoolExecutor, where each process has its own interpreter and GIL, or hand the work to C extensions such as NumPy that release the GIL while computing. To lift the constraint, PEP 703’s free-threaded build appeared experimentally in 3.13 and became officially supported in 3.14, though it is not yet the default build. Since 3.12, subinterpreters can also have a GIL each (PEP 684). The GIL only protects the execution of individual bytecodes and does not make operations such as x += 1 atomic, so shared data needs locks with or without it.</sub> |
| **import 시스템**<br><sub>The import system</sub> | import는 sys.modules 캐시를 먼저 보고, 없으면 sys.path를 뒤져 모듈을 찾아 한 번 실행해요. 컴파일한 바이트코드는 \_\_pycache\_\_에 캐시돼요.<br><sub>import checks the sys.modules cache first and otherwise searches sys.path, finds the module and runs it once. Compiled bytecode is cached in \_\_pycache\_\_.</sub> | import json을 만나면 파이썬은 먼저 sys.modules 딕셔너리를 봐요. 이미 불러온 모듈이면 그 객체를 바로 돌려주므로, 프로그램 곳곳에서 import해도 모듈은 하나이고 두 번째 import는 거의 비용이 없어요. 없으면 파인더(finder)들이 sys.path의 경로를 차례로 뒤져요. sys.path는 실행한 스크립트의 폴더, PYTHONPATH 환경 변수, 표준 라이브러리, site-packages 순서라서, 내 프로젝트에 random.py 같은 파일을 두면 표준 모듈을 가려 버리는 실수가 생겨요. 찾으면 로더(loader)가 모듈 객체를 만들어 먼저 sys.modules에 넣고, 모듈 코드를 위에서 아래로 한 번 실행해 그 안에서 정의된 이름들을 모듈 속성으로 만들어요. 그래서 모듈 최상위의 코드는 처음 import할 때 한 번만 실행돼요. 두 모듈이 서로를 import하는 순환 구조에서는 한쪽이 아직 실행 중인 모듈을 보게 되어 이름이 없다는 오류가 나는데, import를 함수 안으로 옮기거나 공통 부분을 분리해 풀어요. 컴파일한 바이트코드는 \_\_pycache\_\_ 폴더에 util.cpython-313.pyc처럼 버전별로 캐시되고, 소스가 바뀌면 다시 만들어져요. 직접 실행한 파일의 \_\_name\_\_은 "\_\_main\_\_"이고 import될 때는 모듈 이름이라, if \_\_name\_\_ == "\_\_main\_\_": 아래에 둔 코드는 스크립트로 실행할 때만 돌아요.<br><sub>On import json, Python first looks in the sys.modules dict. An already loaded module is returned immediately, so however many places import it there is only one module object, and a second import costs almost nothing. Otherwise finders search the entries of sys.path in order. sys.path holds the folder of the script being run, the PYTHONPATH environment variable, the standard library and site-packages, which is why a file such as random.py in your project can shadow a standard module by mistake. Once found, a loader creates the module object, inserts it into sys.modules first, and runs the module’s code once from top to bottom, turning the names it defines into module attributes. When two modules import each other, one sees the other while it is still executing and finds names missing, which is fixed by moving the import into a function or splitting out the shared part. Compiled bytecode is cached per version in \_\_pycache\_\_, as in util.cpython-313.pyc, and rebuilt when the source changes. A file run directly has \_\_name\_\_ set to "\_\_main\_\_" and an imported one has its module name, so code under if \_\_name\_\_ == "\_\_main\_\_": runs only when the file is executed as a script.</sub> |
| **예외 처리**<br><sub>Exception handling</sub> | try의 예외는 맞는 except로 가고, 없으면 finally를 거쳐 호출자로 올라가요. else는 예외가 없을 때만, finally는 언제나 실행되고, from으로 원인을 연결해요.<br><sub>An exception in try goes to the matching except, or else passes through finally to the caller. else runs only without an error, finally always runs, and from chains the cause.</sub> | 파이썬은 오류를 반환값 대신 예외로 알려요. try 본문에서 예외가 나지 않으면 else 블록이 실행되고, 마지막으로 finally가 실행돼요. else에는 성공했을 때만 할 후속 작업을 두어, try가 보호하는 범위를 꼭 필요한 줄로 좁혀요. int(text)가 ValueError를 던지면 그 아래 줄은 건너뛰고 타입이 맞는 첫 except로 가서 처리한 뒤 finally를 실행해요. 맞는 except가 없으면 finally를 실행한 뒤 예외가 호출 스택을 따라 위로 올라가고, 끝까지 잡히지 않으면 트레이스백을 출력하고 프로그램이 끝나요. except 안에서 raise ConfigError("bad") from e처럼 새 예외를 던지면 원래 예외가 원인(\_\_cause\_\_)으로 연결되어, 트레이스백에 "위 예외가 다음 예외의 직접 원인"이라는 문구와 함께 둘 다 남아요. 모든 예외는 BaseException 아래 계층을 이루고, 일반적인 오류는 Exception 아래에 있어서 except Exception은 Ctrl+C로 생기는 KeyboardInterrupt와 SystemExit을 잡지 않아요. 파이썬은 미리 확인하기(LBYL)보다 일단 해 보고 실패를 처리하는 EAFP 스타일을 선호하지만, 너무 넓은 except는 버그를 숨기니 예상하는 예외만 잡아요. 3.11부터는 동시 작업에서 여러 예외를 한꺼번에 다루는 ExceptionGroup과 except\*가 생겼어요.<br><sub>Python reports errors with exceptions rather than return values. If the try body raises nothing, the else block runs, then finally. Putting follow-up work that should happen only on success in else keeps the try narrowed to the lines that need guarding. If int(text) raises ValueError, the remaining lines are skipped, the first except whose type matches handles it, and then finally runs. With no matching except, finally runs and the exception climbs the call stack; if nothing catches it, a traceback is printed and the program ends. Raising a new exception inside except, as in raise ConfigError("bad") from e, links the original as its cause (\_\_cause\_\_), so the traceback shows both with the line “The above exception was the direct cause of the following exception”. Python favors the EAFP style, trying first and handling failure, over checking first (LBYL), but broad except clauses hide bugs, so catch only the exceptions you expect. Since 3.11, ExceptionGroup and except\* handle several exceptions at once, as from concurrent tasks.</sub> |

## 기다림은 겹치고 계산은 나누기 · Overlap the waiting, split the computing

이벤트 루프 하나로 기다림을 겹치는 asyncio, 작업 성격에 따라 스레드와 프로세스를 고르는 법, 루프를 C로 옮기는 NumPy 벡터화와 브로드캐스팅, 그리고 재고 고치는 프로파일링과 최적화를 봐요.  
*asyncio, which overlaps waiting on one event loop, choosing threads or processes by the kind of work, NumPy vectorization and broadcasting, which move loops into C, and profiling and optimization: measure, then fix.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **asyncio와 이벤트 루프**<br><sub>asyncio and the event loop</sub> | async/await 코루틴은 await에서 이벤트 루프에 제어를 넘겨, 스레드 하나로 많은 기다림을 겹쳐요. 루프를 막는 동기 호출은 피해야 해요.<br><sub>async/await coroutines hand control to the event loop at await, overlapping many waits on one thread. Blocking synchronous calls must be kept off the loop.</sub> | asyncio는 스레드 하나에서 여러 작업을 번갈아 실행하는 협력적 동시성이에요. async def로 정의한 함수를 부르면 본문은 실행되지 않고 코루틴 객체만 생기고, asyncio.run(main())이 이벤트 루프를 만들어 이를 실행해요. 코루틴이 await asyncio.sleep(1)이나 네트워크 응답처럼 기다려야 하는 지점에 이르면 그 자리에서 멈추고 제어를 루프에 돌려줘요. 루프는 그사이 실행 가능한 다른 작업을 돌리고, 기다리던 일이 끝나면 멈췄던 코루틴을 이어서 실행해요. 그래서 1초씩 기다리는 fetch 세 개를 asyncio.gather로 함께 돌리면 순서대로 기다리는 3초가 아니라 약 1초 만에 [0, 1, 2]를 얻어요. 스레드와 달리 작업이 바뀌는 지점이 await로 명확해서 경쟁 상태를 따지기 쉽고, 작업 하나가 가벼워 수천, 수만 개의 연결을 다루는 서버에 잘 맞아요. 대신 협력적이라 await하지 않는 코드, 예를 들어 time.sleep이나 무거운 계산, 동기식 HTTP 라이브러리 호출은 루프 전체를 멈춰 모든 작업이 함께 멈춰요. 그런 일은 asyncio.to\_thread나 run\_in\_executor로 다른 스레드나 프로세스에 보내고, 라이브러리도 aiohttp, httpx, asyncpg 같은 비동기 버전을 써요. 3.11부터는 asyncio.TaskGroup으로 작업을 묶어 하나가 실패하면 나머지를 취소하고 예외를 모아서 처리할 수 있어요.<br><sub>asyncio is cooperative concurrency that runs many tasks in turn on one thread. Calling a function defined with async def runs none of its body and returns a coroutine object, and asyncio.run(main()) creates an event loop to run it. When a coroutine reaches a point where it must wait, such as await asyncio.sleep(1) or a network response, it pauses there and returns control to the loop. The loop runs other ready tasks meanwhile and resumes the paused coroutine when its wait is over. So three fetches that each wait a second, run together with asyncio.gather, return [0, 1, 2] in about 1 second rather than the 3 seconds of waiting one by one. Unlike threads, task switches happen only at await, which makes race conditions easier to reason about, and tasks are cheap, suiting servers that juggle thousands of connections. Being cooperative, though, any code that never awaits, such as time.sleep, heavy computation or a synchronous HTTP library call, stalls the whole loop and every task with it. Send such work to another thread or process with asyncio.to\_thread or run\_in\_executor, and use async libraries such as aiohttp, httpx and asyncpg. NumPy, 압축, 해시처럼 C로 구현된 계산은 실행 중 GIL을 놓아 스레드로도 병렬이 돼요. 프로세스는 메모리를 따로 쓰므로 큰 데이터를 매번 복사하면 이득이 사라지니, multiprocessing.shared\_memory를 쓰거나 데이터를 나눠 각 프로세스가 직접 읽게 해요. 작업 하나가 너무 작으면 나누는 비용이 계산보다 커서 오히려 느려지니, chunksize로 묶어서 보내요. 무엇보다 먼저 병목이 CPU인지 I/O인지 재 보는 것이 출발점이에요.<br><sub>concurrent.futures offers ThreadPoolExecutor and ProcessPoolExecutor behind one interface: ex.map(fn, items) or ex.submit(fn, x) hands out work and collects results. Which to use depends on what the work waits for. Running four one-second pure-Python computations on a thread pool takes about 4 seconds, because the GIL lets one thread execute bytecode at a time. A process pool starts processes with their own interpreter and GIL per core and finishes in about 1 second of true parallelism, plus the cost of starting processes and pickling arguments and results back and forth (the numbers here are illustrative). Work that waits on network or disk, on the other hand, releases the GIL while waiting, so threads also finish in about 1 second, and for very many connections asyncio is lighter still. Computation implemented in C, such as NumPy, compression and hashing, releases the GIL while running and parallelizes with threads too. Processes have separate memory, so copying large data every time wipes out the gain; use multiprocessing.shared\_memory or split the data so each process reads its own part. Jobs that are too small cost more to distribute than to compute, so batch them with chunksize. The starting point is always measuring whether the bottleneck is CPU or I/O.</sub> |
| **NumPy 벡터화와 브로드캐스팅**<br><sub>NumPy vectorization and broadcasting</sub> | ndarray는 한 타입의 값을 연속 버퍼에 담아, 배열 전체 연산을 C 루프 한 번으로 처리해요. 모양이 다른 배열은 브로드캐스팅으로 복사 없이 맞춰요.<br><sub>An ndarray keeps values of one type in a contiguous buffer, so whole-array operations run as a single C loop. | **프로파일링과 최적화**<br><sub>Profiling and optimization</sub> | 추측하지 말고 프로파일러로 핫스팟을 찾은 뒤, 알고리즘과 자료구조, 내장 함수와 라이브러리, 네이티브 코드 순서로 고쳐요.<br><sub>Instead of guessing, find the hotspot with a profiler, then fix algorithms and data structures, built-ins and libraries, and native code, in that order.</sub> | 성능 문제의 원인은 대개 짐작과 다른 곳에 있어서, 먼저 재는 것이 최적화의 첫걸음이에요. python -m cProfile -s tottime app.py는 함수마다 호출 횟수(ncalls)와 그 함수 자체에서 쓴 시간(tottime), 하위 호출을 포함한 시간(cumtime)을 보여줘요. 여기서 fib가 269만 번 불렸다는 사실이 바로 핫스팟을 가리켜요. 순진한 재귀 fib(30)은 같은 값을 반복해 계산하는데, functools.cache(또는 lru\_cache)로 인자별 결과를 기억하면 호출이 31번으로 줄어 이 환경에서 83ms가 22µs가 됐어요. 자료구조 선택도 결정적이에요. 리스트의 in은 처음부터 하나씩 비교하는 O(n)이라 2만 개 중복 제거가 559ms였지만, 집합으로 바꾸면 평균 O(1)이라 1.4ms로 약 400배 빨라요. 일반적인 순서는 알고리즘과 자료구조를 먼저 고치고, 그다음 반복문을 내장 함수, 컴프리헨션, NumPy 같은 라이브러리로 옮기고, 그래도 부족하면 Cython, C 확장, PyPy 같은 네이티브 실행으로 가는 거예요. 작은 코드 조각 비교는 timeit, 메모리 사용은 tracemalloc, 운영 중인 서비스는 멈추지 않고 들여다보는 py-spy 같은 샘플링 프로파일러를 써요. 프로파일러 자체가 실행을 느리게 하므로 절대값보다 비율을 보고, 고친 뒤에는 다시 재서 정말 빨라졌는지 확인해요.<br><sub>Performance problems usually live somewhere other than where you would guess, so measuring is the first step of optimization. python -m cProfile -s tottime app.py shows each function’s call count (ncalls), the time spent in the function itself (tottime) and the time including its callees (cumtime). Use timeit for comparing small snippets, tracemalloc for memory and sampling profilers such as py-spy for services in production, which they inspect without stopping. Profilers slow execution themselves, so read ratios rather than absolute times, and measure again after a fix to confirm it really helped.</sub> |

## 큰 코드베이스를 지키는 도구 · Tools that keep large codebases healthy

| **구조적 패턴 매칭**<br><sub>Structural pattern matching</sub> | match 문은 값의 모양을 패턴과 비교하고 맞으면 값을 꺼내요. 위에서부터 처음 맞는 case 하나만 실행하고, 시퀀스·매핑·클래스·or·가드 패턴을 써요.<br><sub>The match statement compares a value’s shape against patterns and extracts values when one fits. | **collections와 heapq**<br><sub>collections and heapq</sub> | Counter는 개수를, defaultdict는 기본값을, deque는 양끝 O(1) 큐를, heapq는 리스트 기반 최소 힙을 줘요. 직접 구현하지 않아도 되는 표준 자료구조예요.<br><sub>Counter counts, defaultdict supplies defaults, deque is an O(1) double-ended queue and heapq is a list-based min-heap: standard structures you never need to write yourself.</sub> | 표준 라이브러리의 collections와 heapq는 자주 필요한 자료구조를 C로 빠르게 구현해 둔 모음이에요. Counter는 개수를 세는 딕셔너리로, Counter("banana")는 a 3, n 2, b 1을 세고 most\_common(2)가 가장 많은 두 개를 돌려줘요. 덧셈과 뺄셈으로 두 집계를 합치거나 비교할 수도 있어요. defaultdict(list)는 없는 키를 읽을 때 list()를 불러 빈 리스트를 넣어 주므로, 항목을 그룹으로 묶을 때 키가 있는지 확인하는 코드 없이 바로 g[key].append(x)를 할 수 있어요. deque는 양쪽 끝의 추가와 삭제가 O(1)인 큐로, 리스트의 pop(0)이 O(n)인 문제를 피해요. maxlen=3을 주면 꽉 찬 상태에서 4를 넣을 때 반대쪽의 1이 밀려나서 최근 N개 기록이나 슬라이딩 윈도우에 좋아요. heapq는 리스트를 완전 이진 트리로 보는 최소 힙 함수들이에요. heapify가 [5, 1, 4, 2]를 [1, 2, 4, 5]로 재배치해 맨 앞이 항상 최솟값이 되고, heappush와 heappop은 O(log n)이라 우선순위 큐, 작업 스케줄러, 다익스트라 알고리즘에 써요. nsmallest와 nlargest는 상위 k개를 전체 정렬 없이 찾아요. 그 밖에 namedtuple, OrderedDict, ChainMap, 정렬된 리스트에 이진 탐색으로 삽입하는 bisect도 있어요.<br><sub>The standard library’s collections and heapq offer frequently needed data structures, implemented quickly in C. Counter is a dict for counting: Counter("banana") counts a 3, n 2 and b 1, and most\_common(2) returns the top two, while addition and subtraction combine or compare tallies. defaultdict(list) calls list() to insert an empty list when a missing key is read, so grouping items is just g[key].append(x) with no check for the key. deque is a queue with O(1) additions and removals at both ends, avoiding the O(n) cost of a list’s pop(0). With maxlen=3, adding 4 to a full deque pushes 1 out of the other end, ideal for recent-history logs and sliding windows. heapq is a set of functions that treat a list as a complete binary tree forming a min-heap. heapify rearranges [5, 1, 4, 2] into [1, 2, 4, 5] so the front is always the minimum, and heappush and heappop are O(log n), serving priority queues, task schedulers and Dijkstra’s algorithm. nsmallest and nlargest find the top k without a full sort. There are also namedtuple, OrderedDict, ChainMap and bisect, which inserts into sorted lists with binary search.</sub> |

Keep the .venv folder out of git but commit the lock file.</sub> |
| **pytest로 테스트하기**<br><sub>Testing with pytest</sub> | pytest는 test\_ 함수를 자동으로 찾고, fixture로 준비와 정리를 주입하며, 평범한 assert를 다시 써서 실패한 값을 자세히 보여줘요.<br><sub>pytest discovers test\_ functions automatically, injects setup and teardown through fixtures, and rewrites plain assert statements to show failing values in detail.</sub> | pytest는 파이썬에서 가장 널리 쓰이는 테스트 프레임워크예요. test\_\*.py 파일에서 test\_로 시작하는 함수를 자동으로 찾아 실행하므로 클래스나 등록 코드가 필요 없어요. @pytest.mark.parametrize("n", [1, 2, 3])는 같은 테스트를 값마다 따로 만들어 test\_double[1], [2], [3]처럼 개별 결과를 보여줘서, 경계값과 여러 사례를 짧게 시험해요. fixture는 테스트에 필요한 준비물을 만드는 함수로, 테스트 함수의 인자 이름이 db이면 같은 이름의 fixture가 자동으로 주입돼요. yield 앞에서 데이터베이스에 연결하고, 테스트가 끝나면 성공이든 실패든 yield 뒤에서 연결을 닫아요. scope="module"이나 "session"으로 여러 테스트가 한 번 만든 준비물을 공유할 수도 있고, conftest.py에 두면 여러 파일에서 함께 써요. 단언은 특별한 함수 없이 평범한 assert를 써요. pytest가 import할 때 assert 문을 다시 써서, double(3)이 7을 돌려주면 "assert 7 == 6, where 7 = double(3)"처럼 식의 중간 값을 모두 보여줘요. 결과는 2 passed, 1 failed처럼 요약되고, -x는 첫 실패에서 멈추며 -k는 이름으로 골라 실행해요. 외부 API나 시간을 바꿔치는 monkeypatch와 unittest.mock, 커버리지를 재는 pytest-cov, 병렬 실행하는 pytest-xdist 같은 플러그인 생태계가 풍부하고, 표준 unittest 방식의 테스트도 그대로 실행해요.<br><sub>pytest is the most widely used test framework in Python.
