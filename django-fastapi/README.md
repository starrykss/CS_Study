| **WSGI와 ASGI**<br><sub>WSGI and ASGI</sub> | WSGI는 요청마다 함수를 한 번 부르는 동기 약속이고, ASGI는 비동기 약속이에요. 0.1초 걸리는 뷰 20개를 동기 워커 하나는 2.1초에, async 뷰는 0.22초에 끝냈어요.<br><sub>WSGI is a synchronous contract that calls a function once per request, and ASGI is an asynchronous one. One sync worker finished 20 views taking 0.1 s each in 2.1 s; async views finished in 0.22 s.</sub> | 파이썬의 웹 서버와 웹 프레임워크는 서로를 몰라도 함께 쓸 수 있어요. 둘 사이에 정해진 약속이 있기 때문이에요. 오래된 약속인 WSGI는 서버가 요청마다 app(environ, start\_response)라는 함수를 한 번 부르고, 프레임워크가 응답을 돌려줄 때까지 기다리는 동기 방식이에요. gunicorn, uWSGI 같은 서버와 Django, Flask가 이 약속을 따라요. 새 약속인 ASGI는 async def app(scope, receive, send)라는 코루틴으로 연결을 다루고, 메시지를 받고 보내는 것을 비동기로 처리해요. HTTP뿐 아니라 웹소켓처럼 오래 열려 있는 연결도 다룰 수 있어요. uvicorn, Hypercorn, Daphne 같은 서버와 FastAPI, Starlette가 이 약속을 따르고, Django는 둘 다 지원해서 startproject가 wsgi.py와 asgi.py를 함께 만들어 줘요. WSGI의 동기 워커는 응답을 돌려줄 때까지 다른 요청을 받지 못해요. 0.1초를 기다리는 뷰에 요청 20개를 동시에 보내자, gunicorn 동기 워커 하나는 하나씩 처리해 전체 2.1초가 걸렸고 초당 9.5개를 처리했어요. 마지막 요청은 2초 넘게 기다렸어요. --threads 4로 스레드 4개를 주자 0.55초, 초당 36개가 됐어요. 그래서 WSGI 서버는 워커 프로세스와 스레드 수로 동시에 처리할 요청 수를 정해요. ASGI 서버 uvicorn에서 await asyncio.sleep(0.1)로 기다리는 async 뷰를 돌리자, 한 요청이 기다리는 동안 이벤트 루프가 다른 요청을 받아 20개가 0.22초 만에 모두 끝났어요. 스레드를 늘리지 않고도 프로세스 하나가 수많은 대기 중인 연결을 들고 있을 수 있어요. 다만 ASGI가 요청 하나를 빠르게 만들지는 않아요. 외부 API 호출, 웹소켓, 긴 폴링처럼 기다리는 시간이 대부분인 서비스에서 이득이 크고, 계산이 대부분인 요청에는 차이가 없어요. 또 async 뷰 안에서 동기 코드로 기다리면 이벤트 루프 전체가 멈춰서 오히려 나빠지는데, 이 문제는 뒤의 비동기 섹션에서 직접 재요. Django에서 ASGI를 쓰려면 미들웨어와 ORM 호출까지 비동기 경로를 따라야 효과가 나요.<br><sub>Python web servers and web frameworks can be combined without knowing about each other, because a fixed contract sits between them. The older contract, WSGI, is synchronous: the server calls a function app(environ, start\_response) once per request and waits until the framework returns a response. Servers such as gunicorn and uWSGI and frameworks such as Django and Flask follow it. The newer contract, ASGI, handles connections through a coroutine async def app(scope, receive, send), receiving and sending messages asynchronously. Beyond HTTP, it can handle long-lived connections such as WebSockets. Servers such as uvicorn, Hypercorn and Daphne and frameworks such as FastAPI and Starlette follow it, and Django supports both, so startproject creates wsgi.py and asgi.py together. A WSGI sync worker cannot accept another request until it returns a response. Sending 20 concurrent requests to a view that waits 0.1 s made one gunicorn sync worker handle them one at a time, taking 2.1 s in total at 9.5 requests per second, with the last request waiting over 2 seconds. Giving it 4 threads with --threads 4 brought that to 0.55 s, 36 per second. That is why WSGI servers set how many requests run at once through the number of worker processes and threads. Running an async view that waits with await asyncio.sleep(0.1) under the ASGI server uvicorn let the event loop accept other requests while one waited, and all 20 finished within 0.22 s. Without adding threads, a single process can hold many waiting connections. ASGI does not make a single request faster, though. It pays off for services that spend most of their time waiting, such as external API calls, WebSockets and long polling, and makes no difference for requests that are mostly computation. Waiting with synchronous code inside an async view also stops the whole event loop and makes things worse, a problem measured directly in the async section later. To benefit from ASGI in Django, middleware and ORM calls must follow the asynchronous path too.</sub> |
| **미들웨어의 순서**<br><sub>Middleware order</sub> | 요청은 MIDDLEWARE 목록을 위에서 아래로, 응답은 아래에서 위로 지나가요. 중간에서 응답을 돌려주면 안쪽은 실행되지 않고, 기본 미들웨어 7개는 요청당 약 63µs를 더했어요.<br><sub>Requests pass down the MIDDLEWARE list and responses come back up. Answering early skips the inner layers, and the 7 default middleware added about 63 µs per request.</sub> | 미들웨어는 모든 요청과 응답이 거쳐 가는 층이에요. 세션 불러오기, 로그인 사용자 확인, CSRF 검사, 보안 헤더 추가처럼 뷰마다 반복하면 안 되는 일을 한곳에서 처리해요. Django의 미들웨어는 다음 단계를 부르는 함수 get\_response를 받아 그것을 감싼 함수를 돌려주는 구조예요. 그래서 MIDDLEWARE 목록은 양파 껍질처럼 바깥에서 안쪽으로 겹쳐져요. 이름을 기록하는 미들웨어 A, B, C를 이 순서로 넣고 요청을 보내자 기록은 A in, B in, C in, 뷰, C out, B out, A out이었어요. 요청은 목록의 위에서 아래로 내려가 뷰에 닿고, 응답은 아래에서 위로 거꾸로 돌아 나와요. 바깥에 있는 미들웨어는 안쪽 전체가 만든 응답을 보게 되므로, 응답을 압축하거나 헤더를 덧붙이는 미들웨어는 대개 바깥쪽에 둬요. 미들웨어는 get\_response를 부르지 않고 응답을 직접 돌려줄 수도 있어요. B가 특정 조건에서 403을 돌려주게 하자, C와 뷰는 아예 실행되지 않았고 기록은 A in, B in, B blocks, A out이었어요. 로그인하지 않은 사용자를 막거나, IP를 차단하거나, 요청 수를 제한하는 기능이 이렇게 동작해요. 순서가 중요한 미들웨어도 있어요. AuthenticationMiddleware는 SessionMiddleware가 불러온 세션에서 사용자를 찾으므로 반드시 뒤에 와야 해요. 둘의 순서를 바꾸자 첫 요청에서 ImproperlyConfigured 오류가 나며 어디에 무엇을 둬야 하는지 알려 줬어요. 미들웨어에는 비용도 있어요. startproject가 만드는 기본 미들웨어는 7개인데, 테스트 클라이언트로 같은 뷰를 2,000번 부르자 요청당 210µs, 미들웨어를 모두 빼자 147µs로 약 63µs 차이였어요. 모든 요청이 내는 비용이므로, 특정 경로에서만 필요한 일은 미들웨어 대신 데코레이터로 그 뷰에만 붙여요. ASGI에서는 차이가 더 커요. 동기 방식으로 쓰인 미들웨어는 요청마다 스레드를 오가므로, 뒤의 Django async 항목처럼 처리량이 크게 떨어질 수 있어요.<br><sub>Middleware is the layer every request and response passes through. It handles in one place work that should not be repeated in every view, such as loading the session, identifying the logged-in user, checking CSRF and adding security headers. A Django middleware receives get\_response, the function that calls the next stage, and returns a function wrapping it. The MIDDLEWARE list therefore nests like onion layers, from outside to inside. With logging middleware A, B and C in that order, a request produced the log A in, B in, C in, the view, C out, B out, A out. Requests travel down the list to reach the view, and responses come back up in reverse. Outer middleware sees the response produced by everything inside it, so middleware that compresses responses or adds headers usually sits on the outside. Middleware can also return a response by itself without calling get\_response. When B was made to return a 403 under a certain condition, C and the view never ran, and the log read A in, B in, B blocks, A out. Blocking anonymous users, blocking IP addresses and limiting request rates work this way. Some middleware depends on order. AuthenticationMiddleware looks up the user in the session loaded by SessionMiddleware, so it must come after it. Swapping the two raised ImproperlyConfigured on the first request, with a message saying what belongs where. Middleware has a cost too. startproject creates 7 default middleware, and calling the same view 2,000 times through the test client took 210 µs per request, versus 147 µs with all middleware removed, about 63 µs apart. Every request pays that cost, so work needed only on certain routes is attached to those views with a decorator instead of middleware. Under ASGI the difference is larger: middleware written in the synchronous style switches threads on every request, which can cut throughput sharply, as the Django async item later shows.</sub> |
| **URL 라우팅**<br><sub>URL routing</sub> | Django는 URL 패턴을 위에서부터 하나씩 비교해요. 패턴 1,000개에서 맨 뒤 패턴은 215µs로 맨 앞보다 50배 느렸고, include로 묶자 42µs가 됐어요.<br><sub>Django compares URL patterns one at a time from the top. With 1,000 patterns, the last one took 215 µs, 50× slower than the first, and grouping them with include() brought it to 42 µs.</sub> | Django의 URL 설정은 path() 항목의 목록이에요. 요청이 오면 Django는 목록의 처음부터 각 패턴을 정규식으로 바꾼 것과 주소를 차례로 비교하고, 처음으로 일치한 패턴의 뷰를 불러요. path('books/<int:pk>/', views.book)의 <int:pk>는 경로 변환기로, 그 자리에 숫자만 받고 뷰에는 문자열이 아니라 정수로 넘겨 줘요. /p999/42/로 요청하자 뷰는 id=42라는 int를 받았어요. 순서대로 비교하는 방식이라 패턴이 많아지면 뒤쪽 패턴일수록 느려져요. 패턴 1,000개를 만들고 resolve()의 시간을 재자, 첫 패턴은 4.4µs, 500번째는 114µs, 마지막 패턴은 215µs로 맨 앞보다 50배 느렸어요. 어떤 패턴과도 일치하지 않는 주소도 목록을 끝까지 훑은 뒤에야 404가 되므로 167µs가 걸렸어요. 요청 하나에 수백 µs는 작아 보이지만, 모든 요청이 내는 비용이에요. 해결책은 include()로 묶는 거예요. 같은 1,000개를 앞부분이 같은 것끼리 10묶음으로 나눠 include()로 연결하자, 맨 뒤 패턴이 42µs로 줄었어요. Django는 먼저 묶음의 접두사만 비교하고, 일치한 묶음 안에서만 다시 찾기 때문이에요. 앱마다 urls.py를 두고 프로젝트 urls.py에서 include()하는 관례가 정리뿐 아니라 성능에도 도움이 돼요. 아주 자주 불리는 경로를 목록의 앞쪽에 두는 것도 방법이에요. 단, 앞쪽의 넓은 패턴이 뒤쪽의 구체적인 패턴을 가로채지 않게 순서를 확인해야 해요. 변환기는 입력 검사도 해 줘요. <int:id> 자리에 abc가 오자 뷰에 닿기 전에 404가 됐어요. str, int, slug, uuid, path 변환기가 기본으로 있고 직접 만들 수도 있어요. 주소를 만드는 쪽에서는 문자열을 직접 쓰지 않고, 패턴에 name을 붙인 뒤 코드에서는 reverse(), 템플릿에서는 {% url %}로 만들어요. reverse('p7', kwargs={'id': 3})는 /p7/3/을 돌려줬어요. 나중에 경로를 바꿔도 이름만 같으면 모든 링크가 따라 바뀌어요.<br><sub>Django’s URL configuration is a list of path() entries. For each request, Django compares the address against each pattern’s regex in turn from the top of the list and calls the view of the first pattern that matches. In path('books/<int:pk>/', views.book), <int:pk> is a path converter that accepts only digits in that position and passes the view an integer rather than a string. A request to /p999/42/ gave the view an int, id=42. Because comparison is sequential, later patterns get slower as the list grows. With 1,000 patterns, resolve() took 4.4 µs for the first, 114 µs for the 500th and 215 µs for the last, 50 times slower than the first. An address matching no pattern also became a 404 only after scanning the whole list, taking 167 µs. Hundreds of microseconds per request look small, but every request pays them. The fix is grouping with include(). Splitting the same 1,000 patterns into 10 groups by shared prefix and connecting them with include() cut the last pattern to 42 µs, because Django first compares only the group prefixes and then searches only inside the matching group. The convention of one urls.py per app, included from the project urls.py, helps performance as well as organization. Placing very frequently requested routes near the top also works, as long as a broad pattern near the top does not intercept a more specific one further down. Converters validate input too: abc in place of <int:id> became a 404 before reaching the view. str, int, slug, uuid and path converters are built in, and custom ones can be written. When generating addresses, avoid hard-coded strings; give patterns a name and build addresses with reverse() in code and {% url %} in templates. reverse('p7', kwargs={'id': 3}) returned /p7/3/. If a path changes later, every link follows as long as the name stays the same.</sub> |

The 404 response listed every URL pattern, and check --deploy found 7 issues in a fresh project.</sub> | startproject로 만든 Django 프로젝트는 DEBUG = True, 자동 생성된 SECRET\_KEY, 빈 ALLOWED\_HOSTS로 시작해요. 개발할 때는 편하지만, 이 설정 그대로 배포하면 위험해요. DEBUG가 켜져 있으면 Django는 실행한 모든 SQL을 connection.queries에 기록해요. 개발 중 쿼리 수를 확인하는 데는 유용하지만, 같은 프로세스에서 쿼리 2만 개를 실행하자 마지막 9,000개만 남기고 기록 한도를 넘었다는 경고를 냈어요. 오래 도는 프로세스라면 그만큼 메모리를 쓰고 매 쿼리마다 기록 비용을 내요. 더 큰 문제는 오류 페이지예요. 없는 주소에 대한 404 응답이 3,455바이트였는데, 프로젝트에 등록된 URL 패턴 목록이 모두 들어 있었어요. 공격자에게 관리자 주소와 내부 API 경로를 알려 주는 지도가 되는 셈이에요. 처리되지 않은 예외가 나면 500 오류 페이지에 코드 일부, 각 프레임의 지역 변수, 설정 값까지 나와요. Django가 비밀번호나 키처럼 보이는 설정 이름은 가려 주지만, 지역 변수에 들어 있던 개인 정보는 그대로 보여요. DEBUG를 끄자 같은 404가 179바이트짜리 짧은 Not Found로 바뀌었어요. python manage.py check --deploy는 운영에 위험한 설정을 자동으로 찾아 줘요. 새 프로젝트에서 실행하자 문제 7개를 보고했어요. The database connection is closed at the end of every request, so the next request starts by connecting again. PostgreSQL creates a new server process for each connection and goes through authentication and initialization, so this cost is not small. Throughput was measured by sending requests back to back to a view running one query through a single gunicorn worker. With CONN\_MAX\_AGE = 0 it handled 148 per second. The same measurement reached 561 per second, 3.8 times as many, and after the measurement one connection from that worker remained open on the database. None reuses connections without a time limit. From Django 5.1, a connection pool is also available for PostgreSQL. Giving 'pool': True in the OPTIONS of DATABASES makes psycopg’s connection pool open connections ahead of time and lend them out. In the measurement it reached 517 per second, similar to CONN\_MAX\_AGE, with one worker keeping 4 connections open. For workers running many threads, a pool is the more natural fit. Note that connections exist separately in every worker process. With 4 servers each running 8 workers and a pool size of 10, up to 320 connections can appear. PostgreSQL’s max\_connections defaults to 100, and every connection uses server memory, so it cannot be raised blindly. Compute the total number of connections, and if it is still too many, put an external connection pooler such as PgBouncer in front. Connections kept open for a long time can be dropped by a database restart or network equipment, so CONN\_HEALTH\_CHECKS = True checks that a connection is alive at the start of each request.</sub> |

## 파이썬 코드가 SQL이 되기까지 · How Python code becomes SQL

QuerySet이 언제 실행되는지, 관계를 읽을 때 생기는 N+1 쿼리, 동시에 값을 고칠 때 사라지는 갱신, 트랜잭션, 대량의 행을 읽고 쓰는 방법, 그리고 마이그레이션의 비용을 PostgreSQL에서 실측해요.  
*When a QuerySet actually runs, the N+1 queries that appear when reading relations, updates lost under concurrent changes, transactions, ways to read and write many rows, and the cost of migrations, all measured on PostgreSQL.*

| **QuerySet의 지연 평가**<br><sub>QuerySet laziness</sub> | QuerySet은 결과가 필요할 때 실행되고, 한 번 평가하면 결과를 저장해요. filter를 이어도 쿼리는 0번이었고, 존재 여부는 exists()가 count()보다 11배 빨랐어요.<br><sub>A QuerySet runs when its results are needed and stores them once evaluated. Chaining filters ran 0 queries, and exists() was 11× faster than count() for checking existence.</sub> | Django ORM에서 Book.objects.filter(price\_\_gt=50)는 쿼리를 실행하지 않아요. 어떤 SQL을 만들지에 대한 설명, 즉 QuerySet을 돌려줄 뿐이에요. 여기에 exclude()와 order\_by()를 이어 붙여도 쿼리는 0번이었고 0.3ms가 걸렸어요. 각 메서드는 조건이 하나 더해진 새 QuerySet을 돌려주므로, 함수 사이에 QuerySet을 넘기며 조건을 조금씩 붙여 나가는 코드를 부담 없이 쓸 수 있어요. print(qs.query)로 실제로 보낼 SQL을 미리 볼 수도 있어요. 쿼리는 결과가 실제로 필요한 순간에 실행돼요. 순회, list(), len(), bool(), 그리고 슬라이스에 단계를 준 경우가 평가를 일으켜요. list(qs)로 처음 순회하자 쿼리 1번이 5.3ms에 실행됐고, 결과는 QuerySet 안의 캐시에 저장됐어요. 같은 QuerySet을 다시 순회하거나 len()을 부르자 쿼리 없이 0ms에 끝났어요. 그래서 템플릿에서 {% if books %}로 확인한 뒤 {% for %}로 도는 것은 쿼리 한 번이에요. 반대로 캐시를 쓰지 못하는 경우도 있어요. 평가되지 않은 QuerySet에 q2[0]처럼 인덱스를 쓰면 LIMIT 1 쿼리를 그때마다 보내요. q2[0]을 두 번 쓰자 쿼리도 두 번 나갔어요. 반복문이나 템플릿에서 같은 값을 여러 번 쓸 때는 한 번 꺼내 변수에 담아 둬요. 매번 Book.objects.filter(...)를 새로 쓰는 것도 새 QuerySet이라 캐시를 공유하지 않아요. 개수와 존재 여부는 DB에 물어보는 것이 빨라요. 10만 행 표에서 조건에 맞는 행의 count()는 COUNT(\*) 쿼리로 7.8ms, exists()는 SELECT 1 … LIMIT 1 쿼리로 0.7ms였어요. 하나라도 있는지만 알면 되는 곳에서 count() > 0을 쓰면 11배를 낭비하는 셈이에요. len(qs)는 모든 행을 모델 객체로 가져온 뒤 세므로, 그 행들을 어차피 쓸 때만 써요. 이미 평가된 QuerySet이라면 count()와 exists()도 캐시를 써서 쿼리를 보내지 않아요.<br><sub>In the Django ORM, Book.objects.filter(price\_\_gt=50) does not run a query. Each method returns a new QuerySet with one more condition, so code that passes QuerySets between functions and adds conditions bit by bit costs nothing. print(qs.query) shows the SQL that will actually be sent. There are cases where the cache cannot help. Indexing an unevaluated QuerySet such as q2[0] sends a LIMIT 1 query each time; using q2[0] twice sent two queries. | **N+1 쿼리**<br><sub>N+1 queries</sub> | 관계 필드를 처음 읽을 때마다 쿼리가 하나씩 나가요. 책 100권의 저자를 읽자 쿼리가 101번 나갔고, select\_related는 1번, prefetch\_related는 2번으로 줄였어요.<br><sub>Each first read of a related field fires a query. N+1은 템플릿에서 관계 필드를 하나 더 보여 주는 작은 변경으로도 생겨요. 테스트에서 self.assertNumQueries(2)처럼 쿼리 수를 고정해 두면 누군가 이런 변경을 해도 바로 실패해서 알 수 있어요. 개발 중에는 django-debug-toolbar나 앞에서 본 connection.queries로 페이지마다 쿼리 수를 확인해요. 관리자 화면에서도 같은 문제가 생기는데, 다음 섹션에서 재요.<br><sub>The ORM conveniently presents rows of other tables as attributes such as b.author, but what happens behind it is hard to see. Book.objects.all()[:100] queries only the book table. The moment b.author.name is read inside the loop, a separate query fetches that book’s author. Looping over 100 books reading author names sent 101 queries: one for the book list and 100 for authors. This is called the N+1 problem. The code looks fine, and with little development data it is easy not to notice it is slow. Even with PostgreSQL on the same machine over a Unix socket, the 101 queries took 61–68 ms. The fix is to fetch related data up front. It first fetches the book list, then fetches the tags of all those books at once with an IN condition and pairs them in Python. The loop reading tags went from 101 queries taking 82–93 ms to 2 queries taking 6 ms. A Prefetch object can add conditions or ordering to the second query. Pinning the query count in tests, as in self.assertNumQueries(2), makes such a change fail immediately so it gets noticed. During development, django-debug-toolbar or the connection.queries seen earlier shows the query count per page. The admin can hit the same problem, measured in the next section.</sub> |
| **F 식과 경쟁 조건**<br><sub>F expressions and race conditions</sub> | 값을 읽어 와서 바꾼 뒤 저장하면 동시에 들어온 갱신이 사라져요. 스레드 10개가 재고를 1,000번 늘리자 170이 됐고, F 식과 행 잠금은 정확히 1,000이었어요.<br><sub>Reading a value, changing it and saving it back loses concurrent updates. Product.objects.filter(id=1).update(stock=F('stock') + 1)은 값을 파이썬으로 가져오지 않고 UPDATE shop\_product SET stock = stock + 1이라는 SQL을 보내요. DB는 문장 하나를 실행하는 동안 그 행을 잠그므로 증가가 섞이지 않아요. 같은 실험에서 정확히 1,000이 됐고, 왕복이 한 번뿐이라 0.53초로 가장 빨랐어요. 조회수, 좋아요 수, 잔액처럼 더하고 빼는 값에 써요. 두 번째 해결책은 행 잠금이에요. 재고가 충분한지 확인한 뒤 줄이는 것처럼 읽은 값으로 판단해야 한다면, transaction.atomic() 안에서 select\_for\_update()로 행을 잠그고 읽어요. 다른 트랜잭션은 그 행을 잠그려다 기다리게 되고, 앞의 트랜잭션이 커밋한 뒤의 값을 읽어요. 정확히 1,000이었지만, 요청들이 차례로 잠금을 기다리느라 1.9초로 약 3.5배 느렸어요. 잠금은 필요한 곳에만 짧게 써요. 또 save()는 기본으로 모든 필드를 UPDATE해요. 다른 요청이 그사이 다른 필드를 바꿨다면 그 변경도 오래된 값으로 덮어써요. 바꾼 필드만 쓰도록 save(update\_fields=['stock'])처럼 지정하는 습관이 좋아요.<br><sub>p = Product.objects.get(id=1); p.stock += 1; p.save() looks like natural code, but it is split into three steps: reading the value from the database into Python, changing it in Python, and writing it back. When logic depends on the value read, such as checking that stock suffices before decreasing it, the row is locked and read with select\_for\_update() inside transaction.atomic(). Other transactions trying to lock that row wait, and then read the value as committed by the earlier transaction. Also, save() updates every field by default. If another request changed a different field in the meantime, that change is overwritten with a stale value. Specifying only the changed fields, as in save(update\_fields=['stock']), is a good habit.</sub> |

| **캐시**<br><sub>Caching</sub> | 19ms 걸리던 집계 뷰가 캐시 뒤에는 0.3ms였어요. cache\_page는 응답 전체와 HTTP 헤더를, 저수준 API는 데이터만 저장하고, 기본 캐시는 워커마다 따로라 4번 계산됐어요.<br><sub>An aggregate view taking 19 ms took 0.3 ms behind a cache. cache\_page stores the whole response with HTTP headers, the low-level API stores just data, and the default cache is per worker, so it was computed 4 times.</sub> | 같은 결과를 매번 계산할 필요가 없다면 잠시 저장해 두고 다시 써요. 10만 권에서 저자별 평균 가격 상위 10명을 구하는 뷰는 GROUP BY 집계 때문에 요청마다 19~28ms가 걸렸어요. 뷰에 @cache\_page(60)를 붙이자 첫 요청은 18ms로 같았지만, 두 번째부터는 쿼리 0번에 0.3ms였어요. 60배 넘게 빨라졌고, DB도 그만큼 쉬어요. cache\_page는 서버 캐시에 응답 전체를 저장할 뿐 아니라 Cache-Control: max-age=60과 Expires 헤더도 붙여요. 그래서 브라우저와 그 앞의 CDN도 60초 동안 이 응답을 다시 쓰게 돼요. 서버 캐시는 지울 수 있지만 사용자 브라우저에 저장된 것은 지울 수 없다는 점도 기억해요. 캐시 키는 주소를 기준으로 만들어지므로, 로그인한 사용자마다 내용이 다른 페이지에 붙이면 다른 사람의 화면이 보이는 사고가 날 수 있어요. 그런 페이지에는 vary\_on\_cookie를 쓰거나, 응답이 아니라 데이터만 캐시해요. 저수준 API의 cache.get\_or\_set('stats:top', 함수, 60)은 키가 있으면 그 값을 돌려주고, 없으면 함수를 실행해 결과를 저장한 뒤 돌려줘요. 같은 측정에서 두 번째부터 0.27~0.43ms였어요. 사용자마다 다른 페이지 안에서 모두에게 같은 부분, 예를 들어 인기 상품 목록만 캐시할 수 있어요. 데이터가 바뀌면 cache.delete('stats:top')로 지우거나, 키에 버전을 넣어 새 키를 쓰게 해요. 캐시의 어려운 부분은 언제 지울지예요. 만료 시간을 짧게 두면 단순하지만 그동안은 옛 값이 보이고, 저장할 때 지우면 정확하지만 지울 곳을 빠짐없이 챙겨야 해요. 설정하지 않으면 Django의 캐시는 LocMemCache로, 각 프로세스의 메모리 안에 있어요. gunicorn 워커 4개에 같은 요청을 40번 보내자 처음 4번이 캐시 실패였는데, 4개의 서로 다른 프로세스에서 한 번씩이었어요. 워커마다 같은 값을 따로 계산하고 따로 보관하는 셈이고, cache.delete()도 그 요청을 받은 워커 하나의 캐시만 지워요. 서버가 여러 대라면 더 심해져요. 운영에서는 CACHES 설정을 Redis나 Memcached로 바꿔 모든 워커와 서버가 같은 캐시를 보게 해요. Django 4.0부터 Redis 백엔드가 내장돼 있어요.<br><sub>When the same result need not be computed every time, it is stored briefly and reused. A view finding the top 10 authors by average price over 100,000 books took 19–28 ms per request because of its GROUP BY aggregation. With @cache\_page(60) on the view, the first request still took 18 ms, but every following one took 0.3 ms with 0 queries. That is over 60 times faster, and the database rests accordingly. cache\_page not only stores the whole response in the server cache but also adds Cache-Control: max-age=60 and Expires headers, so browsers and any CDN in front reuse the response for 60 seconds too. Remember that the server cache can be cleared but what is stored in users’ browsers cannot. Cache keys are built from the address, so attaching it to pages whose content differs per logged-in user can show one person another’s page. Such pages use vary\_on\_cookie or cache data instead of responses. The low-level API’s cache.get\_or\_set('stats:top', function, 60) returns the value if the key exists and otherwise runs the function, stores the result and returns it. In the same measurement it took 0.27–0.43 ms from the second request on. Inside pages that differ per user, only the parts that are the same for everyone, such as a list of popular products, can be cached this way. When the data changes, delete the key with cache.delete('stats:top') or put a version in the key so a new key is used. The hard part of caching is deciding when to clear. Short expiry times are simple but show stale values meanwhile; clearing on save is accurate but every place that changes the data must be covered. Unconfigured, Django’s cache is LocMemCache, living in each process’s memory. Sending the same request 40 times to 4 gunicorn workers produced 4 cache misses at first, one in each of 4 different processes. Every worker computes and keeps the same value separately, and cache.delete() clears only the cache of the one worker that handled that request. With several servers it gets worse. ## 타입 힌트가 API가 되기까지 · How type hints become an API

타입 힌트로 요청을 해석하고 검증하는 방식, Pydantic 모델의 검증 규칙과 속도, Depends로 만드는 의존성, 응답에서 필드를 걸러 내는 response_model, 그리고 자동으로 만들어지는 OpenAPI 문서를 FastAPI 0.162에서 실측해요.  
*How type hints interpret and validate requests, Pydantic models’ validation rules and speed, dependencies built with Depends, response_model filtering fields out of responses, and automatically generated OpenAPI docs, all measured on FastAPI 0.162.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **타입 힌트 검증**<br><sub>Type-hint validation</sub> | FastAPI는 함수의 타입 힌트로 요청을 해석하고 검증해요. "5"는 int 5로 바뀌었고, abc와 범위를 넘은 500은 함수가 실행되기 전에 이유가 담긴 422로 막혔어요.<br><sub>FastAPI interprets and validates requests using a function’s type hints. "5" became int 5, while abc and an out-of-range 500 were stopped with a 422 explaining why, before the function ran.</sub> | FastAPI의 가장 큰 특징은 파이썬 타입 힌트를 API의 규칙으로 쓴다는 거예요. @app.get('/items/{item\_id}') 아래의 def read(item\_id: int, limit: Limit = 10)를 보면, FastAPI는 경로 문자열에 {item\_id}가 있으므로 item\_id를 경로에서, 나머지 단순한 타입의 매개변수를 쿼리 문자열에서 읽어요. 그리고 힌트에 적힌 타입으로 바꿔요. /items/5로 요청하자 문자열 "5"가 int 5로 들어왔고, 보내지 않은 limit은 기본값 10이었어요. str \| None = None처럼 None을 허용하고 기본값을 주면 선택 항목이 돼요. 바꿀 수 없는 값이 오면 함수는 아예 실행되지 않아요. /items/abc로 요청하자 422 Unprocessable Entity가 돌아왔고, 본문에는 위치 ["path", "item\_id"], 오류 종류 int\_parsing, 입력값 "abc", 그리고 사람이 읽을 설명이 JSON으로 들어 있었어요. 클라이언트는 이 구조를 읽어 어느 입력 칸에 어떤 오류를 보여 줄지 정할 수 있어요. 범위 같은 조건도 선언으로 적어요. Limit = Annotated[int, Query(ge=1, le=100)]으로 만든 타입을 쓰고 ?limit=500을 보내자, less\_than\_equal 오류와 함께 ctx {"le": 100}이 돌아왔어요. 함수 안에서 if 문으로 값을 검사하고 오류 응답을 만드는 반복 코드가 사라져요. Annotated로 만든 Limit 같은 별칭은 여러 엔드포인트에서 다시 쓸 수 있어서, 페이지 크기 제한 같은 규칙을 한곳에서 관리해요. 같은 방식으로 Header(), Cookie(), Body()를 써서 헤더, 쿠키, 본문의 값도 받아요. 매개변수의 이름과 타입만 보고 어디서 읽을지 정하므로 함수 서명이 곧 API의 입력 명세예요. 이 선언은 검증에만 쓰이지 않고 그대로 OpenAPI 문서가 돼요. 검증 로직과 문서가 같은 소스에서 나오므로 서로 어긋날 일이 없어요. 타입 힌트는 편집기의 자동 완성과 mypy 같은 정적 검사에도 그대로 쓰여서, 함수 안에서 item\_id가 int라는 것을 도구들도 알아요. Django에서 비슷한 일을 하려면 경로 변환기, 폼, Django REST framework의 시리얼라이저를 함께 써야 해요.<br><sub>FastAPI’s defining feature is using Python type hints as the rules of an API. Looking at def read(item\_id: int, limit: Limit = 10) under @app.get('/items/{item\_id}'), FastAPI reads item\_id from the path because the path string contains {item\_id}, and the remaining simple-typed parameters from the query string. It then converts them to the types written in the hints. Requesting /items/5 delivered the string "5" as the int 5, and the omitted limit took its default of 10. Allowing None with a default, as in str \| None = None, makes a parameter optional. When a value cannot be converted, the function does not run at all. Requesting /items/abc returned 422 Unprocessable Entity, with a JSON body containing the location ["path", "item\_id"], the error type int\_parsing, the input "abc" and a human-readable explanation. Clients can read this structure to decide which input field shows which error. Conditions such as ranges are written as declarations too. Using a type built as Limit = Annotated[int, Query(ge=1, le=100)] and sending ?limit=500 returned a less\_than\_equal error along with ctx {"le": 100}. The repetitive code that checks values with if statements inside the function and builds error responses disappears. Aliases built with Annotated, such as Limit, can be reused across endpoints, so rules such as page size limits are managed in one place. In the same way, Header(), Cookie() and Body() receive values from headers, cookies and the body. Since the location is decided from the parameter’s name and type alone, the function signature is the API’s input specification. These declarations are not used only for validation; they become the OpenAPI documentation as is. Validation logic and documentation come from the same source, so they never drift apart. Type hints also feed editor autocompletion and static checkers such as mypy, so tools know too that item\_id is an int inside the function. Doing something similar in Django requires combining path converters, forms and Django REST framework serializers.</sub> |
| **Pydantic 모델**<br><sub>Pydantic models</sub> | 요청 본문은 Pydantic 모델로 검증해요. 오류 3개를 한 번에 돌려줬고, 기본은 너그럽게 "3.5"를 숫자로 바꾸고 모르는 필드는 버렸어요. 검증 한 번은 0.97µs였어요.<br><sub>Request bodies are validated with Pydantic models. Pydantic 1보다 몇 배 빨라진 덕분에 검증을 아낄 이유가 거의 없어요. 같은 모델은 요청 검증뿐 아니라 응답 직렬화와 문서에도 쓰이고, 설정 파일이나 환경 변수를 읽는 pydantic-settings, 외부 API 응답을 검사하는 곳에서도 그대로 쓸 수 있어요.<br><sub>Structured input such as a JSON body is declared as a Pydantic model. Pydantic works in a lax mode by default. Sending the string "3.5" as the price converted it to the number 3.5, and an extra field not in the model was silently dropped without an error. That is convenient where every value arrives as a string, as in web forms or query strings, but it can let client mistakes slip by. When stricter rules are needed, switch with model\_config = ConfigDict(strict=True); the same "3.5" became a float\_type error. extra="forbid" turns unknown fields into errors too, catching misspelled field names. Sending JSON missing its closing brace returned a 422 with a json\_invalid error and the position where it broke. Speed was measured as well. Pydantic 2’s validation engine, pydantic-core, is written in Rust. Validating a dictionary into ItemIn took 0.97 µs, and model\_validate\_json, validating directly from JSON bytes, took 1.1 µs. Building a plain Python class without any checks took 0.24 µs, so that is about 4 times as much, but negligible next to a request taking hundreds of microseconds to milliseconds. Being several times faster than Pydantic 1, there is hardly any reason to skimp on validation. The same model is used not only for request validation but also for response serialization and documentation, and works as is in pydantic-settings for reading configuration files and environment variables, or wherever external API responses need checking.</sub> |

## 기다림과 계산을 나누기 · Separating waiting from computing

async 함수 안의 블로킹 코드가 이벤트 루프를 멈추는 모습, 동기 함수를 돌리는 스레드 풀의 한도, CPU 작업과 GIL, 응답 뒤에 실행되는 백그라운드 작업, 그리고 Django의 async 뷰와 ORM을 직접 부하를 걸어 재요.  
*Blocking code inside async functions freezing the event loop, the limit of the thread pool running synchronous functions, CPU work and the GIL, background tasks running after the response, and Django’s async views and ORM, all measured under real load.*

| **async 안의 블로킹**<br><sub>Blocking inside async</sub> | async def 안에서 time.sleep을 부르자 요청 10개가 5초 동안 줄을 섰고, 다른 엔드포인트까지 1.9초를 기다렸어요. await로 기다리거나 def로 쓰자 0.54초였어요.<br><sub>Calling time.sleep inside async def made 10 requests queue for 5 s, and even another endpoint waited 1.9 s. Waiting with await or writing def finished in 0.54 s.</sub> | FastAPI는 엔드포인트를 async def로 쓰는지 def로 쓰는지에 따라 다르게 실행해요. async def 엔드포인트는 이벤트 루프 위에서 직접 실행돼요. 이벤트 루프는 스레드 하나에서 여러 코루틴을 번갈아 실행하는데, 코루틴이 await에서 기다리겠다고 알려 줄 때만 다른 코루틴으로 넘어가요. 그래서 async def 안에서 time.sleep(0.5)처럼 await 없이 기다리는 동기 함수를 부르면, 그 0.5초 동안 루프 전체가 아무것도 하지 못해요. 이 엔드포인트에 요청 10개를 동시에 보내자 하나씩 차례로 처리되어 전체 5.0초가 걸렸고, 마지막 요청은 5초를 기다렸어요. 같은 대기를 await asyncio.sleep(0.5)로 바꾸자 10개가 함께 0.54초에 끝났어요. await는 기다리는 동안 루프에게 제어를 돌려주기 때문에, 루프는 그사이 다른 요청을 받아 진행해요. 실제 코드에서 time.sleep을 쓰는 일은 드물지만, 같은 문제를 일으키는 코드는 흔해요. requests로 외부 API를 부르는 것, 동기 DB 드라이버로 쿼리하는 것, 큰 파일을 open()으로 읽는 것, 무거운 계산을 하는 것이 모두 루프를 막아요. async def 안에서는 httpx.AsyncClient, asyncpg나 psycopg의 async 연결, aiofiles처럼 await할 수 있는 라이브러리를 써야 해요. async를 빼고 일반 def로 쓴 엔드포인트는 FastAPI가 스레드 풀에서 실행해요. time.sleep(0.5)를 그대로 쓴 def 엔드포인트에 10개를 보내자 0.56초에 끝났어요. 동기 라이브러리를 꼭 써야 한다면 async def보다 def가 안전한 선택이에요. 막힌 루프의 피해는 그 엔드포인트 하나로 끝나지 않아요. 블로킹 요청 4개가 도는 중에, 평소 1ms면 끝나는 /hello를 보내자 1.9초를 기다렸어요. 같은 프로세스의 모든 요청이 같은 루프를 쓰기 때문이에요. 이런 문제는 개발 중에 잘 드러나지 않으므로, asyncio의 디버그 모드(PYTHONASYNCIODEBUG=1)를 켜면 오래 걸린 콜백을 경고로 알려 줘요. async def 안에서 동기 함수를 꼭 불러야 한다면 await run\_in\_threadpool(함수)나 asyncio.to\_thread()로 스레드에 넘겨요.<br><sub>FastAPI runs an endpoint differently depending on whether it is written as async def or def. async def endpoints run directly on the event loop. The event loop alternates between many coroutines on one thread, switching only when a coroutine announces at an await that it is going to wait. So calling a synchronous waiting function without await inside async def, such as time.sleep(0.5), leaves the whole loop unable to do anything for those 0.5 s. Sending 10 concurrent requests to this endpoint handled them one after another, taking 5.0 s in total, with the last request waiting 5 seconds. Replacing the wait with await asyncio.sleep(0.5) finished all 10 together in 0.54 s. await hands control back to the loop while waiting, so the loop takes and advances other requests meanwhile. Django의 요청은 세션, 인증, CSRF, 보안 헤더 같은 기본 미들웨어 7개를 거치고, FastAPI의 hello는 아무것도 거치지 않아요. 같은 FastAPI라도 엔드포인트를 def로 바꾸자 7,774개로 처리량이 40% 낮았어요. def는 요청마다 스레드 풀로 넘어갔다 돌아오는 비용을 내기 때문이에요. 기다리는 일이 없는 짧은 엔드포인트라면 async def가 빠르지만, 블로킹 코드가 있다면 앞에서 본 것처럼 def가 안전해요. 실제 앱은 대개 DB를 써요. PostgreSQL 쿼리 하나를 실행하는 엔드포인트로 바꿔 다시 쟀어요. FastAPI는 psycopg의 async 연결 풀로 초당 3,879개, Django는 CONN\_MAX\_AGE로 연결을 재사용하며 1,029개였어요. 격차가 6배에서 3.8배로 줄었어요. 쿼리가 여러 개이고 비즈니스 로직과 직렬화가 더해지면 프레임워크 자체가 차지하는 비중은 더 작아져요. 이 측정에서는 PostgreSQL과 부하 도구 autocannon도 같은 2코어를 나눠 썼으므로 절대값보다 비율을 보는 것이 맞아요. 결론적으로 프레임워크의 기본 처리량은 대부분의 서비스에서 병목이 아니에요. 느린 쿼리 하나, N+1 하나, async 안의 블로킹 하나가 프레임워크 차이보다 훨씬 커요. 관리자 화면, ORM과 마이그레이션, 인증, 폼, 템플릿처럼 갖춰진 기능이 필요한 서비스라면 Django가 개발 시간을 크게 줄여 줘요. 타입 힌트 중심의 API 서버, 자동 문서, async 위주의 입출력이 중요하다면 FastAPI가 잘 맞아요. 둘을 함께 쓰는 팀도 많아요. 관리 기능과 데이터 모델은 Django로, 트래픽이 많은 일부 API는 FastAPI로 나누는 식이에요.<br><sub>Which is faster, Django or FastAPI, is a frequent question, so it was measured under identical conditions. On a 2-core server, with 2 workers and 50 concurrent connections, a hello endpoint returning one JSON object was hammered for 6 seconds. FastAPI’s async def endpoint on uvicorn with uvloop and httptools handled 12,780 requests per second. Django, with DEBUG off, handled 2,103 with gunicorn sync workers and 673 on uvicorn ASGI. FastAPI was 6 times faster than WSGI Django. The difference includes each framework’s default setup: a Django request passes through 7 default middleware such as sessions, authentication, CSRF and security headers, while FastAPI’s hello passes through nothing. The same FastAPI with the endpoint changed to def handled 7,774, 40% lower throughput, because def pays the cost of hopping to the thread pool and back on every request. Short endpoints that never wait are faster as async def, but with blocking code def remains the safe choice seen earlier. Real apps usually use a database, so the measurement was repeated with an endpoint running one PostgreSQL query. FastAPI with psycopg’s async connection pool handled 3,879 per second, and Django reusing connections through CONN\_MAX\_AGE handled 1,029. The gap narrowed from 6 times to 3.8 times. With several queries plus business logic and serialization, the framework’s own share shrinks further. In this measurement PostgreSQL and the load tool autocannon shared the same 2 cores, so the ratios matter more than absolute numbers. In short, a framework’s baseline throughput is not the bottleneck for most services. One slow query, one N+1 or one blocking call inside async outweighs the framework difference by far. For services needing built-in features such as the admin, ORM and migrations, authentication, forms and templates, Django cuts development time substantially. For API servers centred on type hints, automatic documentation and async I/O, FastAPI fits well. Many teams use both, keeping admin features and data models in Django and splitting some high-traffic APIs into FastAPI.</sub> |
| **정적 파일**<br><sub>Static files</sub> | 운영에서 Django는 정적 파일을 내주지 않아 CSS가 404였어요. collectstatic으로 모으고, 해시 이름으로 10년 캐시하고, 미리 압축해 24.7KB짜리 CSS를 5.5KB로 보냈어요.<br><sub>In production Django does not serve static files, so the CSS was a 404. collectstatic gathers them, hashed names allow 10-year caching, and precompression sent a 24.7 KB CSS as 5.5 KB.</sub> | 개발 중에는 runserver가 CSS, JavaScript, 이미지 같은 정적 파일을 알아서 내줘서 신경 쓸 일이 없어요. 그런데 같은 프로젝트를 gunicorn으로 띄우자 관리자 화면의 /static/admin/css/base.css가 404였어요. DEBUG=False에서도, DEBUG=True에서도 마찬가지였어요. 정적 파일을 내주는 기능은 개발 서버인 runserver에만 들어 있고, 운영 서버에서는 따로 준비해야 해요. 파이썬 프로세스가 파일을 하나하나 읽어 보내는 것은 비효율적이라는 판단이에요. 첫 단계는 모으기예요. python manage.py collectstatic은 각 앱의 static 폴더와 STATICFILES\_DIRS에 흩어진 파일을 STATIC\_ROOT 한 폴더로 복사해요. 관리자 화면의 파일 130개가 복사됐고, 650개가 후처리됐어요. 이 폴더를 Nginx 같은 웹 서버가 직접 내주거나, CDN에 올리거나, 앱 안에서 WhiteNoise가 내줘요. WhiteNoise는 미들웨어 하나로 gunicorn에서도 정적 파일을 효율적으로 내주게 해 주는 패키지예요. 두 번째는 캐시예요. 정적 파일은 자주 바뀌지 않으므로 브라우저가 오래 저장해 두면 좋지만, 바뀌었을 때 옛 파일이 남는 문제가 있어요. ManifestStaticFilesStorage는 파일 이름에 내용의 해시를 붙여 base.6398cd16ee3d.css 같은 파일을 만들고, 템플릿의 {% static %} 태그가 이 이름을 가리키게 해요. WhiteNoise는 이런 해시 이름 파일에 Cache-Control: max-age=315360000, public, immutable을 붙여 10년 동안 캐시하게 했어요. 해시가 없는 원래 이름은 60초였어요. 내용이 바뀌면 이름도 바뀌므로 브라우저는 새 파일을 받아요. 세 번째는 압축이에요. WhiteNoise의 저장소는 collectstatic 때 파일마다 gzip과 Brotli로 압축한 .gz, .br 파일을 미리 만들어 둬요. 그래서 정적 폴더는 781개 파일, 6.6MB가 됐어요. 브라우저가 gzip을 받겠다고 하자 24.7KB짜리 CSS가 5.5KB로 나갔어요. 요청마다 압축하지 않으므로 CPU도 아껴요. 사용자가 올린 프로필 사진이나 첨부 파일 같은 media 파일은 정적 파일과 다르게 다뤄요. 배포와 함께 바뀌지 않고 계속 늘어나므로, 서버 디스크가 아니라 S3 같은 객체 저장소에 두고 django-storages 같은 패키지로 연결해요. 서버를 여러 대로 늘리거나 컨테이너를 다시 만들어도 파일이 사라지지 않아요.<br><sub>During development runserver serves static files such as CSS, JavaScript and images automatically, so there is nothing to think about. But running the same project under gunicorn made the admin’s /static/admin/css/base.css a 404, with DEBUG=False and with DEBUG=True alike. Serving static files exists only in the development server, runserver, and must be arranged separately for production servers, the judgement being that a Python process reading and sending files one by one is inefficient. The first step is gathering. python manage.py collectstatic copies files scattered across each app’s static folder and STATICFILES\_DIRS into one STATIC\_ROOT folder. The admin’s 130 files were copied and 650 post-processed. That folder is served directly by a web server such as Nginx, uploaded to a CDN, or served from inside the app by WhiteNoise, a package that with a single middleware makes even gunicorn serve static files efficiently. The second step is caching. Static files rarely change, so browsers should keep them long, but then old files linger after changes. ManifestStaticFilesStorage adds a content hash to file names, producing files such as base.6398cd16ee3d.css, and makes the {% static %} template tag point to that name. WhiteNoise gave such hashed files Cache-Control: max-age=315360000, public, immutable, caching them for 10 years, while the original unhashed name got 60 seconds. When content changes, the name changes too, so browsers fetch the new file. The third step is compression. WhiteNoise’s storage creates gzip- and Brotli-compressed .gz and .br files for each file during collectstatic, which brought the static folder to 781 files and 6.6 MB. When the browser accepted gzip, the 24.7 KB CSS went out as 5.5 KB, and since nothing is compressed per request, CPU is saved as well. Media files uploaded by users, such as profile pictures and attachments, are handled differently from static files. They do not change with deploys and keep growing, so they live not on the server’s disk but in object storage such as S3, connected through a package such as django-storages. Files then survive adding servers or rebuilding containers.</sub> |
