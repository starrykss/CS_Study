## 확장과 부하 분산 · Scaling and load

사용자가 늘어도 느려지지 않게 서버와 데이터를 나누는 방법이에요.  
*Ways to split servers and data so growth doesn’t mean slowdowns.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **수직 vs 수평 확장**<br><sub>Scale up vs scale out</sub> | 수직 확장은 서버를 더 크게, 수평 확장은 같은 서버를 여러 대로 늘려요.<br><sub>Scaling up buys a bigger machine; scaling out adds more of the same machine.</sub> | 수직은 간단하지만 한계와 단일 장애점이 있어요. 웹 서버는 수평으로, DB는 수직부터 시작해 읽기 복제·샤딩으로 넘어가는 경우가 많아요.<br><sub>Up is simple but has a ceiling and a single point of failure. Web tiers usually scale out; databases often scale up first, then add replicas and shards.</sub> |
| **로드 밸런싱**<br><sub>Load balancing</sub> | 여러 서버 앞에서 요청을 나눠 주는 장치예요. 라운드 로빈, 최소 연결, 해시 같은 방식으로 고르고 죽은 서버는 빼요.<br><sub>A component in front of servers that spreads requests using round robin, least connections or hashing, and drops unhealthy servers.</sub> | L4(TCP)와 L7(HTTP 경로·헤더 기반)이 있어요. Nginx, HAProxy, AWS ALB/NLB가 대표적이고, 헬스 체크 경로를 꼭 만들어 두세요.<br><sub>Comes in L4 (TCP) and L7 (HTTP path/header) flavours, e.g. Nginx, HAProxy, AWS ALB/NLB; always expose a health-check endpoint.</sub> |
| **무상태 서버**<br><sub>Stateless servers</sub> | 세션 같은 상태를 서버 메모리에 두지 않고 공유 저장소로 빼서, 어느 서버가 받아도 같은 결과를 내게 해요.<br><sub>Keep state such as sessions out of server memory and in a shared store, so any server can handle any request.</sub> | 스티키 세션은 임시방편이에요. 세션은 Redis나 토큰(JWT)으로, 업로드 파일은 S3 같은 오브젝트 스토리지로 옮기세요.<br><sub>Sticky sessions are a stopgap; move sessions to Redis or tokens (JWT) and uploads to object storage such as S3.</sub> |
| **일관된 해싱**<br><sub>Consistent hashing</sub> | 서버와 키를 같은 해시 링 위에 놓고, 키는 시계 방향으로 처음 만나는 서버에 저장해요. 서버가 늘거나 줄어도 일부 키만 옮겨가요.<br><sub>Servers and keys share one hash ring; each key lives on the next server clockwise, so adding or removing a server moves only a few keys.</sub> | 분산 캐시(Memcached 클라이언트), DynamoDB·Cassandra 파티셔닝에 써요. 서버마다 가상 노드를 여러 개 두면 부하가 고르게 퍼져요.<br><sub>Used by distributed caches and by DynamoDB and Cassandra partitioning; virtual nodes per server even out the load.</sub> |
| **캐시 스탬피드**<br><sub>Cache stampede</sub> | 인기 있는 캐시 항목이 만료되는 순간 수많은 요청이 한꺼번에 DB로 몰려 장애를 일으키는 현상이에요.<br><sub>When a hot cache entry expires, a flood of requests hits the database at once and can take it down.</sub> | 갱신 락(하나만 다시 계산), 만료 전 미리 갱신, TTL에 무작위 값 더하기로 막아요. 이전 값을 잠깐 내주는(stale-while-revalidate) 방식도 좋아요.<br><sub>Prevent it with a rebuild lock, early refresh, randomized TTLs, or serving stale data while revalidating.</sub> |
| **레이트 리밋**<br><sub>Rate limiting</sub> | 일정 시간 동안 받을 수 있는 요청 수를 제한해요. 토큰 버킷은 토큰이 일정 속도로 차고, 요청마다 하나씩 써요.<br><sub>Caps how many requests are accepted per time window; in a token bucket, tokens refill at a steady rate and each request spends one.</sub> | 로그인 시도, 공개 API, 비싼 작업을 보호해요. 사용자·IP·API 키별로 걸고, 초과하면 429와 Retry-After 헤더를 돌려줘요.<br><sub>Protects logins, public APIs and costly endpoints; limit per user, IP or API key and answer 429 with a Retry-After header.</sub> |
| **가십 프로토콜과 장애 감지**<br><sub>Gossip protocols and failure detection</sub> | 중앙 서버 없이 노드들이 무작위 이웃과 정보를 주고받아, 소문처럼 O(log N) 라운드 만에 전체에 퍼뜨리는 방식이에요. 멤버십 관리와 장애 감지에 써요.<br><sub>Nodes swap information with random peers, with no central server, so news spreads like a rumour to everyone in O(log N) rounds; it is used for membership and failure detection.</sub> | 소식을 아는 노드가 라운드마다 무작위 노드 하나에게 전하면 아는 노드 수가 약 2배씩 늘어, 16개 노드면 4라운드쯤에 모두 알게 돼요. 일부 노드가 죽거나 메시지가 빠져도 다른 경로로 퍼지므로 튼튼해요. 각 노드의 하트비트 카운터도 이렇게 퍼뜨리면, 오래 오르지 않는 노드를 먼저 “의심”하고 확인을 거쳐 장애로 판정할 수 있어요(SWIM, φ 누적 감지). 카산드라와 Consul이 이 방식을 써요.<br><sub>If every informed node tells one random peer per round, the informed set roughly doubles, so 16 nodes all know within about 4 rounds. Dead nodes or lost messages don’t stop it, since information takes other routes. Spreading each node’s heartbeat counter the same way lets the cluster first suspect a node whose counter stops rising, then confirm and declare it failed (SWIM, phi-accrual detection). Cassandra and Consul work this way.</sub> |
| **장애 감지**<br><sub>Failure detection</sub> | 하트비트가 끊긴 노드를 언제 죽었다고 볼지 정하는 일이에요. 느린 것과 죽은 것을 구분할 수 없어서 오탐과 감지 지연 사이에서 균형을 잡아요.<br><sub>Deciding when a silent node counts as dead. Slow and dead look identical, so detectors balance false alarms against detection delay.</sub> | 노드 B가 1초마다 하트비트를 보내고 A는 일정 시간 소식이 없으면 B가 죽었다고 판단해요. 그런데 4초짜리 GC 멈춤이나 네트워크 지연도 밖에서 보면 죽은 것과 똑같아요. 타임아웃이 2초면 멀쩡한 B를 5초에 죽었다고 오판해 불필요한 장애 조치(리더 교체, 재배치)를 일으키고, 6초면 오탐은 없지만 진짜 장애도 6초 뒤에야 알아채요. φ 누적 감지기는 예/아니요 대신 의심 정도를 계산해요. 지금까지의 하트비트 간격 분포(평균 1초, 표준편차 0.25초)를 기억해 두고, φ = −log₁₀ P(하트비트가 단지 늦는 중일 확률)를 구해요. 마지막 하트비트 뒤 2초면 φ ≈ 4.5, 2.4초면 φ ≈ 8로, 임계값 8을 넘으면 장애로 처리해요. 네트워크가 원래 들쭉날쭉하면 분포가 넓어져 자동으로 너그러워져요. SWIM은 A가 B에게 직접 ping했는데 응답이 없으면, C와 D에게 대신 B를 확인해 달라고(ping-req) 부탁해요. 하나라도 응답을 받으면 B는 살아 있고 문제는 A의 링크였던 거예요. 모두 실패하면 B를 “의심” 상태로 가십으로 알리고, B는 더 높은 incarnation 번호로 반박할 수 있어요. 비동기 네트워크에서 완벽한 감지기는 불가능하므로, 잘못 쫓겨난 노드가 계속 쓰지 못하게 펜싱 토큰을 함께 써요.<br><sub>Node B sends a heartbeat every second, and A declares B dead after a period of silence. But a four-second GC pause or a network delay looks exactly like a crash from outside. With a 2 s timeout A wrongly declares a healthy B dead at 5 s, triggering needless failover (new leaders, rebalancing); with 6 s there is no false alarm, but real failures also take 6 s to notice. The φ accrual detector outputs a degree of suspicion instead of yes or no. It keeps the distribution of past inter-arrival times (mean 1 s, standard deviation 0.25 s) and computes φ = −log₁₀ P(the heartbeat is merely late): about 4.5 two seconds after the last heartbeat and about 8 at 2.4 s, so a threshold of 8 marks failure, and on jittery networks the wider distribution makes it automatically more tolerant. SWIM handles a missed direct ping by asking C and D to probe B on A’s behalf (ping-req); any reply proves B alive and blames A’s link. If all fail, B is gossiped as “suspect” and can refute with a higher incarnation number. Perfect detection is impossible in asynchronous networks, so fencing tokens keep wrongly evicted nodes from doing damage.</sub> |

## 비동기와 메시징 · Async and messaging

서비스들이 서로 기다리지 않고 메시지와 이벤트로 일하는 방식이에요.  
*How services work through messages and events instead of waiting on each other.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **메시지 큐**<br><sub>Message queues</sub> | 생산자가 메시지를 큐에 넣으면 소비자(워커)가 자기 속도로 꺼내 처리해요. 둘은 서로를 기다리지 않아요.<br><sub>Producers drop messages on a queue and consumers (workers) take them at their own pace; neither waits for the other.</sub> | 이메일 발송, 이미지 변환, 결제 후처리처럼 오래 걸리는 일을 뒤로 빼요. RabbitMQ, SQS가 대표적이고 실패 메시지는 DLQ로 보내요.<br><sub>Push slow work like emails, image processing and post-payment tasks to the background; RabbitMQ and SQS are common, with failed messages parked in a DLQ.</sub> |
| **Pub/Sub · 이벤트 스트리밍**<br><sub>Pub/sub and event streaming</sub> | 이벤트를 토픽에 발행하면 여러 구독자가 각자 받아요. Kafka는 이벤트를 로그로 보관하고 구독자마다 읽은 위치(오프셋)를 따로 관리해요.<br><sub>Publish an event to a topic and many subscribers each receive it; Kafka keeps events as a log and tracks each subscriber’s offset separately.</sub> | 주문 이벤트 하나로 이메일·분석·재고가 각자 반응해요. 보관된 로그를 다시 읽어 재처리하거나 새 서비스를 붙일 수 있어요.<br><sub>One order event can drive email, analytics and inventory independently, and the retained log can be replayed for reprocessing or new consumers.</sub> |
| **멱등성과 재시도**<br><sub>Idempotency and retries</sub> | 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같도록 만드는 성질이에요. 요청마다 고유 키를 붙여 중복을 걸러요.<br><sub>An operation is idempotent if doing it twice has the same effect as doing it once; a unique key per request lets the server drop duplicates.</sub> | 결제·주문 API는 Idempotency-Key 헤더를 받으세요(Stripe 방식). 메시지 소비자도 같은 메시지가 두 번 올 수 있다고 가정하고 처리해요.<br><sub>Payment and order APIs should accept an Idempotency-Key header (as Stripe does); message consumers must assume duplicates.</sub> |
| **사가 패턴**<br><sub>Saga pattern</sub> | 여러 서비스에 걸친 작업을 단계별 로컬 트랜잭션으로 나누고, 중간에 실패하면 앞 단계를 되돌리는 보상 작업을 실행해요.<br><sub>A cross-service operation is split into local transactions; if one fails, compensating actions undo the earlier steps.</sub> | 서비스마다 DB가 따로인 마이크로서비스에서 분산 트랜잭션 대신 써요. 보상 작업도 멱등하게 만들어야 해요.<br><sub>The usual replacement for distributed transactions when each microservice owns its database; compensations must be idempotent too.</sub> |
| **이벤트 소싱**<br><sub>Event sourcing</sub> | 현재 값만 저장하는 대신 일어난 모든 사건(이벤트)을 순서대로 저장하고, 상태는 이벤트를 재생해서 계산해요.<br><sub>Instead of storing only the current value, store every event in order and compute state by replaying them.</sub> | 금융 원장, 감사 기록이 중요한 도메인에 맞아요. 스키마 변경과 재생 비용이 커서 모든 곳에 쓰기보단 필요한 곳에만 써요.<br><sub>Fits ledgers and audit-heavy domains; schema evolution and replay cost make it a targeted tool rather than a default.</sub> |
| **트랜잭셔널 아웃박스**<br><sub>The transactional outbox</sub> | DB 저장과 메시지 발행을 함께 해야 할 때, 둘 중 하나만 성공하는 “이중 쓰기” 문제를 막는 패턴이에요. 보낼 이벤트를 같은 DB 트랜잭션에 함께 저장해요.<br><sub>A pattern that prevents the dual-write problem, where only one of a DB write and a message publish succeeds, by saving the outgoing event in the same database transaction.</sub> | 주문을 DB에 저장한 직후 서비스가 죽으면 OrderCreated 이벤트가 사라져 배송 서비스는 주문을 몰라요. 반대로 먼저 발행하고 DB 커밋이 실패하면 존재하지 않는 주문의 이벤트가 나가요. 아웃박스 패턴은 주문 행과 outbox 행을 하나의 로컬 트랜잭션으로 함께 저장하고, 별도 릴레이가 outbox를 폴링하거나 CDC(Debezium 등)로 읽어 브로커에 발행한 뒤 표시해요. 전달은 최소 한 번이라 중복이 생길 수 있으니 소비자는 멱등하게 만들어요.<br><sub>If the service crashes right after saving an order, the OrderCreated event is lost and shipping never hears of the order. Publish first instead and a failed DB commit leaves an event for an order that doesn’t exist. The outbox pattern stores the order row and an outbox row in one local transaction; a separate relay polls the outbox or reads it through CDC (e.g. Debezium), publishes to the broker and marks the row. Delivery is at least once, so consumers must be idempotent.</sub> |

## 일관성과 합의 · Consistency and consensus

여러 대의 컴퓨터가 같은 데이터에 대해 의견을 맞추는 방법이에요.  
*How many machines agree on the same data.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **CAP 정리**<br><sub>CAP theorem</sub> | 네트워크 분할(P)이 생기면 일관성(C)과 가용성(A) 중 하나를 포기해야 해요.<br><sub>During a network partition (P), a system must give up either consistency (C) or availability (A).</sub> | 분할은 피할 수 없으니 "장애 때 무엇을 택할까"의 문제예요. 은행 잔액은 CP, 좋아요 수나 피드는 AP가 자연스러워요. 평소의 지연까지 따지는 PACELC도 있어요.<br><sub>Partitions happen, so the real question is what to sacrifice when they do: balances lean CP, likes and feeds lean AP; PACELC adds the everyday latency trade-off.</sub> |
| **강한 일관성 vs 최종 일관성**<br><sub>Strong vs eventual consistency</sub> | 강한 일관성은 쓰기 직후 누가 읽어도 새 값을 보장하고, 최종 일관성은 잠시 옛 값이 보일 수 있지만 결국 같아져요.<br><sub>Strong consistency guarantees every read after a write sees it; eventual consistency may briefly show old data but converges.</sub> | 복제 지연 때문에 "방금 바꿨는데 안 바뀌었어요" 버그가 생겨요. 내가 쓴 데이터는 리더에서 읽는 read-your-writes로 많이 해결해요.<br><sub>Replica lag causes “I just changed it but it didn’t change” bugs; read-your-writes (reading your own data from the leader) fixes most of them.</sub> |
| **쿼럼 (N · W · R)**<br><sub>Quorums (N · W · R)</sub> | 복제본 N개 중 W개에 쓰고 R개에서 읽을 때 W + R > N이면 읽는 집합과 쓰는 집합이 반드시 겹쳐 최신 값을 볼 수 있어요.<br><sub>With N replicas, writing to W and reading from R guarantees an overlap, and so the latest value, when W + R > N.</sub> | Cassandra, DynamoDB에서 일관성 수준을 이 값으로 조절해요. 흔한 설정은 N=3, W=2, R=2예요.<br><sub>Cassandra and DynamoDB expose consistency levels this way; N=3, W=2, R=2 is a common setup.</sub> |
| **Raft 합의 알고리즘**<br><sub>Raft consensus</sub> | 노드들이 리더를 선출하고, 리더가 로그를 팔로워에게 복제해 과반이 저장하면 확정해요. 리더가 죽으면 새로 선거해요.<br><sub>Nodes elect a leader; the leader replicates its log to followers and commits an entry once a majority stores it, holding a new election if it dies.</sub> | etcd(쿠버네티스), Consul, CockroachDB, Kafka KRaft가 Raft를 써요. 과반이 필요해서 노드는 3·5대처럼 홀수로 둬요.<br><sub>Used by etcd (Kubernetes), Consul, CockroachDB and Kafka KRaft; clusters use odd sizes like 3 or 5 because a majority is required.</sub> |
| **2단계 커밋 (2PC)**<br><sub>Two-phase commit</sub> | 코디네이터가 모든 참여자에게 준비를 묻고(1단계), 모두 YES면 커밋, 하나라도 NO면 전부 롤백해요(2단계).<br><sub>A coordinator asks every participant to prepare (phase 1), then commits if all vote yes or rolls everyone back if any vote no (phase 2).</sub> | 하나의 DB 안이나 XA 트랜잭션에서 쓰여요. 코디네이터 장애 때 참여자가 잠긴 채 멈출 수 있어 마이크로서비스에선 사가를 선호해요.<br><sub>Used inside databases and XA transactions; a failed coordinator can leave participants blocked, so microservices prefer sagas.</sub> |
| **논리 시계 (램포트)**<br><sub>Logical clocks (Lamport)</sub> | 서버마다 시계가 어긋나므로, 이벤트마다 카운터를 올리고 메시지를 받으면 max(내 값, 받은 값) + 1로 맞춰 원인-결과 순서를 표현해요.<br><sub>Since machine clocks drift, each process bumps a counter per event and, on receiving a message, sets it to max(local, received) + 1, so causes get smaller numbers than effects.</sub> | 분산 로그 정렬, 충돌 해결의 기초예요. 동시 발생까지 구분하려면 벡터 클록, 실제 시간과 섞으려면 HLC(하이브리드 논리 시계)를 써요.<br><sub>The basis for ordering distributed logs and resolving conflicts; vector clocks detect concurrency and hybrid logical clocks mix in wall time.</sub> |
| **벡터 시계**<br><sub>Vector clocks</sub> | 프로세스마다 칸이 하나씩 있는 카운터 벡터로, 두 사건이 인과 관계(먼저 일어남)인지 동시인지를 정확히 판별하는 논리 시계예요.<br><sub>Logical clocks made of a counter vector with one slot per process, which tell exactly whether two events are causally ordered (happened before) or concurrent.</sub> | 각 프로세스는 [P1, P2, P3] 같은 벡터를 들고 사건마다 자기 칸을 1 올려요. 메시지에 벡터를 실어 보내고, 받는 쪽은 칸별 최댓값을 취한 뒤 자기 칸을 올려요. 모든 칸이 작거나 같으면 “먼저 일어남(→)”이고, 어느 쪽도 작지 않으면 동시(∥)예요. 램포트 시계는 숫자 하나라 3 > 1이어도 인과인지 동시인지 알 수 없지만, 벡터 시계는 구분할 수 있어요. 대신 벡터가 프로세스 수만큼 길어지고, 다이나모 계열 저장소가 동시 쓰기 충돌을 찾을 때 써요.<br><sub>Each process keeps a vector such as [P1, P2, P3] and adds 1 to its own slot for every event. Messages carry the vector; the receiver takes the slot-wise maximum, then bumps its own slot. If every slot is less than or equal, one event happened before the other (→); if neither is smaller, they are concurrent (∥). A Lamport clock is a single number, so 3 > 1 can’t distinguish causality from concurrency, but a vector clock can. The cost is a vector as long as the number of processes; Dynamo-style stores use it to detect conflicting concurrent writes.</sub> |
| **CRDT**<br><sub>CRDTs</sub> | 여러 복제본이 서로 조정하지 않고 따로 수정해도, 합치면 반드시 같은 상태로 수렴하도록 설계된 자료형이에요.<br><sub>Data types designed so that replicas edited independently, with no coordination, always converge to the same state once merged.</sub> | 네트워크가 끊긴 채 서울 복제본은 좋아요 2개, 도쿄 복제본은 3개를 받았을 때 “마지막 쓰기 승리”로 합치면 2개가 사라져요. G-카운터는 복제본마다 자기 칸만 올리고, 합칠 때 칸별 최댓값을 취해 [2, 3], 값은 합계 5가 돼요. 합치기 연산이 교환·결합 법칙과 멱등성을 만족하므로 순서나 중복과 상관없이 수렴해요(강한 최종 일관성). PN-카운터, OR-Set, LWW-Register, 공동 편집용 시퀀스 CRDT가 있고 Yjs·Automerge, Riak, Redis Active-Active가 써요.<br><sub>Suppose that while partitioned the Seoul replica gets 2 likes and the Tokyo replica gets 3; a last-write-wins merge loses 2 of them. A G-counter lets each replica bump only its own slot and merges by slot-wise maximum, giving [2, 3] with value 5. Because the merge is commutative, associative and idempotent, replicas converge regardless of order or duplicates (strong eventual consistency). There are PN-counters, OR-sets, LWW-registers and sequence CRDTs for collaborative text, used by Yjs, Automerge, Riak and Redis Active-Active.</sub> |
| **분산 락과 펜싱 토큰**<br><sub>Distributed locks and fencing tokens</sub> | 여러 서버 중 하나만 자원을 쓰게 하는 분산 락은 임대(lease)만으로는 안전하지 않아요. 계속 커지는 펜싱 토큰을 저장소가 확인해야 해요.<br><sub>Distributed locks let only one server use a resource at a time, but a lease alone isn’t safe: the resource must check a monotonically increasing fencing token.</sub> | C1이 10초짜리 임대 락과 토큰 33을 받은 뒤 GC로 멈춘 사이 임대가 만료되고, C2가 토큰 34로 락을 받아 저장소에 써요. 깨어난 C1은 아직 락을 가졌다고 믿고 써서 C2의 데이터를 덮어써요. 펜싱 토큰을 쓰면 저장소가 지금까지 본 최대 토큰(34)보다 작은 33의 요청을 거절해요. ZooKeeper의 zxid나 etcd의 revision처럼 단조 증가하는 값을 토큰으로 쓰고, 확인은 반드시 자원 쪽에서 해야 해요.<br><sub>C1 takes a 10-second lease lock with token 33, then pauses for garbage collection while the lease expires; C2 acquires the lock with token 34 and writes to storage. C1 wakes believing it still holds the lock and overwrites C2’s data. With fencing tokens, storage rejects C1’s request because 33 is smaller than the largest token it has seen, 34. Monotonic values such as ZooKeeper’s zxid or etcd’s revision serve as tokens, and the check must happen at the resource itself.</sub> |
| **머클 트리와 안티 엔트로피**<br><sub>Merkle trees and anti-entropy</sub> | 데이터 블록의 해시를 트리로 쌓아, 두 복제본의 차이를 해시 몇 번만 비교해서 찾아내는 구조예요.<br><sub>A tree built from hashes of data blocks that finds where two replicas differ with only a few hash comparisons.</sub> | 블록마다 해시를 구하고, 부모는 자식 해시들을 이어 붙여 다시 해시해 루트까지 올려요. 두 복제본의 루트가 같으면 전체가 같고, 다르면 자식으로 내려가며 같은 쪽 하위 트리는 통째로 건너뛰어요. 약 log N번만 내려가면 다른 블록을 찾아 그것만 보내면 돼요. 카산드라·다이나모의 안티 엔트로피 복구가 이렇게 복제본을 맞추고, Git의 커밋 구조, 블록체인, 인증서 투명성 로그도 머클 트리를 써요.<br><sub>Hash every block, then hash each pair of child hashes into a parent, up to the root. If two replicas have the same root, everything matches; otherwise descend, skipping any subtree whose hashes agree. About log N steps down reveal the differing block, and only it needs sending. Cassandra and Dynamo’s anti-entropy repair reconciles replicas this way, and Git’s object model, blockchains and Certificate Transparency logs also rely on Merkle trees.</sub> |
| **안티 엔트로피**<br><sub>Anti-entropy</sub> | 복제본 사이에 어긋난 데이터를 찾아 최신 상태로 맞추는 과정이에요. 힌트 핸드오프, 읽기 복구, 백그라운드 머클 비교가 함께 일해요.<br><sub>The process that finds and reconciles divergent data between replicas: hinted handoff, read repair and background Merkle comparison work together.</sub> | 키 x를 A, B, C 세 복제본에 두고 W = 2로 쓰면, C가 잠깐 꺼져 있는 동안의 쓰기는 A와 B에만 반영돼 C는 옛 값(v1, 타임스탬프 10)을 갖게 돼요. 이렇게 어긋난 복제본은 세 가지 방법으로 맞춰요. 힌트 핸드오프는 쓰기 시점에 C 대신 다른 노드 D가 “C에게 x = v2”라는 힌트를 맡아 두었다가 C가 돌아오면 전달해요. 짧은 장애에는 빠르지만, 힌트를 가진 노드도 죽으면 사라져요. 읽기 복구는 R = 2로 B와 C에서 읽었을 때 B는 v2 @20, C는 v1 @10을 돌려주면, 타임스탬프가 최신인 v2를 클라이언트에게 주고 뒤에서 C에 v2를 다시 써 주는 방식이에요. 하지만 아무도 읽지 않는 키는 영영 고쳐지지 않아요. 그래서 백그라운드 안티 엔트로피가 주기적으로 복제본끼리 머클 트리를 비교해, 다른 범위만 찾아 동기화해요. 카산드라에서는 삭제도 톰스톤이라는 쓰기로 퍼지므로, 톰스톤이 정리되기 전(gc\_grace\_seconds 안)에 복구를 돌리지 않으면 지운 데이터가 옛 복제본에서 되살아나요. 최종 일관성 저장소(카산드라, 다이나모, Riak)가 결국 같아지는 이유가 이 과정이고, 타임스탬프 최신 우선(LWW)은 단순하지만 동시에 일어난 두 쓰기 중 하나를 조용히 잃을 수 있어 벡터 시계나 CRDT로 보완하기도 해요.<br><sub>With key x stored on replicas A, B and C and writes using W = 2, a write made while C is briefly down reaches only A and B, leaving C with the old value (v1, timestamp 10). Three mechanisms bring replicas back in line. Hinted handoff has another node, D, keep a hint (“x = v2 for C”) at write time and deliver it when C returns; it is quick for short outages but lost if the hint holder dies too. Read repair, when a read with R = 2 gets v2 @20 from B and v1 @10 from C, returns the newer v2 to the client and writes v2 back to C in the background; keys nobody reads, however, never get fixed. So background anti-entropy periodically compares Merkle trees between replicas and syncs only the ranges that differ. In Cassandra deletions spread as tombstone writes, so if repair does not run before tombstones are purged (within gc\_grace\_seconds), deleted data resurrects from an old replica. This process is why eventually consistent stores such as Cassandra, Dynamo and Riak converge; last-write-wins by timestamp is simple but can silently drop one of two concurrent writes, which vector clocks or CRDTs address.</sub> |

## 아키텍처와 장애 대응 · Architecture and resilience

서비스를 나누고 연결하고, 일부가 고장 나도 전체가 버티게 만드는 설계예요.  
*Designs for splitting and connecting services, and for surviving partial failures.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **모놀리스 vs 마이크로서비스**<br><sub>Monolith vs microservices</sub> | 모놀리스는 하나로 빌드·배포하고, 마이크로서비스는 기능별로 나눠 각자 DB와 배포 주기를 가져요.<br><sub>A monolith is built and deployed as one unit; microservices split by capability, each with its own database and release cycle.</sub> | 마이크로서비스는 팀이 독립적으로 움직일 때 효과가 있어요. 작은 팀이라면 경계를 잘 나눈 모듈러 모놀리스가 대부분 더 나아요.<br><sub>Microservices pay off when teams need to move independently; small teams are usually better served by a well-structured modular monolith.</sub> |
| **API 게이트웨이**<br><sub>API gateway</sub> | 외부 요청이 들어오는 단일 입구예요. 인증, 레이트 리밋, 라우팅, 응답 합치기, 로깅 같은 공통 기능을 한곳에서 처리해요.<br><sub>A single entry point for outside traffic that handles cross-cutting concerns: auth, rate limiting, routing, aggregation and logging.</sub> | Kong, AWS API Gateway, Nginx가 대표적이에요. 화면별로 맞춘 게이트웨이(BFF)를 따로 두기도 해요. 비즈니스 로직은 넣지 마세요.<br><sub>Kong, AWS API Gateway and Nginx are common; some teams add a backend-for-frontend per client. Keep business logic out of it.</sub> |
| **REST · GraphQL · gRPC**<br><sub>REST · GraphQL · gRPC</sub> | REST는 자원(URL)마다 요청하고, GraphQL은 필요한 필드를 쿼리 하나로, gRPC는 스키마로 정한 함수를 바이너리로 호출해요.<br><sub>REST requests one resource URL at a time, GraphQL fetches exactly the needed fields in one query, and gRPC calls schema-defined functions over a binary protocol.</sub> | 공개 API는 REST가 무난하고, 화면이 다양한 앱은 GraphQL, 내부 서비스 간 고성능 통신은 gRPC가 잘 맞아요.<br><sub>REST suits public APIs, GraphQL suits apps with many varied screens, and gRPC suits fast service-to-service calls.</sub> |
| **gRPC**<br><sub>gRPC</sub> | protobuf 스키마로 정의한 함수를 HTTP/2 위에서 이진 메시지로 호출하는 RPC 프레임워크예요. 내부 서비스 사이의 고성능 통신에 잘 맞아요.<br><sub>An RPC framework that calls protobuf-defined functions with binary messages over HTTP/2; a strong fit for high-performance traffic between internal services.</sub> | gRPC에서는 .proto 파일에 service Orders { rpc Get(GetReq) returns (Order); }처럼 함수를, message Order { int64 id = 1; string item = 2; int32 qty = 3; }처럼 메시지를 정의해요. protoc가 Go, Java, Python, TypeScript 등 언어마다 클라이언트 스텁과 서버 인터페이스를 생성해, client.Get(ctx, req)처럼 원격 호출을 로컬 함수처럼 써요. 메시지는 필드 이름 대신 필드 번호와 가변 길이 정수를 쓰는 이진 형식이라 Order{12345, "book", 2}가 JSON으로는 34바이트지만 protobuf로는 11바이트이고, 파싱도 빨라요. 전송은 HTTP/2라 연결 하나에 여러 호출이 동시에 오가고, 단항 외에 서버 스트리밍, 클라이언트 스트리밍, 양방향 스트리밍을 지원해요. 클라이언트가 정한 데드라인(예: 300 ms)은 하위 서비스 호출까지 전파되고, 넘기거나 취소되면 연쇄적으로 작업을 멈춰 자원을 아껴요. 주의할 점도 있어요. 브라우저는 HTTP/2 프레임을 직접 다룰 수 없어 gRPC-Web 프록시가 필요하고, L4 로드 밸런서는 오래 유지되는 HTTP/2 연결을 한 서버에 묶어 버려 L7 밸런서나 클라이언트 쪽 분산이 필요해요. 이진이라 사람이 읽기 어려워 grpcurl과 서버 리플렉션을 쓰고, 호환성을 위해 지운 필드 번호는 절대 재사용하지 않아요(reserved). 공개 API는 여전히 REST·JSON이 무난하고, grpc-gateway로 둘을 함께 제공하기도 해요.<br><sub>In gRPC a .proto file defines functions, such as service Orders { rpc Get(GetReq) returns (Order); }, and messages, such as message Order { int64 id = 1; string item = 2; int32 qty = 3; }. protoc generates client stubs and server interfaces for Go, Java, Python, TypeScript and more, so a remote call reads like a local one: client.Get(ctx, req). Messages use a binary encoding with field numbers and varints instead of names, so Order{12345, "book", 2} takes 34 bytes as JSON but 11 as protobuf, and parses faster. Transport is HTTP/2, so many calls share one connection, and besides unary calls it supports server streaming, client streaming and bidirectional streaming. A deadline set by the client (say 300 ms) propagates to downstream calls, and when it expires or the call is cancelled, work stops along the chain. There are caveats: browsers cannot speak raw HTTP/2 frames and need a gRPC-Web proxy; L4 load balancers pin long-lived HTTP/2 connections to one server, so L7 or client-side balancing is needed; the binary format is hard to read, hence grpcurl and server reflection; and removed field numbers must never be reused (mark them reserved). Public APIs are still easier as REST and JSON, and grpc-gateway can expose both.</sub> |
| **CQRS**<br><sub>CQRS</sub> | 쓰기(명령)와 읽기(조회)를 서로 다른 모델과 저장소로 나눠요. 쓰기 쪽 변경이 이벤트로 읽기 쪽 뷰를 갱신해요.<br><sub>Separates writes (commands) and reads (queries) into different models and stores, with write-side events updating read-side views.</sub> | 읽기가 압도적으로 많거나 화면용 집계가 복잡할 때 유용해요. 읽기 모델이 잠깐 늦을 수 있다는 걸 화면에서 감안해야 해요.<br><sub>Useful when reads dominate or screen-specific aggregates are complex; the UI must tolerate a briefly stale read model.</sub> |
| **서킷 브레이커**<br><sub>Circuit breaker</sub> | 하위 서비스가 계속 실패하면 회로를 열어 호출을 즉시 실패시키고, 잠시 뒤 시험 요청으로 회복을 확인해요.<br><sub>After repeated failures it opens the circuit and fails calls immediately, then probes with a trial request before closing again.</sub> | 느린 서비스 하나가 스레드·커넥션을 다 잡아먹어 전체가 죽는 연쇄 장애를 막아요. Resilience4j, Envoy, 서비스 메시에 들어 있어요.<br><sub>Prevents one slow dependency from exhausting threads and connections and taking everything down; built into Resilience4j, Envoy and service meshes.</sub> |
| **지수 백오프와 지터**<br><sub>Exponential backoff and jitter</sub> | 실패한 요청을 재시도할 때 간격을 1초, 2초, 4초처럼 두 배씩 늘리고, 무작위 값(지터)을 더해 재시도가 한꺼번에 몰리지 않게 해요.<br><sub>Retry failed requests with doubling waits such as 1 s, 2 s, 4 s, plus random jitter so clients don’t retry in lockstep.</sub> | 최대 재시도 횟수와 최대 대기 시간을 꼭 두세요. 멱등하지 않은 요청은 함부로 재시도하면 안 돼요. AWS SDK 등 대부분의 클라이언트에 내장돼 있어요.<br><sub>Always cap attempts and total wait, and never blindly retry non-idempotent requests; most SDKs, AWS included, build this in.</sub> |
| **용량 추정**<br><sub>Back-of-the-envelope estimation</sub> | 사용자 수에서 출발해 초당 요청, 피크, 저장 용량을 어림 계산해 필요한 규모를 잡아요.<br><sub>Start from user counts and roughly derive requests per second, peaks and storage to size the system.</sub> | 시스템 설계 면접과 실제 기획 모두에 써요. 하루 ≈ 10만 초, 피크 ≈ 평균의 2~3배처럼 외워 두면 빨라요.<br><sub>Used in system design interviews and real planning; shortcuts like “a day ≈ 100k seconds” and “peak ≈ 2–3× average” keep it quick.</sub> |
