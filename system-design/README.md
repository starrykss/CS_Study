| **계층별 지연 시간**<br><sub>Latency by layer</sub> | 같은 컴퓨터에서 재자 Map 조회 0.12µs, Redis GET 56µs, PostgreSQL 키 조회 79µs, 커밋 283µs였어요. 소켓을 한 번 건너는 왕복이 자릿수를 바꾸고, 내구성 있는 쓰기는 읽기의 몇 배가 들어요.<br><sub>Measured on one machine, a Map lookup took 0.12 µs, a Redis GET 56 µs, a PostgreSQL key lookup 79 µs and a commit 283 µs. A single socket round trip changes the order of magnitude, and durable writes cost several times a read.</sub> | 시스템 설계의 많은 결정은 어디에 시간이 드는지에 대한 감에서 나와요. 그 감을 숫자로 확인하려고 2코어 컨테이너 한 대에서 여러 계층의 작업을 같은 방법으로 수천 번씩 반복해 중간값을 쟀어요. 프로세스 안의 일은 매우 빨랐어요. 키 백만 개가 든 Map에서 값 하나를 꺼내는 데 0.12µs, 727바이트 JSON을 파싱하는 데 2.3µs, 1KB의 SHA-256 해시가 2.0µs, 운영체제 페이지 캐시에 있는 4KB 파일을 읽는 데 5.1µs였어요. 소켓을 한 번 건너면 자릿수가 바뀌었어요. 같은 컴퓨터 안의 HTTP 요청은 연결을 재사용해도 52µs, Redis GET은 56µs, PostgreSQL의 기본 키 조회는 79µs였어요. 흥미로운 점은 Redis와 PostgreSQL의 차이가 크지 않다는 거예요. 둘 다 시간의 대부분이 요청을 보내고 받는 왕복과 프로토콜 처리이고, 실제 데이터를 찾는 일은 작은 부분이에요. 그래서 캐시의 이득은 한 번의 조회를 빠르게 하는 것보다 DB의 부하를 덜어 주는 데서 더 크게 나와요. 이 점은 URL 단축기 섹션에서 다시 확인해요. 쓰기는 내구성이 비용을 정했어요. INSERT를 커밋하면 PostgreSQL은 WAL을 디스크에 fsync할 때까지 기다리므로 283µs가 걸렸어요. 4KB를 쓰고 fsync만 하는 데도 338µs였어요. synchronous\_commit을 끄자 같은 INSERT가 62µs로 줄었지만, 그 대신 장애가 나면 이미 커밋됐다고 응답한 마지막 몇 개의 트랜잭션을 잃을 수 있어요. 확장과 운영 섹션의 쓰기 묶기는 이 커밋 비용을 여러 행이 나눠 내게 하는 방법이에요. 이 측정값은 모두 같은 컴퓨터 안이라 네트워크가 가장 짧은 경우예요. 서버가 다른 머신에 있으면 왕복마다 네트워크 지연이 더해지고, 데이터센터나 대륙을 건너면 훨씬 커져요. 그래서 요청 하나를 처리하는 데 몇 번의 왕복이 필요한지를 세는 것이 응답 시간을 예측하는 첫걸음이에요. 같은 데이터를 여러 번 왕복해 가져오는 N+1 쿼리가 느린 이유도, 묶어서 보내는 배치가 빠른 이유도 모두 이 왕복 비용에 있어요. 실제 서비스에서는 이런 숫자를 자기 환경에서 직접 재 두면, 설계 회의에서 감이 아니라 근거로 이야기할 수 있어요.<br><sub>Many system design decisions come from a feel for where time goes. To check that feel with numbers, work at several layers was repeated thousands of times the same way on one 2-core container and the medians were taken. Work inside the process was very fast: reading one value from a Map holding a million keys took 0.12 µs, parsing 727 bytes of JSON 2.3 µs, a SHA-256 hash of 1 KB 2.0 µs, and reading a 4 KB file from the operating system’s page cache 5.1 µs. Crossing a socket once changed the order of magnitude. An HTTP request within the same machine took 52 µs even with a reused connection, a Redis GET 56 µs and a PostgreSQL primary-key lookup 79 µs. Interestingly, Redis and PostgreSQL were not far apart: for both, most of the time is the round trip of sending and receiving plus protocol handling, and actually finding the data is a small part. A cache’s benefit therefore comes more from relieving database load than from making a single lookup faster, a point revisited in the URL shortener section. For writes, durability set the cost. Committing an INSERT makes PostgreSQL wait until the WAL is fsynced to disk, which took 283 µs, and writing 4 KB and calling fsync alone took 338 µs. With synchronous\_commit off the same INSERT dropped to 62 µs, but a crash could then lose the last few transactions already reported as committed. Write batching in the scaling and operations section is a way to have many rows share this commit cost. All of these figures come from a single machine, the shortest possible network. When servers sit on other machines, every round trip adds network delay, and crossing data centers or continents adds far more. Counting how many round trips one request needs is therefore the first step in predicting response time; N+1 queries are slow and batching is fast for the very same reason. Measuring such numbers in one’s own environment lets design discussions rest on evidence instead of intuition.</sub> |
| **리틀의 법칙**<br><sub>Little’s law</sub> | 동시 요청 수는 처리량 × 응답 시간과 같았어요. CPU 1ms짜리 서버는 동시 요청 10개까지 처리량이 비례해 늘다가 초당 930개에서 멈췄고, 그 뒤로는 응답 시간만 늘었어요.<br><sub>The number of requests in flight equaled throughput × latency. A server spending 1 ms of CPU per request scaled throughput linearly up to 10 concurrent requests, stalled at 930 per second, and after that only latency grew.</sub> | 리틀의 법칙은 L = λW라는 짧은 식이에요. 시스템 안에 동시에 머무는 요청의 평균 수 L은, 초당 들어와 처리되는 요청의 수 λ에 요청 하나가 머무는 평균 시간 W를 곱한 값과 같아요. 대기열의 모양이나 처리 순서와 상관없이 안정된 시스템이면 늘 성립해요. 확인하려고 요청마다 CPU를 1ms 쓰고 20ms를 기다리는 Node.js 서버를 만들었어요. 기다리는 20ms는 DB나 다른 서비스를 기다리는 시간을 흉내 낸 거예요. 부하 도구 autocannon으로 동시 연결 수를 1, 10, 50, 100으로 바꿔 가며 쟀어요. 동시 연결 1개는 초당 45개를 처리했고 평균 응답 시간은 21.7ms였어요. 10개는 초당 452개, 21.6ms였어요. 응답 시간은 그대로인데 처리량이 정확히 10배가 됐어요. 요청 대부분의 시간이 기다림이라, 그동안 다른 요청을 받을 수 있었기 때문이에요. 50개에서는 초당 914개로 늘었지만 평균 응답 시간이 54ms가 됐고, 100개에서는 930개에 106ms였어요. 요청마다 CPU를 1ms씩 쓰므로 스레드 하나로는 초당 1,000개를 넘을 수 없어요. 처리량이 한계에 닿은 뒤로는 동시 요청을 늘려도 요청들이 CPU를 기다리는 줄만 길어져 응답 시간만 늘어났어요. 네 경우 모두 처리량 × 평균 응답 시간을 계산하면 1.0, 9.7, 49.4, 98.8로 동시 연결 수와 맞았어요. 이 식은 설계에서 자주 쓰여요. 초당 2,000개의 요청을 받고 각 요청이 DB 연결을 평균 5ms 쓴다면, 동시에 쓰이는 연결은 평균 10개이므로 연결 풀은 그보다 여유 있게 잡으면 돼요. 반대로 연결 풀이 20개로 고정되어 있고 쿼리가 느려져 50ms가 걸린다면, 처리할 수 있는 요청은 초당 400개로 줄어요. 응답 시간이 늘면 같은 동시성으로 처리할 수 있는 양이 줄어드는 거예요. 장애 때 응답 시간이 늘면서 스레드와 연결이 모두 묶여 서비스 전체가 멈추는 현상도 이 식으로 설명돼요. 그래서 타임아웃은 동시성이 무한히 쌓이는 것을 막는 장치이기도 해요.<br><sub>Little’s law is the short formula L = λW: the average number of requests inside a system at once, L, equals the number of requests arriving and completing per second, λ, times the average time each one stays, W. It holds for any stable system regardless of queue shape or processing order. To check it, a Node.js server was built that spends 1 ms of CPU and then waits 20 ms per request, the wait imitating time spent on a database or another service. The load tool autocannon varied the number of concurrent connections among 1, 10, 50 and 100. One connection handled 45 requests per second with an average latency of 21.7 ms, and ten handled 452 per second at 21.6 ms: latency unchanged and throughput exactly tenfold, because most of each request’s time was waiting, during which other requests could be accepted. With 50 connections throughput rose to 914 per second, but average latency became 54 ms, and with 100 it was 930 at 106 ms. Spending 1 ms of CPU per request, a single thread cannot exceed 1,000 per second, so once throughput hit that limit, more concurrency only lengthened the line of requests waiting for the CPU and raised latency. In all four cases throughput times average latency came to 1.0, 9.7, 49.4 and 98.8, matching the number of connections. Designers use this formula often. If 2,000 requests arrive per second and each holds a database connection for 5 ms on average, 10 connections are in use on average, so the pool is sized with some headroom above that. Conversely, with a pool fixed at 20 connections and queries slowing to 50 ms, only 400 requests per second can be served: longer latency shrinks what the same concurrency can handle. The same formula explains outages where rising latency ties up every thread and connection until the whole service stops, which is why timeouts also serve to keep concurrency from piling up without limit.</sub> |
| **사용률과 대기열**<br><sub>Utilization and queues</sub> | 평균 처리 시간이 1ms인 서버를 시뮬레이션하자 평균 응답 시간이 사용률 90%에서 10배, 99%에서 97배가 됐어요. p99는 더 빨리 나빠졌고, 처리 시간이 일정하면 대기는 절반이었어요.<br><sub>Simulating a server with a 1 ms mean service time, mean response time became 10× at 90% utilization and 97× at 99%. p99 worsened faster, and constant service times halved the waiting.</sub> | 서버의 사용률이 80%라는 말은 시간의 80% 동안 바쁘다는 뜻이에요. 남은 20%가 있으니 여유가 있어 보이지만, 요청은 고르게 오지 않아요. 몰려서 온 요청은 줄을 서고, 그 줄이 응답 시간을 늘려요. 요청이 무작위로 도착하고 처리 시간도 무작위인 서버 하나를 파이썬으로 시뮬레이션했어요. 평균 처리 시간은 1ms로 고정하고, 도착 속도를 바꿔 사용률 ρ를 50%에서 99%까지 올리며 요청 40만 개가 도착해서 끝날 때까지의 시간을 기록했어요. 평균 응답 시간은 사용률 50%에서 2.0ms, 70%에서 3.3ms, 80%에서 4.9ms였어요. 90%에서는 10.3ms, 95%에서는 20.1ms, 99%에서는 97.5ms로 뛰었어요. 대기열 이론의 공식 S/(1-ρ)가 주는 2, 3.3, 5, 10, 20, 100과 거의 같아요. 처리 시간은 그대로 1ms인데 응답 시간의 대부분이 줄 서는 시간이 된 거예요. 사용률이 90%에서 99%로 9%p 오르는 동안 응답 시간은 10배가 됐어요. 꼬리는 더 가팔랐어요. p99는 50%에서 9.3ms, 90%에서 49.2ms, 99%에서 335ms였어요. 사용자가 느끼는 최악의 경험은 평균보다 훨씬 먼저 무너져요. 다음으로 처리 시간을 무작위가 아니라 늘 정확히 1ms로 바꿨어요. 같은 90%에서 평균이 5.5ms, p99가 22.3ms로 거의 절반이었어요. 처리 시간이 들쭉날쭉할수록 대기열이 길어진다는 뜻이에요. 실제 서비스에서는 대부분 짧은 요청 사이에 가끔 아주 긴 요청이 섞이는데, 이런 요청이 뒤의 짧은 요청들을 모두 기다리게 만들어요. 그래서 리포트 생성처럼 긴 작업은 별도의 워커나 대기열로 떼어 내 처리 시간의 변동을 줄여요. 이 결과는 용량을 계획하는 방법을 바꿔요. 서버가 사용률 100%까지 일할 수 있다고 보고 대수를 정하면, 평소에는 괜찮다가 트래픽이 조금만 늘어도 응답 시간이 몇 배로 뛰어요. 그래서 평소 사용률에 여유를 두고 대수를 정하고, 오토스케일링도 사용률이 한계에 닿기 훨씬 전에 늘리도록 기준을 잡아요. 앞 항목의 리틀의 법칙에서 처리량이 한계에 닿은 뒤 응답 시간만 늘어난 것도 같은 현상이에요.<br><sub>A server at 80% utilization is busy 80% of the time. The remaining 20% looks like headroom, but requests do not arrive evenly: bunched-up requests queue, and the queue lengthens response time. A single server with random arrivals and random service times was simulated in Python. With the mean service time fixed at 1 ms, the arrival rate was varied to raise utilization ρ from 50% to 99%, recording the time from arrival to completion for 400,000 requests. Mean response time was 2.0 ms at 50%, 3.3 ms at 70% and 4.9 ms at 80%, then jumped to 10.3 ms at 90%, 20.1 ms at 95% and 97.5 ms at 99%, nearly matching queueing theory’s S/(1-ρ), which gives 2, 3.3, 5, 10, 20 and 100. Service still took 1 ms, but most of the response time had become time spent waiting in line; while utilization rose 9 points from 90% to 99%, response time grew tenfold. The tail was steeper: p99 was 9.3 ms at 50%, 49.2 ms at 90% and 335 ms at 99%, so the worst experiences users feel collapse long before the average. Next, service time was changed from random to exactly 1 ms every time. At the same 90%, the mean was 5.5 ms and p99 22.3 ms, almost half, meaning the more service times vary, the longer the queues. Real services mostly mix short requests with occasional very long ones, and those make every short request behind them wait, which is why long jobs such as report generation are moved to separate workers or queues to reduce variability. These results change how capacity is planned. Sizing the fleet as if servers could work at 100% leaves things fine on normal days but multiplies response times when traffic rises only slightly, so the number of servers is chosen with headroom over normal utilization, and autoscaling thresholds are set to add capacity well before utilization reaches its limit. The stall in Little’s law, where only latency grew once throughput hit its limit, is the same phenomenon.</sub> |
| **팬아웃과 꼬리 지연**<br><sub>Fan-out and tail latency</sub> | 1%만 느린 백엔드를 100번 동시에 부르자 사용자 요청의 68%가 느려졌어요. 1 − 0.99^N의 계산과 거의 같았고, 중간값마저 느린 응답을 기다렸어요.<br><sub>Calling a backend that is slow only 1% of the time 100 times at once slowed 68% of user requests. This nearly matched 1 − 0.99^N, and even the median waited for a slow reply.</sub> | 검색, 피드, 추천 같은 요청은 여러 백엔드에 동시에 묻고 모든 답을 모아 하나의 응답을 만들어요. 검색 인덱스가 샤드 수십 개로 나뉘어 있거나, 화면 하나에 여러 서비스의 데이터가 필요할 때 그래요. 이때 사용자 요청은 가장 느린 백엔드가 답할 때까지 기다려야 해요. 백엔드 서버를 하나 만들고 요청의 99%는 2ms, 1%는 50ms 만에 답하게 했어요. 개별 서버로 보면 p99가 50ms인 꽤 괜찮은 서버예요. 사용자 요청 하나가 이 백엔드를 N번 동시에 부르고 모두 끝날 때까지 기다리게 한 뒤, 40ms를 넘은 사용자 요청의 비율을 쟀어요. N이 1이면 0.9%였어요. N이 10이면 9.9%, 50이면 43.3%, 100이면 68.0%였어요. 사용자 요청이 느려지려면 N개의 호출 가운데 하나만 느리면 되므로, 그 확률은 1 − 0.99^N이에요. 계산값 9.6%, 39.5%, 63.4%와 거의 같았어요. N이 100일 때는 사용자 요청의 중간값이 51.9ms였어요. 개별 백엔드의 p99가 사용자 요청의 p50이 된 거예요. N이 큰 경우 측정값이 계산보다 조금 나쁜 것은, 동시에 쏟아지는 100개의 요청 때문에 백엔드 자체도 조금 느려졌기 때문이에요. 이 현상은 대규모 시스템에서 평균이 아니라 꼬리 지연, 곧 p99와 p999를 관리해야 하는 이유예요. 백엔드 하나의 드문 지연이 팬아웃을 거치면 흔한 지연이 돼요. 대책은 여러 가지예요. 개별 서버의 꼬리를 줄이려면 GC 멈춤, 디스크 쓰기, 백그라운드 작업처럼 가끔 생기는 지연의 원인을 찾아 없애요. 구조적으로는 팬아웃 수를 줄이거나, 다음 항목처럼 늦은 요청을 다른 복제본에 한 번 더 보내는 헤지 요청을 써요. 검색처럼 완벽한 결과가 꼭 필요하지 않다면, 마감 시간까지 온 답만으로 응답하고 늦은 샤드의 결과는 빼는 방법도 있어요. 결과가 약간 덜 완전해지는 대신 응답 시간이 안정돼요. 어떤 방법이든 출발점은 사용자 요청의 지연을 개별 백엔드의 지연 분포와 팬아웃 수로 나눠 보는 거예요.<br><sub>Requests such as search, feeds and recommendations query several backends at once and assemble every answer into one response, as when a search index is split into dozens of shards or a screen needs data from several services. The user request must then wait until the slowest backend answers. A backend server was built to answer 99% of requests in 2 ms and 1% in 50 ms, a fairly decent server with a p99 of 50 ms on its own. Each user request called it N times concurrently and waited for all of them, and the share of user requests exceeding 40 ms was measured. With N = 1 it was 0.9%; with N = 10, 9.9%; with 50, 43.3%; with 100, 68.0%. One slow call among N is enough to slow the user request, so the probability is 1 − 0.99^N, and the computed values of 9.6%, 39.5% and 63.4% were nearly identical. At N = 100 the median user request took 51.9 ms: the individual backend’s p99 had become the user request’s p50. Measurements at large N were slightly worse than computed because the burst of 100 concurrent requests slowed the backend a little too. This is why large systems manage tail latency, p99 and p999, rather than averages: a rare delay in one backend becomes a common one after fan-out. There are several remedies. Reducing an individual server’s tail means finding and removing the causes of occasional delays such as GC pauses, disk writes and background jobs. Structurally, fan-out can be reduced, or hedged requests can send a late request once more to another replica, as in the next item. Where a perfect result is not essential, as in search, the response can be built from the answers that arrived by a deadline, leaving out late shards, trading slightly less complete results for stable response times. Whatever the method, the starting point is breaking user request latency down into the individual backend’s latency distribution and the fan-out count.</sub> |
| **헤지 요청**<br><sub>Hedged requests</sub> | 6ms 안에 답이 없으면 같은 요청을 한 번 더 보내자 백엔드 10개를 부르는 요청의 p99가 51.7ms에서 11.9ms로 줄었고 추가 요청은 2%였어요. 서버가 붐비면 고정된 기준은 추가 요청을 24.6%로 키웠어요.<br><sub>Resending a request when no answer came within 6 ms cut the p99 of requests calling 10 backends from 51.7 to 11.9 ms for 2% extra requests. When the server got busy, the fixed threshold inflated extra requests to 24.6%.</sub> | 앞 항목에서 백엔드의 드문 지연이 팬아웃 때문에 흔한 지연이 되는 것을 봤어요. 헤지 요청은 이 꼬리를 적은 비용으로 잘라 내는 방법이에요. 요청을 보내고 정해진 시간 안에 답이 없으면 같은 요청을 한 번 더 보내고, 둘 중 먼저 온 답을 쓰고 늦은 쪽은 취소해요. 실제로는 다른 복제본 서버로 보내는 것이 보통이에요. 앞의 백엔드는 평소 2ms 남짓에 답하므로 기준을 6ms로 잡았어요. 6ms 안에 첫 답이 오지 않으면 두 번째 요청을 보내고, Promise.race로 먼저 끝난 쪽을 쓰고, 다른 쪽은 AbortController로 취소했어요. N이 1일 때 p99가 10.4ms에서 8.3ms로 줄었고 추가 요청은 1.0%였어요. N이 10일 때는 p99가 51.7ms에서 11.9ms로, 40ms를 넘는 사용자 요청이 9.9%에서 0%로 줄었고, 추가 요청은 2.0%였어요. 느린 1%의 호출만 다시 보내므로, 전체 부하를 2% 늘리는 대가로 꼬리를 거의 없앤 거예요. 첫 요청이 50ms짜리 느린 경우에 걸려도, 6ms 뒤에 보낸 두 번째 요청은 99% 확률로 2ms 만에 답하기 때문이에요. N이 50일 때는 느린 요청이 43.3%에서 1.0%로 줄었고 추가 요청은 4.6%였어요. 그런데 N이 100이면 사정이 달라졌어요. 사용자 요청마다 100개의 호출이 한꺼번에 쏟아지자 서버가 붐벼 평소 응답도 6ms를 넘기 시작했어요. 그러자 헤지가 불필요하게 자주 일어나 추가 요청이 24.6%로 불었고, 이 추가 요청이 다시 서버를 붐비게 했어요. p99는 55.3ms에서 41.7ms로 줄었지만 중간값은 9.7ms로 늘었어요. 고정된 기준이 부하를 키운 거예요. 그래서 실제로는 기준을 고정값 대신 최근에 잰 p95 같은 값으로 정해 서버 상태에 따라 움직이게 하고, 헤지 요청이 전체의 몇 %를 넘지 않도록 상한을 둬요. 첫 요청을 취소하는 것도 중요해요. 취소하지 않으면 두 요청이 끝까지 서버 자원을 써요. 그리고 헤지 요청은 같은 요청이 두 번 실행되므로 읽기나 멱등한 요청에만 써야 해요. 결제나 주문처럼 두 번 실행되면 안 되는 요청에 쓰면 중복 처리가 생겨요.<br><sub>The previous item showed a backend’s rare delays becoming common through fan-out. Hedged requests cut that tail at little cost: send a request, and if no answer arrives within a set time, send the same request once more, use whichever answer arrives first and cancel the other. In practice the second request usually goes to another replica. Since the earlier backend normally answers in a little over 2 ms, the threshold was set to 6 ms. If no answer came within 6 ms, a second request was sent, Promise.race took whichever finished first, and the other was cancelled with an AbortController. At N = 1 the p99 fell from 10.4 to 8.3 ms with 1.0% extra requests. At N = 10 the p99 fell from 51.7 to 11.9 ms and user requests over 40 ms went from 9.9% to 0%, with 2.0% extra requests. Only the slow 1% of calls are resent, so the tail nearly vanished at the price of 2% more load: even when the first request hits a 50 ms slow case, the second, sent 6 ms later, answers in 2 ms with 99% probability. At N = 50 slow requests dropped from 43.3% to 1.0% with 4.6% extra requests. At N = 100, though, things changed. With 100 calls pouring out per user request, the server became busy and normal replies began exceeding 6 ms, so hedges fired needlessly often, extra requests swelled to 24.6%, and those extra requests made the server busier still. p99 fell from 55.3 to 41.7 ms, but the median rose to 9.7 ms: the fixed threshold had amplified the load. In practice, thresholds are therefore tied to recently measured values such as the p95 so they move with server conditions, and a cap keeps hedges below a few percent of all requests. Cancelling the first request matters too, since otherwise both keep consuming server resources to the end. And because hedging runs the same request twice, it is only for reads or idempotent requests; using it for payments or orders that must not run twice creates duplicate processing.</sub> |
| **캐시 적중률**<br><sub>Cache hit rates</sub> | 키 백만 개에 대한 요청에서 1% 크기의 LRU 캐시는 쏠림이 큰 분포에서 58.6%, 덜한 분포에서 23.2%를 맞혔어요. 캐시를 10배로 키울 때마다 적중률은 13~26%p씩만 올랐어요.<br><sub>Over requests to a million keys, an LRU cache holding 1% of keys hit 58.6% under heavy skew and 23.2% under mild skew. Each tenfold increase in cache size raised the hit rate by only 13 to 26 points.</sub> | 캐시는 자주 쓰는 데이터를 빠른 곳에 두는 거예요. 얼마나 도움이 될지는 캐시의 크기보다 요청이 키에 어떻게 퍼져 있는지에 더 크게 달려 있어요. 대부분의 서비스에서 요청은 소수의 인기 있는 키에 몰리고, 이런 분포를 흔히 Zipf 분포로 표현해요. 순위가 k인 키가 받는 요청이 1/k^s에 비례하고, 지수 s가 클수록 더 몰려요. 키 백만 개에 대한 요청 200만 번을 s = 1.0과 s = 0.8로 만들고, 가장 오래 쓰지 않은 것을 버리는 LRU 캐시의 적중률을 쟀어요. 처음 4분의 1은 캐시를 채우는 데 쓰고 나머지로 적중률을 셌어요. s = 1.0에서는 키의 0.1%, 곧 1,000개만 담는 캐시가 40.3%를 맞혔어요. 1%인 1만 개는 58.6%, 10%인 10만 개는 77.9%였어요. s = 0.8에서는 같은 크기가 10.0%, 23.2%, 48.8%를 맞혔어요. 같은 1% 캐시라도 요청의 쏠림에 따라 적중률이 두 배 넘게 달라진 거예요. 캐시를 10배로 키울 때마다 적중률은 13에서 26%p씩만 올랐어요. 크기를 늘릴수록 새로 담기는 키는 점점 덜 인기 있는 것들이라, 같은 메모리를 더 써도 얻는 적중이 줄어들어요. 마지막 몇 %p를 위해 메모리를 몇 배로 쓰게 되는 거예요. 적중률은 DB 부하로 바로 이어져요. 58.6%를 맞히면 DB로 가는 요청은 41.4%로 줄고, 77.9%면 22.1%로 줄어요. 적중률이 80%에서 90%로 오르면 DB 부하는 절반이 돼요. 그래서 적중률 몇 %p의 차이가 DB 서버 대수를 바꾸기도 해요. 반대로 캐시가 장애로 비면 DB에 갑자기 몇 배의 요청이 몰리므로, 캐시를 비운 상태에서 DB가 견딜 수 있는지도 따져야 해요. 실무에서는 캐시 크기를 감으로 정하지 않아요. 실제 접근 로그를 캐시 시뮬레이터에 넣고 크기별 적중률 곡선을 그려, 곡선이 평평해지기 시작하는 지점을 골라요. 키마다 크기가 다르면 개수가 아니라 바이트 기준으로 따져야 하고, TTL로 만료되는 데이터라면 만료가 적중률을 깎는 효과도 함께 봐야 해요.<br><sub>A cache keeps frequently used data somewhere fast, and how much it helps depends more on how requests spread across keys than on its size. In most services requests pile onto a few popular keys, a distribution commonly modeled as Zipf: the key ranked k receives requests proportional to 1/k^s, and the larger the exponent s, the heavier the skew. Two million requests over a million keys were generated with s = 1.0 and s = 0.8, and the hit rate of an LRU cache, which evicts the least recently used entry, was measured, using the first quarter to fill the cache and counting hits over the rest. With s = 1.0, a cache holding 0.1% of keys, just 1,000, hit 40.3%; 1%, or 10,000 keys, hit 58.6%; and 10%, or 100,000, hit 77.9%. With s = 0.8 the same sizes hit 10.0%, 23.2% and 48.8%. The same 1% cache thus differed by more than double depending on skew. Each tenfold increase in size raised the hit rate by only 13 to 26 percentage points: as the cache grows, the newly stored keys are ever less popular, so more memory buys fewer hits, and the last few points cost several times the memory. Hit rates translate directly into database load: hitting 58.6% cuts requests reaching the database to 41.4%, and 77.9% cuts them to 22.1%, while raising the hit rate from 80% to 90% halves database load. A few points of hit rate can therefore change the number of database servers. Conversely, if the cache empties in an outage, the database suddenly receives several times its usual requests, so whether it survives an empty cache must be considered too. In practice cache sizes are not guessed: real access logs are fed into a cache simulator to plot hit rate against size, and the point where the curve starts to flatten is chosen. When keys vary in size, the analysis should be in bytes rather than counts, and for data expiring by TTL, the hit rate lost to expiry must be weighed as well.</sub> |

| **짧은 코드 만들기**<br><sub>Making short codes</sub> | 무작위 6자리 코드 100만 개는 몇 번씩 부딪쳤고 7자리는 한 번도 부딪치지 않았어요. md5를 16진수 7자리로 자르자 200만 개에서 7,434번 부딪쳤어요.<br><sub>A million random 6-character codes collided a few times, while 7 characters never collided. Three million link rows were created and two ways of deleting the 900,000 expired ones were compared. The first is DELETE FROM links WHERE created < cutoff. It took 706 ms and generated 192 MB of WAL, because PostgreSQL logs every deleted row, so deletion produces writes in proportion to what is deleted. With replicas, all 192 MB travels over the network and the replicas repeat the work, and replication lag can grow during the deletion. After deleting, the table was 379 MB, the same as before, and even after VACUUM it remained 379 MB. In PostgreSQL the space of deleted rows only becomes reusable by new rows once VACUUM cleans it; it is not returned to the operating system. Reclaiming disk space requires VACUUM FULL, which rewrites the entire table under an exclusive lock that stops the service meanwhile. The second way is to partition the table by creation date into quarters from the start. The same 3 million rows were loaded into a partitioned table, and the expired quarter was detached with DETACH PARTITION and removed with DROP TABLE. Detaching took 1.2 ms and dropping 56.5 ms, with 41 kB of WAL, because the partition’s files are removed whole instead of deleting rows one by one, and the space returns to the operating system immediately. Data deleted by time, such as logs, events, notifications and expiring links, is therefore best partitioned by that time from the beginning. The partition key must be part of the primary key, however, and lookups by code do not know the partition key and must search every partition. Where lookups by code dominate, another approach keeps the code table as is, indexes the expiry time and deletes in small batches; deleting tens of thousands of rows at a time keeps locks and WAL from arriving all at once and limits the impact on the service.</sub> |

## 읽기와 쓰기 중 어디에 비용을 둘까 · Whether to pay on reads or on writes

읽을 때 모으는 풀 방식, 쓸 때 나눠 주는 푸시 방식, 셀럽만 따로 다루는 혼합 방식의 읽기와 쓰기 비용, Redis 타임라인 캐시의 메모리, 같은 행에 몰리는 좋아요 카운터를 사용자 2만 명과 글 100만 개의 PostgreSQL과 Redis로 실측해요.  
*Read and write costs of the pull model that gathers on read, the push model that distributes on write and the hybrid model that treats celebrities separately, the memory of Redis timeline caches, and like counters that pile onto one row, measured with PostgreSQL holding 20,000 users and a million posts, plus Redis.*

There are two broad designs, and the difference is whether the cost falls on reads or on writes. For the experiment, PostgreSQL was given 20,000 users, 4.18 million follow relations and a million posts. Every user follows 10 celebrity accounts plus close to 200 others at random, averaging 209 follows per user, and each user has 50 posts with creation times spread over the last 30 days. The first design is the pull model. Writing a post merely inserts one row into posts, and reading the feed joins follows and posts to gather the posts of everyone followed, sorts them by creation time and takes the newest 20, with a composite index on author and creation time in posts. Reading 200 users’ feeds took a p50 of 53.5 ms and a p99 of 73.8 ms. The execution plan shows PostgreSQL gathering the posts of 209 authors with two parallel workers and a top-N sort keeping only the top 20. The result is only 20 rows, yet choosing them meant scanning 209 × 50, about 10,000 posts, and reading over 8,000 pages. Even with a per-author index, pulling a few recent posts per author and merging them scales with the number of people followed, so users who follow more people get proportionally slower feeds. The model’s strength is simplicity: writing costs one row regardless of follower count, unfollows and deleted posts are reflected in the very next read, and no separate timeline store is needed. The problem is that feeds are a classic read-heavy feature: users post a few times a day but refresh their feeds dozens of times. With all the cost on reads, database CPU goes mostly to assembling feeds as users grow, which leads to the push model of the next item, distributing posts in advance at write time to make reads cheap. For small services or ones where people follow few accounts, pull is often enough.</sub> |
| **푸시 방식**<br><sub>The push model</sub> | 글을 쓸 때 팔로워의 타임라인마다 한 줄씩 넣자 읽기가 0.44ms로 120배 빨라졌어요. 대신 셀럽의 글 하나는 2만 줄, 48.5ms가 됐고 사용자 200명의 타임라인이 214.7MB였어요.<br><sub>Inserting a row into every follower’s timeline at write time made reads 0.44 ms, 120 times faster. In exchange, one celebrity post became 20,000 rows and 48.5 ms, and 200 users’ timelines took 214.7 MB.</sub> | 푸시 방식은 글을 쓸 때 그 글을 팔로워 모두의 타임라인에 미리 넣어 둬요. 팬아웃 온 라이트라고도 해요. timelines 테이블에 소유자, 작성 시각, 글 id를 기본 키로 두고, 글이 생기면 follows에서 그 작성자의 팔로워를 모두 찾아 한 줄씩 넣어요. 피드를 읽을 때는 내 타임라인에서 최신 20줄을 인덱스로 읽기만 하면 돼요. 사용자 200명의 타임라인을 미리 채운 뒤 같은 피드를 읽자 p50 0.44ms, p99 1.73ms였어요. 풀 방식의 53.5ms보다 120배 빨라요. 조인도 정렬도 없이 인덱스의 한 범위를 읽는 것뿐이기 때문이에요. 비용은 쓰기로 옮겨 가요. 팔로워가 194명인 보통 사용자가 글을 쓰면 타임라인 194줄을 넣는 데 1.8ms가 걸렸어요. 팔로워가 19,990명인 셀럽이 글을 쓰면 2만 줄을 넣는 데 48.5ms가 걸렸어요. 이 실험의 셀럽은 2만 명이지만, 실제 서비스의 유명인은 팔로워가 수천만 명이라 글 하나가 수천만 번의 쓰기가 되고, 마지막 팔로워의 타임라인에 글이 보이기까지 몇 분이 걸릴 수도 있어요. 이것을 셀럽 문제, 또는 핫 유저 문제라고 해요. 저장 공간도 커져요. 사용자 200명의 타임라인을 채우자 209만 줄, 214.7MB였어요. 한 명에 약 1만 줄, 1MB예요. 같은 글이 팔로워 수만큼 복사되기 때문이에요. 모든 사용자에게 이렇게 하면 원래 글 데이터의 수백 배가 필요해요. 그래서 실제 푸시 방식에는 몇 가지 장치가 붙어요. 타임라인에는 최근 몇백 개만 남기고, 더 오래된 글은 필요할 때 풀 방식으로 채워요. 몇 주째 들어오지 않은 사용자의 타임라인은 아예 만들지 않고, 다시 들어오면 그때 만들어요. 팬아웃 쓰기는 글쓴이의 요청 안에서 하지 않고 메시지 대기열에 넣어 워커들이 비동기로 나눠 처리해요. 글쓴이는 바로 응답을 받고, 팔로워들의 타임라인은 몇 초 안에 채워져요. 팔로를 끊거나 글을 지웠을 때는 이미 복사된 줄들을 찾아 지워야 하므로, 삭제와 수정이 풀 방식보다 복잡해져요. 셀럽 문제는 다음 항목의 혼합 방식으로 풀어요.<br><sub>The push model places each post into all followers’ timelines in advance when it is written, also called fan-out on write. A timelines table keyed by owner, creation time and post id receives one row per follower, found in follows, whenever a post is created. Reading the feed then means just reading the newest 20 rows of one’s own timeline through the index. With 200 users’ timelines prefilled, the same feeds read at a p50 of 0.44 ms and a p99 of 1.73 ms, 120 times faster than pull’s 53.5 ms, because there is no join or sort, only a range read from an index. The cost moves to writes. When an ordinary user with 194 followers posted, inserting 194 timeline rows took 1.8 ms; when a celebrity with 19,990 followers posted, inserting 20,000 rows took 48.5 ms. The celebrity here has 20,000 followers, but real public figures have tens of millions, so one post becomes tens of millions of writes and may take minutes to reach the last follower’s timeline, the celebrity or hot-user problem. Storage grows too: filling 200 users’ timelines took 2.09 million rows and 214.7 MB, about 10,000 rows and 1 MB per user, since each post is copied once per follower, and doing this for every user would need hundreds of times the original post data. Practical push systems therefore add several devices. Timelines keep only the most recent few hundred entries, filling older ones by pull when needed. Users absent for weeks get no timeline at all until they return. Fan-out writes are not done inside the author’s request but placed on a message queue for workers to process asynchronously, so the author gets an immediate response and followers’ timelines fill within seconds. Unfollows and deleted posts require finding and removing already-copied rows, making deletions and edits more complex than with pull. The celebrity problem is solved by the hybrid model of the next item.</sub> |
| **혼합 방식**<br><sub>The hybrid model</sub> | 보통 사용자의 글은 푸시하고 셀럽 10명의 글만 읽을 때 모으자 읽기가 1.16ms, 셀럽의 글쓰기는 다시 한 줄이 됐어요. 결과는 풀 방식과 똑같은 20개였어요.<br><sub>Pushing ordinary users’ posts and gathering only 10 celebrities’ posts at read time made reads 1.16 ms and celebrity writes one row again. The hybrid model applies each according to the account: posts by ordinary users with few followers are pushed into followers’ timelines, while posts by celebrities with huge followings are not. Reading the feed takes the newest 20 entries from one’s own timeline, separately gathers the 20 newest posts of followed celebrities, merges the two and sorts again to pick 20. With timelines excluding the 10 celebrities filled for 200 users, a query combining both results with UNION ALL was run. It took a p50 of 1.16 ms and a p99 of 4.48 ms, 46 times faster than pull’s 53.5 ms, with p99 far steadier, down from 73.8 ms, because only 10 celebrities × 50 posts, 500 posts, are gathered directly. Comparing pull and hybrid results for the same user, the 20 posts matched exactly, order included. Celebrity writes returned to inserting one row into posts, removing the previous item’s 20,000-row fan-out and its 48.5 ms. Ordinary users’ posts are still pushed but finish in a few milliseconds with a few hundred followers. Celebrities are usually separated by follower count, with accounts above a threshold such as hundreds of thousands or millions no longer pushed but gathered at read time, and accounts crossing the threshold require their posts to be removed from or added back to timelines. The hybrid model has weaknesses too: a user following hundreds of celebrities makes read-time gathering large again. So celebrities’ recent post lists are often cached separately, and reads merely merge the cached lists; since many people read celebrities’ posts, the hit rate is high. Large social services are reported to use such hybrids. Feed design is ultimately deciding where to place cost by looking at the shape of the data, the distribution of follower counts. When most accounts have few followers and a tiny minority have enormous numbers, handling that minority in the tail separately is more efficient than applying one model to everyone.</sub> |

Telling upstream the pace the slow side can handle, so production slows, is called backpressure, and the same principle appears in many places. TCP matches the sender’s pace through the window, in which the receiver advertises its remaining buffer. In Node.js streams, write returns false once the write buffer exceeds highWaterMark and the producer waits for the drain event, something pipe handles automatically. In message queues, consumer lag, the number of piled-up messages, is the backpressure signal, and growing lag calls for more consumers or slower production. At entry points where production cannot be slowed, such as user requests, rejecting the overflow as in the previous item is backpressure’s final form. In short, every queue in a system needs a bound, and what happens when it fills, whether to wait, reject or drop the oldest, must be decided in advance. An unbounded queue hides problems until the outage.</sub> |

There are two prices. The first is that much latency, since rows are invisible in the database while buffered. The second is losing the batch if the application dies while collecting. | **분산 ID 생성**<br><sub>Distributed ID generation</sub> | DB 시퀀스는 왕복마다 id 하나라 초당 8,824개였고, 스노플레이크는 서버 혼자 초당 400만 개를 만들었어요. 시계를 5ms 되돌리자 확인 없는 구현은 중복 250개를 만들었어요.<br><sub>A DB sequence gives one id per round trip, 8,824 per second, while Snowflake generated 4 million per second locally.
