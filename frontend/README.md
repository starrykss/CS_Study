## 프론트엔드 구조와 설계 · Frontend architecture and design

컴포넌트를 나누는 기준, 디자인 시스템, 폴더 구조, 모노레포와 마이크로 프론트엔드, 아일랜드 아키텍처와 Web Components예요.  
*How to split components, design systems, folder structure, monorepos and micro frontends, islands architecture and Web Components.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **컴포넌트 설계**<br><sub>Component design</sub> | 컴포넌트는 하나의 역할을 맡게 나누고, 데이터는 props로 내려보내고 이벤트는 콜백으로 올려요. 상속보다 조합으로 유연하게 만들어요.<br><sub>Components should each take one role, with data flowing down as props and events flowing up through callbacks, and composition making them flexible instead of inheritance.</sub> | 데이터 요청, 상태, 화면, 이벤트가 600줄짜리 컴포넌트 하나에 몰리면 작은 수정에도 전체를 이해해야 하고 다른 곳에서 재사용할 수 없어요. 데이터와 상태를 다루는 위쪽 컴포넌트와 props만 받아 그리는 아래쪽 컴포넌트로 역할을 나누면 표시 컴포넌트는 Storybook과 테스트에서 혼자 다룰 수 있어요. 데이터는 props로 내려가고 사용자의 행동은 onBuy 같은 콜백으로 위에 알리는 단방향 흐름이라 버그를 추적하기 쉬워요. props가 수십 개로 늘어나면 Card.Header, Card.Body처럼 조각을 끼워 넣는 합성 컴포넌트나 children을 써서 API를 단순하게 해요. 여러 단계를 그대로 통과만 하는 props(prop drilling)는 컨텍스트나 조합으로 줄여요. 너무 잘게 쪼개면 오히려 파일을 오가는 비용이 커지니 “함께 바뀌는 것은 함께”를 기준으로 삼아요.<br><sub>When fetching, state, UI and events pile into one 600-line component, every small change needs the whole picture and nothing can be reused. Splitting roles between upper components that own data and state and lower components that only render props lets display components live alone in Storybook and tests. Data flows down as props and user actions report up through callbacks such as onBuy, a one-way flow that makes bugs easy to trace. When props multiply into dozens, compound components such as Card.Header and Card.Body or children keep the API simple. Props that merely pass through many levels (prop drilling) are reduced with context or composition. Splitting too finely adds file-hopping costs, so use “what changes together stays together” as the rule.</sub> |
| **디자인 시스템**<br><sub>Design systems</sub> | 색·간격·글자 같은 디자인 결정을 토큰으로 만들고, 그 위에 기본 컴포넌트와 패턴을 쌓은 공유 UI 언어예요. 일관성과 개발 속도를 함께 높여요.<br><sub>A design system turns design decisions such as color, spacing and type into tokens and builds primitives and patterns on top, a shared UI language that raises consistency and speed.</sub> | 가장 아래층의 디자인 토큰은 --color-primary, --space-4처럼 이름 붙은 값으로, 디자인 도구(Figma 변수)와 코드가 같은 이름을 공유해요. Button, Input 같은 기본 요소는 토큰만 쓰고 variant, size처럼 정해진 선택지만 열어 두어 아무 색이나 쓰지 못하게 해요. 폼, 카드, 내비게이션 같은 패턴은 기본 요소를 조합해 만들고, 페이지는 패턴을 배치하는 일에 집중해요. Storybook에서 컴포넌트를 상태별 스토리로 모아 보면 카탈로그, 사용 문서, 시각 회귀 테스트를 한곳에서 해결해요. 접근성(포커스, 대비, 레이블)을 기본 요소에 넣어 두면 그걸 쓰는 모든 화면이 자동으로 좋아져요. 디자이너와 개발자가 같은 이름으로 대화하게 되는 것이 가장 큰 효과예요.<br><sub>At the bottom, design tokens are named values such as --color-primary and --space-4, shared by design tools (Figma variables) and code. Primitives such as Button and Input use only tokens and expose fixed choices such as variant and size, so arbitrary colors cannot creep in. Patterns such as forms, cards and navigation compose primitives, and pages focus on arranging patterns. Storybook gathers components as per-state stories, providing a catalog, usage docs and visual regression tests in one place. Accessibility built into primitives, focus, contrast and labels, improves every screen that uses them. The biggest win is designers and developers speaking with the same names.</sub> |
| **폴더 구조**<br><sub>Folder structure</sub> | 파일을 종류(components, hooks)보다 기능(cart, auth) 단위로 모으고, app → features → shared 방향으로만 의존하게 해요.<br><sub>Group files by feature (cart, auth) rather than by type (components, hooks), and let dependencies flow only from app to features to shared.</sub> | components/, hooks/, utils/처럼 종류별로 나누면 처음엔 깔끔해 보이지만, 장바구니 기능 하나를 고치려면 네다섯 폴더를 오가야 해요. 기능별 구조는 features/cart 안에 그 기능의 UI, API 호출, 상태, 타입을 모아 함께 바뀌는 코드를 가까이 둬요(colocation). app(라우팅, 전역 설정) → features → shared(공용 UI, 유틸)처럼 의존 방향을 한쪽으로 고정하면 순환 의존이 생기지 않아요. 각 기능은 index.ts로 공개할 것만 내보내고 내부 파일은 숨겨서, 다른 곳이 내부 구현에 기대지 못하게 해요. 기능끼리 직접 import하는 것은 eslint-plugin-boundaries 같은 규칙으로 막아요. Feature-Sliced Design은 이런 규칙을 층(layer)과 조각(slice)으로 정리한 대표적인 방법론이에요.<br><sub>Grouping by type, as in components/, hooks/ and utils/, looks tidy at first, but fixing the cart means visiting four or five folders. Feature-based structure keeps a feature’s UI, API calls, state and types together in features/cart, colocating code that changes together. Fixing the direction app (routing, global setup) → features → shared (common UI, utilities) prevents circular dependencies. Each feature exports only its public surface through index.ts and hides internals, so nothing depends on implementation details. Direct imports between features are blocked with rules such as eslint-plugin-boundaries. Feature-Sliced Design is a well-known methodology that formalizes these rules into layers and slices.</sub> |
| **모노레포**<br><sub>Monorepos</sub> | 여러 앱과 공유 패키지를 한 저장소에서 관리해요. 워크스페이스로 패키지를 연결하고, Turborepo·Nx가 바뀐 것만 빌드하고 결과를 캐시해요.<br><sub>A monorepo keeps many apps and shared packages in one repository, linking packages through workspaces while Turborepo or Nx build only what changed and cache results.</sub> | apps/web, apps/admin과 packages/ui, packages/api-client를 한 저장소에 두면 라이브러리와 그것을 쓰는 앱을 한 번의 PR로 함께 바꿀 수 있어요. pnpm 워크스페이스는 "@acme/ui": "workspace:\*"로 로컬 패키지를 바로 연결해서 npm에 배포하지 않아도 수정이 즉시 반영돼요. Turborepo나 Nx는 패키지 의존 그래프를 알기 때문에 ui를 고치면 그것에 영향받는 앱만 다시 빌드하고 테스트해요. 작업 입력의 해시로 결과를 캐시하고 원격 캐시로 팀과 CI가 공유하면, 누군가 이미 빌드한 것은 다시 하지 않아 CI 시간이 크게 줄어요. 공통 ESLint, TypeScript 설정도 packages/config로 나눠 일관성을 지켜요. 대신 저장소가 커지면서 권한 관리, CI 설계, 도구 학습 같은 운영 부담도 함께 늘어요.<br><sub>Keeping apps/web, apps/admin, packages/ui and packages/api-client together lets one PR change a library and every app using it. pnpm workspaces link local packages through "@acme/ui": "workspace:\*", so edits apply instantly without publishing to npm. Turborepo or Nx know the package dependency graph, so editing ui rebuilds and retests only the apps it affects. Caching results by a hash of task inputs and sharing them through a remote cache means nothing already built by a teammate or CI is built again, cutting CI time sharply. Shared ESLint and TypeScript settings live in packages/config for consistency. In return, a growing repository brings operational overhead in access control, CI design and tooling knowledge.</sub> |
| **마이크로 프론트엔드**<br><sub>Micro frontends</sub> | 큰 프론트엔드를 팀별 앱으로 나눠 독립적으로 개발·배포하고, shell 앱이 런타임에 조합해요. 기술보다 조직 규모의 문제를 푸는 아키텍처예요.<br><sub>Micro frontends split a large frontend into per-team apps that develop and deploy independently and are composed at run time by a shell app, an architecture for organizational scale rather than technology.</sub> | shell(호스트) 앱이 헤더와 라우팅을 맡고, 상품 팀과 장바구니 팀이 만든 앱 조각을 런타임에 불러와 한 화면에 합쳐요. Module Federation(webpack, Rspack, Vite 플러그인)의 exposes로 각 팀이 조각을 공개하면 다른 팀 배포와 상관없이 자기 일정대로 배포할 수 있어요. React 같은 공통 라이브러리는 shared의 singleton으로 한 번만 불러와 중복 다운로드와 버전 충돌을 막아요. 대신 빌드·배포 구성이 복잡해지고, 팀마다 디자인과 의존성 버전이 어긋나지 않게 맞추는 비용, 런타임 오류 추적의 어려움이 생겨요. iframe, Web Components, 서버에서 HTML 조각을 합치는 방식도 같은 목표의 다른 구현이에요. 수십 명 이상이 한 프론트엔드를 다루는 큰 조직에서만 이득이고, 작은 팀은 모노레포와 모듈 경계로 충분해요.<br><sub>A shell (host) app owns the header and routing and loads pieces built by, say, the products team and the cart team into one screen at run time. With Module Federation (webpack, Rspack or Vite plugins), each team exposes its piece and deploys on its own schedule regardless of other teams. Common libraries such as React load once as singletons in shared, avoiding duplicate downloads and version clashes. The costs are complex build and deploy setups, effort to keep design and dependency versions aligned across teams, and harder runtime error tracing. Iframes, Web Components and server-side HTML composition are other implementations of the same goal. It pays off only for large organizations with dozens of people on one frontend; small teams do fine with a monorepo and module boundaries.</sub> |
| **아일랜드 아키텍처**<br><sub>Islands architecture</sub> | 페이지는 서버에서 정적 HTML로 만들고, 상호작용이 필요한 부분(섬)만 골라 JavaScript를 붙여요. 보내는 JS가 크게 줄어요.<br><sub>Islands architecture renders the page as static HTML on the server and attaches JavaScript only to interactive parts (islands), shrinking the JS shipped.</sub> | 전통적인 SSR 앱은 HTML을 보낸 뒤 페이지 전체를 하이드레이션해서, 정적인 본문과 푸터에도 컴포넌트 코드가 함께 내려가요. 아일랜드 아키텍처(Astro 등)는 기본적으로 JS를 0KB 보내고, 검색창이나 댓글처럼 상호작용이 필요한 컴포넌트에만 client:load, client:visible, client:idle 같은 지시어로 JS를 붙여요. client:visible은 화면에 보일 때까지 활성화를 미뤄 첫 로딩을 더 가볍게 해요. 섬들은 서로 독립적으로 하이드레이션되므로 한 섬의 무거운 코드가 다른 부분을 막지 않아요. 블로그, 문서, 마케팅, 상품 상세처럼 콘텐츠 중심 사이트에 특히 잘 맞고, 화면 전체가 상호작용인 대시보드에는 이점이 적어요. React 서버 컴포넌트의 “필요한 곳만 클라이언트”, Qwik의 재개(resumability)도 같은 문제를 다른 방식으로 풀어요.<br><sub>Traditional SSR apps send HTML and then hydrate the whole page, shipping component code even for static articles and footers. Islands architecture, as in Astro, ships 0 KB of JS by default and adds it only to interactive components such as search or comments through directives such as client:load, client:visible and client:idle. client:visible delays activation until the island scrolls into view, lightening the first load. Islands hydrate independently, so one heavy island never blocks the rest. It suits content-heavy sites such as blogs, docs, marketing and product pages, and helps less for dashboards that are interactive throughout. React Server Components’ “client only where needed” and Qwik’s resumability tackle the same problem differently.</sub> |
| **Web Components**<br><sub>Web Components</sub> | Custom Elements, Shadow DOM, slot으로 만드는 브라우저 표준 컴포넌트예요. 프레임워크와 상관없이 어디서나 같은 태그로 써요.<br><sub>Web Components are browser-standard components built from Custom Elements, Shadow DOM and slots, used as the same tag in any framework or none.</sub> | class UserCard extends HTMLElement를 customElements.define('user-card', UserCard)로 등록하면 <user-card>를 일반 HTML 태그처럼 써요. connectedCallback, attributeChangedCallback 같은 수명 주기 메서드로 요소가 붙거나 속성이 바뀔 때 반응해요. attachShadow로 만든 Shadow DOM은 안쪽 스타일이 밖으로 새지 않고 바깥 CSS도 들어오지 않아 진짜 캡슐화를 줘요(CSS 변수와 ::part로 의도된 부분만 열어요). slot은 바깥에서 넣은 내용을 컴포넌트 안의 정해진 자리에 보여줘요. 표준 기술이라 React, Vue, 순수 HTML 어디서든 같은 컴포넌트를 쓸 수 있어 여러 프레임워크를 쓰는 조직의 디자인 시스템 공유에 좋아요. Lit 같은 작은 라이브러리가 작성을 편하게 해 주고, 서버 렌더링(Declarative Shadow DOM)과 폼 연동(ElementInternals)은 추가로 챙겨야 해요.<br><sub>Registering class UserCard extends HTMLElement with customElements.define('user-card', UserCard) makes <user-card> usable like any HTML tag. Lifecycle methods such as connectedCallback and attributeChangedCallback react when the element attaches or attributes change. A Shadow DOM from attachShadow keeps inner styles from leaking out and outer CSS from leaking in, giving true encapsulation, with CSS variables and ::part opening only intended parts. Slots show content supplied from outside in set places inside the component. As a standard, the same component works in React, Vue or plain HTML, ideal for sharing a design system across frameworks. Small libraries such as Lit ease authoring, while server rendering (Declarative Shadow DOM) and form integration (ElementInternals) need extra care.</sub> |

| **서버 상태 관리**<br><sub>Server state management</sub> | 서버에서 온 데이터는 키 기반 캐시로 다뤄요. | **API 계층**<br><sub>The API layer</sub> | 주소·인증 헤더·오류 처리·토큰 갱신 같은 네트워크 세부사항을 api 모듈 하나에 모으고, 컴포넌트는 이름 있는 함수만 불러요.<br><sub>The API layer gathers network details, base URL, auth headers, error handling and token refresh, into one module, and components call only named functions.</sub> | 컴포넌트마다 fetch를 직접 부르면 기본 주소, 인증 헤더, 오류 처리 방식이 화면마다 달라지고 바꿀 때 전부 찾아 고쳐야 해요. http() 같은 래퍼 하나가 기본 주소와 헤더를 붙이고, 401이 오면 토큰을 갱신한 뒤 원래 요청을 다시 보내요. fetch는 404나 500에서 예외를 던지지 않으니 res.ok를 확인해 상태 코드와 메시지를 담은 ApiError로 바꿔 던지면, 화면은 한 가지 모양의 오류만 다루면 돼요. 컴포넌트와 서버 상태 라이브러리는 api.todos(page)처럼 이름 있는 함수만 부르므로 엔드포인트가 바뀌어도 한 곳만 고쳐요. | **가상 스크롤**<br><sub>Virtual scrolling</sub> | 긴 목록에서 지금 보이는 행과 약간의 여유분만 DOM에 렌더해요. 10,000행도 노드 수십 개로 부드럽게 스크롤해요.<br><sub>Virtual scrolling renders only the visible rows of a long list plus a little overscan, so even 10,000 rows scroll smoothly with a few dozen nodes.</sub> | 행 10,000개를 모두 그리면 DOM 노드가 수만 개가 되어 스타일 계산과 레이아웃이 느려지고 메모리도 많이 써요. 가상 스크롤(윈도잉)은 스크롤 위치와 행 높이로 지금 보일 범위를 계산해 그 행과 위아래 overscan 몇 개만 렌더해요. 스크롤하면 같은 노드들을 transform: translateY로 새 위치에 옮기며 내용만 바꿔 재사용해요. 전체 높이는 계산해서 컨테이너에 주기 때문에 스크롤바 길이와 위치는 진짜 목록처럼 보여요. 행 높이가 제각각이면 estimateSize로 추정한 뒤 실제로 렌더하며 측정해 보정해요. | **무한 스크롤**<br><sub>Infinite scroll</sub> | 목록 끝의 감시 요소를 IntersectionObserver로 지켜보다가 보이면 다음 페이지를 불러 이어 붙여요. 페이지는 커서 기반으로 요청해요.<br><sub>Infinite scroll watches a sentinel at the end of the list with IntersectionObserver and appends the next page when it appears, requesting pages by cursor.</sub> | 목록 맨 끝에 빈 센티널 요소를 두고 IntersectionObserver로 화면에 들어오는지 관찰하면, scroll 이벤트를 계속 계산하는 것보다 훨씬 가벼워요. rootMargin: '400px'을 주면 끝에 닿기 전에 미리 다음 페이지를 불러 사용자가 빈 화면을 보지 않아요. 서버는 items와 함께 nextCursor를 돌려주고, 다음 요청은 “이 항목 다음부터”라는 커서로 보내요. offset=20 방식은 그 사이 새 글이 추가되거나 삭제되면 항목이 밀려 같은 글이 두 번 나오거나 빠지는 문제가 있어요. | **스크립트 로딩 방식**<br><sub>Script loading</sub> | 일반 script는 HTML 해석을 멈춰요. async는 받는 즉시, defer는 해석 뒤 순서대로 실행하고, module은 기본이 defer예요.<br><sub>Plain scripts halt HTML parsing; async runs on arrival, defer runs in order after parsing, and modules defer by default.</sub> | 속성 없는 <script src>는 내려받고 실행이 끝날 때까지 HTML 해석을 멈춰서, head에 있으면 첫 화면이 그만큼 늦어져요. async는 해석과 동시에 내려받고 도착하는 즉시 실행해요 · 실행 순서가 보장되지 않아 광고, 분석처럼 다른 코드와 독립된 스크립트에 맞아요. defer는 동시에 받아 두고 HTML 해석이 끝난 뒤 DOMContentLoaded 직전에 적힌 순서대로 실행해서, 앱 코드의 기본 선택이에요. type="module"은 기본으로 defer처럼 동작하고, import로 이어진 의존 모듈은 받아 봐야 알 수 있어 연쇄 대기가 생기니 modulepreload로 미리 알려요. 렌더를 막는 큰 CSS도 같은 문제를 일으켜서, 첫 화면에 필요한 CSS만 먼저 보내는 것이 좋아요. 서드파티 스크립트는 성능을 가장 크게 해치는 경우가 많으니 꼭 필요한지부터 따져요.<br><sub>A plain <script src> stops HTML parsing until it downloads and runs, so placing it in head delays the first screen by that much. async downloads in parallel and runs as soon as it arrives, with no order guarantee, suiting independent scripts such as ads and analytics. defer downloads in parallel and runs in document order after parsing, just before DOMContentLoaded, the default choice for app code. type="module" behaves like defer by default, and because imported dependencies are discovered only after download, modulepreload announces them early to avoid waterfalls. | **웹 글꼴 최적화**<br><sub>Web font optimization</sub> | font-display: swap으로 글자가 숨지 않게 하고, 서브셋·woff2로 크기를 줄이고, preload로 일찍 받아요. 대체 글꼴 크기를 맞춰 밀림도 줄여요.<br><sub>font-display: swap keeps text visible, subsetting and woff2 shrink files, preload fetches early, and fallback metric matching reduces shifts.</sub> | 웹 글꼴이 늦게 오면 브라우저가 한동안 글자를 숨기는 FOIT가 생겨 첫 화면이 비어 보여요. font-display: swap은 대체 글꼴로 먼저 보여주고 도착하면 바꾸는데, 두 글꼴의 폭이 다르면 줄바꿈이 바뀌며 화면이 밀려서 size-adjust, ascent-override로 대체 글꼴의 크기를 맞춰요. 한글은 완성형 글자가 11,172자라 글꼴 파일이 크기 때문에, 자주 쓰는 글자로 서브셋을 만들고 unicode-range로 나눠 필요한 조각만 받게 해요. 압축률이 좋은 woff2를 쓰고 실제로 쓰는 굵기만 포함하며, 여러 굵기가 필요하면 가변 글꼴 하나로 대신해요. <link rel="preload" as="font" crossorigin>는 CSS 해석을 기다리지 않고 글꼴을 바로 요청하게 해요. 다운로드가 전혀 없는 시스템 글꼴 스택도 좋은 선택이에요.<br><sub>A late web font can trigger FOIT, where browsers hide text for a while and the first screen looks empty. font-display: swap shows a fallback first and switches on arrival, but differing widths reflow lines and shift the page, so size-adjust and ascent-override align the fallback’s metrics. | **트리 셰이킹**<br><sub>Tree shaking</sub> | 번들러가 ESM의 import·export를 정적으로 분석해 쓰이지 않는 코드를 결과물에서 빼요. | **긴 작업 쪼개기**<br><sub>Breaking up long tasks</sub> | 50ms를 넘는 긴 작업은 클릭과 입력을 막아 INP를 나쁘게 해요. 작업을 조각내고 사이사이 메인 스레드를 양보하거나 Web Worker로 옮겨요.<br><sub>Tasks over 50ms block clicks and input and worsen INP, so split work into chunks that yield the main thread, or move it to a Web Worker.</sub> | 브라우저의 JavaScript, 스타일 계산, 레이아웃, 이벤트 처리는 모두 메인 스레드 하나에서 돌아서, 300ms짜리 작업이 실행 중이면 그 사이의 클릭은 끝날 때까지 기다려요. 이런 지연이 INP(Interaction to Next Paint) 점수를 나쁘게 해요. 큰 반복 작업을 작은 조각으로 나누고 조각 사이마다 await로 메인 스레드를 양보하면, 브라우저가 그 틈에 쌓인 입력과 화면 갱신을 먼저 처리해요. scheduler.yield()는 양보한 뒤 다시 자기 차례를 앞쪽에 받는 API로 Chrome과 Firefox가 지원하고, 없는 브라우저에서는 setTimeout(0)으로 대신해요. 이미지 처리나 큰 데이터 파싱처럼 정말 무거운 계산은 Web Worker로 옮겨 메인 스레드를 비워요. | **콘텐츠 해시 캐싱**<br><sub>Content-hash caching</sub> | 파일 이름에 내용의 해시를 넣으면 해시 파일은 1년 동안 캐시하고, HTML만 매번 확인해 새 이름을 받아요. 긴 캐시와 즉시 갱신을 함께 얻어요.<br><sub>Putting a content hash in file names lets hashed files be cached for a year while only HTML is rechecked for new names, achieving long caching and instant updates together.</sub> | 빌드 도구는 app.3f9a1c.js처럼 파일 내용으로 만든 해시를 이름에 넣어서, 내용이 같으면 이름도 같고 한 글자라도 바뀌면 이름이 바뀌어요. 이름이 곧 내용의 지문이므로 해시 파일은 Cache-Control: max-age=31536000, immutable로 영원히 캐시해도 오래된 파일을 받을 일이 없어요. 대신 index.html은 no-cache로 매번 서버에 확인해서, 배포 후 바뀐 파일 이름 목록을 바로 받아요. 자주 바뀌는 앱 코드와 거의 안 바뀌는 라이브러리(vendor)를 다른 파일로 나누면 배포해도 vendor는 캐시를 그대로 써서 재방문이 빨라요. 배포 중 캐시된 옛 HTML이 지운 파일을 요청할 수 있으니 이전 버전 파일은 잠시 남겨 둬요. 이 방식 덕분에 CDN 캐시를 수동으로 비우는 일이 거의 필요 없어져요.<br><sub>Build tools embed a hash of the file’s content in its name, as in app.3f9a1c.js, so identical content keeps the same name and any change produces a new one. | **예측 로딩**<br><sub>Predictive loading</sub> | 사용자가 누르기 전에 다음 화면의 코드와 데이터를 미리 받아 두거나(prefetch), 페이지를 통째로 미리 렌더(prerender)해 전환을 즉시로 만들어요.<br><sub>Predictive loading fetches the next screen’s code and data before the click (prefetch) or renders the whole page ahead (prerender), making navigation instant.</sub> | 보통은 링크를 누른 뒤에야 다음 화면의 코드와 데이터를 받기 시작해 그만큼 기다려요. 마우스를 올리는 순간 queryClient.prefetchQuery로 데이터를 받아 두면 올리고 누르기까지의 수백 ms를 벌어, 누를 때 이미 캐시에 있어요. Playwright E2E tests drive a real browser through money-critical journeys such as sign-up and checkout, but they are slower and flakier, so keep only the essential ones. A “testing trophy” with component tests as the most efficient center is commonly recommended. Running Storybook stories as visual regression tests catches style breakage too.</sub> |
| **API 모킹 (MSW)**<br><sub>API mocking (MSW)</sub> | MSW는 네트워크 단계에서 요청을 가로채 가짜 응답을 줘요. 같은 핸들러를 개발, 테스트, Storybook에서 함께 써요.<br><sub>MSW intercepts requests at the network level and returns fake responses, sharing the same handlers across development, tests and Storybook.</sub> | Mock Service Worker는 fetch 함수를 바꾸지 않고 브라우저에서는 서비스 워커로, Node에서는 요청 가로채기로 동작해서 앱 코드는 진짜 API를 부르는 그대로예요. http.get('/api/todos', () => HttpResponse.json([...]))처럼 핸들러를 정의하면 그 경로의 응답이 바뀌어요. 500 오류, 빈 목록, 3초 지연처럼 실제 서버로는 만들기 어려운 상황을 핸들러 하나로 재현해 오류 화면과 로딩 화면을 확실히 개발해요. 백엔드 API가 준비되기 전에도 약속한 모양대로 화면을 먼저 만들 수 있어 병렬 개발이 가능해요. setupWorker(브라우저)와 setupServer(Node)가 같은 핸들러를 쓰니 Vitest, Storybook, Playwright가 한 가지 가짜 API를 공유해요. 가짜가 실제 API와 어긋나지 않도록 OpenAPI 명세에서 핸들러를 생성하거나 계약 테스트를 곁들여요.<br><sub>Mock Service Worker leaves fetch untouched, running as a service worker in the browser and as request interception in Node, so app code calls the real API as usual. Defining a handler such as http.get('/api/todos', () => HttpResponse.json([...])) changes the response for that path. Situations hard to produce with a real server, such as 500 errors, empty lists or three-second delays, take one handler, making error and loading screens easy to build. UI work can proceed against the agreed shape before the backend API exists, enabling parallel development. setupWorker (browser) and setupServer (Node) use the same handlers, so Vitest, Storybook and Playwright share one fake API. To keep mocks from drifting, generate handlers from the OpenAPI spec or add contract tests.</sub> |
| **프론트엔드 모니터링**<br><sub>Frontend monitoring</sub> | 사용자 브라우저의 오류를 수집하고, 소스맵으로 원본 코드 위치를 찾고, 실사용자 성능 지표(RUM)로 진짜 체감 성능을 봐요.<br><sub>Frontend monitoring collects errors from users’ browsers, maps them back to source with source maps, and tracks real-user performance metrics (RUM).</sub> | 로컬에서 재현되지 않는 오류는 대부분 사용자 브라우저에서만 일어나요. Sentry 같은 도구는 오류를 스택, 브라우저·OS 정보, 직전 클릭과 요청 같은 기록(breadcrumbs)과 함께 모으고 같은 원인끼리 묶어 보여줘요. 배포된 코드는 압축돼 a.js:1:48213처럼 위치를 알 수 없으니, 빌드 때 소스맵을 모니터링 서비스에만 올려(공개 서버에는 올리지 않고) 원본 파일과 줄로 되돌려요. web-vitals 라이브러리로 실제 사용자의 LCP, INP, CLS를 모아 75번째 백분위수(p75)로 보면 실험실 측정과 다른 진짜 체감 성능이 보여요. 모든 이벤트를 보내면 비용이 커지니 샘플링 비율을 정하고, 세션 재생은 입력값과 개인정보를 가려요. 배포 버전(release)을 붙여 두면 어떤 배포 이후 오류가 늘었는지 바로 찾을 수 있어요.<br><sub>Errors that never reproduce locally mostly happen only in users’ browsers. Tools such as Sentry collect errors with stacks, browser and OS details and breadcrumbs of recent clicks and requests, grouping those with the same cause. Deployed code is minified, so locations such as a.js:1:48213 mean nothing until source maps, uploaded only to the monitoring service and never to the public server, map them back to original files and lines. Collecting real users’ LCP, INP and CLS with the web-vitals library and reading the 75th percentile (p75) reveals actual experience, unlike lab tests. Sending everything gets costly, so set sample rates, and session replays mask inputs and personal data. Tagging releases shows immediately which deploy increased errors.</sub> |

| **로딩 상태 설계**<br><sub>Designing loading states</sub> | 기다림의 길이에 따라 표시를 달리해요. 아주 짧으면 아무것도, 조금 길면 실제 모양의 스켈레톤, 몇 초 이상이면 진행률과 취소를 보여줘요.<br><sub>Vary loading feedback by wait time: nothing for very short waits, a content-shaped skeleton for longer ones, and progress with cancel for several seconds.</sub> | 응답이 300ms 안에 오면 스피너를 띄웠다 지우는 것 자체가 깜빡임이 되니, 짧은 지연 뒤에만 로딩 표시를 보여줘요. 기다림이 길어지면 실제 콘텐츠와 같은 모양과 크기의 스켈레톤을 보여줘서 무엇이 올지 예고하고, 자리가 그대로라 데이터가 와도 레이아웃이 밀리지 않아요. React의 Suspense 경계를 어디에 두느냐에 따라 화면 조각이 나타나는 순서와 단위가 정해져요. 업로드나 내보내기처럼 몇 초 이상 걸리는 작업은 진행률과 취소 버튼을 줘서 사용자가 통제감을 갖게 해요. 이미 본 데이터를 다시 받을 때는 화면을 비우지 말고 옛 데이터를 그대로 둔 채 상단의 얇은 진행 막대 정도만 보여줘요. 로딩 중인 영역에는 aria-busy를 달아 보조 기술에도 상태를 알려요.<br><sub>When responses arrive within 300ms, flashing a spinner on and off is just flicker, so show loading feedback only after a short delay. For longer waits, a skeleton matching the content’s shape and size previews what is coming and holds its place, so nothing shifts when data arrives. Where React Suspense boundaries sit decides the order and granularity in which parts of the screen appear. Tasks taking several seconds, such as uploads or exports, get progress and a cancel button so users stay in control. When refetching data already seen, keep the old data on screen and show only a thin progress bar at the top. Mark loading regions with aria-busy so assistive technology knows too.</sub> |
| **포커스 관리**<br><sub>Focus management</sub> | 모달을 열면 포커스를 안으로 옮겨 가두고, 닫으면 원래 버튼으로 돌려줘요. 묶인 컨트롤은 roving tabindex로, 화면 전환 뒤엔 새 제목으로 포커스를 옮겨요.<br><sub>Move focus into modals and trap it there, return it to the opener on close, use roving tabindex for grouped controls, and focus the new heading after navigation.</sub> | 키보드와 스크린 리더 사용자에게 포커스는 “지금 내가 있는 곳”이에요. <dialog>의 showModal()은 열 때 포커스를 안으로 옮기고 Tab이 모달 안에서만 돌게 하며 배경을 비활성으로 만들어 줘요. 닫을 때는 열기 전에 저장해 둔 document.activeElement로 포커스를 돌려줘서 사용자가 길을 잃지 않게 해요. 툴바, 탭 목록, 라디오 그룹처럼 묶인 컨트롤은 그룹 전체가 Tab 한 번이고 안에서는 화살표 키로 움직이는 roving tabindex 패턴을 써요. SPA는 페이지를 새로 받지 않아 화면이 바뀐 걸 보조 기술이 모를 수 있으니, 라우트가 바뀌면 새 화면의 h1로 포커스를 옮기거나 라이브 영역으로 안내해요. :focus-visible로 키보드 포커스를 분명히 보여주고, 포커스 표시를 없애기만 하는 스타일은 피해요.<br><sub>For keyboard and screen reader users, focus means “where I am now.” <dialog> showModal() moves focus inside on open, keeps Tab cycling within the modal and makes the background inert. On close, focus returns to the document.activeElement saved before opening, so users never get lost. Grouped controls such as toolbars, tab lists and radio groups use the roving tabindex pattern: one Tab stop for the group, arrow keys inside. SPAs never load a new page, so assistive technology may miss screen changes; after route changes, move focus to the new screen’s h1 or announce it through a live region. Make keyboard focus obvious with :focus-visible, and avoid styles that simply remove focus indicators.</sub> |
| **국제화**<br><sub>Internationalization</sub> | 문구 번역뿐 아니라 숫자·통화·날짜·복수형 형식과 글자 방향(RTL)까지 언어에 맞게 처리해요. Intl API와 ICU 메시지가 핵심 도구예요.<br><sub>Internationalization covers not only translation but number, currency, date and plural formats and text direction (RTL), with the Intl API and ICU messages as core tools.</sub> | Intl.NumberFormat은 같은 12000을 ko-KR에서는 ₩12,000으로, de-DE에서는 12.000 ₩으로 바꾸듯 천 단위 구분, 소수점, 통화 기호 위치를 언어에 맞게 처리해요. 날짜도 Intl.DateTimeFormat에 맡겨야 “2026. 11. 10.”과 “Nov 10, 2026”처럼 순서와 구분자가 맞아요. 영어는 1 item, 3 items로 바뀌지만 언어마다 복수형 규칙이 달라서, ICU 메시지 형식 {n, plural, one {...} other {...}}로 번역 문장 안에 규칙을 담아요. 번역 조각을 문자열로 이어 붙이면 어순이 다른 언어에서 깨지므로 변수 자리를 가진 완성된 문장을 번역해요. 아랍어·히브리어처럼 오른쪽에서 쓰는 언어는 dir="rtl"로 레이아웃이 거울처럼 뒤집히니 margin-left 대신 margin-inline-start 같은 논리 속성을 써요. 독일어처럼 영어보다 30% 이상 길어지는 언어를 위해 레이아웃에 여유를 둬요.<br><sub>Intl.NumberFormat renders the same 12000 as ₩12,000 in ko-KR and 12.000 ₩ in de-DE, handling separators, decimals and currency symbol placement per locale. Dates also go through Intl.DateTimeFormat so order and separators come out right, as in “2026. 11. 10.” versus “Nov 10, 2026.” English shifts from 1 item to 3 items, but plural rules differ by language, so ICU message syntax {n, plural, one {...} other {...}} embeds the rules in translations. Concatenating translated fragments breaks in languages with different word order, so translate whole sentences with placeholders. Right-to-left languages such as Arabic and Hebrew mirror layouts with dir="rtl", so use logical properties such as margin-inline-start instead of margin-left. Leave room in layouts for languages such as German that can run over 30% longer than English.</sub> |
| **애니메이션 성능**<br><sub>Animation performance</sub> | width·top처럼 레이아웃을 바꾸는 속성 대신 transform·opacity로 움직이면 합성 단계만 다시 해서 부드러워요. 레이아웃 변화는 FLIP으로 바꿔요.<br><sub>Animating transform and opacity instead of layout properties such as width or top only recomposites and stays smooth, while FLIP turns layout changes into transform animations.</sub> | 브라우저는 스타일 → 레이아웃 → 페인트 → 합성 순으로 화면을 그리는데, width나 top을 애니메이션하면 매 프레임 이 과정을 처음부터 다시 해서 끊기기 쉬워요. transform과 opacity는 합성 단계만 다시 하고 GPU가 처리해서 메인 스레드가 바빠도 부드럽게 움직여요. 60fps를 내려면 한 프레임을 16.7ms 안에 끝내야 하고, 120Hz 화면이면 그 절반이에요. will-change: transform은 곧 움직일 요소에 미리 레이어를 만들어 주지만, 남용하면 메모리를 많이 써서 꼭 필요한 요소에만 잠깐 써요. FLIP 기법은 처음(First)과 끝(Last) 위치를 재고, 그 차이만큼 transform으로 되돌린(Invert) 뒤 0으로 재생(Play)해서 목록 재정렬 같은 레이아웃 변화를 transform 애니메이션으로 바꿔요. prefers-reduced-motion을 켠 사용자에게는 움직임을 줄이거나 없애요.<br><sub>Browsers paint in the order style, layout, paint and composite, and animating width or top reruns the whole sequence every frame, easily stuttering. transform and opacity only recomposite on the GPU, staying smooth even when the main thread is busy. 60 fps requires finishing each frame within 16.7 ms, and half that on 120 Hz screens. will-change: transform pre-creates a layer for an element about to move, but overuse consumes lots of memory, so apply it briefly and only where needed. The FLIP technique measures First and Last positions, Inverts the difference with transform and Plays it back to zero, turning layout changes such as list reordering into transform animations. Users with prefers-reduced-motion get reduced or no motion.</sub> |
| **View Transitions**<br><sub>View Transitions</sub> | startViewTransition으로 DOM 변경을 감싸면 브라우저가 전후 스냅숏을 찍어 전환 애니메이션을 만들어요. 같은 이름의 요소는 위치와 크기가 자연스럽게 이어져요.<br><sub>Wrapping a DOM change in startViewTransition makes the browser snapshot before and after and animate between them, and elements sharing a name morph smoothly.</sub> | document.startViewTransition(() => updateDOM())을 쓰면 브라우저가 변경 전 화면을 스냅숏으로 찍고, 변경 후 화면과 기본 크로스페이드로 이어 줘요. 목록의 썸네일과 상세 화면의 큰 이미지에 같은 view-transition-name을 주면 그 요소는 위치와 크기가 자연스럽게 변하는 공유 요소 전환이 돼요. ::view-transition-old와 ::view-transition-new 의사 요소에 CSS 애니메이션을 주면 속도와 효과를 마음대로 바꿔요. 같은 문서 안의 전환은 주요 브라우저가 모두 지원하고, @view-transition { navigation: auto; }는 페이지를 새로 불러오는 MPA 사이 이동에도 전환을 걸어요. 지원하지 않는 브라우저에서는 그냥 즉시 바뀌므로 점진적 향상으로 안전하게 도입할 수 있어요. prefers-reduced-motion을 켠 사용자에게는 애니메이션을 줄여요.<br><sub>Calling document.startViewTransition(() => updateDOM()) has the browser snapshot the old view and connect it to the new one with a default crossfade. Giving a list thumbnail and a detail hero image the same view-transition-name creates a shared-element transition where position and size change smoothly. CSS animations on the ::view-transition-old and ::view-transition-new pseudo-elements change timing and effects freely. Same-document transitions work in all major browsers, and @view-transition { navigation: auto; } applies transitions between full page loads in MPAs. Unsupported browsers simply switch instantly, so it is a safe progressive enhancement. Users with prefers-reduced-motion get reduced animation.</sub> |
| **프론트엔드 인증 처리**<br><sub>Frontend auth handling</sub> | 토큰은 저장 위치마다 위험이 달라요. 갱신은 동시 요청이 몰려도 한 번만 하고, 보호된 화면은 원래 주소를 기억해 로그인 뒤 돌려보내요.<br><sub>Token storage locations carry different risks; refresh once even when concurrent requests fail, and protected screens remember the original URL to return users after login.</sub> | localStorage에 둔 토큰은 JavaScript로 읽히기 때문에 XSS 취약점 한 번이면 그대로 탈취돼요. 메모리에 두면 안전하지만 새로고침하면 사라지고, httpOnly·Secure·SameSite 쿠키는 JS가 읽을 수 없어 리프레시 토큰을 두기에 알맞아요. 그래서 짧게 사는 액세스 토큰은 메모리에, 리프레시 토큰은 httpOnly 쿠키에 두는 조합이 흔해요. 여러 요청이 동시에 401을 받으면 각자 갱신하지 않고 하나의 갱신 요청을 함께 기다린 뒤(single-flight) 새 토큰으로 재시도해서 사용자는 끊김을 못 느껴요. 로그인이 필요한 화면은 /login?next=/dashboard처럼 원래 주소를 기억해 로그인 뒤 돌려보내요. 화면을 숨기는 건 UX일 뿐이고 진짜 권한 검사는 서버가 해야 하며, 쿠키를 쓰면 CSRF 대책과 CSP를 함께 챙겨요.<br><sub>Tokens in localStorage are readable by JavaScript, so a single XSS flaw steals them. Memory is safer but lost on reload, while httpOnly, Secure, SameSite cookies are unreadable by JS and suit refresh tokens. A common combination keeps short-lived access tokens in memory and refresh tokens in httpOnly cookies. When several requests get 401 at once, they wait on one shared refresh (single-flight) instead of each refreshing, then retry with the new token so users notice nothing. Protected screens remember the original URL, as in /login?next=/dashboard, and return users after login. Hiding screens is only UX, since the server must enforce real permissions, and cookies call for CSRF defenses alongside a CSP.</sub> |
