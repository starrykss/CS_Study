## 타입의 기초 · The basics of types

타입이 무엇을 약속하는지, 컴파일러가 타입을 어떻게 알아내고 좁히는지예요.  
*What a type promises, and how the compiler infers and narrows types.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **왜 TypeScript인가**<br><sub>Why TypeScript</sub> | 자바스크립트에 정적 타입을 더해, 코드를 실행하기 전에 타입 오류를 찾아 주는 언어예요. 컴파일하면 평범한 JS가 돼요.<br><sub>A language that adds static types to JavaScript and finds type errors before the code runs; it compiles to plain JavaScript.</sub> | type Item = { name: string; price: number }라고 적어 두면 price에 "3" 같은 문자열을 넣는 순간 편집기에 빨간 줄이 생겨요. 순수 JS였다면 0 + "3"이 "03"이 되는 버그가 조용히 배포됐을 거예요. 검사가 끝나면 tsc는 타입 표기를 모두 지운 평범한 JS를 내보내서 브라우저와 Node.js에서 그대로 실행돼요. 타입 정보 덕분에 자동 완성, 정의로 이동, 안전한 이름 바꾸기도 가능해요. 다만 검사는 컴파일 시점에만 하므로 서버 응답 같은 외부 데이터는 따로 검증해야 해요.<br><sub>With type Item = { name: string; price: number }, putting a string such as "3" into price draws a red squiggle immediately. In plain JavaScript, 0 + "3" would quietly become "03" and ship as a bug. After checking, tsc emits plain JavaScript with every annotation removed, which runs as is in browsers and Node.js. The type information also powers autocomplete, go-to-definition and safe renames. Checking happens only at compile time, so external data such as server responses still needs validation.</sub> |
| **타입 추론**<br><sub>Type inference</sub> | 타입을 적지 않아도 초기값과 문맥을 보고 컴파일러가 타입을 알아내는 기능이에요.<br><sub>The compiler works out types from initial values and context, even when no type is written.</sub> | let count = 0은 number, const mode = "dark"는 바뀌지 않으므로 리터럴 타입 "dark", let theme = "dark"는 바뀔 수 있으니 넓은 string이 돼요. 배열과 객체도 안의 값으로 추론되고, nums.map((n) => …)의 n처럼 콜백 매개변수는 놓인 자리(문맥)로 추론돼요. 함수의 반환 타입도 본문에서 알아내지만 매개변수는 직접 적어야 해요. 초기값 없는 let x나 표기 없는 매개변수는 any가 되니 noImplicitAny(strict)로 막아요. 보통은 매개변수와 공개 API에 타입을 적고 지역 변수는 추론에 맡겨요.<br><sub>let count = 0 is number; const mode = "dark" never changes, so it gets the literal type "dark"; let theme = "dark" may change, so it widens to string. Arrays and objects are inferred from their contents, and callback parameters such as n in nums.map((n) => …) are inferred from context. Return types are inferred from the body, but parameters need annotations. A let x without a value or an unannotated parameter becomes any, which noImplicitAny (part of strict) forbids. The usual style annotates parameters and public APIs and lets inference handle locals.</sub> |
| **배열과 튜플**<br><sub>Arrays and tuples</sub> | 배열은 같은 타입 원소의 목록(number[])이고, 튜플은 길이와 자리마다 타입이 정해진 배열([number, string])이에요.<br><sub>An array is a list of one element type (number[]); a tuple fixes its length and the type of each position ([number, string]).</sub> | const ids: number[]에 "4"를 push하면 오류예요. Array<string>도 같은 뜻이에요. [number, number]는 좌표처럼 정확히 두 개의 숫자를 담고, [key: string, value: number]처럼 자리에 이름을 붙여 뜻을 적을 수도 있어요. readonly string[]은 push나 sort 같은 변경 메서드가 없어서 함수 매개변수로 받을 때 원본을 지켜 줘요. React의 useState가 [값, 설정 함수] 튜플을 돌려주기 때문에 const [count, setCount]처럼 이름을 자유롭게 붙일 수 있어요.<br><sub>Pushing "4" onto const ids: number[] is an error, and Array<string> means the same as string[]. [number, number] holds exactly two numbers, like a coordinate, and labels such as [key: string, value: number] document each slot. readonly string[] has no mutating methods such as push or sort, protecting the caller’s array when used as a parameter. Because React’s useState returns a [value, setter] tuple, you can name both freely, as in const [count, setCount].</sub> |
| **any·unknown·never**<br><sub>any, unknown and never</sub> | any는 타입 검사를 끄는 탈출구, unknown은 모든 값을 받되 확인한 뒤에만 쓰는 안전한 타입, never는 값이 하나도 없는 타입이에요.<br><sub>any is an escape hatch that turns checking off, unknown accepts every value but must be checked before use, and never is the type with no values at all.</sub> | let a: any = JSON.parse(text)에서 a.foo.bar()는 아무 검사 없이 통과해 런타임에야 터져요. 같은 값을 unknown으로 받으면 u.foo부터 오류가 나고, typeof u === "string"처럼 확인한 블록 안에서만 문자열로 쓸 수 있어요. never는 항상 throw하는 함수의 반환 타입이나 모든 경우를 처리한 뒤의 불가능한 분기에 나타나요. 타입을 집합으로 보면 unknown은 맨 위(모든 값), never는 맨 아래(공집합)예요. 외부 입력은 any 대신 unknown으로 받는 습관을 들여요.<br><sub>With let a: any = JSON.parse(text), a.foo.bar() passes unchecked and fails only at run time. Received as unknown, even u.foo is an error, and the value can be used as a string only inside a check such as typeof u === "string". never appears as the return type of functions that always throw and in impossible branches after every case is handled. Seen as sets, unknown is the top (every value) and never the bottom (the empty set). Make a habit of receiving external input as unknown rather than any.</sub> |
| **유니언과 리터럴 타입**<br><sub>Unions and literal types</sub> | 유니언(A \| B)은 여러 타입 중 하나인 값이고, 리터럴 타입은 "idle"이나 8처럼 정확히 그 값 하나만 허용하는 타입이에요.<br><sub>A union (A \| B) is a value of one of several types, and a literal type allows exactly one value such as "idle" or 8.</sub> | type Status = "idle" \| "loading" \| "error"에 "done"을 넣으면 오류라서 상태 이름의 오타가 컴파일 시점에 잡혀요. type Id = string \| number는 두 값 집합의 합집합이라, id.toUpperCase()처럼 한쪽에만 있는 메서드는 바로 쓸 수 없고 String(id)처럼 둘 다 가능한 일만 허용돼요. 한쪽으로 쓰려면 typeof로 먼저 좁혀요. 8 \| 16 \| 24 같은 숫자 리터럴 유니언도 되고, 편집기가 허용되는 값을 자동 완성해 줘요. 리터럴 유니언은 enum 대신 가장 많이 쓰는 방식이에요.<br><sub>Assigning "done" to type Status = "idle" \| "loading" \| "error" is an error, so status typos are caught at compile time. type Id = string \| number is the union of both value sets, so methods on only one side, such as id.toUpperCase(), are rejected and only shared operations such as String(id) are allowed. Narrow with typeof first to use one side. Numeric literal unions such as 8 \| 16 \| 24 work too, and the editor autocompletes the allowed values. Literal unions are the most common alternative to enums.</sub> |
| **타입 좁히기**<br><sub>Narrowing</sub> | 조건문을 보고 블록마다 더 구체적인 타입을 알아내는 컴파일러의 분석이에요. typeof, instanceof, in, ===가 대표 도구예요.<br><sub>The compiler’s analysis of conditions that works out a more specific type in each block, using typeof, instanceof, in and ===.</sub> | v: string \| number \| Date \| null에서 v === null을 먼저 return하면 그 아래에서 v는 string \| number \| Date예요. typeof v === "string" 블록 안에서는 문자열 메서드를 쓸 수 있고, instanceof Date까지 거르면 마지막에 남는 건 number뿐이라 toFixed가 허용돼요. 객체 유니언 Circle \| Square는 "r" in s처럼 속성 존재로 나눠요. 이렇게 return과 분기를 따라가며 남은 가능성을 계산하는 것을 제어 흐름 분석이라 해요. typeof null이 "object"라서 객체 검사 전에 null을 먼저 거르는 게 안전해요.<br><sub>For v: string \| number \| Date \| null, returning early on v === null leaves string \| number \| Date below. Inside typeof v === "string", string methods are available, and once instanceof Date is filtered out only number remains, so toFixed is allowed. Object unions such as Circle \| Square split by property, as in "r" in s. Following returns and branches to compute what remains is called control-flow analysis. Because typeof null is "object", filter null before object checks.</sub> |
| **interface와 type**<br><sub>interface and type</sub> | 둘 다 타입에 이름을 붙여요. interface는 객체 모양을 정의하고 확장·병합에 강하며, type은 유니언·튜플·함수 등 무엇에든 이름을 붙여요.<br><sub>Both name types: interface defines object shapes and excels at extension and merging, while type can name anything, including unions, tuples and functions.</sub> | interface User { id: number; name: string }처럼 객체가 가져야 할 속성을 적고, interface Admin extends User로 확장해요. 같은 이름의 interface를 다시 선언하면 자동으로 합쳐져서(선언 병합) 라이브러리 타입을 보강할 때 써요. type Point = { x: number; y: number }도 객체 모양을 표현하고, type Id = string \| number처럼 interface로는 안 되는 유니언에도 이름을 붙여요. type은 &(교차 타입)로 확장해요. 객체 모양에는 어느 쪽이든 괜찮고, 팀에서 한 규칙으로 통일하는 게 더 중요해요.<br><sub>interface User { id: number; name: string } lists the properties an object must have, and interface Admin extends User builds on it. Redeclaring an interface with the same name merges the declarations, which is used to augment library types. type Point = { x: number; y: number } describes object shapes too, and type Id = string \| number names a union, which interface cannot. A type extends with & (intersection). Either works for object shapes; agreeing on one team convention matters more.</sub> |
| **선택적 속성과 readonly**<br><sub>Optional and readonly properties</sub> | 속성 뒤의 ?는 “없어도 되는” 선택적 속성, 앞의 readonly는 “만든 뒤 바꿀 수 없는” 속성이에요.<br><sub>A ? after a property makes it optional, and readonly before it means it cannot change after creation.</sub> | subtitle?: string은 생략해도 되고, 타입이 string \| undefined가 돼요. 그래서 p.subtitle.length는 오류이고 p.subtitle?.length ?? 0처럼 없을 때를 처리해야 해요. readonly id: number는 객체를 만든 뒤 p.id = 2처럼 다시 대입하면 오류예요. Readonly<Post>는 모든 속성을 한 번에 readonly로 만들지만 안쪽 객체까지 얼리지는 않아요. readonly는 컴파일 시점 검사일 뿐이라 런타임에도 막으려면 Object.freeze를 함께 써요.<br><sub>subtitle?: string may be omitted, and its type becomes string \| undefined. So p.subtitle.length is an error, and absence must be handled, as in p.subtitle?.length ?? 0. readonly id: number makes a later p.id = 2 an error. Readonly<Post> makes every property readonly at once, but not nested objects. readonly is only a compile-time check, so pair it with Object.freeze to enforce it at run time.</sub> |

## 함수와 객체의 타입 · Typing functions and objects

함수에 타입을 붙이는 법, 구조적 타이핑, 그리고 객체 타입을 합치고 좁히고 단언하는 도구들이에요.  
*Typing functions, structural typing, and the tools for combining, narrowing and asserting object types.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **함수에 타입 붙이기**<br><sub>Typing functions</sub> | 함수 타입은 매개변수 타입과 반환 타입으로 이뤄져요. 함수 타입에 이름을 붙이고, 오버로드로 여러 호출 모양을 표현해요.<br><sub>A function type consists of parameter types and a return type; function types can be named, and overloads describe several call shapes.</sub> | function greet(name: string, loud?: boolean)처럼 매개변수에 타입을 적고, 반환 타입은 보통 본문에서 추론돼요. ?는 생략 가능한 매개변수예요. type Handler = (e: MouseEvent) => void에 이름을 붙여 두면 그 자리에 넘긴 콜백의 e가 자동으로 MouseEvent가 돼요. ...nums: number[]처럼 나머지 매개변수는 배열 타입으로 받아요. 문자열을 넣으면 number, 배열을 넣으면 number[]를 돌려주는 함수처럼 입력에 따라 결과가 다르면 오버로드 시그니처를 여러 개 선언해요. 유니언으로 충분하면 그쪽이 더 단순해요.<br><sub>Annotate parameters as in function greet(name: string, loud?: boolean); the return type is usually inferred from the body, and ? marks an optional parameter. Naming type Handler = (e: MouseEvent) => void makes e in any callback passed there a MouseEvent automatically. Rest parameters such as ...nums: number[] take an array type. When results depend on input, such as returning number for a string and number[] for an array, declare several overload signatures. A union is simpler when it suffices.</sub> |
| **구조적 타이핑**<br><sub>Structural typing</sub> | 타입 호환을 이름이 아니라 구조(속성과 그 타입)로 판단해요. 필요한 속성만 갖추면 어떤 객체든 통과해요.<br><sub>Type compatibility is decided by structure, properties and their types, rather than by names; any object with the required properties fits.</sub> | draw(p: Point)에 { x: 1, y: 2, z: 3 }을 담은 변수 v를 넘기면 x와 y가 맞으므로 통과해요. 남는 z는 상관없어요. Point를 언급한 적 없는 class Pixel { x = 0; y = 0 }의 인스턴스도 모양이 같아서 넘길 수 있어요. 예외로, 객체 리터럴을 바로 넘길 때는 초과 속성 검사가 z를 오타로 보고 오류를 내요. Java·C#처럼 선언한 이름으로 비교하는 명목적 타이핑과 달라서, JS의 덕 타이핑 습관을 그대로 표현할 수 있어요.<br><sub>Passing a variable v holding { x: 1, y: 2, z: 3 } to draw(p: Point) works because x and y match; the extra z does not matter. An instance of class Pixel { x = 0; y = 0 }, which never mentions Point, fits too because the shape matches. The exception is a fresh object literal, where the excess property check treats z as a likely typo and reports an error. Unlike nominal typing in Java or C#, which compares declared names, this captures JavaScript’s duck typing directly.</sub> |
| **교차 타입**<br><sub>Intersection types</sub> | A & B는 A이면서 동시에 B인 값이에요. 객체 타입끼리 교차하면 두 모양의 속성을 모두 가져야 해요.<br><sub>A & B is a value that is both A and B; intersecting object types requires the properties of both.</sub> | type Doc = Named & Stamped이면 Doc 값은 name과 createdAt을 모두 가져야 해요. 여러 작은 타입을 조합해 큰 타입을 만들 때 써요. string & number처럼 원시 타입끼리 교차하면 둘 다인 값이 없어서 never가 돼요. 같은 속성의 타입이 충돌해도 그 속성이 never가 되니 주의해요. 제네릭과 함께 쓰면 <T>(o: T) => T & { id: string }처럼 “받은 객체에 id를 더한 결과”를 정확하게 표현해요. 유니언은 “둘 중 하나”, 교차는 “둘 다”로 기억해요.<br><sub>With type Doc = Named & Stamped, a Doc must have both name and createdAt, which is how larger types are composed from small ones. Intersecting primitives such as string & number leaves no value that is both, so the result is never, and conflicting types for the same property also turn that property into never. With generics, <T>(o: T) => T & { id: string } precisely describes “the input object plus an id”. Remember: a union means either, an intersection means both.</sub> |
| **enum과 as const**<br><sub>enum and as const</sub> | enum은 이름 붙인 상수 모음이지만 실제 JS 객체를 만들어 내는 TS 전용 문법이에요. 요즘은 as const 객체와 리터럴 유니언을 더 많이 써요.<br><sub>An enum is a set of named constants, but it is TypeScript-only syntax that emits a real JavaScript object; as const objects and literal unions are now more common.</sub> | enum Dir { Up, Down }은 0, 1로 번호가 매겨지고, 컴파일하면 Dir[0] === "Up" 같은 역매핑까지 담은 객체 코드가 생겨요. 다른 타입 문법처럼 지워지지 않기 때문에 타입만 지우는 Node.js 실행이나 erasableSyntaxOnly 설정과 맞지 않아요. 대안으로 const Role = { Admin: "admin", User: "user" } as const로 값을 readonly 리터럴로 고정하고, typeof Role[keyof typeof Role]로 "admin" \| "user" 타입을 뽑아요. 평범한 JS 객체라 어떤 도구에서도 그대로 동작해요.<br><sub>enum Dir { Up, Down } numbers its members 0 and 1, and compiles to object code that even includes a reverse map such as Dir[0] === "Up". Because it is not erased like other type syntax, it clashes with Node.js type stripping and the erasableSyntaxOnly setting. The alternative, const Role = { Admin: "admin", User: "user" } as const, freezes the values as readonly literals, and typeof Role[keyof typeof Role] derives the type "admin" \| "user". As a plain JavaScript object, it works with every tool.</sub> |
| **as const와 satisfies**<br><sub>as const and satisfies</sub> | satisfies는 값이 어떤 타입을 만족하는지 검사만 하고 추론된 정확한 타입은 그대로 둬요. as const는 값을 가장 좁은 리터럴 타입으로 고정해요.<br><sub>satisfies checks that a value conforms to a type while keeping its precise inferred type, and as const fixes values to their narrowest literal types.</sub> | const a: Theme = { gap: 8, brand: "#36f" }처럼 타입을 표기하면 a는 넓은 Record 타입이 되어 a.gap이 number라는 사실을 잊고, a.typo 같은 없는 키도 허용돼요. 같은 객체에 satisfies Theme을 붙이면 Theme 규칙에 맞는지는 확인하면서 gap: number, brand: string이라는 정확한 타입이 유지되고, 오타 키도 잡혀요. [8, 16] as const는 number[]가 아니라 readonly [8, 16] 튜플이 돼요. 설정 객체, 라우트 표, 디자인 토큰에 특히 유용하고, as const satisfies T로 함께 쓰기도 해요.<br><sub>Annotating const a: Theme = { gap: 8, brand: "#36f" } widens a to a broad Record type, forgetting that a.gap is a number and allowing nonexistent keys such as a.typo. Adding satisfies Theme to the same object checks it against Theme while keeping gap: number and brand: string, and catches typo keys. [8, 16] as const becomes the readonly tuple [8, 16] rather than number[]. It is especially handy for config objects, route tables and design tokens, and the two combine as as const satisfies T.</sub> |
| **타입 단언**<br><sub>Type assertions</sub> | as와 !는 “컴파일러보다 내가 더 잘 안다”는 선언이에요. 아무것도 검사하거나 변환하지 않아서, 틀리면 그대로 런타임 버그가 돼요.<br><sub>as and ! declare that you know better than the compiler; they check and convert nothing, so a wrong assertion simply becomes a runtime bug.</sub> | document.getElementById("app")의 타입은 HTMLElement \| null이라 바로 쓰면 오류예요. el!.textContent처럼 !를 붙이면 null이 아니라고 보증하는 것이고, 실제로 없으면 런타임에 터져요. el as HTMLInputElement는 값은 그대로 두고 타입만 바꿔 말해서, 실제로 div라면 input.value는 undefined예요. "3" as unknown as number 같은 이중 단언은 거의 항상 버그예요. 가능하면 el instanceof HTMLInputElement처럼 검사로 좁혀서 컴파일러가 직접 확인하게 하고, 외부 데이터는 런타임 검증으로 확인해요.<br><sub>document.getElementById("app") has type HTMLElement \| null, so using it directly is an error. el!.textContent promises it is not null and crashes at run time if it is. el as HTMLInputElement changes only the declared type, so if the element is really a div, input.value is undefined. Double assertions such as "3" as unknown as number are almost always bugs. Prefer narrowing with checks such as el instanceof HTMLInputElement so the compiler verifies it, and validate external data at run time.</sub> |
| **인덱스 시그니처와 Record**<br><sub>Index signatures and Record</sub> | [key: string]: number는 “어떤 키든 값은 number”, Record<K, V>는 “키 집합 K의 모든 키에 값 V”를 뜻해요.<br><sub>[key: string]: number means any key maps to a number, and Record<K, V> means every key in K maps to V.</sub> | interface Scores { [name: string]: number }는 키를 미리 모르는 사전에 써요. 다만 s.park처럼 없는 키도 number로 보이니 noUncheckedIndexedAccess를 켜서 number \| undefined로 정확하게 만들어요. Record<"ko" \| "en", string>은 유니언의 모든 키를 요구해서, 번역 표에서 en 하나를 빠뜨리면 바로 오류가 나요. Record<string, T>는 인덱스 시그니처와 같은 뜻이에요. 키가 실행 중에 자주 추가·삭제되면 Map<K, V>가 더 알맞고, get의 결과에 undefined가 포함되어 안전해요.<br><sub>interface Scores { [name: string]: number } suits dictionaries whose keys are unknown in advance. A missing key such as s.park still looks like a number, so enable noUncheckedIndexedAccess to get number \| undefined. Record<"ko" \| "en", string> requires every key in the union, so a translation table missing en is an immediate error. Record<string, T> means the same as an index signature. For keys added and removed at run time, Map<K, V> fits better, and its get includes undefined for safety.</sub> |

<a id="ts-generic"></a>

## 제네릭과 유틸리티 타입 · Generics and utility types

타입을 매개변수로 받아 재사용하는 법과, 기존 타입에서 새 타입을 뽑아내는 도구들이에요.  
*Reusing code by passing types as parameters, and deriving new types from existing ones.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **제네릭**<br><sub>Generics</sub> | 타입을 매개변수(<T>)로 받아, 여러 타입에 재사용하면서도 타입 정보를 잃지 않는 방법이에요.<br><sub>Generics take types as parameters (<T>), so code can be reused across types without losing type information.</sub> | firstAny(arr: any[])는 어떤 배열이든 받지만 결과도 any라서 무엇이 들어갔는지 잊어버려요. function first<T>(arr: T[]): T는 number 배열을 넣으면 number가, 문자열 배열을 넣으면 string이 나와요. T는 보통 인자에서 추론되고, 필요하면 first<string>(…)처럼 직접 넘겨요. interface Box<T> { value: T }처럼 타입도 제네릭이 될 수 있고, Array<T>, Promise<T>, Map<K, V>가 대표 예예요. 한 번만 쓰이는 타입 매개변수는 대개 필요 없어서 그냥 구체 타입을 써요.<br><sub>firstAny(arr: any[]) accepts every array, but its result is any and forgets what went in. function first<T>(arr: T[]): T returns number for a number array and string for a string array. T is usually inferred from the arguments and can be passed explicitly as first<string>(…). Types can be generic too, as in interface Box<T> { value: T }, with Array<T>, Promise<T> and Map<K, V> as the classic examples. A type parameter used only once is usually unnecessary; use the concrete type instead.</sub> |
| **제네릭 제약**<br><sub>Generic constraints</sub> | T extends 조건으로 타입 매개변수가 가져야 할 최소한의 모양을 정해요. 조건을 지키는 타입만 받으면서 결과 타입은 구체적으로 유지돼요.<br><sub>T extends … sets the minimum shape a type parameter must have, accepting only conforming types while keeping the result specific.</sub> | 제약 없는 longest<T>(a: T, b: T)에서 a.length를 쓰면 T에 length가 있다는 보장이 없어 오류예요. longer<T extends { length: number }>로 바꾸면 문자열·배열처럼 length가 있는 타입만 받아요. longer("ab", "c")의 결과는 string, longer([1, 2], [3])는 number[]처럼 넘긴 타입이 그대로 나오고, longer(10, 20)은 호출 단계에서 거부돼요. <T = string>처럼 기본 타입을 정해 두면 추론할 단서가 없을 때 그 타입을 써요. K extends keyof T처럼 다른 매개변수와 엮을 수도 있어요.<br><sub>In an unconstrained longest<T>(a: T, b: T), using a.length is an error because T may lack length. Changing it to longer<T extends { length: number }> accepts only types with a length, such as strings and arrays. longer("ab", "c") returns string and longer([1, 2], [3]) returns number[], keeping the exact type passed in, while longer(10, 20) is rejected at the call. A default such as <T = string> applies when there is nothing to infer. Constraints can link parameters too, as in K extends keyof T.</sub> |
| **keyof와 인덱스 접근 타입**<br><sub>keyof and indexed access types</sub> | keyof T는 T의 키 이름 유니언이고, T[K]는 그 키의 값 타입이에요. 둘을 합치면 키를 안전하게 다루는 함수를 만들어요.<br><sub>keyof T is the union of T’s key names and T[K] is the type of that key’s value; together they type functions that handle keys safely.</sub> | type User = { id: number; name: string }에서 keyof User는 "id" \| "name", User["name"]은 string이에요. function get<T, K extends keyof T>(o: T, k: K): T[K]는 get(u, "name")에 string을 돌려주고, 없는 키 "age"는 호출 단계에서 거부해요. (typeof list)[number]처럼 [number]로 인덱스하면 배열 원소의 타입을 꺼낼 수 있어요. keyof와 T[K]는 Partial, Pick 같은 유틸리티 타입과 매핑된 타입의 재료예요.<br><sub>For type User = { id: number; name: string }, keyof User is "id" \| "name" and User["name"] is string. function get<T, K extends keyof T>(o: T, k: K): T[K] returns string for get(u, "name") and rejects the unknown key "age" at the call. Indexing with [number], as in (typeof list)[number], extracts an array’s element type. keyof and T[K] are the building blocks of utility types such as Partial and Pick, and of mapped types.</sub> |
| **객체 유틸리티 타입**<br><sub>Object utility types</sub> | Partial, Required, Pick, Omit, Readonly는 기존 객체 타입을 변형해 새 타입을 만드는 내장 제네릭이에요.<br><sub>Partial, Required, Pick, Omit and Readonly are built-in generics that transform an existing object type into a new one.</sub> | Todo { id, title, done }에서 Partial<Todo>는 모든 속성을 선택적으로, Required는 반대로 모두 필수로 바꿔요. Pick<Todo, "id" \| "title">은 고른 키만 남기고, Omit<Todo, "id">는 그 키를 빼요. Readonly<Todo>는 모든 속성을 readonly로 만들어요. 조합하면 수정 요청 타입을 Partial<Omit<Todo, "id">>처럼 한 줄로 정확하게 표현해요. 원본 Todo를 고치면 파생된 타입도 자동으로 따라와서 같은 모양을 두 번 관리할 일이 없어요.<br><sub>For Todo { id, title, done }, Partial<Todo> makes every property optional and Required makes them all required. Pick<Todo, "id" \| "title"> keeps only the chosen keys, and Omit<Todo, "id"> removes them. Readonly<Todo> makes every property readonly. Combined, a patch type is written precisely in one line as Partial<Omit<Todo, "id">>. Change Todo and every derived type follows, so no shape is maintained twice.</sub> |
| **함수·유니언 유틸리티 타입**<br><sub>Function and union utility types</sub> | Parameters, ReturnType, Awaited는 함수에서 타입을 뽑고, Extract, Exclude, NonNullable은 유니언을 거르는 내장 타입이에요.<br><sub>Parameters, ReturnType and Awaited extract types from functions, while Extract, Exclude and NonNullable filter unions.</sub> | Parameters<typeof load>는 [id: number] 같은 매개변수 튜플을, ReturnType<typeof load>는 반환 타입을 줘요. async 함수라면 Promise<…>이 나오니 Awaited로 감싸 실제 값의 타입을 꺼내요. 유니언 S = "a" \| "b" \| "c"에서 Extract<S, "a" \| "b">는 맞는 멤버만 남기고, Exclude는 그 멤버를 빼서 "c"를 남겨요. NonNullable<string \| null>은 string이에요. 라이브러리가 타입을 따로 내보내지 않아도 함수에서 바로 뽑아 쓸 수 있어 정의가 한곳에 모여요.<br><sub>Parameters<typeof load> gives the parameter tuple, such as [id: number], and ReturnType<typeof load> the return type. For an async function this is Promise<…>, so wrap it in Awaited to get the resolved value’s type. For S = "a" \| "b" \| "c", Extract<S, "a" \| "b"> keeps the matching members and Exclude removes them, leaving "c". NonNullable<string \| null> is string. Types can be pulled straight from functions even when a library exports none, keeping one source of truth.</sub> |

<a id="ts-advanced"></a>

## 고급 타입 기법 · Advanced type techniques

불가능한 상태를 없애는 모델링부터 타입 수준의 조건문, 반복, 문자열 조합까지예요.  
*From modeling that rules out impossible states to type-level conditions, loops and string building.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **판별 유니언**<br><sub>Discriminated unions</sub> | 공통 꼬리표 속성(status, type 등)의 리터럴 값으로 구분되는 유니언이에요. 꼬리표를 확인하면 나머지 속성이 정확히 좁혀져요.<br><sub>A union whose members are told apart by the literal value of a shared tag property such as status or type; checking the tag narrows the rest precisely.</sub> | Result를 { status: "ok"; data } \| { status: "error"; message } \| { status: "loading" }로 정의하면, switch (r.status)의 각 case 안에서 r이 해당 모양으로 좁혀져 ok일 때만 r.data에 접근할 수 있어요. data와 message를 둘 다 선택적 속성으로 두는 방식과 달리 “성공인데 오류 메시지도 있는” 불가능한 상태를 아예 만들 수 없어요. default에서 const x: never = r로 대입해 두면, 나중에 새 상태를 추가했을 때 처리하지 않은 모든 switch가 컴파일 오류로 드러나요. 화면 상태, Redux 액션, API 결과 모델링의 기본이에요.<br><sub>Defining Result as { status: "ok"; data } \| { status: "error"; message } \| { status: "loading" } narrows r inside each case of switch (r.status), so r.data is reachable only when ok. Unlike making data and message both optional, impossible states such as a success with an error message simply cannot be written. Assigning const x: never = r in default turns every unhandled switch into a compile error when a new status is added later. It is the standard way to model screen states, Redux actions and API results.</sub> |
| **사용자 정의 타입 가드**<br><sub>User-defined type guards</sub> | 반환 타입을 p is Fish처럼 적은 함수예요. true를 돌려주면 그 값이 Fish라고 컴파일러가 믿고 타입을 좁혀요.<br><sub>A function whose return type reads like p is Fish; when it returns true, the compiler trusts that the value is a Fish and narrows it.</sub> | function isFish(p: Fish \| Bird): p is Fish로 만들면 if (isFish(pet)) 안에서는 Fish, else에서는 Bird로 좁혀져요. [1, null, 2].filter((x): x is number => x !== null)은 number[]가 되는데, TS 5.5부터는 이런 단순한 경우를 자동으로 추론해요. asserts v is string을 반환 타입으로 쓰면 통과하지 못할 때 예외를 던지고, 그다음 줄부터 v를 string으로 좁혀요. 주의할 점은 검사 로직이 틀려도 컴파일러는 그대로 믿는다는 것이에요. 복잡한 검사는 zod 같은 스키마 라이브러리에 맡기면 안전해요.<br><sub>With function isFish(p: Fish \| Bird): p is Fish, pet is a Fish inside if (isFish(pet)) and a Bird in else. [1, null, 2].filter((x): x is number => x !== null) yields number[], and since TS 5.5 such simple cases are inferred automatically. An asserts v is string return type throws when the check fails and narrows v to string from the next line on. The catch is that the compiler trusts the guard even if its logic is wrong, so leave complex checks to schema libraries such as zod.</sub> |
| **조건부 타입과 infer**<br><sub>Conditional types and infer</sub> | T extends U ? X : Y로 타입을 분기하는 타입 수준의 삼항 연산자예요. infer로 패턴 속의 타입을 꺼낼 수 있어요.<br><sub>A type-level ternary, T extends U ? X : Y, that branches on types; infer pulls types out of a pattern.</sub> | type Is<T> = T extends string ? "y" : "n"에서 Is<"hi">는 "y", Is<42>는 "n"이에요. 유니언을 넘기면 멤버마다 따로 적용되어 Is<"a" \| 1>은 "y" \| "n"이 돼요(분배). T extends Promise<infer U> ? U : T는 Promise<number>에서 number를 꺼내고, T extends (infer E)[] ? E : never는 배열의 원소 타입을 꺼내요. 내장 ReturnType과 Awaited도 이 방식으로 구현되어 있어요. 분배를 막으려면 [T] extends [U]처럼 감싸고, 앱 코드에서는 꼭 필요할 때만 써요.<br><sub>With type Is<T> = T extends string ? "y" : "n", Is<"hi"> is "y" and Is<42> is "n". A union argument is processed member by member, so Is<"a" \| 1> is "y" \| "n" (distribution). T extends Promise<infer U> ? U : T extracts number from Promise<number>, and T extends (infer E)[] ? E : never extracts an array’s element type. The built-in ReturnType and Awaited are implemented this way. Wrap as [T] extends [U] to prevent distribution, and use these sparingly in application code.</sub> |
| **매핑된 타입**<br><sub>Mapped types</sub> | [K in keyof T]로 기존 타입의 키를 하나씩 돌며 속성을 변형해 새 객체 타입을 만드는 문법이에요.<br><sub>Syntax that iterates over the keys of an existing type with [K in keyof T] and transforms each property into a new object type.</sub> | type Flags<T> = { [K in keyof T]: boolean }은 { dark: string; beta: number }를 { dark: boolean; beta: boolean }으로 바꿔요. 값 타입 T[K]를 유지하고 ?만 붙이면 Partial을 직접 만든 셈이고, -readonly나 -?처럼 앞에 -를 붙이면 수식어를 떼어 내요. as 절로 키 이름 자체를 바꿀 수도 있어서, 이벤트 맵에서 click을 onclick 핸들러로 바꾸는 식이에요. as에서 never를 돌려주면 그 키를 걸러 내요. Partial, Required, Readonly, Record가 모두 매핑된 타입이에요.<br><sub>type Flags<T> = { [K in keyof T]: boolean } turns { dark: string; beta: number } into { dark: boolean; beta: boolean }. Keeping T[K] and adding ? rebuilds Partial, and a leading -, as in -readonly or -?, removes modifiers. An as clause renames the keys themselves, turning click in an event map into an onclick handler, and returning never there filters a key out. Partial, Required, Readonly and Record are all mapped types.</sub> |
| **템플릿 리터럴 타입**<br><sub>Template literal types</sub> | 백틱 문법으로 문자열 리터럴 타입을 조합하고 변형해요. 클래스 이름, 이벤트 이름, 경로 같은 규칙 있는 문자열을 타입으로 검사해요.<br><sub>Backtick syntax combines and transforms string literal types, type-checking patterned strings such as class names, event names and paths.</sub> | `${Color}-${Size}`는 색 2개와 크기 3개를 곱해 "red-sm"부터 "blue-lg"까지 6개의 리터럴 유니언을 만들어요. `/users/${number}`처럼 원시 타입을 끼우면 "/users/42"는 통과하고 "/users/kim"은 거부하는 패턴이 돼요. Capitalize, Uppercase, Lowercase, Uncapitalize 같은 내장 타입으로 대소문자를 바꿔 "onClick" 같은 이름도 만들어요. 매핑된 타입의 as, infer와 함께 쓰면 경로 문자열에서 매개변수 이름을 뽑는 것까지 가능해요. 조합이 너무 많아지면 컴파일이 느려지니 주의해요.<br><sub>`${Color}-${Size}` multiplies 2 colors by 3 sizes into a union of 6 literals, from "red-sm" to "blue-lg". Slotting in a primitive, as in `/users/${number}`, creates a pattern that accepts "/users/42" and rejects "/users/kim". Built-ins such as Capitalize, Uppercase, Lowercase and Uncapitalize change case to derive names such as "onClick". Combined with mapped-type as clauses and infer, they can even extract parameter names from path strings. Too many combinations slow the compiler, so take care.</sub> |
| **브랜드 타입**<br><sub>Branded types</sub> | 구조가 같은 값을 의미별로 구분하기 위해 가짜 꼬리표 속성을 교차한 타입이에요. 런타임 비용 없이 “섞이면 안 되는 값”을 막아요.<br><sub>Types that intersect a phantom tag property to distinguish same-shaped values by meaning, preventing mix-ups at no run-time cost.</sub> | type UserId = string과 type OrderId = string은 둘 다 그냥 string이라 cancel(user.id)처럼 엉뚱한 ID를 넘겨도 통과해요. type Brand<T, B> = T & { \_\_brand: B }로 Brand<string, "UserId">와 Brand<string, "OrderId">를 만들면 구조적으로 다른 타입이 되어 섞어 쓰면 컴파일 오류가 나요. 런타임 값은 여전히 문자열이에요. 브랜드는 parseOrderId 같은 검증 함수 한곳에서만 붙여서, 그 타입이 “검증을 거친 값”임을 보장해요. ID, 통화 단위, 정제된 HTML 등에 쓰고, zod의 .brand()도 같은 원리예요.<br><sub>type UserId = string and type OrderId = string are both plain strings, so cancel(user.id) compiles even with the wrong ID. With type Brand<T, B> = T & { \_\_brand: B }, Brand<string, "UserId"> and Brand<string, "OrderId"> become structurally different, and mixing them is a compile error, while the runtime values remain strings. Attach brands only in one validating function such as parseOrderId, so the type guarantees the value was checked. They suit IDs, currencies and sanitized HTML, and zod’s .brand() works the same way.</sub> |

## 설정, 빌드, 생태계 · Configuration, builds and the ecosystem

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **tsconfig.json**<br><sub>tsconfig.json</sub> | 어떤 파일을, 얼마나 엄격하게, 어떤 JS로 컴파일할지 정하는 TypeScript 컴파일러의 설정 파일이에요.<br><sub>The TypeScript compiler’s configuration file, deciding which files to compile, how strictly, and into which JavaScript.</sub> | target은 출력할 JS 문법 버전(ES2022 등), module은 import·require 방식(NodeNext, ESNext 등)을 정해요. strict: true 하나가 noImplicitAny, strictNullChecks 같은 엄격한 검사 묶음을 켜므로 새 프로젝트에서는 꼭 켜요. noUncheckedIndexedAccess는 배열·인덱스 접근에 undefined 가능성을 더하고, noEmit은 번들러가 빌드할 때 tsc는 검사만 하게 해요. paths는 @/components 같은 import 별칭을 정하는데 번들러에도 같은 설정이 필요해요. extends로 공통 설정을 물려받을 수 있어요.<br><sub>target sets the output syntax version, such as ES2022, and module the import system, such as NodeNext or ESNext. strict: true enables a family of checks including noImplicitAny and strictNullChecks, so turn it on for every new project. noUncheckedIndexedAccess adds undefined to array and index access, and noEmit makes tsc only check while a bundler builds. paths defines import aliases such as @/components, which the bundler must mirror. extends inherits shared presets.</sub> |
| **컴파일과 타입 지우기**<br><sub>Compilation and type erasure</sub> | TypeScript의 타입은 컴파일 시점에만 존재해요. 출력된 JS에는 타입이 하나도 남지 않고, 검사와 변환은 서로 다른 도구가 맡기도 해요.<br><sub>TypeScript types exist only at compile time; nothing of them survives in the output, and checking and transpiling are often done by different tools.</sub> | interface User와 (u: User): string 같은 표기는 컴파일하면 모두 지워지고 로직은 한 글자도 바뀌지 않아요. tsc는 타입 검사와 JS 출력을 함께 하지만 느리고, esbuild·swc·Vite는 파일마다 타입을 지우기만 해서 아주 빠른 대신 오류를 잡지 않아요. 그래서 “빌드는 성공했는데 타입 오류가 있는” 상황을 막으려면 편집기와 CI에서 tsc --noEmit으로 검사를 따로 돌려요. 요즘은 Node.js(22.18+), Deno, Bun이 .ts 파일을 직접 실행하는데, 타입만 지우는 방식이라 enum처럼 코드를 만들어 내는 문법은 지원하지 않아요.<br><sub>Annotations such as interface User and (u: User): string are all erased on compilation, leaving the logic untouched. tsc both checks and emits but is slow, while esbuild, swc and Vite strip types file by file, which is very fast but catches no errors. To avoid builds that succeed despite type errors, run tsc --noEmit separately in editors and CI. Node.js (22.18+), Deno and Bun now run .ts files directly, but because they only strip types, syntax that generates code, such as enums, is not supported.</sub> |
| **선언 파일과 @types**<br><sub>Declaration files and @types</sub> | .d.ts 파일은 구현 없이 타입 정보만 담은 선언 파일이에요. 타입 없이 작성된 JS 라이브러리를 TypeScript와 이어 줘요.<br><sub>A .d.ts file holds type information without implementations, connecting untyped JavaScript libraries to TypeScript.</sub> | clamp(v, lo, hi)처럼 타입 없이 작성된 JS 함수를 가져오면 TS는 모양을 몰라 any로 다뤄요. math.d.ts에 export declare function clamp(v: number, lo: number, hi: number): number처럼 선언만 적으면 타입 검사와 자동 완성이 살아나요. 직접 쓰지 않아도 npm i -D @types/lodash처럼 DefinitelyTyped 커뮤니티가 만든 선언을 설치할 수 있고, 요즘 라이브러리는 대부분 타입을 내장해요. declare global { interface Window { … } }처럼 기존 타입에 속성을 더하는 보강도 선언 파일로 해요. 라이브러리를 만들 땐 declaration: true로 .d.ts를 자동 생성해요.<br><sub>Importing an untyped JavaScript function such as clamp(v, lo, hi) leaves TypeScript blind, treating it as any. Writing only a declaration in math.d.ts, export declare function clamp(v: number, lo: number, hi: number): number, brings back checking and autocomplete. Instead of writing them, you can install community declarations from DefinitelyTyped, as in npm i -D @types/lodash, and most modern libraries bundle their own. Augmentations such as declare global { interface Window { … } } also live in declaration files. When publishing a library, declaration: true generates .d.ts files.</sub> |
| **런타임 검증**<br><sub>Runtime validation</sub> | 타입은 런타임에 사라지므로, 외부에서 들어오는 데이터는 zod 같은 스키마로 실제로 검사해야 해요. 스키마에서 타입을 뽑아 쓰면 둘이 어긋나지 않아요.<br><sub>Types vanish at run time, so data entering from outside must be checked with a schema such as zod; deriving the type from the schema keeps them in sync.</sub> | await res.json()은 any를 돌려주고, 여기에 as User를 붙여도 실제 모양은 아무도 확인하지 않아서 서버 응답이 바뀌면 엉뚱한 곳에서 조용히 깨져요. z.object({ id: z.number(), name: z.string().min(1) })로 스키마를 선언하고 type User = z.infer<typeof UserSchema>로 타입을 뽑으면 규칙과 타입이 한곳에 모여요. safeParse는 예외 없이 성공 여부를 돌려주고, 성공하면 parsed.data가 User 타입이에요. API 응답, 폼 입력, 환경 변수, localStorage처럼 시스템 경계에서만 검증하고, 경계 안쪽에서는 검증된 타입을 믿고 써요.<br><sub>await res.json() returns any, and adding as User checks nothing, so a changed server response breaks something far away, silently. Declaring z.object({ id: z.number(), name: z.string().min(1) }) and deriving type User = z.infer<typeof UserSchema> keeps rules and type in one place. safeParse reports success without throwing, and on success parsed.data is a User. Validate only at system boundaries such as API responses, form input, environment variables and localStorage, and trust the validated types inside.</sub> |
| **클래스와 접근 제어자**<br><sub>Classes and access modifiers</sub> | TS는 JS 클래스에 public·protected·private 접근 제어자, abstract, implements, 매개변수 속성을 더해요.<br><sub>TypeScript adds public, protected and private modifiers, abstract, implements and parameter properties to JavaScript classes.</sub> | abstract class Base는 직접 new 할 수 없고, abstract area()는 자식 클래스가 반드시 구현해야 해요. public은 어디서나, protected는 자신과 자식에서만, private은 클래스 안에서만 쓸 수 있어요. constructor(public r: number)처럼 매개변수 앞에 제어자를 붙이면 속성 선언과 대입이 한 번에 돼요. implements Shape는 클래스가 인터페이스의 모양을 지키는지 검사해요. 단, TS의 private은 컴파일 시점에만 막으므로 런타임에도 숨기려면 JS 표준 #private 필드를 써요.<br><sub>abstract class Base cannot be instantiated directly, and subclasses must implement abstract area(). public members are usable anywhere, protected ones in the class and its subclasses, and private ones only inside the class. A modifier before a constructor parameter, as in constructor(public r: number), declares and assigns the property in one go. implements Shape checks that the class matches an interface. TypeScript’s private is enforced only at compile time, so use standard #private fields to hide members at run time too.</sub> |
| **데코레이터**<br><sub>Decorators</sub> | @로 클래스나 메서드에 붙이는 함수예요. 정의를 감싸 새 동작을 더하거나 메타데이터를 붙여요.<br><sub>Functions attached to classes or methods with @ that wrap the definition to add behavior or attach metadata.</sub> | @logged를 getUser 위에 붙이면 클래스를 정의할 때 logged(fn, ctx)가 실행되고, 원래 메서드를 감싼 새 함수가 그 자리를 대신해요. 그래서 getUser를 부를 때마다 로그가 먼저 찍혀요. 이렇게 로깅, 캐시, 권한 검사 같은 공통 관심사를 메서드 본문에서 떼어 낼 수 있어요. TS 5부터는 표준(Stage 3) 데코레이터를 지원하지만, NestJS·Angular는 매개변수 데코레이터와 reflect-metadata가 필요해서 옛 experimentalDecorators 방식을 계속 써요. 두 방식은 함수 시그니처가 달라서 섞어 쓸 수 없어요.<br><sub>Placing @logged above getUser runs logged(fn, ctx) when the class is defined, and the wrapped function it returns replaces the original method. Every getUser call now logs first. Cross-cutting concerns such as logging, caching and authorization can be lifted out of method bodies this way. TS 5 supports standard (stage 3) decorators, but NestJS and Angular still use the legacy experimentalDecorators mode because they need parameter decorators and reflect-metadata. The two flavors have different signatures and cannot be mixed.</sub> |
