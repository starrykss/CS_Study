## 코드가 실행되기까지 · From code to execution

우리가 쓴 코드가 컴퓨터가 실행하는 형태로 바뀌는 과정이에요.  
*How the code we write becomes something a computer runs.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **컴파일 과정**<br><sub>Compilation pipeline</sub> | 소스 코드는 토큰으로 쪼개지고(어휘 분석), 문법 트리(AST)가 되고(구문 분석), 최적화를 거쳐 기계어나 바이트코드가 돼요.<br><sub>Source is split into tokens (lexing), shaped into a syntax tree (parsing), optimized and emitted as machine code or bytecode.</sub> | 린터·포매터·번들러·코드 변환기가 모두 AST를 다뤄요. 에러 메시지의 "unexpected token"은 파싱 단계에서 났다는 뜻이에요.<br><sub>Linters, formatters, bundlers and codemods all work on ASTs; “unexpected token” means the parser gave up.</sub> |
| **컴파일러 · 인터프리터 · JIT**<br><sub>Compiler · Interpreter · JIT</sub> | 컴파일러는 미리 전부 번역하고, 인터프리터는 읽으면서 바로 실행하고, JIT는 실행하면서 자주 쓰는 부분만 기계어로 바꿔요.<br><sub>A compiler translates everything up front, an interpreter runs as it reads, and a JIT compiles hot code while running.</sub> | V8·JVM이 JIT라서 처음엔 느리다가 빨라져요(워밍업). 서버리스의 콜드 스타트 문제도 여기서 생겨요.<br><sub>V8 and the JVM are JITs, so they start slower and speed up (warm-up); serverless cold starts come from this.</sub> |
| **바이트코드와 가상 기계**<br><sub>Bytecode and virtual machines</sub> | 소스를 특정 CPU의 기계어 대신 가상 기계용 명령어(바이트코드)로 바꾸고, VM이 그 명령어를 실행해요.<br><sub>Compile source into instructions for a virtual machine (bytecode) rather than for a specific CPU, then let the VM execute them.</sub> | 스택 기계는 PUSH 2, PUSH 3, ADD처럼 피연산자 스택에 값을 올리고 꺼내며 계산해요. JVM, CPython, WebAssembly가 스택 기계이고, Lua와 안드로이드의 Dalvik은 레지스터 기계예요. 한 번 컴파일한 바이트코드를 어느 운영체제에서나 같은 VM으로 실행할 수 있고, 자주 실행되는 부분은 JIT가 기계어로 다시 번역해 빠르게 해요.<br><sub>A stack machine computes by pushing and popping an operand stack: PUSH 2, PUSH 3, ADD. The JVM, CPython and WebAssembly are stack machines; Lua and Android’s Dalvik are register machines. Bytecode compiled once runs on any OS with the same VM, and a JIT recompiles hot paths into machine code for speed.</sub> |
| **평가 전략**<br><sub>Evaluation strategies</sub> | 식을 언제 계산하느냐의 규칙이에요. 인자를 먼저 다 계산하는 조급한 평가, 필요할 때 계산하는 지연 평가, 결과가 정해지면 멈추는 단락 평가가 있어요.<br><sub>Rules for when expressions are computed: eager evaluation computes arguments first, lazy evaluation waits until a value is needed, and short-circuiting stops once the result is known.</sub> | 대부분의 언어는 함수 호출 전에 인자를 모두 계산해서 쓰지 않을 인자도 계산해요. &&, \|\|는 앞에서 결과가 정해지면 뒤를 계산하지 않아 user && user.name 같은 안전 장치가 돼요. Haskell은 기본이 지연 평가라 무한 리스트에서 필요한 만큼만 꺼내고, 한 번 계산한 값(thunk)은 기억해 다시 계산하지 않아요. 지연 평가는 부수 효과의 순서를 예측하기 어렵게 만들어요.<br><sub>Most languages evaluate every argument before a call, even unused ones. && and \|\| skip the right side when the left already decides, which makes guards like user && user.name safe. Haskell is lazy by default, so it can take just what it needs from an infinite list, and a forced thunk is remembered rather than recomputed. Laziness makes the order of side effects harder to predict.</sub> |
| **동적 디스패치와 vtable**<br><sub>Dynamic dispatch and vtables</sub> | 같은 메서드 호출이 객체의 실제 타입에 따라 다른 함수로 연결되는 방법이에요. 객체가 함수 표(vtable)를 가리켜요.<br><sub>How one method call reaches different functions depending on an object’s real type: the object points at a function table (vtable).</sub> | 각 객체는 자기 클래스의 vtable을 가리키는 포인터를 품고, 호출 시 vptr을 읽고 → 표의 칸을 읽고 → 그 주소를 불러요. 간접 호출이라 인라인이 막혀 조금 느리기 때문에, JIT는 자주 오는 타입을 바로 부르는 인라인 캐시로 최적화해요. C++ virtual, Java(기본이 가상), Rust dyn Trait(팻 포인터)가 이 방식이고 Python·JS는 사전이나 히든 클래스로 메서드를 찾아요.<br><sub>Each object carries a pointer to its class’s vtable; a call loads the vptr, loads the table slot and calls that address. The indirection blocks inlining and costs a little, so JITs use inline caches that call the common type directly. C++ virtual functions, Java (virtual by default) and Rust dyn Trait (fat pointers) work this way, while Python and JS look methods up in dictionaries or hidden classes.</sub> |
| **매크로와 메타프로그래밍**<br><sub>Macros and metaprogramming</sub> | 컴파일 전에 코드를 다른 코드로 바꿔 주는 규칙이에요. 텍스트를 바꾸는 매크로는 위험하고, 구문 트리를 바꾸는 매크로는 안전해요.<br><sub>Rules that rewrite code into other code before compilation: text macros are risky, syntax-tree macros are safe.</sub> | C 전처리기의 #define SQ(x) x \* x는 SQ(1 + 2)를 1 + 2 \* 1 + 2로 펼쳐 5가 나와요(기대값 9). Rust macro\_rules!, Lisp defmacro 같은 구문 트리 매크로는 (1 + 2)를 한 덩어리로 다루고 이름 충돌도 막아요(위생적 매크로). 직렬화·테스트 같은 반복 코드 생성과 DSL에 쓰이지만, 남용하면 디버깅이 어려워요.<br><sub>The C preprocessor’s #define SQ(x) x \* x expands SQ(1 + 2) into 1 + 2 \* 1 + 2, giving 5 instead of 9. Syntax-tree macros such as Rust’s macro\_rules! and Lisp’s defmacro treat (1 + 2) as a unit and avoid name capture (hygiene). They generate boilerplate such as serialization and tests and build DSLs, but overuse makes debugging hard.</sub> |

## 타입 시스템 · Type systems

값의 종류를 약속해서 실수를 미리 막는 장치예요.  
*Promises about kinds of values that catch mistakes early.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **정적 vs 동적 타입**<br><sub>Static vs dynamic typing</sub> | 정적 타입은 실행 전에 타입을 검사하고, 동적 타입은 실행하면서 확인해요. 요즘 정적 언어는 타입 추론으로 덜 써도 돼요.<br><sub>Static typing checks types before running; dynamic typing checks while running. Modern static languages infer most types.</sub> | 큰 팀·긴 수명의 코드는 TypeScript·Kotlin 같은 정적 타입이 리팩터링과 자동 완성을 크게 도와요.<br><sub>For large teams and long-lived code, static types (TypeScript, Kotlin) make refactoring and autocomplete far better.</sub> |
| **암묵적 형 변환**<br><sub>Implicit type coercion</sub> | 언어가 타입이 다른 값을 몰래 바꿔 계산하는 거예요. JS의 == 와 + 연산이 대표적이에요.<br><sub>The language silently converts values of different types to make an operation work; JS’s == and + are infamous.</sub> | 항상 ===를 쓰고, 숫자 변환은 Number()로 명시하세요. 폼 입력값은 항상 문자열로 들어와요.<br><sub>Always use ===, convert explicitly with Number(), and remember form inputs arrive as strings.</sub> |
| **제네릭**<br><sub>Generics</sub> | 타입을 매개변수로 받아, 하나의 코드로 여러 타입을 안전하게 다뤄요.<br><sub>Take types as parameters so one piece of code safely handles many types.</sub> | List<T>, Promise<T>, API 응답 래퍼처럼 컨테이너를 만들 때 필수예요. any로 도망가지 말고 제네릭으로 타입을 이어 주세요.<br><sub>Essential for containers like List<T>, Promise<T> and API response wrappers; reach for generics instead of any.</sub> |
| **null 안전성**<br><sub>Null safety</sub> | null일 수 있는 값을 타입으로 표시하고, ?. 같은 연산자로 안전하게 접근해요. 컴파일러가 null 체크 누락을 잡아 줘요.<br><sub>Mark values that may be null in their types and access them safely with operators like ?.; the compiler flags missing checks.</sub> | TypeScript strictNullChecks, Kotlin의 String?, Swift Optional을 켜 두세요. NullPointerException이 크게 줄어요.<br><sub>Turn on TypeScript strictNullChecks or use Kotlin String? and Swift Optional; null-pointer crashes drop sharply.</sub> |
| **제네릭 구현: 소거와 단형화**<br><sub>Implementing generics: erasure vs monomorphization</sub> | 제네릭 함수 하나를 기계 코드로 만드는 방법은 크게 둘이에요. 타입을 지워 한 벌로 만들거나, 타입마다 복사본을 만들어요.<br><sub>A generic function becomes machine code in one of two main ways: erase the types and compile once, or copy it per type.</sub> | Java는 타입 매개변수를 지우고(소거) Object로 한 번 컴파일한 뒤 호출하는 쪽에 형 변환을 넣어서, 실행 중엔 List<String>인지 알 수 없어요. C++ 템플릿과 Rust는 쓰인 타입마다 전용 코드를 만들어(단형화) 빠르지만 바이너리가 커져요. C#·.NET은 실행 중에도 타입을 아는 구체화된 제네릭으로 둘 사이를 절충하고, Go는 GC 모양별로 묶어요.<br><sub>Java erases type parameters, compiles once against Object and inserts casts at call sites, so a List<String> can’t be detected at run time. C++ templates and Rust generate specialized code for each type used (monomorphization): fast, but binaries grow. C#/.NET keeps types at run time with reified generics, and Go groups instantiations by GC shape.</sub> |
| **서브타이핑과 변성**<br><sub>Subtyping and variance</sub> | Dog가 Animal의 하위 타입일 때, Dog 목록도 Animal 목록의 하위 타입일까요? 읽기만 하면 예(공변), 쓰기도 하면 아니요(무변)예요.<br><sub>If Dog is a subtype of Animal, is a list of Dogs a list of Animals? For reading, yes (covariant); with writing, no (invariant).</sub> | 꺼내기만 하는 생산자(읽기 전용 목록, 반환값)는 공변, 받기만 하는 소비자(비교기, 함수 인자)는 반공변이에요. 넣고 꺼내는 변경 가능 목록은 무변이어야 하는데, Java 배열은 공변이라 Cat을 넣으면 ArrayStoreException이 나요. Java는 PECS(? extends / ? super), Kotlin·C#은 out/in으로 변성을 선언해요.<br><sub>Producers you only read from (read-only lists, return values) are covariant, consumers you only feed (comparators, function parameters) are contravariant, and mutable containers must be invariant; Java arrays are covariant, so storing a Cat throws ArrayStoreException. Java expresses variance with PECS (? extends / ? super), Kotlin and C# with out/in.</sub> |
| **서브타이핑**<br><sub>Subtyping</sub> | S가 T의 서브타입이면 T가 필요한 모든 자리에 S 값을 대신 넣어도 안전해요. 타입들은 맨 위 Any부터 맨 아래 Nothing까지 위아래 관계를 이뤄요.<br><sub>If S is a subtype of T, an S value can safely go wherever a T is expected. Types form a hierarchy from Any at the top to Nothing at the bottom.</sub> | 서브타입 관계 S <: T는 “T를 기대하는 곳 어디에나 S를 넣어도 된다”는 약속이에요. Dog <: Animal이면 feed(a: Animal)에 Dog를 넘길 수 있어요. 하위 타입을 상위 타입 변수에 담는 업캐스트는 언제나 안전해서 자동으로 일어나고, 반대 방향 다운캐스트(a as Dog)는 실제 값이 Cat일 수 있으니 실행 중에 검사해야 해요. Kotlin의 is, TypeScript의 타입 가드처럼 검사 후 자동으로 좁혀 주는 문법이 안전한 방법이에요. 타입들은 위아래로 이어진 계층을 이뤄요. 맨 위의 Any(Object, unknown)는 모든 값을 담고, 맨 아래의 Nothing(never)은 값이 하나도 없어서 모든 타입의 서브타입이에요. 그래서 항상 예외를 던지는 fail()의 반환 타입을 Nothing으로 두면 Int가 필요한 자리에도 쓸 수 있어요. 서브타입과 상속은 달라요. 인터페이스 구현은 코드를 물려받지 않고도 서브타입이 되고, Square extends Rectangle처럼 상속은 했지만 너비만 바꾸는 코드가 깨진다면 진짜 서브타입이 아니에요(리스코프 치환 원칙 위반). Java·Kotlin 같은 명목적 언어는 선언으로, TypeScript·Go 인터페이스 같은 구조적 언어는 모양으로 서브타입을 정해요. 제네릭 타입끼리의 서브타입 관계는 변성이 정해요.<br><sub>The subtype relation S <: T promises that an S can be used anywhere a T is expected: with Dog <: Animal, feed(a: Animal) accepts a Dog. Upcasting, storing a subtype in a supertype variable, is always safe and happens implicitly; downcasting the other way (a as Dog) must be checked at run time, since the value might really be a Cat. Flow-sensitive checks such as Kotlin’s is or TypeScript’s type guards narrow the type safely. Types form a hierarchy: Any (Object, unknown) at the top holds every value, and Nothing (never) at the bottom has no values at all, making it a subtype of every type, so a fail() that always throws can be typed Nothing and used where an Int is required. Subtyping is not inheritance: implementing an interface creates a subtype without inheriting code, and a Square that extends Rectangle but breaks code that sets only the width is not a true subtype (a Liskov violation). Nominal languages such as Java and Kotlin establish subtypes by declaration, while structural ones such as TypeScript and Go interfaces infer them from shape. How subtyping carries over to generic types is the job of variance.</sub> |
| **대수적 자료형과 패턴 매칭**<br><sub>Algebraic data types and pattern matching</sub> | “원이거나, 사각형이거나, 삼각형”처럼 경우를 나열한 타입(합 타입)을 만들고, 패턴 매칭으로 경우마다 꺼내 처리해요.<br><sub>Define a type by listing its cases (a sum type), such as “a circle, a rectangle or a triangle”, and take values apart with pattern matching.</sub> | 각 경우는 자기 데이터를 들고 다니고(Circle(r), Rect(w, h)), match로 경우를 나눠 꺼내요. 컴파일러가 빠진 경우를 잡아 주는 빠짐 검사 덕분에 새 경우를 추가하면 고칠 곳이 모두 드러나요. null 대신 Option<T> = Some(x) \| None을 쓰면 빈 값 처리를 강제할 수 있어요. 구조체 같은 곱 타입과 합 타입을 합쳐 대수적 자료형이라고 불러요.<br><sub>Each case carries its own data (Circle(r), Rect(w, h)), and match splits on the case. Exhaustiveness checking makes the compiler flag missing cases, so adding a case reveals every place to update. Option<T> = Some(x) \| None replaces null and forces you to handle absence. Product types (structs) plus sum types make algebraic data types, found in Rust, Swift, Kotlin sealed classes, TypeScript discriminated unions and Haskell.</sub> |
| **패턴 매칭**<br><sub>Pattern matching</sub> | 값의 모양을 위에서부터 패턴과 맞춰 보고, 맞은 갈래에서 안의 값을 꺼내 이름에 묶어요. 빠진 경우는 컴파일러가 잡아 줘요.<br><sub>Tries a value against patterns from the top, pulling inner values out into names in the arm that matches. The compiler catches missing cases.</sub> | match는 갈래를 위에서부터 차례로 맞춰 보고 처음 맞는 갈래 하나만 실행해요. Rect(3, 4)는 Circle(r) 갈래 둘을 지나 Rect(w, h)에 맞으며 w = 3, h = 4가 묶여 12를 계산해요. 패턴은 중첩할 수 있어서 Some(Point { x: 0, y })는 “Some으로 감싸져 있고, 안의 Point의 x가 0이면 y를 꺼내라”를 한 번에 표현해요. 상수 비교, 이름 묶기, \_(아무거나), 범위, 여러 패턴의 \|, 남은 부분을 받는 .. 같은 패턴을 섞어 써요. 순서가 의미를 정하기 때문에 넓은 패턴을 먼저 쓰면 아래의 좁은 갈래는 절대 실행되지 않고, 컴파일러가 도달 불가 경고를 내요. if 가드는 모양이 맞은 뒤 조건을 하나 더 검사해요. 합 타입에 대한 match는 빠짐 검사를 받아서, Tri 갈래를 지우면 “Tri가 처리되지 않았다”는 컴파일 오류가 나요. 컴파일러는 갈래를 결정 트리나 점프 테이블로 바꿔 효율적으로 실행해요. Rust·Scala·Haskell·OCaml의 match, Python 3.10의 match 문, Java 21과 C#의 switch 패턴이 있고, if-else 사슬과 instanceof 캐스팅을 대신해 실수를 컴파일 시간에 잡아 줘요.<br><sub>A match tries its arms from the top and runs only the first that fits. Rect(3, 4) skips both Circle(r) arms and matches Rect(w, h), binding w = 3 and h = 4 to compute 12. Patterns nest, so Some(Point { x: 0, y }) says in one go “wrapped in Some, with a Point whose x is 0; pull out y”. Literal checks, name bindings, \_ (anything), ranges, alternatives with \| and .. for the rest can be mixed. Because order defines meaning, a broad pattern placed first makes narrower arms below it unreachable, and the compiler warns. An if guard adds one more condition after the shape matches. Matches over sum types are checked for exhaustiveness: delete the Tri arm and compilation fails with “Tri not covered”. Compilers turn the arms into decision trees or jump tables for efficient dispatch. Rust, Scala, Haskell and OCaml have match, Python 3.10 added a match statement, and Java 21 and C# offer switch patterns; all replace if-else chains and instanceof casts so mistakes surface at compile time.</sub> |
| **명목적 타입과 구조적 타입**<br><sub>Nominal vs structural typing</sub> | 타입이 맞는지를 이름과 선언으로 판단하면 명목적, 필드·메서드의 모양으로 판단하면 구조적 타입이에요.<br><sub>Nominal typing decides compatibility by names and declarations; structural typing by the shape of fields and methods.</sub> | Java·C#은 모양이 같아도 implements를 선언해야 하지만, TypeScript는 필요한 필드만 있으면 통과하고 Go는 메서드만 맞으면 인터페이스를 구현한 것으로 봐요. Python·Ruby의 덕 타이핑은 같은 판단을 실행 중에 해요. 명목적은 의도를 드러내 우연한 일치를 막고, 구조적은 유연해요. TS에서는 브랜드 타입으로 명목성을 흉내 내요.<br><sub>Java and C# require an explicit implements even when shapes match, while TypeScript accepts any value with the needed fields and Go treats matching methods as implementing an interface. Duck typing in Python and Ruby makes the same judgment at run time. Nominal typing states intent and blocks accidental matches; structural typing is flexible. TypeScript emulates nominal types with branded types.</sub> |
| **트레잇·인터페이스·타입 클래스**<br><sub>Traits, interfaces and type classes</sub> | 타입이 “무엇을 할 수 있는지”를 동작의 계약으로 정의하고, 타입마다 따로 구현을 붙여요. 상속 없이 능력을 조합해요.<br><sub>Define what a type can do as a behavior contract and attach implementations per type, combining capabilities without inheritance.</sub> | 트레잇은 필요한 메서드 목록과 기본 구현을 담고, impl Describe for Point처럼 타입마다 구현을 붙여요. 이미 있는 타입(i32)에도 나중에 붙일 수 있고, 제네릭 함수는 T: Describe처럼 트레잇을 조건으로 받아요. 상속이 “무엇인가(is-a)”를 계층에 묶는다면 트레잇은 “무엇을 할 수 있나”를 따로 붙여 다이아몬드 문제를 피해요. Rust trait, Haskell type class, Swift protocol, Go·Java interface가 이 계열이에요.<br><sub>A trait lists required methods plus default implementations, and impl Describe for Point attaches one per type, even to existing types like i32. Generic functions take traits as bounds, as in T: Describe. Where inheritance ties “is-a” into a hierarchy, traits attach “can-do” separately and avoid the diamond problem. Rust traits, Haskell type classes, Swift protocols and Go and Java interfaces belong to this family.</sub> |

## 메모리, 스코프, 클로저 · Memory, scope and closures

변수가 어디에 살고 언제 사라지는지에 대한 규칙이에요.  
*Rules for where variables live and when they disappear.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **스택과 힙**<br><sub>Stack vs heap</sub> | 함수 호출마다 쌓이는 스택에는 지역 변수와 참조가, 힙에는 객체가 저장돼요. 스택은 자동으로 정리되고 힙은 GC나 직접 해제가 필요해요.<br><sub>Each call pushes a stack frame of locals and references; objects live on the heap. The stack cleans itself; the heap needs GC or manual freeing.</sub> | 재귀가 깊으면 스택이 넘치고, 힙 객체를 계속 붙잡으면 메모리 누수가 생겨요.<br><sub>Deep recursion overflows the stack; holding onto heap objects leaks memory.</sub> |
| **값 전달 vs 참조 전달**<br><sub>Pass by value vs reference</sub> | 숫자 같은 원시값은 복사되어 전달되고, 객체·배열은 같은 객체를 가리키는 참조가 전달돼요.<br><sub>Primitives like numbers are copied; objects and arrays are passed as references to the same object.</sub> | 함수 안에서 인자로 받은 배열을 고치면 호출한 쪽도 바뀌어요. React 상태를 직접 수정하면 안 되는 이유예요.<br><sub>Mutating an array argument changes the caller’s array too, which is why React state must not be mutated.</sub> |
| **가비지 컬렉션**<br><sub>Garbage collection</sub> | 루트(전역·스택)에서 닿을 수 있는 객체를 표시하고, 닿지 않는 객체를 자동으로 해제해요.<br><sub>Marks objects reachable from roots (globals, stack) and automatically frees the rest.</sub> | GC 멈춤이 응답 지연 튐의 원인이 되기도 해요. 큰 캐시·전역 맵·해제 안 한 리스너가 대표적인 누수예요.<br><sub>GC pauses can cause latency spikes. Big caches, global maps and forgotten listeners are classic leaks.</sub> |
| **참조 카운팅**<br><sub>Reference counting</sub> | 객체마다 가리키는 곳의 수를 세서 0이 되면 바로 해제해요. 서로를 가리키는 순환은 0이 안 돼서 새요.<br><sub>Each object counts its references and is freed when the count reaches zero; cycles never reach zero and leak.</sub> | Swift(ARC)·Python·C++ shared\_ptr이 이 방식이에요. 델리게이트·부모 참조는 weak로 두세요.<br><sub>Swift ARC, Python and C++ shared\_ptr use it. Make delegate and parent references weak.</sub> |
| **스코프**<br><sub>Scope</sub> | 변수를 찾을 수 있는 범위예요. 코드에 쓰인 위치로 정해지고, 안쪽에서 바깥쪽 순서로 찾아요.<br><sub>Where a variable can be seen, decided by where it is written and searched from inner to outer scopes.</sub> | let·const의 블록 스코프를 쓰고 var는 피하세요. 같은 이름을 안쪽에 다시 선언하면 바깥 변수가 가려져요(섀도잉).<br><sub>Prefer block-scoped let/const over var. Redeclaring a name inside hides the outer one (shadowing).</sub> |
| **클로저**<br><sub>Closure</sub> | 함수가 만들어질 때의 주변 변수를 기억해서, 바깥 함수가 끝난 뒤에도 그 변수를 쓸 수 있어요.<br><sub>A function remembers the variables around it when created and can use them after the outer function has returned.</sub> | 비공개 상태, 콜백, React 훅이 클로저예요. 반복문 안의 비동기 콜백이 마지막 값만 보는 버그도 클로저 때문이에요.<br><sub>Private state, callbacks and React hooks are closures; so is the classic bug where loop callbacks all see the last value.</sub> |
| **소유권과 빌림**<br><sub>Ownership and borrowing</sub> | 값마다 주인이 하나뿐이고, 다른 곳은 값을 “빌려” 써요. 규칙을 컴파일러가 검사해 GC 없이 메모리 안전성을 얻어요 (Rust).<br><sub>Every value has exactly one owner and others “borrow” it; the compiler enforces the rules, giving memory safety without a garbage collector (Rust).</sub> | 대입하면 소유권이 옮겨 가서 옛 변수는 더 쓸 수 없고, 주인이 스코프를 벗어나면 값이 자동으로 해제돼요. 읽기 빌림(&)은 여러 개가 동시에 가능하지만, 쓰기 빌림(&mut)은 혼자만 가능해요. 빌림 검사기가 이 규칙으로 댕글링 포인터, 이중 해제, 데이터 경쟁을 컴파일 단계에서 막아요.<br><sub>Assignment moves ownership, so the old variable becomes unusable, and a value is freed automatically when its owner leaves scope. Many shared borrows (&) may coexist, but a mutable borrow (&mut) must be alone. The borrow checker uses these rules to reject dangling pointers, double frees and data races at compile time.</sub> |
| **RAII와 결정적 해제**<br><sub>RAII and deterministic cleanup</sub> | 자원(파일, 락, 연결)의 수명을 객체의 수명에 묶어서, 스코프를 벗어나는 순간 자동으로 정리되게 해요.<br><sub>Tie a resource’s lifetime (file, lock, connection) to an object’s lifetime, so it is released automatically when the scope ends.</sub> | 파일을 직접 열고 닫으면 일찍 return하거나 예외가 날 때 close()를 건너뛰어 누수가 생겨요. RAII는 생성자에서 자원을 얻고 소멸자에서 놓아, 예외로 빠져나가도 스택을 풀며 소멸자가 불려요. C++ 소멸자, Rust Drop, Python with, C# using, Java try-with-resources, Go defer가 같은 목적이고, GC가 언제 돌지 모르는 자원에 꼭 필요해요.<br><sub>Opening and closing a file by hand leaks it whenever an early return or exception skips close(). RAII acquires the resource in a constructor and releases it in a destructor, which still runs while the stack unwinds after an exception. C++ destructors, Rust Drop, Python with, C# using, Java try-with-resources and Go defer serve the same purpose, essential for resources whose release can’t wait for an unpredictable GC.</sub> |
| **꼬리 호출 최적화**<br><sub>Tail-call optimization</sub> | 함수의 마지막 동작이 다른 함수 호출이면, 지금 프레임을 버리고 재사용할 수 있어요. 재귀가 반복문처럼 스택을 쓰지 않아요.<br><sub>When a function’s last action is a call, the current frame can be discarded and reused, so recursion runs in constant stack like a loop.</sub> | n \* fact(n − 1)은 호출 뒤 곱셈이 남아 프레임이 n개 쌓이고 깊으면 스택 오버플로가 나요. 누적값을 인자로 넘기는 fact(n − 1, n \* acc)는 호출이 마지막 동작이라 컴파일러가 점프로 바꿔 프레임 하나로 끝내요. Scheme은 이를 보장하지만 Python·Java는 하지 않아서 반복문으로 바꾸거나 트램펄린 기법을 써요.<br><sub>n \* fact(n − 1) still has a multiply pending after the call, so n frames pile up and deep inputs overflow the stack. Passing an accumulator, fact(n − 1, n \* acc), makes the call the final action, so the compiler turns it into a jump within one frame. Scheme guarantees this, but Python and Java don’t, so code there is rewritten as loops or uses trampolines.</sub> |

## 비동기와 예외 처리 · Asynchrony and exceptions

기다리는 일과 실패하는 일을 다루는 방법이에요.  
*Handling work that waits and work that fails.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **콜백 → Promise → async/await**<br><sub>Callbacks → Promises → async/await</sub> | 비동기 작업을 콜백으로 이으면 중첩이 깊어지고, Promise는 체인으로 펴고, async/await는 동기 코드처럼 읽히게 해요.<br><sub>Chaining async work with callbacks nests deeply; promises flatten it into chains; async/await reads like synchronous code.</sub> | await를 반복문에서 하나씩 쓰면 순차 실행돼 느려요. 독립적인 요청은 Promise.all로 동시에 보내고, 에러는 try/catch로 잡으세요.<br><sub>Awaiting in a loop runs requests one by one; send independent ones together with Promise.all and catch errors with try/catch.</sub> |
| **스레드 vs 코루틴**<br><sub>Threads vs coroutines</sub> | 스레드는 OS가 강제로 번갈아 실행하는 무거운 실행 단위이고, 코루틴은 스스로 양보하며 번갈아 실행되는 가벼운 단위예요.<br><sub>Threads are heavy units the OS preempts; coroutines are light units that take turns by yielding voluntarily.</sub> | 동시 연결이 많은 서버는 코루틴(Go, Kotlin, Java 가상 스레드)으로 적은 자원에 많은 작업을 처리해요.<br><sub>Servers with many connections use coroutines (Go, Kotlin, Java virtual threads) to handle lots of work cheaply.</sub> |
| **예외 처리**<br><sub>Exception handling</sub> | 예외가 던져지면 catch를 만날 때까지 호출 스택을 거슬러 올라가며 프레임을 정리해요(스택 되감기).<br><sub>A thrown exception unwinds the call stack, frame by frame, until a catch handles it.</sub> | 예외를 잡고 아무것도 안 하면 버그가 숨어요. 처리할 수 있는 곳에서 잡고, 나머지는 로깅 후 상위로 보내세요. finally로 자원을 정리하세요.<br><sub>Catching and ignoring hides bugs. Catch where you can act, log and rethrow otherwise, and clean up in finally.</sub> |
| **제너레이터와 이터레이터**<br><sub>Generators and iterators</sub> | yield로 값을 하나 내주고 그 자리에 멈췄다가, 다음 요청이 오면 이어서 실행하는 함수예요. 무한한 수열도 필요한 만큼만 만들어요.<br><sub>A function that hands out a value with yield, pauses there, and resumes on the next request; even infinite sequences are produced only as needed.</sub> | 제너레이터는 지역 변수와 “다음에 실행할 줄”을 저장해 두고 next()마다 다음 yield까지만 실행해요. 이터레이터 규약을 따라 for 문에 바로 쓸 수 있고, 큰 파일을 한 줄씩 처리하거나 지연 파이프라인을 만들 때 메모리를 아껴요. Python yield, JS function\*, C# yield return이 대표적이고, async/await도 이 원리 위에 세워졌어요.<br><sub>A generator saves its local variables and “the next line to run”, executing only up to the next yield on each next(). It follows the iterator protocol, so it plugs straight into for loops, and it saves memory when processing huge files line by line or building lazy pipelines. Python yield, JS function\* and C# yield return are common forms, and async/await is built on the same idea.</sub> |
| **채널(CSP)과 액터 모델**<br><sub>Channels (CSP) and the actor model</sub> | 공유 메모리와 락 대신 메시지를 주고받아 협력하는 동시성 모델이에요. Go는 채널, Erlang·Akka는 액터의 우편함을 써요.<br><sub>Concurrency models that cooperate by passing messages instead of sharing memory under locks: Go uses channels, Erlang and Akka use actor mailboxes.</sub> | Go의 고루틴은 채널로 값을 주고받고, 버퍼 없는 채널은 보내는 쪽과 받는 쪽이 만날 때까지 기다려 동기화도 해 줘요. 액터는 자기 상태를 혼자 소유하고 우편함의 메시지를 하나씩 처리해서 락이 필요 없어요. Erlang은 죽은 액터를 감독자가 다시 띄우는 “let it crash” 철학으로 높은 가용성을 얻어요. 대신 교착 상태와 메시지 폭주는 여전히 조심해야 해요.<br><sub>Goroutines exchange values over channels, and an unbuffered channel makes sender and receiver meet, synchronizing them. An actor owns its state alone and processes mailbox messages one at a time, so it needs no locks. Erlang’s supervisors restart crashed actors (“let it crash”), a key to its famous availability. Deadlocks and message floods still need care.</sub> |
| **액터 모델**<br><sub>The actor model</sub> | 상태를 혼자 가진 액터들이 우편함을 통해 비동기 메시지만 주고받는 동시성 모델이에요. 메시지를 하나씩 처리하니 락이 필요 없어요.<br><sub>A concurrency model in which actors, each owning its state, exchange only asynchronous messages through mailboxes. Handling one message at a time removes the need for locks.</sub> | 액터는 자기 상태를 혼자 소유하는 작은 계산 단위예요. 다른 액터는 그 상태를 직접 읽거나 바꿀 수 없고, 메시지를 보내 부탁할 수만 있어요. 메시지는 액터의 우편함에 쌓이고 액터는 하나씩 순서대로 처리하므로, 계좌 액터에 +100, −30, +50이 동시에 도착해도 잔액은 락 없이 정확히 220이 돼요. 메시지를 처리하면서 액터가 할 수 있는 일은 세 가지뿐이에요. 다른 액터에게 메시지 보내기, 새 액터 만들기, 다음 메시지를 처리할 동작 바꾸기. 메시지는 비동기라 보내는 쪽은 기다리지 않고, 같은 주소 방식으로 다른 머신의 액터에도 보낼 수 있어서(위치 투명성) 분산 시스템으로 자연스럽게 커져요. 실패는 감독자 액터가 맡아요. 일꾼이 예외로 죽으면 감독자가 정해진 전략대로 다시 띄우므로, 곳곳에 방어 코드를 넣기보다 “죽게 두고 재시작(let it crash)”하는 설계가 가능해요. Erlang·Elixir(WhatsApp, 통신 장비), Akka, Microsoft Orleans가 대표적이에요. 주의할 점은 우편함이 무한히 쌓이지 않게 하는 배압, 서로의 응답을 기다리는 교착, 그리고 메시지 순서는 같은 송신자–수신자 사이에서만 보장된다는 점이에요.<br><sub>An actor is a small unit of computation that alone owns its state: no one else can read or change it directly, only ask by sending messages. Messages queue in the actor’s mailbox and are processed one at a time, so even if +100, −30 and +50 arrive at an account actor together, the balance comes out at exactly 220 without locks. While handling a message an actor can do only three things: send messages, create new actors and decide how to handle the next message. Sending is asynchronous, and actors on other machines are addressed the same way (location transparency), so systems grow naturally into distributed ones. Failures go to supervisor actors: when a worker crashes, its supervisor restarts it according to a strategy, enabling a “let it crash” design instead of defensive code everywhere. Erlang and Elixir (WhatsApp, telecom equipment), Akka and Microsoft Orleans are the best-known implementations. Watch for unbounded mailboxes (add backpressure), actors deadlocked waiting on each other’s replies, and the fact that ordering is guaranteed only between one sender and one receiver.</sub> |
| **예외 vs 결과 타입**<br><sub>Exceptions vs result types</sub> | 오류를 보이지 않는 탈출구(예외)로 던질지, 반환 값(Result)으로 돌려줄지의 선택이에요.<br><sub>Should errors escape through an invisible exit (exceptions) or come back as values (results)?</sub> | 예외는 코드가 짧지만 시그니처만 봐서는 어디서 튈지 알 수 없어요. Rust의 Result<T, E>나 Haskell의 Either는 실패가 타입에 드러나고, 처리하지 않으면 컴파일러가 경고해요. ? 연산자는 실패하면 그 자리에서 오류를 그대로 돌려줘 간결하게 전파하고, Go는 (값, err) 두 개를 돌려주고 매번 검사해요. Swift는 던지는 함수에 throws와 try 표시를 강제해 중간을 택했어요.<br><sub>Exceptions keep code short, but signatures don’t reveal what may throw. Rust’s Result<T, E> and Haskell’s Either put failure in the type, and ignoring it draws a compiler warning. The ? operator returns the error on the spot for concise propagation, while Go returns (value, err) and checks every time. Swift takes a middle road by requiring throws and try markers.</sub> |
