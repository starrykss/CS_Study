## 데이터 파이프라인 기초 · Pipeline foundations

데이터를 옮기고, 바꾸고, 정해진 때에 안전하게 다시 돌리는 법이에요.  
*Moving and transforming data, and rerunning it safely on schedule.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **ETL과 ELT**<br><sub>ETL vs ELT</sub> | 여러 원천에서 데이터를 뽑아(Extract) 바꾸고(Transform) 싣는(Load) 일이에요. 요즘은 먼저 싣고 웨어하우스 안에서 바꾸는 ELT가 대세예요.<br><sub>Extract data from many sources, transform it and load it somewhere useful. Today the norm is ELT: load first, then transform inside the warehouse.</sub> | ETL은 별도 서버에서 정제·조인·집계를 끝낸 결과만 웨어하우스에 넣어서, 새 질문이 생기면 원본부터 다시 추출해야 해요. ELT는 원본을 그대로 적재한 뒤 SQL로 단계적으로 변환해요(원본 → 정제 → 마트, 메달리온 구조의 bronze·silver·gold). 싼 오브젝트 스토리지와 강력한 클라우드 웨어하우스 덕분이고, dbt가 SQL 변환을 버전 관리·테스트하는 코드로 다뤄요. 개인정보처럼 적재 전에 지워야 하는 데이터는 여전히 ETL로 처리해요.<br><sub>ETL finishes cleaning, joining and aggregating on a separate server and loads only the result, so a new question means extracting again. ELT lands the raw data as-is and transforms it in stages with SQL (raw → staging → marts, the bronze/silver/gold medallion layers). Cheap object storage and powerful cloud warehouses made this possible, and dbt treats SQL transforms as versioned, tested code. Data that must be scrubbed before landing, such as PII, still goes through ETL.</sub> |
| **배치와 스트림 처리**<br><sub>Batch and stream processing</sub> | 배치는 데이터를 모아 한 번에 처리하고, 스트림은 들어오는 즉시 하나씩 처리해요. 처리량과 지연을 맞바꿔요.<br><sub>Batch gathers data and processes it in one go; streaming processes each event as it arrives. It is a trade of throughput for latency.</sub> | 배치(Spark, dbt)는 하루치를 모아 밤에 돌려 처리량이 크고 다시 돌리기 쉽지만 결과가 몇 시간에서 하루 늦어요. 스트림(Flink, Kafka Streams)은 초 단위로 결과를 내지만 상태 관리, 늦게 온 데이터, 순서 처리가 어려워요. 몇 초씩 묶어 처리하는 마이크로 배치(Spark Structured Streaming)는 그 중간이에요. 람다 아키텍처는 배치와 스트림을 함께 두고, 카파 아키텍처는 스트림 하나에 재처리를 맡겨요.<br><sub>Batch jobs (Spark, dbt) run a day’s worth at night: high throughput and easy to rerun, but results arrive hours to a day late. Stream processors (Flink, Kafka Streams) answer in seconds but must handle state, late data and ordering. Micro-batching (Spark Structured Streaming) sits in between. A Lambda architecture runs both paths side by side; a Kappa architecture uses one stream and replays it for reprocessing.</sub> |
| **워크플로 오케스트레이션**<br><sub>Workflow orchestration</sub> | 작업들과 그 의존 관계를 DAG(방향 비순환 그래프)로 정의하고, 정해진 시간에 순서대로 실행·재시도·알림을 맡겨요.<br><sub>Define tasks and their dependencies as a DAG (directed acyclic graph) and let the orchestrator run, retry and alert on schedule.</sub> | Airflow 같은 오케스트레이터는 앞 작업이 끝난 작업부터 실행하고 서로 무관한 작업은 병렬로 돌려요. 실패하면 간격을 두고 재시도하고, 품질 검사에 걸리면 하류 작업을 멈춰 틀린 숫자가 대시보드에 나가지 않게 해요. 버그를 고친 뒤 과거 날짜를 다시 돌리는 백필도 오케스트레이터의 일이에요. 실제 무거운 계산은 Spark나 웨어하우스의 SQL이 하고, 오케스트레이터는 순서와 상태를 관리해요.<br><sub>An orchestrator such as Airflow starts a task once its upstreams succeed and runs independent tasks in parallel. Failures are retried after a delay, and a failed quality check halts downstream tasks so bad numbers never reach a dashboard. Backfills, rerunning past dates after a fix, are its job too. The heavy computation happens in Spark or warehouse SQL; the orchestrator manages order and state. Dagster, Prefect and Argo Workflows are alternatives.</sub> |
| **멱등한 파이프라인**<br><sub>Idempotent pipelines</sub> | 같은 작업을 몇 번 다시 돌려도 결과가 똑같도록 만들어요. 재시도와 백필이 흔한 데이터 파이프라인의 기본기예요.<br><sub>Make every job produce the same result no matter how many times it reruns: the foundation of pipelines where retries and backfills are routine.</sub> | 단순히 INSERT로 덧붙이면 실패 후 재시도할 때마다 중복이 쌓여요. 대신 날짜 파티션을 통째로 덮어쓰거나(INSERT OVERWRITE), 키로 맞춰 합치는 MERGE(업서트)를 써요. 작업은 now() 대신 실행 날짜를 인자로 받아야 언제 다시 돌려도 같은 결과가 나와요. 수학적으로는 f(f(x)) = f(x)인 성질이에요.<br><sub>A plain INSERT appends duplicates each time a failed job is retried. Instead, overwrite the whole date partition (INSERT OVERWRITE) or MERGE (upsert) on a key. Jobs should take the run date as a parameter instead of calling now(), so a rerun at any time yields the same output. Mathematically it is the property f(f(x)) = f(x).</sub> |
| **변경 데이터 캡처 (CDC)**<br><sub>Change data capture (CDC)</sub> | 데이터베이스의 트랜잭션 로그를 읽어 삽입·수정·삭제를 이벤트로 흘려보내요. 원본 DB에 부담 없이 거의 실시간으로 복제해요.<br><sub>Read a database’s transaction log and stream every insert, update and delete as events: near-real-time replication with little load on the source.</sub> | DB는 모든 변경을 먼저 WAL(PostgreSQL)이나 binlog(MySQL)에 적어요. Debezium 같은 CDC 커넥터가 복제본처럼 이 로그를 읽어 카프카 토픽으로 보내고, 웨어하우스·검색 색인·캐시가 각자 반영해요. updated\_at으로 주기적으로 조회하는 방식은 삭제를 못 보고 두 조회 사이의 중간 변경을 놓치며 큰 테이블을 반복해서 훑어요. 서비스 이벤트를 안전하게 내보내는 아웃박스 패턴과도 함께 쓰여요.<br><sub>Databases write every change to a log first, the WAL in PostgreSQL or the binlog in MySQL. A CDC connector such as Debezium reads that log like a replica and publishes to Kafka topics, where warehouses, search indexes and caches apply the changes. Polling with updated\_at misses deletes, loses intermediate changes between polls and rescans large tables. CDC is often paired with the outbox pattern for publishing service events safely.</sub> |
| **백필과 재처리**<br><sub>Backfills and reprocessing</sub> | 지난 기간의 파이프라인을 다시 돌려 잘못 만든 데이터를 고치거나 새로 추가한 열을 채우는 일이에요. 날짜 파티션과 덮어쓰기가 있어야 안전해요.<br><sub>Rerunning a pipeline over past periods to fix data built wrongly or to fill in newly added columns; date partitions and overwrites make it safe.</sub> | 정제 단계에 버그가 있었다면 11-04~11-07 파티션이 틀렸고, 그 위에서 만든 리포트까지 오염돼요. 코드를 고친 뒤 그 기간만 지정해 다시 실행하는데(airflow dags backfill -s … -e …), 의존 순서(정제 → 리포트)를 지키고 동시 실행 수를 제한해 원본 시스템에 부담을 주지 않아요. 각 작업은 INSERT OVERWRITE … PARTITION처럼 파티션을 통째로 덮어써야 여러 번 다시 돌려도 중복 없이 같은 결과가 나와요(멱등성). 새 열을 추가했을 때 과거 데이터를 채우는 것도 백필이에요.<br><sub>If the clean step had a bug, partitions 11-04 to 11-07 are wrong, and so are the reports built on them. After fixing the code you rerun just that range (airflow dags backfill -s … -e …), respecting dependency order (clean → report) and limiting concurrency so sources aren’t overloaded. Each task should overwrite whole partitions, as INSERT OVERWRITE … PARTITION does, so reruns give the same result without duplicates (idempotency). Populating history for a newly added column is a backfill too.</sub> |

## 저장과 포맷 · Storage and formats

분석에 맞게 데이터를 저장하고 모델링하는 법이에요.  
*Storing and modeling data for analytics.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **OLTP와 OLAP**<br><sub>OLTP and OLAP</sub> | 서비스용 DB(OLTP)는 행 하나를 빠르게 읽고 쓰고, 분석용 DB(OLAP)는 수백만 행의 몇 개 열을 훑어 집계해요.<br><sub>Service databases (OLTP) read and write single rows fast; analytics databases (OLAP) scan a few columns across millions of rows.</sub> | OLTP(MySQL, PostgreSQL)는 행 단위로 저장해 주문 하나를 넣고 고치는 짧은 트랜잭션을 초당 수천 번 처리해요. OLAP(BigQuery, Snowflake, ClickHouse, Redshift)는 열 단위로 저장해 필요한 열만 연속으로 읽고, 비슷한 값이 모여 압축도 잘 돼요. 분석 쿼리가 서비스를 느리게 만들지 않도록 둘을 나누고, CDC나 배치로 데이터를 옮겨요.<br><sub>OLTP systems (MySQL, PostgreSQL) store data by row and handle thousands of short transactions per second, each touching one order. OLAP systems (BigQuery, Snowflake, ClickHouse, Redshift) store data by column, read only the needed columns contiguously and compress well because similar values sit together. The two are kept apart so analytics never slows the product, with CDC or batch jobs moving data between them.</sub> |
| **열 지향 파일 포맷 (Parquet)**<br><sub>Columnar files (Parquet)</sub> | 파케이 파일은 행 그룹마다 열 조각으로 저장하고, 끝의 푸터에 통계를 담아 필요한 부분만 읽게 해요.<br><sub>Parquet stores each row group as column chunks and keeps statistics in a footer, so readers fetch only what they need.</sub> | 리더는 푸터의 행 그룹별 min/max 통계로 조건에 맞을 수 없는 행 그룹을 통째로 건너뛰고(조건 내려보내기), 남은 곳에서도 필요한 열만 읽어요(열 고르기). 열마다 사전 인코딩, RLE(같은 값 연속을 개수로), 델타 인코딩을 한 뒤 Snappy나 Zstd로 압축해요. Spark, Trino, DuckDB, BigQuery가 모두 읽는 사실상 표준이고, ORC도 같은 원리예요.<br><sub>Using the footer’s per-row-group min/max statistics, a reader skips row groups that cannot match the filter (predicate pushdown), then reads only the needed columns from the rest (column pruning). Each column is dictionary-encoded, run-length encoded and delta-encoded before Snappy or Zstd compression. It is the de facto standard read by Spark, Trino, DuckDB and BigQuery; ORC works the same way.</sub> |
| **파티셔닝과 프루닝**<br><sub>Partitioning and pruning</sub> | 데이터를 날짜 같은 열 값별 폴더로 나눠 저장하면, 조건에 맞는 폴더만 읽어서 스캔 양이 크게 줄어요.<br><sub>Splitting data into folders by a column such as date lets queries read only the folders that match, slashing the bytes scanned.</sub> | dt=2026-11-10/처럼 하이브 스타일로 나누면 WHERE dt = …인 쿼리는 그 폴더만 읽어요(파티션 프루닝). 하지만 시간·국가까지 너무 잘게 나누면 1MB짜리 작은 파일이 수만 개 생겨 목록 조회와 파일 열기 비용이 일을 압도해요. 주기적으로 작은 파일을 수백 MB 단위로 합치고(compaction), 자주 거르는 열로만 나눠요. Iceberg의 숨은 파티셔닝, Z-order·클러스터링은 파일 안의 정렬까지 다뤄요.<br><sub>With Hive-style folders like dt=2026-11-10/, a query filtering on dt reads only that folder (partition pruning). Partition too finely, by hour and country, and tens of thousands of 1 MB files appear, so listing and opening files dominate the work. Compaction periodically merges small files into a few hundred MB each, and partitions should follow the columns you filter on most. Iceberg’s hidden partitioning, Z-ordering and clustering go further and sort data within files.</sub> |
| **레이크·웨어하우스·레이크하우스**<br><sub>Lake, warehouse and lakehouse</sub> | 데이터 레이크는 오브젝트 스토리지에 쌓인 파일이고, 테이블 포맷이 그 위에 트랜잭션과 스냅숏을 얹으면 레이크하우스가 돼요.<br><sub>A data lake is files in object storage; add a table format with transactions and snapshots on top and it becomes a lakehouse.</sub> | 레이크(S3, GCS)는 싸고 어떤 형식이든 담지만, 그대로는 반쯤 쓴 파일이 보이고 스키마도 없어요. Apache Iceberg, Delta Lake, Hudi는 “지금 테이블 = 이 파일들”이라는 스냅숏을 기록하고, 쓰기는 새 파일과 새 스냅숏을 만든 뒤 포인터를 원자적으로 바꿔요. 그래서 읽는 쪽은 항상 일관된 모습을 보고, 옛 스냅숏으로 과거를 조회하는 타임 트래블도 돼요. 웨어하우스(Snowflake, BigQuery)의 기능을 레이크에서 Spark·Trino·Flink가 함께 쓰는 구조예요.<br><sub>Lakes (S3, GCS) are cheap and hold any format, but on their own expose half-written files and enforce no schema. Apache Iceberg, Delta Lake and Hudi record snapshots, “the table is these files”, and each write adds new files and a new snapshot before atomically swapping a pointer. Readers therefore always see a consistent table, and time travel queries old snapshots. The result brings warehouse features (Snowflake, BigQuery) to the lake, shared by Spark, Trino and Flink.</sub> |
| **테이블 포맷 (Iceberg)**<br><sub>Table formats (Iceberg)</sub> | 오브젝트 스토리지의 파일 위에 메타데이터 트리를 얹어, 포인터 하나를 원자적으로 바꾸는 것으로 커밋하는 테이블 규약이에요.<br><sub>A convention that puts a metadata tree over files in object storage and commits by atomically swapping a single pointer.</sub> | Apache Iceberg 같은 테이블 포맷은 “지금 이 테이블은 이 파일들이다”를 트리로 기록해요. 카탈로그가 현재 메타데이터 파일(v3.metadata.json)을 가리키고, 메타데이터는 스냅숏의 매니페스트 목록을, 매니페스트는 실제 Parquet 데이터 파일과 그 통계(열별 최솟값·최댓값)를 가리켜요. 쓰기는 기존 파일을 절대 고치지 않아요. 새 데이터 파일과 새 매니페스트, 새 메타데이터(v4)를 모두 써 둔 뒤 카탈로그 포인터를 v3 → v4로 비교 후 교체(CAS)하는 한 번의 원자적 연산이 곧 커밋이에요. 그래서 읽던 쿼리는 v3를 끝까지 일관되게 보고, 새 쿼리는 v4를 봐요. 두 작업이 동시에 v3를 기준으로 커밋하면 먼저 바꾼 쪽이 이기고, 진 쪽은 v4를 다시 읽어 겹치는 파일이 없으면 v5로 재시도하는 낙관적 동시성이에요. 옛 스냅숏이 남아 있으니 FOR TIMESTAMP AS OF로 과거 시점을 조회하는 타임 트래블이 되고, expire\_snapshots로 오래된 스냅숏과 파일을 지우고 rewrite\_data\_files로 작은 파일을 합쳐요. 열을 이름이 아닌 ID로 추적해 이름 변경이 안전하고, 파티션 값을 열에서 계산하는 숨은 파티셔닝도 지원해요. Delta Lake와 Hudi도 같은 원리이고, Spark·Trino·Flink·Snowflake가 같은 테이블을 함께 써요.<br><sub>A table format such as Apache Iceberg records “the table is these files” as a tree: the catalog points at the current metadata file (v3.metadata.json), the metadata at a snapshot’s manifest list, and manifests at the Parquet data files along with their statistics (per-column min and max). Writes never modify existing files. A writer creates new data files, new manifests and new metadata (v4), and the commit is a single atomic compare-and-swap of the catalog pointer from v3 to v4, so running queries keep a consistent view of v3 while new ones see v4. When two jobs commit concurrently from v3, the first swap wins and the loser rereads v4 and, if no files overlap, retries as v5: optimistic concurrency. Old snapshots enable time travel with FOR TIMESTAMP AS OF, while expire\_snapshots removes old snapshots and files and rewrite\_data\_files compacts small files. Columns are tracked by ID rather than name, making renames safe, and hidden partitioning derives partition values from columns. Delta Lake and Hudi work on the same principle, and Spark, Trino, Flink and Snowflake can all share the same tables.</sub> |
| **스타 스키마와 차원 모델링**<br><sub>Star schemas and dimensional modeling</sub> | 가운데에 측정값을 담은 사실 테이블을, 둘레에 맥락을 설명하는 차원 테이블을 두는 분석용 모델이에요.<br><sub>An analytics model with a fact table of measurements in the middle and dimension tables of context around it.</sub> | 사실 테이블(fact\_sales)은 판매 한 건마다 한 행으로 수량·금액 같은 숫자와 차원 키만 담고, 차원 테이블은 날짜·상품·매장·고객을 설명해요. “카테고리별 월 매출”은 사실 테이블을 두 차원과 조인해 묶으면 돼요. 차원을 더 정규화하면 눈송이(snowflake) 스키마가 되어 저장은 줄지만 조인이 늘어요. 킴볼의 차원 모델링에서 나왔고, 조인이 단순해 BI 도구와 사람이 쓰기 쉬워요.<br><sub>The fact table (fact\_sales) holds one row per sale with numbers such as quantity and amount plus dimension keys; dimension tables describe the date, product, store and customer. “Monthly revenue by category” is a join of the fact table with two dimensions and a group-by. Normalizing dimensions further gives a snowflake schema: less storage, more joins. It comes from Kimball’s dimensional modeling, and its simple joins suit BI tools and people alike.</sub> |
| **천천히 변하는 차원 (SCD)**<br><sub>Slowly changing dimensions</sub> | 고객 주소처럼 가끔 바뀌는 차원 값을 이력과 함께 관리하는 방법이에요. 덮어쓰면 과거 리포트까지 바뀌어요.<br><sub>Ways to track dimension values that change now and then, such as a customer’s address; overwriting rewrites past reports.</sub> | Type 1은 그냥 덮어써서 이력이 사라져요. Type 2는 옛 행에 유효 기간 끝(valid\_to)과 current = N을 적고 새 대리 키로 새 행을 추가해, 매출이 그 시점의 행을 가리키게 해요. 그래서 2025년 매출은 서울, 2026년 매출은 부산으로 정확히 집계돼요. Type 3은 “이전 값” 열 하나만 두는 방식이고, dbt snapshot이 Type 2를 자동으로 관리해 줘요.<br><sub>Type 1 simply overwrites and loses history. Type 2 closes the old row (valid\_to, current = N) and adds a new row with a new surrogate key, so each sale points at the row valid at the time: 2025 sales stay in Seoul and 2026 sales count toward Busan. Type 3 keeps a single “previous value” column. dbt snapshots maintain Type 2 automatically.</sub> |
| **작은 파일 문제와 컴팩션**<br><sub>Small files and compaction</sub> | 데이터 양이 아니라 파일 개수가 쿼리와 저장소를 느리게 만드는 문제예요. 작은 파일을 큰 파일로 합치는 컴팩션으로 해결해요.<br><sub>A problem where the number of files, not the amount of data, slows queries and storage; compaction merges small files into large ones.</sub> | 스트리밍 잡이 1분마다 파일을 쓰면 하루에 2 MB짜리 파일이 1,440개 생겨요. 쿼리 엔진은 파일마다 열고, 목록을 조회하고, 메타데이터와 푸터를 읽어야 해서 실제 데이터를 읽는 시간보다 이 비용이 더 커지고, 오브젝트 스토리지 요청 비용도 늘어요. 컴팩션은 작은 파일들을 512 MB~1 GB 정도로 합쳐 다시 쓰고, 테이블 포맷이 스냅숏을 원자적으로 바꿔 읽는 쪽은 영향을 받지 않아요(Delta OPTIMIZE, Iceberg rewrite\_data\_files). 쓰기 간격을 늘리고, 쓰기 전에 repartition하고, 사용자 ID처럼 너무 잘게 파티션을 나누지 않는 것이 예방책이에요.<br><sub>A streaming job writing a file every minute leaves 1,440 files of 2 MB per day. The query engine must open, list and read metadata and footers for each, so that overhead outweighs reading the data itself, and object-storage request costs climb too. Compaction rewrites the small files into files of roughly 512 MB to 1 GB, and the table format swaps the snapshot atomically so readers are unaffected (Delta OPTIMIZE, Iceberg rewrite\_data\_files). Longer write intervals, repartitioning before writes and avoiding overly fine partitions such as by user ID prevent it.</sub> |

<a id="de-dist"></a>

## 분산 처리 · Distributed processing

수천 대의 서버가 한 작업을 나눠 처리하는 원리예요.  
*How thousands of servers share one job.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **맵리듀스**<br><sub>MapReduce</sub> | 큰 작업을 map(조각마다 동시에 변환)과 reduce(키별로 합치기)로 나눠 수천 대의 서버에서 처리하는 모델이에요.<br><sub>A model that splits huge jobs into map (transform every chunk in parallel) and reduce (combine per key) across thousands of servers.</sub> | 단어 세기라면 map이 조각마다 (단어, 1)을 내보내고, 셔플이 같은 단어를 같은 리듀서로 모으고, reduce가 개수를 더해요. 셔플은 네트워크로 데이터를 크게 옮겨 가장 비싸서, map 쪽에서 미리 합치는 컴바이너로 양을 줄여요. 2004년 구글 논문에서 나와 Hadoop으로 퍼졌고, 중간 결과를 디스크에 써서 느리지만 장애에 튼튼했어요. 지금은 Spark가 같은 모델을 메모리 위에서 더 빠르게 돌려요.<br><sub>For word count, map emits (word, 1) for each chunk, the shuffle routes equal words to the same reducer, and reduce adds them up. The shuffle moves lots of data over the network and is the costliest step, so combiners pre-aggregate on the map side. The model came from Google’s 2004 paper and spread through Hadoop, which wrote intermediate results to disk: slow, but resilient to failures. Spark now runs the same model faster in memory.</sub> |
| **Spark의 실행 모델**<br><sub>How Spark executes</sub> | Spark는 변환을 바로 실행하지 않고 계획으로 쌓았다가, 액션이 오면 셔플을 경계로 단계를 나눠 병렬로 실행해요.<br><sub>Spark doesn’t run transformations immediately; it builds a plan and, when an action arrives, splits it into stages at shuffles and runs them in parallel.</sub> | filter·select 같은 좁은 변환은 파티션끼리 1:1이라 한 단계(stage)에 묶이고, groupBy·join 같은 넓은 변환은 같은 키를 모아야 해서 셔플과 함께 새 단계가 시작돼요. 단계 안에서는 파티션마다 태스크가 실행기(executor)에서 동시에 돌아요. Catalyst 최적화기가 필터를 앞당기고 필요한 열만 읽게 계획을 다시 짜고, 반복해서 쓰는 데이터는 cache()로 메모리에 올려요. 셔플 수를 줄이는 게 성능의 핵심이에요.<br><sub>Narrow transformations such as filter and select map partitions one-to-one and are fused into a single stage; wide ones such as groupBy and join must gather equal keys, so a shuffle starts a new stage. Within a stage, one task per partition runs on the executors at once. The Catalyst optimizer rewrites the plan to push filters down and read only needed columns, and cache() keeps reused data in memory. Cutting shuffles is the key to speed.</sub> |
| **분산 조인 전략**<br><sub>Distributed join strategies</sub> | 여러 서버에 나뉜 테이블을 조인할 땐, 작은 쪽을 모두에게 복사하거나 같은 키끼리 모이도록 셔플해요.<br><sub>To join tables spread over many servers, either copy the small side to everyone or shuffle both so equal keys meet.</sub> | 한쪽이 작으면(Spark 기본 10MB 이하) 통째로 모든 실행기에 보내는 브로드캐스트 조인을 써서 큰 테이블은 움직이지 않아요. 둘 다 크면 키의 해시로 다시 나눠 같은 키를 한 실행기에 모은 뒤 정렬해 병합하는 정렬 병합 조인을 써요. 셔플이 네트워크와 디스크를 많이 써서 조인 비용의 대부분을 차지해요. 옵티마이저는 테이블 통계로 전략을 고르므로 통계가 낡으면 엉뚱한 선택을 해요.<br><sub>If one side is small (under 10 MB by default in Spark), a broadcast join ships it whole to every executor and the big table never moves. When both sides are big, a sort-merge join repartitions both by key hash so matching keys land on the same executor, then sorts and merges them. The shuffle’s network and disk traffic is most of a join’s cost. Optimizers choose using table statistics, so stale statistics lead to poor choices.</sub> |
| **데이터 스큐**<br><sub>Data skew</sub> | 특정 키에 데이터가 몰리면 그 키를 맡은 태스크 하나가 끝나지 않아 전체 작업이 그 하나를 기다려요.<br><sub>When one key holds most of the data, the single task handling it lags and the whole job waits for it.</sub> | null 키나 거대한 고객 하나가 데이터의 대부분을 차지하면 groupBy·join 뒤 한 태스크만 수십 배 오래 걸려요(낙오자). 소금 치기(salting)는 키에 0~N 난수를 붙여 여러 태스크로 나눈 뒤, 부분 결과를 원래 키로 한 번 더 합쳐요. Spark 3의 적응형 쿼리 실행(AQE)은 치우친 조인 파티션을 자동으로 쪼개요. null 키를 미리 걸러 따로 처리하는 것도 흔한 해법이에요.<br><sub>If a null key or one giant customer dominates, one task after a groupBy or join runs dozens of times longer than the rest (a straggler). Salting appends a random 0–N to the key to spread it over several tasks, then combines the partial results by the original key. Spark 3’s adaptive query execution (AQE) splits skewed join partitions automatically. Filtering null keys out and handling them separately is another common fix.</sub> |
| **분산 SQL 엔진**<br><sub>Distributed SQL engines</sub> | 코디네이터가 SQL을 조각으로 나눠 많은 워커에게 맡기고, 워커들이 스토리지의 파일을 동시에 읽어 부분 결과를 합쳐요.<br><sub>A coordinator splits SQL into fragments for many workers, which scan files from storage in parallel and merge their partial results.</sub> | Trino·Presto, BigQuery, Snowflake, Athena가 이 구조(MPP, 대규모 병렬 처리)예요. 워커는 파일 조각을 나눠 스캔하고 각자 부분 집계를 낸 뒤 교환해 최종 결과를 만들어요. 데이터는 오브젝트 스토리지에, 계산은 필요할 때만 띄우는 저장·계산 분리 구조라 워커 수를 따로 늘리고 줄일 수 있어요. 비용과 시간이 스캔한 바이트에 비례하니 파티셔닝과 열 지향 포맷이 곧 돈을 아껴요.<br><sub>Trino/Presto, BigQuery, Snowflake and Athena follow this massively parallel processing (MPP) design. Workers scan their share of file splits, compute partial aggregates, then exchange and combine them into the final answer. Data lives in object storage while compute spins up on demand, so the separation of storage and compute lets workers scale independently. Cost and time track bytes scanned, so partitioning and columnar formats save real money.</sub> |

## 스트림 처리 · Stream processing

끝없이 흐르는 이벤트를 실시간으로 다루는 법이에요.  
*Handling endless event streams in real time.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **로그 기반 메시지 브로커**<br><sub>Log-based message brokers</sub> | Kafka 토픽은 파티션마다 추가만 하는 로그예요. 메시지는 읽어도 지워지지 않고, 소비자는 어디까지 읽었는지(오프셋)만 기록해요.<br><sub>A Kafka topic is an append-only log per partition: reading doesn’t delete messages, and consumers just record how far they have read (offsets).</sub> | 같은 키는 해시로 늘 같은 파티션에 들어가서 키별 순서가 보장돼요. 소비자 그룹은 파티션을 나눠 맡아 병렬로 읽고, 한 소비자가 죽으면 리밸런스로 다른 소비자가 커밋된 오프셋부터 이어 읽어요. 보관 기간 동안 메시지가 남아 있어 다른 그룹이 처음부터 다시 읽거나(재처리) 새 시스템을 붙일 수 있어요. 파티션 수가 그룹 안 최대 병렬도를 정해요.<br><sub>A key always hashes to the same partition, so per-key order is preserved. A consumer group splits partitions among its members to read in parallel, and when one dies a rebalance hands its partitions to another, resuming from the committed offset. Messages stay for the retention period, so another group can replay from the start or a new system can be attached. The partition count caps parallelism within a group. Redpanda, Pulsar and Kinesis are similar.</sub> |
| **스트림의 윈도**<br><sub>Windows on streams</sub> | 끝없는 이벤트 흐름을 시간 구간(윈도)으로 묶어야 개수·합계 같은 집계를 낼 수 있어요.<br><sub>To count or sum an endless stream of events, you first group it into time intervals: windows.</sub> | 고정(tumbling) 윈도는 10초씩 겹치지 않게 잘라 분당 주문 수 같은 집계에 쓰고, 슬라이딩 윈도는 20초 창을 10초마다 밀어 이동 평균을 내요. 세션 윈도는 활동 사이 공백(예: 30분)으로 나눠 사용자 방문 단위 분석에 써요. Flink, Kafka Streams, Spark Structured Streaming, Apache Beam이 모두 이 세 가지를 지원해요.<br><sub>Tumbling windows cut back-to-back slices, say 10 seconds, for metrics such as orders per minute; sliding windows move a 20-second window every 10 seconds to produce moving averages. Session windows split on gaps of inactivity (say 30 minutes) to analyze individual visits. Flink, Kafka Streams, Spark Structured Streaming and Apache Beam support all three.</sub> |
| **이벤트 시각과 워터마크**<br><sub>Event time and watermarks</sub> | 이벤트는 발생한 시각보다 늦게 도착해요. 워터마크는 “이 시각 이전 이벤트는 거의 다 왔다”는 추정으로 윈도를 닫을 때를 정해요.<br><sub>Events arrive later than they happen; a watermark estimates that “events before this time are in” and decides when to close a window.</sub> | 네트워크 지연이나 오프라인이던 기기 때문에 이벤트는 순서가 뒤섞여 늦게 와요. 처리 시각이 아니라 이벤트 시각으로 집계해야 재처리해도 같은 결과가 나와요. 워터마크가 윈도 끝을 지나면 결과를 확정해 내보내고, 그 뒤에 온 이벤트는 허용 지연 안이면 결과를 갱신하고 넘으면 버리거나 따로 보관해요. 오래 기다리면 정확하지만 늦고, 빨리 닫으면 빠르지만 놓치는 맞바꿈이에요.<br><sub>Network delays and devices that were offline make events arrive late and out of order. Aggregating by event time, not processing time, keeps reprocessing consistent. When the watermark passes a window’s end the result is emitted; later events update it if they fall within the allowed lateness, and are dropped or sent to a side output otherwise. Waiting longer is more complete but slower: a trade-off between latency and completeness.</sub> |
| **전달 보장과 정확히 한 번**<br><sub>Delivery guarantees and exactly-once</sub> | 장애가 나도 각 이벤트가 결과에 정확히 한 번만 반영되게 하려면, 입력 위치·상태·출력을 함께 커밋해야 해요.<br><sub>For each event to affect the result exactly once despite failures, input position, state and output must be committed together.</sub> | 먼저 커밋하고 처리하면 장애 시 유실(최대 한 번), 처리하고 나중에 커밋하면 장애 시 중복(최소 한 번)이 생겨요. 정확히 한 번은 입력 오프셋, 처리기 상태, 출력 쓰기를 하나의 트랜잭션으로 묶어 얻어요. Flink 체크포인트와 2단계 커밋 싱크, Kafka 트랜잭션이 이 방식이에요. 실무에선 최소 한 번 전달에 이벤트 ID 기반 멱등 쓰기를 더해 같은 효과를 내는 경우가 많아요.<br><sub>Committing before processing loses data on a crash (at-most-once); committing after processing duplicates it (at-least-once). Exactly-once comes from committing the input offset, operator state and sink writes in one transaction, as Flink checkpoints with two-phase-commit sinks and Kafka transactions do. In practice, at-least-once delivery plus idempotent writes keyed by event ID often achieves the same effect.</sub> |
| **배압과 소비 지연**<br><sub>Backpressure and consumer lag</sub> | 생산이 소비보다 빠르면 버퍼가 차고 지연이 쌓여요. 배압은 하류가 상류에게 “천천히”라고 알려 시스템을 지켜요.<br><sub>When producers outpace consumers, buffers fill and lag builds; backpressure lets downstream tell upstream to slow down.</sub> | 버퍼를 무한정 늘리면 결국 메모리가 터지므로, 크기를 제한하고 가득 차면 상류의 속도를 늦춰요. Flink는 크레딧 기반 배압을, Reactive Streams는 소비자가 request(n)으로 필요한 만큼만 당겨 받는 방식을 써요. 카프카에서는 소비 지연(consumer lag)을 지표로 보고 알림을 걸며, 파티션과 소비자를 늘려 처리량을 키워요. 실시간성이 덜 중요하면 샘플링으로 일부를 버리기도 해요.<br><sub>An unbounded buffer eventually exhausts memory, so buffers are capped and, when full, upstream is throttled. Flink uses credit-based backpressure, and Reactive Streams has consumers pull only what they can handle with request(n). With Kafka, teams monitor and alert on consumer lag and add partitions and consumers to raise throughput. When freshness matters less, sampling drops part of the load.</sub> |
| **스트림 상태와 체크포인트**<br><sub>Stream state and checkpoints</sub> | 스트림 처리기는 집계 상태를 메모리에 들고 있어요. 체크포인트로 상태와 입력 위치를 함께 저장해 두면 장애 후에도 정확히 한 번 처리한 것처럼 이어 갈 수 있어요.<br><sub>Stream processors keep aggregate state in memory; checkpoints save that state together with input positions so processing can resume after a failure as if each event were handled exactly once.</sub> | 키별 개수를 세는 연산자의 상태 {a: 5, b: 3}은 메모리에만 있어서 죽으면 사라져요. Flink는 소스에서 체크포인트 배리어를 데이터 사이에 흘려보내고, 배리어가 지나가는 순간 각 연산자가 자기 상태를 내구성 있는 저장소(S3 등)에 저장해요. 소스는 그때의 Kafka 오프셋을 함께 기록해요. 장애가 나면 마지막 체크포인트의 상태로 되돌리고 소스를 그 오프셋부터 다시 읽어, 그 사이 처리분을 정확히 한 번 반영해요. 결과를 외부로 쓰는 싱크까지 정확히 한 번이려면 트랜잭션 커밋이나 멱등 쓰기가 필요해요.<br><sub>A per-key count such as {a: 5, b: 3} lives only in memory and vanishes on a crash. Flink injects checkpoint barriers at the source that flow between records; as a barrier passes, each operator saves its state to durable storage such as S3, and the source records its Kafka offset. After a failure the job restores the last checkpoint’s state and rereads the source from that offset, so the work in between is reflected exactly once. For the output to be exactly-once end to end, the sink also needs transactional commits or idempotent writes.</sub> |

## 품질과 운영 · Quality and operations

믿을 수 있는 데이터를 지키고, 큰 데이터를 싸게 세는 법이에요.  
*Keeping data trustworthy, and counting big data cheaply.*

| 개념 | 설명 | 실무 팁 |
| --- | --- | --- |
| **데이터 품질 검사**<br><sub>Data quality checks</sub> | 빈 값, 중복, 허용되지 않은 값, 범위, 볼륨, 신선도를 자동으로 검사해 깨진 데이터가 대시보드에 닿기 전에 막아요.<br><sub>Automatically check for nulls, duplicates, invalid values, ranges, volume and freshness so broken data is stopped before it reaches a dashboard.</sub> | not\_null, unique, accepted\_values, 범위 같은 행 단위 규칙과, 오늘 적재된 행 수가 평소보다 급감했는지(볼륨), 마지막 갱신이 언제인지(신선도), 스키마가 맞는지 같은 전체 단위 검사를 함께 해요. 실패한 행은 격리 테이블로 보내고 담당자에게 알리며, 심각하면 파이프라인을 멈춰요. dbt tests, Great Expectations, Soda가 대표 도구이고, 생산자와 스키마·품질을 약속하는 데이터 계약도 쓰여요.<br><sub>Row-level rules (not\_null, unique, accepted\_values, ranges) are combined with dataset-level checks: did today’s row count drop sharply (volume), when was it last updated (freshness), does the schema still match? Failing rows go to a quarantine table and the owner is alerted; severe failures halt the pipeline. dbt tests, Great Expectations and Soda are common tools, and data contracts formalize schema and quality promises with producers.</sub> |
| **스키마 진화**<br><sub>Schema evolution</sub> | 데이터 형식은 시간이 지나며 바뀌어요. 옛 데이터와 새 코드가 서로 읽을 수 있도록 호환 규칙을 지키며 바꿔요.<br><sub>Data formats change over time; evolve them under compatibility rules so old data and new code can still read each other.</sub> | Avro·Protobuf 메시지는 스키마 레지스트리에 등록된 스키마 ID를 달고 다녀요. 기본값이 있는 선택 필드를 추가하면 옛 소비자는 무시하고 새 소비자는 옛 데이터에 기본값을 채워 둘 다 문제없어요. 필드를 지우거나 이름·타입을 바꾸면 레지스트리가 등록을 거부해 배포를 막아요. BACKWARD(새 리더가 옛 데이터), FORWARD(옛 리더가 새 데이터), FULL(둘 다) 같은 호환 모드로 허용 범위를 정해요.<br><sub>Avro and Protobuf messages carry the ID of a schema registered in a schema registry. Adding an optional field with a default works both ways: old consumers ignore it and new consumers fill the default into old data. Removing a field or changing its name or type is rejected by the registry, blocking the deploy. Compatibility modes such as BACKWARD (new readers, old data), FORWARD (old readers, new data) and FULL (both) set what is allowed.</sub> |
| **데이터 계보와 카탈로그**<br><sub>Lineage and catalogs</sub> | 어떤 데이터가 어디서 와서 어디로 가는지 그래프로 기록해, 바꾸기 전 영향과 숫자가 틀렸을 때 원인을 찾아요.<br><sub>Record as a graph where each dataset comes from and where it goes, to see the impact of a change and trace a wrong number to its cause.</sub> | 카탈로그는 테이블·열 단위로 누가 무엇을 읽고 쓰는지 수집해요(OpenLineage, DataHub, Amundsen, dbt docs, Unity Catalog). 원본 열의 이름을 바꾸기 전에 하류 대시보드·리포트·모델 중 무엇이 영향받는지 확인하고(영향 분석), 숫자가 이상하면 위로 거슬러 실패한 적재를 찾아요(근본 원인 분석). 설명, 소유자, 개인정보 같은 민감도 태그를 달아 검색과 접근 권한 관리에도 써요.<br><sub>Catalogs collect who reads and writes what, down to tables and columns (OpenLineage, DataHub, Amundsen, dbt docs, Unity Catalog). Before renaming a source column, check which dashboards, reports and models depend on it (impact analysis); when a number looks off, walk upstream to the failed load (root-cause analysis). Descriptions, owners and sensitivity tags such as PII also drive search and access control.</sub> |
| **데이터 카탈로그**<br><sub>Data catalogs</sub> | 회사의 데이터를 찾고, 이해하고, 믿고, 통제하기 위해 메타데이터를 한곳에 모은 저장소예요. 엔진들이 테이블 위치를 찾는 기술 카탈로그 역할도 해요.<br><sub>A store that gathers metadata so people can find, understand, trust and govern data; it also acts as the technical catalog engines use to locate tables.</sub> | 데이터가 수천 개의 테이블로 늘어나면 “매출은 어느 테이블을 봐야 하지?”가 가장 흔한 질문이 돼요. 데이터 카탈로그는 이 검색창 역할을 해요. 검색 결과에 소유 팀, 인증 여부, 마지막 갱신 시각, 설명을 함께 보여 줘서 tmp.revenue\_test\_v2 같은 버려진 테이블 대신 믿을 수 있는 sales.daily\_revenue를 고르게 해요. 모으는 메타데이터는 세 종류예요. 기술 메타데이터(스키마, 저장 위치, 파티션, 행 수), 비즈니스 메타데이터(설명, “순매출” 같은 용어 정의, 소유자), 운영 메타데이터(신선도, 품질 검사 결과, 누가 얼마나 쓰는지)예요. 한편 Hive Metastore, AWS Glue, Iceberg REST 카탈로그 같은 기술 카탈로그는 테이블 이름을 현재 메타데이터와 파일 위치로 바꿔 주는 서비스라, Spark·Trino·Flink가 같은 이름으로 같은 테이블을 함께 써요. 거버넌스도 카탈로그에서 해요. email 열에 PII 태그를 달면 정책이 따라와 분석가에게는 자동으로 가려진 값(k\*\*\*@mail.com)을 보여 주고, 누가 무엇을 봤는지 감사 로그를 남겨요. DataHub, OpenMetadata, Amundsen, Unity Catalog가 대표적이고, 메타데이터는 손으로 쓰면 금방 낡으니 파이프라인과 쿼리 로그에서 자동으로 수집해요.<br><sub>Once data spreads across thousands of tables, “which table has revenue?” becomes the most common question, and a data catalog is the search box that answers it. Results show the owning team, certification, last update and description, steering people to a trusted sales.daily\_revenue instead of an abandoned tmp.revenue\_test\_v2. It collects three kinds of metadata: technical (schema, storage location, partitions, row counts), business (descriptions, glossary terms such as “net revenue”, owners) and operational (freshness, quality-check results, who uses what and how often). Technical catalogs such as Hive Metastore, AWS Glue and Iceberg REST catalogs resolve a table name to its current metadata and files, so Spark, Trino and Flink share the same tables under the same names. Governance lives there too: tagging the email column as PII attaches a policy that shows analysts a masked value (k\*\*\*@mail.com) and records who saw what in an audit log. DataHub, OpenMetadata, Amundsen and Unity Catalog are well-known examples, and since hand-written metadata goes stale quickly, it is harvested automatically from pipelines and query logs.</sub> |
| **근사 집계: HyperLogLog**<br><sub>Approximate counting: HyperLogLog</sub> | 고유한 값의 개수를 12KB 정도의 메모리로 약 1% 오차 안에서 추정하는 확률적 자료구조예요.<br><sub>A probabilistic structure that estimates the number of distinct values in about 12 KB of memory, within roughly 1% error.</sub> | 해시는 무작위 비트처럼 보여서, 앞쪽 0이 k개 연속인 값은 대략 2ᵏ개를 봐야 나와요. 앞 비트로 버킷을 고르고 버킷마다 본 0 길이의 최댓값만 저장한 뒤, 레지스터들의 조화평균으로 전체 개수를 추정해요. 레지스터 최댓값끼리 합칠 수 있어 일별 스케치로 주간·월간 고유 사용자를 바로 구해요. Redis PFCOUNT, BigQuery APPROX\_COUNT\_DISTINCT, Druid가 쓰고, Count-Min Sketch(빈도)와 t-digest(분위수)가 같은 계열이에요.<br><sub>Hashes look like random bits, so a value with k leading zeros typically appears only after about 2ᵏ distinct items. HyperLogLog uses the leading bits to pick a bucket, stores only the longest zero run seen per bucket, and estimates the total from the registers’ harmonic mean. Sketches merge by taking register maxima, so daily sketches roll up into weekly or monthly unique users. Redis PFCOUNT, BigQuery APPROX\_COUNT\_DISTINCT and Druid use it; Count-Min Sketch (frequencies) and t-digest (quantiles) are relatives.</sub> |
| **레저버 샘플링**<br><sub>Reservoir sampling</sub> | 끝을 모르는 스트림에서 메모리 k칸만으로, 모든 항목이 같은 확률로 뽑히는 무작위 표본을 만드는 알고리즘이에요.<br><sub>An algorithm that keeps a uniform random sample of a stream of unknown length using only k slots of memory.</sub> | 처음 k개(예: 3개)는 그대로 담아요. i번째 항목부터는 k/i 확률로 표본에 넣고, 넣을 때는 기존 칸 하나를 무작위로 골라 밀어내요. 뒤에 온 항목일수록 들어갈 확률은 낮지만, 먼저 들어간 항목도 나중에 밀려날 수 있어서, n개를 모두 본 뒤에는 모든 항목이 정확히 k/n 확률로 남아 있어요. 한 번만 훑으면 되고 메모리는 k칸뿐이라 로그·이벤트 표본 추출이나 큰 데이터 미리보기에 쓰여요. 항목마다 가중치가 다르면 A-Res 같은 가중 버전을 써요.<br><sub>The first k items (say 3) go straight in. From item i on, each is added with probability k/i, evicting a randomly chosen existing slot when it is. Later items are less likely to get in, but earlier ones can be evicted later, so after n items every item remains with probability exactly k/n. It needs one pass and k slots of memory, which suits sampling logs and events or previewing huge data. When items carry weights, weighted variants such as A-Res are used.</sub> |
| **개인정보 보호 파이프라인**<br><sub>Privacy in data pipelines</sub> | 이름·이메일·카드 같은 개인 식별 정보(PII)를 열마다 알맞게 보호하고, 접근을 나누고, 요청이 오면 지울 수 있게 파이프라인을 설계해요.<br><sub>Design pipelines to protect personally identifiable information (PII) column by column, separate access, and keep data deletable on request.</sub> | 원본의 PII 열은 용도에 맞게 바꿔요: 이름·전화는 마스킹(김\*지), 다른 테이블과 조인해야 하는 이메일은 솔트를 넣은 해시, 카드는 토큰화(실제 값은 별도 금고에), 나이는 30대처럼 범주화해요. 분석가는 보호된 뷰만 보고, 원래 값은 승인된 서비스만 금고를 통해 되돌리며 모든 조회를 감사 로그에 남겨요. 삭제 요청에 대비해 사용자별 키로 암호화해 두면, 키만 파기해도 백업과 로그에 남은 사본까지 읽을 수 없게 돼요(암호 파쇄). 개인정보보호법과 GDPR의 삭제권·목적 외 이용 금지를 기술로 뒷받침하는 방법이에요.<br><sub>Transform raw PII columns to suit their use: mask names and phones, hash emails with a salt when they are needed as join keys, tokenize cards with the real values kept in a separate vault, and generalize ages into ranges like 30s. Analysts query protected views, only approved services detokenize through the vault, and every lookup is audited. Encrypting with a per-user key prepares for deletion requests: destroying just that key makes even copies in backups and logs unreadable (crypto-shredding). These techniques back legal duties such as the right to erasure and purpose limitation under privacy laws and the GDPR.</sub> |
