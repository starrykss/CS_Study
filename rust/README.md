| **소유권과 이동**<br><sub>Ownership and moves</sub> | Rust의 모든 값에는 주인이 하나뿐이고, 대입과 함수 전달은 소유권을 옮겨요. 이동된 값은 컴파일러가 쓰지 못하게 막고, 주인이 사라지면 자동으로 해제돼요.<br><sub>Every Rust value has exactly one owner, and assignment and passing to functions move ownership. The compiler forbids using moved values, and values are freed automatically when their owner goes away.</sub> | Rust는 가비지 컬렉터 없이도, C처럼 손으로 free를 부르지 않고도 메모리를 안전하게 관리해요. 그 바탕이 소유권 규칙이에요. 첫째, 모든 값에는 주인(owner)인 변수가 있어요. 둘째, 주인은 한 번에 하나뿐이에요. 셋째, 주인이 범위를 벗어나면 값이 해제돼요. let s = String::from("hi")는 힙에 두 바이트를 할당하고, 스택의 s에는 포인터, 길이, 용량으로 된 24바이트 헤더가 놓여 s가 버퍼의 주인이 돼요. let t = s는 이 헤더 24바이트만 t로 복사하고 s를 더 이상 쓸 수 없게 만들어요. 이것이 이동(move)이에요. 힙 버퍼는 복사되지 않으니 빠르고, 주인이 여전히 하나라서 s와 t가 같은 버퍼를 두 번 해제하는 이중 해제가 원천적으로 불가능해요. C++의 std::move와 달리 Rust에서는 이동이 기본 동작이고, 이동된 변수는 비어 있는 상태로 남는 게 아니라 아예 쓸 수 없어요. 이 환경에서 이동한 뒤 s를 출력하려 하자 error[E0382]: borrow of moved value: `s`와 함께 이동이 일어난 줄과 사용된 줄을 짚어 주며 컴파일이 실패했어요. 함수 인자로 넘기는 것도 이동이라, take(t)를 부른 뒤에는 t를 쓸 수 없고, 값은 take의 매개변수가 범위를 벗어나는 함수 끝에서 해제돼요. 값을 돌려받으려면 함수가 반환해 소유권을 다시 넘기거나, 다음 장의 빌림을 써요. 이 모든 검사는 컴파일 때 끝나서 실행 중에는 아무 비용이 없고, 해제 시점이 코드 구조로 정해지므로 GC처럼 언제 멈출지 모르는 일도 없어요.<br><sub>Rust manages memory safely without a garbage collector and without calling free by hand as in C. Underneath are the ownership rules. First, every value has an owner variable. Second, there is only one owner at a time. Third, when the owner leaves scope, the value is freed. let s = String::from("hi") allocates two bytes on the heap, and s on the stack holds a 24-byte header of pointer, length and capacity, making s the buffer’s owner. let t = s copies just this 24-byte header into t and makes s unusable. This is a move. The heap buffer is not copied, so it is fast, and since there is still only one owner, a double free in which s and t free the same buffer is impossible by construction. Unlike C++’s std::move, moving is Rust’s default behavior, and a moved variable is not left in some empty state but cannot be used at all. Here, trying to print s after the move failed to compile with error[E0382]: borrow of moved value: `s`, pointing out the line where the move happened and the line where s was used. Passing a function argument is also a move, so t cannot be used after calling take(t), and the value is freed at the end of take, when its parameter leaves scope. To get a value back, the function returns it, handing ownership back, or the code uses the borrowing described next. All these checks finish at compile time and cost nothing at run time, and because the freeing point is fixed by the structure of the code, there are no unpredictable pauses as with a GC.</sub> |
| **빌림 규칙**<br><sub>The borrowing rules</sub> | 빌림은 소유권을 넘기지 않고 값을 쓰는 참조예요. 공유 참조 &T는 여럿, 가변 참조 &mut T는 하나만 허용해서 댕글링과 데이터 경쟁을 컴파일 때 막아요.<br><sub>Borrowing uses a value through a reference without taking ownership. Many shared &T or a single &mut T are allowed, which stops dangling references and data races at compile time.</sub> | 매번 소유권을 넘기고 돌려받으면 불편하니, Rust는 값을 잠시 빌려 쓰는 참조를 제공해요. 참조에는 두 종류가 있어요. 공유 참조 &T는 값을 읽기만 하는 참조로, 동시에 여러 개를 만들 수 있어요. 가변 참조 &mut T는 값을 바꿀 수 있는 참조로, 한 번에 딱 하나만 있을 수 있고 그동안에는 다른 공유 참조도 있으면 안 돼요. 즉 여럿이 함께 보거나 하나가 바꾸거나 둘 중 하나만 허용하는 규칙이라서 "공유 XOR 변경(aliasing XOR mutation)"이라고 불러요. 이 단순한 규칙이 여러 종류의 버그를 한꺼번에 막아요. let first = &v[0]으로 벡터의 첫 원소를 빌린 채 v.push(4)를 부르면, push는 용량이 모자랄 때 버퍼를 재할당하므로 first가 해제된 메모리를 가리키게 될 수 있어요. C++에서는 반복자 무효화로 실행 중에 조용히 메모리를 망가뜨리는 버그지만, Rust는 이 환경에서처럼 error[E0502]: cannot borrow `v` as mutable because it is also borrowed as immutable로 컴파일 단계에서 막아요. 가변 참조를 두 개 만들면 E0499가 나요. 빌림은 선언된 블록 끝이 아니라 마지막으로 쓰이는 지점까지만 유효해요(비어휘적 수명, NLL). 그래서 println!("{first}")를 push 앞으로 옮기면 그대로 컴파일돼요. 같은 규칙이 스레드에도 적용되어, 두 스레드가 같은 데이터를 동시에 바꾸는 데이터 경쟁은 안전한 Rust에서 컴파일되지 않아요. 이런 검사를 하는 컴파일러의 부분을 빌림 검사기(borrow checker)라고 하고, 모두 컴파일 때 끝나서 실행 비용은 없어요. 처음에는 빌림 검사기와 싸우는 느낌이 들지만, 오류 메시지가 문제 지점을 정확히 짚어 줘요.<br><sub>Handing ownership over and back every time would be tedious, so Rust offers references that borrow a value for a while. There are two kinds. A shared reference &T only reads the value, and many can exist at once. A mutable reference &mut T can change the value, and only one may exist at a time, with no shared references alongside it. The rule allows either many readers together or one writer, never both, which is why it is called aliasing XOR mutation. This simple rule stops several kinds of bugs at once. If a vector’s first element is borrowed with let first = &v[0] and then v.push(4) is called, push may reallocate the buffer when capacity runs out, leaving first pointing at freed memory. In C++ that is iterator invalidation, a bug that silently corrupts memory at run time, but Rust stops it at compile time, as it did here with error[E0502]: cannot borrow `v` as mutable because it is also borrowed as immutable. Creating two mutable references gives E0499. A borrow is valid only until its last use, not to the end of the block where it was declared (non-lexical lifetimes, NLL), so moving println!("{first}") before the push compiles as is. The same rule applies to threads, so data races, in which two threads change the same data at once, do not compile in safe Rust. The part of the compiler doing these checks is called the borrow checker, and since everything finishes at compile time, there is no run-time cost. At first it can feel like fighting the borrow checker, but its error messages pinpoint exactly where the problem is.</sub> |
| **수명**<br><sub>Lifetimes</sub> | 수명은 참조가 유효한 구간이에요. 컴파일러는 참조가 가리키는 값보다 오래 쓰이지 않는지 확인하고, 애매할 때만 'a 같은 표기로 관계를 알려 줘요.<br><sub>A lifetime is the span in which a reference is valid. The compiler checks that no reference outlives its value, and only in ambiguous cases do annotations such as 'a state the relationship.</sub> | 수명(lifetime)은 참조가 유효한 코드 구간이에요. 빌림 검사기는 모든 참조가 그것이 가리키는 값보다 오래 쓰이지 않는지 확인해서 댕글링 참조를 막아요. 내부 블록에서 let x = 5를 만들고 r = &x로 빌린 뒤 블록 밖에서 r을 쓰면, x는 블록 끝에서 해제되는데 r은 그 뒤에도 쓰여요. 이 환경에서 이 코드는 error[E0597]: `x` does not live long enough와 함께 x가 해제되는 지점과 r이 나중에 쓰이는 지점을 보여 주며 컴파일되지 않았어요. 대부분의 경우 컴파일러가 수명을 스스로 추론하지만, 함수가 참조를 여러 개 받아 참조를 돌려줄 때는 결과가 어느 입력을 빌렸는지 시그니처만으로는 알 수 없어요. fn longest(a: &str, b: &str) -> &str는 a와 b 중 더 긴 것을 돌려주는데, 호출하는 쪽은 결과를 언제까지 써도 되는지 알아야 하므로 E0106 missing lifetime specifier 오류가 나요. 이럴 때 fn longest<'a>(a: &'a str, b: &'a str) -> &'a str처럼 수명 매개변수를 적어요. 이 표기는 세 참조가 같은 수명 'a를 공유한다는 관계를 말할 뿐이고, 실제로 'a는 a와 b가 모두 살아 있는 구간, 즉 더 짧은 쪽이 되어서 결과도 그 안에서만 쓸 수 있어요. 수명 표기는 값의 수명을 늘리거나 바꾸지 않고, 컴파일러가 검사할 수 있도록 관계를 설명할 뿐이며, 실행 코드에는 아무것도 더하지 않아요. 생략 규칙(elision) 덕분에 대부분의 함수는 표기가 필요 없어요. 입력 참조가 하나면 출력이 그 수명을 받고, &self를 받는 메서드면 출력이 self의 수명을 받아요. 문자열 리터럴은 실행 파일에 들어 있어 프로그램 내내 살아 있으므로 타입이 &'static str이에요. 구조체에 참조를 담을 때도 struct Parser<'a> { input: &'a str }처럼 수명을 적어서, 구조체가 빌린 데이터보다 오래 살지 못하게 해요.<br><sub>A lifetime is the stretch of code in which a reference is valid. The borrow checker prevents dangling references by checking that no reference is used longer than the value it points to. Create let x = 5 in an inner block, borrow it with r = &x, and use r outside the block, and x is freed at the block’s end while r is still used afterward. Here that code failed to compile with error[E0597]: `x` does not live long enough, showing where x is dropped and where r is later used. Most of the time the compiler infers lifetimes itself, but when a function takes several references and returns one, its signature alone does not say which input the result borrows. fn longest(a: &str, b: &str) -> &str returns the longer of a and b, and since callers need to know how long the result may be used, it fails with E0106 missing lifetime specifier. In such cases a lifetime parameter is written, as in fn longest<'a>(a: &'a str, b: &'a str) -> &'a str. The annotation only states that the three references share one lifetime 'a; in practice 'a becomes the span where both a and b are alive, the shorter of the two, so the result can be used only within it. Lifetime annotations neither extend nor change how long values live; they describe relationships so the compiler can check them, and they add nothing to the generated code. Thanks to the elision rules, most functions need no annotations: with a single input reference the output takes its lifetime, and for methods taking &self the output takes self’s. String literals live inside the executable for the whole program, so their type is &'static str. A struct holding a reference also states a lifetime, as in struct Parser<'a> { input: &'a str }, so the struct cannot outlive the data it borrows.</sub> |
| **Copy와 Clone**<br><sub>Copy and Clone</sub> | 정수 같은 단순한 Copy 타입은 대입하면 비트가 복사되고, 자원을 가진 타입은 이동해요. 깊은 복사는 clone을 명시적으로 불러서 비용이 코드에 드러나요.<br><sub>Simple Copy types such as integers are copied bit for bit on assignment, while types that own resources move. Deep copies require an explicit clone, so their cost shows in the code.</sub> | 모든 대입이 이동인 것은 아니에요. i32, u8, f64, bool, char, 그리고 공유 참조 &T처럼 스택에만 있는 단순한 타입은 Copy 트레이트를 구현해요. let x = 5; let y = x는 비트를 그대로 복사하므로 x와 y를 모두 계속 쓸 수 있어요. 이런 타입은 복사가 싸고 해제할 자원도 없어서 이동으로 막을 이유가 없기 때문이에요. 반면 String처럼 힙 자원을 가진 값은 대입하면 이동해요. 같은 내용의 독립된 값이 정말 필요하면 s.clone()을 명시적으로 불러요. clone은 새 힙 버퍼를 할당하고 내용을 복사하는 깊은 복사예요. Rust는 이렇게 비싼 복사를 반드시 코드에 드러나게 해서, 성능 문제가 숨지 않게 해요. 코드에 clone이 너무 많다면 빌림으로 바꿀 수 있는지 살펴볼 신호예요. 직접 만든 타입도 #[derive(Clone, Copy)]로 Copy가 될 수 있어요. f64 두 개로 된 점 구조체 P는 16바이트라 Copy로 만들면 대입이 memcpy 한 번과 같아요. Copy는 Clone을 상위 트레이트로 요구해서 둘을 함께 derive해요. 하지만 모든 필드가 Copy여야 하고, String, Vec, Box처럼 자원을 소유하거나 Drop을 구현한 타입은 Copy가 될 수 없어요. 비트만 복사하면 두 값이 같은 힙 버퍼를 가리키고 둘 다 해제하려 할 것이기 때문이에요. 이 제약은 컴파일러가 강제해서, Drop을 구현한 타입에 Copy를 derive하면 컴파일 오류가 나요. 정리하면 Copy는 암묵적이고 항상 싼 비트 복사이고, Clone은 명시적이며 비쌀 수 있는 복제예요. Rc나 Arc의 clone은 예외적으로 데이터를 복사하지 않고 참조 수만 늘리는 얕은 복제예요.<br><sub>Not every assignment is a move. Simple stack-only types such as i32, u8, f64, bool, char and the shared reference &T implement the Copy trait. let x = 5; let y = x copies the bits as they are, so both x and y remain usable. Such types are cheap to copy and own no resources to free, so there is no reason to restrict them with moves. Values that own heap resources, such as a String, move on assignment instead. When an independent value with the same contents is truly needed, call s.clone() explicitly. clone is a deep copy that allocates a new heap buffer and copies the contents. Rust insists that expensive copies like this appear in the code, so performance problems cannot hide; too many clones in code are a signal to check whether borrowing would do. Your own types can become Copy with #[derive(Clone, Copy)] too. A point struct P made of two f64 values is 16 bytes, and making it Copy turns assignment into a single memcpy. Copy requires Clone as a supertrait, so the two are derived together. But every field must be Copy, and types that own resources or implement Drop, such as String, Vec and Box, can never be Copy, because copying just the bits would leave two values pointing at the same heap buffer, both trying to free it. The compiler enforces this, so deriving Copy on a type that implements Drop is a compile error. In short, Copy is an implicit and always cheap bit copy, while Clone is an explicit and possibly expensive duplicate. The clone of Rc or Arc is an exception: a shallow clone that copies no data and only increments a reference count.</sub> |
| **Drop과 해제 순서**<br><sub>Drop and destruction order</sub> | Drop 트레이트는 소멸자예요. 주인이 범위를 벗어나면 컴파일러가 drop 호출을 넣고, 지역 변수는 선언의 역순으로 해제돼요.<br><sub>The Drop trait is the destructor. The compiler inserts a drop call when the owner leaves scope, and locals are dropped in reverse order of declaration.</sub> | Rust에서 값이 해제될 때 할 일은 Drop 트레이트의 drop 메서드에 적어요. | **트레이트와 정적 디스패치**<br><sub>Traits and static dispatch</sub> | 트레이트는 타입이 구현할 동작의 약속이에요. 제네릭에 트레이트 경계를 걸면 컴파일러가 타입마다 코드를 만들어 직접 호출하고 인라인해요.<br><sub>A trait is a promise of behavior that types implement. Traits can also have methods with default implementations, and they can be implemented later for types that already exist. The orphan rule, however, requires that the trait or the type be defined in your own crate, so you cannot implement someone else’s trait for someone else’s type. Traits are used together with generics. The T: Area in fn total<T: Area>(xs: &[T]) is a trait bound requiring T to be a type that implements Area. Calling total(&circles) fixes T as C, so the compiler turns x.area() into a direct call to C::area and even inlines it, producing the same machine code as hand-written code. This is called static dispatch. To achieve it, the compiler performs monomorphization, generating a separate copy of the generic function for each type used. Here, using a generic biggest on an i32 array and an f64 array produced two functions in the executable, biggest::<i32> and biggest::<f64>. It is the same approach as C++ templates, so the abstraction costs nothing at run time, but using many types increases compile time and binary size. The standard library’s traits are wired into the language: implementing Display makes a type printable with {}, implementing Iterator makes it usable in for loops, and implementing Add enables the + operator. #[derive(Debug, Clone, PartialEq, Eq, Hash)] generates implementations of such common traits automatically.</sub> |
| **트레이트 객체**<br><sub>Trait objects</sub> | dyn Trait는 실행 중에 타입이 정해지는 트레이트 객체예요. 데이터와 vtable 두 포인터로 된 팻 포인터로 다루고, 메서드는 vtable을 거쳐 간접 호출돼요.<br><sub>dyn Trait is a trait object whose type is decided at run time. It is handled through a fat pointer of data and vtable, and methods are called indirectly through the vtable.</sub> | 제네릭은 컴파일 때 타입이 하나로 정해져야 해요. 그래서 원과 사각형처럼 서로 다른 타입을 한 Vec에 섞어 담으려면 트레이트 객체가 필요해요. dyn Area는 "Area를 구현한 어떤 타입"을 뜻하고, 크기를 컴파일 때 알 수 없으므로 Box<dyn Area>나 &dyn Area처럼 포인터 뒤에 둬요. 이 포인터는 데이터를 가리키는 포인터와 vtable을 가리키는 포인터로 된 팻 포인터라서, 이 환경에서 Box<dyn Area>와 &dyn Area는 모두 16바이트였어요. vtable은 컴파일러가 (트레이트, 구체 타입) 쌍마다 하나씩 읽기 전용 메모리에 만들어 두는 표예요. 그 타입의 drop 함수, 크기와 정렬, 그리고 트레이트의 각 메서드 주소가 들어 있어요. s.area()를 부르면 vtable에서 area의 주소를 읽어 간접 호출하는데, 이것이 동적 디스패치예요. C++의 가상 함수와 비슷하지만 vptr가 객체 안이 아니라 포인터 쪽에 있어서, 같은 타입이라도 트레이트 객체로 쓸 때만 비용을 내요. 대가도 있어요. 간접 호출은 인라인할 수 없고, Box마다 따로 할당된 객체가 메모리에 흩어져 캐시에도 불리해요. 이 환경에서 도형 100만 개의 넓이를 합하는 데 enum과 match는 약 2.7ms, Box<dyn Area>는 약 4.2ms가 걸렸어요. 그래서 고르는 기준은 이래요. 변형이 정해진 닫힌 집합이면 enum이 가장 단순하고 빠르고, 속도가 최우선이면 제네릭, 플러그인처럼 나중에 다른 크레이트가 새 타입을 추가하는 열린 구조이거나 코드 크기를 줄이고 싶으면 dyn이에요. 모든 트레이트가 dyn이 될 수 있는 것은 아니에요. 제네릭 메서드가 있거나 Self를 값으로 돌려주는 메서드가 있으면 vtable을 만들 수 없어서 dyn으로 쓸 수 없는데, 이를 dyn 호환성(예전 이름은 객체 안전성)이라고 해요.<br><sub>Generics require a single type to be fixed at compile time, so mixing different types, such as circles and rectangles, in one Vec needs trait objects. dyn Area means "some type that implements Area," and since its size is unknown at compile time it sits behind a pointer, as in Box<dyn Area> or &dyn Area. That pointer is a fat pointer made of a pointer to the data and a pointer to a vtable, so here both Box<dyn Area> and &dyn Area were 16 bytes. A vtable is a table the compiler builds once per (trait, concrete type) pair in read-only memory. It holds that type’s drop function, its size and alignment, and the address of each of the trait’s methods. Calling s.area() reads area’s address from the vtable and calls it indirectly; this is dynamic dispatch. It resembles C++ virtual functions, but the vptr lives in the pointer rather than inside the object, so a type pays the cost only when used as a trait object. There is a price: indirect calls cannot be inlined, and objects allocated separately per Box are scattered through memory, which is unkind to the cache. Summing the areas of a million shapes here took about 2.7 ms with an enum and match versus about 4.2 ms with Box<dyn Area>. So the choice goes like this: an enum is simplest and fastest for a closed set of variants, generics when speed comes first, and dyn for open structures, such as plugins where other crates add new types later, or to shrink code size. Not every trait can be dyn. A trait with generic methods or with methods returning Self by value cannot form a vtable and cannot be used as dyn; this is called dyn compatibility, formerly object safety.</sub> |
| **제네릭과 impl Trait**<br><sub>Generics and impl Trait</sub> | 제네릭은 타입을 매개변수로 받아 타입마다 코드를 만드는 비용 없는 추상화예요. impl Trait로 복잡한 반환 타입을 숨기고, where 절과 연관 타입으로 관계를 표현해요.<br><sub>Generics take types as parameters and generate code per type, a zero-cost abstraction. impl Trait hides complicated return types, and where clauses and associated types express relationships.</sub> | 제네릭은 타입을 매개변수로 받아 여러 타입에 쓸 수 있는 코드를 만들어요. struct Stack<T> { items: Vec<T> }는 Stack<i32>로도 Stack<String>으로도 쓸 수 있고, 컴파일러는 쓰인 타입마다 알맞은 메모리 배치와 메서드를 따로 만들어요. impl<T> Stack<T> { … }는 모든 T에 대한 메서드를, impl Stack<i32> { … }는 특정 타입에만 있는 메서드를 정의해요. 표준 라이브러리의 Vec<T>, Option<T>, Result<T, E>, HashMap<K, V>가 모두 이런 제네릭 타입이에요. 반복자나 클로저를 돌려주는 함수는 실제 타입이 너무 길거나 아예 이름을 쓸 수 없어요. 이 환경에서 (0..n).filter(\|x\| x % 2 == 0)을 돌려주는 evens 함수의 진짜 타입은 Filter<Range<u32>, evens::{{closure}}>였어요. 이럴 때 반환 타입을 impl Iterator<Item = u32>로 쓰면 "Iterator를 구현한 어떤 타입"이라는 것만 드러내고 구체 타입을 숨길 수 있어요. 숨겨도 컴파일러는 실제 타입을 알고 있어서 정적 디스패치와 인라인이 그대로이고, 크기도 그대로 8바이트였어요. dyn과 달리 힙 할당이나 간접 호출이 없어요. 경계가 여러 개라 시그니처가 길어지면 fn show<T>(x: T) where T: Display + Debug처럼 where 절로 옮겨요. 트레이트 안에서 정하는 연관 타입도 있어요. Iterator의 type Item처럼 구현마다 하나로 정해지는 타입은, 타입 매개변수로 둘 때보다 쓰는 쪽이 간단해져요. const 제네릭은 fn sum<const N: usize>(a: [i32; N])처럼 배열 길이 같은 상수 값도 매개변수로 받아요. 제네릭은 실행 비용이 없지만, 타입마다 코드가 생기므로 많이 쓰면 컴파일 시간과 실행 파일 크기가 늘어요. 이것이 문제가 되면 일부를 dyn으로 바꿔 한 벌의 코드만 만들게 할 수 있어요.<br><sub>Generics take types as parameters to make code usable with many types. struct Stack<T> { items: Vec<T> } can be used as Stack<i32> or Stack<String>, and the compiler generates a suitable memory layout and methods for each type used. impl<T> Stack<T> { … } defines methods for every T, while impl Stack<i32> { … } defines methods for one specific type only. The standard library’s Vec<T>, Option<T>, Result<T, E> and HashMap<K, V> are all generic types like this. Functions that return iterators or closures have actual types that are too long or cannot be named at all. Here, the real type of evens, which returns (0..n).filter(\|x\| x % 2 == 0), was Filter<Range<u32>, evens::{{closure}}>. Writing the return type as impl Iterator<Item = u32> reveals only that it is "some type implementing Iterator" and hides the concrete type. Though hidden, the compiler knows the real type, so static dispatch and inlining remain, and the size stayed 8 bytes. Unlike dyn, there is no heap allocation or indirect call. When several bounds make a signature long, they move into a where clause, as in fn show<T>(x: T) where T: Display + Debug. Traits can also define associated types: a type fixed once per implementation, such as Iterator’s type Item, is simpler for users than an extra type parameter. Const generics take constant values such as array lengths as parameters, as in fn sum<const N: usize>(a: [i32; N]). Generics cost nothing at run time, but since code is generated per type, heavy use increases compile time and executable size. When that becomes a problem, part of the code can switch to dyn so that only one copy is generated.</sub> |

## 소유권을 넓히는 도구들 · Tools that stretch ownership

| **Box**<br><sub>Box</sub> | Box는 힙에 있는 값을 혼자 소유하는 8바이트 포인터예요. 재귀 타입의 크기를 정해 주고, 크기를 모르는 dyn Trait를 담는 데 써요.<br><sub>A Box is an 8-byte pointer that solely owns a value on the heap. Box는 값을 혼자 소유하므로 소유권 규칙이 그대로 적용되어, 다른 변수에 대입하면 이동하고, b가 범위를 벗어나면 Drop이 힙 메모리를 해제해요. 비용은 C에서 malloc과 free를 직접 부르는 것과 같고, 가비지 컬렉터가 끼지 않아요. Box가 꼭 필요한 첫 번째 경우는 재귀 타입이에요. Box는 Deref를 구현해서 \*b로 안의 값을 쓰거나 b.method()처럼 안의 메서드를 바로 부를 수 있어요.<br><sub>Box<T> is the simplest smart pointer. Box::new(5) allocates one i32 on the heap, and on the stack sits b, an 8-byte pointer to it. Since a Box solely owns its value, the ownership rules apply as they are: assigning it to another variable moves it, and when b leaves scope, Drop frees the heap memory. The cost is the same as calling malloc and free directly in C, with no garbage collector involved. The first case that truly needs a Box is a recursive type. Rust must know every type’s size at compile time, and a type that contains itself directly, such as enum List { Cons(i32, List), Nil }, would be infinitely large. Here this code failed with error[E0072]: recursive type `List` has infinite size, plus a hint to break the cycle with indirection such as Box, Rc or &. Changing it to Cons(i32, Box<List>) puts a pointer of known size, 8 bytes, where the next node goes, so it compiles, and the nodes become a linked list allocated separately on the heap and joined by pointers. Recursive data structures such as trees and expression trees are all built this way. The second case is values whose size cannot be known at compile time: trait objects such as dyn Trait differ in size per concrete type, so they live behind a pointer as Box<dyn Trait>. The third is moving very large values. Moving a value copies its bytes on the stack, but once it is in a Box, only the 8-byte pointer moves. Box implements Deref, so \*b reaches the inner value and b.method() calls the inner type’s methods directly.</sub> |
| **Rc와 Weak**<br><sub>Rc and Weak</sub> | Rc는 참조 수를 세서 여러 소유자가 한 값을 함께 소유하게 해요. clone은 수만 올리고, 서로 가리키는 순환은 Weak로 끊어요.<br><sub>Rc counts references so several owners can share one value. clone only bumps the count, and Weak breaks cycles in which values point at each other.</sub> | 소유권 규칙은 주인을 하나로 정하지만, 그래프의 노드처럼 여러 곳에서 한 값을 가리키고 누가 마지막으로 쓸지 컴파일 때 알 수 없는 경우가 있어요. Rc<T>(reference counted)는 이런 공유 소유를 위한 스마트 포인터예요. Rc::new(5)는 힙에 RcBox를 만들고, 그 안에 강한 참조 수, 약한 참조 수, 값이 함께 들어 있어요. Rc 자체는 RcBox를 가리키는 8바이트 포인터예요. Rc::clone(&a)는 값을 복사하지 않고 강한 수만 1 올리는 싼 연산이라, 깊은 복사인 일반 clone과 구분하려고 Rc::clone이라고 명시적으로 쓰는 관례가 있어요. 이 환경에서 clone 후 Rc::strong\_count는 2였어요. Rc가 drop될 때마다 강한 수가 1 줄고, 0이 되는 순간 안의 값이 drop돼요. Rc::downgrade로 만든 Weak<T>는 강한 수에 들어가지 않는 약한 참조예요. 값을 살려 두지 않으므로, 쓰기 전에 upgrade()로 Option<Rc<T>>를 얻어 아직 살아 있는지 확인해요. 이 환경에서 a와 b를 모두 drop하기 전에는 Some(5), 후에는 None이 나왔어요. Weak가 꼭 필요한 이유는 순환 참조예요. 두 노드 x와 y가 Rc로 서로를 가리키면 각자의 강한 수가 2가 되고, 범위를 벗어나 지역 변수가 사라져도 서로가 1씩 붙잡고 있어서 영원히 drop되지 않아요. 이 환경에서도 drop 메시지가 하나도 찍히지 않았어요. Rust의 메모리 안전은 이런 누수까지 막아 주지는 않으므로, 트리에서 자식은 Rc로, 부모를 가리키는 역방향 참조는 Weak로 만들어요. Rc의 수 갱신은 원자적이지 않아서 한 스레드 안에서만 쓸 수 있고, 스레드 사이에서는 같은 일을 원자적으로 하는 Arc를 써요.<br><sub>The ownership rules fix a single owner, but sometimes several places point at one value, as with graph nodes, and which of them uses it last cannot be known at compile time. Rc<T> (reference counted) is the smart pointer for such shared ownership. Rc::new(5) creates an RcBox on the heap holding the strong count, the weak count and the value together, and an Rc itself is an 8-byte pointer to the RcBox. Rc::clone(&a) copies no value; it is a cheap operation that adds 1 to the strong count, and by convention it is written explicitly as Rc::clone to distinguish it from an ordinary deep clone. Here Rc::strong\_count was 2 after the clone. Each time an Rc is dropped the strong count falls by 1, and the moment it reaches 0 the inner value is dropped. An Rc hands out only shared references, so changing the inner value takes RefCell as well, in the form Rc<RefCell<T>>. A Weak<T> made with Rc::downgrade is a weak reference not counted among the strong ones. Weak is essential because of reference cycles. If two nodes x and y point at each other through Rc, each strong count becomes 2, and even after the local variables vanish at the end of scope, each holds the other at 1, so they are never dropped. Indeed not a single drop message was printed here. Rust’s memory safety does not prevent leaks like this, so in a tree, children are held by Rc and back references to parents are made Weak. Rc’s count updates are not atomic, so it can be used only within one thread; across threads, Arc does the same job atomically.</sub> |
| **RefCell과 내부 가변성**<br><sub>RefCell and interior mutability</sub> | RefCell은 공유 참조로도 값을 바꾸게 해 주는 내부 가변성 타입이에요. 빌림 규칙을 실행 중에 검사해서, 어기면 panic이 나요.<br><sub>RefCell is an interior-mutability type that lets values change even through shared references. It checks the borrowing rules at run time, and breaking them panics.</sub> | 빌림 규칙에 따르면 &T 공유 참조로는 값을 바꿀 수 없어요. 하지만 Rc로 공유하는 그래프의 노드를 고치거나, 공유된 객체 안에 캐시를 두는 것처럼 공유하면서 바꿔야 할 때가 있어요. 이를 위해 Rust는 내부 가변성(interior mutability)을 제공하고, RefCell<T>가 대표적인 타입이에요. RefCell은 &c 같은 공유 참조만 있어도 c.borrow\_mut()로 안의 값에 대한 가변 참조를 얻게 해 줘요. 규칙을 없애는 것은 아니고, 빌림 규칙의 검사를 컴파일 때에서 실행 중으로 옮기는 거예요. RefCell은 현재 빌림 상태를 세는 카운터를 값과 함께 가지고 있어서, 이 환경에서 RefCell<i32>는 16바이트였어요. borrow()는 읽기 수를 1 올린 가드 Ref를, borrow\_mut()는 아무도 빌리지 않았을 때만 가드 RefMut를 돌려주고, 가드가 drop되면 수가 원래대로 돌아가요. 읽기 빌림 r1이 살아 있는 동안 try\_borrow\_mut()를 부르면 이 환경에서 Err가 돌아왔고, borrow\_mut()를 부르면 RefCell already borrowed라는 panic이 났어요. 컴파일러가 잡아 주지 못하므로, 가드를 오래 들고 있지 않고 빌림을 짧은 범위에 가두는 것이 중요해요. 흔한 조합은 Rc<RefCell<T>>예요. Rc로 여러 곳에서 공유하고 RefCell로 바꿔요. 참조를 내줄 필요 없이 값을 통째로 읽고 쓰기만 하는 Copy 타입에는 카운터가 없는 더 가벼운 Cell<T>의 get과 set을 써요. RefCell과 Cell은 스레드 사이에서 쓸 수 없고(Sync가 아님), 스레드 사이에서는 같은 역할을 하는 Mutex와 RwLock을 써요. 내부 가변성은 결국 UnsafeCell이라는 기본 타입 위에 만들어져 있어요.<br><sub>By the borrowing rules, a value cannot be changed through a shared reference &T. Yet sometimes things must be shared and changed at once, such as editing nodes of a graph shared through Rc or keeping a cache inside a shared object. For this Rust offers interior mutability, and RefCell<T> is its best-known type. With just a shared reference such as &c, RefCell lets c.borrow\_mut() obtain a mutable reference to the inner value. The rules are not abolished; their checking moves from compile time to run time. A RefCell keeps a counter of its current borrow state alongside the value, so RefCell<i32> was 16 bytes here. borrow() returns a Ref guard after adding a reader, borrow\_mut() returns a RefMut guard only when nobody holds a borrow, and when a guard is dropped the count goes back. | **Vec의 구조**<br><sub>Inside Vec</sub> | Vec는 포인터·용량·길이 24바이트와 힙 버퍼로 돼요. 빈 Vec은 할당하지 않고, 첫 push에 4칸을 잡은 뒤 두 배씩 늘어요.<br><sub>A Vec is 24 bytes of pointer, capacity and length plus a heap buffer. Vec::new() allocates nothing yet, so it costs almost nothing. The buffer is allocated when the first element is pushed, and here a Vec<i32> reached a capacity of 4 on its first push. For small elements a few slots are reserved from the start to avoid repeated tiny allocations. After that, each time it filled up, the capacity doubled to 8, 16, 32, 64 and 128, and each growth allocates a larger buffer, moves the elements and frees the old buffer. Thanks to doubling, each push costs O(1) on average. Unlike in C++, if a reference borrowing an element is still alive while a possibly reallocating push is called, the borrow checker reports a compile error, so iterator-invalidation bugs cannot happen. Iterators cannot go out of range and read more clearly, which is why Rust code prefers them.</sub> |

Miri는 Rust 프로그램을 해석 실행하면서 범위 밖 접근, 해제 후 사용, 잘못된 정렬, 빌림 규칙 위반 같은 정의되지 않은 동작을 찾아 줘요.<br><sub>Rust’s safety guarantees hold only as far as the compiler can prove them. To do things it cannot verify, such as touching hardware directly, calling C libraries or building low-level data structures for performance, you need unsafe. The raw pointers \*const T and \*mut T are not protected by the borrowing rules and may be null or point at freed memory or misaligned addresses. Creating a raw pointer is safe, but dereferencing it is dangerous, so using \*p directly here gave error[E0133]: dereference of raw pointer is unsafe and requires unsafe block. Importantly, unsafe does not switch off the borrow checker or type checking. Every rule beyond those five still applies, and unsafe is only a promise that "I have proven this part safe." | **스레드와 move**<br><sub>Threads and move</sub> | thread::spawn은 클로저를 새 OS 스레드에서 실행해요. 스레드가 더 오래 살 수 있어서 지역 변수는 move로 넘겨야 하고, join으로 결과를 받아요.<br><sub>thread::spawn runs a closure on a new OS thread. OS 스레드는 생성과 전환에 커널이 끼고 각자 수 MB의 스택을 예약해서, 동시에 수천에서 수만 개의 작업을 다뤄야 하는 네트워크 서버에서는 async 런타임을 쓰는 것이 일반적이에요. 스레드 이름이나 스택 크기는 thread::Builder로 정할 수 있어요.<br><sub>Rust’s standard threads map 1:1 to operating-system threads. thread::spawn takes a closure, runs it on a new thread and returns a JoinHandle. The issue is lifetimes. A new thread may outlive the function that created it, so if the closure merely borrows the local v, the thread could use v after the function has returned and v has been freed. | **Send와 Sync**<br><sub>Send and Sync</sub> | Send는 다른 스레드로 넘겨도 되는 타입, Sync는 여러 스레드가 함께 참조해도 되는 타입이에요. 컴파일러가 자동으로 판단해서 데이터 경쟁을 컴파일 때 막아요.<br><sub>Send marks types safe to move to another thread, and Sync marks types safe to reference from several threads at once. The compiler derives them automatically and stops data races at compile time.</sub> | Rust가 스레드 사이의 안전을 보장하는 핵심은 Send와 Sync라는 두 표시 트레이트예요. 메서드는 없고, 타입이 어떤 성질을 가졌는지만 표시해요. T가 Send이면 T의 소유권을 다른 스레드로 넘겨도 안전하고, T가 Sync이면 &T를 여러 스레드가 동시에 가져도 안전해요. 이 두 트레이트는 자동 트레이트라서, 구조체의 모든 필드가 Send이면 그 구조체도 자동으로 Send가 돼요. 대부분의 타입은 둘 다 만족하지만, 몇몇 타입은 일부러 빠져 있어요. Rust 커뮤니티는 이를 "두려움 없는 동시성(fearless concurrency)"이라고 불러요. unsafe impl Send로 직접 표시할 수도 있지만, 그때는 안전을 프로그래머가 증명해야 해요.<br><sub>The core of how Rust guarantees safety between threads is two marker traits, Send and Sync. They have no methods and only mark what properties a type has. If T is Send, ownership of a T can safely move to another thread; if T is Sync, several threads can safely hold &T at the same time. Both are auto traits, so a struct whose fields are all Send is automatically Send as well. Most types satisfy both, but a few are deliberately left out. Rc<T> updates its reference count with ordinary, non-atomic integer operations, so two threads cloning or dropping at once could corrupt the count and cause a double free or a leak. That is why Rc is neither Send nor Sync, and trying to send an Rc to a thread here gave error[E0277]: `Rc<i32>` cannot be sent between threads safely. Arc<T>, which does the same job with atomic operations, is both Send and Sync when T is, so it can be shared between threads. It is the same 8-byte pointer as Rc and costs only a little more for the atomic operations. RefCell<T> counts borrows non-atomically, so it can be moved to another thread (Send) but not shared (not Sync). Mutex<T> protects its data with a lock, so it is Sync as long as T is Send. thread::spawn requires the closure it receives to be Send and 'static, so any sharing that breaks these rules is filtered out by type checking. As a result, a program with a data race simply does not compile in safe Rust, which the Rust community calls "fearless concurrency." You can mark a type yourself with unsafe impl Send, but then proving its safety is up to you.</sub> |

Rust 매크로는 텍스트가 아니라 이미 토큰으로 나뉜 트리를 다루므로 괄호가 어긋나거나 연산자 우선순위가 뒤틀리는 전처리기 버그가 없어요. 또 위생적이라서, 매크로 안에서 만든 변수는 호출한 쪽에 같은 이름의 변수가 있어도 섞이지 않아요. 펼쳐진 결과는 보통 코드처럼 타입 검사와 빌림 검사를 받아요. 절차적 매크로는 더 강력해요. 컴파일러가 코드의 토큰 흐름을 별도 크레이트의 Rust 함수에 넘기면, 그 함수가 원하는 대로 분석해 새 코드를 돌려줘요. #[derive(Debug, Clone)]처럼 구조체에 트레이트 구현을 자동으로 만들어 주는 derive 매크로, #[tokio::main]처럼 함수를 감싸는 속성 매크로, sqlx::query!처럼 함수처럼 부르는 매크로가 있어요. serde의 직렬화도 이렇게 만들어져요. 대가는 컴파일 시간과 읽기 어려움이에요. cargo expand로 펼친 결과를 볼 수 있고, 함수나 제네릭으로 충분한 일에는 매크로를 쓰지 않는 것이 좋아요.<br><sub>Rust macros are recognized by the exclamation mark after their name, and the everyday println!, vec!, format! and assert\_eq! are all macros. They are macros rather than functions because they do things functions cannot. println! takes no fixed number of arguments and checks at compile time that the format string matches the number and types of its arguments. A declarative macro built with macro\_rules! matches the code fragment it is called with against patterns of fragment specifiers such as $x:expr, $name:ident and $t:ty, and generates new code in place from the body of the first matching rule. $($rest:expr),+ is a pattern for one or more comma-separated expressions, so one macro can accept any number of arguments. In the example, maxm!(3, 9, 4) matches the second rule and expands to max(3, maxm!(9, 4)), then to max(3, max(9, maxm!(4))), and ends with the first rule. The test here produced 9. Two things set it far apart from C’s #define. Rust macros work on trees of tokens rather than text, so there are no preprocessor bugs from mismatched parentheses or twisted operator precedence. They are also hygienic, so a variable created inside a macro never mixes with a same-named variable at the call site. The expansion is type-checked and borrow-checked like ordinary code. Procedural macros are more powerful. The compiler hands the code’s token stream to a Rust function in a separate crate, which analyzes it however it likes and returns new code. There are derive macros such as #[derive(Debug, Clone)] that generate trait implementations for a struct, attribute macros such as #[tokio::main] that wrap a function, and function-like macros such as sqlx::query!. serde’s serialization is built this way. The costs are compile time and readability. cargo expand shows the expanded result, and macros are best avoided where a function or generics will do.</sub> |

| **반복자**<br><sub>Iterators</sub> | map, filter 같은 어댑터는 계획만 세우는 지연 값이고, collect나 for 같은 소비자가 당길 때 원소가 하나씩 흘러가요. 반복자 체인은 손으로 쓴 루프만큼 빨랐어요.<br><sub>Adapters such as map and filter are lazy values that only build a plan, and elements flow through one at a time when a consumer such as collect or for pulls them. Iterator 트레이트는 다음 원소를 Option으로 돌려주는 next() 하나만 구현하면 되고, 그러면 map, filter, zip, enumerate, take, skip, fold, sum 같은 수십 개의 메서드가 기본 구현으로 따라와요. 핵심은 지연 평가예요. v.iter().map(\|x\| x \* 2)는 아무것도 계산하지 않고, 원래 반복자와 클로저를 담은 Map이라는 값을 돌려줄 뿐이에요. 이 환경에서 map의 클로저 안에 println을 넣고 반복자를 만들기만 했을 때는 한 줄도 찍히지 않았어요. 실제 계산은 collect, sum, count, for 반복문처럼 값을 소비하는 쪽이 next()를 부를 때 일어나고, 원소는 체인 전체를 하나씩 통과해요. 출력도 created가 먼저 찍히고 그다음 map 1, map 2, map 3, 마지막에 [2, 4, 6]이 나왔어요. 단계마다 중간 Vec을 만들지 않으므로 메모리를 아끼고, 필요한 만큼만 당기므로 (1..) 같은 무한 범위도 다룰 수 있어요. The Iterator trait requires only next(), which returns the next element as an Option, and in return dozens of methods such as map, filter, zip, enumerate, take, skip, fold and sum come with default implementations. The key is lazy evaluation. v.iter().map(\|x\| x \* 2) computes nothing; it merely returns a value called Map holding the original iterator and the closure. Here, with a println inside the map closure, merely creating the iterator printed nothing at all. The actual computation happens when a consumer such as collect, sum, count or a for loop calls next(), and each element passes through the whole chain one at a time. The output printed created first, then map 1, map 2, map 3 and finally [2, 4, 6]. No intermediate Vec is built at each stage, which saves memory, and since only as much as needed is pulled, even infinite ranges such as (1..) can be used. (1..).filter(\|n\| n % 7 == 0).take(3) stopped at [7, 14, 21], and (1..).map(\|x\| x \* x).find(\|&y\| y > 50) stopped the moment it found 64, calling the closure exactly 8 times. There are three ways to iterate: iter() yields &T, iter\_mut() yields &mut T, and into\_iter() yields T itself, consuming the collection. Performance makes iterators a prime example of a zero-cost abstraction. The compiler inlines the adapters and closures into a single loop, so over 20 million elements a filter, map and sum chain took 44 ms and an index loop doing the same took 44 ms (--release). Iterators cannot run out of range, so they need no index bounds checks and avoid mistakes such as off-by-one errors. That is why iterator chains are more idiomatic in Rust than index loops, and clippy recommends replacing loops that only index with iterators. When data parallelism is needed, the rayon crate’s par\_iter() runs the same chain on several cores.</sub> |
| **클로저와 Fn 트레이트**<br><sub>Closures and the Fn traits</sub> | 클로저는 캡처를 어떻게 쓰느냐에 따라 Fn, FnMut, FnOnce 중 하나가 돼요. 캡처한 값만 담은 익명 구조체라서 크기도 캡처에 따라 0바이트부터 달라졌어요.<br><sub>A closure becomes Fn, FnMut or FnOnce depending on how it uses its captures. It is an anonymous struct holding only what it captured, so its size, starting from 0 bytes, varied with the captures.</sub> | 클로저는 주변 변수를 캡처할 수 있는 익명 함수예요. Rust에서 클로저는 컴파일러가 만드는 익명 구조체로, 캡처한 변수를 필드로 갖고 호출 연산자를 구현해요. 캡처한 변수를 어떻게 쓰는지에 따라 세 가지 트레이트 중 무엇을 구현할지가 자동으로 정해져요. 값을 읽기만 하면 &T로 빌려 Fn이 되고 몇 번이든 동시에 불러도 안전해요. 값을 바꾸면 &mut T로 빌려 FnMut이 되고 한 번에 한 곳에서만 부를 수 있어요. 캡처한 값을 소비하면, 예를 들어 drop하거나 다른 곳으로 이동시키면 FnOnce가 되어 한 번만 부를 수 있어요. 이 세 트레이트는 포함 관계라서 Fn인 클로저는 FnMut과 FnOnce를 받는 곳에도 넘길 수 있어요. 함수는 받을 클로저의 종류를 이 트레이트로 적고, 컴파일러가 맞는지 검사해요. 이 환경에서 Fn을 받는 함수에 n += 1처럼 값을 바꾸는 클로저를 넘기자 error[E0594]: cannot assign to `n`, as it is a captured variable in a `Fn` closure가 나며 매개변수를 FnMut로 바꾸라는 도움말이 붙었어요. move \|\| drop(name)은 name을 소비하므로 FnOnce인데, 두 번 부르자 error[E0382]: use of moved value: `eat`와 closure cannot be invoked more than once라는 설명이 나왔어요. move 키워드는 캡처를 빌림 대신 소유로 바꿀 뿐이고, 어떤 트레이트인지는 본문이 정해요. 그래서 move 클로저도 값을 읽기만 하면 Fn이에요. 크기도 캡처가 정해요. 이 환경에서 아무것도 캡처하지 않은 클로저는 0바이트, &name 하나를 빌린 클로저는 8바이트, 두 변수를 빌린 클로저는 16바이트, String을 move한 클로저는 24바이트, i32를 move한 adder는 4바이트였어요. 클로저를 받는 방식은 두 가지예요. impl Fn이나 제네릭으로 받으면 클로저마다 코드가 따로 만들어져 호출이 인라인되고, Box<dyn Fn>으로 받으면 서로 다른 클로저를 한 타입으로 담을 수 있는 대신 vtable을 거쳐 호출해요. Box<dyn Fn>은 데이터 포인터와 vtable 포인터로 된 16바이트 팻 포인터였어요.<br><sub>A closure is an anonymous function that can capture surrounding variables. In Rust, a closure is an anonymous struct generated by the compiler, with the captured variables as fields and an implementation of the call operator. How it uses its captured variables automatically decides which of three traits it implements. If it only reads them, it borrows &T and is Fn, safe to call any number of times, even concurrently. If it changes them, it borrows &mut T and is FnMut, callable from only one place at a time. If it consumes a captured value, for example by dropping it or moving it elsewhere, it is FnOnce and can be called only once. The three traits nest, so an Fn closure can also be passed where FnMut or FnOnce is expected. Functions state the kind of closure they accept with these traits, and the compiler checks the match. Here, passing a mutating closure such as n += 1 to a function that takes Fn produced error[E0594]: cannot assign to `n`, as it is a captured variable in a `Fn` closure, with a hint to change the parameter to FnMut. move \|\| drop(name) consumes name, so it is FnOnce, and calling it twice produced error[E0382]: use of moved value: `eat` with the explanation closure cannot be invoked more than once. The move keyword only switches captures from borrowing to owning, while the body decides the trait, so a move closure that only reads is still Fn. The captures also decide the size. Here a closure capturing nothing was 0 bytes, one borrowing &name 8 bytes, one borrowing two variables 16 bytes, one moving a String 24 bytes, and the adder moving an i32 4 bytes. There are two ways to accept a closure. Taking impl Fn or a generic generates separate code per closure so calls inline, while taking Box<dyn Fn> can hold different closures as one type but calls through a vtable. The Box<dyn Fn> was a 16-byte fat pointer made of a data pointer and a vtable pointer.</sub> |
| **실전 오류 처리**<br><sub>Error handling in practice</sub> | 라이브러리는 thiserror로 구별 가능한 오류 enum을 만들고, 애플리케이션은 anyhow로 어떤 오류든 담아 context로 설명을 쌓아요. ?는 From으로 오류를 변환해 줘요.<br><sub>Libraries build distinguishable error enums with thiserror, while applications hold any error in anyhow and stack messages with context. ? converts errors through From.</sub> | Rust의 오류는 Result 값이고, ? 연산자가 Err를 만나면 함수에서 바로 돌려줘요. 실제 프로젝트에서는 여러 출처의 오류를 어떤 타입으로 모을지가 문제인데, 흔히 두 크레이트를 함께 써요. 라이브러리는 호출자가 실패 종류에 따라 다르게 대응할 수 있도록 오류를 enum으로 정의해요. 이때 Display와 std::error::Error를 손으로 구현하는 대신 thiserror의 derive를 쓰면, 각 변형에 붙인 #[error("bad port: {0}")] 같은 문구로 Display가 만들어지고 Error 트레이트도 구현돼요. 이 환경에서 Missing 변형은 missing key `port`로, BadPort는 bad port: invalid digit found in string으로 찍혔어요. 변형의 필드에 #[from]을 붙이면 ParseIntError를 ConfigError로 바꾸는 From 구현이 생겨요. ? 연산자는 Err를 돌려줄 때 From으로 변환하므로, s.parse::<u16>()?만 써도 파싱 오류가 자동으로 BadPort가 돼요. 호출자는 match로 Err(ConfigError::BadPort(e))를 골라 처리할 수 있고, 이 환경에서는 99999를 넣자 number too large to fit in target type을 담은 BadPort가 잡혔어요. 애플리케이션은 대개 오류의 종류보다 무슨 일을 하다가 실패했는지가 중요해요. anyhow::Error는 Error를 구현한 어떤 오류든 담는 8바이트 포인터라서 함수마다 anyhow::Result<T>를 돌려주면 되고, with\_context로 원인 위에 사람이 읽을 설명을 쌓을 수 있어요. 없는 파일을 읽자 Error: reading config.toml, 그 아래 Caused by: No such file or directory (os error 2)가 찍혀서 무엇을 하다 왜 실패했는지가 함께 보였어요. main이 anyhow::Result<()>를 돌려주면 Err일 때 이 메시지를 출력하고 종료 코드 1로 끝나요. RUST\_BACKTRACE를 켜면 오류가 생긴 위치의 백트레이스도 붙어요. 선택 기준은 호출자예요. 호출자가 실패 종류를 구별해 다르게 행동해야 하면 thiserror로 만든 enum을, 로그에 남기거나 사용자에게 보여 주기만 하면 anyhow를 써요. 그래서 라이브러리 크레이트는 thiserror, 실행 파일은 anyhow를 쓰는 조합이 흔해요. 공개 API에 anyhow::Error를 노출하면 호출자가 오류를 구별할 수 없으므로 라이브러리에서는 피해요.<br><sub>Errors in Rust are Result values, and the ? operator returns from the function at once when it meets an Err. In real projects, the question is which type gathers errors from many sources, and two crates are commonly used together. Libraries define their errors as an enum so callers can respond differently by kind of failure. Instead of implementing Display and std::error::Error by hand, thiserror’s derive builds Display from text such as #[error("bad port: {0}")] on each variant and implements the Error trait. Here the Missing variant printed as missing key `port` and BadPort as bad port: invalid digit found in string. Putting #[from] on a variant’s field generates a From implementation converting ParseIntError into ConfigError. Because the ? operator converts through From when returning an Err, writing just s.parse::<u16>()? turns a parse error into BadPort automatically. Callers can pick it out with match on Err(ConfigError::BadPort(e)), and here passing 99999 was caught as a BadPort holding number too large to fit in target type. Applications usually care less about the kind of error than about what was being done when it failed. anyhow::Error is an 8-byte pointer holding any error that implements Error, so each function can simply return anyhow::Result<T>, and with\_context stacks a human-readable message on top of the cause. Reading a missing file printed Error: reading config.toml followed by Caused by: No such file or directory (os error 2), showing both what was being done and why it failed. When main returns anyhow::Result<()>, an Err prints this message and the process exits with code 1. Turning on RUST\_BACKTRACE also attaches a backtrace of where the error arose. The deciding factor is the caller. When callers must tell kinds of failure apart and act differently, use an enum built with thiserror, and when they only log it or show it to a user, use anyhow. That is why library crates with thiserror and executables with anyhow is a common combination. Exposing anyhow::Error in a public API leaves callers unable to distinguish errors, so libraries avoid it.</sub> |
| **panic과 되감기**<br><sub>Panics and unwinding</sub> | 예상할 수 있는 실패는 Result, 버그는 panic이에요. panic은 기본으로 스택을 되감으며 Drop을 실행하고 종료 코드 101로 끝났고, panic = "abort"에서는 정리 없이 134로 끝났어요.<br><sub>Expected failures are Results and bugs are panics. A panic unwinds the stack by default, running Drop and ending with exit code 101, while panic = "abort" ended with 134 and no cleanup.</sub> | Rust는 실패를 두 종류로 나눠요. 파일이 없거나, 네트워크가 끊기거나, 사용자 입력이 잘못된 것처럼 정상적인 실행 중에도 일어날 수 있는 실패는 Result로 돌려줘서 호출자가 처리하게 해요. 반대로 배열 범위를 넘거나, 절대 깨지면 안 되는 불변 조건이 깨진 것처럼 프로그램 자체의 버그는 panic으로 즉시 멈춰요. panic은 다른 언어의 예외처럼 흐름 제어에 쓰지 않고, 계속 실행하면 더 위험한 상태를 알리는 장치예요. unwrap()과 expect()도 None이나 Err이면 panic을 내므로, 테스트나 실패할 수 없음이 확실한 곳에서만 쓰고 라이브러리 코드는 Result를 돌려줘요. 이 환경에서 길이 3인 Vec에 인덱스 10으로 접근하자, C처럼 옆 메모리를 조용히 읽는 대신 index out of bounds: the len is 3 but the index is 10이라는 메시지와 파일과 줄 위치를 찍고 panic이 났어요. 그래서 안전한 Rust에서는 범위 밖 접근이 정의되지 않은 동작이나 보안 취약점으로 이어지지 않아요. panic의 기본 동작은 되감기예요. panic이 난 지점부터 스택을 거꾸로 올라가며 각 지역 변수의 Drop을 실행해서 파일을 닫고, 잠금을 풀고, 메모리를 돌려줘요. 이 환경에서도 Drop을 구현한 guard 변수의 drop guard가 찍힌 뒤 프로세스가 종료 코드 101로 끝났어요. 다른 스레드에서 난 panic은 그 스레드만 끝내고 join이 Err를 돌려주며, std::panic::catch\_unwind로 되감기를 잡을 수도 있어서 C와의 경계나 스레드 풀이 panic 하나로 전체가 무너지지 않게 할 때 써요. Mutex를 잡은 채 panic이 나면 그 Mutex는 오염 상태가 되어 다음 lock()이 Err를 돌려줘요. Cargo.toml의 프로필에 panic = "abort"를 두면 되감지 않고 즉시 프로세스를 끝내요. 이 환경에서 같은 코드가 Drop을 실행하지 않고 SIGABRT로 종료 코드 134를 냈어요. 되감기용 코드와 표가 빠져 실행 파일이 조금 작아지고 빨라질 수 있지만, 정리와 catch\_unwind를 포기하는 선택이라 임베디드나 크기에 민감한 환경, 또는 panic 후 즉시 재시작하는 서비스에서 써요.<br><sub>Rust splits failures into two kinds. Failures that can happen even in normal operation, such as a missing file, a dropped network connection or bad user input, are returned as Result for the caller to handle. Bugs in the program itself, such as indexing past an array or breaking an invariant that must never break, stop immediately with a panic. A panic is not used for control flow like exceptions in other languages; it signals that continuing would be more dangerous. unwrap() and expect() also panic on None or Err, so they are used only in tests or where failure is certain to be impossible, and library code returns Result. Here, accessing a length-3 Vec at index 10 did not silently read neighboring memory as C would; it panicked, printing the message index out of bounds: the len is 3 but the index is 10 along with the file and line. So in safe Rust, out-of-bounds access never turns into undefined behavior or a security hole. The default behavior of a panic is unwinding. Starting at the panic, the stack is walked backward, running each local variable’s Drop to close files, release locks and return memory. Here too, drop guard from a guard variable implementing Drop was printed before the process ended with exit code 101. A panic in another thread ends only that thread and makes join return Err, and std::panic::catch\_unwind can catch the unwinding, which is used at boundaries with C or to keep a thread pool from collapsing over one panic. If a panic happens while a Mutex is held, that Mutex becomes poisoned and the next lock() returns Err. Putting panic = "abort" in a Cargo.toml profile ends the process immediately without unwinding. Here the same code exited via SIGABRT with code 134 without running Drop. Dropping the unwinding code and tables can make the executable slightly smaller and faster, but it gives up cleanup and catch\_unwind, so it is chosen for embedded or size-sensitive environments, or for services that restart right after a panic.</sub> |
| **성능 다루기**<br><sub>Tuning performance</sub> | 경계 검사는 대개 거의 공짜였고, 미리 할당하기와 release 프로필 설정, target-cpu가 더 큰 차이를 냈어요. 무엇보다 고치기 전에 측정해요.<br><sub>Bounds checks were usually nearly free, while preallocation, release profile settings and target-cpu made larger differences. Above all, measure before fixing.</sub> | Rust 코드의 성능을 다룰 때 첫 규칙은 항상 --release로 빌드하고, 고치기 전에 측정하는 거예요. perf나 cargo flamegraph로 시간이 어디에 쓰이는지 보고, criterion으로 변경 전후를 통계적으로 비교해요. 흔한 걱정은 경계 검사예요. 안전한 Rust는 a[i]마다 범위를 검사하지만, 실제로는 대개 거의 공짜예요. 이 환경에서 2천만 원소의 a[i] \* b[i] 인덱스 루프와 zip 반복자가 모두 16ms였고, 어셈블리를 보니 LLVM이 루프 앞에서 길이를 한 번 확인한 뒤 SIMD 명령으로 벡터화하고, 범위를 넘는 경우만 끝에서 따로 처리했어요. 컴파일러가 증명할 수 없는 임의 인덱스로 읽는 경우에도 검사 있는 버전 20ms, unsafe get\_unchecked 20ms로 차이가 거의 없었어요. 분기 예측이 항상 맞기 때문이에요. 그래서 get\_unchecked는 측정으로 효과가 확인된 곳에만 써요. 더 큰 차이는 보통 할당과 메모리 접근에서 나와요. Vec::new()에서 시작해 push하면 용량이 찰 때마다 더 큰 버퍼를 할당하고 원소를 복사해요. 이 환경에서 2천만 번 push가 49ms, Vec::with\_capacity로 미리 잡으면 42ms였어요. 반복문 안에서 String이나 Vec을 매번 새로 만들지 말고 clear()로 재사용하는 것도 같은 원리예요. release 프로필은 더 조일 수 있어요. lto = true는 링크할 때 크레이트 경계를 넘어 인라인하고 최적화하며, codegen-units = 1은 크레이트를 여러 조각으로 나눠 병렬 컴파일하는 대신 한 덩어리로 최적화해요. 이 환경에서 실행 파일이 456KB에서 392KB로 줄었고, strip = true와 panic = "abort"까지 더하면 318KB였어요. 대신 빌드 시간이 늘어요. 마지막은 대상 CPU예요. 기본 x86-64 빌드는 모든 x86-64 CPU에서 돌아가도록 오래된 SSE2 명령까지만 써요. RUSTFLAGS="-C target-cpu=native"로 이 CPU의 AVX2와 AVX-512를 허용하자, 캐시에 들어가는 4,096개 원소의 곱셈 합을 10만 번 반복하는 계산이 88ms에서 26ms로 3.4배 빨라졌어요. 하지만 그 명령이 없는 CPU에서는 실행 파일이 아예 돌지 않으므로, 배포용으로는 x86-64-v3처럼 대상 수준을 명시하거나 실행 중에 CPU 기능을 확인해 경로를 고르는 방법을 써요.<br><sub>The first rules for Rust performance are to always build with --release and to measure before fixing anything. perf or cargo flamegraph shows where the time goes, and criterion compares before and after statistically. A common worry is bounds checks. Safe Rust checks the range on every a[i], but in practice this is usually nearly free. Here an a[i] \* b[i] index loop and a zip iterator over 20 million elements both took 16 ms, and the assembly showed LLVM checking the length once before the loop, vectorizing with SIMD instructions and handling only the out-of-range case separately at the end. Even reads at random indices, which the compiler cannot prove safe, took 20 ms with checks versus 20 ms with unsafe get\_unchecked, because the branch predictor is always right. So get\_unchecked is used only where measurement confirms a benefit. Bigger differences usually come from allocation and memory access. Pushing onto a Vec started with Vec::new() allocates a bigger buffer and copies the elements every time capacity runs out. Here 20 million pushes took 49 ms, and 42 ms with Vec::with\_capacity reserving up front. Reusing a String or Vec with clear() instead of creating a new one on every loop iteration follows the same principle. The release profile can be tightened further. lto = true inlines and optimizes across crate boundaries at link time, and codegen-units = 1 optimizes each crate as one unit instead of splitting it into pieces compiled in parallel. Here the executable shrank from 456 KB to 392 KB, and to 318 KB with strip = true and panic = "abort" added, at the cost of longer builds. The last lever is the target CPU. The default x86-64 build uses instructions only up to the older SSE2 so it runs on every x86-64 CPU. Allowing this CPU’s AVX2 and AVX-512 with RUSTFLAGS="-C target-cpu=native" made a computation repeating a multiply-sum over 4,096 cache-resident elements 100,000 times go from 88 ms to 26 ms, 3.4× faster. But the executable will not run at all on CPUs lacking those instructions, so distributed builds either name a target level such as x86-64-v3 or check CPU features at run time to choose a code path.</sub> |
